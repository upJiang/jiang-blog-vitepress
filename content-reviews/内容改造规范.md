# 小江AI 博客全站内容改造规范

> 本文档定位：全站 371 篇文章重写时的裁决标准和写作基准。它不是发布内容，不进入站点构建（已由 `config.ts` 的 `srcExclude` 排除），只作为仓库内的工作规范存档。
>
> 适用范围：前端、后端、SEO 三个栏目的重写；AI 与 Agent、AI Infra、AI 实践三个栏目已达标，作为全站质量基准，不重写。算法与重学前端锁定不动。

---

## 一、首先要认清的问题：内容质量是分化的，不是全部 AI 味

在动手之前，先接受一个反直觉的事实：**你抱怨的"一看就是 AI 写的、学不到东西"，只发生在前端、后端、SEO 三个栏目。AI 与 Agent 那 98 篇其实已经是你想要的样子。**

用门禁脚本的真实口径（剥掉代码、表格、URL、markdown 符号后数纯中文字符）实测：

| 栏目 | 篇数 | 代表文章纯中文字数 | 真实状态 |
| --- | --- | --- | --- |
| AI 与 Agent | 98 | 6000～6500 | 深度、推演、真实源码台账都已达标，是**全站标杆** |
| AI Infra | 38 | 平均 2.6 万 | 达标 |
| AI 实践 | 11 | 平均 2.1 万 | 达标 |
| **前端** | 68 | 多数 1000～2000 | **痛点**：概念三段带过、标题像目录 |
| **后端** | 69 | 多数 2000～2700 | **痛点**：缺递进主线、缺深度 |
| **SEO** | 26 | 多数 2000～2300 | **痛点**：结构好但空、缺实证 |

三个短栏目共 163 篇，占全站近一半。这就是读者感觉"学不到东西"的来源。

**结论：改造不是推倒重来，而是把 AI 与 Agent 栏目已经跑通的"写作方法 + 深度门禁"，复制到另三个栏目。**

## 二、门禁为什么"没作用"：约束押错了对象

现有门禁分三层：

1. **`ai-agent:check`（最强）**：仅对 AI 与 Agent 生效。6000 纯正文、完整推演链、来源台账覆盖键、tp-knowledge 源码路径 + 测试路径存在性核对、跨文章同构句、H2 数量、标题复述次数。
2. **`content:check`（通用）**：所有栏目，但只查 frontmatter 与清单一致、围栏闭合、H1 唯一、无"参考资料/本文产物/开始前可以了解"模板残留、内部链接不失效。
3. **`content:quality`**：结构 + 跨文章重复长段落 + 内容锁（只锁算法和重学前端）。

关键事实：**前端、后端、SEO 没有任何"论证深度"或"最少展开"约束**。一篇 1000 字、三段带过一个概念的 Post，门禁是绿的。

**门禁本身是好的，只是适用范围太窄。** 改造方向是：把 ai-agent 里"证明有效"的深度约束抽象成可复用脚本，参数化作用于前端/后端/SEO，而不是再写一堆只看格式的新规则。

## 三、四个参考资料各贡献什么

不要混淆这四份材料的用途，混用会走弯路：

| 参考 | 它给什么 | 别误用它 |
| --- | --- | --- |
| **hello-agents** | 「入门到进阶」的**递进主线骨架**：从一次最小调用 → 循环 → 工具 → 记忆 → 多 Agent → 生产 | 别照搬它的内容；你已有更深的素材 |
| **tp-knowledge** | **深度与证据标准**：一个概念在真实系统里怎么落地、怎么失败、怎么写测试 | 别泄露私有路径/接口/表结构/提示词到公开文章 |
| **interview-project** | 前端**真实技术问题**（手写、源码原理、HTTP、缓存等） | 它本身是 Demo 级浅度，取其问题不取其浅 |
| **seoOpt-chrome-plugin** | SEO **可复现实证**：匿名 GET、HTML 源码、渲染 DOM、Schema 校验的真实证据 | 别只截图凑数，要文字说清证据能证明什么、不能证明什么 |

**一句话**：hello-agents 给骨架，tp-knowledge 给深度和证据标准，interview-project/seoOpt 给前端和 SEO 的具体问题。三者拼起来，就是你想要的"自然、有深度、能迁移"。

## 四、什么算"有深度"：不设字数门槛，设论证门槛

用户已明确：**不设统一硬字数门槛**。这是对的，也和 AGENTS.md 原则一致（"概念解释到什么程度，取决它在论证中的重要性"）。

取代字数的，是下面这条**可验证的论证深度标准**。每篇重写后的文章，必须同时满足：

### 4.1 一条完整推演链（硬性，每条都要能指出来）

沿「**输入 → 状态变化 → 调用顺序 → 输出 → 失败证据 → 验证结果**」至少走通一次。换句话说，文章里必须有一个地方，读者能跟着一个具体输入，看到它怎么一步步变成可验证的结果，以及在某个环节失败时会怎样。

例（前端请求客户端）：输入是"用户连续点了两次提交"，状态变化是"第一次请求 pending，第二次进入去重"，调用顺序是"transport → protocol → validation → domain result"，输出是"只有一次写操作到达服务端"，失败证据是"超时后盲目重试产生两单"，验证是"断言 write 只调用了一次"。

### 4.2 问题式标题，不是目录式标题

标题要承诺一个"读者会遇到的真实问题"或"要解释的机制"，不要罗列技术名词。

| 目录式（现在的坏标题） | 问题式（要改成的方向） |
| --- | --- |
| `typescript-decorators-metadata`（纯名词） | 你已有好范式：`TS 装饰器、初始化顺序与元数据边界` |
| `mysql-crud-parameter-binding` | 你已有好范式：`MySQL 类型、约束、主键与索引键` |
| `component-library-design-system`（太宽泛） | 从 Button 契约扩展到 Token 与版本（点出具体场景） |

判断标准：**去掉技术名词后，标题能否复述"问题、机制、实现、验证、边界"中的至少前两个。** 能，就是好标题；只能复述名词，就是目录。

### 4.3 概念展开到什么程度，由它在论证中的重要性决定

不是每个概念都要独立成节。一个概念如果只是背景，一两句带过即可；如果它是后面结论成立的前提，就展开讲机制、位置、处理过程、使用和验证。

禁止"定义、输入、输出、验证、边界"这种机械五件套铺满每个概念。

## 五、去 AI 味：不是删词，是让每篇有"证据"和"判断"

AI 味的根源不是某个词，而是**没有具体材料支撑的空转论证**。只要每篇都绑真实源码、真实运行、真实失败，AI 味自然消失。这是治本，比加更多 prompt 规则有效。

具体落地三件事（可直接执行）：

### 5.1 每篇绑定可核对材料，而不是"可能""通常""一般"

- 前端/后端：一段**可运行代码**（能 `node` 或 `pnpm` 跑），或一个源码级事实（如 React 的 Render/Commit 分阶段、Vue 的 effect 依赖清理）。
- SEO：seoOpt 插件**真实跑一次**产生的证据（匿名 GET 的原始响应、HTML 里的 Canonical、渲染后 DOM、Schema 校验结果）。
- 没材料支撑的判断，明确标记为"设计建议"或"待验证"，不写成已确认事实。

### 5.2 允许有明确判断，禁止编造

作者可以下判断（"这个场景用工作流就够了，不需要 Agent"），但数字、事故、性能、准确率、上线结果、个人经历一律不编。

### 5.3 完稿后用两个工具扫一遍

- `article-write`（尤其 `write-zh-prose.md` 和 `write-zh.md`）：扫段末总结句、升华句、翻案腔、讲解腔、空泛形容词、破折号。
- `humanizer-zh`：扫宣传语、三段式、否定式排比、模糊归因、AI 高频词、过度粗体。

扫完按"改动越少越好"的原则处理，自然、清晰、稳定的句子不动。

## 六、分栏目改造策略

### 6.1 AI 与 Agent（98 篇）——不动，作为标杆

已达标。个别残留同构句用 `humanizer-zh` 扫一遍即可，不值得重写。**它的质量就是你后面所有栏目的"天花板参照"。**

### 6.2 AI Infra / AI 实践 ——不动

篇幅和深度都够，不是痛点。

### 6.3 前端（68 篇）——最优先重写

**问题**：篇幅断崖（多数 1000～2000 字）、缺论证主线、标题像目录。

**动作**：
1. 建递进主线（对齐 hello-agents 范式）：`语言与运行时 → TS 类型系统 → 框架原理(React/Vue 双线) → 构建工具 → 工程体系(测试/性能/安全/观测) → 跨端与插件`。
2. 现有 `content.ts` 已有 `stageKey` 分组，但分组之间无 `dependsOn` 承接，补依赖关系。
3. 每篇按第四节标准重写：要有一条完整推演链 + 可运行代码 + 问题式标题。
4. React 的 8 篇（Fiber/Work Loop/Lanes/Render/Commit/RenderCommit/Reconciliation/Hooks）主题重叠，重写时补全互相引用、删除重复，而不是各写各的。

### 6.4 后端（69 篇）——优先主线，再逐篇

**问题**：比前端稍深，但重写时要先解决"没有递进主线"。

**动作**：
1. 把 `backend-learning-roadmap.md` 变成真正的主线骨架（像 ai-agent 的 12 阶段），68 篇挂上去、补 `dependsOn`。
2. 重点补"两个请求同时改同一行数据"级别的问题式标题（`transaction-acid-isolation-mvcc` 已是好范式），而不是 `mysql-crud-parameter-binding` 这类目录标题。
3. 已有代码示例要确保可运行（Node/NestJS、Python/FastAPI、Go/Gin 三线并行，这是你的特点，保留）。

### 6.5 SEO（26 篇）——最接近可直接对齐，优先用实证

**问题**：标题和结构其实不错（证据、边界、验证意识都在），只是篇幅短、缺实例。是三个短栏目里最容易救的。

**动作**：
1. 每篇把 seoOpt 插件真实跑一遍，把产生的证据（响应、HTML、DOM、Schema）嵌进去，一篇自然从 2000 字到 6000+，且可复现。
2. 保持已有的"证据等级、检测边界、不把分数当排名"这个高度，别为了凑字数加空话。

## 七、门禁怎么调整（配合改造）

改造不是删门禁，是把深度约束泛化。建议新增一个 `check-deep-content.ts`，参数化：

- **栏目白名单**：前端、后端、SEO（ai-agent 已有专门脚本）。
- **深度校验**：每篇必须命中「完整推演链」的六个要素（输入/状态/调用/输出/失败/验证），正则可复用 `hasCompleteWalkthrough`。
- **标题校验**：标题不能是纯技术名词罗列（可设一个启发式：标题去掉中英技术名词后，是否仍含"问题/机制/边界/验证"等语义动词）。
- **材料校验**：代码块必须有语言标记且语言一致（已有）；可选地要求前端/后端文章含至少一个可运行代码块或源码级引用。

**不设字数门槛**，与用户决定一致。

注意：现有 `ai-agent:check` 那套"来源台账 + tp-knowledge 源码/测试路径核对"很重，前端/后端是否照搬需要权衡。前端/后端的"证据"更多是官方文档、规范、可运行代码，不是 tp-knowledge 私有源码，所以证据模型要更轻，不要为了对齐而伪造一套私有台账。

## 八、落地顺序（建议）

1. **先定基准**：把本规范定稿，作为唯一裁判。
2. **修门禁**：写 `check-deep-content.ts`，让前端/后端/SEO 也有深度校验（可先只对前端生效）。
3. **写 3 篇样板**：前端、后端、SEO 各挑一篇最差的，按新标准重写成"新榜样"。这三篇出来，后面 160 篇就有了可对照的实物。
4. **前端全量重写**（你本职、痛点最集中）。
5. **后端** → **SEO** 跟进，各维护一条递进主线。

每篇重写完，跑 `content:check` + `content:quality` + 新的 `deep:check` + `article-write` + `humanizer-zh` 五道关口，再手动从「初学者」和「资深工程师」两个角度各读一遍，验证主题讲清、论证连续、示例可信、语言自然。

## 九、红线（写任何一篇时都要遵守）

1. 私有项目（tp-knowledge、seoOpt、interview-project）只能作为只读取证，公开文章**不得出现项目名、本机路径、内部接口、表结构、真实数据、提示词、截图、凭证**。
2. 不编造事故、性能数字、用户规模、准确率、上线结果、个人经历。
3. Fake Adapter / 脚本化模型 / 内存仓库只能在正文明确标记为测试替身，不能当成真实 API、持久化或供应商行为的证明。
4. 配置示例必须说明哪些值要替换；严格 JSON 不写注释，带注释用 `jsonc`。
5. 重要结论用粗体强调，只加粗真正要记住的短语或短句，禁止整段加粗、机械段首加粗、高密度强调。
6. 不执行 `git add` / `commit` / `push`，不动自动部署配置。
