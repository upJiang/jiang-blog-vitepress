### Git 生成 hash 是根据什么

Git 生成 commit ID 依赖以下因素：

1. **文件快照内容**（保留不变）
2. **提交者信息**（可能变化）
3. **提交时间戳**（变为新时间）
4. **父 commit ID**（指向当前分支）

### Cherry-pick 中 pick 的 commit 是一样的吗

不一样

此时：

- 代码改动完全相同
- 新 commit 的父节点变为 dev 分支最新提交
- 时间戳更新为 cherry-pick 操作时间

### Rebase 跟 Reset 、merge 的区别

Rebase 通常用于整理提交历史，将一个分支的提交转移到另一个分
支上，并重写提交历史。而 Reset 则是用来移动 HEAD 指针，重置
当前分支的状态到某个特定的提交，可能影响工作目录和暂存区。

|          |                            |                               |
| -------- | -------------------------- | ----------------------------- |
|          | git rebase                 | git reset                     |
| 核心目标 | 整理提交历史（时间线改写） | 撤销/回退到指定状态（时光机） |
| 操作对象 | 分支间的提交关系           | 当前分支的 HEAD 指针位置      |
| 历史影响 | 创建新提交（改写历史）     | 直接移动指针（可能丢弃提交）  |
| 协作风险 | 高（需强制推送）           | 低（通常用于本地）            |

- _需要保留分支轨迹时选 Merge_（如版本发布记录）
- _需要整洁历史时选 Rebase_（如功能开发分支）

⚠️ **永远不要对已推送到远程的公共分支使用 rebase**（会导致协
作成员的历史混乱）

|            |                    |                              |
| ---------- | ------------------ | ---------------------------- |
| 对比维度   | Merge              | Rebase                       |
| 提交历史   | 保留分叉结构       | 生成线性历史                 |
| Commit ID  | 原提交保持不变     | 生成全新提交（哈希值改变）   |
| 操作安全性 | 安全（不修改历史） | 危险（重写历史，需强制推送） |
| 冲突处理   | 一次性解决所有冲突 | 需逐个提交处理冲突           |
| 适用场景   | 公共分支合并       | 本地分支整理                 |
