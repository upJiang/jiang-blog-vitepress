# 确定性程序与模型推理怎样划分边界

同一个 Agent 可以让模型判断用户在问什么，却不能让模型决定用户能看哪些文档；可以让模型把自然语言整理成筛选条件，却不能让模型直接拼接 SQL 并执行。边界画错，系统会同时失去可预测性和安全性。

本文从一个“查询知识并生成答案”的功能开始，把职责拆成两类：确定性程序处理权限、状态、预算、格式和副作用；模型处理开放语义、改写和候选计划。最后产出一张能放进 ADR 的职责分配表。

## 先看两种决策的差别

~~~mermaid
flowchart LR
  A[用户问题] --> B[模型：识别意图/改写]
  B --> C[程序：Schema 校验]
  C --> D[程序：主体与范围过滤]
  D --> E[检索与工具]
  E --> F[模型：组织候选答案]
  F --> G[程序：引用/状态/输出校验]
  G --> H[返回或拒绝]
~~~

模型输出是带概率的建议，程序校验是系统的裁判。流程图里每一次从模型回到程序，都应该有一个明确的数据契约，而不是用自然语言约定“模型会遵守”。

## 什么适合确定性代码

以下结果需要同样输入得到可解释、可审计的结果：

- 身份认证、租户和数据范围。
- 余额、配额、预算、任务状态和幂等键。
- JSON Schema、字段类型、数值范围和枚举。
- 数据库事务、唯一约束和权限前过滤。
- 终态、Deadline、取消、重试次数和工具白名单。

这些逻辑可以被模型建议影响输入，但最终值要由代码从可信状态计算。比如模型可以提取“查询上周发布的文档”，程序负责把时间范围解析为明确 UTC 区间，并把范围与主体权限相交。

## 什么适合模型推理

模型擅长处理开放输入和语言变化：

- 从不同说法中识别用户任务。
- 将问题改写成多个检索查询候选。
- 根据工具描述选择可能相关的只读工具。
- 对证据进行自然语言归纳，生成草稿。
- 给 Claim 生成引用位置候选。

这些结果必须经过结构化输出、白名单、证据和质量检查。模型“说自己查过”不等于真的调用了工具；模型输出一个 URL 也不等于该 URL 在用户范围内。

## 第一步：用职责表拆一个功能

| 决策 | 建议负责人 | 可信输入 | 失败语义 |
| --- | --- | --- | --- |
| 用户在问知识还是闲聊 | 模型 + Schema | 用户消息 | 无法判断则进入澄清 |
| 是否允许查某范围 | 程序 | 身份、ACL、范围版本 | 拒绝或无结果，不越权 |
| 检索哪些关键词 | 模型候选 + 程序限制 | 问题与词表 | 空查询走安全默认 |
| 是否调用工具 | 程序白名单 + 模型建议 | 工具契约、预算 | 非法工具拒绝 |
| 答案事实是否可说 | 程序验证 | Claim、Evidence | 缺证据降级或拒答 |
| 是否修改业务数据 | 程序审批/命令 | 业务状态与授权 | 未实现能力不暴露 |

表里的“模型 + 程序”不是把裁判权平均分配，而是模型产生候选，程序验证并决定是否采用。

## 第二步：把模型输出变成输入契约

结构化输出至少要校验：意图枚举、查询数组长度、过滤字段、日期格式、工具名称和参数。校验失败时保留可观测错误，但不要把原始模型 JSON 直接传到 SQL、HTTP Header 或模板。

程序还要做语义约束：查询长度上限、禁止的字段、时间范围最大跨度、工具参数互斥关系和当前主体范围。JSON Schema 能验证形状，不能替代业务规则。

一个最小执行边界：

~~~text
模型输出 QueryPlan
 -> JSON Schema 校验
 -> 业务范围收敛
 -> 白名单通道构造查询
 -> 执行并记录证据
~~~

这里没有把模型写出的字符串拼到 SQL。查询构造器只接受有限的结构化字段，或者使用全文/向量索引接口。

## 第三步：处理“模型很自信但事实错误”

回答阶段必须区分三种情况：

1. 检索有证据，Claim 与证据范围匹配，可以生成。
2. 检索有相关片段，但不足以证明 Claim，应降低表述或继续补充检索。
3. 没有用户可见证据，不能把模型常识当作本库事实，应明确无证据。

这不是让模型自我检查一句“请不要幻觉”就结束。证据绑定、引用范围、ACL 和终态由程序执行；模型只负责根据允许使用的证据组织语言。

## 反例：用关键词特判代替语义理解

有人会在代码里写“标题包含某词就进入检索”“出现某句就拒绝”。它可能修复当前回归用例，却对同义表达、拼写变化、上下文和多语言输入失效，也容易被绕过。

更稳妥的方式是一次结构化理解得到意图、实体和指代，程序再用确定性约束校验。对于安全红线，使用主体、范围、工具权限和数据状态；不要把安全依赖在一句关键词上。

## 反例：把金额和状态交给模型

模型可以把“退回最近一次扣费”提取为候选命令，但金额、订单状态、退款次数和幂等键必须来自数据库事务。模型输出“已经退款”没有任何副作用证明。

若当前系统只有只读能力，公开接口不应展示写工具、审批或 mutation 设计为“现有能力”。未来方案要放在演进章节，标记它还没有实现。

## 评审时问这七个问题

1. 这个结果是否需要同样输入稳定一致？如果是，程序是否拥有最终决定权？
2. 模型输出有没有明确 Schema、白名单和范围收敛？
3. 权限是否在检索前过滤，缓存命中和引用生成后是否仍核对？
4. 事务和副作用是否可以被重复调用？有没有幂等边界？
5. 缺证据、超时、解析失败和模型不可用分别是什么结果？
6. 观测能否区分模型建议、程序拒绝和依赖错误？
7. 回归测试是否覆盖同义问法，而不是只测一条关键词？

## 迁移练习

选一个“查询系统访问方法”的只读功能，写出输入、模型候选、程序校验、检索、证据和终态。再故意让模型返回一个越界范围和一个不存在工具，验证系统在模型建议错误时仍不越权。
