# 05｜构建新索引，并在校验后激活

文档更新后，解析和向量生成需要时间。如果一边处理一边覆盖在线片段，用户可能同时搜到一半新内容和一半旧内容；如果旧任务比新任务更晚完成，知识还可能倒退。

本篇引入候选版本：新内容在旁边完整构建，质量检查通过后一次激活。正在执行的旧回合继续使用创建时版本，新回合才读取新版本。

## 先认识三类版本

```mermaid
flowchart LR
  A[来源版本] --> B[解析与切片产物]
  B --> C[候选知识版本]
  C -->|校验通过| D[在线知识版本]
```

来源版本表示文件或外部来源发生了变化；解析与切片产物记录处理规则；知识版本把一组已经验证的来源组合成可查询快照。向量只是这个快照的检索投影，不是原始知识事实。

## 第一步：重复任务复用已有结果

队列可能重复投递同一个导入任务。入口先按来源和版本查找已有结果；已经成功处理时直接返回，不再次调用解析与嵌入服务。

```text
输入一：source=A，version=7 -> 创建候选，生成向量
输入二：source=A，version=7 -> 返回已有结果，不重复生成
```

幂等意味着重复同一请求得到同一业务效果，不是所有错误都静默忽略。版本不同仍会创建新的候选。

## 第二步：在候选区完成全部构建

构建顺序是解析、切片、质量检查、嵌入和持久化候选。任何一步失败，当前在线版本保持不变。

```python
async def build_candidate(source):
    parsed = await parse(source)
    chunks, report = split_and_check(parsed)
    vectors = await embed(chunks)
    return await save_candidate(source.version, chunks, vectors, report)
```

这是根据真实执行链重写的最小示例。输入是一个明确来源版本，输出是尚未在线的候选；解析、覆盖率或向量失败都不会部分激活。

## 第三步：旧任务为什么不能覆盖新任务

假设版本 7 先开始，版本 8 后开始却先完成。版本 8 激活后，版本 7 最终写入时必须重新检查“自己仍是最新来源吗”。检查失败就标记为过期，不修改在线指针。

这条保护发生在最终写入的事务边界内。只在任务启动时检查一次不够，因为新版本可能在长时间处理期间出现。

## 第四步：一次事务完成激活

候选校验通过后，同一数据库事务写入版本关系、片段状态和在线指针。提交前检索只看到旧版本，提交后新回合能看到完整新版本。

已经创建的回合会钉住旧知识版本。这样一次长回答在补充检索时不会突然混用后来发布的内容，评测也能重放当时的知识快照。

## 第五步：缓存也要理解版本和权限

检索缓存键至少包含规范化查询、知识版本和访问范围指纹。同一句问题在不同版本或不同权限下不应共用候选。

缓存命中后仍会复核可见性，因为权限可能刚被撤销。第 07 篇会详细处理这条边界。

## 正常结果和失败结果

| 场景 | 在线版本 | 候选结果 |
| --- | --- | --- |
| 新版本全部通过 | 切换到新版本 | active |
| OCR 失败 | 保持旧版本 | failed |
| 切片覆盖不足 | 保持旧版本 | rejected |
| 向量服务失败 | 保持旧版本 | failed |
| 旧任务晚完成 | 保持较新版本 | stale |
| 同版本重放 | 不变化 | idempotent replay |

测试会让两个版本以相反顺序完成，并确认在线版本不会倒退；另一个测试重复提交相同版本，确认嵌入只执行一次。

## 当前实现的边界

激活是数据库内的版本切换，不宣称对外部向量服务实现分布式事务。旧版本保留多久取决于评测、回放和存储策略，没有通用天数。

下一篇使用已经发布的版本，组合精确、全文、向量和表格检索。

## 用一条时间线理解候选与激活

假设线上正在使用知识版本 V1。用户上传新文件后创建来源版本 S2，后台任务基于它构建候选 V2。构建期间查询仍固定读取 V1；只有解析覆盖、片段关系和索引检查全部通过，激活指针才在一个事务中从 V1 改为 V2。

| 时间 | 后台动作 | 在线查询看到什么 |
| --- | --- | --- |
| T1 | 创建 S2 和候选 V2 | V1 |
| T2 | 解析、切片、写全文与向量投影 | V1 |
| T3 | 质量门禁通过 | V1 |
| T4 | 事务内激活 V2 | 新回合看到 V2 |
| T5 | 旧回合继续运行 | 仍使用创建时钉住的 V1 |

再制造一个顺序问题：较早的构建任务 V2 执行很慢，后来创建的 V3 先完成并激活。V2 最终提交时必须比较来源代次或当前候选身份，发现自己已过期后结束，不能覆盖 V3。这个测试能证明“任务成功”与“允许激活”是两个判断。

重复收到同一个来源哈希时，可以复用已经完成的版本或返回当前任务，而不是再次生成一套片段。删除旧版本也不应与激活绑在同一操作中；需要先确认没有运行回合、审计或回滚仍引用它。下一篇将从已激活版本中建立多路检索。
