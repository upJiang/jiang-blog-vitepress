# Skill 设计方法：把成功 Prompt 变成稳定工作流

Skill 是一份可被 Agent 发现并按需读取的任务方法包，可以包含入口说明、参考资料、脚本、模板和资源。它位于临时 Prompt 与具体执行工具之间，用来复用稳定规则、减少上下文浪费，并把适合程序验证的步骤交给确定性脚本。

第一次让 Agent 检查发布文章时，你解释了 Frontmatter、链接、隐私和构建命令，结果很好。第二次换了一篇文章，又要粘贴同一段 Prompt；第三次 Agent 漏掉敏感信息检查，你只好继续补充。此时问题已经不是“怎样写更长提示词”，而是怎样把稳定方法、确定性检查和失败处理做成可发现的 Skill。

一个有效 Skill 的可观察结果是：用户用自然说法提出同类任务时，它会正确触发；Agent 先读取短入口，再按步骤加载需要的参考和脚本；输入不足时追问；脚本失败时保留真实错误；输出遵循约定结构。

## Skill 是可按需加载的任务方法包

Skill 是一个包含 `SKILL.md` 和可选资源的目录。元数据告诉 Agent“它做什么、何时使用”，正文描述工作流、输入、边界和输出，需要时再执行 `scripts/`、读取 `references/` 或使用 `assets/`。

它不训练新模型，不运行独立后端，也不自动获得工具权限。Skill 的输入是用户任务与当前上下文，处理仍由宿主 Agent 完成，输出是按统一方法生成并验证的产物。外部实时数据和受控动作通常来自现有 Tool 或 MCP Server。

同一个概念可以用目录表示，也可以用执行状态表示。目录强调信息放在哪里；状态链强调何时加载：`metadata visible -> matched -> SKILL.md loaded -> resources used -> output verified`。验证时既要检查目录合法，也要检查真实 Prompt 是否在正确阶段触发。

## 脱敏能力地图揭示了哪些模式

本机可见 Skill 合并重复来源并隐去私有名称后，可以归纳为六类。公开这张地图是为了发现结构模式，不代表公开安装路径、内部配置或业务流程。

| 类别 | 典型任务 | 稳定资产 | 常见边界 |
| --- | --- | --- | --- |
| 业务自动化 | 写文档、处理缺陷、生成报告 | 流程、模板、状态规则 | 外部写入与身份审批 |
| 数据查询 | 业务库、行为数据、缓存事实 | 查询脚本、口径参考 | 只读、脱敏、环境隔离 |
| 文档与媒体 | PDF、Word、表格、演示、视频 | 渲染脚本、版式模板 | 文件类型与视觉验证 |
| UI、SEO 与测试 | 页面设计、审计、浏览器验证 | 检查表、测试命令 | 设计输入、截图和网络 |
| 记忆与复盘 | 保存、恢复、回顾工作 | 摘要 Schema、索引 | 明确授权、撤回和隐私 |
| Skill 与 Plugin 开发 | 创建、验证和打包能力 | 脚手架、校验器、评测集 | 触发准确率和分发范围 |

这些 Skill 的共同点不是主题，而是流程已经稳定到能写出输入、步骤、输出和验证。数据查询类通常把易错操作放进低自由度脚本；写作类保留更高表达自由度；文档类必须加渲染与视觉检查。Skill 的自由度应跟错误成本匹配。

## 从四种重复信号挖掘机会

### 重复 Prompt 暴露稳定输入

把最近使用过的长 Prompt 放在一起，标出每次都出现的目标、文件类型、工具和完成条件。重复部分是候选流程，可变部分是未来 Skill 输入。若每次目标完全不同，只是语气相似，不值得封装。

### 固定检查表暴露可验证步骤

发布、Review、排障和报告常有固定清单。判断哪些项目可以由脚本确定，哪些必须由 Agent 结合语义评审。全靠自然语言会漏项，全靠脚本又无法理解上下文；Skill 可以组织两者的顺序和证据。

### 频繁纠错暴露隐含边界

“不要推送”“截图不要进仓库”“只查测试环境”等重复纠正，比理想流程更有价值。先判断它应进入全局/仓库规则还是 Skill：始终有效的安全边界放规则，只有该任务出现时才需要的步骤放 Skill，能机械阻断的部分再放脚本或权限层。

### 一次成功任务暴露最小样本

不要在没有真实任务前写万能 Skill。先完成一个代表案例，保存输入、关键决策、工具证据、产物和失败点，再找两个变体。三次任务仍共享主干时才抽象；否则继续使用 Prompt 更轻。

## 用机会卡决定是否开发

| 维度 | 低价值信号 | 高价值信号 |
| --- | --- | --- |
| 重复频率 | 偶发一次 | 每周或多人重复 |
| 流程稳定度 | 每次都重新决策 | 主干步骤和结果稳定 |
| 失败成本 | 可随手修正 | 容易漏项、越权或返工 |
| 确定性资产 | 只有一句提示 | 有脚本、参考、模板或验证器 |
| 触发边界 | 无法描述何时使用 | 有明确正例和负例 |
| 维护所有者 | 来源不清 | 有责任人与更新信号 |

机会卡输入是真实任务记录，输出是“保持 Prompt、写规则、开发 Skill 或连接 MCP”的决策。流程不稳定时先做几次人工实践；任务始终适用的硬约束写进项目规则；依赖实时外部数据时由 MCP 提供能力，Skill 只组织用法。

## 四层目录实现渐进式披露

```text
article-publishing-check/
├── SKILL.md
├── scripts/
│   └── check_article.py
├── references/
│   ├── publishing-policy.md
│   └── review-rubric.md
└── assets/
    └── review-report.md
```

第一层是始终可见的 `name` 和 `description`，用于发现；第二层是触发后读取的 `SKILL.md`，保持短小且能执行；第三层是按步骤读取的参考与脚本；资产是输出要复制或填充的模板。`SKILL.md` 到参考保持一层引用，避免 Agent 在深层链接中迷路。

`scripts/` 适合无需进入上下文的确定性实现，Agent 应执行它并读取结果，不必把全部源码塞进 Prompt。`references/` 放较长政策、API 或领域知识；`assets/` 放报告模板、图片或交付骨架。文件只有在提高可靠性时才增加，空目录不是成熟度指标。

## 描述决定触发的精度和召回

Frontmatter 的 `name` 使用小写连字符并保持稳定；`description` 同时说明做什么和何时使用，包含用户真实说法，也写清容易误触发的边界。正文不要承担发现职责，因为未触发前 Agent 往往只看得到元数据。

```markdown
---
name: article-publishing-check
description: 检查 Markdown 技术文章的 Frontmatter、标题、内部链接、示例、敏感信息和发布门禁。用户要求发布前检查、文章验收、内容质量检查或排查文章构建失败时使用；不要用于普通文案润色。
---

# 文章发布检查

## 输入

- 文章路径或明确的文章集合
- 仓库发布规范与允许执行的命令

## 工作流

1. 读取仓库规则和发布政策。
2. 运行确定性检查脚本，保留退出码与问题位置。
3. 按评审量表检查语义、来源和隐私。
4. 修复仅限授权范围；重新运行检查。
5. 使用报告模板输出通过项、失败项和未验证项。

## 边界

- 不提交、不推送、不发布，除非用户分别明确授权。
- 不把密钥、内部地址或真实业务数据写入报告。
```

元数据先用任务语言建立触发候选，正文再检查输入和权限，随后读取政策、执行脚本并填报告。缺少文章路径时追问；脚本失败时输出位置而不是继续声称通过；用户只要求润色时负例阻止 Skill 抢占普通写作。

真实 Frontmatter 需要符合目标产品限制。Codex Skill 的名称、描述、发现目录和显式调用方式应以当前官方文档为准；若同时支持 Claude Code，要在各自环境验证，不要假设所有扩展字段通用。

## 自由度要与脆弱性匹配

高自由度任务有多个合理答案，例如文章语气复核，Skill 给原则和输出标准即可。中自由度任务有推荐流程，例如故障排查，提供顺序、分支和示例。低自由度任务涉及脆弱或危险操作，例如数据库查询、制品发布，应使用经过测试的脚本、固定参数和明确审批。

自由度不是让 Agent“发挥多少”，而是允许它在哪些决策上选择。把稳定解析、哈希和格式校验交给脚本，把来源可信度和论证完整性留给语义评审。脚本输入和输出要结构化，非零退出保留真实错误；不能捕获所有异常后返回“检查完成”。

恢复策略也按层划分：输入缺失先补齐；参考过期指出来源；脚本失败报告命令和退出信息；外部服务不可用标记未验证；权限不足停止副作用。Skill 不应为了交付漂亮报告而吞掉失败。

## 从成功任务走到可回归评测

1. 保存一个成功任务的输入、过程和可验证产物。
2. 找出稳定步骤、变量、错误和边界。
3. 写最小 `SKILL.md`，先不增加不必要资源。
4. 把确定性步骤移入脚本，长知识移入参考，交付格式移入资产。
5. 建立直接触发、间接触发、负例和边界输入组成的评测集。
6. 记录是否触发、是否读对资源、工具结果和最终质量。
7. 每次只改一个描述或步骤，回放评测并比较回归。

评测要同时覆盖触发与执行。只测显式 `$skill-name` 无法发现自然语言漏触发，只测最终报告又无法定位是描述、步骤、脚本还是参考资料造成错误。负例优先保证精度，避免一个宽泛 Skill 抢走所有相近任务。

版本更新信号包括仓库规则变化、外部 API 变化、频繁人工纠正和评测失败。维护者应能从某个失败案例追溯到一处资源，而不是重写整个 Skill。

## Skill、规则、MCP 与 SubAgent 的组合边界

| 需求 | 所属层 | 示例 |
| --- | --- | --- |
| 对仓库始终有效的约束 | 项目规则 | 默认不提交、正确测试命令 |
| 可复用任务方法 | Skill | 文章发布检查流程 |
| 实时外部数据或动作 | MCP | 查询当前版本、创建记录 |
| 独立上下文与并行 | SubAgent | 同时做来源审查和安全审查 |

组合时由 Skill 编排方法，不要让它复制 MCP 的认证逻辑；SubAgent 接收 Skill 中可隔离的子任务，但权限不会因委派扩大；项目规则始终约束所有执行者。若 Skill 只是启动一个 Tool 而没有流程价值，直接使用 Tool 更简单。


**`SKILL.md` 应该写得多详细？**

写到 Agent 能识别输入、按顺序执行、知道何时加载资源、怎样处理失败和判断完成即可。不要复制模型已经知道的通用知识或整份 API 手册。正文过长就把专项资料拆到 `references/`；执行者仍需猜关键参数时需要补充，每次加载大量无关知识时需要删减。

**什么时候用脚本，什么时候让 Agent 判断？**

解析 Frontmatter、检查路径、计算哈希和固定格式适合脚本；论证是否充分、证据是否支持 Claim 等语义任务留给 Agent。风险越高、步骤越脆弱，自由度越低。**确定性问题交给脚本，判断性问题要求 Agent 给出依据。**

**Skill 修改后怎样防止旧任务回归？**

保存触发和执行两类评测：自然语言正例、相似负例、边界输入、脚本错误和产物基线。真实任务出现新纠错时先添加失败用例，再修改描述或流程；每次只改变一层并回放全部用例，避免新案例通过时旧触发范围已经退化。
