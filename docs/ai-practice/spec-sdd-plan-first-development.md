# Spec 与 SDD：让规格连接需求、代码与验证

需求说“给订单接口增加状态筛选”，开发仍然要回答很多问题：状态有哪些，能否多选，非法值返回什么，旧客户端是否受影响，索引能否支撑查询。Spec 把这些决定写成可检查合同。本文所说的 SDD 指以规格驱动设计和开发，让实现与测试都能追溯到同一条约束。

## 需求、规格和计划承担不同责任

需求说明用户问题，规格定义可观察行为，计划描述怎样修改系统。三者混在一起，会让实现细节冒充业务约束，也会在更换技术方案时迫使团队重写需求。

```text
需求：运营人员按订单状态缩小列表范围。
规格：GET /orders?status=paid,shipped 接受已公布状态集合；
      未提供参数时保持旧行为；非法状态返回 422 和稳定错误码。
计划：扩展查询模型，增加仓储过滤，补索引评估和契约测试。
```

规格中的结论都要有来源。产品决定状态集合，现有接口提供兼容基线，数据库计划来自源码与执行计划。未知项标记为待确认，不能由模型补成事实。

## 规格要写状态变化和失败边界

接口规格不只描述成功响应。输入缺失、重复值、权限不足、超时和空结果会走向不同终态。筛选后得到空列表与非法状态也不能共用模糊的“查询失败”。

有副作用的功能还要写幂等、并发和回滚。创建订单时，同一幂等键是否复用结果，两个请求怎样竞争库存，部分写入由事务回滚还是补偿。实现之前没有回答这些问题，测试只能覆盖表面路径。

## 从规格条目建立验证关系

给每条规格稳定 ID，代码和测试引用它：

| 规格 ID | 可观察行为 | 验证 |
| --- | --- | --- |
| ORD-FILTER-01 | 无参数保持旧列表行为 | 旧契约回归测试 |
| ORD-FILTER-02 | 合法状态支持多选 | API 与仓储集成测试 |
| ORD-FILTER-03 | 非法状态返回 422 | 错误合同测试 |
| ORD-FILTER-04 | 用户只能看到授权范围 | 权限隔离测试 |

测试不是从标题自动生成。它要构造能推翻规格的反例：混合合法与非法值、重复参数、空字符串、不同租户相同订单号，以及分页过程中状态变化。

## 实施时保护当前基线

开始前保存仓库状态、相关接口响应和测试基线。修改只覆盖规格声明的行为，发现旧约束冲突时暂停对应部分并更新决策记录。为了让测试通过而偷偷改变规格，会让评审者无法判断产品意图是否变化。

数据库迁移、缓存键和客户端类型属于发布兼容面。新代码可以回滚，不代表新数据一定能被旧版本读取。规格写明向前与向后兼容要求，计划再据此选择双写、分阶段迁移或候选版本。

## 可执行追溯要使用稳定关系

规格、代码和测试之间不要只靠标题中的相似文字关联。为规格条目分配稳定 ID，测试元数据引用 ID，CI 生成覆盖矩阵：哪些活动规格有测试，哪些测试引用已删除规格，哪些失败阻断候选。

```ts
type SpecTrace = {
  specId: string
  specVersion: number
  testIds: string[]
  implementationRefs: string[]
  status: 'draft' | 'active' | 'deprecated'
}
```

矩阵只能证明存在引用，不能证明测试断言真的覆盖行为。评审仍要检查反例、权限范围和失败路径。反过来，未建立引用也不代表实现错误，它表示当前交付缺少可追溯证据。

规格版本进入测试报告和候选制品。流水线若读取到更新中的规格，先固定一个活动修订再执行；同一轮中途切到新版，会让前半测试与后半实现依据不同合同。

## 规格变化需要版本和影响分析

产品后来要求增加 `cancelled` 状态，应创建规格修订并列出受影响的 Schema、查询、索引、前端筛选和监控。运行中的任务继续使用创建时的版本，新请求使用活动版本，避免一次执行前后读取不同合同。

删除规格也要处理派生物。废弃字段可能仍被 SDK、缓存和报表使用，先观察调用，再经过兼容窗口移除。只改文档标题不会让旧依赖消失。

## 哪些任务不需要完整 SDD

一次局部文案修改没有跨模块合同，用清晰任务说明和差异审查即可。多人协作、接口演进、权限规则或数据迁移出现时，规格的追溯价值会快速上升。

判断标准是错误代价和协作边界，不是文档篇幅。最小规格可以只有几条可观察行为、明确未知项和对应测试。它需要让另一位开发者知道哪些结果算对、哪些变化必须重新确认。
