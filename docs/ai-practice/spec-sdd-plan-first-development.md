# Spec 与 SDD 实践：主流工具、可执行规格与真实仓库落地

“增加批量导出”只有五个字，代码里却会迅速长出一串未经确认的决定：谁能导出，导出当前页还是全部筛选结果，数据量大时同步还是异步，是否包含敏感字段，任务能否重复创建，下载链接多久过期。

Plan 可以先调查这些问题，Spec 则把确认后的行为变成版本化工件。SDD，也就是规格驱动开发，进一步要求计划、实现、测试和 Review 都能回到这份规格。它最有价值的地方，不是多写几份 Markdown，而是让需求变化发生时，我们知道哪段设计、哪项任务和哪些测试需要一起变化。

为了避免只谈理念，本文让四个当前有代表性的开源方法处理同一个需求：为已有管理系统增加带权限的订单批量导出。样本是根据主题匹配和 2026-08-12 的 GitHub Star 快照选出的：Superpowers 约 270,890，Spec Kit 约 126,309，OpenSpec 约 64,602，BMAD Method 约 51,787。**Star 说明社区关注度，不证明方法适合你的团队。**

## 先建立同一把尺子

我们的仓库已经存在订单列表、RBAC、异步任务和对象存储，不允许推倒重来。需求有四条硬约束：

- 只有 `orders.export` 权限可以发起、查看和下载；
- 导出范围复用列表筛选与服务端租户 Scope；
- 超过 1,000 条转异步任务，下载地址 24 小时过期；
- CSV 不含手机号、地址和内部备注。

变化也很现实：实现中途，安全负责人可能要求所有下载写审计事件，产品也可能把阈值改成 5,000。比较四种方法时，我关心的不是它们能否生成漂亮目录，而是它们怎样回答六件事：需求如何澄清，会留下什么工件，怎样读取已有代码，设计怎样进入实现和测试，多 Agent 如何协作，需求变化后旧规格怎样更新。

## Superpowers：先约束 Agent 的开发纪律

Superpowers 更像一组会在正确阶段触发的工程 Skills。它强调在编码前进行头脑风暴和设计，把实现计划拆成小任务，随后按测试驱动、系统化调试、代码审查和完成验证推进。对我们的导出需求，它不会先要求采用某一种中央规格格式，而会先阻止 Agent 直接开写。

一次典型推进会是：讨论导出主体、范围、阈值和安全边界，形成设计；把任务拆成权限失败测试、任务模型、导出服务、Worker、下载接口和页面状态；每个任务保持小步验证；完成后由审查步骤对照计划与测试证据。

它对已有仓库很友好，因为流程可以围绕当前代码工作，不必先迁移整套项目管理方式。Skill 也适合把“先取证、再计划、先写失败测试”注入不同编码 Agent。

但 Superpowers 的主要约束力在执行纪律。若团队需要一份长期产品规格、需求到测试的稳定 ID，或跨季度维护的变更历史，仅靠 Skills 不够。设计文档和任务如果没有独立版本规则，几次迭代后仍可能与代码漂移。

**我的选择：团队最痛的是 Agent 直接写代码、跳过测试和完成验证时，先引入 Superpowers 式纪律。** 它可以和其他规格体系叠加，不必单独承担全部需求治理。

## Spec Kit：从原则到任务的标准化工件链

Spec Kit 的重心是把需求逐步转成规格、澄清、技术计划和可执行任务，并用项目原则约束这些工件。它适合新项目、大功能，或希望团队共享一套清晰产物链的场景。

导出需求进入这套方法后，规格首先用用户故事和验收场景描述行为：有权限用户按筛选导出、无权限用户被拒绝、大结果进入异步、敏感字段不出现。澄清阶段集中关闭阈值、格式、过期和审计问题。技术计划再结合仓库研究 RBAC、任务框架、对象存储和迁移策略，最后生成带依赖顺序的任务。

它的优势是让业务规格与技术计划分开。产品变更“阈值从 1,000 到 5,000”时，先更新规格中的规则和验收，再更新计划、任务与相关测试，不会只改代码常量。多 Agent 也容易按任务依赖分配，只要主 Agent 防止并行任务同时改共享契约。

代价同样明显。已有仓库如果每个小改动都完整生成原则、规格、计划、研究、数据模型、契约和任务，文档维护会超过编码。工具生成的文本还可能看似完整却没有仓库证据，例如计划声称“复用 ExportService”，实际项目根本没有这个组件。

**我的选择：新项目、跨模块大功能或多人长期协作，优先评估 Spec Kit。** 在旧仓库落地时，应先裁剪模板，并强制“现状证据”引用实际路径、符号和测试，而非接受通用架构描述。

## OpenSpec：把已有系统的变化单独管理

OpenSpec 更适合已有仓库的增量变化。它把当前规格与本次 change 分开：proposal 解释为什么变，delta spec 描述新增、修改或删除的行为，tasks 连接实现；完成后再把已验证变化归档进主规格。

对订单导出来说，我们不需要重新描述整个管理系统。可以创建一个 `order-export` change，proposal 记录业务目标与影响面，增量规格只写导出能力：

```markdown
## ADDED Requirements

### Requirement: Authorized order export
系统 SHALL 只允许拥有 orders.export 权限的主体导出其当前 Scope 内的订单。

#### Scenario: unauthorized request
- WHEN 用户没有 orders.export 权限
- THEN 创建接口返回拒绝
- AND 不创建任务或对象文件

#### Scenario: asynchronous export
- WHEN 匹配结果超过配置阈值
- THEN 系统创建可幂等复用的异步任务
- AND 下载结果不包含敏感字段
```

实现中途新增“下载必须审计”时，先把它作为新增 Requirement 和 Scenario 放进同一个 change，再补任务与测试。变更完成、验证通过后归档，当前规格就反映系统已经承诺的行为，临时讨论和旧方案留在变更历史中。

这种增量模型对维护中的产品很自然，也适合 PR Review：Reviewer 可以同时看到 proposal、spec delta、tasks 和代码 Diff。它不替你决定技术架构，现状调查和具体计划仍需团队补充。若主规格从未建立或长期不归档，change 会变成互相冲突的文档堆。

**我的选择：在真实已有仓库增加功能，我会优先试 OpenSpec。** 它把注意力放在“系统承诺发生了什么变化”，比为每次小需求重建完整项目规格更轻。

## BMAD Method：用角色和阶段管理更大的产品过程

BMAD Method 的覆盖面更宽。它通过分析、产品、架构、项目管理、开发、测试等角色及工作流，把模糊想法逐步推进到规划和实现。对于一人团队或多 Agent 团队，它提供的价值是视角分离：分析者追问业务机会，产品角色整理 PRD，架构角色处理技术约束，开发与测试角色执行和审查。

在导出案例中，产品视角会追问谁为什么需要导出、成功如何衡量；架构视角会判断同步与异步、数据 Scope、任务幂等和对象存储；测试视角会从越权、并发、过期与大数据量攻击方案。多个 Agent 可以承担独立角色，但所有角色仍应共享经确认的需求 ID 和仓库证据，不能各自发明一份真相。

它适合从想法到产品的完整工作，尤其是需求本身还不成熟、希望用角色对话扩大思考时。代价是仪式和上下文更多。一个成熟系统里的局部修复若也启动完整角色链，会让模型花大量时间生成可预测文档，反而稀释关键 Diff。

**我的选择：需要从市场、产品一路走到研发，或希望用多 Agent 模拟完整团队时评估 BMAD。** 对已有仓库的小型增量，我不会把它作为默认入口。

## 四种方法处理同一变化时，差异才会显现

假设开发中途出现两个变化：阈值改为 5,000，下载必须写审计事件。

| 方法 | 首先更新什么 | 对已有代码的连接 | 多 Agent 协作 | 主要维护成本 |
| --- | --- | --- | --- | --- |
| Superpowers | 设计与实施计划，重新执行测试纪律 | 由调查与计划步骤建立 | 适合按小任务委派 | 设计、计划和执行证据可能分散 |
| Spec Kit | 规格与澄清，再同步计划和任务 | 技术计划显式研究仓库 | 任务依赖清楚，适合较大并行 | 完整工件链较重 |
| OpenSpec | 当前 change 的 delta requirement 与 scenario | 天然围绕现有系统增量 | 可按 change tasks 拆分 | 需要维护主规格和归档纪律 |
| BMAD Method | 产品、架构、测试等角色产物 | 由角色工作流逐步研究 | 角色并行能力强 | 上下文、角色交接和流程开销最大 |

任何工具都无法自动消除规格漂移。最可靠的连接是给 Requirement 稳定 ID，把它写入任务和测试名，PR 检查“改了行为是否同步改 Spec”，完成后再归档。Spec 不应详细复制源码，否则每次重命名都造成无价值维护；它应该保存系统对用户、调用者和运维者承诺的行为。

```yaml
requirement: EXP-003
statement: 下载订单导出文件时必须记录审计事件
implementation:
  - server/services/order_export.py
tests:
  - tests/order_export/test_download_audit.py
status: verified
```

这类追踪记录允许 Reviewer 从需求找到代码和测试，也允许 Agent 在需求变化时搜索影响面。它并不证明测试内容正确，所以仍需要独立审查和运行证据。

## 我会怎样在团队里落地

选择不该从“哪个项目 Star 多”开始，而应从当前瓶颈开始：

- 新项目或跨域大功能，先用 Spec Kit 建立从业务规格到任务的统一工件；
- 已有仓库的增量功能，用 OpenSpec 管理变化和归档；
- Agent 经常跳步、过早编码或为了过测试而改测试，引入 Superpowers 式执行纪律；
- 产品还处于探索期，且需要产品、架构、测试多视角协作，再考虑 BMAD Method；
- 一两个文件、行为明确、当天能完成的小改动，使用轻量 Markdown Spec 即可。

轻量 Spec 只要能回答目标、非目标、现状证据、行为变化、文件范围、验收和未决问题，就已经足够。没有必要为了符合 SDD 名称制造十份空泛文档。

工具也不应一次铺满团队。挑一个真实中型需求，记录澄清缺口、文档维护时间、返工、Review Finding 和测试追踪效果。第一次需求变化后再复盘，因为**规格系统的质量不在首次生成时，而在变化发生后还能否保持行为、代码与测试一致。**
