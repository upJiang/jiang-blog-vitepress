# 怎样从重复工作中识别 MCP 机会

从跨系统复制、实时查询和标准操作判断普通 API、CLI、Skill 或 MCP。**MCP**、**Opportunity Analysis**、**Tool** 分别指向同一条执行链上的不同对象：重复步骤、数据实时性、系统数量、调用频率、使用者、权限和错误处理责任进入系统，现有 API 或 CLI、重复成本、候选工具、资源、协议需求、维护者和验收条件保存处理中间状态，最终得到机会清单、能力边界、选择理由、风险和小范围验证方案。

从重复工作中识别 MCP 机会位于重复工作被产品化为外部能力之前的机会分析层，主要机制是先找跨系统复制、实时查询和稳定动作，再判断普通脚本、CLI、Skill 或 API 是否足够；只有多个 Host 需要统一发现和调用时才引入 MCP。从“能做 MCP”反推需求、把一次性流程协议化、Server 暴露底层数据库、没有身份模型和忽略客户端并不支持所需能力会让链路在不同位置停止，错误记录必须保留发生阶段、当时的状态和终止原因。

::: info 贯穿示例

从重复工作中识别 MCP 机会场景：团队每天在缺陷系统、代码仓库和文档之间复制信息，希望编辑器与桌面助手都能调用同一套只读查询。从重复工作中识别 MCP 机会需要的身份、权限、版本和业务事实由应用提供，模型与外部内容只产生候选。

:::

## 先确认重复工作的边界

从“能做 MCP”反推需求会破坏现有 API 或 CLI 与机会清单之间的对应关系，排查时先保留原始输入摘要和发生阶段，再判断是否允许重试。

把一次性流程协议化影响重复成本或下游解释，不能和从“能做 MCP”反推需求共用“重新调用一次模型”的处理方式。

## 什么样的重复动作值得抽成能力

MCP 实践中，执行者负责计划和改动，工具提供证据，脚本负责可重复检查。因此现有 API 或 CLI 与重复成本要有唯一写入方，其他组件只能通过版本化命令申请修改。

自动化脚本与从重复工作中识别 MCP 机会解决的问题相邻，但控制权不同，比较时要看谁选择选择能力、谁保存现有 API 或 CLI、谁确认机会清单。

CLI 可以参与同一请求，却不能替代从重复工作中识别 MCP 机会；组合后仍要单独检查数据实时性的可信来源和从“能做 MCP”反推需求的终止规则。

从重复工作中识别 MCP 机会使用的身份、范围和版本来自可信运行时，重复步骤可以表达意图，但不能提升权限或改写活动 Release。

把一次性流程协议化发生时，错误回到重复成本的所有者处理，上游缺输入、当前组件违反不变量和下游不可用分别形成不同终态。

从重复工作中识别 MCP 机会的确定性边界位于现有 API 或 CLI 写入之前。模型在 MCP 中只提交候选值，程序仍要从认证、版本和策略快照补入可信字段。

从重复工作中识别 MCP 机会内部可以使用更细的临时对象，跨边界只暴露稳定协议。替换自动化脚本时，调用方不需要理解内部缓存和 SDK 响应。

## 机会判断需要哪些证据

从重复工作中识别 MCP 机会的输入合同至少列出重复步骤、数据实时性和系统数量，每项都注明来源、是否必需、允许的缺省值，以及缺失后是在入口拒绝还是进入降级路径。

评估 MCP 机会时，现有 API 或 CLI 只是输入证据；重复成本要绑定到具体流程和版本，候选工具还要记录授权范围与可观察回执。把三者压成一段描述，后面就无法判断问题究竟来自接口缺失，还是流程本身不值得自动化。

并发分支按稳定身份合并候选工具，完成顺序只反映耗时，不能决定结果属于哪个请求，更不能让迟到的旧状态覆盖新修订。

输出合同同时描述机会清单和能力边界，并为拒绝、取消、部分完成和未知状态提供固定形状，调用方据此分支，无需解析错误文案猜测结果。

重复成本参与乐观并发检查；处理开始后若版本变化，旧候选只保留作审计，不能继续写入现有 API 或 CLI。

重复步骤里若包含模型填写的同名字段，应用会丢弃它，再从认证、配置或活动版本中补入可信值，因为结构校验通过不等于授权或业务校验通过。

需求假设、文件定位、差异、命令输出、失败说明和回滚入口组成从重复工作中识别 MCP 机会的最小追踪材料，日志只保存稳定 ID、版本和错误类，完整 Prompt、文档正文与凭证不进入指标标签。

撤回或删除数据实时性时，相关缓存、候选和未完成任务按版本失效；稳定 ID 可以保留审计关系，已撤回内容不能继续进入机会清单。

契约还需要描述新鲜度。重复成本对应的数据发生变化后，旧缓存、旧候选和未完成任务怎样失效，应由版本或时间规则直接判断，不能依赖模型注意到矛盾。

删除和撤回也属于数据生命周期。从重复工作中识别 MCP 机会引用的原始对象被移除时，稳定 ID 可以保留审计关系，正文与派生结果则按策略失效，避免继续向用户展示过期内容。

::: warning 从重复工作中识别 MCP 机会的可信边界

机会清单通过结构校验后仍是候选。从重复工作中识别 MCP 机会使用的身份、权限、知识版本与业务事实由应用从可信服务读取，核对完成后才能执行或交付。

:::

## 从动作记录到 MCP 契约

从重复工作中识别 MCP 机会时，先记录一次原始流程的调用次数、复制字段和失败位置，再模拟候选工具的输入、回执与授权。只有这些记录显示跨 Host 复用确实减少了重复工作，才有理由进入 MCP 设计。

读取任务约束接收重复步骤并建立现有 API 或 CLI，入口校验未通过就地结束，后续模型、检索器或工具调用次数保持为零。

选择能力读取重复成本并执行主题逻辑，参数由应用组装，外部返回先保存为能力边界，尚未获得修改领域状态的资格。

执行最小改动检查结构、范围、版本和主题不变量；机会清单缺少来源、落在旧版本或越过权限时，现有 API 或 CLI 停在 rejected 或 failed。

验证并交付先保存机会清单与终止原因，再产生事件或通知，交付失败可以重放，核心状态写入失败则不能对外宣称完成。

选择能力出现部分结果时，由任务合同决定保留、补偿还是整体丢弃；机会清单若可重建就重新生成，外部副作用则查询回执或执行补偿。

实现可以使用函数、Graph、Middleware 或 Workflow，现有 API 或 CLI 的所有权和从“能做 MCP”反推需求的停止规则不会随框架改变。

部分成功需要在步骤边界处理。选择能力已经产生一部分机会清单时，程序按任务合同决定保留、补偿或整体丢弃，并记录未完成项，不能默认为全部成功。

选择能力和执行最小改动都要写明逆向动作或不可逆原因，机会清单若可重建就删除后重算，已发送的外部命令只能查询回执或补偿。

## 沿一次跨客户端查询推演

沿“从重复工作中识别 MCP 机会场景：团队每天在缺陷系统、代码仓库和文档之间复制信息，希望编辑器与桌面助手都能调用同一套只读查询”推演从重复工作中识别 MCP 机会：入口创建 request_id，读取可信身份，把重复步骤和当前版本写入初始状态。

读取任务约束生成现有 API 或 CLI 与输入摘要；若数据实时性缺失，请求返回 rejected，并指出缺少哪项材料，不继续消耗模型或外部服务配额。

选择能力按“先找跨系统复制、实时查询和稳定动作，再判断普通脚本、CLI、Skill 或 API 是否足够；只有多个 Host 需要统一发现和调用时才引入 MCP”推进，每次依赖调用保存 call_id、参数摘要、开始时间与状态版本，以便判断超时前是否已经产生结果。

候选结果对应机会清单、能力边界、选择理由、风险和小范围验证方案，执行最小改动逐项检查权限、版本与领域约束，问题列表为空才允许形成下一状态。

验证并交付写入终态；客户端断开只影响交付通道，重新连接时读取已经保存的现有 API 或 CLI 或事件游标，不重跑核心逻辑。

故障注入选择 Server 暴露底层数据库，程序保留原候选和错误位置，只重做失败边界，不能从入口复制整个任务并产生第二份状态。

推演结束后用 request_id 关联现有 API 或 CLI、机会清单与终止原因，测试据此排除并发请求串线，并确认失败路径没有遗留未关闭资源。

从重复工作中识别 MCP 机会在输入拒绝时不调用依赖，正常路径按 5 个阶段推进，有限修复只重做失败边界。调用次数是控制流断言，不是性能宣传。

从重复工作中识别 MCP 机会的最终记录用 request_id 关联现有 API 或 CLI、机会清单和失败问题，测试据此证明结果来自本次执行，没有混入并发请求。

## 一个可交付的最小试点

从重复工作中识别 MCP 机会正常完成时，现有 API 或 CLI、重复成本和机会清单指向同一次执行，重复读取返回同一终态，未完成分支已经取消或有明确所有者。

需求假设、文件定位、差异、命令输出、失败说明和回滚入口用于还原从重复工作中识别 MCP 机会的处理过程，可以按阶段和版本聚合；敏感正文留在受控存储中，不复制到日志与指标。

能力边界可能是合法的空结果，但必须带范围、版本和原因；任务明确要求找到材料时，同一个空结果进入拒答而非成功。

依赖返回成功状态只证明传输完成。从重复工作中识别 MCP 机会还要检查机会清单是否满足业务范围、质量阈值和当前版本，明确拒绝也可能是正确终态。

现有 API 或 CLI 的状态迁移必须单调：完成不能退回运行中，取消不能被迟到结果覆盖，失败重试也不能绕过入口已经固定的权限。

从重复工作中识别 MCP 机会的成功证据最终要同时回答输入是什么、执行了哪些步骤、交付了什么以及为什么停止；任一项缺失都应留在未确认状态。

从重复工作中识别 MCP 机会把业务验收与服务健康分开。依赖返回 200 只说明传输成功，机会清单仍要满足当前范围和质量要求；明确拒答也可能是正确终态。

从重复工作中识别 MCP 机会的观测指标按阶段和版本聚合。评估 MCP 时，把错误、空结果、拒绝、恢复和资源消耗分开统计，避免一个成功率掩盖不同故障。

## 发现权限或收益不足时停止

MCP 机会分析的故障要回到流程本身：接口不可用属于依赖失败，重复成本估错属于判断失败，工具回执缺字段属于契约失败，交付后没有审计则属于治理缺口。不同责任层要分别修复，不能靠重新调用一次模型掩盖评估错误。

遇到从“能做 MCP”反推需求时，先记录发生阶段、错误类别和责任对象。从重复工作中识别 MCP 机会保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

遇到把一次性流程协议化时，先记录发生阶段、错误类别和责任对象。从重复工作中识别 MCP 机会保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

遇到 Server 暴露底层数据库时，先记录发生阶段、错误类别和责任对象。从重复工作中识别 MCP 机会保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

遇到没有身份模型时，先记录发生阶段、错误类别和责任对象。从重复工作中识别 MCP 机会保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

遇到忽略客户端并不支持所需能力时，先记录发生阶段、错误类别和责任对象。从重复工作中识别 MCP 机会保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

从重复工作中识别 MCP 机会将终态、可重试性和资源清理结果写入记录；后台扫描器根据现有 API 或 CLI 判断任务是在运行、等待恢复还是已失败。

从重复工作中识别 MCP 机会执行前固定 Deadline、动作上限、重复签名、无进展阈值、预算和取消信号；任一条件触发，选择能力停止创建新工作。

从重复工作中识别 MCP 机会把重试时间和次数计入总预算。MCP 每次重试先扣减剩余额度，达到上限就保留原始错误。

从重复工作中识别 MCP 机会的清理动作设计成幂等操作；仍被活动任务或 Lease 引用的资源拒绝删除。

## 用客户端和协议样本验证

抽样一周内的重复任务，按输入变化、系统边界、实时性、调用者和失败责任评分，并用最小 Server 验证一个高价值候选；测试显式给出重复步骤、初始现有 API 或 CLI、预期机会清单和终止原因，不能只断言返回值非空。

从重复工作中识别 MCP 机会的单元测试用 Fake Adapter 固定机会清单与错误，断言参数、调用顺序、状态修订和清理动作，这些结果只证明本地控制逻辑。

契约测试围绕重复步骤、现有 API 或 CLI 和能力边界构造合法与非法样本，Schema 解析成功后继续检查权限、版本与领域不变量。

故障测试注入从“能做 MCP”反推需求和把一次性流程协议化，记录选择能力是否被调用、现有 API 或 CLI 是否改变、资源是否释放，以及同一身份重试会不会重复执行。

从重复工作中识别 MCP 机会的集成测试连接真实协议与隔离存储，检查序列化、约束、并发和超时；需要在线服务时另行记录服务版本、时间、配置与凭证条件。

从重复工作中识别 MCP 机会的回归报告要保留失败类型分布。在 MCP 的回归中，拒绝、超时、权限错误和空结果必须保持各自类型，状态变化本身就是行为契约。

从重复工作中识别 MCP 机会的性质测试随机改变现有 API 或 CLI 顺序、重复提交、完成顺序或状态版本，断言权限不扩大、终态不倒退、同一身份不产生两次副作用。

MCP 的离线评测关注质量变化，运行时测试关注控制和恢复，两类证据都齐全才可交付。从重复工作中识别 MCP 机会只有两类证据都存在，才能同时回答“结果是否合格”和“系统是否安全完成”。

## 共享能力的维护成本

MCP 机会评估要锁定被复用的 API 或 CLI 版本、认证方式和返回 Schema。接口升级后，旧的重复步骤仍按原合同回放，只有完成兼容性测试才能把新版本纳入能力目录。

从重复工作中识别 MCP 机会的容量主要受上下文大小、并行任务、外部工具、测试时长和审查成本影响，并发可能缩短单次等待，也会占用连接、配额、内存和下游吞吐，必须沿读取任务约束、收集仓库证据、选择能力、执行最小改动、验证并交付逐层核算。

从重复工作中识别 MCP 机会的候选版本在固定样本上比较正确性、错误类型、延迟和资源消耗，从“能做 MCP”反推需求等安全红线回归时直接停止发布，不能用平均质量抵消。

从“能做 MCP”反推需求的降级路径在发布前写好，可以减少非关键增强、返回已经确认的机会清单，或明确暂时无法确认，缺失事实不能交给模型补写。

评估一组重复步骤时，先用 `request_id` 找到调用频率、输入来源、权限边界、失败回执和人工补救时间，再比较封装成工具后的收益。没有这些记录，就不能仅凭“看起来重复”决定引入 MCP。

从重复工作中识别 MCP 机会的数据按证据用途分级保留，聚合字段可以留得更久，重复步骤和大体积机会清单设置短期限、访问控制与删除通道。

从重复工作中识别 MCP 机会先在单进程实现现有 API 或 CLI、超时、错误和测试，只有恢复与容量证据提出要求时，再增加队列、Lease、分布式缓存或工作流引擎。

从重复工作中识别 MCP 机会的监控阈值要对应可执行动作。

回滚要覆盖代码之外的状态。从重复工作中识别 MCP 机会若改变 Schema、缓存键或持久化记录，旧版本是否还能读取新写入数据必须提前验证；无法双向兼容时采用候选版本隔离。

## 什么时候用普通 API 更合适

采用从重复工作中识别 MCP 机会前先画出重复步骤到机会清单的最小控制图；固定函数已经能完成任务时，新增模型决策和跨进程现有 API 或 CLI 只会扩大测试与运维范围。

MCP 与自动化脚本的区别在于能力是否能被多个客户端发现并按合同调用。脚本仍可由程序固定步骤驱动，MCP 只提供受控能力目录，不替客户端决定业务流程，也不替后端确认权限。

CLI 可以与从重复工作中识别 MCP 机会组合，但外部知识仍需授权，工具调用仍需校验，模型产生的机会清单仍停留在候选状态。

从重复工作中识别 MCP 机会适合价值足够、从“能做 MCP”反推需求可观察且预算可接受的任务，高风险、不可逆的决定需要确定性规则或人工批准。

格式正确但事实错误的机会清单是必要反例；若它直接进入成功，说明执行最小改动缺少业务验证，应保留候选并给出证据问题。

执行期间修改重复成本可以检验并发设计，旧动作若仍能覆盖现有 API 或 CLI，说明版本或 Lease 有缺口，增加 Prompt 规则无法修复这类竞态。

识别 MCP 机会会引入新的连接层和权限责任。记录中既要说明复用收益，也要写清新增的失败、撤销和回滚路径。

先用一个现有 API、几类明确错误和确定性测试验证机会，再考虑并发、缓存或队列。

如果需求无法说明实时性、权限和失败责任，先保留现有脚本，不因为“可以接 MCP”就增加协议层。

## MCP 机会的最小试点

把“一个查询动作被多个客户端重复实现”缩成一个本地可以完成的小实验。入口先写目标、输入、可修改范围和验收命令，客户端数量、发现需求、权限、生命周期和失败成本由文件或内存仓库保存，模型输出只作为候选。

实现顺序从确定性步骤开始，再接入工具或协议。正常结果同时满足形状和领域条件，只有一层转发却没有复用收益用稳定错误表示。不要把“MCP 机会”的 Fake Adapter、内存存储或本地测试成功写成远程服务已经可用。

“MCP 机会”的故障样本至少包含缺少输入、权限拒绝、超时、重复提交和取消。“MCP 机会”的每种样本都断言调用次数、状态修订、资源清理和最终报告，修复后重新执行同一命令。

评审“MCP 机会”时比较直接实现与新增能力的成本、可替换性和故障面。先保留普通 API，证据足够再协议化。

把“MCP 机会”的一次成功和一次失败都交给另一位开发者复现，观察他能否根据日志找到责任层。如果只能重新阅读“MCP 机会”的完整 Prompt 才能理解，说明契约或事件还不够清楚。

示例的结论范围限于当前解释器、依赖和隔离资源。“MCP 机会”使用的真实凭证、网络服务、生产数据和发布授权另行验证，不能从本地退出码推导出来。

## MCP 机会的边界案例

在“MCP 机会”中，入口收到的资料可能不完整，程序先保存缺口和当前版本，不能让模型用常识填入 客户端数量、发现需求、权限、生命周期和失败成本。“MCP 机会”的输入后来补齐时，新的执行沿同一个任务 ID 继续；已经结束的失败记录不被覆盖。

只有一层转发而没有复用收益时，记录客户端数量、发现请求、实际鉴权检查和一次调用的维护成本。未发现、发现失败、工具执行成功但返回空值、下游状态未知应分开统计，避免把“接上协议”误当成机会成立。

“MCP 机会”的正常输出先经过范围、版本和权限检查，再进入交付或下一个节点。先保留普通 API，证据足够再协议化。“MCP 机会”的输出只满足结构而没有可验证来源时，状态保持为候选，前端应显示缺口而不是成功标记。

用重复提交、并发完成、取消和进程退出四个样本回归。回归“MCP 机会”时，检查同一幂等键是否只产生一个有效终态，迟到事件是否被拒绝，临时资源是否释放，重新连接是否能读到同一份事件。

这组检查的结果应带命令、解释器或服务版本、输入摘要和退出码。“MCP 机会”没有运行证据时，只能写“待验证”；离线替身通过也不能推导真实模型、网络服务或生产权限已经通过。
