# SubAgent 协作：拆分任务、并行取证与结果合并

并行可以缩短等待，也会增加任务串线、重复修改和迟到结果覆盖新状态的风险。适合交给 SubAgent 的工作必须拥有窄目标、独立输入和可单独验收的输出。只把一份长任务切成三段自然语言，不会形成安全的协作边界。

假设主任务要定位一个构建失败，同时核对依赖变更和测试覆盖。三项调查可以并行读取不同证据，最终修改仍由一个明确所有者完成。

## 任务边界要能独立判定完成

子任务写清目标、允许读取的范围、是否可写、预期产物、验收方式和停止条件：

```json
{
  "taskId": "dependency-audit",
  "goal": "找出锁文件变化对应的直接依赖升级",
  "readScope": ["package.json", "lockfile", "release-notes"],
  "writeScope": [],
  "output": "带文件位置的版本差异与兼容风险",
  "stop": "缺少锁文件时返回 evidence_missing"
}
```

“研究一下为什么失败”缺少验收边界，子任务可能重复主任务已经完成的排查，也可能修改无关文件。

## 并行前检查依赖和写入集合

两个任务存在数据依赖时应串行。测试分析必须读取代码修复后的结果，就不能与修复同时开始。两个任务都要写同一文件，也不适合直接并行；即使修改不同段落，格式化和导入排序仍可能冲突。

只读任务也可能争用外部配额或读取变化中的快照。创建子任务时固定代码修订、规则版本和知识范围，合并前再检查主工作区是否变化。旧快照上的结论可以保留为历史证据，不能覆盖新版本。

## 上下文按任务最小化

子任务只接收完成目标所需的规则、文件和工具。把父任务全部对话和权限复制过去，会让旧假设进入新判断，也扩大误操作范围。

父任务中的身份和权限由运行时传递，不能让子任务从自然语言中自行选择。需要额外文件时，子任务返回请求，由父任务确认是否扩大范围。范围扩大应产生新的合同版本。

## 合并依据稳定 ID

每个结果带 `taskId`、输入修订、终态、证据引用和未完成项。先完成的结果只代表耗时较短，不代表优先级更高。主任务按合同槽位收集结果，再处理冲突。

依赖审计说“升级会破坏 API”，测试调查却找到兼容用例时，合并器保留两个来源和冲突类型，不让综合模型任选一个。关键证据缺失时，最终状态显示部分完成。

## 可写任务需要单一所有者

稳妥的方式是子任务提交分析或补丁候选，主任务统一应用。确实需要多个可写单元时，为每个任务分配互不重叠的文件集合，并记录变更基线。提交前检查越界文件和当前版本，冲突后回到人工合并。

测试、格式化和构建属于共享验证，通常在合并后由父任务运行。子任务的局部测试只能证明候选在其快照上成立。

## 合并器要验证结果合同

子任务返回自然语言摘要还不够。合并前先校验 taskId、输入修订、证据引用、修改文件集合和终态，再把结果放入父任务的对应槽位。缺少必需字段的结果进入 rejected_result，不继续交给综合模型猜测。

```ts
type ChildResult = {
  taskId: string
  contractVersion: number
  baseRevision: string
  status: 'complete' | 'incomplete' | 'failed' | 'cancelled'
  evidenceIds: string[]
  touchedFiles: string[]
}
```

两个结果引用同一文件时，先比较是否违反 writeScope，再比较 baseRevision。即使文本补丁可以自动合并，语义上也可能同时修改同一合同，仍需要单一所有者重新验证。结果没有文件冲突，也可能因共享类型、生成文件或锁文件产生依赖冲突，合并后测试负责发现这类跨文件关系。

父任务终态使用单调规则。必需子任务未完成时，父任务不能进入 complete；父任务已 cancelled 后，迟到的 complete 只写审计，不恢复执行。状态约束放在运行时，不能依赖模型读懂时间顺序。

## 超时、取消和迟到结果

父任务取消后停止创建新子任务，并向活动任务传播取消。已经发出的外部写操作要查询回执，不能假定取消等于回滚。子任务超时后保留已取得证据，终态标记为 incomplete。

迟到结果写入时比较任务版本和父任务状态。父任务已完成或合同已修订，结果进入审计记录，不再参与当前合并。重试沿用稳定任务身份并增加尝试号，避免产生两份有效结果。

## 用故障样本验证协作

至少覆盖读写范围越界、两个任务返回同名文件、必需任务超时、父任务取消和工作区中途变化。断言结果没有串线，终态不会倒退，临时资源已清理，缺少证据时没有生成确定结论。

并行是否值得应从真实 Trace 判断。若模型调用很短，拆分、传递上下文和合并的成本可能更高；若任务拥有独立慢 I/O 和不同权限，窄合同可以同时降低等待和权限并集。
