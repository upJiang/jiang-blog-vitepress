# 实现文章检查 Skill：规则、脚本与评测

文章检查同时包含确定规则和编辑判断。Markdown 语法、链接目标、隐私词和 frontmatter 可以由程序检查；论证是否连续、例子能否支撑结论，需要阅读上下文。把两类问题都交给模型，会让稳定门禁随措辞波动。

这篇文章把检查过程拆成可执行链路，输出是带证据的问题清单和经过确认的修改，不追求一次调用自动改完全文。

## 通过条件必须可以观察

规则应描述可观察结果，比如“本地链接必须存在”“代码围栏必须带语言”“公开正文不得出现本机绝对路径”。“文章要有深度”无法直接做布尔判断，需要拆成核心概念是否有定义、机制、边界和验证等审阅维度。

```ts
type Issue = {
  code: string
  file: string
  line?: number
  evidence: string
  severity: 'error' | 'warning' | 'review'
  fixable: boolean
}
```

`error` 阻断发布，`warning` 表示已确认风险，`review` 留给语义判断。严重级别来自规则，不由模型临时提高。

## 检查链按证据成本排序

先解析文件和 frontmatter，再检查代码围栏与链接，随后做隐私扫描，最后调用模型审阅正文。入口错误时停止昂贵步骤，避免对无法构建的文件继续消耗 Token。

```mermaid
flowchart LR
  A[解析 Markdown] --> B[结构与链接]
  B --> C[隐私扫描]
  C --> D[语义审阅]
  D --> E[差异确认]
  E --> F[复跑检查]
```

每一步保存输入哈希。文件在审阅中被其他进程修改，旧问题不能直接写回新版本；重新读取后再生成补丁。

## 链接检查要理解路径语义

本地链接去掉锚点和查询参数，按当前文件目录解析，再判断目标文件或 VitePress 路由是否存在。标题锚点还要遵循站点的 slug 规则。外部 URL 容易受限流、登录和地区影响，应区分“访问成功”“暂时不可达”和“本次未检查”。

代码围栏检查只确认语法和语言标签，不证明代码可运行。可执行示例需要独立测试命令，伪代码则在正文标识，避免读者把教学片段当成完整实现。

## 隐私扫描不能过度承诺

绝对路径、凭证格式、内网主机和私有项目名可以先用规则匹配。命中后只保留最小证据并遮蔽敏感片段，报告不应再次完整复制秘密。没有命中只表示当前规则未发现问题，不等于整篇文章已经脱敏。

模型接收正文、当前规范和确定性结果，输出限定为候选问题，包含引用段落、缺失机制和修改理由。模型不直接宣布链接存在，也不修改导航字段。

## 自动修复范围要小

全角标点、明确的破折号替换和缺失语言标签可以生成候选补丁。删段、重排章节、修改技术结论会改变作者意图，需要人工确认。补丁应用后重跑检查，新的错误归属于新版本，不覆盖原记录。

检查器自身失败也要进入结果。链接脚本崩溃、模型超时和规范文件缺失分别标记，不能合并成“文章未通过”。

## Markdown 要经过语法树再检查

标题、链接、代码块和 frontmatter 属于结构化语法，直接用正则扫描整份 Markdown 会把代码示例里的链接当成正文，也会在嵌套围栏、转义字符和 HTML 块上误报。检查器应先用与站点构建一致的解析器生成 AST，再让规则访问节点类型、源码位置和解析后的目标。

```ts
type CheckContext = {
  file: string
  sourceHash: string
  ast: unknown
  routeIndex: ReadonlyMap<string, string>
  policyVersion: string
}

type Rule = (context: CheckContext) => readonly Issue[]
```

本地链接规则从 Link 节点取目标，代码围栏规则只访问 Code 节点，隐私规则按文本节点、代码节点和链接目标分别配置。外部链接检查使用有界并发、超时和缓存，并保留最终 URL 与状态分类；301、401、429、DNS 失败和 TLS 失败不能归成同一种断链。

自动修复也从节点位置生成补丁，并在应用前比较 `sourceHash`。文件已经变化就放弃旧补丁，重新解析。这样才能避免语义审阅耗时期间覆盖作者刚写入的内容。

## 评测同时看误报和漏报

准备一组小型样本，故意放入断链、错误围栏、路径泄漏、缺少边界的结论和完全正常的段落。规则检查断言精确位置，语义审阅允许有限措辞差异，但必须命中对应问题类型并引用正确证据。

规则版本、模型版本和文章哈希一起写入报告，才能解释同一篇文章为何得到不同结果。最终交付明确哪些检查真实运行、哪些依赖替身、哪些外部事实仍待验证。
