# Coding Harness 排障：上下文、工具、环境与反馈

沿一次不可重复任务的 Trace 区分输入截断、工具失败、越界修改、卡循环和恢复错误。**Harness**、**Context Engineering**、**Troubleshooting** 分别指向同一条执行链上的不同对象：原任务、上下文快照、工具调用、文件差异、进程输出、测试结果、权限事件和终止原因进入系统，Trace、阶段、上下文预算、工具状态、工作区版本、循环计数、Checkpoint 和恢复次数保存处理中间状态，最终得到故障层级、证据链、最小修复、回归用例和仍未知的部分。

Coding Harness 位于编码 Agent 失败时从输入到环境的分层诊断层，主要机制是先确认输入是否完整，再检查工具契约、环境与权限，随后检查修改和测试，最后检查循环与恢复；每层只用可观察证据排除。直接改 Prompt、把环境错误归因模型、重复运行破坏性命令、恢复到错误工作区、日志缺调用身份和只修当前问法会让链路在不同位置停止，错误记录必须保留发生阶段、当时的状态和终止原因。

::: info 贯穿示例

Coding Harness 场景：编码 Agent 多次声称完成，但文件没有变化，随后重试又修改了错误目录，需要从 Trace 找到第一处偏差。Coding Harness 需要的身份、权限、版本和业务事实由应用提供，模型与外部内容只产生候选。

:::

## 先保存症状和执行范围

直接改 Prompt 会破坏 Trace 与故障层级之间的对应关系，排查时先保留原始输入摘要和发生阶段，再判断是否允许重试。

把环境错误归因模型影响阶段或下游解释，不能和直接改 Prompt 共用“重新调用一次模型”的处理方式。

## 排障对象是控制链而不是一句提示词

Harness 实践中，执行者负责计划和改动，工具提供证据，脚本负责可重复检查。因此 Trace 与阶段要有唯一写入方，其他组件只能通过版本化命令申请修改。

系统排障与 Coding Harness 解决的问题相邻，但控制权不同，比较时要看谁选择选择能力、谁保存 Trace、谁确认故障层级。

Trace 可以参与同一请求，却不能替代 Coding Harness；组合后仍要单独检查上下文快照的可信来源和直接改 Prompt 的终止规则。

Coding Harness 使用的身份、范围和版本来自可信运行时，原任务可以表达意图，但不能提升权限或改写活动 Release。

把环境错误归因模型发生时，错误回到阶段的所有者处理，上游缺输入、当前组件违反不变量和下游不可用分别形成不同终态。

Coding Harness 的确定性边界位于 Trace 写入之前。模型在 Harness 中只提交候选值，程序仍要从认证、版本和策略快照补入可信字段。

Coding Harness 内部可以使用更细的临时对象，跨边界只暴露稳定协议。替换系统排障时，调用方不需要理解内部缓存和 SDK 响应。

## 请求、工具、环境和反馈各自保存什么

Coding Harness 的输入合同至少列出原任务、上下文快照和工具调用，每项都注明来源、是否必需、允许的缺省值，以及缺失后是在入口拒绝还是进入降级路径。

排查 Coding Harness 时，Trace 负责串起调用，阶段记录当前拥有控制权的执行边界，上下文预算则说明某段输入为何被裁剪或拒绝。三类记录必须带同一个 Run ID 和版本快照，否则看到的只是零散日志，无法判断卡住发生在读取、修改还是验证。

并发分支按稳定身份合并上下文预算，完成顺序只反映耗时，不能决定结果属于哪个请求，更不能让迟到的旧状态覆盖新修订。

输出合同同时描述故障层级和证据链，并为拒绝、取消、部分完成和未知状态提供固定形状，调用方据此分支，无需解析错误文案猜测结果。

阶段参与乐观并发检查；处理开始后若版本变化，旧候选只保留作审计，不能继续写入 Trace。

原任务里若包含模型填写的同名字段，应用会丢弃它，再从认证、配置或活动版本中补入可信值，因为结构校验通过不等于授权或业务校验通过。

需求假设、文件定位、差异、命令输出、失败说明和回滚入口组成 Coding Harness 的最小追踪材料，日志只保存稳定 ID、版本和错误类，完整 Prompt、文档正文与凭证不进入指标标签。

撤回或删除上下文快照时，相关缓存、候选和未完成任务按版本失效；稳定 ID 可以保留审计关系，已撤回内容不能继续进入故障层级。

契约还需要描述新鲜度。阶段对应的数据发生变化后，旧缓存、旧候选和未完成任务怎样失效，应由版本或时间规则直接判断，不能依赖模型注意到矛盾。

删除和撤回也属于数据生命周期。Coding Harness 引用的原始对象被移除时，稳定 ID 可以保留审计关系，正文与派生结果则按策略失效，避免继续向用户展示过期内容。

::: warning Coding Harness 的可信边界

故障层级通过结构校验后仍是候选。Coding Harness 使用的身份、权限、知识版本与业务事实由应用从可信服务读取，核对完成后才能执行或交付。

:::

## 从输入到回执逐层取证

Coding Harness 要对照同一个 Run ID 的时间线：输入快照、工具参数、工作区差异、测试退出码和恢复动作逐项出现。某一步没有对应 Span 或阶段状态，排障结论就只能保留为未确认，而不是继续往下猜。

读取任务约束接收原任务并建立 Trace，入口校验未通过就地结束，后续模型、检索器或工具调用次数保持为零。

选择能力读取阶段并执行主题逻辑，参数由应用组装，外部返回先保存为证据链，尚未获得修改领域状态的资格。

执行最小改动检查结构、范围、版本和主题不变量；故障层级缺少来源、落在旧版本或越过权限时，Trace 停在 rejected 或 failed。

验证并交付先保存故障层级与终止原因，再产生事件或通知，交付失败可以重放，核心状态写入失败则不能对外宣称完成。

选择能力出现部分结果时，由任务合同决定保留、补偿还是整体丢弃；故障层级若可重建就重新生成，外部副作用则查询回执或执行补偿。

实现可以使用函数、Graph、Middleware 或 Workflow，Trace 的所有权和直接改 Prompt 的停止规则不会随框架改变。

部分成功需要在步骤边界处理。选择能力已经产生一部分故障层级时，程序按任务合同决定保留、补偿或整体丢弃，并记录未完成项，不能默认为全部成功。

选择能力和执行最小改动都要写明逆向动作或不可逆原因，故障层级若可重建就删除后重算，已发送的外部命令只能查询回执或补偿。

## 沿一次“没有反应”推演

沿“Coding Harness 场景：编码 Agent 多次声称完成，但文件没有变化，随后重试又修改了错误目录，需要从 Trace 找到第一处偏差”推演 Coding Harness：入口创建 request_id，读取可信身份，把原任务和当前版本写入初始状态。

读取任务约束生成 Trace 与输入摘要；若上下文快照缺失，请求返回 rejected，并指出缺少哪项材料，不继续消耗模型或外部服务配额。

选择能力按“先确认输入是否完整，再检查工具契约、环境与权限，随后检查修改和测试，最后检查循环与恢复；每层只用可观察证据排除”推进，每次依赖调用保存 call_id、参数摘要、开始时间与状态版本，以便判断超时前是否已经产生结果。

候选结果对应故障层级、证据链、最小修复、回归用例和仍未知的部分，执行最小改动逐项检查权限、版本与领域约束，问题列表为空才允许形成下一状态。

验证并交付写入终态；客户端断开只影响交付通道，重新连接时读取已经保存的 Trace 或事件游标，不重跑核心逻辑。

故障注入选择重复运行破坏性命令，程序保留原候选和错误位置，只重做失败边界，不能从入口复制整个任务并产生第二份状态。

推演结束后用 request_id 关联 Trace、故障层级与终止原因，测试据此排除并发请求串线，并确认失败路径没有遗留未关闭资源。

Coding Harness 在输入拒绝时不调用依赖，正常路径按 5 个阶段推进，有限修复只重做失败边界。调用次数是控制流断言，不是性能宣传。

Coding Harness 的最终记录用 request_id 关联 Trace、故障层级和失败问题，测试据此证明结果来自本次执行，没有混入并发请求。

## 正常回执和未知状态

Coding Harness 正常完成时，Trace、阶段和故障层级指向同一次执行，重复读取返回同一终态，未完成分支已经取消或有明确所有者。

需求假设、文件定位、差异、命令输出、失败说明和回滚入口用于还原 Coding Harness 的处理过程，可以按阶段和版本聚合；敏感正文留在受控存储中，不复制到日志与指标。

证据链可能是合法的空结果，但必须带范围、版本和原因；任务明确要求找到材料时，同一个空结果进入拒答而非成功。

依赖返回成功状态只证明传输完成。Coding Harness 还要检查故障层级是否满足业务范围、质量阈值和当前版本，明确拒绝也可能是正确终态。

Trace 的状态迁移必须单调：完成不能退回运行中，取消不能被迟到结果覆盖，失败重试也不能绕过入口已经固定的权限。

Coding Harness 的成功证据最终要同时回答输入是什么、执行了哪些步骤、交付了什么以及为什么停止；任一项缺失都应留在未确认状态。

Coding Harness 把业务验收与服务健康分开。依赖返回 200 只说明传输成功，故障层级仍要满足当前范围和质量要求；明确拒答也可能是正确终态。

Coding Harness 的观测指标按阶段和版本聚合。评估 Harness 时，把错误、空结果、拒绝、恢复和资源消耗分开统计，避免一个成功率掩盖不同故障。

## 失败责任层和停止条件

Coding Harness 的故障应从现象回到证据：没有文件内容是读取权限问题，差异不符合预期是编辑问题，测试未启动是执行边界问题，测试通过却没有交付摘要则是验收问题。每层都有自己的复现命令，重复让 Agent 重试会让工作区更难回放。

遇到直接改 Prompt 时，先记录发生阶段、错误类别和责任对象。Coding Harness 保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

遇到把环境错误归因模型时，先记录发生阶段、错误类别和责任对象。Coding Harness 保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

Coding Harness 处理重复运行破坏性命令时需要稳定身份和结果回执，再次收到同一请求先读取旧结果；外部结果未知就停在 unknown，不能猜测失败后重新执行。

遇到恢复到错误工作区时，先记录发生阶段、错误类别和责任对象。Coding Harness 保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

遇到日志缺调用身份时，先记录发生阶段、错误类别和责任对象。Coding Harness 保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

遇到只修当前问法时，先记录发生阶段、错误类别和责任对象。Coding Harness 保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

Coding Harness 将终态、可重试性和资源清理结果写入记录；后台扫描器根据 Trace 判断任务是在运行、等待恢复还是已失败。

Coding Harness 执行前固定 Deadline、动作上限、重复签名、无进展阈值、预算和取消信号；任一条件触发，选择能力停止创建新工作。

Coding Harness 把重试时间和次数计入总预算。Harness 每次重试先扣减剩余额度，达到上限就保留原始错误。

Coding Harness 的清理动作设计成幂等操作；仍被活动任务或 Lease 引用的资源拒绝删除。

## 用事件序列复现故障

录制一次因输入截断失败的任务，再分别注入工具超时、权限拒绝、测试失败和卡循环，验证诊断树能给出不同结论；测试显式给出原任务、初始 Trace、预期故障层级和终止原因，不能只断言返回值非空。

Coding Harness 的单元测试用 Fake Adapter 固定故障层级与错误，断言参数、调用顺序、状态修订和清理动作，这些结果只证明本地控制逻辑。

契约测试围绕原任务、Trace 和证据链构造合法与非法样本，Schema 解析成功后继续检查权限、版本与领域不变量。

故障测试注入直接改 Prompt 和把环境错误归因模型，记录选择能力是否被调用、Trace 是否改变、资源是否释放，以及同一身份重试会不会重复执行。

Coding Harness 的集成测试连接真实协议与隔离存储，检查序列化、约束、并发和超时；需要在线服务时另行记录服务版本、时间、配置与凭证条件。

Coding Harness 的回归报告要保留失败类型分布。在 Harness 的回归中，拒绝、超时、权限错误和空结果必须保持各自类型，状态变化本身就是行为契约。

Coding Harness 的性质测试随机改变 Trace 顺序、重复提交、完成顺序或状态版本，断言权限不扩大、终态不倒退、同一身份不产生两次副作用。

Harness 的离线评测关注质量变化，运行时测试关注控制和恢复，两类证据都齐全才可交付。Coding Harness 只有两类证据都存在，才能同时回答“结果是否合格”和“系统是否安全完成”。

## 日志、预算和长期维护

排障记录必须把运行时版本、工具协议和 Trace Schema 一起保存。命令回执的字段发生变化时，旧记录仍按原 Schema 读取，新的字段只能通过版本化迁移加入，不能在查询时凭空补齐。

Coding Harness 的容量主要受上下文大小、并行任务、外部工具、测试时长和审查成本影响，并发可能缩短单次等待，也会占用连接、配额、内存和下游吞吐，必须沿读取任务约束、收集仓库证据、选择能力、执行最小改动、验证并交付逐层核算。

Coding Harness 的候选版本在固定样本上比较正确性、错误类型、延迟和资源消耗，直接改 Prompt 等安全红线回归时直接停止发布，不能用平均质量抵消。

直接改 Prompt 的降级路径在发布前写好，可以减少非关键增强、返回已经确认的故障层级，或明确暂时无法确认，缺失事实不能交给模型补写。

处理一个卡住的编码任务时，先用 `request_id` 找到最后一条观察、命令的启动与退出记录、工作区差异和验证事件，再决定重试命令、恢复快照还是交给人工。责任层由回执确定，不由 Harness 的最终文案决定。

Coding Harness 的数据按证据用途分级保留，聚合字段可以留得更久，原任务和大体积故障层级设置短期限、访问控制与删除通道。

Coding Harness 先在单进程实现 Trace、超时、错误和测试，只有恢复与容量证据提出要求时，再增加队列、Lease、分布式缓存或工作流引擎。

Coding Harness 的监控阈值要对应可执行动作。

回滚要覆盖代码之外的状态。Coding Harness 若改变 Schema、缓存键或持久化记录，旧版本是否还能读取新写入数据必须提前验证；无法双向兼容时采用候选版本隔离。

## 什么时候退回人工排查

采用 Coding Harness 前先画出原任务到故障层级的最小控制图；固定函数已经能完成任务时，新增模型决策和跨进程 Trace 只会扩大测试与运维范围。

Coding Harness 关注的是动作链能否被复现。Harness 保存候选动作和回执，系统组件确认进程、文件系统或网络的事实；两者都不能用模型的解释替代原始证据。

Trace 可以与 Coding Harness 组合，但外部知识仍需授权，工具调用仍需校验，模型产生的故障层级仍停留在候选状态。

Coding Harness 适合价值足够、直接改 Prompt 可观察且预算可接受的任务，高风险、不可逆的决定需要确定性规则或人工批准。

格式正确但事实错误的故障层级是必要反例；若它直接进入成功，说明执行最小改动缺少业务验证，应保留候选并给出证据问题。

执行期间修改阶段可以检验并发设计，旧动作若仍能覆盖 Trace，说明版本或 Lease 有缺口，增加 Prompt 规则无法修复这类竞态。

Harness 排障会增加 Trace、依赖调用和恢复责任。记录中要把新增的停止、降级与回滚路径写出来。

先用一个 Trace 和几类明确错误验证责任定位，再考虑并发、缓存或队列。

只有证据指向模型理解错误时才改 Prompt，其他故障先修复对应的协议、权限或运行时边界。

## 从症状回到责任层

排查 Harness 时先记录用户输入、任务 ID、工具目录版本、工作区快照和完整命令。症状“没有输出”可能来自模型流为空、工具未注册、权限拒绝、进程被取消或事件交付断线，不能只修改 Prompt。沿 Trace 查看每一层是否产生输入和输出，先判断请求有没有进入 Runtime，再判断模型是否返回候选，最后检查工具和事件是否完成。

修复按最小责任层推进。Schema 解析失败修复适配器或契约，工具超时修复 Deadline 和重试，路径越界修复沙箱规则，事件缺帧修复游标和持久化，只有确认模型理解错误才调整描述或示例。每次修改保留原始失败样本，新增一个同类变体，避免针对某句问法加关键词特判。

回归顺序是 Fake Adapter 单元测试、隔离文件系统测试、协议集成测试和真实环境冒烟。测试报告区分已执行、跳过和需要凭证的部分。排障完成后删除临时密钥和截图，保留错误分类、修复版本和仍存在的边界，方便下一次故障直接定位。

## Harness 排障的事件自测

把“一次执行显示“没有反应””缩成一个本地可以完成的小实验。入口先写目标、输入、可修改范围和验收命令，上下文装配、工具调用、进程回执、验证和交付事件由文件或内存仓库保存，模型输出只作为候选。

实现顺序从确定性步骤开始，再接入工具或协议。正常结果同时满足形状和领域条件，过期快照、命令阻塞或渠道断开用稳定错误表示。不要把“一次执行显示“没有反应””的 Fake Adapter、内存存储或本地测试成功写成远程服务已经可用。

“一次执行显示“没有反应””的故障样本至少包含缺少输入、权限拒绝、超时、重复提交和取消。“一次执行显示“没有反应””的每种样本都断言调用次数、状态修订、资源清理和最终报告，修复后重新执行同一命令。

评审“一次执行显示“没有反应””时比较直接实现与新增能力的成本、可替换性和故障面。按最后稳定事件决定重试或停止。

把“一次执行显示“没有反应””的一次成功和一次失败都交给另一位开发者复现，观察他能否根据日志找到责任层。如果只能重新阅读“一次执行显示“没有反应””的完整 Prompt 才能理解，说明契约或事件还不够清楚。

示例的结论范围限于当前解释器、依赖和隔离资源。“一次执行显示“没有反应””使用的真实凭证、网络服务、生产数据和发布授权另行验证，不能从本地退出码推导出来。

## 一次执行显示“没有反应”的边界案例

在“一次执行显示“没有反应””中，入口收到的资料可能不完整，程序先保存缺口和当前版本，不能让模型用常识填入 上下文装配、工具调用、进程回执、验证和交付事件。“一次执行显示“没有反应””的输入后来补齐时，新的执行沿同一个任务 ID 继续；已经结束的失败记录不被覆盖。

过期快照要带上快照版本与当前版本，命令阻塞要保存进程组和超时原因，渠道断开则区分进程是否仍在运行。没有启动、启动后退出、执行完成但无产物、产物尚未确认分别进入不同状态，恢复动作先查询回执再决定是否重跑。

“一次执行显示“没有反应””的正常输出先经过范围、版本和权限检查，再进入交付或下一个节点。按最后稳定事件决定重试或停止。“一次执行显示“没有反应””的输出只满足结构而没有可验证来源时，状态保持为候选，前端应显示缺口而不是成功标记。

用重复提交、并发完成、取消和进程退出四个样本回归。回归“一次执行显示“没有反应””时，检查同一幂等键是否只产生一个有效终态，迟到事件是否被拒绝，临时资源是否释放，重新连接是否能读到同一份事件。

“一次执行显示“没有反应””这组检查的结果应带命令、解释器或服务版本、输入摘要和退出码。“一次执行显示“没有反应””没有运行证据时，只能写“待验证”；离线替身通过也不能推导真实模型、网络服务或生产权限已经通过。
