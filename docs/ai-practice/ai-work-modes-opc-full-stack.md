# Plan、Auto、Goal 与 OPC：AI 时代的个人全栈工作系统

Plan 描述准备采取的有限步骤，Auto 表示在授权边界内自动连续执行，Goal 保存跨多轮持续追踪的目标，OPC 则把产品、工程和增长工作放进一个个人运营系统。它们处在不同层级：前三者控制 Agent 的执行方式，OPC 组织更长周期的工作。选择更自动的模式不代表需求更清楚或权限更充分。

一个人准备上线订阅产品：访谈用户、设计页面、写前后端、接支付、测试、部署、做 SEO，再看数据。把这段目标交给 Agent 并开启最高权限，看起来最省事，实际把三件事混在一起：需求是否清楚、允许自动执行到哪里、工作要持续多久。

Plan、Auto、Goal 分别回答其中不同问题。把它们选对之后，还要用 Spec、测试、MCP、Skill 和人类门禁把产品到经营连起来。OPC 的价值不是让一个人假装精通所有岗位，而是用系统减少切换和重复，同时让责任留在正确位置。

## Plan、Auto、Goal 不是一条强弱刻度

Plan Mode 用于复杂或模糊任务的调查、澄清和实施方案，默认不执行计划中的仓库修改。Auto 是 Codex 权限预设：典型配置允许在工作区读取、编辑和运行命令，越出工作区或访问网络时由沙箱和审批策略控制。Goal Mode 用于持续数小时或数天的可验证目标，支持进度、暂停和恢复。

| 模式 | 主要输入 | 核心处理 | 输出 | 不代表什么 |
| --- | --- | --- | --- | --- |
| Plan | 模糊目标、仓库事实、约束 | 调查、提问、比较与决策 | 可实施计划 | 不自动执行计划 |
| Auto | 明确任务与工作区权限 | 自动读写和运行允许动作 | 工作区差异与验证 | 不等于 Full Access |
| Goal | 长期目标、完成条件、里程碑 | 持续追踪、Heartbeat、恢复 | 可验证进度或终态 | 不扩大任何权限 |

三者可以组合：先 Plan 澄清订阅范围，再在 Auto 权限内实现局部功能，最后用 Goal 持续追踪上线前的多个里程碑。权限始终由沙箱、审批、MCP/App Tool 授权和外部系统角色决定。

用另一种状态表达：Plan 将 `ambiguous` 变成 `decision_complete`；Auto 决定 `allowed_action` 是否可自动执行；Goal 让 `in_progress` 跨时间持续到 `complete/blocked/cancelled`。它们作用在不同状态维度，因此不存在“Goal 比 Auto 权限更高”的推论。

## 同一个需求怎样选择模式

“增加团队邀请功能”可以处于三种状态。若邀请角色、有效期和计费影响未知，进入 Plan 或 Spec，先读取现有权限模型并询问关键选择。若接口、页面和测试模式都已有，只需增加一个确定字段，用 Auto 完成小范围修改和验证。若目标包含邀请、邮件、审计、灰度和跨天观测，则用 Goal 追踪里程碑。

| 判断问题 | 是 | 否 |
| --- | --- | --- |
| 业务行为或范围仍模糊？ | Plan/Spec | 继续判断 |
| 代码路径未知或方案有明显取舍？ | Plan | 继续判断 |
| 任务可在一轮内完成且授权清楚？ | Auto | 继续判断 |
| 需要跨小时/天持续跟踪与恢复？ | Goal | 普通任务会话 |

选择后仍要写好输入：目标、相关上下文、约束和完成条件。Goal 还需要里程碑、Heartbeat、失败终态和总预算；Auto 还需确认工作区与网络策略；Plan 还需明确哪些决策必须由用户完成。

## Auto 为什么不等于 Full Access

Codex 官方资料将 Auto 描述为工作区写加按需审批的常用预设：可在工作目录读取、编辑、运行命令，工作区外写入或网络访问通常需要审批。具体行为由当前 Surface、配置、组织策略和会话权限决定，应使用状态或权限界面确认。

Full Access 会显著扩大技术边界，仍不等于业务授权。即使进程能访问生产网络，用户没有明确要求部署、扣费或发消息，Agent 也不能自行执行。相反，`approval_policy=never` 只是“不弹审批”，不会给沙箱外能力；被拒动作应失败而不是绕过。

Auto-review 让独立 Reviewer 处理原本需要互动的部分审批，不改变沙箱边界，也不替代生产和外部应用自身的确认。自动化与授权必须分开设计。

## Goal 怎样持续工作但不扩大权限

Goal 以非空、可验证目标开始，持续保存进度并按 Heartbeat 推进。它适合长测试、分阶段迁移准备、持续调研或跨天交付。每次 Heartbeat 只在当前允许工具和环境内继续，不能因为运行时间更长就获得网络、密钥或外部写权限。

目标输入应包含完成条件和终态：例如“目标文章全部可访问、内容门禁通过、旧路由 404、未提交未部署”。状态记录已完成步骤、当前证据、下一检查和阻塞。若外部审批缺失，Goal 保持等待或阻塞，不能把等待时间解释成默许。

恢复时先重新读取工作区和外部状态，因为长任务期间可能有人修改文件或环境。重放有副作用动作要用幂等 ID 或先查最终状态，避免重复发布、发消息和扣费。

## OPC 是责任系统，不是无限自动化

One Person Company 表示一个人承担产品经营的最终责任，AI 扩展调查、生成、验证和运营能力。它不等于无人公司，也不表示一个模型拥有公司账号的全部权限。创始人仍对定位、资金、法律、用户承诺和生产风险负责。

OPC 的输入是用户问题、资源和风险偏好，处理跨产品、设计、工程、增长与运营，输出是可持续业务结果。验证既看软件质量，也看获客、留存、收入、成本和合规。AI 可以提出候选和执行受控流程，人类保留不可逆取舍。

“AI 全栈”也不是一个人记住所有语法，而是能从用户需求走到可运行系统，并知道每层的边界、验证与求助条件。陌生领域需要官方资料、专家 Review 或受控实验，不能让自信文本替代专业责任。

## 一个人怎样组织十类工作

| 角色 | AI 适合协助 | 必须保留的人类判断 | 关键证据 |
| --- | --- | --- | --- |
| 产品 | 访谈整理、竞品与 Spec 草案 | 用户价值、优先级 | 访谈、行为指标 |
| 设计 | 信息架构、状态清单、对照检查 | 品牌与关键体验 | 设计源、可用性结果 |
| 前端 | 组件、状态、响应式、可访问性 | 体验取舍 | 构建、浏览器、视觉检查 |
| 后端 | API、数据、任务和测试 | 领域不变量 | 契约与集成测试 |
| 数据 | 查询、看板和异常候选 | 指标口径与因果 | 版本化 SQL、时间窗口 |
| 测试 | 用例、回归、自动化执行 | 风险接受 | 失败复现与门禁 |
| DevOps | 配置比较、候选预检、Runbook | 生产切流与回滚 | 制品、健康、审计 |
| SEO | 关键词聚类、技术审计、内链建议 | 品牌与内容价值 | 搜索平台和页面证据 |
| 运营 | 内容草案、工单归类、反馈摘要 | 对外承诺与关系 | 发布记录、用户反馈 |
| 复盘 | 聚合轨迹、提取模式 | 归因与长期选择 | 规则、Skill、MCP、评测 |

同一个人可以按阶段切换角色，但不要让实现者视角吞掉验证者视角。高风险领域引入外部专家或第二 Reviewer，AI 不能成为回避专业门槛的理由。

## AI 全栈闭环从需求走向能力沉淀

```mermaid
flowchart LR
  N[需求与指标] --> S[Spec / Plan]
  S --> B[设计与实现]
  B --> V[测试与 Review]
  V --> R[候选发布与人类门禁]
  R --> M[观测与用户反馈]
  M --> L[复盘]
  L --> A[规则 / Skill / MCP / 评测]
  A -.改善下一轮.-> N
```

需求阶段确认谁的问题，Plan 或 Spec 消除歧义，设计与实现产生候选，测试与 Review 提供独立证据，发布由人批准，观测连接真实结果，复盘再选择沉淀层。稳定规则进入 `AGENTS.md`/`CLAUDE.md`，重复方法进入 Skill，外部实时能力进入 MCP，历史失败进入测试和评测。

正常路径最终改善下一轮输入。验证失败回到实现，业务指标无改善回到需求，生产异常先回滚再复盘。闭环不是要求所有步骤全自动，而是每一步有输入、输出、证据和责任。

## 人类门禁放在不可逆和责任节点

| 动作 | AI 可自动准备 | 人类门禁 |
| --- | --- | --- |
| 改工作区代码 | 调查、修改、测试、Review | 接受最终差异 |
| Git 提交与推送 | 生成消息、列差异 | 明确授权提交/推送 |
| 生产发布 | 候选构建、预检、回滚清单 | 切流和异常处置 |
| 数据库与资金 | 生成只读分析、模拟方案 | 写入、删除、支付和退款 |
| 对外内容与消息 | 草拟、校对、排期 | 品牌承诺和真实发送 |
| 法律与隐私 | 检查清单、风险候选 | 专业意见和责任签署 |

门禁要通过权限系统、审批和分离凭证落实，不只写在 Prompt 中。AI 的准备工作应让人快速判断，而不是制造“都已经做到最后一步，只差点确认”的压力。

## 从个人工具箱逐步构建 OPC 系统

第一阶段先做好任务输入和仓库规则，保证 Agent 知道目标、目录、命令与授权。第二阶段把频繁复制的外部事实做成窄 MCP，把重复发布、Review 和报告做成 Skill。第三阶段建立 Spec、测试、候选发布和观测，形成 Harness。

第四阶段才使用 Goal 管理长周期目标和多个里程碑，并建立成本、Heartbeat、取消与恢复。每次只自动化稳定环节，保留异常处理和人工回退；用实际周期、返工、错误和经营指标评估，而不是统计 Agent 调用次数。


**Goal 为什么不会扩大沙箱和审批权限？**

Goal 管理任务持续性，沙箱和审批管理动作能力，外部系统再管理真实身份与角色。它们是独立维度。Goal 每次推进仍只能使用当前允许的文件、网络和 Tool；缺少审批时只能等待或失败。即使目标写“完成生产发布”，也不会凭空生成生产凭证或跳过应用确认。

**一人公司是否不再需要专业协作？**

一个人可以借 AI 覆盖更多基础工作，法律、财务、安全、品牌和高风险工程仍可能需要专业 Review。OPC 缩短信息传递，不取消专业门槛。应提前定义何时引入专家、第二 Reviewer 或外包，让证据承担判断，让人承担责任。

**哪些工作最值得先自动化？**

优先选择高频、规则稳定、输入可得、输出可验证且失败可恢复的任务，例如内容检查、测试执行、报告汇总和只读查询。低频、高歧义、不可逆或依赖关系信任的工作先保留人工。**技术上能自动执行，只是自动化评估的起点。**

**怎样证明 OPC 工作系统改善了业务？**

同时观察需求到发布周期、返工、缺陷、恢复时间、人工等待、模型与工具成本，以及获客、激活、留存和收入。固定口径与时间窗口，把过程效率和业务结果分开。更快发布但用户没有获得价值不算成功，业务改善也不能自动归因于 AI；需要版本化实验、用户反馈和持续复盘逐步建立证据。
