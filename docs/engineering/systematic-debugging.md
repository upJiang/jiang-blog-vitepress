# 系统化调试方法

接口偶尔返回 500，重试又恢复。看到数据库日志里也有错误，很容易直接认定“数据库不稳定”，然后增加重试。若真实原因是连接池耗尽，更多重试只会放大压力。

本篇使用问题、观察、假设、实验、结果和复盘六个阶段定位故障。目标不是一次猜中，而是让每一步都缩小可能范围，并留下可复现证据。

## 第一步：把现象写成可证伪描述

记录环境、版本、入口、时间范围、输入条件、预期和实际结果。将“偶尔很慢”改成“版本 A 在并发读写时，某类请求 P95 上升且返回 503；版本 B 未出现”。先确认监控口径和最近变更，避免把追踪故障当业务故障。

```mermaid
flowchart LR
  P[明确问题] --> O[收集观察]
  O --> H[提出假设]
  H --> E[单变量实验]
  E --> R[比较结果]
  R --> F[修复与回归]
  F --> K[沉淀门禁]
```

## 第二步：沿执行链保存证据

从用户入口依次查看网关、应用、连接池、SQL、队列和外部依赖。使用 requestId、traceId、taskId 关联，同步保存版本和配置。日志、指标与 Trace 各有盲区，单条错误不能代表全局趋势。

调试数据也遵守隐私边界。不要为了方便把 Token、Cookie、正文或数据库快照复制到不受控环境。使用脱敏样本或合成数据复现。

## 第三步：一次只验证一个假设

假设要包含预测：“如果连接池耗尽是原因，那么并发增加时 checkout 等待先上升，SQL 自身耗时保持稳定；提高池大小会暂时降低等待但增加数据库连接。”实验固定其他变量，保留对照组。

二分版本、禁用一个插件、缩小输入、替换依赖为可控 fake 都是实验。性能实验多次运行并报告分布，冷启动与预热分开；并发问题用 barrier 或故障注入放大，而不是依靠肉眼刷新。

## 第四步：区分根因和触发条件

超大请求可能触发 OOM，但根因也可能是无界缓冲；网络抖动触发重试风暴，根因是没有预算。修复既要处理直接缺陷，也要增加资源上限、错误分类和观测，使相同模式不会换个入口再次出现。

| 实验结果 | 下一步 |
| --- | --- |
| 关闭缓存后故障消失 | 检查缓存版本、失效和序列化 |
| SQL 快但连接等待高 | 查长事务、池容量与实例总数 |
| 只在新版本出现 | 二分变更并检查配置差异 |
| 只在真实代理出现 | 查缓冲、超时与请求头 |
| 无法稳定复现 | 增加受控观测，不先宣称根因 |

## 第五步：修复后故意重现旧故障

回归用例要在修复前失败、修复后通过。除了正常路径，还检查失败副作用、并发与恢复。线上或候选验证保留保护指标，异常时可恢复上一版本。

复盘记录事实时间线、影响、根因、为什么原门禁没有发现、修复与后续 owner。避免写“某人操作错误”，应解释系统为何允许一次错误操作扩散。

## 调试何时结束

当问题可复现、根因有证据、修复通过反例、相同风险有门禁并且未验证范围被明确记录时，调试才结束。无法取得关键数据时，结论写成假设与缺口，不用完整故事填补空白。

下一篇把修复放入 Git 和发布链路，区分工作区修改、提交、推送和部署这些不同授权与风险。
