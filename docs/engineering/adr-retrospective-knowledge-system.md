# 技术方案、ADR、复盘与个人知识体系

半年后有人问“为什么选择这个队列”“当时为什么没有做事务 Outbox”，团队只能翻聊天记录。技术方案如果不写约束、替代方案和验证结果，最后只剩一个看似确定的结论。

本章用一条知识 Agent 的“数据库提交后派发任务”决策示例，展示 ADR 怎样记录判断；再用复盘区分事实、假设、结果和行动，最后给出可检索的个人知识卡片结构。

## 先分清三种文字

**事实**能从代码、测试、日志、规范或会议记录直接核对，例如当前没有事务 Outbox。

**判断**是在约束下做出的选择，例如先用数据库恢复扫描而不是立刻引入 Outbox。

**行动**是尚未完成的后续，例如补一个派发失败演练。把行动写成过去式，会让读者误以为能力已经存在。

## ADR 应回答什么

一份 ADR 最小包含：背景、问题、约束、决策、替代方案、后果、验证、状态、日期和关联变更。

```mermaid
flowchart LR
  A[观察到问题] --> B[记录约束与证据]
  B --> C[比较替代方案]
  C --> D[做出可回退决策]
  D --> E[实现与验证]
  E --> F[结果与后续行动]
```

ADR 不是设计文档的百科全书，也不是把所有讨论复制进去。它记录为什么在当时选择了这条路，让未来的人能判断约束变化后是否需要替换。

## 第一步：写一个具体背景

不要写“系统需要高可靠”。改成可核对的场景：API 在数据库事务提交后向 Worker Broker 派发任务；当前代码可能在提交成功后网络失败，任务记录会停在 pending；系统已有恢复扫描，当前没有跨系统原子发布。

这段背景包含事实与缺口，没有宣称“已解决”。读者知道问题边界、现状和为什么要决策。

## 第二步：列出约束和证据

约束可能包括：

- 不能在数据库事务内等待 Broker。
- 任务必须可查询、幂等和恢复。
- Worker 可以重复消费，不能重复产生有效副作用。
- 本周期不引入新的基础设施。
- 发布需要有可回滚制品。

每条约束都附证据类型：源码位置、集成测试、部署脚本、官方行为或明确的数据缺口。不要用“据说”作为约束。

## 第三步：比较替代方案

| 方案 | 优点 | 代价 | 当前选择 |
| --- | --- | --- | --- |
| 事务内同步派发 | 表面简单 | 长事务、Broker 故障拖住提交 | 不采用 |
| 提交后直接派发 | 事务短 | 可能提交后丢派发 | 临时采用，需恢复扫描 |
| Transactional Outbox | 数据库提交和待派发事实同事务 | 新表、Relay、运维复杂度 | 演进方案 |
| 业务方轮询 pending | 依赖少 | 延迟与扫描成本 | 作为当前恢复兜底 |

表格里的“当前选择”必须和现有代码一致；没有实现的 Outbox 只能写演进，不可写成现状。

## 第四步：写决策和影响

决策需要说清：任务记录先提交，派发失败写入可观察错误并由恢复扫描重试；Worker 领取使用 owner/lease 条件；最终状态写入幂等。影响包括短暂派发延迟、重复消息、需要监控 pending 年龄和恢复扫描健康。

同时写停止条件：如果 pending 年龄超过阈值、派发失败率上升或恢复扫描无法追平，就停止继续扩大流量并重新评估 Outbox。

## 第五步：把验证写成可执行项

验证不是“上线观察”。列出具体动作：隔离数据库提交后阻断 Broker，确认任务留在 pending；恢复 Broker 后扫描器重试；同时注入两个 Worker，确认只有一个 owner 完成；检查重复消息不产生第二个终态。

每项写输入、观察字段、预期结果和清理。数字使用实际配置或标成实验参数，不编造成功率。

## 复盘怎样避免指责和空话

复盘结构可以是：时间线、用户影响、事实证据、当时假设、实际原因、哪些防线有效、哪些防线缺失、行动、负责人、截止日期和验证方式。

“加强监控”“提高稳定性”不可执行。改成“给 pending 任务增加最老年龄指标；当它连续两个观察窗口超过业务预算时告警；在隔离环境模拟 Broker 不可用，确认告警触发”。

不要把未经核实的推测写成根因。可以保留候选假设，并标记下一步实验。

## 个人知识卡片如何可迁移

一张卡片只记录一个可复用问题：背景、最小模型、判断条件、命令/代码、正常结果、反例、适用范围、来源、版本和链接到相邻卡片。

例如“`idle in transaction` 先查什么”应链接 PostgreSQL 锁、应用事务边界和发布排障，而不是把整篇文档复制三遍。

知识卡片也要写失效条件。框架版本、协议、云服务行为变化后，重新验证并更新日期，不用旧经验冒充当前规范。

## ADR 模板

~~~markdown
# ADR-编号：一句话决策

状态：提议 / 已接受 / 已替代
日期：YYYY-MM-DD

## 背景与问题
## 已确认事实与约束
## 方案选项
## 决策
## 后果与风险
## 验证与回滚
## 后续行动
~~~

模板只保证字段齐全，不能替代具体证据。文件名、编号和状态要能在仓库搜索与发布记录中找到。

## 迁移练习

为一次 Agent 版本升级写 ADR：固定知识版本、模型版本、评测门禁、切流条件和回滚点。再写一页复盘，明确哪些是测试事实，哪些是暂时假设，哪些行动还没有完成。
