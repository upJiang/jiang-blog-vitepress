# 性能工程方法

性能优化从一个用户任务开始：打开页面、看到主要内容、完成点击或输入。页面总耗时只是结果，真正需要定位的是 DNS、连接、响应、解析、脚本、布局、绘制和交互延迟分别占了多少。

## 指标先对应用户任务

平均加载时间会被少量极端样本拉动，也看不出用户是否在关键内容出现前离开。指标应写清用户动作、时间起点、时间终点、分位数和采样范围。

常见的用户体验指标包括 Largest Contentful Paint、Interaction to Next Paint 和 Cumulative Layout Shift。它们分别描述主要内容出现、交互响应和布局稳定性。指标不是目标本身，业务页面还要说明用户完成任务的成功率和错误率。

```text
导航开始 -> 文档可解析 -> 关键资源完成 -> 主要内容绘制
          -> 输入响应 -> 任务完成
```

每个阶段的测量都要保存页面版本、设备类别、网络条件和时间窗口。没有这些维度，优化前后的数字无法比较。
## 预算把目标变成工程约束

预算可以限制首屏传输大小、关键请求数量、脚本执行时间和长任务时长。预算不应从某个固定数字照搬，而应从目标设备、网络和业务任务的基线测量得到。

预算检查适合放进 CI，但它只能发现候选制品超过阈值，不能证明真实用户体验达标。构建产物很小，第三方脚本仍可能在运行时增加请求和主线程工作。
## 先看 Trace，再决定改什么

Network 面板回答资源何时发现、何时请求和何时完成；Performance Trace 回答主线程在执行什么、布局和绘制为何变慢；内存快照回答对象由谁保留。三类证据不要用一张 Lighthouse 分数替代。

```js
performance.mark('search-start')
// 执行一次真实的搜索交互
performance.mark('search-end')
performance.measure('search-interaction', 'search-start', 'search-end')
```

这段代码只测量当前页面的一次交互。正式采集还需要统一采样、隐私过滤、页面版本和上报失败处理。
## 资源交付与执行顺序

HTML 中直接出现的关键资源更容易被预加载扫描器发现。`preload` 只适合确实会在近期使用的资源，类型和跨源属性不匹配会造成重复请求。脚本的 `defer`、`async` 和模块执行时机不同，不能只看文件大小判断影响。

图片要选择适合显示尺寸的格式和候选源，字体要限制字重并设置回退。压缩降低传输量，不能修复服务端首字节慢、缓存失效或关键资源发现过晚。
## 主线程与渲染边界

长任务会阻塞输入和渲染。批量 DOM 读取后再批量写入，可以减少强制同步布局；大量计算应拆分、延后或移到 Worker。把所有内容放进 `requestAnimationFrame` 也不能保证不卡，它仍运行在主线程。

动画优先选择合成友好的属性，但新图层会消耗内存和合成带宽。用 Paint Flashing 与 Layers 面板验证实际变化，不能看到 `transform` 就断言一定更快。
## 真实用户数据怎样回归

实验室测试固定设备和网络，适合比较单个变更；真实用户数据包含设备、地区、缓存和交互差异，适合观察发布后分布。两者都要按页面版本分组，保留 p75 或其他事先约定的分位数。

发布性能改动时，先在预览环境跑基线，再用小流量观察关键指标和错误率。指标改善但转化下降，说明优化可能改变了资源或交互行为，不能继续扩大流量。
## 验证和回滚

每个优化项写出假设、改动、受影响阶段、测量命令和回滚方式。删除一个资源、改变缓存策略或拆分代码都可能影响错误路径。保留旧制品和旧预算规则，发布后用同一 Trace、同一设备矩阵和同一统计口径复测。
