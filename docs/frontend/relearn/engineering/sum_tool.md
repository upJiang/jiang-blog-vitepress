# 前端工具链方法

从一次接手失败开始：README 里的启动命令在新机器报错，本地 Node 版本与 CI 不同，构建还依赖某位同事全局安装的 CLI。先让仓库在空环境中只靠锁文件和项目脚本启动，再讨论是否更换构建工具。

本篇围绕五个动作建立工具链：安装、开发、检查、构建、发布。每个动作都有明确输入、输出和退出方式，开发者不用知道一层层包装后的内部命令。

工具链不是工具名称合集，而是从源码到可验证制品的一组稳定入口。先固定运行时、包管理器和锁文件，再让本机与 CI 调用相同项目脚本。期望结果是新机器无需全局 CLI 就能启动，失败时能定位到具体检查，而不是依赖某个人的环境状态。

## 步骤一：定义稳定入口

```json
{
  "packageManager": "pnpm@10.14.0",
  "engines": { "node": ">=20 <23" },
  "scripts": {
    "dev": "vite",
    "lint": "eslint .",
    "typecheck": "vue-tsc --noEmit",
    "test": "vitest run",
    "build": "vite build",
    "verify": "pnpm lint && pnpm typecheck && pnpm test && pnpm build"
  }
}
```

输入是受支持的 Node 范围、固定包管理器版本与六个项目动作，输出是本机和 CI 都能调用的统一命令。项目脚本是团队契约，底层工具可以升级或替换；构建 CLI 放在项目依赖中，运行时与包管理器版本通过版本文件、Corepack 或环境管理器固定，并由 CI 重新验证。

## 步骤二：按问题评估工具

| 维度 | 要收集的证据 |
| --- | --- |
| 反馈时间 | 冷启动、首页面、单文件修改、类型检查 |
| 正确性 | 开发/构建等价性、Source Map、插件边界 |
| 生态 | 必需框架、测试、SSR、浏览器目标支持 |
| 运维 | 锁文件、缓存、离线/镜像源、漏洞更新 |
| 退出成本 | 配置耦合、私有插件、迁移路径 |

用代表性项目和同一测试场景比较，不以简单 demo 的一次耗时决定团队迁移。构建快但 Source Map 错误、开发正常但生产插件语义不同，都属于不可接受回归。

## 步骤三：区分脚手架与持续维护

脚手架只在创建项目时运行，复制出的配置会随时间分叉。需要统一更新的规则应放在版本化共享包、可组合配置或自动迁移脚本中。

```text
project template --create once--> repository
shared config -----versioned----> lint / ts / test
codemod --------explicit run----> source migration
```

共享配置也要有 SemVer、变更日志和兼容范围。大版本先在消费样本中验证，再逐项目升级；不要让所有项目被迫在同一天接受一项不可回滚变化。

## 步骤四：缓存不改变结果

缓存 key 至少包含锁文件、工具版本、目标平台和相关配置。先在无缓存环境证明命令正确，再启用缓存；提供 `--no-cache` 或清理单项目缓存的诊断方式。

远程缓存还要处理权限：缓存内容可能包含源码、路径或构建产物，不能让不同信任域共享可写 key。缓存命中应能观测，但不上传完整命令参数中的 Secret。

## 步骤五：升级一次依赖

1. 阅读目标版本迁移指南与 Changelog；
2. 建最小复现覆盖项目特有插件；
3. 更新版本和锁文件，记录自动迁移 diff；
4. 运行 verify、代表页面和构建产物比较；
5. 在独立分支/PR 评审，保留旧版本回退条件；
6. 合并后观察错误、构建时间与产物变化。

依赖更新工具可以创建 PR，不能替代行为验证。跨多个大版本时分段迁移更容易定位弃用与配置变化。

## 故意制造一次失败

把某插件从 devDependency 移除，但本机仍有全局安装。开发者机器可能继续成功，干净 CI 会报找不到命令。这正是为什么空环境和冻结安装是最低门禁。

再修改缓存 key，故意忽略 lockfile。升级依赖后若命中旧缓存，制品可能与声明版本不一致；回归测试应通过构建元数据或清缓存对比发现它。

## 工具链是否真的改善

可观察数据包括冷启动分布、CI 各步骤耗时、失败原因、缓存命中率、升级滞后和开发者调查。不要用命令执行次数评估个人效率，也不把遥测变成个人绩效。

新工具需要写退出条件：解决的问题消失、维护者缺失、安全支持结束或迁移成本超过收益时，如何移除。能被替换的工具链比依赖内部知识的统一 CLI 更可持续。
