# 前端工具链方法

工具链把运行时、包管理、编译、检查、测试、构建和发布组合成可重复入口。选择工具的依据是反馈周期、生态兼容、迁移成本和退出路径，流行度不能代替这些约束。

## 版本从运行时开始锁定

项目应声明 Node、包管理器和依赖版本，提交锁文件，并在本地与 CI 使用同一安装命令。全局安装的隐式版本、宽泛 semver 和被手工修改的 node_modules 都会破坏复现。

~~~json
{
  "packageManager": "pnpm@10.0.0",
  "engines": {
    "node": ">=22 <23"
  }
}
~~~

版本范围只是约束，真正安装结果还受锁文件、平台、原生依赖和 registry 影响。干净环境构建与制品摘要能提供更强证据。

## 每个入口回答一个问题

`dev` 负责本地反馈，`lint` 检查静态规则，`test` 验证合同，`build` 生成生产制品，`preview` 验证制品。命令名和退出码稳定后，底层工具可以替换，调用者不用知道实现细节。

工具配置要有唯一来源。TypeScript、测试、打包器和编辑器各维护一份 alias，会产生“开发能跳转、构建找不到”的漂移。能共享结构化配置就共享，不能共享时写一致性测试。

## 开发速度与生产正确性分开测

热更新快不代表生产构建稳定，打包快也不代表页面运行快。工具评估至少记录冷启动、增量构建、类型检查、生产构建、产物结构和源码映射。

迁移打包器时选真实项目基线，覆盖动态 import、CSS、Worker、静态资源、SSR 和插件。只用 Hello World 得出的速度不能预测业务仓库。

## 插件扩大供应链和维护面

插件在构建进程中通常拥有文件和网络权限。添加前检查维护状态、依赖树、许可证、配置复杂度和替代方案，升级时阅读 breaking changes 并在隔离分支验证产物。

配置能用标准能力解决时，不急着引入插件。确实需要自定义插件，应定义输入、输出、缓存键和错误行为，并为它写最小集成测试。

## 缓存必须包含所有影响输入

编译缓存的键应覆盖源码、锁文件、运行时、配置、环境变量和目标平台。漏掉一个影响构建的输入，缓存就可能返回过期结果。遇到“清缓存就好”的问题，应继续找到缺失的键或未声明依赖。

## 升级和退出是工具链的一部分

统一版本不等于永久冻结。定期升级能缩小安全和兼容跨度，每次升级要有变更记录、回归和回滚点。停止维护的工具需要给出迁移窗口与自动转换，避免所有项目同时停工。

验证工具链时在干净目录安装、构建和预览，再故意改变 Node 版本、删除锁文件或修改配置，确认门禁能发现漂移。监控构建时间和失败分类，用于改进反馈，不用于计算个人效率。
