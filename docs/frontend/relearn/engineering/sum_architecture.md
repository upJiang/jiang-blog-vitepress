# 前端架构与组件化

前端架构要控制变化怎样传播。页面新增一个字段时，哪些组件、状态、接口、测试和发布单元会被迫一起改，这条路径比目录有几层、用了哪个框架更能说明架构质量。

## 从变化轴设计边界

组件边界应围绕职责、变化频率和所有权建立。展示规则、业务状态、数据获取和路由生命周期混在一个组件里，任何改动都会触碰同一文件，也难以独立验证。

~~~text
页面入口
  -> 用例状态与权限
  -> 领域组件
  -> UI 组件
  -> 浏览器与外部服务适配
~~~

这不是固定分层模板。简单页面可以合并层次，跨页面复用的业务规则则要从视图中抽出。判断依据是变化是否经常一起发生，以及错误需要在哪个边界被拦住。

## 组件合同要包含状态和失败

一个可复用组件至少要明确输入、输出事件、受控或非受控状态、加载与错误、焦点行为和样式扩展点。只列 props 类型，仍然无法解释异步更新、权限变化和卸载时怎样收尾。

~~~ts
type SearchBoxProps = {
  value: string
  disabled?: boolean
  onChange(value: string): void
  onSubmit(value: string): Promise<void>
}
~~~

这个接口还需要约定提交期间能否继续输入、拒绝后由谁显示错误、并发提交怎样取消。组件文档和测试应围绕这些状态转换，而不是只做一张静态截图。

## 状态归属由一致性范围决定

只影响当前输入框的状态留在组件内。多个兄弟共享的筛选条件放到最近共同所有者。需要跨路由恢复、服务端同步或多人协作的状态进入专门存储和协议层。

全局 store 能让任何组件读取数据，也会扩大更新和依赖范围。把服务端缓存、表单草稿、URL 查询参数和用户会话塞进同一个 store，会让失效规则互相干扰。先区分谁是事实来源，再决定缓存和同步策略。

## 依赖方向要稳定

业务模块可以依赖通用 UI、类型和平台适配，通用组件不应反向知道某个页面的接口字段。跨层导入、循环依赖和深路径引用会让模块的私有实现变成公共合同。

路由级代码分割和懒加载改变的是交付边界。它可以减少首屏脚本，也会引入 chunk 请求、加载错误和预取策略。架构设计要把运行时失败与回滚一并考虑。

## SPA、MPA 与微前端是发布选择

SPA 用客户端路由维持页面壳和状态，适合连续交互；MPA 让导航回到文档边界，隔离和缓存更直接。微前端把团队或发布单元拆开，但会增加运行时依赖、样式隔离、路由、认证和重复依赖成本。

选择前列出导航体验、独立发布、故障隔离、首屏、SEO 和运维约束。不能因为团队人数多就自动上微前端，也不能因为框架支持路由就默认所有页面都进一个 SPA。

## 架构用改动实验验证

选一项真实横切变化，例如增加权限状态或替换接口字段，记录它经过的模块、团队和制品。再模拟某个组件加载失败、接口超时和旧版本回滚，观察故障是否被边界限制。

架构文档应记录当前依赖图、关键合同和已知取舍。组件数量、代码行数和复用率只能提供线索，最终证据仍是变化成本与故障范围。
