# 持续集成方法

持续集成把每次候选变更放进可重复环境，构建同一制品并尽早验证。它的价值来自反馈速度、结果可信度和失败阻断，预览地址只是其中一个输出。

## 流水线围绕不可变制品

依赖安装、类型检查、测试和构建应在锁定的运行时与依赖版本中执行。构建完成后给制品计算版本或摘要，后续预览、验收和发布使用同一份产物，避免每个环境重新构建得到不同结果。

~~~text
提交 -> 静态检查 -> 测试 -> 构建制品
     -> 预览部署 -> 浏览器验收 -> 发布候选
~~~

阶段失败要有明确退出码、日志和归属。把所有命令放进一个大脚本会让失败定位变慢，也不利于缓存和并行。

## 门禁按风险分层

格式、lint 和类型检查反馈快，适合最先运行。单元与组件测试验证局部合同，浏览器测试覆盖关键用户路径，安全和依赖扫描检查供应链。构建验证确保产物能在目标模式生成。

没有一类检查能替代其他层。快照通过不能证明交互正确，端到端通过也可能漏掉权限和异常分支。变更影响共享协议、路由或构建配置时，应扩大回归范围。

## 预览环境要隔离状态

每个变更拥有独立 URL 和版本，能减少互相覆盖。环境需要明确 API 目标、认证方式、种子数据和清理策略，避免测试把共享数据改坏。

预览成功只证明候选在该配置下可访问。生产 CDN、真实网络、权限、浏览器分布和第三方服务仍可能不同，所以发布前还要做配置差异检查和回滚演练。

## 缓存只能加速，不能改变结果

依赖缓存、编译缓存和测试分片应以锁文件、运行时、配置和源码摘要作为键。缓存命中后仍要保证输出与干净构建一致。定期在无缓存环境重跑，可以发现被工作区或旧产物掩盖的问题。

对不稳定测试要保存重试前后的证据。直接重试到成功会把竞态变成绿色，正确做法是隔离用例、记录随机种子、时钟、网络和资源状态，再修复确定性。

## 发布要保留可回滚路径

持续交付把通过门禁的制品准备好，持续部署再自动推向用户。无论自动程度如何，都要记录当前版本、候选版本、数据库或配置兼容性、健康检查和回滚步骤。

前端静态资源需要考虑 HTML 与 chunk 的版本配对。旧页面引用的新旧资源并存一段时间，资源命名和 CDN 清理必须允许在途用户继续加载。

## 用故意失败验证流水线

提交一个可控的类型错误、失败测试和超预算资源，确认它们分别在预期阶段阻断。修复后检查进入预览和发布的制品摘要是否一致，再模拟健康检查失败并执行回滚。

流水线本身也要监控排队时间、执行时长、失败率、重试和缓存命中。指标用于定位反馈瓶颈，不能拿来评价个人产出。
