# 前端质量体系：静态检查、测试与变更门禁

前端质量体系用类型检查、Lint、单元测试、组件测试、契约测试和浏览器验证覆盖不同风险。它位于代码变更与发布入口之间，用较低成本证明语法、行为和跨边界集成仍然成立。层级按风险与反馈速度选择，不按工具名称堆叠。

全部依赖 E2E 会让反馈慢且定位困难，全部依赖单测又无法发现路由、浏览器和接口集成错误。质量体系把风险放到最便宜且可信的层验证，并让高风险跨边界路径保留少量真实浏览器证据。

## 分层输入与故障

类型检查发现结构矛盾，Lint 发现可静态识别约束；单元测试覆盖纯逻辑和状态机；组件测试覆盖渲染、事件、焦点；契约测试核对请求响应；E2E 验证部署后的关键用户任务。可访问性、视觉、性能和安全是横切门禁。

测试层不是按文件夹决定，而是按真实依赖决定。Mock 掉 fetch、Router 和 DOM 后的“组件测试”可能只剩实现细节；使用真实生产 API 的单测又会不稳定。
## 结算流程矩阵

金额计算与优惠规则用表驱动单测；组件测试验证表单错误和按钮状态；契约 fixture 验证订单请求；E2E 只跑一条成功和关键失败；服务端仍负责最终金额和幂等。每条风险只在必要层重复。
## 稳定性原则

通过角色、名称和用户行为定位元素，不依赖 CSS 类或内部 state。异步测试等待具体结果，不固定 sleep。时间、随机、网络和浏览器权限由显式 fixture 控制，失败保留 trace、截图和请求证据。

Flaky 测试先定位竞态和环境，不默认重试掩盖。确需重试时记录首次失败并限制次数。测试数据可并行隔离，清理只删除本用例资源。
## 变更门禁

PR 快速门禁运行类型、Lint、单元和关键组件；合并或候选环境运行契约、E2E、视觉和性能；生产切流后做低风险冒烟和监控。门禁输出能关联提交与制品。

测试层级在反馈速度、保真度、故障定位和维护成本之间取舍。选择应从具体风险出发，覆盖率百分比不能单独代表质量。
## 从风险到测试层

把需求拆成可观察风险：金额/权限/状态机用快速单元和属性测试；组件键盘、焦点和错误状态用 DOM 组件测试；前后端 schema 用契约测试；浏览器导航、跨域、Worker、Hydration 用少量 E2E；布局和主题变化才需要视觉回归。每层都应声明输入、环境、输出证据和失败归属。

```text
单元：纯规则/转换，毫秒级定位
组件：用户可见状态和事件，隔离网络
契约：请求/响应/错误联合，双方独立构建
E2E：真实浏览器关键路径，保留 trace
生产冒烟：低风险真实入口，验证制品与监控
```

测试夹具要控制时钟、随机、网络、权限和数据所有权；并行执行使用唯一租户/ID，清理确认 count 为零。重试只能减少环境噪声，不能掩盖第一次失败；Flaky 应记录重现概率、trace 和根因。
## 质量门禁的反馈设计

提交阶段只运行确定、快速且能定位的检查；候选制品运行真实浏览器、视觉、性能和安全扫描；发布后比较 release 基线并触发回滚。覆盖率只说明执行过代码，不说明断言了正确边界；门禁应结合变更风险、历史故障和用户路径。
