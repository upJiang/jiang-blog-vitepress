# 上下文窗口怎样保留近期状态与关键事实

长对话不能靠“最近 20 条消息”管理。二十条简短问答可能只占很少 Token，一条完整日志却可能超过全部历史；更麻烦的是，按条数截断会把 Tool Call 与 Tool Result 分开，也可能只留下“不是周一”而删掉它所否定的旧结论。

上下文窗口策略要回答三个问题：哪些内容必须留在本轮，哪些旧内容可以移出，移出的内容怎样找回来。一个可靠方案通常组合三种手段：用滑动窗口保留近期连续对话，用锚点和语义分组保护关键状态，把较大且可重读的材料留在外部存储，只向模型提供摘要与稳定引用。

本篇沿一段排障对话推演。用户正在定位远程访问失败，Agent 已经调用工具读取审批状态，随后用户补充新日志并问“这个拒绝是哪里产生的”。窗口快满时，当前问题、最新日志、未完成动作和对应 Tool Result 必须保留；十轮前的寒暄可以移出，原始日志则应留在对象存储中供再次读取。

::: info 窗口选择的最小不变量

- 当前问题与安全规则一定存在。
- 消息组要么完整保留，要么完整省略。
- 保留下来的历史顺序与原会话一致。
- 每项省略都有原因和恢复引用。
- 最终请求仍为模型输出留有预算。

:::

## 为什么固定消息条数会失效

消息条数与模型消耗没有稳定关系。一条“好的”很短，一段报错栈、Tool Result 或文档表格很长。按最近 N 条保留，可能在某次输入刚好可用，换一份日志就超限。预算必须按目标模型 Token 计算，无法使用目标 Tokenizer 时采用保守估算并留出安全余量。

固定条数也看不懂消息关系。Tool Call 通常由 Assistant 消息提出，Tool Result 使用独立 Role 返回。窗口边界恰好落在两者之间时，模型只看到一个无来由的结果，或者看见调用却不知道执行结果。部分供应商甚至会因调用与结果不配对而拒绝请求。

否定和纠正同样依赖上下文。“负责人是平台组”之后，用户说“不是平台组，是安全组”。若窗口只保留纠正句，读者还能勉强理解，模型却未必知道纠正对象；只保留旧结论则更糟。纠正消息、被纠正 Claim 和最新权威 Evidence 应形成一个可识别关系。

指代依赖最近焦点。用户先谈制度 A，再切换到制度 B，最后问“它何时生效”。只按相似度选历史可能把内容更多的 A 选回来，按最近连续窗口则更容易保留焦点切换。相关性排序不能替代对话时序。

窗口还承载未完成工作。Agent 已创建一个异步任务或正在等待审批时，任务 ID、动作快照和等待原因不能因为消息较旧而被裁掉。这些状态最好保存在结构化 Turn 中，每轮再渲染必要摘要，而不是依赖某条自然语言消息永远留在 Prompt。

## 滑动窗口保留了什么，又丢掉了什么

Token 滑动窗口从最近消息向前累计成本，直到达到近期历史预算。它保留连续时序，适合处理“刚才”“继续”“上一条错误”等局部指代。短会话没有触发阈值时可以原样保留，不必为了形式统一每轮都生成摘要。

选择方向通常是从尾部向前，输出时恢复原始顺序。单条最新消息超过全部近期预算时，可以保留末尾一段，因为新日志的错误结尾常包含最终异常；但这个选择必须记录 `truncated=true`，并保留完整消息引用。对于代码、JSON 和 Tool Result，直接从字符中间截断会破坏结构，应使用对应解析器生成预览。

滑动窗口的优点是确定、快速、无需模型调用。相同历史和预算会得到相同输出，摘要服务故障时可以作为降级。它的损失也很明确：较早但关键的约束可能被移出，长期任务目标可能消失，最近几轮里的大段低价值输出可能挤掉更早的关键决定。

因此滑动窗口适合作为近期层，不应单独承担全部历史。旧消息要么进入可回查摘要，要么转成结构化工作状态，要么留在原会话中按需读取。把窗口外内容直接删除，会让摘要修复、审计和新预算重编译都失去来源。

窗口边界应对外可见。结果至少包含 `keep_from_message_id`、保留消息 ID、省略数量、原始与编译 Token 数、截断标记和摘要引用。只返回一组消息，后续无法判断模型是真的没有看见某条信息，还是看见后忽略了它。

## 锚点怎样保护当前任务的承重状态

有些内容不能只靠“最近”获得优先权。稳定规则、当前问题、用户刚刚确认的范围、未完成动作和输出合同属于锚点。装配器先计算这些必保项的成本，再把剩余空间交给近期窗口。必保项本身超限时，正确结果是调用前失败，而不是静默删掉某条安全规则。

锚点应尽量短而结构化。一个未完成工具动作可以表示为工具名、`call_id`、参数摘要、当前状态和 Deadline，不需要把此前所有思考重新复制。知识范围使用稳定 Scope 与 Release，不能塞一段“请记住我们只看新版”的自然语言后期待模型永不遗忘。

锚点也需要生命周期。动作完成后，`pending_action` 锚点由结果摘要替换；用户改变目标后，旧目标退出当前锚点但仍保留在历史；审批过期后，不再把“已批准”作为有效状态。永久 Pin 所有曾经重要的消息，最终会让锚点自己占满窗口。

优先级不是越多越好。若每个组件都把自己的输出标为最高优先级，装配器无法裁剪。优先级应由统一策略定义，材料生产者只提交类型与重要性证据。例如安全规则和当前问题是硬约束，未完成动作是状态约束，历史纠正是高价值候选，普通确认消息是低价值候选。

锚点变化要产生预算修订。工具从 pending 变成 completed 后，装配器使用新的状态版本，旧缓存不再复用。模型不能在输出里声明某条消息为 pinned 并改变下轮规则，是否固定由应用根据状态机决定。

## 为什么要按消息组而不是单条选择

消息组是一组必须共同解释的消息。最常见的是一轮 User 与 Assistant、Tool Call 与 Tool Result、审批申请与决定、错误尝试与对应修复。组内消息保留原 Role 与顺序，窗口只能整体选择。

Tool Call 组还要考虑多工具并行。一次 Assistant 消息可能提出三个调用，随后返回三个 Tool Result。若模型协议要求同一轮配对，这四条消息属于同一个组；如果应用已把结果转换成独立 Observation，也可以按每个 `call_id` 建组，再在最终渲染时生成协议允许的结构。组边界由模型网关与运行时共同确定，不能只看相邻行。

一轮对话不总是一个组。用户一次上传了很大的日志，Assistant 先确认接收，随后工具解析出摘要。把原始附件引用、解析结果和当前问题作为一组有意义，把附件全文放进同组则会导致整组永远装不下。大对象应留在外部，组内保存预览和引用。

组选择先放入必保组，再从最新可选组向前扫描。某组超出剩余预算时可以跳过，继续检查更早但更小的组，不过这样会产生时间缺口。清单必须记录缺口，摘要或状态锚点负责补充必要连续性。对强时序任务，也可以在第一个装不下的组处停止，不再选择更早内容。

选择结束后按原始消息序号渲染，不能按优先级排序消息。把最近 User、旧 Assistant、最新 Tool Result 重新排列，可能制造从未发生过的对话。优先级只决定入选，不决定历史顺序。

## 纠正链和未完成动作怎样进入窗口

纠正不是一条孤立消息，而是对已有状态的变更。应用可以记录 `supersedes_message_id` 或被修正的 Claim ID，装配时优先选择最新值，同时保留足以说明变化的短链。例如“负责人是平台组”后来被改成“安全组”，当前状态锚点直接写负责人为安全组并引用纠正消息；旧说法留在历史中标为已撤销，不能和新值并列成两个候选答案。

用户撤回目标时也要更新结构化状态。“不要再发布，先只做预览”会让发布动作进入取消或失效，而不是给旧动作旁边追加一句自然语言。窗口里保留新目标、取消状态和旧 `call_id`，运行时据此阻止迟到的发布候选。只依赖模型读懂否定句，无法阻止已经排队的外部动作。

未完成 Tool Call 需要区分三种状态。`proposed` 还未授权，可以重新规划；`running` 已经发给外部服务，窗口应保留调用身份与查询回执的方法；`unknown` 表示连接中断且副作用无法确认，模型不能建议简单重试。完成后，原始大结果可以移出，但短结果摘要和回执继续服务当前决策。

一个动作跨多轮等待人工审批时，不必永久保留申请前的完整对话。审批记录保存动作指纹、目标、风险和截止时间，本轮窗口渲染成短锚点。批准后参数若改变，状态机要求重新审批；窗口里写着“已经批准”不能覆盖指纹检查。

并发用户消息会产生另一个边界。第一个 Turn 尚未结束，用户又补充条件时，系统要么取消旧 Turn 并用新状态重编译，要么建立有序后继关系。两个 Turn 不能各自从不同窗口生成结果后按完成时间覆盖 Conversation 焦点。窗口选择依赖明确的消息版本，而不是数据库此刻能查到的最后几行。

## 外部状态引用怎样释放窗口

有些材料价值高，却不必每轮全文出现。完整日志、长文档、代码文件、工具原始 JSON 和执行 Trace 可以保存在外部存储。窗口中放一段有界预览、内容哈希、来源 ID、读取工具和必要元数据，模型需要细节时再请求特定范围。

引用不是一句随意路径。它至少要绑定对象身份、版本、权限范围、内容类型和生命周期。文件更新后旧哈希失效；权限撤回后读取工具拒绝；临时工具结果过期后，窗口不应继续展示一个已无法恢复的引用。模型生成的任意 URL 或本机路径不能自动成为可信引用。

外部化适合可重读的大对象，不适合当前决策所需的唯一短事实。若模型必须知道“当前审批状态为 denied”才能选择下一步，就把这个状态放入锚点，并附回执引用；只给一个数据库行 ID，模型还要多一次工具调用才能理解，会增加延迟和失败点。

摘要也是一种外部状态引用，但它有损。原日志引用可以重新读取原文，摘要只保留生成器选择的信息。恢复路径要保留原消息范围，摘要发现遗漏后能够重建。不能把摘要保存后立刻销毁原对话，再声称可恢复。

外部化的取舍是用额外 I/O 和工具调用换取更小输入。频繁读取同一小对象可能不划算，读取工具过多也会扩大能力面。应根据对象大小、访问频率、更新速度和安全等级决定，而不是统一把所有上下文写进文件。

## 一段排障会话怎样被裁剪

假设模型窗口可用于近期历史的预算是 1,200 Token。当前问题与稳定规则已经在总装配器中保留，不计入这 1,200。历史包含以下内容：

| 顺序 | 消息组 | 内容 | 估算成本 | 决定 |
| --- | --- | --- | --- | --- |
| 1 | turn-1 | 环境确认与寒暄 | 160 | 省略 |
| 2 | turn-2 | 旧版部署建议 | 340 | 省略并由摘要覆盖 |
| 3 | turn-3 | 用户纠正目标为新版制度 | 120 | 锚点保留 |
| 4 | tool-7 | 查询审批状态的调用与结果 | 280 | 整组保留 |
| 5 | turn-5 | 用户粘贴长日志 | 1,600 | 外部化，保留 260 Token 预览 |
| 6 | turn-6 | 当前追问与最近答复 | 310 | 保留 |

装配器先放 `turn-3`，因为它决定“新版”焦点；再放 `tool-7` 和 `turn-6`；长日志不直接进入，改放对象引用、错误尾部和哈希。合计 970 左右，仍有余量给必要的消息封装。`turn-1` 与 `turn-2` 不再放原文，摘要说明曾尝试旧版方案且已被用户否定。

模型看到的状态链是：当前范围为新版，工具确认审批状态为 denied，新日志尾部显示网关返回 `permission_denied`，用户问责任层。它可以据此判断错误发生在权限校验而非模型生成。若 Tool Result 被裁掉，只剩错误文本，模型无法区分网关拒绝与日志里引用的旧错误。

成功路径输出一份窗口清单：选中组、外部引用、摘要版本、使用预算和省略原因。模型回答后，Trace 可以证明它看见了哪些状态。失败路径若长日志预览仍超限，就进一步按行结构取错误尾部；必保组超限则停止并返回配置错误，不把当前问题挤出去。

## 输出预留不足时为什么不能继续塞历史

上下文窗口包含输入和输出时，近期历史预算必须在扣除输出预留后计算。用户要求生成完整迁移方案，输出可能很长；如果输入占满窗口，模型会截断回答或 API 直接拒绝。装配器不能假设每轮输出都只有几百 Token。

输出预留可以由任务类型和输出合同决定。分类、路由或短结构化结果预留较少，长文档、代码或多 Claim 回答预留更多。模型网关返回实际 usage 后，系统可以校准策略，但不能用上一轮短回答推断下一轮也短。

工具调用也可能是模型输出。模型需要生成多个带参数的 Tool Call 时，输出 Schema 和参数长度占用输出空间。并行工具数量有上限，超过后应分批规划，不能让一个候选动作列表挤掉终止标记。

输出流接近上限时，运行时可以要求模型在完整语义边界停止并返回续写游标，但这种协议要提前设计。直接截断 JSON 或代码会产生不可解析结果。当前问题若要求不可拆分的结构，输出预留无法满足时在调用前拒绝或选择合适模型。

## 多个模型怎样共享同一段会话

同一应用可能把短路由交给小模型，把深度回答交给大模型。两者窗口、Tokenizer、消息协议和工具 Schema 成本不同，因此不能缓存一份已经裁好的消息列表供所有模型复用。共享的是原始会话、摘要与材料身份，具体窗口由目标模型配置重新编译。

模型路由必须发生在最终窗口计算之前。若先按大窗口装配，再因成本切到小模型，请求可能直接超限；若先按小窗口激进裁剪，再切回大模型，关键信息已经无谓丢失。路由可以先使用一个很短的固定输入决定模式，随后由选定模型的编译器生成正式上下文。

Tokenizer 不同还会改变边界。中文、代码和特殊标记在不同模型中不一定得到相同数量的 Token。装配清单保存计数器身份和配置版本，模型升级后重新跑临界预算测试。只调整一个 `context_window` 数字而沿用旧估算，会让边界请求出现难以复现的超限。

Prompt Cache 也不应支配窗口正确性。为了保持前缀稳定，可以把不变规则和工具定义放前面，把变化历史放后面；但权限变化、工具撤回或策略升级必须使旧前缀失效。不能为了提高命中率继续向新请求发送已经不适用的内容。

## 窗口裁剪的失败证据怎样定位

**当前问题消失**通常来自把当前问题也放进可选历史，或最终渲染后再次从头截字符串。检查装配清单中问题是否为 required，再对比发送给 SDK 的最终消息。清单存在而最终请求缺失，问题在渲染或网关；清单本身没有，问题在选择策略。

**Tool Call 与结果拆散**表现为 API 协议错误，或模型无法解释 Tool Result。沿 `group_id` 和 `call_id` 检查两条消息是否共同入选。修复应调整组边界和模型适配，不是在 System Prompt 中解释“你之前调用过工具”。

**摘要覆盖纠正**表现为摘要仍写旧结论，而近期历史有新否定。检查摘要覆盖的最后消息 ID，确保新消息没有被错误标成已总结；编译时同一 Claim 出现冲突，以新纠正和当前 Evidence 为准，并把摘要标记为待重建。

**按字符数估算导致超限**表现为本地预算显示未满，供应商返回 Context Length 错误。记录估算值、目标 Tokenizer 复算值、工具 Schema 和消息封装成本。修复计数与安全余量，不能每次收到错误就随意删一半历史。

**过度裁剪导致重复行动**表现为模型再次调用已经完成的工具。检查完成回执是否进入结构化工作状态，而不是只存在已移出窗口的 Tool Result。关键动作状态应由 Runtime 提供短锚点，窗口策略不承担业务幂等。

**外部引用无法读取**表现为模型决定展开日志，工具却返回过期或无权限。引用创建时绑定生命周期，装配前检查可读性；过期后提供重新生成预览的路径或明确说明材料不可用。不能让模型根据旧摘要补造缺失细节。

## 滑动、优先级和外部化怎样组合

只有几轮对话、消息体积稳定时，Token 滑动窗口已经足够。它实现简单、延迟低，失败行为确定。此时引入摘要模型和向量记忆只会增加成本与不确定性。

对话中存在重要纠正、当前工作状态或审批时，在滑动窗口外加入少量结构化锚点。锚点解决“不能丢什么”，滑动窗口解决“最近发生什么”。不要把所有重要内容复制为 Pin，完成或过期后及时退出。

长日志、文件和大 Tool Result 使用外部引用。窗口保留预览、身份和读取方法，模型按需展开。外部化解决“内容太大”，却不会自动判断相关性；预览选择和读取工具仍要测试。

长期对话再加入摘要。摘要覆盖窗口外历史，原消息保持可回查；近期窗口与摘要之间通过消息 ID 连续衔接。摘要生成失败时使用确定性裁剪继续，不把旧摘要错误扩大。下一篇会专门展开摘要的触发、保留字段和验证。

多 Agent 隔离适合子任务产生大量中间过程、父任务只需要有限结果的情况。它通过独立窗口减少污染，但需要任务合同、来源和结果合并，不是扩大单窗口的免费手段。简单会话不应为了省几条消息拆成多个 Agent。

## 怎样验证关键状态没有在窗口边界丢失

单元测试先固定消息和预算，断言选择完全确定。测试短会话全部保留、长会话从尾部选择、必保项超限失败、组完整性、原始顺序、外部引用和省略清单。只断言“消息数量小于 N”无法证明语义关系完好。

边界测试把预算设为组成本减一、恰好相等和加一，验证不会出现半组。对超长单消息分别测试纯文本尾部保留、JSON 结构预览和日志按行截断。每种截断都返回原始引用与 `truncated` 标记。

多轮回归至少覆盖指代切换、否定纠正、未完成工具动作和用户撤回目标。隐藏正文后，测试仍能用消息 ID 说明哪个事实来自近期历史、哪个来自摘要、哪个来自 Evidence。模型答对一次不是窗口正确的充分证据。

故障测试让摘要服务超时、外部对象过期、目标 Tokenizer 不可用和 Tool Result 延迟返回。正常路径使用完整材料，降级路径有明确损失，停止路径不调用模型。取消发生在装配中时，中止尚未完成的读取任务，已保存的会话与对象不被删除。

```bash
PYTHONPATH=examples/ai-agent python3 -m unittest discover \
  -s examples/ai-agent/tests -p 'test_*.py'
```

集成测试还要把最终消息真正交给目标模型适配器的计数与协议校验，确认 Tool Call 配对和总窗口约束。观测时分别看原始历史、编译历史、摘要覆盖范围、外部引用读取和输出截断，才能判断信息损失发生在哪一层。

上线新策略时先做影子编译。对同一个 Turn 同时运行旧、新选择器，只保存材料 ID、成本和差异，不把候选输入发送给模型。重点检查当前问题、纠正链、未完成动作和 Evidence 是否被新策略漏掉，再用固定回归集比较回答。这样可以在不影响读者的情况下发现窗口迁移问题。

切换后保留策略版本。正在运行的 Turn 沿用开始时的编译规则，新 Turn 使用新版本；回滚时只切回旧选择器，不修改原始会话。若新策略写入了新的消息组或摘要字段，旧版本必须能忽略额外字段并继续读取，无法兼容时使用独立候选存储。

监控需要分布而不是单个平均值。按任务类型观察被省略消息数、必保项占比、外部引用读取率、供应商超限错误和回答截断。某一类排障任务频繁读取窗口外日志，说明预览太短或分组不合理；所有任务都接近硬上限，则应检查规则与工具定义膨胀，而不是继续压缩用户问题。

窗口策略的目标不是让模型“记住一切”，而是让当前决策所需的信息完整、可信且可恢复。近期连续性由滑动窗口承担，承重状态由锚点承担，大对象由外部引用承担，旧历史由摘要承担。四者各自有损失，组合时把损失写进清单，才能在模型回答出错时找到真正的窗口边界。
