# 上下文窗口怎样保留近期状态与关键事实

“保留最近 20 条消息”无法稳定管理窗口。二十条寒暄可能很短，一条日志就可能占满预算；按消息截断还会拆开 Tool Call 与 Tool Result，或者只留下纠正结论，删掉它所纠正的对象。

窗口策略需要同时保护近期连续性、当前任务锚点和可恢复的外部状态。三种手段各有损失，通常组合使用。

## 滑动窗口保留局部连贯

滑动窗口从最新消息向前选择，优点是顺序自然、实现简单，适合主题连续的短对话。它会丢掉较早的目标、长期约束和仍未完成的动作，单独使用容易出现“记得刚才说了什么，却忘了为什么在做”。

窗口应按 Token 计算，并以消息组为单位。一个用户请求、助手工具候选、工具结果和最终回答构成关系组，要么一起保留，要么用摘要或外部引用替代。

## 锚点保护当前状态

锚点是不能仅按时间淘汰的结构化状态，例如：

- 当前目标和用户范围。
- 正在处理的实体与版本。
- 未完成工具调用及对应回执。
- 用户最近一次明确纠正。
- 必须满足的输出合同。

锚点也要有所有者和过期条件。上一主题的 `document_id` 在用户明确切换问题后应降级，不能永远占据焦点。

## 外部引用保存大对象

原始日志、文件和完整工具结果放在对象存储或数据库，窗口只携带稳定引用、摘要、哈希和可读范围。模型需要细节时再调用受控读取工具。

引用必须绑定用户范围和生命周期。一个对象在上一轮可见，下一轮权限撤回后不能继续读取；引用过期要返回明确状态，不让模型根据旧摘要补全原文。

## 纠正链要作为整体

对话先说“制度周一生效”，后来用户纠正“不是周一，是审批通过后的次日”。只留下第一条会传播旧事实，只留下“不是周一”又缺少新值。窗口选择要识别这组修订关系，保留最终结论和它替代的对象 ID。

更可靠的做法是把当前事实写入结构化会话状态：

```json
{
  "focus": "policy-7",
  "effective_rule": "审批通过后的次日",
  "supersedes_message": "msg-18"
}
```

历史仍保留原始记录，本轮上下文读取当前状态与必要原话。

## 输出预留不够时先停止添加

窗口算法常在输入恰好塞满时才发现没有输出空间。输入预算必须提前扣除最大输出与安全余量。剩余空间不足以放入硬锚点时，请求应在调用前失败或要求缩小任务，不能继续删规则和当前问题。

## 多模型共享会话时使用各自视图

不同模型的窗口、工具协议和 tokenizer 可能不同。同一 Conversation 不应保存一份“最终 Prompt”，而应保存材料与关系，由每个模型适配器编译自己的视图。

模型切换后重新估算 Token，保持相同焦点、范围和状态版本。若降级模型窗口更小，记录新裁剪计划，避免把质量变化误判为模型能力差异。

## 组合策略的顺序

先装入硬锚点，再加入近期完整消息组，随后按相关性选择较早历史，大对象使用外部引用。仍超限时压缩已闭合的旧阶段，不压缩未完成动作和当前证据。

窗口变更要记录原因，例如 `recent_group`、`active_focus`、`externalized_large_result` 或 `budget_exceeded`。排障时可以直接定位是哪项策略删除了材料。

## 边界测试比平均长度更重要

测试应故意把预算卡在消息组边界，覆盖多字节字符、工具并行、纠正链、焦点切换、权限撤回和模型降级。断言不能只看 Token 小于上限，还要看关系完整、顺序稳定和引用可读取。

窗口管理的目标是让当前决策拥有足够状态。保留越多历史并不自动更好，能说明每一项为什么存在、删掉后如何恢复，才算可维护。
