# 什么是 Agent 循环

不用框架实现一次有限行动循环，观察决策、执行、状态更新、异常和终止。**Agent Loop**、**Python**、**ReAct** 分别指向同一条执行链上的不同对象：开发者规则、用户问题、消息历史和本次可见资料进入系统，用户问题、消息、步骤数、工具观察、状态版本、最终答案和终止原因保存处理中间状态，最终得到文本、结构化对象、工具调用候选、完成状态或可分类错误。

Agent 循环位于模型调用与应用控制边界。它的主要机制是循环每轮读取状态，由模型返回 final 或 tool_call；运行时校验并执行工具，把观察追加到状态，随后检查轮数、Deadline 和取消。未知动作、重复调用、工具异常、没有状态变化、超过最大轮数、Deadline 到期和取消信号会让链路在不同位置停止，错误记录必须保留发生阶段、当时的状态和终止原因。

::: info 贯穿示例

Agent 循环场景：用户询问为什么自己的远程访问申请被拒绝，系统需要在不猜测账号状态的前提下给出解释。身份、权限、版本和业务事实由应用提供，模型与外部内容只产生需要检查的候选。

:::

这次推演用请求快照、响应类型、停止原因、用量字段和业务校验记录把请求和终态关联起来。与 ReAct、状态机、固定工作流和 LangGraph 比较时，重点看输入来源、状态所有者、下一步的决策者和失败终点。

一次 Agent 循环执行可以画成“装配输入 → 发送请求 → 解析响应 → 校验候选 → 写入结果”。开发者规则在入口出现，用户问题记录进度，文本只有通过当前主题的校验条件后才会成为可交付结果。

未知动作与重复调用会产生不同证据。前者先检查用户问题和输入来源，后者沿调用记录定位依赖或状态冲突；不区分发生位置，重试会掩盖原始原因。

Agent 循环与 ReAct 的共同点不代表它们可以互换。当前主题拥有消息，相邻组件只通过契约读取或提交候选，不能直接修改这个状态。

实现 Agent 循环时，代码顺序应与状态顺序一致：入口拒绝不会调用依赖，正常分支保存步骤数，错误分支返回稳定类型，测试分别断言调用次数、参数、输出和清理结果。

## Agent 循环的定义与作用

Agent 循环是一个由程序控制的有限状态循环。模型读取目标和当前观察，返回“最终回答”或“调用某个工具”的候选；运行时验证候选、执行工具、把结果追加为新观察，然后再次调用模型。循环的价值在于下一步会随观察变化，边界则来自动作白名单、权限、预算和停止条件。

它不是“不断问模型直到满意”。模型不拥有工具执行权，也不能直接修改步骤数、身份或终态。一个最小状态至少包含用户问题、观察列表、已执行步数和运行状态。生产系统还会增加 Turn ID、Deadline、取消标记、状态版本和工具回执，但这些字段是在最小控制流成立后逐步加入的。

不用框架实现一次有限行动循环，观察决策、执行、状态更新、异常和终止。在“Agent 循环场景：用户询问为什么自己的远程访问申请被拒绝，系统需要在不猜测账号状态的前提下给出解释”这类任务里，Agent 循环负责把开发者规则带入处理链，并明确文本可以交付的条件。

Agent 循环位于模型调用与应用控制边界。它处理循环每轮读取状态，由模型返回 final 或 tool_call；运行时校验并执行工具，把观察追加到状态，随后检查轮数、Deadline 和取消，身份认证、授权结果和最终业务状态仍由应用中的确定性组件负责。

开发者规则是这条链路的起点。来源缺失时，程序只能拒绝请求或采用明确记录的默认值；模型补出的字段没有可信来源，不能继续驱动发送请求。

未知动作会直接破坏用户问题与文本之间的对应关系。排查时先保留原始输入摘要和发生阶段，再判断是否允许重试。

重复调用属于另一类风险，它影响的是消息或下游解释。两类错误不能共用“重新调用一次模型”这样的处理方式。

Agent 循环的完成条件至少包含用户问题、消息、文本和检查结论。只有最终文字，没有这些中间记录，无法证明结果来自本次请求。

单进程 Demo 可以把状态放在内存中，但仍要保留输入、状态转移和停止原因。跨进程、带权限或有副作用的任务再把这些字段持久化，不能依赖 Prompt 代替状态。

Agent 循环还要把业务条件写成状态条件：消息历史何时就绪，文本何时允许交付，未知动作发生后是否还能继续。

Agent 循环对外区分完成、部分完成和无法确认。三个状态如果都包装成一段顺畅文字，上层界面无法采用不同处理方式。

Agent 循环接收开发者规则、用户问题、消息历史和本次可见资料，向下游交付文本、结构化对象、工具调用候选、完成状态或可分类错误。输入与输出之间采用明确契约，避免调用方把一句含糊目标直接交给底层适配器。

应用负责消息顺序、可信字段和完成判定，模型适配器只负责一次调用。因此用户问题与消息要有唯一写入方，其他组件只能通过版本化命令申请修改。

ReAct 与 Agent 循环解决的问题相邻，但控制权不同。比较两者时要看谁选择解析响应、谁保存用户问题、谁确认文本。

状态机可以参与同一请求，却不能替代 Agent 循环的职责。组合之后，用户问题的可信来源和未知动作的终止规则仍需单独检查。

步骤数若只保存在 SDK 对象里，重试或进程退出后就失去解释依据。需要恢复或审计的字段进入持久层，体积较大的结果只保存稳定引用。

Agent 循环使用的身份、范围和版本来自可信运行时。用户消息、检索文本和模型候选可以表达意图，不能提升权限或改写活动 Release。

重复调用发生时，错误应回到拥有该状态的组件处理。上游缺输入、当前组件违反不变量、下游不可用分别形成不同终态。

Agent 循环的确定性边界位于用户问题写入之前。模型可以建议值，应用核对来源和当前版本；涉及权限、金额、发布或不可逆动作时，再进入策略或人工批准。

Agent 循环内部可以使用更细的临时对象，跨边界只暴露稳定协议。替换 ReAct 时，调用方不需要理解内部缓存和 SDK 响应。

## 从用户输入到最终回答的执行链路

沿“查询远程访问规定”推演一次。第 0 轮状态是 `question` 已写入、`observations=[]`、`steps=0`、`status=running`。模型看到可用工具 `search_notes`，提出 `ToolCall(name="search_notes", arguments={...})`。运行时确认工具存在、参数合法且调用只读，随后执行检索。

工具返回的字符串不会直接成为最终答案。运行时把它追加到 observations，步数变为 1，再把新状态交给模型。第 1 轮模型可以基于观察返回 FinalAnswer。运行时把状态改为 completed 并返回答案。谁决定了什么很清楚：模型选择候选动作，工具产生外部观察，运行时修改状态并确认终止。

若工具抛出 TimeoutError，运行时追加稳定的 `tool_error:TimeoutError` 观察。模型下一轮可以选择保守回答，运行时也可以依据错误类型直接停止。错误不能被改写成“没有相关资料”，因为超时和检索空结果是不同事实。

Agent 循环的输入合同至少列出开发者规则、用户问题和消息历史。每项都注明来源、是否必需、允许的缺省值，以及缺失后是在入口拒绝还是进入降级路径。

状态合同中的用户问题表示当前进度，消息保存本次执行依赖的快照，步骤数负责关联前后动作。三个字段用途不同，不能合并成一段自由文本。

并发分支按稳定身份合并步骤数。完成顺序只反映耗时，不能决定结果属于哪个请求，也不能让后返回的旧状态覆盖新修订。

输出合同同时描述文本和结构化对象，并为拒绝、取消、部分完成和未知状态提供固定形状。调用方据此分支，不解析错误文案猜测结果。

消息参与乐观并发检查。处理开始时读取的版本已经变化，旧候选保留为审计材料，但不能继续写入当前状态。

开发者规则里若包含模型可填写的同名字段，应用会丢弃它，再从认证、配置或活动版本中补入可信值。结构校验通过不等于授权或业务校验通过。

请求快照、响应类型、停止原因、用量字段和业务校验记录组成 Agent 循环的最小追踪材料。日志保存稳定 ID、版本和错误类，完整 Prompt、文档正文与凭证不进入指标标签。

撤回或删除用户问题时，依赖它的缓存、候选和未完成任务要按版本失效。稳定 ID 可以保留审计关系，已撤回内容不能继续进入文本。

契约还需要描述新鲜度。消息对应的数据发生变化后，旧缓存、旧候选和未完成任务怎样失效，应由版本或时间规则直接判断，不能依赖模型注意到矛盾。

删除和撤回也属于数据生命周期。Agent 循环引用的原始对象被移除时，稳定 ID 可以保留审计关系，正文与派生结果则按策略失效，避免继续向用户展示过期内容。

Agent 循环的处理机制是：循环每轮读取状态，由模型返回 final 或 tool_call；运行时校验并执行工具，把观察追加到状态，随后检查轮数、Deadline 和取消。这条描述要落成可检查的状态变化，不能只停在框架节点名称上。

装配输入接收开发者规则并建立用户问题。入口校验未通过时就地结束，后续模型、检索器或工具调用次数保持为零。

发送请求固定身份、范围、配置版本和绝对 Deadline。子步骤只继承剩余时间，不能各自重新获得完整超时。

解析响应读取消息并执行主题逻辑。调用参数由应用组装，外部返回先保存为候选，尚未获得修改领域状态的资格。

校验候选检查候选的结构、范围、版本和主题不变量。文本缺少来源、落在旧版本或越过权限时，当前状态停在 rejected 或 failed。

写入结果先保存文本与终止原因，再产生事件或通知。交付失败可以重放，核心状态写入失败则不能对外宣称完成。

解析响应出现部分结果时，由任务合同决定保留、补偿还是整体丢弃。可重建制品可以重新生成，外部副作用需要查询回执或执行补偿。

实现可以使用函数、Graph、Middleware 或 Workflow，用户问题的所有权和未知动作的停止规则不会随框架改变。

部分成功需要在步骤边界处理。解析响应已经产生一部分文本时，程序按任务合同决定保留、补偿或整体丢弃，并记录未完成项，不能默认为全部成功。

每个步骤都应有逆向动作或明确的不可逆说明。可重建制品可以删除后重算，已发送的外部命令只能查询回执或补偿；两类失败不能共用同一重试函数。

发送请求阶段冻结 scope、release、policy 和 deadline_at。用户或模型在正文中提供的同名值只作为普通内容，不覆盖运行时快照。

候选结果对应文本、结构化对象、工具调用候选、完成状态或可分类错误。校验候选逐项检查权限、版本与领域约束，问题列表为空才允许形成下一状态。

写入结果写入终态。客户端断开只影响交付通道，不触发核心逻辑重跑；重新连接时读取已经保存的状态或事件游标。

故障注入选择工具异常。程序保留原候选和错误位置，只重做失败边界，不能从入口复制整个任务并产生第二份状态。

推演结束后用 request_id 关联用户问题、文本与终止原因。测试据此排除并发请求串线，也能确认失败路径没有遗留未关闭资源。

Agent 循环在输入拒绝时不调用依赖，正常路径按 5 个阶段推进，有限修复只重做失败边界。调用次数是控制流断言，不是性能宣传。

Agent 循环的最终记录用 request_id 关联用户问题、文本和失败问题，测试据此证明结果来自本次执行，没有混入并发请求。

Agent 循环正常完成时，用户问题、消息和文本指向同一次执行。重复读取返回同一终态，未完成分支已经取消或有明确所有者。

请求快照、响应类型、停止原因、用量字段和业务校验记录用于还原处理过程。它们可以按阶段和版本聚合，敏感正文留在受控存储中，不复制到日志与指标。

结构化对象可能是合法的空结果。空结果要带范围、版本和原因；如果任务要求必须找到材料，则同一个空结果应进入拒答而非成功。

依赖返回成功状态只证明传输完成。Agent 循环还要检查文本是否满足业务范围、质量阈值和当前版本，明确拒绝也可能是正确终态。

并发完成时，每个分支保留自己的身份和局部预算。汇合节点按任务合同接纳可用结果，慢分支不能抹掉已经确认的记录。

用户问题的状态迁移必须单调：完成不能退回运行中，取消不能被迟到结果覆盖，失败重试也不能绕过入口已经固定的权限。

Agent 循环的成功证据最终要同时回答输入是什么、执行了哪些步骤、交付了什么以及为什么停止；任一项缺失都应留在未确认状态。

Agent 循环把业务验收与服务健康分开。依赖返回 200 只说明传输成功，文本仍要满足当前范围和质量要求；明确拒答也可能是正确终态。

Agent 循环的观测指标按阶段和版本聚合。错误率、空结果率、拒绝率、恢复次数与资源消耗回答不同问题，不能压成一个成功率。

::: warning Agent 循环的可信边界

文本通过结构校验后仍是候选。身份、权限、知识版本与业务事实由应用从可信服务读取，核对完成后才能执行或交付。

:::

## 循环终止与异常处理

正常终止是模型返回 FinalAnswer，并且答案通过业务检查。除此之外，运行时至少要处理未知工具、参数错误、工具超时、最大步数、总 Deadline、用户取消和连续无进展。硬限制必须写在循环条件和执行器中，只写进 Prompt 不能阻止模型继续提议动作。

最大步数检查有一个容易忽略的顺序问题：模型调用前检查剩余步数，执行动作后再更新计数。否则最后一次工具调用可能已经产生副作用，却因计数超限丢失回执。取消也不是抛出异常就结束，程序要先阻止新动作，再等待或中止可取消操作，保存已完成副作用，最后写入 cancelled 终态。

卡循环可以用动作签名和状态变化判断。连续两轮提出相同工具和同一组参数，且观察没有新增信息，继续调用模型通常只会消耗预算。运行时应保存 `no_progress` 原因并停止。工具临时超时是否重试，要同时检查工具幂等性、剩余 Deadline 和重试次数；未知工具与权限拒绝通常不应盲目重试。

Agent 循环按输入、状态、依赖、结果和交付五个位置分类错误。分类决定恢复动作，不能用同一个重试循环处理全部失败。

遇到未知动作时，系统要返回稳定的错误类型、发生阶段和可重试标记。Agent 循环保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

重复调用需要稳定身份和结果回执。再次收到同一请求时先读取旧结果；外部结果未知就停在 unknown，不能猜测失败后重新执行。

遇到工具异常时，系统要返回稳定的错误类型、发生阶段和可重试标记。Agent 循环保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

遇到没有状态变化时，系统要返回稳定的错误类型、发生阶段和可重试标记。Agent 循环保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

遇到超过最大轮数时，系统要返回稳定的错误类型、发生阶段和可重试标记。Agent 循环保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

Deadline 到期要同时记录开始时间、剩余时限和最后一次进展。Agent 循环收到这类证据后停止新增工作，只允许释放资源、保存可恢复状态或返回已经确认的局部结果。

Agent 循环结束错误处理时保存终态、可重试性和资源清理结果。后台扫描器依靠这些字段区分仍在运行、等待恢复和已经失败的任务。

Agent 循环在执行前写入绝对 Deadline、最大动作数、重复签名、无进展阈值、预算和人工取消信号。任一条件触发后都不再创建新工作。

Agent 循环把重试时间和次数计入总预算。依赖连续失败会减少后续额度，达到上限后保留原始错误，不再用模型重新措辞掩盖失败。

Agent 循环的清理动作可以重复执行。临时对象、文件句柄、子进程、连接或 Lease 仍被活动任务引用时，清理器必须拒绝删除。

固定输入快照、断言响应类型、覆盖空结果与超时，并核对业务字段是否由可信系统补齐。测试需要显式给出开发者规则、初始用户问题、预期文本和终止原因，不能只断言返回值非空。

Agent 循环的单元测试用 Fake Adapter 固定文本与错误，断言参数、调用顺序、状态修订和清理动作。它只证明本地控制逻辑。

契约测试围绕开发者规则、用户问题和结构化对象构造合法与非法样本。Schema 解析成功后继续检查权限、版本与领域不变量。

故障测试注入未知动作和重复调用，记录依赖是否被调用、状态是否改变、资源是否释放，以及同一身份重试会不会重复执行。

在解析响应前后终止执行进程，可以检查恢复边界。调用前退出允许重新领取；外部动作后退出先查回执；终态写入后只重放交付。

集成测试连接真实协议与隔离存储，检查序列化、约束、并发和超时。需要在线服务时单独记录服务版本、时间、配置与是否具备凭证。

Agent 循环的回归报告要保留失败类型分布。明确拒绝变成超时、权限错误变成普通空结果，都属于行为回归，即使总通过数没有变化。

性质测试可以补足固定样本。随机改变消息顺序、重复提交、完成顺序或状态版本，断言权限不扩大、终态不倒退、同一身份不产生两次副作用。

离线评测关注固定输入下的质量变化，运行时测试关注控制和恢复。Agent 循环只有两类证据都存在，才能同时回答“结果是否合格”和“系统是否安全完成”。

## 状态复杂化后的框架选择

当状态只在单进程内存中、工具均为只读、任务能在一个请求内完成，普通 while 循环最容易理解和测试。需要条件边、并行节点和显式状态合并时，可以使用状态图框架；任务跨分钟、跨进程或需要断线恢复时，还要把 Turn、事件、Checkpoint 与 Lease 放进持久化运行时。

框架不会替你决定状态所有者。无论使用图框架、队列还是持久化工作流，都要回答：谁写 steps，谁保存工具回执，恢复后怎样避免重复副作用，取消与完成并发时哪个状态获胜。若这些问题在普通循环里没有答案，换框架只会把缺口藏进回调和中间件。

迁移前先保留同一组确定性测试：脚本化模型依次返回工具调用和最终答案，Fake Tool 返回固定观察；另一个用例让工具超时，再断言终态和调用次数；最后让模型持续返回相同动作，断言步数上限或无进展检测生效。框架版只有通过同一行为契约，才算等价迁移。

Agent 循环长期运行后，输入 Schema、用户问题结构和依赖配置可能独立升级。每次执行固定一组版本，旧记录才能被正确读取或迁移。

Agent 循环的容量主要受上下文长度、并发请求、供应商限流和输出预算影响。并发可能缩短单次等待，也会同时占用连接、配额、内存和下游吞吐，容量要沿调用链逐层核算。

候选版本在固定样本上比较正确性、错误类型、延迟和资源消耗。未知动作等安全红线回归时直接停止发布，不能用平均质量抵消。

未知动作的降级路径在发布前写好：减少非关键增强、返回已经确认的结果，或明确暂时无法确认。缺失事实不能交给模型补写。

Agent 循环的运行手册从 request_id 定位请求快照、响应类型、停止原因、用量字段和业务校验记录，再决定重试、补偿、取消或回滚，无需先展开完整敏感内容。

数据保留按证据用途分级。聚合字段可以保留更久，原始输入和大结果设置短期限、访问控制与删除通道。

Agent 循环先在单进程实现状态、超时、错误和测试；只有恢复与容量证据提出要求时，再增加队列、Lease、分布式缓存或工作流引擎。

Agent 循环的监控阈值要对应可执行动作。上下文长度、并发请求、供应商限流和输出预算中的某项接近上限时，系统可以限流、排队、缩小候选或切换保守路径；只发送告警不会保护正在运行的任务。

回滚要覆盖代码之外的状态。Agent 循环若改变 Schema、缓存键或持久化记录，旧版本是否还能读取新写入数据必须提前验证；无法双向兼容时采用候选版本隔离。

采用 Agent 循环前先画最小控制图。固定函数已经能完成任务时，新增模型决策和跨进程状态只会扩大测试与运维范围。

Agent 循环与 ReAct 的差别落在控制权：谁选择下一步，谁保存用户问题，谁确认文本可信。

状态机可以与 Agent 循环组合。组合之后，外部知识仍需授权，工具调用仍需校验，模型输出仍停留在候选状态。

Agent 循环适合价值足够、失败可观察、动作可约束且预算可接受的任务。高风险且不可逆的决定需要确定性规则或人工批准。

格式正确但事实错误的文本是必要反例。系统若直接进入成功，说明业务验证缺失；保留候选并给出证据问题，才符合边界。

执行期间修改消息可以检验并发设计。旧动作仍能覆盖新状态，说明版本或 Lease 有缺口，增加 Prompt 规则无法修复竞态。

Agent 循环增加了状态、调用、恢复责任和故障面。设计记录应明确获得的能力，也列出新增的退出、降级与回滚路径。

演进可以从最小闭环开始：一个调用、一个状态对象、一组明确错误和几条确定性测试。真实 Trace 证明瓶颈后，再加入并发、缓存、队列或更复杂策略。
