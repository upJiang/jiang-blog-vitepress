# 什么是 Agent 循环

一次普通模型调用只有一条直线：应用提交输入，模型返回候选。模型如果发现缺少账号状态，只能在现有上下文里回答“不知道”，或者猜一个结果。Agent 循环允许它先提出查询动作，程序执行查询，把结果作为新观察放回状态，再让模型决定下一步。

这段循环听起来像连续调用模型，真正决定它是不是 Agent 的是控制关系。模型提出候选动作，运行时决定动作能否执行；工具负责读取或修改外部世界；状态保存已经发生的事实；停止条件限制循环能走多远。模型没有权限直接执行工具，也不能宣布一个未通过应用校验的任务已经完成。

::: info 最小 Agent 循环

1. 运行时把目标、已有观察和可用工具交给模型。
2. 模型返回最终回答，或者返回一个工具调用候选。
3. 运行时校验候选。允许执行时调用工具，并把结果追加为观察。
4. 新状态进入下一轮，直到完成或触发停止条件。

:::

本文不用框架实现这条链。贯穿任务仍是“我的账号为什么不能远程访问”，但最小示例只使用一个只读的 `search_notes` 工具。它能证明循环怎样推进，不能证明模型有真实推理能力，也没有实现生产环境的权限、持久化和恢复。

## Agent 循环的定义与作用

Agent 循环是一个由程序控制、由模型参与决策的有限状态循环。它适合下一步依赖新观察的任务。开始时，系统只知道用户目标；模型根据当前状态提出动作；工具返回外部结果；模型读取更新后的状态后，可能继续调用工具，也可能生成最终回答。

“有限”很重要。循环必须受最大步骤、总时限、预算、取消信号和无进展规则约束。只在 Prompt 里写“不要无限循环”没有执行力，模型仍可能连续提出同一个搜索。硬限制由代码检查，触发后不再创建新动作。

### 模型、运行时、工具和状态各自负责什么

模型负责把目标与观察转换为 `ToolCall` 或 `FinalAnswer`。这两个类型是候选决定，不是已经发生的业务事实。模型可以建议查询 `search_notes`，但它不能自己访问数据，也不能把参数里的用户范围当成可信权限。

运行时拥有循环。它读取当前状态，调用模型，解析决定，检查工具是否存在，执行允许的工具，再修改步骤数、观察和终态。最大步骤与错误分类也由运行时执行。换成另一个模型，控制规则不应跟着丢失。

工具把受控能力暴露给运行时。只读检索返回观察，有副作用的工具还需要授权、幂等键、回执和补偿。工具收到的身份与权限由程序注入，不能接受模型自报的用户 ID 或 Scope。

状态记录这次执行已经知道什么。最小状态可以只有问题、观察列表、决策次数和运行状态；需要恢复时再增加 Turn ID、状态版本、Deadline、工具回执和检查点。把这些字段埋在 Prompt 文本里，程序就无法可靠判断是否超限、是否重复执行以及恢复到哪一步。

| 参与者 | 可以决定 | 不能决定 |
| --- | --- | --- |
| 模型 | 候选回答或候选工具调用 | 权限、真实工具结果、业务完成状态 |
| 运行时 | 是否执行、怎样更新状态、何时停止 | 工具背后的业务事实 |
| 工具 | 在授权范围内读取或执行 | 修改循环上限、伪造最终回答 |
| 业务校验 | 候选是否可交付 | 替模型补写缺失证据 |

### Agent 循环与相邻概念的差别

固定工作流的步骤和分支由程序预先写好。输入 A 总是经过步骤 B、C，条件 D 成立就进入 E。Agent 循环把部分“下一步选什么”交给模型，因此能处理路径难以提前枚举的任务，也增加了不可预测动作、重复尝试和成本失控的风险。

ReAct 是组织推理、行动与观察的一种常见模式，Agent 循环是承载这类模式的运行结构。运行时可以使用 ReAct，也可以要求模型直接输出结构化动作；无论 Prompt 怎样写，动作执行和终止仍由程序控制。Function Calling 或 Tool Calling 提供结构化动作协议，本身没有循环、状态和停止策略。

状态机描述合法状态与转换，Agent 循环可以实现为状态机。两者关注点不同：状态机保证从 running 到 completed、failed 等转换合法；Agent 循环描述模型决策、工具执行和新观察怎样反复发生。任务只有确定步骤时，普通状态机或工作流往往更简单。

一个确定性函数已经能算出结果时，不需要 Agent。权限判断、金额计算、数据库约束和发布开关都应留在程序中。Agent 适合路径需要根据开放信息调整，并且每个动作都能检查、限制和停止的任务。

## 从用户输入到最终回答的执行链路

开始时，运行时创建状态：问题是“远程访问需要满足什么条件”，观察为空，`steps=0`，状态为 running。工具注册表里只有 `search_notes`，它接收查询文本和数量上限，返回一段只读检索结果。

### 第 0 轮先产生动作候选

运行时把问题、观察副本和工具说明交给模型。观察为空，脚本化模型返回：

```text
ToolCall(
  name="search_notes",
  arguments={"query": "远程访问需要满足什么条件", "limit": 2}
)
```

返回 `ToolCall` 只表示模型希望调用工具。运行时先把决策次数增加为 1，再从注册表查找工具。真实系统还要校验参数 Schema、注入可信范围、执行授权并检查剩余时间。本文示例只检查工具名称是否存在，把这些生产约束留给后面的工具文章。

工具返回“需要设备合规与审批”。运行时把这段文本追加到 `observations`。它没有直接把工具结果作为最终答案，因为原始结果可能需要解释，也可能包含不可信指令。状态现在是：

```text
question = "远程访问需要满足什么条件"
observations = ["需要设备合规与审批"]
steps = 1
status = "running"
```

### 第 1 轮根据观察结束循环

模型再次读取相同问题和新的观察，返回 `FinalAnswer(text="根据检索结果：需要设备合规与审批")`。运行时把决策次数增加为 2，将状态改为 completed，并返回状态与答案。这里的 `steps` 统计模型做了几次决定，不是工具调用次数：第一轮决定调用工具，第二轮决定给出答案。

在完整系统里，FinalAnswer 仍要经过事实、引用与权限校验。工具结果只能支持“通用条件”，不能支持“你的设备不合规”。如果用户问的是个人失败原因，而工具只返回制度，业务校验应拒绝这个具体归因，或者让循环调用经过授权的账号状态工具。

### 状态转移要能从记录中复原

一条可调试的轨迹至少记录轮次、输入状态版本、模型决定、工具调用标识、观察摘要和停止原因。正文与凭证不宜复制到普通指标中，可以用受控引用和哈希关联。

| 轮次 | 输入观察 | 模型候选 | 运行时动作 | 新状态 |
| --- | --- | --- | --- | --- |
| 0 | 空 | 调用 `search_notes` | 校验并执行工具 | running，steps=1 |
| 1 | 检索结果 | 返回最终回答 | 保存候选并结束 | completed，steps=2 |

如果日志只有最终文本，就无法回答工具是否真的执行、回答用了哪次结果、循环为什么停止。相反，完整 Prompt 全量写入日志又会泄露用户数据。工程上保存结构化轨迹，敏感内容保留在权限受控的存储中。

### 工具失败也是一种观察

假设 `search_notes` 抛出 `TimeoutError`。示例捕获异常，把 `tool_error:TimeoutError` 追加到观察，然后进入下一轮。脚本化模型看到这个观察后返回“检索失败，当前无法核对答案”，运行时以 completed 结束。

这个结果表示循环正常产出了一条保守回答，不表示检索成功。若业务要求必须取得证据，校验层应把它改为 failed 或 rejected。运行时完成、工具成功与任务完成是三个不同状态，不能只用一个布尔值表示。

空结果也不能伪装成超时。工具成功返回空列表，说明在本次范围与查询下没有命中；超时说明结果未知；权限拒绝说明当前身份不允许查询。三种观察会导向不同动作，工具适配器应返回稳定类型，示例用字符串只是为了让最小代码容易阅读。

### 用联合类型限制模型决定

`Decision = ToolCall | FinalAnswer` 把模型输出限制为两条分支。接入真实模型时，适配器负责把结构化输出解析为这两个数据类。缺字段、未知类型和非法参数应在适配器或运行时入口失败，不能把任意 JSON 直接传给工具。

`ToolCall` 只保存工具名和候选参数，没有用户身份、租户范围或知识版本。这是刻意的边界：这些可信字段来自运行时。即使模型参数里出现 `scope_ids`，工具命令也要丢弃它，再从认证上下文生成真实范围。

`FinalAnswer` 只有文本，适合讲清最小控制流。证据型系统通常会扩展为答案、Claim、Evidence 引用和验证状态，但这些字段属于可信回答阶段，不应在第一版循环里同时展开。

### 让模型只能读取状态副本

`DecisionModel` 是一个 Protocol。`decide` 接收问题和观察列表，返回 Decision。运行时传入 `list(state.observations)`，因此模型适配器拿到的是浅拷贝，不能直接向真实状态追加观察或修改步数。

这个隔离让状态只有一个写入方。模型调用失败时，运行时仍知道上一版状态是什么；测试也能断言模型调用前后的变化。观察元素在示例里是不可变字符串，所以浅拷贝足够。换成可变字典后，需要不可变数据结构或深层复制，避免适配器修改内部对象。

### while 循环就是最小运行时

`run_agent` 创建 AgentState，随后在 `steps < max_steps` 时调用模型。每次模型返回一个有效决定，steps 就加一。FinalAnswer 让状态进入 completed；ToolCall 进入工具分支；循环退出仍未回答时，状态进入 failed 并抛出 `step_limit_reached`。

工具注册表 `dict[str, Tool]` 是动作白名单。模型返回未注册名称时，代码不会动态导入函数或执行同名命令，而是设置 failed 并抛出 `unknown_tool`。工具白名单解决“能调用什么”，参数 Schema、授权和副作用控制还需要单独实现。

示例只把 `TimeoutError` 和 `ValueError` 转成错误观察。前者代表依赖在规定时间内没有结果，后者代表输入或工具业务校验失败。其他异常向外传播，避免把程序缺陷伪装成模型可处理的观察。生产代码会使用自定义错误类型和统一结果对象，而不是依赖 Python 内置异常名称作为长期协议。

### ScriptedModel 不是假装在线模型

`ScriptedModel` 根据观察数量返回固定决定。第一次调用工具；有正常观察就给出答案；最后一条观察以 `tool_error:` 开头时返回保守文本。它只用于验证运行时控制流，无法评价 Prompt、模型推理、工具选择质量或 Token 消耗。

使用这种脚本化策略，测试不需要 API Key，不受模型随机性影响，也不会把伪造的 usage 写成在线结果。真实模型适配器应有另一组集成测试，核对请求字段、响应解析和错误映射；模型效果再由固定评测集验证。

### 运行最小示例时应该观察什么

正常用例给 `search_notes` 一个固定函数，执行后应得到 completed、steps=2，答案包含工具返回值。测试证明两轮状态变化和工具结果进入下一次决策，没有证明答案适合生产。

工具超时用例让函数抛出 `TimeoutError`，应当看到一条错误观察，第二轮产生保守回答。未知工具用例让模型返回未注册名称，运行时必须在调用工具前失败。步数用例让模型不断返回调用，达到上限后停止，不能继续请求模型。

这些测试还应检查调用次数。未知工具时工具调用为零；正常路径工具调用一次、模型调用两次；达到 `max_steps` 后模型调用次数不超过上限。调用次数是控制流证据，不是性能指标。

## 循环终止与异常处理

循环能产生 FinalAnswer，只解决了正常出口。生产系统更难的部分是明确所有非正常出口，并让每种出口留下可恢复或可解释的状态。

### 最终回答与硬限制

最终回答是模型主动结束的候选。运行时解析成功后，仍要做结构、证据和业务校验。校验失败可以执行一次范围有限的修复，也可以直接拒答；不能把“模型说完成了”当成任务完成。

最大步骤是最直接的硬限制。步数应明确统计模型决定、工具调用还是两者，否则配置含义会漂移。本文代码统计模型决定，FinalAnswer 也占一步。若 `max_steps=1`，模型第一轮选择工具后就没有第二轮生成答案，最终触发步数上限。这种行为需要测试和文档说明。

总 Deadline 限制整次任务，而不是给每个子步骤重新发一份完整超时。进入模型和工具前都计算剩余时间。Deadline 到期后不再创建新动作，只允许取消正在运行的可取消操作、保存回执并写终态。当前最小示例没有实现 Deadline，不能据此声称支持长任务超时控制。

预算限制可以覆盖 Token、工具次数、外部费用或并行度。模型仍可能提出超预算动作，运行时返回 `budget_exceeded` 并停止。预算字段来自程序配置，Prompt 中的数字只帮助模型规划，不是硬约束。

### 未知工具、参数错误与权限拒绝

未知工具通常表示模型输出与当前工具目录不一致，或模型产生了不存在的名称。运行时记录原始候选和可用工具版本，然后失败。原样重试可能再次得到同一名称，除非策略明确允许一次受限修复，否则不应无限要求模型“换一个”。

参数错误发生在 Schema 或业务校验。缺少可修复字段时，可以把结构化问题作为观察交给模型一次；范围越权、身份伪造和禁止动作直接拒绝，不能让模型通过改写参数绕过。权限拒绝属于确定性结果，重试前必须有授权状态变化。

工具异常要区分超时、临时不可用、空结果和未知执行结果。有副作用的工具在网络断开后可能已经执行，简单重试会重复操作。运行时先用幂等键查询回执；无法确认时进入 unknown 或人工处理，不猜测失败后再次执行。

### 无进展与过早结束

模型连续提出相同工具与相同参数，工具又返回相同观察，状态没有新增信息。运行时可以对动作名称、规范化参数和关键观察生成签名，连续重复达到阈值后以 `no_progress` 停止。只检查最大步骤也能终止，但会多消耗几轮预算，且无法指出任务卡住的原因。

另一端是过早结束。模型第一轮没有使用所需工具，直接根据参数知识回答。若任务合同要求当前证据，业务校验就应拒绝 FinalAnswer，并返回 `evidence_required`，最多允许一次明确的工具补充。设置“至少循环几轮”只能粗略阻止早退，不能证明模型获得了正确证据。

Tool Result 会不断扩大上下文。每轮原样保留大段搜索结果，循环可能在达到步骤上限前先耗尽窗口。运行时要为观察设置独立预算，保留稳定来源 ID，压缩重复结果，并确保压缩后的内容仍能回查。观察压缩属于上下文策略，不能删除工具错误、否定条件和未完成动作。

### 取消需要处理竞态

用户取消时，入口先写入取消意图，运行时停止发起新模型调用和工具动作。已发出的调用可能稍后返回，写状态时必须检查版本或终态，迟到结果不能把 cancelled 改回 running 或 completed。

只读工具可以丢弃迟到结果；有副作用的工具要查询回执并保存已经发生的动作。取消不等于回滚，程序只能补偿那些有明确逆向操作的副作用。当前最小示例没有取消和回执，因此只适合单进程、只读、短任务。

错误记录至少包含发生阶段、状态版本、稳定错误码、是否可重试和最后一次进展。对外可以返回简化文案，内部不能只保存“Agent 失败了”。模型错误、工具失败、权限拒绝、步数耗尽和证据不足需要不同的恢复动作。

### 状态不变量比循环语法更重要

状态转换要有可以被测试的硬规则。running 只能进入 completed、failed、cancelled 或 expired，终态不能被迟到的模型响应改回 running。steps 只能增加，观察列表只能追加经过运行时接纳的结果，工具异常也要以结构化观察或错误终态保存。若某个分支直接改写整份状态，恢复和审计都会失去依据。

每一轮开始前可以检查三个条件：当前状态仍是 running，剩余步骤大于零，当前版本没有被取消或替换。模型返回后先解析和校验，再决定是否增加 steps 或创建工具任务。这样未知 JSON、权限拒绝和解析异常不会被算成一次成功动作。示例把 steps 在解析后增加，是为了突出最小流程；生产运行时可以把“模型调用次数”和“工具执行次数”拆成两个计数器。

工具执行前生成稳定的动作 ID，执行结果带回同一个 ID。结果写入状态时比较版本，旧版本的结果只能作为审计记录，不能覆盖较新的观察。进程在工具成功后崩溃时，恢复逻辑先查询动作 ID 的回执，再决定补写成功结果或标记未知。仅靠 `steps=1` 无法知道副作用有没有发生。

终态也要说明交付条件。completed 表示控制流结束，不一定表示答案有足够证据；failed 表示程序无法继续，可能需要人工排查；rejected 表示输入或候选违反了确定性规则；cancelled 表示用户或策略停止了任务。把这些状态都转换成一段普通文本，调用方就无法决定是否重试、是否展示草稿以及是否允许下一步操作。

设计评审时可以拿一条最短轨迹逐项询问：初始问题由谁写入，第一轮模型看到了哪些观察，工具执行是否有授权，工具结果怎样和动作配对，哪一条规则让循环停止，迟到结果会写到哪里。回答不出其中任一项，就先补状态契约，再讨论模型和框架。

## 状态复杂化后的框架选择

普通 while 循环适合状态留在单进程内存、工具只读、任务在一次请求内结束的情况。它的优势是控制流直接，状态变化和异常出口容易测试。学习 Agent 时先写这个版本，可以看清框架后来替你管理了什么。

### 什么时候使用状态图

任务出现条件路由、多个节点、并行分支和显式状态合并时，状态图比嵌套 while 与 if 更容易审查。每个节点读取状态并返回局部更新，边决定下一节点，Reducer 规定并行结果怎样合并。

状态图没有自动解决权限和副作用。模型节点仍只产生候选，工具节点仍要授权，合并函数仍要防止迟到状态覆盖新版本。Checkpoint 能保存图执行位置，也要配合稳定的 Turn 身份和工具回执才能安全恢复。

### 什么时候加入队列与持久化

任务跨越一次 HTTP 请求、执行时间较长或需要断线恢复时，状态必须离开进程内存。入口创建 Turn，Worker 按状态版本领取任务，每个步骤保存事件和检查点。Lease 表示哪个 Worker 暂时拥有执行权，ACK 表示队列消息已经处理；它们解决并发与故障恢复，不改变 Agent 循环的基本职责。

持久化后要防止重复副作用。Worker 可能在工具执行成功后、保存状态前崩溃，消息重新投递时无法只凭步骤数判断是否执行过。每次动作需要稳定 call_id 和幂等键，恢复时先查回执，再决定补写状态、重试或进入 unknown。

### 什么时候选择持久化工作流

任务持续数小时或数天、包含等待人工审批、定时器和跨服务补偿时，持久化工作流可以记录执行历史并在进程重启后恢复。它适合确定性编排和长时间等待；模型调用与外部工具仍作为 Activity 或等价边界执行，重试和超时要按副作用语义配置。

框架选择可以沿三个问题判断：状态是否需要跨进程保存，分支是否多到普通控制流难以审查，副作用是否需要可靠恢复。三个答案都是否，while 循环已经够用。先引入分布式队列或工作流，会增加序列化、租约、重复投递和运维成本，却没有带来任务能力。

### 迁移时保持同一行为契约

从 while 循环迁移到状态图或队列，不要同时改 Prompt、工具参数和完成标准。先复用同一组确定性测试：正常路径执行一次工具后完成；工具超时产生可分类观察；未知工具在执行前失败；连续动作达到上限后停止；取消后的迟到结果不能覆盖终态。

迁移前后的轨迹不必使用相同内部字段，但要回答相同问题：初始输入是什么，模型提出了什么，程序执行了哪些动作，状态怎样变化，最终为何停止。框架版如果只能展示节点成功，却无法关联工具回执和终止原因，就还没有达到原来循环的行为契约。

生产系统最终可能同时使用状态图、队列和持久化工作流。状态图表达单个 Turn 内的决策与分支，队列把执行交给 Worker，工作流管理长时间等待和恢复。它们是不同层的组件，不应为了“生产级”把所有能力都塞进第一个 Agent 循环。

最小循环建立了后续课程的坐标：Tool Calling 约束动作形状，Context 决定每轮看到什么，Memory 提供调用外的可检索信息，Runtime 保存 Turn 与恢复状态，Eval 检查循环是否真的完成任务。无论系统扩展到哪一层，模型提出候选、程序执行约束、状态保存事实这条边界都应保留。
