# Agent 模式选择手册

根据任务不确定性、依赖、质量、延迟、成本和风险选择最小可行模式。**Pattern Selection**、**Decision**、**Agent** 分别指向同一条执行链上的不同对象：任务目标、分支可预测性、外部动作、依赖关系、质量阈值、Deadline、预算和失败代价进入系统，decision_id、candidate_pattern、required_state、tool_scope、cost_envelope、stop_rule、fallback 和 rejection_reason 保存处理中间状态，最终得到模式选择、拒绝其他模式的具体原因、状态需求、停止条件、验证方式和降级方案。

Agent 模式选择手册位于课程知识的检索入口与决策参考层。它的主要机制是先排除固定函数和普通工作流已经能完成的任务，再根据运行时不确定性、依赖图、是否需要多路径搜索及失败成本选择最小模式，并为升级条件设置可测指标。从流行框架反推需求、单步任务使用多 Agent、把并行误当无依赖、没有客观评分却使用 Reflection、搜索空间无法评估仍用 ToT 和高风险动作缺人工确认会让链路在不同位置停止，错误记录必须保留发生阶段、当时的状态和终止原因。

::: info 贯穿示例

Agent 模式选择手册场景：团队准备自动生成一份需要查资料、核对冲突并交付报告的结果，需要决定单 Agent、DAG 还是研究循环。身份、权限、版本和业务事实由应用提供，模型与外部内容只产生需要检查的候选。

:::

这次推演用定义、输入、状态所有者、决策者、输出和适用限制把请求和终态关联起来。与确定性工作流、ReAct、Planning、Reflection、DAG、Handoff 和研究型 Agent 比较时，重点看输入来源、状态所有者、下一步的决策者和失败终点。

一次 Agent 模式选择手册执行可以画成“定位问题层次 → 确认控制者 → 比较相邻概念 → 选择主文章 → 用反例复核”。任务目标在入口出现，decision_id 记录进度，模式选择只有通过当前主题的校验条件后才会成为可交付结果。

从流行框架反推需求与单步任务使用多 Agent 会产生不同证据。前者先检查 decision_id 和输入来源，后者沿调用记录定位依赖或状态冲突；不区分发生位置，重试会掩盖原始原因。

Agent 模式选择手册与确定性工作流的共同点不代表它们可以互换。当前主题拥有 candidate_pattern，相邻组件只通过契约读取或提交候选，不能直接修改这个状态。

Agent 模式选择手册用来反查系统层次，不替代主文章。定位时依次确认任务目标、decision_id、下一步决策者与模式选择，再沿依赖进入对应机制和实现。

## 先判断任务需要多少运行时决策

根据任务不确定性、依赖、质量、延迟、成本和风险选择最小可行模式。在“Agent 模式选择手册场景：团队准备自动生成一份需要查资料、核对冲突并交付报告的结果，需要决定单 Agent、DAG 还是研究循环”这类任务里，Agent 模式选择手册负责把任务目标带入处理链，并明确模式选择可以交付的条件。

Agent 模式选择手册位于课程知识的检索入口与决策参考层。它处理先排除固定函数和普通工作流已经能完成的任务，再根据运行时不确定性、依赖图、是否需要多路径搜索及失败成本选择最小模式，并为升级条件设置可测指标，身份认证、授权结果和最终业务状态仍由应用中的确定性组件负责。

任务目标是这条链路的起点。来源缺失时，程序只能拒绝请求或采用明确记录的默认值；模型补出的字段没有可信来源，不能继续驱动确认控制者。

从流行框架反推需求会直接破坏 decision_id 与模式选择之间的对应关系。排查时先保留原始输入摘要和发生阶段，再判断是否允许重试。

单步任务使用多 Agent 属于另一类风险，它影响的是 candidate_pattern 或下游解释。两类错误不能共用“重新调用一次模型”这样的处理方式。

Agent 模式选择手册的完成条件至少包含 decision_id、candidate_pattern、模式选择和检查结论。只有最终文字，没有这些中间记录，无法证明结果来自本次请求。

单进程 Demo 可以把状态放在内存中，但仍要保留输入、状态转移和停止原因。跨进程、带权限或有副作用的任务再把这些字段持久化，不能依赖 Prompt 代替状态。

Agent 模式选择手册还要把业务条件写成状态条件：外部动作何时就绪，模式选择何时允许交付，从流行框架反推需求发生后是否还能继续。

Agent 模式选择手册对外区分完成、部分完成和无法确认。三个状态如果都包装成一段顺畅文字，上层界面无法采用不同处理方式。

## 固定函数、工作流与 Agent 的分界

Agent 模式选择手册接收任务目标、分支可预测性、外部动作、依赖关系、质量阈值、Deadline、预算和失败代价，向下游交付模式选择、拒绝其他模式的具体原因、状态需求、停止条件、验证方式和降级方案。输入与输出之间采用明确契约，避免调用方把一句含糊目标直接交给底层适配器。

术语表只负责导航和比较，完整机制、代码与验证仍由对应主文章负责。因此 decision_id 与 candidate_pattern 要有唯一写入方，其他组件只能通过版本化命令申请修改。

确定性工作流与 Agent 模式选择手册解决的问题相邻，但控制权不同。比较两者时要看谁选择比较相邻概念、谁保存 decision_id、谁确认模式选择。

ReAct 可以参与同一请求，却不能替代 Agent 模式选择手册的职责。组合之后，分支可预测性的可信来源和从流行框架反推需求的终止规则仍需单独检查。

required_state 若只保存在 SDK 对象里，重试或进程退出后就失去解释依据。需要恢复或审计的字段进入持久层，体积较大的结果只保存稳定引用。

Agent 模式选择手册使用的身份、范围和版本来自可信运行时。用户消息、检索文本和模型候选可以表达意图，不能提升权限或改写活动 Release。

单步任务使用多 Agent 发生时，错误应回到拥有该状态的组件处理。上游缺输入、当前组件违反不变量、下游不可用分别形成不同终态。

Agent 模式选择手册的确定性边界位于 decision_id 写入之前。模型可以建议值，应用核对来源和当前版本；涉及权限、金额、发布或不可逆动作时，再进入策略或人工批准。

Agent 模式选择手册内部可以使用更细的临时对象，跨边界只暴露稳定协议。替换确定性工作流时，调用方不需要理解内部缓存和 SDK 响应。

## Router 适合有限模式选择

Agent 模式选择手册的输入合同至少列出任务目标、分支可预测性和外部动作。每项都注明来源、是否必需、允许的缺省值，以及缺失后是在入口拒绝还是进入降级路径。

状态合同中的 decision_id 表示当前进度，candidate_pattern 保存本次执行依赖的快照，required_state 负责关联前后动作。三个字段用途不同，不能合并成一段自由文本。

并发分支按稳定身份合并 required_state。完成顺序只反映耗时，不能决定结果属于哪个请求，也不能让后返回的旧状态覆盖新修订。

输出合同同时描述模式选择和拒绝其他模式的具体原因，并为拒绝、取消、部分完成和未知状态提供固定形状。调用方据此分支，不解析错误文案猜测结果。

candidate_pattern 参与乐观并发检查。处理开始时读取的版本已经变化，旧候选保留为审计材料，但不能继续写入当前状态。

任务目标里若包含模型可填写的同名字段，应用会丢弃它，再从认证、配置或活动版本中补入可信值。结构校验通过不等于授权或业务校验通过。

定义、输入、状态所有者、决策者、输出和适用限制组成 Agent 模式选择手册的最小追踪材料。日志保存稳定 ID、版本和错误类，完整 Prompt、文档正文与凭证不进入指标标签。

撤回或删除分支可预测性时，依赖它的缓存、候选和未完成任务要按版本失效。稳定 ID 可以保留审计关系，已撤回内容不能继续进入模式选择。

契约还需要描述新鲜度。candidate_pattern 对应的数据发生变化后，旧缓存、旧候选和未完成任务怎样失效，应由版本或时间规则直接判断，不能依赖模型注意到矛盾。

删除和撤回也属于数据生命周期。Agent 模式选择手册引用的原始对象被移除时，稳定 ID 可以保留审计关系，正文与派生结果则按策略失效，避免继续向用户展示过期内容。

::: warning Agent 模式选择手册的可信边界

模式选择通过结构校验后仍是候选。身份、权限、知识版本与业务事实由应用从可信服务读取，核对完成后才能执行或交付。

:::

## Planning 适合未知步骤的任务

Agent 模式选择手册的处理机制是：先排除固定函数和普通工作流已经能完成的任务，再根据运行时不确定性、依赖图、是否需要多路径搜索及失败成本选择最小模式，并为升级条件设置可测指标。这条描述要落成可检查的状态变化，不能只停在框架节点名称上。

定位问题层次接收任务目标并建立 decision_id。入口校验未通过时就地结束，后续模型、检索器或工具调用次数保持为零。

确认控制者固定身份、范围、配置版本和绝对 Deadline。子步骤只继承剩余时间，不能各自重新获得完整超时。

比较相邻概念读取 candidate_pattern 并执行主题逻辑。调用参数由应用组装，外部返回先保存为候选，尚未获得修改领域状态的资格。

选择主文章检查候选的结构、范围、版本和主题不变量。模式选择缺少来源、落在旧版本或越过权限时，当前状态停在 rejected 或 failed。

用反例复核先保存模式选择与终止原因，再产生事件或通知。交付失败可以重放，核心状态写入失败则不能对外宣称完成。

比较相邻概念出现部分结果时，由任务合同决定保留、补偿还是整体丢弃。可重建制品可以重新生成，外部副作用需要查询回执或执行补偿。

实现可以使用函数、Graph、Middleware 或 Workflow，decision_id 的所有权和从流行框架反推需求的停止规则不会随框架改变。

部分成功需要在步骤边界处理。比较相邻概念已经产生一部分模式选择时，程序按任务合同决定保留、补偿或整体丢弃，并记录未完成项，不能默认为全部成功。

每个步骤都应有逆向动作或明确的不可逆说明。可重建制品可以删除后重算，已发送的外部命令只能查询回执或补偿；两类失败不能共用同一重试函数。

## Reflection 只修复可观察问题

用“Agent 模式选择手册场景：团队准备自动生成一份需要查资料、核对冲突并交付报告的结果，需要决定单 Agent、DAG 还是研究循环”推演一次 Agent 模式选择手册。入口创建 request_id，读取可信身份，把任务目标和当前版本写入初始状态。

定位问题层次阶段生成 decision_id 与输入摘要。若分支可预测性缺失，请求返回 rejected，并指出缺少哪项材料，不继续消耗模型或外部服务配额。

确认控制者阶段冻结 scope、release、policy 和 deadline_at。用户或模型在正文中提供的同名值只作为普通内容，不覆盖运行时快照。

比较相邻概念按“先排除固定函数和普通工作流已经能完成的任务，再根据运行时不确定性、依赖图、是否需要多路径搜索及失败成本选择最小模式，并为升级条件设置可测指标”推进。每次依赖调用保存 call_id、参数摘要、开始时间与状态版本，后续才能判断超时前是否已经产生结果。

候选结果对应模式选择、拒绝其他模式的具体原因、状态需求、停止条件、验证方式和降级方案。选择主文章逐项检查权限、版本与领域约束，问题列表为空才允许形成下一状态。

用反例复核写入终态。客户端断开只影响交付通道，不触发核心逻辑重跑；重新连接时读取已经保存的状态或事件游标。

故障注入选择把并行误当无依赖。程序保留原候选和错误位置，只重做失败边界，不能从入口复制整个任务并产生第二份状态。

推演结束后用 request_id 关联 decision_id、模式选择与终止原因。测试据此排除并发请求串线，也能确认失败路径没有遗留未关闭资源。

Agent 模式选择手册在输入拒绝时不调用依赖，正常路径按 5 个阶段推进，有限修复只重做失败边界。调用次数是控制流断言，不是性能宣传。

Agent 模式选择手册的最终记录用 request_id 关联 decision_id、模式选择和失败问题，测试据此证明结果来自本次执行，没有混入并发请求。

## DAG、多 Agent 与 Handoff 怎样选择

Agent 模式选择手册正常完成时，decision_id、candidate_pattern 和模式选择指向同一次执行。重复读取返回同一终态，未完成分支已经取消或有明确所有者。

定义、输入、状态所有者、决策者、输出和适用限制用于还原处理过程。它们可以按阶段和版本聚合，敏感正文留在受控存储中，不复制到日志与指标。

拒绝其他模式的具体原因可能是合法的空结果。空结果要带范围、版本和原因；如果任务要求必须找到材料，则同一个空结果应进入拒答而非成功。

依赖返回成功状态只证明传输完成。Agent 模式选择手册还要检查模式选择是否满足业务范围、质量阈值和当前版本，明确拒绝也可能是正确终态。

并发完成时，每个分支保留自己的身份和局部预算。汇合节点按任务合同接纳可用结果，慢分支不能抹掉已经确认的记录。

decision_id 的状态迁移必须单调：完成不能退回运行中，取消不能被迟到结果覆盖，失败重试也不能绕过入口已经固定的权限。

Agent 模式选择手册的成功证据最终要同时回答输入是什么、执行了哪些步骤、交付了什么以及为什么停止；任一项缺失都应留在未确认状态。

Agent 模式选择手册把业务验收与服务健康分开。依赖返回 200 只说明传输成功，模式选择仍要满足当前范围和质量要求；明确拒答也可能是正确终态。

Agent 模式选择手册的观测指标按阶段和版本聚合。错误率、空结果率、拒绝率、恢复次数与资源消耗回答不同问题，不能压成一个成功率。

## 研究任务何时需要搜索式推理

Agent 模式选择手册按输入、状态、依赖、结果和交付五个位置分类错误。分类决定恢复动作，不能用同一个重试循环处理全部失败。

遇到从流行框架反推需求时，系统要返回稳定的错误类型、发生阶段和可重试标记。Agent 模式选择手册保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

遇到单步任务使用多 Agent 时，系统要返回稳定的错误类型、发生阶段和可重试标记。Agent 模式选择手册保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

遇到把并行误当无依赖时，系统要返回稳定的错误类型、发生阶段和可重试标记。Agent 模式选择手册保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

遇到没有客观评分却使用 Reflection 时，系统要返回稳定的错误类型、发生阶段和可重试标记。Agent 模式选择手册保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

遇到搜索空间无法评估仍用 ToT 时，系统要返回稳定的错误类型、发生阶段和可重试标记。Agent 模式选择手册保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

遇到高风险动作缺人工确认时，系统要返回稳定的错误类型、发生阶段和可重试标记。Agent 模式选择手册保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

Agent 模式选择手册结束错误处理时保存终态、可重试性和资源清理结果。后台扫描器依靠这些字段区分仍在运行、等待恢复和已经失败的任务。

Agent 模式选择手册在执行前写入绝对 Deadline、最大动作数、重复签名、无进展阈值、预算和人工取消信号。任一条件触发后都不再创建新工作。

Agent 模式选择手册把重试时间和次数计入总预算。依赖连续失败会减少后续额度，达到上限后保留原始错误，不再用模型重新措辞掩盖失败。

Agent 模式选择手册的清理动作可以重复执行。临时对象、文件句柄、子进程、连接或 Lease 仍被活动任务引用时，清理器必须拒绝删除。

## 风险、预算与可恢复性怎样限制模式

用同一任务分别画固定流程、ReAct、Planning、DAG、Handoff 和研究循环的控制图，比较状态数、调用数、失败面与可撤销性。测试需要显式给出任务目标、初始 decision_id、预期模式选择和终止原因，不能只断言返回值非空。

Agent 模式选择手册的单元测试用 Fake Adapter 固定模式选择与错误，断言参数、调用顺序、状态修订和清理动作。它只证明本地控制逻辑。

契约测试围绕任务目标、decision_id 和拒绝其他模式的具体原因构造合法与非法样本。Schema 解析成功后继续检查权限、版本与领域不变量。

故障测试注入从流行框架反推需求和单步任务使用多 Agent，记录依赖是否被调用、状态是否改变、资源是否释放，以及同一身份重试会不会重复执行。

在比较相邻概念前后终止执行进程，可以检查恢复边界。调用前退出允许重新领取；外部动作后退出先查回执；终态写入后只重放交付。

集成测试连接真实协议与隔离存储，检查序列化、约束、并发和超时。需要在线服务时单独记录服务版本、时间、配置与是否具备凭证。

Agent 模式选择手册的回归报告要保留失败类型分布。明确拒绝变成超时、权限错误变成普通空结果，都属于行为回归，即使总通过数没有变化。

性质测试可以补足固定样本。随机改变消息顺序、重复提交、完成顺序或状态版本，断言权限不扩大、终态不倒退、同一身份不产生两次副作用。

离线评测关注固定输入下的质量变化，运行时测试关注控制和恢复。Agent 模式选择手册只有两类证据都存在，才能同时回答“结果是否合格”和“系统是否安全完成”。

## 用同一任务比较不同控制图

Agent 模式选择手册长期运行后，输入 Schema、decision_id 结构和依赖配置可能独立升级。每次执行固定一组版本，旧记录才能被正确读取或迁移。

Agent 模式选择手册的容量主要受概念覆盖、交叉链接、术语一致性和版本维护影响。并发可能缩短单次等待，也会同时占用连接、配额、内存和下游吞吐，容量要沿调用链逐层核算。

候选版本在固定样本上比较正确性、错误类型、延迟和资源消耗。从流行框架反推需求等安全红线回归时直接停止发布，不能用平均质量抵消。

从流行框架反推需求的降级路径在发布前写好：减少非关键增强、返回已经确认的结果，或明确暂时无法确认。缺失事实不能交给模型补写。

Agent 模式选择手册的运行手册从 request_id 定位定义、输入、状态所有者、决策者、输出和适用限制，再决定重试、补偿、取消或回滚，无需先展开完整敏感内容。

数据保留按证据用途分级。聚合字段可以保留更久，原始输入和大结果设置短期限、访问控制与删除通道。

Agent 模式选择手册先在单进程实现状态、超时、错误和测试；只有恢复与容量证据提出要求时，再增加队列、Lease、分布式缓存或工作流引擎。

Agent 模式选择手册的监控阈值要对应可执行动作。概念覆盖、交叉链接、术语一致性和版本维护中的某项接近上限时，系统可以限流、排队、缩小候选或切换保守路径；只发送告警不会保护正在运行的任务。

回滚要覆盖代码之外的状态。Agent 模式选择手册若改变 Schema、缓存键或持久化记录，旧版本是否还能读取新写入数据必须提前验证；无法双向兼容时采用候选版本隔离。

## 模式升级和退回的触发条件

采用 Agent 模式选择手册前先画最小控制图。固定函数已经能完成任务时，新增模型决策和跨进程状态只会扩大测试与运维范围。

Agent 模式选择手册与确定性工作流的差别落在控制权：谁选择下一步，谁保存 decision_id，谁确认模式选择可信。

ReAct 可以与 Agent 模式选择手册组合。组合之后，外部知识仍需授权，工具调用仍需校验，模型输出仍停留在候选状态。

Agent 模式选择手册适合价值足够、失败可观察、动作可约束且预算可接受的任务。高风险且不可逆的决定需要确定性规则或人工批准。

格式正确但事实错误的模式选择是必要反例。系统若直接进入成功，说明业务验证缺失；保留候选并给出证据问题，才符合边界。

执行期间修改 candidate_pattern 可以检验并发设计。旧动作仍能覆盖新状态，说明版本或 Lease 有缺口，增加 Prompt 规则无法修复竞态。

Agent 模式选择手册增加了状态、调用、恢复责任和故障面。设计记录应明确获得的能力，也列出新增的退出、降级与回滚路径。

演进可以从最小闭环开始：一个调用、一个状态对象、一组明确错误和几条确定性测试。真实 Trace 证明瓶颈后，再加入并发、缓存、队列或更复杂策略。

相邻文章提供的能力只按依赖引入。确定性工作流解决不了当前失败时，不应为了目录完整强行组合；设计保持可替换，后续需求出现再扩展。
