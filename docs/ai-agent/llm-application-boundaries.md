# LLM 应用的能力边界

用户提交一段报销说明，大模型可以整理费用类型，也可以直接决定是否打款。两者都能生成一个看似明确的结果，风险却完全不同：分类结果还能复核，打款会立即产生真实副作用。

本篇先理解 LLM 怎样工作，再用“可验证性”和“错误代价”决定它适合承担什么。学会边界，比学会某个 Prompt 模板更早也更重要。

## LLM 为什么能回答问题

大语言模型根据输入上下文预测接下来更合适的 Token。训练让它学到语言、代码和知识模式，但生成过程并不是从一个实时事实数据库逐条取答案。

同一个问题可能因模型版本、上下文和采样设置得到不同表达。输出流畅也不等于事实正确，模型还可能缺少私有数据、最新状态或精确业务规则。

```mermaid
flowchart LR
  A[用户输入] --> B[上下文与指令]
  B --> C[模型生成候选]
  C --> D[程序校验]
  D --> E[允许展示或执行]
```

## 第一步：先判断任务是否适合概率输出

模型擅长需要语义理解、归纳和表达的任务，例如摘要、分类候选、查询改写和从证据组织答案。结果有多种合理表达，通常也能由人或程序复核。

精确计费、权限裁决、库存扣减、密码校验和数据库约束更适合确定性程序。这里要求同一条件得到可证明的一致结果，错误还可能直接造成损失。

## 第二步：把事实接到外部来源

模型不知道企业当前数据，可以通过检索或工具读取。RAG 给模型提供相关资料，Tool Calling 让模型提出结构化调用，Agent 再根据结果决定下一步。

外部来源没有消除风险：检索可能漏召回，工具返回可能过期，文档也可能包含恶意指令。程序仍要负责权限、参数校验、超时和输出验证。

## 第三步：按错误代价选择控制方式

| 任务 | 模型角色 | 程序控制 |
| --- | --- | --- |
| 改写文章 | 直接生成候选 | 长度、敏感信息和人工审阅 |
| 知识问答 | 基于证据组织答案 | 权限、检索范围、引用验证 |
| 工单分类 | 提议分类 | 枚举校验、低置信度人工处理 |
| 退款判断 | 提取原因与风险 | 规则计算、审批和幂等执行 |
| 删除数据 | 解释用户意图 | 身份、授权、确认与审计 |

越接近不可逆副作用，模型越适合提供建议，确定性系统和人越需要保留最终控制。

## 正常结果和失败结果

正常设计让模型把报销说明整理成结构化候选，再由程序校验字段、读取政策和计算额度。证据不足时进入人工复核。

失败设计让模型根据自然语言直接返回“approved”，应用不检查来源就打款。一次提示注入、误解或过期规则都会变成真实操作。

## 用四个问题完成架构判断

1. 输出是否存在唯一正确值？
2. 结果能否由规则、数据或人复核？
3. 错误会造成什么副作用，能否恢复？
4. 需要的事实是否在当前授权上下文中？

如果任务路径固定、规则明确，普通程序通常更简单。只有下一步会随观察结果变化时，才继续考虑 Agent。

下一篇用一次资料问答走完 Agent 生命周期。

## 做一次任务边界评审

学习这部分最有效的方法，是拿手头的一个需求填写“任务边界卡”。假设需求是“读取一封客户邮件，判断是否退款”。先不要讨论模型选型，把动作拆开：提取订单号、总结诉求、读取订单状态、计算退款资格、执行退款。前两项允许存在措辞差异，适合让模型提供候选；读取状态应由工具完成；资格计算来自确定性规则；真正退款还涉及身份、幂等和审计。

| 待评审问题 | 需要记录的内容 |
| --- | --- |
| 输入从哪里来 | 用户输入、数据库、文件，还是第三方系统 |
| 正确结果能否证明 | 能用规则校验、与证据比对，还是只能人工判断 |
| 错误代价 | 只是文案不佳，还是会泄露数据、扣款或删除资源 |
| 模型需要什么事实 | 事实的版本、权限范围和更新时间 |
| 谁拥有最终决定权 | 模型、确定性程序，还是经过授权的人 |

填写后再决定实现形式。纯文本整理可以直接调用模型；基于资料回答适合 RAG；会根据观察改变步骤的开放任务才考虑 Agent。若最关键的一列“如何验证”仍为空，继续增加 Prompt 通常解决不了问题，应先补数据来源或人工复核。

把这张卡迁移到工作中时，评审的产物不是一句“可以上 AI”，而是一条边界清楚的执行链：模型负责哪些候选，程序校验哪些字段，副作用由谁确认，失败后返回什么。后续模型或框架变化时，这些边界仍然有效。
