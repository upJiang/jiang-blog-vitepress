# 推理过程应该保存什么，不应该依赖什么

模型完成复杂任务时可能进行内部推理，但应用不应该把隐藏思维过程当作数据库记录、审计证据或安全依据。工程上需要保存的是可验证的输入、结构化决策、动作、证据和结果。

## 内部推理与可审计记录不是一回事

内部推理服务模型生成，具体形式可能不公开也不稳定。审计记录服务系统恢复与责任判断，需要字段明确、来源可查、版本固定。要求模型输出一长段“思考过程”，不会自动得到真实的因果记录。

运行时可以保存 `selected_tool`、`reason_code`、`evidence_ids` 和 `stop_reason`，这些字段能被程序验证。

## 对用户解释依据，不展示隐式思维

用户需要知道答案使用了哪些事实、适用范围和不确定性。可以返回简洁的结论依据和引用，不必展示模型内部逐 Token 推理。

例如“根据当前发布规则的第 3 节，远程访问需要设备登记”是可核对解释；“我先想到 A，又感觉 B”既不可验证，也可能暴露不应公开的信息。

## 复杂任务用结构化中间产物

规划任务保存 SearchPlan，检索保存 Evidence，回答保存 Claim 与引用，工具执行保存 Command 和 Result。每个对象都有 Schema 与所有者，模型只填写允许的候选字段。

结构化中间产物也可能错误，因此仍需校验。它的价值是错误能定位，而不是宣称模型已经“可解释”。

## 置信度不能由模型自报决定

模型给自己的答案打 0.9 分没有校准依据。可用信号来自证据覆盖、来源冲突、验证器问题、检索排名和历史评测。系统可以据此升级模型、补搜或拒答。

涉及权限或安全的决定必须由确定性策略执行，不能因为模型说“我很确定”而放宽。

## 什么时候需要分步接口

当任务可以拆成可验证阶段时，分步有用，例如先生成计划、再执行、最后验证。简单分类和抽取不必强制长推理，额外文字会增加延迟与出错面。

后续的 Tree of Thoughts 会并行搜索多个候选，但它保存的仍是候选状态和评分，不是依赖公开隐式思维。
