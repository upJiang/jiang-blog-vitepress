# 推理过程的使用边界与审计记录

订单金额是 120 元，活动规则写明免邮门槛为 99 元。系统回答“本单免邮”，结论可以通过两个输入和一次比较验证。若模型同时生成一段很长的推导，却在中间把门槛写成 89 元，解释越流畅，越容易让读者忽略错误前提。

**Chain of Thought（思维链）** 通常指模型为多步任务进行的中间推理。工程系统不应把一段自由文本思维链当作事实证据、权限依据或审计日志。可交付解释要重新建立在已验证前提上，审计记录要保存程序真正执行过的动作与版本。

## 同一次请求会产生四类不同记录

| 产物 | 主要用途 | 可信来源 | 是否适合作为业务接口 |
| --- | --- | --- | --- |
| 模型内部推理 | 帮助模型生成候选 | 模型运行过程 | 否 |
| 公开解释 | 帮用户理解结论 | 已验证事实与计算步骤 | 可以，需验证 |
| Runtime Trace | 还原执行过程 | 程序事件、工具回执、状态迁移 | 是 |
| 决策记录 | 审计关键结论 | 策略版本、Evidence、动作与终态 | 是 |

四类产物可能谈论同一个问题，职责不同。内部推理不保证可获得，也不应成为应用依赖的字段。公开解释是模型输出的一部分，仍可能写错。Trace 记录系统做了什么，决策记录说明使用了哪些已验证输入和规则。

把完整 Prompt 和模型推理写进日志，看起来信息丰富，实际会复制用户数据、检索正文和敏感规则，还缺少稳定结构。排查时真正需要的是 request ID、模型调用、工具参数摘要、Evidence 版本、验证问题和停止原因。
## 显式步骤不会自动提高正确性

“请一步一步思考”有时能改善多步任务表现，也可能得到结构完整的错误链。以下情况尤其常见：

1. 第一个事实前提已经错误，后续推导保持内部一致。
2. 模型省略关键分支，却把剩余步骤写得很详细。
3. 计算中间值出错，结论继续沿用。
4. 解释在答案生成后补写，与模型实际生成路径不一致。
5. 逻辑连接词很多，论证仍然循环或缺少证据。

步骤数量、`because` 出现次数和解释长度不能当置信度。置信度如果没有针对任务结果做校准，只能表示模型或启发式的自我判断。

需要精确计算时使用计算器、代码执行或领域引擎；需要事实时使用受限检索；需要权限时查询认证和策略。推理负责组合这些观察，不替代它们。
## 内部推理为什么不该成为稳定协议

应用一旦解析模型自由文本中的“步骤 3”来决定工具调用，就把控制流绑定到了易变措辞。模型升级、语言变化或一次格式偏差都可能破坏解析。

工具调用应通过结构化动作候选进入 Runtime，公开解释通过单独 Schema 生成，状态转换由程序事件记录。模型可以在内部进行复杂计算，对外只需提供合同要求的结果。

有些模型接口会报告 Reasoning Token 用量，有些会返回摘要或受控解释。可用字段和语义取决于具体接口与版本。应用不能假设总能读取完整内部过程，也不能从 Token 数量推断推理质量。

这并不妨碍系统给用户解释。解释应从可公开、可验证的材料重新构建，例如“订单金额 120 元，大于活动版本 v7 的 99 元门槛，因此满足免邮条件”。这段话足以核对结论，不需要展示模型所有隐式联想。
## 公开解释可以做成可验证步骤

对于计算、规则判断和证据综合，可以定义有限的 PublicStep：

```text
PublicStep {
  step_id
  kind: given | calculation | conclusion
  statement
  premise_ids
  evidence_ids
}
```

`given` 必须绑定 Evidence。`calculation` 引用已经出现的前提，不能引用未来步骤。`conclusion` 从前面步骤得出，并成为最后一个节点。

免邮案例可以表示为：

```json
[
  {
    "step_id": "s1",
    "kind": "given",
    "statement": "订单金额为 120 元",
    "evidence_ids": ["order-total:v3"]
  },
  {
    "step_id": "s2",
    "kind": "given",
    "statement": "活动版本 v7 的免邮门槛为 99 元",
    "evidence_ids": ["shipping-policy:v7"]
  },
  {
    "step_id": "s3",
    "kind": "calculation",
    "statement": "120 大于等于 99",
    "premise_ids": ["s1", "s2"]
  },
  {
    "step_id": "s4",
    "kind": "conclusion",
    "statement": "本单满足免邮金额条件",
    "premise_ids": ["s3"]
  }
]
```

这里仍要留意措辞。“满足免邮金额条件”比“订单一定免邮”更准确，因为地区、商品类型或促销叠加可能还有其他条件。公开解释的粒度必须与已验证前提一致。

步骤 Schema 能检查引用完整性和顺序，无法独自证明 `120 >= 99` 的计算正确。计算步骤应交给确定性执行器验证，事实步骤回查当前 Evidence，领域结论再经过业务规则检查。
## Runtime Trace 记录真实动作

Agent 在回答前执行了查询理解、检索、重排、模型生成和验证。Trace 可以记录：

```text
request_id
turn_id
policy_version
release_id
stage_name
model_call_id
tool_call_id
parameter_digest
evidence_ids
validation_issue_codes
state_revision
stop_reason
duration_ms
usage
```

Trace 的事件来自程序边界，不能由模型补写“我调用了搜索”。工具适配器成功返回只说明调用完成，业务结果还要保存状态和回执。模型声称“已更新配置”而 Trace 没有对应工具成功事件时，系统必须按未执行处理。

参数摘要用于关联和去重，敏感参数存入受控审计存储或只保存哈希。完整 Prompt、文档正文和凭证不进入 Metric 标签。需要排查内容时，通过 Evidence ID 和访问控制读取原记录。

Trace 适合回答“系统做了什么、何时做、在哪一步失败”。它不需要解释模型每个词为什么生成，也不应伪装成业务事实证明。
## 决策记录让审计关注关键输入

高风险结论或动作可以单独生成 DecisionRecord：

```text
DecisionRecord {
  request_id
  input_digest
  action_names
  evidence_refs
  policy_version
  decision_summary
  final_answer
  stop_reason
}
```

`decision_summary` 用受控模板描述采用的规则和结果，例如“根据活动 v7 的门槛与订单快照 v3，金额条件通过”。它不复述自由文本内部推理。

输入保存摘要或内容哈希，原始内容留在按保留策略管理的存储中。EvidenceRef 同时保存 ID 与版本，否则后续文档更新后无法还原当时依据。

工具审批还要记录审批人、动作参数哈希和资源版本。审批结果属于程序事实，不能只保存在一段助手消息里。

## 哪些任务需要公开步骤

规则判断、费用计算、配置差异和带引用的因果解释适合提供简短步骤，因为前提和运算可核对。简单事实查询通常直接给结论和引用即可，强制分五步只会增加噪声。

开放式创作没有唯一推导链，展示步骤可能限制输出，也缺少客观验证标准。高风险医疗、法律和金融场景不能因为解释详细就自动可信，还需要领域系统、专业审核和清楚的适用范围。

编码 Agent 的可靠解释是“修改了哪些文件、运行了哪些测试、结果是什么”。一段声称自己全面考虑过边界的思维文本，无法替代代码差异与测试证据。
## 推理型模型也要受运行时控制

模型内部推理更强或推理预算更高，只改变候选生成能力。身份、Scope、工具参数、审批、Deadline 和副作用幂等仍由 Runtime 管理。

模型可以提出“查询订单状态”的动作，程序从当前身份补入用户范围；模型可以生成比较结论，验证器检查 Claim 对应的 Evidence；模型可以建议继续探索，循环上限决定是否真的继续。

更长推理还会增加延迟与成本。任务 Router 应按复杂度和风险决定是否使用，模型 Router 再在能力、SLO 和预算内选型。不要给所有请求固定最高推理强度，也不要把推理 Token 当作质量 KPI。
## 评测要检查结果和记录是否一致

推理相关 Eval 可以覆盖：

| 场景 | 关键断言 |
| --- | --- |
| 前提有当前 Evidence | PublicStep 通过来源检查 |
| 前提引用未知 Evidence | 公开解释被拒绝 |
| 步骤引用未来节点 | 顺序验证失败 |
| 计算结果错误 | 确定性执行器发现不一致 |
| 模型声称工具已执行 | Trace 无回执时不得交付为成功 |
| 文档版本更新 | 决策记录仍指向当时版本 |
| 用户正文含敏感数据 | 普通日志只保存摘要 |
| 解释很长但 Claim 无来源 | 事实验证仍失败 |
| 简单问题 | 不强制生成冗长步骤 |
| 模型或 Prompt 升级 | 稳定合同仍可解析和回放 |

线上观察公开解释验证失败率、工具声称与 Trace 不一致、各模式成本和用户是否展开解释。完整模型输入与输出按隐私策略受控保存，不能为了调试默认永久留存。

可解释性落地后，应能回答三件具体的事：结论用了哪些可见事实，程序实际执行了哪些动作，最终由哪条规则和哪个版本裁决。模型内部如何组织 Token 不需要成为第四份业务真相。
