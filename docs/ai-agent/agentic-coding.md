# 编码 Agent 怎样从仓库证据走到验证结果

**Agentic Coding** 把编码任务拆成可审查的控制流：读取仓库规则，确认工作区状态，定位最小修改面，提交候选差异，运行测试和构建，再把证据交给人工。`task`、`repo instructions`、`file ownership`、`diff`、`test result` 和 `residual risk` 各自保存不同事实，不能用模型的一句“已完成”代替。

本文沿一次构建失败修复展开，重点看修改范围、用户已有差异、测试失败和交付证据。未读约束、覆盖用户差异、测试命令错误、只修单个用例特判和构建失败仍宣称完成，分别对应输入、写入、验证和交付边界。

::: info 贯穿示例

贯穿示例是修复一次构建失败：Agent 只能修改任务列出的模块，必须保留用户已有差异，测试失败时交付失败证据和未完成项，不能扩大范围升级全部依赖。

:::

## 编码任务为什么需要仓库级承载层

未读约束会破坏 task 与受控动作之间的对应关系，排查时先保留原始输入摘要和发生阶段，再判断是否允许重试。

修改无关文件影响 repo instructions 或下游解释，不能和未读约束共用“重新调用一次模型”的处理方式。

## 任务、规则、所有权与写入权限

Agentic Coding 的 Harness 持有工作区、工具和权限，模型只能根据观察提出动作候选。因此 task 与 repo instructions 要有唯一写入方，其他组件只能通过版本化命令申请修改。

IDE 助手与编码 Agent 解决的问题相邻，但控制权不同，比较时要看谁选择检查权限、谁保存 task、谁确认受控动作。

代码生成可以参与同一请求，却不能替代编码 Agent；组合后仍要单独检查环境观察的可信来源和未读约束的终止规则。

编码 Agent 使用的身份、范围和版本来自可信运行时，用户目标可以表达意图，但不能提升权限或改写活动 Release。

修改无关文件发生时，错误回到 repo instructions 的所有者处理，上游缺输入、当前组件违反不变量和下游不可用分别形成不同终态。

编码 Agent 的确定性边界位于 task 写入之前。模型在 Agentic Coding 中只提交候选值，程序仍要从认证、版本和策略快照补入可信字段。

编码 Agent 内部可以使用更细的临时对象，跨边界只暴露稳定协议。替换 IDE 助手时，调用方不需要理解内部缓存和 SDK 响应。

## 快照、差异和测试结果怎样成为状态

编码 Agent 的输入合同至少列出用户目标、环境观察和能力目录，每项都注明来源、是否必需、允许的缺省值，以及缺失后是在入口拒绝还是进入降级路径。

编码 Agent 要把任务目标、仓库规则、文件所有权和工作区修订号分开记录。目标定义完成条件，规则限制可做的修改，所有权避免并发覆盖，修订号用于测试和合并前的乐观检查；自然语言摘要不能替代这些字段。

并发分支按稳定身份合并 file ownership，完成顺序只反映耗时，不能决定结果属于哪个请求，更不能让迟到的旧状态覆盖新修订。

Agentic Coding 的对外结果要分别表达可交付内容、缺口、取消和未知状态，调用方不必解析错误文案。

repo instructions 参与乐观并发检查；处理开始后若版本变化，旧候选只保留作审计，不能继续写入 task。

观察版本、动作参数、审批、文件差异、进程结果、截图和测试输出组成编码 Agent 的最小追踪材料，日志只保存稳定 ID、版本和错误类，完整 Prompt、文档正文与凭证不进入指标标签。

契约还需要描述新鲜度。repo instructions 对应的数据发生变化后，旧缓存、旧候选和未完成任务怎样失效，应由版本或时间规则直接判断，不能依赖模型注意到矛盾。

删除和撤回也属于数据生命周期。编码 Agent 引用的原始对象被移除时，稳定 ID 可以保留审计关系，正文与派生结果则按策略失效，避免继续向用户展示过期内容。

::: warning 编码 Agent 的可信边界

受控动作通过结构校验后仍是候选。编码 Agent 使用的身份、权限、知识版本与业务事实由应用从可信服务读取，核对完成后才能执行或交付。

:::

## 从定位问题到交付补丁的执行链

编码 Agent 的一次交付要留下从仓库约束到测试结果的证据链：先记录任务和规则版本，再提交最小差异，运行相关测试和构建，最后列出未完成项。若工作区版本在验证前变化，Agent 应重新检查差异，而不是沿用旧结论。

观察环境接收用户目标并建立 task，入口校验未通过就地结束，后续模型、检索器或工具调用次数保持为零。

检查权限读取 repo instructions 并执行主题逻辑，参数由应用组装，外部返回先保存为可审查差异，尚未获得修改领域状态的资格。

执行并重新观察检查结构、范围、版本和主题不变量；受控动作缺少来源、落在旧版本或越过权限时，task 停在 rejected 或 failed。

实现可以使用函数、Graph、Middleware 或 Workflow，task 的所有权和未读约束的停止规则不会随框架改变。

部分成功需要在步骤边界处理。

## 沿一次构建失败推演最小修复

沿“编码 Agent 场景：编码助手需要读取仓库、修改一个文件并运行测试，但不能访问工作区之外的路径，也不能在测试失败时宣称完成”推演编码 Agent：入口创建 request_id，读取可信身份，把用户目标和当前版本写入初始状态。

观察环境生成 task 与输入摘要；若环境观察缺失，请求返回 rejected，并指出缺少哪项材料，不继续消耗模型或外部服务配额。

检查权限按“编码 Agent 先读取仓库约束和测试，再定位最小修改面；编辑后运行相关测试、静态检查和构建，最终交付差异、证据与未完成项”推进，每次依赖调用保存 call_id、参数摘要、开始时间与状态版本，以便判断超时前是否已经产生结果。

运行确定性验证写入终态；客户端断开只影响交付通道，重新连接时读取已经保存的 task 或事件游标，不重跑核心逻辑。

故障注入选择覆盖用户差异，程序保留原候选和错误位置，只重做失败边界，不能从入口复制整个任务并产生第二份状态。

推演结束后用 request_id 关联 task、受控动作与终止原因，测试据此排除并发请求串线，并确认失败路径没有遗留未关闭资源。

编码 Agent 在输入拒绝时不调用依赖，正常路径按 5 个阶段推进，有限修复只重做失败边界。调用次数是控制流断言，不是性能宣传。

编码 Agent 的最终记录用 request_id 关联 task、受控动作和失败问题，测试据此证明结果来自本次执行，没有混入并发请求。

## 差异、测试与人工审查怎样闭环

编码 Agent 正常完成时，task、repo instructions 和受控动作指向同一次执行，重复读取返回同一终态，未完成分支已经取消或有明确所有者。

观察版本、动作参数、审批、文件差异、进程结果、截图和测试输出用于还原编码 Agent 的处理过程，可以按阶段和版本聚合；敏感正文留在受控存储中，不复制到日志与指标。

依赖返回成功状态只证明传输完成。编码 Agent 还要检查受控动作是否满足业务范围、质量阈值和当前版本，明确拒绝也可能是正确终态。

task 的状态迁移必须单调：完成不能退回运行中，取消不能被迟到结果覆盖，失败重试也不能绕过入口已经固定的权限。

编码 Agent 的成功证据最终要同时回答输入是什么、执行了哪些步骤、交付了什么以及为什么停止；任一项缺失都应留在未确认状态。

编码 Agent 把业务验收与服务健康分开。依赖对 Agentic Coding 返回 200 只说明传输完成，内容仍要满足当前范围和质量条件。

编码 Agent 的观测指标按阶段和版本聚合。评估 Agentic Coding 时，把错误、空结果、拒绝、恢复和资源消耗分开统计，避免一个成功率掩盖不同故障。

## 用户差异、命令失败与未知结果

编码 Agent 的失败证据有明确顺序：读不到文件先查路径和权限，修改不符合预期先看差异，测试未执行先查命令和环境，测试失败则保留退出码与日志，审查未完成时停止交付。重新生成补丁不是对所有层都有效的修复。

遇到未读约束时，先记录发生阶段、错误类别和责任对象。编码 Agent 保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

遇到修改无关文件时，先记录发生阶段、错误类别和责任对象。编码 Agent 保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

编码 Agent 发现覆盖用户差异后重新读取权威状态，旧候选可以保留作审计，却不能覆盖新版本；前后状态无法兼容时，当前尝试以 conflict 结束。

遇到测试命令错误时，先记录发生阶段、错误类别和责任对象。编码 Agent 保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

遇到只修单个用例特判时，先记录发生阶段、错误类别和责任对象。编码 Agent 保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

遇到构建失败仍宣称完成时，先记录发生阶段、错误类别和责任对象。编码 Agent 保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

编码 Agent 将终态、可重试性和资源清理结果写入记录；后台扫描器根据 task 判断任务是在运行、等待恢复还是已失败。

编码 Agent 执行前固定 Deadline、动作上限、重复签名、无进展阈值、预算和取消信号；任一条件触发，检查权限停止创建新工作。

编码 Agent 把重试时间和次数计入总预算。Agentic Coding 每次重试先扣减剩余额度，达到上限就保留原始错误。

编码 Agent 的清理动作设计成幂等操作；仍被活动任务或 Lease 引用的资源拒绝删除。

## 在隔离仓库中回放编码任务

使用隔离工作区和假环境重放观察动作循环，断言越界动作被拒绝、写操作需要审批、验证失败不会标记完成；测试显式给出用户目标、初始 task、预期受控动作和终止原因，不能只断言返回值非空。

编码 Agent 的单元测试用 Fake Adapter 固定受控动作与错误，断言参数、调用顺序、状态修订和清理动作，这些结果只证明本地控制逻辑。

契约测试围绕用户目标、task 和可审查差异构造合法与非法样本，Schema 解析成功后继续检查权限、版本与领域不变量。

故障测试注入未读约束和修改无关文件，记录检查权限是否被调用、task 是否改变、资源是否释放，以及同一身份重试会不会重复执行。

编码 Agent 的集成测试连接真实协议与隔离存储，检查序列化、约束、并发和超时；需要在线服务时另行记录服务版本、时间、配置与凭证条件。

编码 Agent 的回归报告要保留失败类型分布。在 Agentic Coding 的回归中，拒绝、超时、权限错误和空结果必须保持各自类型，状态变化本身就是行为契约。

编码 Agent 的性质测试随机改变 task 顺序、重复提交、完成顺序或状态版本，断言权限不扩大、终态不倒退、同一身份不产生两次副作用。

Agentic Coding 的离线评测关注质量变化，运行时测试关注控制和恢复，两类证据都齐全才可交付。编码 Agent 只有两类证据都存在，才能同时回答“结果是否合格”和“系统是否安全完成”。

## 编码 Agent 的容量、版本和交付治理

编码 Agent 需要冻结仓库快照、用户差异、命令合同和制品 Schema。规则升级后，旧任务仍按原快照回放，新的写入范围不能覆盖未参与本次任务的改动。

编码 Agent 的容量主要受观察体积、工具调用、后台进程、浏览器会话、文件差异和循环步数影响，并发可能缩短单次等待，也会占用连接、配额、内存和下游吞吐，必须沿观察环境、提出动作、检查权限、执行并重新观察、运行确定性验证逐层核算。

编码 Agent 的候选版本在固定样本上比较正确性、错误类型、延迟和资源消耗，未读约束等安全红线回归时直接停止发布，不能用平均质量抵消。

未读约束的降级路径在发布前写好，可以减少非关键增强、返回已经确认的受控动作，或明确暂时无法确认，缺失事实不能交给模型补写。

排查代码改动时，先用 `request_id` 找仓库快照、动作参数、命令回执、测试输出和候选制品摘要，再决定回滚文件、重跑测试还是保留人工差异。模型的解释只能作为线索。

编码 Agent 的数据按证据用途分级保留，聚合字段可以留得更久，用户目标和大体积受控动作设置短期限、访问控制与删除通道。

编码 Agent 先在单进程实现 task、超时、错误和测试，只有恢复与容量证据提出要求时，再增加队列、Lease、分布式缓存或工作流引擎。

编码 Agent 的监控阈值要对应可执行动作。Agentic Coding 的分支、依赖、上下文和预算接近上限时，应限流或缩小候选；告警本身不会停止正在运行的任务。

回滚要覆盖代码之外的状态。编码 Agent 若改变 Schema、缓存键或持久化记录，旧版本是否还能读取新写入数据必须提前验证；无法双向兼容时采用候选版本隔离。

## 编码 Agent 与 IDE 助手、代码生成的边界

采用编码 Agent 前先画出用户目标到受控动作的最小控制图；固定函数已经能完成任务时，新增模型决策和跨进程 task 只会扩大测试与运维范围。

IDE 助手通常把建议交给开发者确认，编码 Agent 可能直接修改工作区并运行命令，因此必须把写入范围、审批、回执和验证交给程序保存。Agent 不能替用户确认制品可发布。

代码生成可以与编码 Agent 组合，但外部知识仍需授权，工具调用仍需校验，模型产生的受控动作仍停留在候选状态。

编码 Agent 适合价值足够、未读约束可观察且预算可接受的任务，高风险、不可逆的决定需要确定性规则或人工批准。

执行期间修改 repo instructions 可以检验并发设计，旧动作若仍能覆盖 task，说明版本或 Lease 有缺口，增加 Prompt 规则无法修复这类竞态。

编码 Agent 增加了 task、依赖调用、恢复责任和故障面，设计记录既要说明获得的能力，也要列出新增的退出、降级与回滚路径。

编码 Agent 的交付物不只是补丁。它还应返回读取过的约束、修改文件、测试命令、未运行的检查和仍待人工判断的风险。若测试失败，先保存原始输出和工作目录，再决定修复、回滚或停止；不能为了得到绿色结果删除失败用例，也不能把未执行的命令写成已验证。

一个可复核的编码循环从仓库边界开始：先读取贡献规则、依赖锁文件和目标模块的测试，再建立修改前快照；实现阶段只允许写入任务契约列出的文件；验证阶段按最小测试、类型检查、构建和差异审查逐层推进。发现测试与需求冲突时，Agent 应返回冲突证据并停止，不应自行扩大范围去改动无关模块。交付报告把已执行与未执行的命令分开，后续开发者才能准确判断剩余风险。

## 把一次改动拆成可回放的证据链

用户提出“修复构建失败”时，编码 Agent 先记录仓库根目录、当前分支、工作区差异和命令入口。读取构建日志后，把错误归类为依赖解析、类型错误、运行时配置或测试断言，再只向对应模块发送读取任务。每次工具调用都带文件范围和只读或可写权限，返回内容保存为摘要和行号，避免下一轮凭记忆猜测。

实现阶段先写最小补丁，再运行与错误直接相关的测试。测试通过后执行类型检查和构建，若新失败来自已有差异，报告必须区分“任务新增”与“基线已有”。Agent 不应因为一条命令失败就自动删除锁文件、升级全部依赖或重写测试。涉及数据库迁移、网络调用或生产配置时，先停在计划状态，等待明确的变更范围。

补丁提交前要检查三类回归。行为回归确认正常输入、空输入和错误输入的输出仍符合契约；边界回归确认权限、超时、取消和重复执行不产生副作用；维护性回归确认新增接口有测试、错误信息保留原始原因、文档命令与实际脚本一致。只有这些证据齐全，编码 Agent 才能把候选补丁交给人工审查。

涉及依赖升级时还要保存锁文件差异和许可证变化。构建环境、操作系统和凭证权限会改变结果，报告中应写明实际环境。未能复现的错误只能标记为待确认，不能用一次本地成功覆盖线上风险。

对外提交前还要确认补丁没有把调试输出、临时文件或访问令牌写入仓库。安全扫描和差异审查是编码 Agent 的交付步骤，不是发布后再补的清理工作。

代码审查还要确认用户已有差异没有被回退。Agent 只能说明自己修改的范围，来源不明的变更保留并标注风险。

当任务需要修改多个仓库时，分别建立快照和验证记录，不能用一个“全部通过”覆盖其中一个仓库没有运行测试的事实。

## 编码循环的评测、回归与交付自测

用“一个需要修改代码并运行测试的任务”回放时，Harness 先固定观察版本、工作区和执行预算。仓库快照、写入范围、命令回执和候选制品由事件和 Checkpoint 保存，模型只能提出动作候选，策略层决定候选能否进入执行器。

正常路径是观察、候选、授权、动作、再观察和确定性验证。每次动作都带 `attempt_id`，输出包含退出码、差异或截图摘要。测试失败、工作区有用户差异或制品与源码不一致要保留原始回执，不能让模型用一句“已完成”覆盖。

测试故意让观察过期、工具未知、命令超时和渠道断开。在“编码任务”中，前两种在执行前拒绝，后两种要根据是否产生副作用决定重试或进入未知状态。恢复从最后一个 Checkpoint 开始，不重放已经确认的写动作。

“编码任务”的离线 Fake Adapter 只验证接口和状态迁移，真实浏览器、终端或供应商还要做权限、资源和网络测试。没有授权就只交付差异和证据。

“编码任务”的取舍要写清：更大的观察窗口能减少重新读取，却会增加 Token 和敏感内容暴露；更长的自动循环能覆盖更多步骤，却提高失控和回滚成本。

“编码任务”的回放报告保存策略版本、动作数量、失败阶段和清理结果，平台升级后再用同一组事件比较，才能判断变化来自实现还是环境。

## 编码任务的边界案例

在“编码任务”中，入口收到的资料可能不完整，程序先保存缺口和当前版本，不能让模型用常识填入 仓库快照、写入范围、命令回执和候选制品。“编码任务”的输入后来补齐时，新的执行沿同一个任务 ID 继续；已经结束的失败记录不被覆盖。

测试失败要保留失败命令和仓库快照，工作区已有用户差异要记录共同祖先，制品与源码不一致要比较修订和摘要。未运行测试、命令失败、测试通过但没有制品、制品来源尚未确认分别阻止交付或进入人工复核。

“编码任务”的正常输出先经过范围、版本和权限检查，再进入交付或下一个节点。没有授权就只交付差异和证据。“编码任务”的输出只满足结构而没有可验证来源时，状态保持为候选，前端应显示缺口而不是成功标记。

用重复提交、并发完成、取消和进程退出四个样本回归。回归“编码任务”时，检查同一幂等键是否只产生一个有效终态，迟到事件是否被拒绝，临时资源是否释放，重新连接是否能读到同一份事件。

这组检查的结果应带命令、解释器或服务版本、输入摘要和退出码。“编码任务”没有运行证据时，只能写“待验证”；离线替身通过也不能推导真实模型、网络服务或生产权限已经通过。
