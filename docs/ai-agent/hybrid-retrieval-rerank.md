# 精确、全文、向量、结构化检索与重排

“ERR-1042”适合精确匹配，“在家办公如何接入系统”适合语义向量，“哪个角色负责第二级审批”可能来自表格。只使用一种检索通道，会在另一类问题上明显退化。

混合检索的目标不是堆更多算法，而是让不同通道提供候选，再用稳定方式融合、重排和验证。下面用三个查询类型拆开整条链。

## 召回、融合和重排是三个阶段

```mermaid
flowchart LR
  A[查询理解] --> B[多路召回]
  B --> C[候选融合去重]
  C --> D[重排]
  D --> E[权限与证据检查]
  E --> F[上下文预算]
```

**召回**追求不要漏掉相关候选；**融合**把不同列表变成一份候选集；**重排**用更精细的模型或规则把真正相关内容放前面。最后还要检查权限、版本和证据完整性。

## 五类通道分别擅长什么

### 精确与别名

错误码、工单号、产品名和缩写优先精确匹配。系统可以维护受控别名，例如把完整名称与常用简称映射，但别名也需要版本和来源。

### 标题与全文

PostgreSQL 全文检索或搜索引擎倒排索引擅长词项匹配，可使用标题加权、短语和语言分词。它对专有词稳定，也容易解释“为什么命中”。

### 向量

向量通道擅长同义表达和自然语言问题，但可能把主题相近、事实无关的片段排在前面。它是候选召回，不是事实验证。

### 表格

表格可以按表题、列名、行字段建立结构化表示。用户问“哪个角色负责审批”时，命中整张表后还要定位具体行列，不能只返回表格的扁平文字。

### 结构化过滤

日期、版本、状态、类型和知识范围用数据库字段过滤。它们是确定性条件，不应向量化后希望模型“差不多匹配”。

## 查询理解决定启用哪些通道

不是每个问题都启动全部通道。一个轻量路由可以提取：专有标识、可能标题、自然语言查询、表格意图和结构条件。

```text
输入：ERR-1042 在新版客户端如何处理？
精确词：ERR-1042
语义查询：新版客户端 错误处理
版本过滤：当前激活版本
启用：精确 + 全文 + 向量
```

路由结果由模型结构化生成时，程序仍校验版本和权限。模型不能把用户范围改成全局。

## 为什么不能直接比较不同通道分数

全文相关度可能是 12.4，余弦相似度可能是 0.82，业务精确命中可能是布尔值。把它们线性相加需要校准尺度，否则一个通道会因为数值范围占据全部排序。

Reciprocal Rank Fusion（RRF）只使用每个候选在列表中的名次：

```text
score(d) = Σ 1 / (k + rank_i(d))
```

`k` 是平滑常数，`rank_i` 是候选在第 i 个通道的名次。候选在多条列表都靠前时得分更高。

### 手工融合三条列表

```text
全文：[A, B, C]
向量：[B, D, A]
标题：[A, E, B]
```

取教学用 `k=10`：A 得到 `1/11 + 1/13 + 1/11`，B 得到 `1/12 + 1/11 + 1/13`。A 与 B 都因多路出现而领先。生产参数要用评测集选择，这里只演示计算。

融合前按稳定证据 ID 去重，保留各通道名次和命中原因，便于 Trace 和调试。

## 重排为什么放在候选之后

Cross-encoder 或 LLM 重排同时阅读查询和候选文本，判断相关性通常比单独向量更精细，但成本更高。先由便宜通道召回几十条，再重排到少量证据。

重排输入要控制长度，保留标题路径和关键内容。输出应是候选 ID 与分数，不让模型改写原文。重排超时可以回退融合排序，但要记录降级状态。

重排也会出错。评测需要比较“召回是否包含答案”和“重排是否把相关证据提到前 K”，不能把两阶段问题混在一起。

## 证据预算限制最终上下文

Top 20 候选不能全部发给模型。证据选择还要考虑：

- 覆盖用户问题的不同子目标；
- 去掉内容高度重复片段；
- 相同来源不要占满预算；
- 父片段和相邻片段按需展开；
- 表格保持相关行列；
- 总 Token 不超过本轮证据预算。

多目标问题可以先为每个子目标保留最少证据，再按全局相关性补齐。这样不会因为一个强势主题挤掉其他问题。

## 缓存键必须包含权限和版本

检索缓存不能只使用查询文字。至少考虑：

```text
用户可见范围摘要
知识版本
检索策略版本
Embedding/重排模型版本
规范化查询
```

命中缓存后仍可执行一次快速范围校验，支持权限即时撤销。缓存内容只保存证据 ID 和必要排序信息，读取正文时再从当前可见数据获取。

## 降级链怎样保持可解释

| 故障 | 降级 |
| --- | --- |
| 向量服务不可用 | 保留精确、标题与全文检索 |
| 重排超时 | 使用融合名次并标记降级 |
| 全文分词异常 | 保留精确和向量，触发索引告警 |
| 某一数据源超时 | 使用已有证据判断覆盖度；不足则明确说明 |
| 所有通道无结果 | 返回证据不足，不用模型常识补齐 |

降级不是永远返回答案。若剩余通道无法支持事实，正确终态就是“当前资料不足”。

## 建立检索评测表

每个问题标注：相关证据、允许范围、问题类型和关键实体。评测至少包含：

- Hit@K：前 K 是否命中任一相关证据；
- Recall@K：相关证据覆盖比例；
- MRR：第一个相关结果的倒数名次；
- 重排提升：相关证据从融合到重排的名次变化；
- ACL 正确性：不可见证据是否始终为零；
- 降级结果：依赖失败时是否保持安全语义。

不要只用五个自己熟悉的问题。查询要覆盖专有名词、同义表达、表格、版本、无结果和越权范围。

## 本文实践结果

手工完成三路候选融合后，再为每个候选记录：证据 ID、来源版本、命中通道、各通道名次、融合分数、重排分数、权限检查和最终选择原因。这张记录就是检索 Trace 的核心。
