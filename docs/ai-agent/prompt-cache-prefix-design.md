# Prompt Cache 的稳定前缀与失效边界

模型请求经常重复系统规则、工具定义、输出 Schema 和一段稳定历史。**Prompt Cache（提示缓存）** 让服务端复用已经处理过的输入前缀，减少重复计算。它缓存的是输入处理结果，模型仍会为当前完整请求生成新输出。

前缀匹配关注请求序列，不会理解两段文字语义相同。JSON 键顺序、空格、工具排列或规则版本变化，都可能让变化点之后的内容失去命中。具体匹配条件、最小长度和有效期以供应商当前文档为准。

## 内容按变化频率排序

一个适合缓存的请求通常从低变化走向高变化：

```text
稳定应用规则
→ 稳定工具与输出 Schema
→ 会话中较稳定的历史
→ 当前问题、检索证据和工具结果
```

规则放到用户输入后面，会导致每轮都在很早位置变化；动态时间戳、随机 ID 和无意义排序也会破坏字节稳定性。当前日期确实影响任务时可以放在动态区域，不要混进共享前缀。

## 稳定序列化比文本微调更重要

工具目录按稳定 ID 排序，Schema 使用确定的键顺序，集合先规范化，换行与编码固定。不要在每次请求中生成不同 UUID 作为规则的一部分，也不要让日志追踪字段进入模型输入。

## 断点对应内容生命周期

部分服务允许显式缓存断点，部分采用自动前缀缓存。显式断点应放在稳定且足够长的区域之后。多个断点可以对应应用级规则、租户级工具和会话级历史，但每层共享范围不同。

用户私有历史不能为了提高命中率放进跨用户共享前缀。缓存实现必须保证隔离，应用也不要自己把私有 Prompt 用宽泛键存进公共缓存。

## 派生请求从已发送对象追加

构造多轮请求时，最好保留上一轮真正发送的消息序列，在尾部追加新内容。重新从数据库渲染整段历史，时间格式、排序和空白可能变化，语义没变也会失去缓存。

这种做法仍要检查规则和权限版本。权限撤回后，不能因为旧前缀可命中就继续发送其中的私有材料。缓存收益服从数据边界。

## 权限变化怎样失效

缓存不传播信任。当前用户范围、租户、知识 Release 或工具权限变化时，上下文装配器重新生成可见材料；即使供应商内部仍有旧前缀，应用也不再提交它。

自己实现 Prompt 缓存时，键至少绑定模型、规则版本、工具目录版本、租户和内容哈希。命中后仍检查当前授权。只用 `conversation_id` 作为键会把版本和权限变化藏起来。

## usage 怎样解释命中

服务端通常通过 usage 细项报告缓存读取 Token。观测需要同时记录总输入、缓存读取、非缓存输入、输出、模型和延迟。命中率可以写成：

```text
cache_ratio = cached_input_tokens / total_input_tokens
```

这个比例只能说明输入复用，不能证明回答质量、事实正确或账单一定按某个比例下降。价格、缓存写入和读取口径由供应商决定，金额计算要绑定当时的价格版本。

## 与其他缓存分工

Prompt Cache 复用模型输入前缀；响应缓存复用完整输出；检索缓存复用候选证据；工具缓存复用外部调用结果。四类缓存的键与安全边界不同。

对时效性问题使用响应缓存风险很高，而稳定前缀仍可复用。检索缓存命中后需要重新授权，Prompt Cache 命中也不能让旧证据绕过当前 Release。

## 失效从第一个变化点排查

命中突然下降时，对两次请求进行结构化对比，找出第一个不同字段。常见原因包括规则时间戳、工具排序、Schema 生成器升级、历史重新渲染和模型路由变化。

不要把完整 Prompt 打进日志。记录各段哈希、长度、版本和首个差异路径即可；需要查看原文时通过受控调试工具，并清理临时资料。

## 回归测试分三部分

确定性测试同一输入多次渲染得到相同字节与哈希。失效测试改变规则、工具、租户和权限，断言对应前缀版本变化。在线小样本读取真实 usage，确认供应商确实报告命中。

质量回归与缓存回归分开。相同请求在有无缓存时应满足相同业务断言，缓存命中不能改变工具权限、证据引用和终态。若为了稳定前缀保留过期材料，成本优化已经越过正确性边界。
