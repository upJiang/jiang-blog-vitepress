# Prompt Cache 的稳定前缀与失效边界

长 Prompt 经常重复携带同一批内容：系统规则、工具定义、输出 Schema、少量示例，以及一段已经确认的会话历史。每次都从头处理这些 Token，会增加输入成本和首 Token 等待时间。**Prompt Cache**让服务端复用已经处理过的输入前缀，当前请求只继续处理没有命中的后半段。

这里的“前缀”是关键。缓存不会判断两段说明表达的意思是否相同，也不会因为两个 JSON 对象解析后相等就认定可以复用。位于可缓存边界之前的内容、顺序和相关请求设置必须满足服务方的精确匹配条件。前面越早出现变化，后面越长的内容失去复用。

::: info Prompt Cache 缓存的不是答案

命中缓存后，模型仍会根据本次完整输入重新生成输出。相同前缀不保证回答相同，也不能证明答案正确。`cached_tokens` 只说明多少输入 Token 从缓存读取。

:::

缓存设计因此属于 Request Builder，而不是回答质量层。上下文编译器决定哪些内容稳定、它们以什么顺序出现、断点放在哪里；模型适配器发送请求并读取 Usage；业务验证仍检查证据、权限和最终结果。

## 精确前缀匹配意味着什么

可以把一次模型输入写成 `P + V`。`P` 是可复用前缀，包含稳定规则和工具；`V` 是本次变化的尾部，包含用户问题、时间、请求身份和当前检索证据。第二个请求若仍以同一个 `P` 开头，服务端可能读取缓存；`P` 中任何一个字段变化，都可能把命中位置截断到变化发生之前。

变化不一定来自正文。工具数组换了顺序、Structured Output Schema 多了一个可选字段、图片 detail 改变、开发者消息被重新分段，都会影响渲染后的模型输入。把 `{"a":1,"b":2}` 换成 `{"b":2,"a":1}`，应用看到的是同一个对象，序列化字节和 Token 序列却可能不同。

同样的业务状态还可能因为默认值产生不同请求。一个调用显式发送 `parallel_tool_calls=false`，另一个依赖 SDK 默认；一个字段缺失，另一个字段是 `null`。服务方如何把这些字段纳入缓存契约取决于具体 API，但应用首先要保证自己发出的结构确定，不能让 Map 遍历、随机 ID 或当前时间渗进稳定区。

稳定前缀不是永远不变的前缀。策略发布、工具升级和输出 Schema 变更都应产生新版本。目标是同一个版本在相同输入条件下渲染出相同内容，让失效发生在有意发布时，而不是每个请求都随机变化。

## 按共享范围和变化频率排列内容

设计前缀时，可以先给每块输入标注共享范围与变化频率。范围越广、变化越慢的内容越靠前；只属于单次请求的内容放在断点之后。

| 内容 | 常见共享范围 | 变化频率 | 推荐位置 |
| --- | --- | --- | --- |
| 核心行为规则 | 同一应用版本 | 低 | 前缀最前部 |
| 工具与输出 Schema | 同一能力版本 | 低到中 | 稳定规则之后 |
| 会话已确认历史 | 单个会话 | 持续追加 | 会话断点之前 |
| 用户身份与 Scope | 单次请求或会话 | 可能撤回 | 动态尾部或运行时 |
| 当前问题与证据 | 单次请求 | 高 | 断点之后 |
| 请求 ID、时间戳 | 单次请求 | 每次变化 | Metadata，不进入稳定前缀 |

“动态”是位置属性，不是注释。即使文本前写了 `VOLATILE`，只要它出现在稳定工具定义之前，时间戳变化仍会让后面的工具失去复用。真正有效的处理是移动到断点之后，或者只放进请求 Metadata 和 Trace。

共享范围还决定缓存键。跨用户完全相同的产品规则可以共用一个稳定版本；带用户偏好的指令只适合在该用户或会话范围复用。把用户身份写进一个全局稳定块，会让每个用户拥有不同前缀；为了提高命中而删掉身份隔离也不安全。缓存优化不能改变原有可信边界。

工具定义的排序需要确定。可以按 Namespace 和工具名排序，在发布阶段生成规范化 JSON；运行时只引用已发布版本。若按当前权限临时删除数组元素，工具顺序与内容会频繁变化。前一篇已经把能力发现和执行授权分开，这里继续沿用：目录决定模型看到什么，授权层决定调用能否执行，缓存只要求已选择的前缀保持稳定。

## 隐式断点和显式断点解决不同输入形状

OpenAI 对较早模型提供自动的前缀复用，对 GPT-5.6 及之后的模型增加了可配置断点。当前规则、支持的内容块和计费方式应以 [Prompt Caching 官方文档](https://developers.openai.com/api/docs/guides/prompt-caching) 为准。下面解释的是当前接口形状，不应当写死成跨供应商协议。

**隐式模式**适合持续追加的对话。服务端默认在最新用户消息或 Tool 消息处设置隐式断点。第一轮可以写入“规则 + 用户问题一”，第二轮在其后追加助手回答和用户问题二，旧前缀仍有机会读取，最新位置继续形成新的可复用点。

单次独立请求的形状不同。两次请求只有规则相同，时间戳和用户问题都不同；默认断点若放在最新用户消息之后，整个候选前缀包含动态内容，第二次很可能无法读取第一次的条目。此时在稳定规则末尾放一个显式断点，动态字段全部位于其后，才能让独立请求共用规则前缀。

**显式断点加隐式模式**同时保留稳定前缀和滚动对话的写入机会。它适合规则稳定、会话历史也会连续复用的交互。**显式模式**则关闭隐式断点，只读写应用标记的位置；当尾部每次都变而且不会再次复用时，可以避免为动态后缀持续写缓存。

显式断点标在支持的内容块上，断点包含该块及之前渲染的全部输入。Responses API 不能把断点直接放在顶层 `instructions`，需要把可复用开发者指令放入 `developer` 消息的 `input_text`。当前每次请求最多创建四个新缓存写入；设置更多逻辑区域并不会带来无限断点，应用需要把变化周期接近的内容合并。

## 多个断点怎样按生命周期分配

一条长 Prompt 里可能有不止一种稳定内容。产品规则几周才改一次，工具 Schema 随版本发布，参考材料每天更新，会话历史每轮追加。只在最新消息后放一个断点，意味着四种生命周期被绑在一起；参考材料更新时，原本没有变化的规则和工具也可能重新写入。

多个断点可以把这些区域分开。第一个放在产品规则之后，第二个放在工具定义之后，第三个放在共享参考材料之后。服务端遇到多个可用条目时，可以读取最长的匹配前缀。工具升级后，规则断点仍可能命中；参考材料变化后，规则与工具组成的前缀仍有复用机会。

断点不是越多越好。GPT-5.6 当前每个请求最多写入四个新条目，隐式模式的最新消息会占用一个写入位置。每增加一个断点，都可能产生一次写入成本和新的观测维度。两个区域变化频率相近、共享范围相同，就没有必要拆开。先用真实请求统计变化周期，再决定哪个边界值得占一个位置。

可以把断点规划写成版本表，而不是散落在 Prompt 模板里的标记：

| 区域 | 示例版本 | 失效触发 | 是否需要独立断点 |
| --- | --- | --- | --- |
| 产品规则 | `policy-v3` | 策略发布 | 通常需要 |
| 工具定义 | `tools-v8` | Schema 或顺序变化 | 工具较大时需要 |
| 共享材料 | `handbook-r12` | 材料发布 | 复用频繁时需要 |
| 会话历史 | `conversation-42` | 追加或压缩 | 交给隐式断点或末级显式断点 |

文件与图片也能参与可缓存前缀，但身份相同不够。图片内容、顺序和 detail 设置要保持一致；文件换了内容，即使文件名未改，也应视为新版本。把每次请求生成的临时下载地址塞在断点前，会让实际内容相同却无法匹配，优先使用稳定文件身份或供应商支持的文件引用。

Structured Output Schema 与工具 Schema 类似。字段顺序、描述、枚举和严格模式改变，都可能影响断点前的渲染。业务只改了用户问题，输出 Schema 却由不确定的对象遍历重新排序，缓存指标会像工具升级一样下降。发布阶段生成规范化 Schema，并把版本放入内部追踪，可以快速区分有意失效与构建漂移。

多断点的测试要覆盖部分命中。改变共享材料但保留规则和工具，预期仍能读取较短前缀；改变工具 Schema，预期只能复用规则；改变规则开头，预期整条稳定区都失效。只测“全命中”和“全不命中”，无法证明边界真的放在设计位置。

## GPT-5.6 请求怎样标记稳定规则

下面的请求把产品规则放在 Developer Message 中，并在最后一个 `input_text` 上标记显式断点。用户问题位于断点之后，`mode: "explicit"` 阻止最新用户消息形成额外隐式写入。

```jsonc
{
  "model": "gpt-5.6",
  "prompt_cache_key": "knowledge-agent:policy-v3",
  "prompt_cache_options": {
    "mode": "explicit",
    "ttl": "30m"
  },
  "input": [
    {
      "type": "message",
      "role": "developer",
      "content": [
        {
          "type": "input_text",
          "text": "只使用当前用户可见的证据，缺少证据时明确拒答。",
          "prompt_cache_breakpoint": {
            "mode": "explicit"
          }
        }
      ]
    },
    {
      "type": "message",
      "role": "user",
      "content": [
        {
          "type": "input_text",
          "text": "远程访问申请什么时候生效？"
        }
      ]
    }
  ]
}
```

示例规则很短，只用于展示结构。当前 GPT-5.6 的可缓存前缀至少要有 1,024 Token；生产请求需要规则、工具或共享材料达到实际门槛。总请求超过门槛，不代表断点前的匹配部分也达到门槛，排查时要统计断点之前渲染出的 Token。

`prompt_cache_key`帮助相关请求路由到更可能持有相同前缀的机器。它不会让不同内容变成相同前缀，也不是访问控制键。键值应稳定且低基数，并与真实共享范围相符；把每次生成的 Request ID 当缓存键，等于主动放弃复用。

对于 GPT-5.6，当前官方文档要求设置 `prompt_cache_key` 才能使用更可靠的隐式和显式匹配。单个键的流量过高也会降低局部性，官方给出的当前建议约为每分钟 15 个请求；高流量服务应通过稳定分片分散，而不是随机生成键。这个阈值属于平台运营建议，需要随官方文档更新。

## 一次缓存写入和读取怎样发生

用两个独立的知识问答请求推演。应用版本是 `policy-v3`，工具版本是 `tools-v8`，两次请求使用同一个缓存键。稳定前缀由规则和工具组成，显式断点位于工具定义之后；用户问题、Scope、知识 Release 和检索证据位于动态尾部。

第一次请求输入“远程访问申请需要哪些条件”。服务端在断点查不到现有条目，处理完整输入，并把满足门槛的前缀写入缓存。响应 Usage 中，`cache_write_tokens` 表示新写入的 Token；`cached_tokens` 可能为零。应用同时保存内部 `prefix_fingerprint`、策略版本、工具版本和实际 Usage，不保存完整敏感 Prompt 到指标标签。

第二次请求输入“申请审批后什么时候生效”。规则和工具没有变化，动态问题与证据不同。服务端在相同键和精确前缀处找到缓存，Usage 中 `cached_tokens` 大于零；动态尾部仍按普通输入处理，模型重新生成回答。缓存读取没有绕过检索，第二个问题仍使用当前 Release 的证据。

失败变体在规则前插入当前时间。稳定前缀从 `08:41` 变成 `08:42`，第二次请求无法读取第一次写入的完整前缀，`cache_write_tokens` 再次升高。业务回答可能仍然正确，但成本和延迟退化。修复是把时间放到断点之后，或者从 Prompt 移入 Metadata，而不是扩大缓存 TTL。

权限变体撤回当前用户的文档 Scope。稳定规则和工具仍可命中缓存，运行时用新的 Scope 检索并拒绝不可见证据。缓存内容属于同一组织的输入优化，不是授权快照；命中缓存不能恢复已经撤回的权限。

这条轨迹包含完整证据：输入记录包含版本与动态问题；状态记录包含缓存键、内部前缀指纹和断点位置；模型调用返回读写 Token；检索与授权产生自己的结果；最终输出通过证据验证。若答案失败，缓存指标只能说明输入复用情况，不能替代检索和回答 Trace。

## 派生请求为什么应从已发送请求追加

同一 Turn 里可能产生评审、摘要或候选比较等派生调用。它们希望复用主请求的规则、工具和已确认历史。若每个调用都从高层配置重新构建，默认字段、工具排序、消息分块和空值处理都可能产生细小差异。

更可靠的方式是在主请求发送前保存脱敏的结构快照和前缀指纹，派生请求复制已发送的稳定部分，只追加自己需要的消息。代码层面要把共享工具数组视为不可变对象，避免某个分支原地排序或过滤后影响其他请求。

追加也有边界。派生调用如果切换模型、改变工具、重写 Developer Message 或换输出 Schema，它就不再是同一缓存前缀。程序应把这些差异列为显式参数，生成新指纹并接受失效；不要为了看起来“复用父请求”而隐瞒真实变化。

上下文压缩是另一种有意重写。旧消息被摘要替代以后，请求会从替换位置产生新前缀。压缩减少后续输入长度，却可能牺牲现有缓存。是否值得取决于剩余会话长度、原历史大小和缓存价格，不能只比较本轮 Token。

恢复任务时使用持久化的消息和版本重新渲染，但仍要检查实际前缀。序列化代码升级后，即便业务状态没有变，Wire 形状也可能变化。恢复记录应保存 Builder 版本与内部指纹，遇到差异时明确记为新缓存代际，不声称复用了崩溃前缓存。

## Prompt Cache 与其他缓存解决什么问题

Prompt Cache 容易和结果缓存混淆。结果缓存把一个确定请求映射到已经生成的答案，命中后可能完全不调用模型；Prompt Cache 只复用输入计算，模型仍读取动态尾部并生成新的输出。前者需要定义答案何时过期，后者关心前缀是否精确一致。

语义缓存又是另一种机制。它把意思相近的问题映射到旧答案或旧中间结果，匹配通常基于向量距离或规则。两个问题“远程访问何时生效”和“VPN 审批多久生效”可能被判为相似，但它们涉及的资源、策略版本和用户范围未必相同。语义缓存若直接返回答案，必须重新检查 Scope、知识 Release、时效和引用，不能沿用旧请求的授权结论。

检索缓存保存查询到候选证据的中间结果。缓存键通常包含规范化查询、权限范围、知识版本和检索配置；命中以后还要重新鉴权。它减少搜索与重排开销，不会让模型的规则和工具前缀自动命中。Prompt Cache 和检索缓存可以同时工作，但应分别记录 Usage 和候选版本。

应用内的会话摘要缓存保存一份可恢复状态，解决进程重启或多 Worker 共享；Provider 的 Prompt Cache 不应承担持久化。服务端缓存淘汰以后，应用仍需从 Message、Checkpoint 和 Release 重建输入。若系统只有一个缓存键却没有自己的会话状态，缓存 Miss 会暴露出数据已经丢失。

四种缓存的失效原因也不同：Prompt Cache 因前缀变化或服务端淘汰失效；结果缓存因业务数据、权限和回答策略变化失效；语义缓存还受相似阈值和误命中影响；检索缓存要绑定知识版本与 ACL。把它们统一成一个 `cache_hit` 指标，故障时无法判断省掉的是模型输入、模型生成还是检索调用。

::: warning 缓存命中不传播信任

旧答案、旧检索结果和已处理前缀都不能提升内容的可信等级。用户输入仍是用户输入，外部文档仍是不可信证据，身份和权限继续从本次运行时读取。

:::

## 权限变化为什么不能由缓存处理

Prompt Cache 复用的是模型已经处理过的输入前缀。它不知道用户当前是否仍能读取文档，也不判断某个工具调用是否越权。把 `allowed_scopes` 写进稳定规则并缓存，只能记录写入当时的值；权限撤回后继续复用会产生过期安全状态。

可信身份与 Scope 由应用在每次请求入口读取。检索器按当前范围过滤，Tool Runtime 在执行前授权，Answer Validator 检查每条 Claim 的 Evidence 是否仍对当前用户可见。这些动作即使前缀全部命中也不能省略。

为了让工具前缀稳定，应用可以保持 Schema 不变，用运行时 `allowed_tools` 或自有授权层限制可调用集合。前一篇讲过延迟发现，目录也可以提前减少模型看到的工具。无论采用哪种显示策略，执行时拒绝都是最后防线。

多租户服务的缓存键也不能直接放明文邮箱、租户名或内部路径。使用稳定的脱敏标识并按实际共享范围分区。前缀内容是否允许跨用户复用，还受组织、数据保留和供应商政策约束；不能为了命中率跨越原有数据隔离。

## 读写 Token 怎样解释成本

GPT-5.6 及之后的当前计费把缓存读、缓存写和普通输入分开。官方文档显示，缓存读取按普通输入价格的 0.1 倍计费，写入按 1.25 倍计费；其余未读未写 Token 按普通输入计费。较早模型没有同样的写入收费规则，因此报表必须带模型和日期，不能把不同代际混在一条趋势里。

缓存写比普通输入贵，意味着重复写入却很少读取会增加成本。监控至少保留 `input_tokens`、`cached_tokens`、`cache_write_tokens`、模型、缓存键分区、前缀版本和请求类型。把 `cached_tokens / input_tokens`当成唯一指标，会忽略写入费用和调用次数。

一次响应同时出现读取与写入是正常的。隐式模式可以读取早期前缀，又把新追加的对话写到最新断点。判断是否浪费，要看新写内容之后有没有机会复用；单次变化的用户尾部不值得持续写时，显式模式更合适。

缓存 Token 仍计入速率限制，命中也不保证零延迟。服务端还要处理动态尾部并生成输出。性能看板应把输入处理、首 Token、总生成时间和业务完成率分开；缓存优化导致模型调用次数增加时，总延迟可能反而上升。

当前 GPT-5.6 的 TTL 通过 `prompt_cache_options.ttl`设置，官方文档目前只支持 `30m`。每次复用会刷新期限，服务端也可能保留更久，但应用不能把更久保留当承诺。缓存自然淘汰后出现 Miss 是正常状态，不应重试同一模型请求只为制造命中。

## 缓存失效怎样定位到第一个变化

`cached_tokens=0`只是结果，排查要继续定位变化来自哪里。先确认断点前达到模型要求的最小 Token，再检查是否有前一次写入、缓存键是否一致；这些条件满足后，比较实际前缀。

| 现象 | 先检查什么 | 常见原因 |
| --- | --- | --- |
| 每次都写、从不读 | 时间戳、Request ID、用户问题的位置 | 动态内容位于断点前 |
| 工具升级后命中骤降 | 工具版本、顺序、Schema 指纹 | 有意发布或非确定排序 |
| 只有部分会话能命中 | 缓存键分片、请求速率、前缀长度 | 路由局部性或低于门槛 |
| 读写同时增加 | 隐式断点位置、追加历史 | 读取旧前缀并写入新后缀 |
| 命中很高但成本不降 | 单 Turn 调用数、输出成本 | 调用过多或生成占主导 |
| 命中后答案仍越权 | 当前 Scope、Evidence 可见性 | 把缓存误当授权 |

应用可以在每次有意重写时记录动作，例如 `policy_release`、`tool_schema_upgrade`、`history_compaction` 或 `image_reencode`，附带旧新指纹与区域名。若前缀变化但没有任何重写事件，优先检查非确定序列化和构建后突变。

第一处差异比整份 Diff 更有用。变化发生在规则开头，后面的工具和示例都无法复用；变化只在断点后的用户问题，不影响稳定前缀。调试工具返回字节或 Token 索引、所属区域和 Builder 版本，不需要把全文打印到日志。

超时和取消也要分类。缓存查找由服务端处理，应用通常无法单独重试该步骤；整个请求超时后按模型调用策略处理。若外部动作已经执行，不能因为缓存状态未知就重放 Tool Call。Prompt Cache 没有改变 Agent 的幂等与副作用规则。

## 怎样验证稳定前缀、成本和回答都没有回归

本地单元测试覆盖确定排序、规范序列化、动态字段隔离、派生请求追加和第一差异定位。共享示例可以用统一命令运行：

```bash
PYTHONPATH=examples/ai-agent python3 -m unittest discover \
  -s examples/ai-agent/tests -p 'test_*.py'
```

契约测试固定一份 SDK 请求，断言 Developer Message 中的断点、`prompt_cache_options`和 `prompt_cache_key`没有在升级时丢失。它还要覆盖错误形状：断点放在不支持的块上应收到稳定的 400 分类；显式模式没有任何显式断点时，不应声称已经启用缓存。

在线测试连续发两次共享前缀、不同用户问题的请求。第一次记录写入，第二次检查 `usage.input_tokens_details.cached_tokens`；测试只在真实 Usage 出现后报告命中，不能用本地哈希相等代替。另一个用例在断点前修改一个字符，确认读取减少或失效，用于证明测试确实观察到前缀边界。

成本回归把相同业务用例放在不同模型、缓存模式和会话长度下，统计读、写、普通输入、模型调用次数与最终完成状态。缓存命中提升而拒答准确性下降，说明上下文或权限被错误移动；成本下降但首轮延迟上升，说明断点或工具常驻策略需要调整。

恢复测试在保存会话后升级 Builder。恢复请求先渲染前缀并比较版本，差异被记录为有意失效；旧缓存不可用时正常处理，不能把 Miss 当任务失败。取消发生在模型请求中时保存调用状态，后续恢复按供应商响应和 Agent 状态决定是否重试，不根据 `cached_tokens`猜执行结果。

验证结束时需要同时回答三件事：相同版本能否产生相同前缀，服务端是否实际读取缓存，业务结果是否仍满足权限和证据要求。前两个问题属于性能工程，最后一个属于产品正确性。只有三者一起通过，稳定前缀才是真的优化，而不是把错误输入处理得更快。
