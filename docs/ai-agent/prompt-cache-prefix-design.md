# Prompt Cache：稳定前缀怎样复用计算

许多模型调用反复携带相同的系统规则、工具定义和长文档前缀。Prompt Cache 利用相同前缀复用部分计算。它优化调用成本和延迟，不保存业务记忆，也不会让模型知道上一次回答。

## 缓存命中依赖稳定前缀

可复用内容放在输入前部，变化频繁的用户问题、时间和请求 ID 放后部。工具定义顺序、空格或序列化方式变化，都可能改变前缀。应用应使用稳定构建器，而不是每次遍历无序集合。

```text
[系统策略][固定工具定义][共享资料][会话状态][当前问题]
<--------- 可稳定复用 ---------><-- 高频变化 -->
```

## 缓存键不是由业务随意猜测

不同供应商对缓存启用、前缀长度和 usage 字段的定义可能不同，应以当前官方接口为准。应用能做的是保持输入稳定，记录实际返回的缓存计量，不要用“字符串看起来一样”推断命中。

模型、工具 Schema、策略版本或共享资料改变时，前缀应自然失效。为了追求命中而继续复用过期策略，会把性能优化变成正确性问题。

## Prompt Cache 与记忆、结果缓存不同

Prompt Cache 复用模型对输入前缀的处理；记忆保存以后需要检索的用户或任务信息；结果缓存直接复用某个查询的输出。三者的键、有效期和隐私风险都不同。

用户问题相同也不能直接共享结果，除非缓存键同时包含租户、权限范围、知识版本和生成策略。Prompt Cache 由供应商处理前缀，不等于业务结果可跨用户复用。

## 怎样验证设计是否有效

选择一组固定系统规则，连续发送不同用户问题，记录每次输入 Token、缓存相关计量和总延迟；再改变工具定义或模型，观察缓存计量是否变化。没有供应商返回证据时，只能说前缀已稳定，不能声称命中。

测试还应确认敏感信息没有被提升到共享前缀。个体记忆、访问令牌和私有证据应留在请求隔离区域。

## 不要为了缓存破坏上下文结构

固定前缀仍要短而清晰。把所有历史文档放前面也许增加可缓存长度，却会引入冲突和无关信息。先按上下文工程选择材料，再优化其中稳定部分。

缓存失效应只影响性能，不影响答案正确性。若缓存不可用就无法完成请求，说明系统把优化机制误当成了状态存储。
