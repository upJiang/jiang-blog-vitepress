# Reflection 怎样发现问题并做有限修复

Reflection 不是让模型反复评价自己。可靠的修复从可观察问题开始：缺少引用、字段不完整、证据冲突或工具返回错误。验证器指出具体问题，修复步骤只处理被允许修改的部分。

## 验证结果是 Reflection 的输入

答案先经过结构、事实绑定、权限、隐私和完整性检查。结果以错误码和位置表达，例如 `missing_citation:claim-2`，而不是一句“答案不够好”。

模型可以帮助重写句子，确定性验证器负责判断引用是否存在、证据是否可见和字段是否齐全。

## 修复范围要小于原任务

缺少引用时，先在当前证据中寻找绑定；格式错误时只重建结构；证据不足时触发一次受限补搜。修复不能扩大 ACL、替换知识版本或删除已经被证据支持的关键步骤。

保存原答案、问题列表和修复候选，验证通过后再替换。直接覆盖会让开发者无法判断修复是否造成信息丢失。

## 一次有限修复轨迹

原答案包含两条 Claim，其中第二条没有 Evidence。验证器返回缺失绑定；修复器在现有证据中找不到直接支持，于是发起一个补充查询；仍无结果后删除该断言，并在回答中说明资料不足。

这条路径没有让模型编造引用，也没有反复“再想一次”。终态是信息更少但可证明。

## 轮数和退出条件由程序控制

每类问题设置最大修复次数，记录修复前后问题集合。如果新一轮没有减少问题，立即停止；权限、注入和关键证据不足通常不可通过改写修复，应直接拒答。

模型声称“已修复”没有意义，必须重新运行同一组验证器。

## Reflection 适合有外部判据的任务

代码测试失败、Schema 校验失败、引用缺失和覆盖维度不足都有可观察信号，适合有限 Reflection。审美偏好或没有标准答案的问题，反复自评容易增加措辞而不增加事实。

如果失败总发生在同一环节，应修检索、工具或 Prompt，而不是无限增加修复轮次。
