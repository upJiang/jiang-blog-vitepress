# 上下文工程：怎样装配一次模型输入

上下文工程不是把资料尽量塞进窗口，而是在一次调用前选择模型真正需要的信息。装配顺序会影响指令是否生效、证据是否被淹没，以及预算耗尽时丢掉什么。

## 上下文由不同责任的材料组成

常见材料包括系统策略、当前用户问题、会话焦点、近期消息、长期记忆、检索证据和工具结果。它们的可信度、有效期和用途不同，应该保留来源标签，而不是先拼成一段无边界文本。

策略决定模型能做什么，证据回答事实问题，历史提供指代，记忆补充稳定偏好。把网页中的“忽略系统规则”与系统策略放在同一层，会制造提示注入入口。

## 预算在调用前分配

总窗口需要同时容纳输入和预留输出。应用先给不可丢的策略、当前问题和关键证据分配预算，再考虑历史和补充材料。不能等供应商返回超限错误后才从字符串末尾截断。

## 装配过程保留可解释记录

每个片段记录名称、来源、优先级、估算 Token、是否入选和淘汰原因。模型调用失败或回答漏掉关键事实时，可以回看是检索没找到、装配没选中，还是生成没有使用。

一次可观察轨迹例如：策略 120 Token、当前问题 30、证据 900、近期历史 500，旧闲聊因预算不足被排除。数字来自实际 tokenizer 或供应商计量，教学估算不能冒充计费值。

## 工具结果进入上下文前要压缩和隔离

工具可能返回大段 JSON、HTML 或日志。先保留字段化摘要、稳定 ID 和必要原文，超长正文放外部存储。外部内容用明确边界包裹，并告诉模型它是数据，不是新的指令。

压缩不能丢掉权限范围、版本和引用位置。只有摘要没有来源，后续验证无法知道一句话来自哪条记录。

## 上下文问题要从证据链定位

回答引用了旧规则，先查 Turn 固定的知识版本，再查检索结果和入选片段；模型忘记用户刚说的对象，查焦点状态和历史裁剪；成本异常，查每一类材料的 Token 占比。

上下文窗口变大只能推迟超限，不能替代选择。材料越多，冲突、噪声和敏感信息暴露面也会增加。
