# 结构化输出约束格式，不证明业务事实

模型返回一段 JSON，程序成功解析，字段也符合 Schema，这个结果可以直接写入数据库或调用工具吗？答案取决于字段是什么。`query` 和 `limit` 可以由模型提出，`user_id`、可访问范围、当前知识版本和审批结果不能交给模型决定。

结构化输出解决的是协议稳定性。它让模型按指定字段、类型和枚举返回结果，减少缺键、类型漂移和无法解析的自由文本。它没有连接业务数据库，也没有替当前用户执行授权，更无法证明某个字段来自最新证据。

::: info 四层校验

1. **响应层**，调用是否完成，是否发生拒绝、截断或服务错误。
2. **Schema 层**，输出能否解析，字段、类型和枚举是否符合约束。
3. **应用层**，长度、组合关系、允许字段和领域规则是否成立。
4. **事实层**，身份、权限、版本与结论是否由可信来源确认。

:::

前两层可以由 API 和 SDK 帮忙，后两层仍属于应用。本文用“生成一次知识搜索参数”贯穿四层校验，最后故意让模型返回格式完全正确、业务上却越权的对象，观察程序应该在哪里拒绝。

## 自由文本为什么不适合直接驱动程序

模型很擅长生成说明文字，程序需要稳定分支。假设应用想从用户问题中提取搜索词和结果数量，模型可能返回“建议搜索远程访问，取五条左右”，也可能返回 Markdown、代码围栏或一段带解释的 JSON。靠字符串截取和正则解析，Prompt 稍微调整就可能改变格式。

普通 JSON mode 能保证输出是合法 JSON，却不保证具体 Schema。`limit` 可能是字符串，`query` 可能缺失，模型也可能增加 `scope_ids`。应用仍要手写校验与重试。Structured Outputs 把 Schema 交给模型服务，严格模式下，正常结构化结果会遵守支持的 JSON Schema 子集。

格式约束带来三个直接收益。调用方可以使用类型化对象，不必从说明文字猜字段；拒绝可以作为独立内容类型处理；Schema 成为模型适配器与业务代码之间的显式契约。它减少的是输出形状的不确定性。

这里容易出现一个危险推论：既然服务保证 Schema，一切校验都可以删除。Schema 只能检查它表达出来的条件，而且数据仍由模型生成。`status` 被限制为 `approved | rejected`，模型仍可能在没有审批记录时选择 approved。`user_id` 被定义为非空字符串，也不代表它等于当前登录用户。

结构化输出适合提取、分类、规划和工具参数候选。业务真相需要另一个来源。金额从订单服务读取，权限从认证与策略服务读取，知识版本从当前 Release 快照读取，证据关系从检索和验证链路读取。

## Structured Outputs 在调用链中的位置

一次结构化调用仍从普通模型请求开始。应用准备消息和 Schema，模型服务生成类型化输出，SDK 解析为对象，业务代码再处理对象。Structured Outputs 位于“生成候选”与“应用消费”之间，没有跨过模型边界。

### 返回给用户的结构与工具参数是两类契约

当前 OpenAI 接口提供两种常见使用方式。希望模型给用户返回固定结构时，可以使用结构化 `text.format`；希望模型调用应用能力时，使用 Function Calling，并给函数参数设置严格 Schema。

两者都使用 JSON Schema，却有不同的下游。前者可能生成页面要展示的步骤、分类或抽取结果，应用仍要验证内容。后者生成动作候选，运行时还要执行工具查找、参数校验、授权和调用。选择哪种方式，取决于模型是在回答用户，还是在请求应用执行能力。

### JSON mode 只保证合法 JSON

JSON mode 适合模型或接口暂不支持严格 Schema 的场景。它保证输出可解析为 JSON，不保证字段匹配某个对象。应用必须继续用 Pydantic、Zod 或其他验证器检查结构，并处理截断、拒绝与内容策略导致的不完整结果。

Structured Outputs 在支持时更省事，仍不能跳过响应状态。模型可能拒绝请求；请求可能因为最大输出 Token 或内容策略而 incomplete；网络与认证也可能在生成前失败。不能看到 `output_text` 非空就直接反序列化。

### Schema 是版本化接口

Schema 改字段名、枚举或嵌套关系，会影响 Prompt、模型输出、SDK 类型和业务消费者。生产代码应给 Schema 一个稳定名称和版本，记录每次调用使用的版本。新旧 Worker 并存时，消费者要知道自己能解析哪些版本，不能只靠部署时间猜测。

Schema 描述候选数据，不应包含模型无权提供的字段。把 `user_id` 和 `scope_ids` 放入工具参数，会诱导调用方相信模型填出的值。更稳妥的做法是让模型只返回 query、limit 等语义参数，运行时再将可信认证上下文合并成命令。

## Schema 能保证哪些形状

严格结构化输出支持 JSON Schema 的一个子集。官方文档要求根节点是 object，object 需要设置 `additionalProperties: false`，字段需要出现在 required 中；需要可选值时，可以用与 null 的联合类型表达。并非所有 JSON Schema 关键字都支持，提交不支持的 Schema 会在请求阶段报错。

一份搜索参数 Schema 可以写成：

```json
{
  "type": "object",
  "properties": {
    "query": {
      "type": "string",
      "description": "只包含当前问题需要检索的语义"
    },
    "limit": {
      "type": "integer",
      "description": "候选结果上限"
    }
  },
  "required": ["query", "limit"],
  "additionalProperties": false
}
```

这个 Schema 能阻止模型增加第三个字段，也能保证 limit 是整数。它没有表达 query 去掉空白后必须非空，也没有限制 limit 落在 1 到 20。具体模型和 Schema 子集可能支持部分数值或字符串约束，应用层仍应保留领域校验，避免把供应商能力当成唯一防线。

### required 不等于有用值

字段存在，不代表字段可用。`query=""` 满足“字段是字符串”，却不能用于搜索；`limit=0` 是整数，却不符合业务范围；`reason="未知"` 可能满足枚举，却没有提供决策需要的证据。

应用验证器要检查规范化后的值。文本去除首尾空白后判空，数组检查长度和重复，数值检查上下界，字段组合检查互斥与依赖。失败时返回稳定错误码，比如 `query_is_empty` 或 `limit_out_of_range`，不要让调用方解析自然语言。

### 枚举不证明状态真实

把状态约束为 pending、approved、rejected，可以防止拼写漂移。模型选择 approved 只是一项候选分类。审批状态要从审批系统按对象 ID 查询，或者由确定性规则计算。

同理，模型可以把 Claim 的 `support_status` 设成 supported，真正的验证器仍要检查每个 evidence_id 是否存在、当前用户是否可见、证据是否直接支持断言。结构化字段让验证更容易执行，不能替代验证本身。

### additionalProperties 防止字段悄悄扩散

禁止额外字段可以发现契约漂移，也能减少模型塞入身份和权限参数的机会。应用层仍要使用允许字段集合再检查一次，特别是从旧缓存、手写 JSON 或非严格模型适配器接收数据时。

缓存里的历史对象可能早于当前 Schema。直接 `dict.update` 合并新字段，会绕过模型服务的严格输出保证。所有进入执行边界的对象，无论来自模型、缓存还是消息队列，都要按当前接收版本重新验证。

## Schema 设计从消费者的分支开始

设计结构化输出时，先写调用方真正需要执行的分支，再反推字段。把一段自然语言回答拆成十几个字段，界面最后只读取 `status` 和 `summary`，其余字段既占 Token，也扩大了事实校验面。反过来，只返回一个 `result` 字符串，调用方又要重新解析自由文本。

搜索参数的消费者只有两个分支：参数有效就进入授权，参数无效就停止或有限修复。因此 query 与 limit 足够。模型没有必要返回“是否允许搜索”“属于哪个用户”和“使用哪个知识版本”，这些值的消费者本来就是确定性程序。

### 字段名称要表达可观察含义

`confidence` 很常见，却容易失去含义。它是模型对分类的自评、检索分数、证据覆盖率，还是应用校准后的概率？四者不能共用一个字段。若调用方没有针对这个数字的稳定决策，就先删除。需要时拆成 `model_confidence`、`retrieval_score` 或 `evidence_coverage`，并为每项说明生产者和取值范围。

布尔字段也会隐藏状态。`success=false` 无法区分拒绝、无结果、超时和参数错误。更适合用受限枚举表示结果类型，同时保留结构化原因。枚举值要由程序定义，模型负责选择候选；进入业务终态前，程序仍会根据实际执行结果覆盖它。

字段描述用于帮助模型理解语义，不能承担程序约束。写“limit 必须小于 20”有助于生成，但真正的上界要放进 Schema 支持的约束和应用验证。Prompt、description 与验证器出现不同数字时，系统应以确定性验证器为准，并把这类不一致加入契约测试。

### 可选字段要区分缺失、空值与不适用

严格模式要求字段列入 required，需要可选语义时可以允许 null。null 应表示明确的“当前不适用或无法提供”，空字符串表示一个字符串值，缺失字段则是协议错误。三者如果在业务层都转换成空字符串，调用方就失去了失败原因。

比如抽取审批信息时，`approver` 可以是 string 或 null。只有证据明确说明无需审批时，null 才可能表示不适用；证据没有提及审批人时，它表示未知。若业务需要区分两者，应增加 `approver_status` 枚举，而不是要求模型凭空补一个姓名。

数组也要定义空集合的语义。`evidence_ids=[]` 可能表示该结论不需要外部证据，也可能表示检索失败。安全的默认是“没有支撑”，只有确定性规则产生的结论才能显式标成不需要证据。模型不能靠空数组跳过验证。

### 联合结果不要把控制流藏进顶层 anyOf

很多任务希望同时表示成功、拒绝和需要补充信息。可以在根 object 中放一个 `kind` 枚举，再为各分支准备允许 null 的字段，由应用根据 kind 检查组合关系。当前严格 Schema 对根节点和 anyOf 有约束，生成 Schema 前要检查所用 SDK 最终产物，不能只看 Python 或 TypeScript 类型定义。

组合验证仍由应用完成。kind=success 时 result 不能为空，kind=needs_input 时 missing_fields 至少有一项，kind=refused 时不能带可执行命令。Schema 能表达一部分条件，业务验证器保留完整不变量，避免供应商支持范围变化后失去约束。

### Schema 大小也是上下文与维护成本

属性、枚举和嵌套层级越多，模型越难一次生成，Schema 传输和缓存也更重。官方接口对属性总数、嵌套深度、字符串总长度和枚举规模有上限。即使尚未接近硬限制，数百个业务枚举也会让版本兼容和评测变得困难。

大型领域对象可以拆成两步。模型先生成小型意图或动作候选，程序根据候选选择对应的窄 Schema，再请求具体参数。这样每次只暴露当前动作所需字段，也能减少模型看到无关工具和参数的机会。延迟增加了一次调用，换来更小的契约和更清楚的权限边界，是否值得要用实际任务评测。

## 从模型对象到领域命令的数据流

模型输出进入业务前可以经过“解析、规范化、领域校验、授权、快照、执行”六个边界。每一步产生不同错误，全部塞进一个 try/except 会丢掉恢复信息。

解析阶段只处理协议。它确认响应 completed、内容不是 refusal，并把输出转换为候选类型。这里不访问数据库，也不判断用户权限。解析失败通常属于模型适配器、Schema 或响应状态问题。

规范化阶段处理不改变语义的转换，比如去掉 query 首尾空白、把语言标签统一为小写、删除数组重复项。规范化前后都可记录摘要，便于发现模型持续输出多余空格或旧枚举。不能在这里把未知 Scope 替换成默认 Scope，那已经改变权限语义。

领域校验检查对象内部是否自洽。limit 是否在业务上限内，时间范围起止是否有序，多个字段是否互斥，引用 ID 是否符合允许格式，都在这一层完成。失败对象仍是候选，不会写入领域状态。

授权阶段加入可信上下文。它从当前请求读取用户、租户和角色，从活动配置读取 Release 与策略版本，再判断这次动作是否可执行。授权函数接收候选参数和 AuthContext，返回不可变命令。模型对象不会在原地升级为可信对象，类型边界能防止后续代码误用。

快照阶段固定执行需要的版本。请求排队时，权限或 Release 可能变化；系统要么在消费时重新授权，要么按任务合同继续创建时快照。无论选择哪种语义，都要保留版本 ID。只保存 query 和 limit，恢复时无法知道原任务在哪个范围执行。

执行阶段只接受已经授权的命令。检索器、工具或数据库仓储不再解析模型自由文本。它返回成功、空结果、拒绝、超时或未知执行状态，运行时据此继续，而不是让模型把错误解释成成功。

### 候选类型与领域类型要分开

可以给两个对象相似字段，但不要复用同一个类。`SearchArguments` 表示模型可提出的语义参数，`SearchCommand` 表示应用已注入身份和版本的可执行命令。后者只能由授权函数创建。

这种类型分离会多写几行映射代码，却让代码审查更直接：任何调用检索器的位置都必须拿到 SearchCommand；测试也能证明 scope 只来自 AuthContext。若所有字段共用一个通用字典，可信来源只存在于开发者记忆里。

候选结果保存原始响应引用和 Schema 版本，领域命令保存授权版本和创建时间。日志通过请求 ID 关联两者，不必复制敏感正文。发生越权候选时，可以看到模型提出过什么，同时证明它没有进入执行。

这两步对应不同失败。参数解析失败说明模型候选不满足工具契约，可以在受限次数内让模型修复 query 或 limit。授权失败说明当前可信上下文缺少范围或版本，重新生成参数没有意义。把两类错误都反馈成“请重试”，会让模型反复改写与权限无关的字段。

### 为什么不直接让 Pydantic 接收全部字段

类型库通常可以配置忽略额外字段。对普通配置兼容很方便，放在安全边界却可能隐藏越权候选：模型返回 `scope_ids=["other-team"]`，解析器忽略它，日志又只保存解析后对象，团队就看不到模型曾试图提交可信字段。

动作入口更适合拒绝额外字段并保留脱敏的验证问题。它不代表模型恶意，可能只是 Prompt 或工具描述让字段边界不清。记录错误能帮助修正 Schema，同时保证错误候选没有进入执行。

### 类型化对象仍然需要不可变快照

SearchCommand 生成后应绑定本次认证与 Release 快照。执行期间权限或 Release 变化时，系统按策略决定继续旧快照、取消或重新授权，不能让模型参数动态覆盖。命令尽量使用不可变对象，避免中间件在执行前悄悄替换范围。

如果命令进入队列，消费者再次检查 Schema 版本和授权新鲜度。序列化成功只证明消息格式正确，不能证明权限在排队期间没有撤回。

## 用一个格式正确的越权结果推演四层校验

用户问：“帮我查远程访问失败原因，最多返回 5 条。”应用希望模型生成搜索参数。模型返回：

```json
{
  "query": "远程访问失败原因",
  "limit": 5,
  "scope_ids": ["other-team"],
  "release_id": "release-latest"
}
```

这段文本是合法 JSON。若使用的严格 Schema 禁止额外字段，响应不会以这一结构作为正常解析结果；若它来自 JSON mode、旧缓存或另一个适配器，应用允许字段检查会以 `untrusted_fields:release_id,scope_ids` 拒绝。模型不能选择搜索范围或活动 Release。

模型修复后返回：

```json
{
  "query": "远程访问失败原因",
  "limit": 5
}
```

响应层确认调用 completed 且没有 refusal；Schema 层确认字段与类型；应用层确认 query 非空、limit 在范围内。最后，授权层从当前认证上下文读取用户 ID 和可见 Scope，从配置读取 Release，构造 SearchCommand。只有这条命令能进入检索器。

再换一个输入：“确认我的设备不合规，并返回原因。”模型可以生成 query，却不能确认前提。工具得到的证据若只写通用制度，回答层不能输出“你的设备不合规”。参数结构和搜索命令都正确，事实校验仍会拒绝具体结论。这个反例说明格式验证与 Claim 支撑是两条独立链路。

### 结构化空结果怎样处理

模型可能返回 `{"query": "远程访问", "limit": 5}`，检索器正常执行却没有命中。空候选是合法业务结果，不是 Schema 错误。系统应保留查询范围、Release 和空结果原因，再决定安全拒答或换一个检索策略。

如果模型返回空 query，参数验证在调用检索前结束，检索次数保持为零。两种“空”发生位置不同，指标和恢复动作也不同。

## 拒绝、截断与 Schema 错误怎样停止

模型服务可能返回 refusal。客户端应读取对应内容类型，不能把拒绝文本当成目标对象解析，也不能补一个符合 Schema 的默认对象继续执行。拒绝是本轮生成的终态，业务是否允许换方案由上层决定。

输出到达最大 Token 或被内容策略中断时，响应可能 incomplete。即使前缀看起来像完整 JSON，也要先检查响应状态。部分对象不能进入数据库或工具执行，除非任务协议专门支持分片并有完整性标记。

Schema 本身不受支持时，请求会失败。部署前要把 Schema 编译和一次最小调用纳入集成测试，不能等真实用户触发。根节点类型、required、`additionalProperties` 和不支持关键字都应有静态检查。

SDK 解析失败、网络错误和服务错误要保留原类别。把它们统一交给模型“修复 JSON”，既不会恢复网络，也可能掩盖适配器版本不兼容。只有模型正常返回、应用层字段校验失败，并且错误不涉及权限时，才适合做一次有限修复。

::: warning 绝不让模型补可信字段

身份、租户、可见范围、活动 Release、审批结果、余额和最终权限来自可信服务。缺少这些值时停止或降级，不能要求模型按 Schema 填一个占位值。

:::

## 怎样测试结构与事实边界

Schema 测试固定有效与无效对象。有效 query 和 limit 应解析成功；空 query、布尔类型的 limit、越界 limit 和额外字段都要失败。Python 中 `bool` 是 `int` 的子类，验证器需要确认所用库对这类边界的实际行为，不能只测普通整数。

授权测试证明模型字段无法进入可信命令。给候选增加 `scope_ids` 应返回 untrusted_fields；解析干净参数后，SearchCommand 的用户、Scope 和 Release 必须等于 AuthContext，而不是模型文本。

响应适配测试覆盖 completed、refusal、incomplete 和错误对象。只有 completed 且解析成功的输出进入应用验证；其他状态保留原因并停止。使用 Fake Response 可以验证分支，不能伪造在线模型支持的 Schema 范围。

事实测试故意构造一个 Schema 完全合法、内容不受证据支持的对象。比如 Claim 文本写“账号已停用”，evidence_ids 为空，验证器必须标为 unsupported。再给一个不可见证据 ID，权限校验仍要失败。结构化输出让 Claim 与 Evidence 容易关联，不会自动建立支撑关系。

版本测试同时运行 v1 与 v2 Schema 消费者。旧对象进入新消费者时，要明确迁移或拒绝；新对象进入旧消费者不能依赖忽略字段。队列、缓存和数据库中的对象都标注 Schema 版本，回滚时才能判断兼容范围。

回归样本还要保留历史失败对象，包括缺字段、旧枚举、额外可信字段、拒绝和截断响应。新版本如果只在最新模型的正常输出上通过，却开始接受旧缓存中的越权字段，仍然属于契约回归。回放时同时断言执行器调用次数，校验失败对象必须在执行边界之前结束。

共享示例的确定性测试已经覆盖额外可信字段被拒绝，以及 AuthContext 注入真实范围。运行 `yarn ai-agent:examples` 可以验证本地契约。它不发送真实模型请求，也不会产生在线 usage。

## 生产接入要保存哪些证据

一次结构化调用至少关联模型、SDK、Schema 名称与版本、请求 ID、响应状态、解析结果和应用验证问题。普通日志记录字段名与错误码，不保存凭证和完整敏感内容。需要排查具体候选时，通过受控引用读取原始响应。

指标要按层统计。服务错误率反映调用可用性，Schema 解析失败反映接口兼容，应用字段失败反映 Prompt 或契约质量，授权拒绝与事实不支持反映业务边界。把它们合成一个“结构化成功率”，会让团队不知道该改模型、Schema 还是权限配置。

上线新 Schema 时先用固定样本回放，再走影子解析或小流量版本。比较的不只是解析率，还包括额外字段、空值、枚举分布、授权拒绝和最终业务结果。不能用更高的 Schema 通过率抵消越权候选增加。

缓存键包含模型、Prompt 与 Schema 版本。否则新代码可能读到旧结构，或者旧结果在权限与 Release 变化后继续使用。命中缓存后仍要重新做当前授权，结构化对象不会因为缓存过一次就永久可信。

Structured Outputs 最终提供的是更可靠的候选接口。它把“模型说了什么”转换成程序能稳定读取的对象，让后续校验有明确入口。真正决定对象能否执行或交付的，仍是应用保存的身份、权限、版本、证据和业务状态。
