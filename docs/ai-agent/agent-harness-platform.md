# Agent Harness 怎样成为可治理的平台

Harness 把协议适配、运行时、沙箱、策略、评测和观测做成可替换能力，重点是让多个产品共享控制面，而不是把所有模型能力压成最低公分母。`platform version`、`adapter`、`capability`、`policy`、`tenant scope`、`rollout` 和 `run artifact` 必须能在一次执行中互相定位。

本文沿一次新工具灰度进入租户的路径展开：能力先在候选版本中验证，再由策略决定哪些租户可见，运行时记录版本和回滚点。平台抽象遮蔽关键能力、租户配置互相影响、升级没有兼容测试和治理层成为单点瓶颈，属于不同阶段的失败。

::: info 贯穿示例

贯穿示例是一个新工具的灰度发布：工具只允许读取租户自己的知识库，候选版本先在隔离租户回放，失败或越权时要能撤回，而不是用平均回答质量掩盖控制错误。

:::

## Harness 解决什么重复建设

平台抽象遮蔽关键能力会破坏 platform version 与受控动作之间的对应关系，排查时先保留原始输入摘要和发生阶段，再判断是否允许重试。

最低公分母限制模型影响 adapter 或下游解释，不能和平台抽象遮蔽关键能力共用“重新调用一次模型”的处理方式。

平台还要处理能力的生命周期。工具描述、参数 Schema、策略版本和执行器版本一起形成能力快照，候选版本只能在快照固定后进入回放。灰度期间若某租户撤销权限，平台应让新请求立即不可见，已经运行的写动作则依据动作状态选择取消、等待回执或转人工确认。这样升级、撤权和回滚不会被一次模型重试混在一起。

## 能力适配器与租户策略如何隔离

Harness 持有工作区、工具和权限，模型只能根据观察提出动作候选。因此 platform version 与 adapter 要有唯一写入方，其他组件只能通过版本化命令申请修改。

内部开发平台与 Harness 解决的问题相邻，但控制权不同，比较时要看谁选择检查权限、谁保存 platform version、谁确认受控动作。

Agent Framework 可以参与同一请求，却不能替代 Harness；组合后仍要单独检查环境观察的可信来源和平台抽象遮蔽关键能力的终止规则。

Harness 使用的身份、范围和版本来自可信运行时，用户目标可以表达意图，但不能提升权限或改写活动 Release。

最低公分母限制模型发生时，错误回到 adapter 的所有者处理，上游缺输入、当前组件违反不变量和下游不可用分别形成不同终态。

Harness 的确定性边界位于 platform version 写入之前。模型在 Agent Harness 中只提交候选值，程序仍要从认证、版本和策略快照补入可信字段。

Harness 内部可以使用更细的临时对象，跨边界只暴露稳定协议。替换内部开发平台时，调用方不需要理解内部缓存和 SDK 响应。

## 平台版本、租户配置与运行状态

Harness 的输入合同至少列出用户目标、环境观察和能力目录，每项都注明来源、是否必需、允许的缺省值，以及缺失后是在入口拒绝还是进入降级路径。

Harness 平台要把平台版本、适配器配置、能力契约和 Run Spec 分开保存。平台版本决定基础接口，适配器描述供应商边界，能力契约约束工具参数，Run Spec 固定租户和风险范围；分开后新版本才能只影响新任务。

并发分支按稳定身份合并 capability，完成顺序只反映耗时，不能决定结果属于哪个请求，更不能让迟到的旧状态覆盖新修订。

Agent Harness 的对外结果要分别表达可交付内容、缺口、取消和未知状态，调用方不必解析错误文案。

adapter 参与乐观并发检查；处理开始后若版本变化，旧候选只保留作审计，不能继续写入 platform version。

观察版本、动作参数、审批、文件差异、进程结果、截图和测试输出组成 Harness 的最小追踪材料，日志只保存稳定 ID、版本和错误类，完整 Prompt、文档正文与凭证不进入指标标签。

契约还需要描述新鲜度。adapter 对应的数据发生变化后，旧缓存、旧候选和未完成任务怎样失效，应由版本或时间规则直接判断，不能依赖模型注意到矛盾。

删除和撤回也属于数据生命周期。Harness 引用的原始对象被移除时，稳定 ID 可以保留审计关系，正文与派生结果则按策略失效，避免继续向用户展示过期内容。

::: warning Harness 的可信边界

受控动作通过结构校验后仍是候选。Harness 使用的身份、权限、知识版本与业务事实由应用从可信服务读取，核对完成后才能执行或交付。

:::

## 一个候选能力怎样进入执行链

Harness 平台的发布验证要同时替换一个模型适配器和一个执行环境，比较新旧 Run 的领域契约、Policy、Eval 与 Trace。只有运行中的任务仍使用创建时版本，新任务才使用候选版本，平台化才没有破坏恢复边界。

观察环境接收用户目标并建立 platform version，入口校验未通过就地结束，后续模型、检索器或工具调用次数保持为零。

检查权限读取 adapter 并执行主题逻辑，参数由应用组装，外部返回先保存为可审查差异，尚未获得修改领域状态的资格。

执行并重新观察检查结构、范围、版本和主题不变量；受控动作缺少来源、落在旧版本或越过权限时，platform version 停在 rejected 或 failed。

实现可以使用函数、Graph、Middleware 或 Workflow，platform version 的所有权和平台抽象遮蔽关键能力的停止规则不会随框架改变。

部分成功需要在步骤边界处理。

## 沿一次新工具灰度推演发布路径

沿“Harness 场景：编码助手需要读取仓库、修改一个文件并运行测试，但不能访问工作区之外的路径，也不能在测试失败时宣称完成”推演 Harness：入口创建 request_id，读取可信身份，把用户目标和当前版本写入初始状态。

观察环境生成 platform version 与输入摘要；若环境观察缺失，请求返回 rejected，并指出缺少哪项材料，不继续消耗模型或外部服务配额。

检查权限按“平台把协议适配、运行时、沙箱、Policy、Eval 和 Observability 做成版本化接口，团队可以替换模型或执行环境而不改变领域契约”推进，每次依赖调用保存 call_id、参数摘要、开始时间与状态版本，以便判断超时前是否已经产生结果。

运行确定性验证写入终态；客户端断开只影响交付通道，重新连接时读取已经保存的 platform version 或事件游标，不重跑核心逻辑。

故障注入选择租户配置互相影响，程序保留原候选和错误位置，只重做失败边界，不能从入口复制整个任务并产生第二份状态。

推演结束后用 request_id 关联 platform version、受控动作与终止原因，测试据此排除并发请求串线，并确认失败路径没有遗留未关闭资源。

Harness 在输入拒绝时不调用依赖，正常路径按 5 个阶段推进，有限修复只重做失败边界。调用次数是控制流断言，不是性能宣传。

Harness 的最终记录用 request_id 关联 platform version、受控动作和失败问题，测试据此证明结果来自本次执行，没有混入并发请求。

## 平台发布怎样同时验证行为和控制

Harness 正常完成时，platform version、adapter 和受控动作指向同一次执行，重复读取返回同一终态，未完成分支已经取消或有明确所有者。

观察版本、动作参数、审批、文件差异、进程结果、截图和测试输出用于还原 Harness 的处理过程，可以按阶段和版本聚合；敏感正文留在受控存储中，不复制到日志与指标。

依赖返回成功状态只证明传输完成。Harness 还要检查受控动作是否满足业务范围、质量阈值和当前版本，明确拒绝也可能是正确终态。

platform version 的状态迁移必须单调：完成不能退回运行中，取消不能被迟到结果覆盖，失败重试也不能绕过入口已经固定的权限。

Harness 的成功证据最终要同时回答输入是什么、执行了哪些步骤、交付了什么以及为什么停止；任一项缺失都应留在未确认状态。

Harness 把业务验收与服务健康分开。依赖对 Agent Harness 返回 200 只说明传输完成，内容仍要满足当前范围和质量条件。

Harness 的观测指标按阶段和版本聚合。评估 Agent Harness 时，把错误、空结果、拒绝、恢复和资源消耗分开统计，避免一个成功率掩盖不同故障。

## 配置串扰、升级不兼容与回滚

平台化后的故障要区分适配器不可用、策略拒绝、运行状态冲突和交付失败。适配器可以切换受支持的实现，策略拒绝必须保留，状态冲突需要按版本重试，交付失败只重放事件；统一重跑会破坏平台的治理边界。

遇到平台抽象遮蔽关键能力时，先记录发生阶段、错误类别和责任对象。Harness 保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

遇到最低公分母限制模型时，先记录发生阶段、错误类别和责任对象。Harness 保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

租户配置互相影响触及 Harness 的安全边界，重试不会使它自动合法；执行路径保存拒绝规则和输入来源，清除未授权候选，并以稳定错误结束当前动作。

遇到升级没有兼容测试时，先记录发生阶段、错误类别和责任对象。Harness 保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

遇到治理层成为单点瓶颈时，先记录发生阶段、错误类别和责任对象。Harness 保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

Harness 将终态、可重试性和资源清理结果写入记录；后台扫描器根据 platform version 判断任务是在运行、等待恢复还是已失败。

Harness 执行前固定 Deadline、动作上限、重复签名、无进展阈值、预算和取消信号；任一条件触发，检查权限停止创建新工作。

Harness 把重试时间和次数计入总预算。Agent Harness 每次重试先扣减剩余额度，达到上限就保留原始错误。

Harness 的清理动作设计成幂等操作；仍被活动任务或 Lease 引用的资源拒绝删除。

## 用租户样本回放平台契约

使用隔离工作区和假环境重放观察动作循环，断言越界动作被拒绝、写操作需要审批、验证失败不会标记完成；测试显式给出用户目标、初始 platform version、预期受控动作和终止原因，不能只断言返回值非空。

Harness 的单元测试用 Fake Adapter 固定受控动作与错误，断言参数、调用顺序、状态修订和清理动作，这些结果只证明本地控制逻辑。

契约测试围绕用户目标、platform version 和可审查差异构造合法与非法样本，Schema 解析成功后继续检查权限、版本与领域不变量。

故障测试注入平台抽象遮蔽关键能力和最低公分母限制模型，记录检查权限是否被调用、platform version 是否改变、资源是否释放，以及同一身份重试会不会重复执行。

Harness 的集成测试连接真实协议与隔离存储，检查序列化、约束、并发和超时；需要在线服务时另行记录服务版本、时间、配置与凭证条件。

Harness 的回归报告要保留失败类型分布。在 Agent Harness 的回归中，拒绝、超时、权限错误和空结果必须保持各自类型，状态变化本身就是行为契约。

Harness 的性质测试随机改变 platform version 顺序、重复提交、完成顺序或状态版本，断言权限不扩大、终态不倒退、同一身份不产生两次副作用。

Agent Harness 的离线评测关注质量变化，运行时测试关注控制和恢复，两类证据都齐全才可交付。Harness 只有两类证据都存在，才能同时回答“结果是否合格”和“系统是否安全完成”。

## 多租户容量、版本和治理

Harness 要把能力目录、Policy、租户配额、审批和评测版本绑定到一次 Run。平台升级时保留旧能力的执行器和事件解析器，已运行任务不能被新策略半途改写。

平台容量要按租户、能力目录和风险等级分层计算：观察体积决定存储和 Token，浏览器或终端会话决定并发连接，写动作决定审批和对账占用，循环步数决定执行时间。并发只能缩短可并行的等待，不能突破租户配额；达到上限时暂停新 Run，保留活动 Run 的 Checkpoint，并在恢复前再次检查版本和策略。

平台达到配额上限时，先按租户和能力目录暂停新 Run，保留活动 Run 的 Checkpoint 与审批状态；恢复时再次检查 Policy 和版本，不能直接把排队任务全部放开。

Harness 的候选版本在固定样本上比较正确性、错误类型、延迟和资源消耗，平台抽象遮蔽关键能力等安全红线回归时直接停止发布，不能用平均质量抵消。

平台抽象遮蔽关键能力的降级路径在发布前写好，可以减少非关键增强、返回已经确认的受控动作，或明确暂时无法确认，缺失事实不能交给模型补写。

平台故障先用 `request_id` 定位租户、能力目录版本、审批记录、资源配额、动作回执和评测结果，再决定限流、撤回能力还是恢复 Run。平台指标只能帮助筛选，处置仍依赖这些证据。

Harness 的数据按证据用途分级保留，聚合字段可以留得更久，用户目标和大体积受控动作设置短期限、访问控制与删除通道。

Harness 先在单进程实现 platform version、超时、错误和测试，只有恢复与容量证据提出要求时，再增加队列、Lease、分布式缓存或工作流引擎。

Harness 的监控阈值要对应可执行动作。Agent Harness 的分支、依赖、上下文和预算接近上限时，应限流或缩小候选；告警本身不会停止正在运行的任务。

回滚要覆盖代码之外的状态。Harness 若改变 Schema、缓存键或持久化记录，旧版本是否还能读取新写入数据必须提前验证；无法双向兼容时采用候选版本隔离。

## 平台 Harness 与 Runtime、Framework 的边界

采用 Harness 前先画出用户目标到受控动作的最小控制图；固定函数已经能完成任务时，新增模型决策和跨进程 platform version 只会扩大测试与运维范围。

内部开发平台提供通用部署和权限能力，Harness 平台还要统一模型、工具、状态、事件和评测协议。租户可以选择已发布能力，不能修改策略或跳过审批；平台负责确认受控动作可回放。

Agent Framework 可以与 Harness 组合，但外部知识仍需授权，工具调用仍需校验，模型产生的受控动作仍停留在候选状态。

Harness 适合价值足够、平台抽象遮蔽关键能力可观察且预算可接受的任务，高风险、不可逆的决定需要确定性规则或人工批准。

执行期间修改 adapter 可以检验并发设计，旧动作若仍能覆盖 platform version，说明版本或 Lease 有缺口，增加 Prompt 规则无法修复这类竞态。

Harness 增加了 platform version、依赖调用、恢复责任和故障面，设计记录既要说明获得的能力，也要列出新增的退出、降级与回滚路径。

## 平台化前先冻结能力契约

Harness 平台面对的不是一个模型，而是多个团队、模型供应商和工具版本。平台入口要把租户、项目、风险等级、预算、允许工具和数据区域转换成不可变的 Run Spec。执行器读取 Spec，创建版本化的 Turn，所有事件和 Artifact 都带 `platform_version` 与 `policy_version`。平台管理员发布新版本只影响新任务，运行中的任务继续使用创建时的契约。

平台目录应区分能力发现和权限授予。目录可以列出工具名称、输入 Schema、延迟和风险标签，但调用前仍由租户策略和当前用户 Scope 决定。删除或下线工具时，旧 Run 仍需能读取历史定义，新的 Run 直接拒绝。把目录当作实时全局变量，会让恢复任务在同一 Turn 中换用另一套参数。

平台观测至少关联 Run、Turn、Action、事件和成本记录。租户只能查看自己的细节，平台运维查看聚合或经过审计的 Trace。删除项目时先停止新 Run，撤销 Lease 和凭证，再清理对象、索引、日志和缓存。回归测试覆盖版本兼容、租户隔离、工具下线、预算耗尽和平台升级期间的恢复。

发布检查不能只比较回答文本。候选版本至少要在固定输入上回放三类证据：动作是否仍被同一 Policy 允许，失败是否保留原来的终态和错误类型，旧 Run 是否能继续读取它创建时的能力快照。任何一项不满足，都应让候选停在 `rejected`，而不是用平均质量或少量成功样本抵消控制面回归。

平台升级还要区分“新请求不可见”和“运行中动作如何收尾”。撤回能力后，入口立即拒绝新的调用；已经发出的只读动作可以等待回执，未知副作用的动作则进入对账或人工接管。这个区分应写入事件和回滚记录，否则恢复任务会误用新版本执行器重复旧动作。

平台的默认值必须显式写入 Run Spec。没有指定模型、区域或数据保留期时，采用经过审核的策略版本并记录来源；不能让不同 Worker 根据本地环境自行选择。这样同一个任务在重试和回放时仍能得到可解释的行为。

平台租户删除和策略撤销都要经过双重确认。先停止新的 Run，再等待外部 Action 回执，最后清理凭证与派生数据，顺序错了就可能留下无法解释的孤儿动作。

## Harness 平台的发布自测

用“一个新工具能力从候选版本进入一个租户”回放时，Harness 先固定观察版本、工作区和执行预算。能力目录、Policy、租户配额、审批和评测版本由事件和 Checkpoint 保存，模型只能提出动作候选，策略层决定候选能否进入执行器。

正常路径是观察、候选、授权、动作、再观察和确定性验证。每次动作都带 `attempt_id`，输出包含退出码、差异或截图摘要。版本撤回、租户隔离失败或紧急停止要保留原始回执，不能让模型用一句“已完成”覆盖。

测试故意让观察过期、工具未知、命令超时和渠道断开。在“平台灰度”中，前两种在执行前拒绝，后两种要根据是否产生副作用决定重试或进入未知状态。恢复从最后一个 Checkpoint 开始，不重放已经确认的写动作。

“平台灰度”的离线 Fake Adapter 只验证接口和状态迁移，真实浏览器、终端或供应商还要做权限、资源和网络测试。只对新任务启用新版本，旧任务继续使用快照。

“平台灰度”的取舍要写清：更大的观察窗口能减少重新读取，却会增加 Token 和敏感内容暴露；更长的自动循环能覆盖更多步骤，却提高失控和回滚成本。

“平台灰度”的回放报告保存策略版本、动作数量、失败阶段和清理结果，平台升级后再用同一组事件比较，才能判断变化来自实现还是环境。

## 平台发布的兼容性检查

平台发布前要同时检查能力 Schema、Policy、事件解析器和租户配置的兼容性。新版本可以增加可选字段，但不能让旧 Run 读取不到原来的终态；工具下线时保留历史定义，恢复任务才能解释已经发生的动作。兼容测试应覆盖新旧版本交叉读取，而不是只启动一个新容器。

租户灰度还要验证隔离：候选版本的缓存键、Trace 查询和对象存储前缀都必须包含租户范围。发现跨租户命中时立即撤回候选并冻结相关 Run，不能用清缓存或再次调用模型当作修复。

## 平台灰度 的边界案例

在“平台灰度”中，入口收到的资料可能不完整，程序先保存缺口和当前版本，不能让模型用常识填入 能力目录、Policy、租户配额、审批和评测版本。“平台灰度”的输入后来补齐时，新的执行沿同一个任务 ID 继续；已经结束的失败记录不被覆盖。

版本撤回要保存撤回原因和仍在运行的 Run，租户隔离失败要记录租户、策略和访问来源，紧急停止要保留最后一个 Checkpoint。未创建、调用失败、结果为空、终态未知分别处理，恢复不能重新启用已撤回能力。

“平台灰度”的正常输出先经过范围、版本和权限检查，再进入交付或下一个节点。只对新任务启用新版本，旧任务继续使用快照。“平台灰度”的输出只满足结构而没有可验证来源时，状态保持为候选，前端应显示缺口而不是成功标记。

用重复提交、并发完成、取消和进程退出四个样本回归。回归“平台灰度”时，检查同一幂等键是否只产生一个有效终态，迟到事件是否被拒绝，临时资源是否释放，重新连接是否能读到同一份事件。

这组检查的结果应带命令、解释器或服务版本、输入摘要和退出码。“平台灰度”没有运行证据时，只能写“待验证”；离线替身通过也不能推导真实模型、网络服务或生产权限已经通过。
