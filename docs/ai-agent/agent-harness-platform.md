# Agent Harness 怎样成为可治理的平台

一个团队把“读取知识库”做成了新工具，准备只给两个租户试用。工具能否上线，取决于模型回答得好不好，也取决于它是否只读当前租户的数据、失败时能否撤回、升级后旧 Run 是否仍能恢复。单个 Harness 能守住一次执行，平台还要守住能力版本和发布范围。

本文沿一次新工具灰度发布展开。目标是把多个产品共享的 Harness 组织成控制面：能力可注册，策略可审查，租户可分批启用，Run 可回放，失败可回滚。平台不抹平供应商差异，也不把平均质量指标当成安全证明。

::: info 贯穿案例

工具 capability=kb.read.v2 只允许读取租户自己的知识库。候选版本先在隔离租户回放，再开放给 5% 的内部租户。任何越权、版本不兼容或质量门禁失败都必须停止扩散。

:::

## 从一次 Run 到共享控制面

上一篇的 Harness 解决一次 Run 的身份、动作和终态。平台化之后，多个产品会同时提交 Run，能力由不同团队维护，模型和执行环境也会变化。若每个产品自己解释策略，平台就无法回答“这次动作依据哪个版本被允许”。

平台控制面至少要拥有三类稳定对象：

| 对象 | 记录什么 | 谁能修改 |
| --- | --- | --- |
| Capability | 名称、Schema、风险、依赖和适配器能力 | 能力维护者 |
| Policy | 身份、租户范围、预算、审批和版本 | 平台治理者 |
| Release | 候选组合、灰度范围、开始和撤回时间 | 发布控制器 |

Run 只引用不可变版本。运行时读取 active Release，选择匹配租户的 Policy，再把 Capability 版本写进执行事件。后来修改配置不会改变已经开始的 Run，恢复时也能重新获得同一组约束。

## 能力目录需要表达“能做什么”和“不能做什么”

注册一个工具不能只填名称和函数。平台应要求维护者声明：

~~~json
{
  "capability": "kb.read.v2",
  "input_schema": {
    "query": "string",
    "scope": "tenant-scoped"
  },
  "effects": ["read"],
  "risk": "low",
  "adapter": ["http-2026-01", "local-3"],
  "rollback": "disable-release"
}
~~~

Schema 描述参数形状，scope 描述允许读取的范围，effects 描述副作用，adapter 列表说明已验证的协议能力。rollback 只表示平台可以撤回入口，不能假设外部系统已经撤销了已发生的写操作。

能力版本升级时要建立兼容矩阵。新增可选字段可以保持旧调用，改变结果语义、权限范围或错误分类则必须创建新版本。平台不应根据模型试探调用来判断适配器是否支持某项能力。

## 策略版本决定谁能看到候选能力

Policy 把身份、租户、环境、模型、预算和审批条件固定下来。案例中的 5% 灰度不能由模型决定，也不能只在前端隐藏按钮。Runtime 在执行前检查租户是否属于当前 Release，Harness 在工具调用前再次检查 scope 和 capability version。

策略决策需要稳定原因码：

~~~json
{
  "policy_version": "policy-18",
  "tenant": "tenant-07",
  "capability": "kb.read.v2",
  "decision": "allow",
  "reason_codes": ["internal_canary", "tenant_scope_match"]
}
~~~

用户能看到的是解释文案，审计和回滚依赖的是版本与原因码。策略变更后，新 Run 读取新版本，旧 Run 继续使用启动时的快照，除非安全控制明确要求撤销。

## 灰度发布要以证据推进

发布控制器按阶段推进 Release：

1. 在隔离租户运行固定回放，确认 Schema、权限和终态。
2. 对内部租户开放，比较新旧能力的错误、延迟和引用覆盖。
3. 扩大到小比例租户，监控越权拒绝、超时、空结果和成本。
4. 达到门禁后切为 active；任一硬门禁失败就撤回候选。

门禁分成两层。安全门禁包括越权调用次数为零、旧策略不能继续授权和撤回后新 Run 不再拿到能力。质量门禁包括证据覆盖、拒答正确性、终态一致性和资源清理。平均回答分数不能覆盖一条越权记录。

## Run Artifact 让平台可以回放

平台需要保存可定位的 Run Artifact，而不是把所有 Prompt 写进日志。最小材料包括：

- Run、租户、身份和策略版本。
- Capability、适配器和模型版本。
- Context 计划、工具调用 ID、状态修订和事件序号。
- 结果摘要、验证结果、失败原因和资源清理状态。

原始文档、用户隐私和凭证留在受控存储，指标只使用稳定 ID 和脱敏分类。Artifact 的保留期限与租户策略绑定，撤回能力时同时使派生缓存失效，避免旧证据继续出现在新 Run。

## 适配器兼容性要显式验证

平台统一的是控制合同，供应商的停止原因、并行工具、取消和 usage 仍可能不同。适配器应提供能力矩阵，并以真实协议样本做契约测试：

~~~text
adapter -> normalize -> preserve(provider_stop_reason, usage, tool_call_id)
~~~

规范化只改变字段位置和错误模型，不得把 cancelled 映射成 completed，也不能丢弃原始停止原因。缺少某项能力时，路由器应选择已声明支持的路径，不能发送一次可能产生副作用的探测请求。

## 失败传播和回滚要先设计

当灰度工具越权时，平台先冻结 Release，再拒绝新 Run，保留旧能力版本供回滚。已经开始的 Run 按策略决定完成、取消或隔离，不能让撤回动作覆盖已提交的外部副作用。

每个失败都要指向责任边界：

| 失败 | 平台动作 | 不能做的事 |
| --- | --- | --- |
| Schema 不兼容 | 阻止发布，要求新能力版本 | 运行时猜字段 |
| 租户范围错误 | 拒绝候选并报警 | 依赖模型自我约束 |
| 质量门禁下降 | 停止扩散，保留旧 Release | 用平均值掩盖长尾 |
| 适配器丢失停止原因 | 下线适配器 | 把未知状态当成功 |
| 已有 Run 需要恢复 | 按启动快照恢复 | 自动切到未审查版本 |

回滚本身也要记录版本、时间、触发原因和影响范围。回滚只撤回能力入口，外部系统的补偿动作由对应业务服务负责。

## 评测和观测要按版本、租户切片

平台级指标至少分为执行健康、控制安全和结果质量三组。每组按 Capability、Policy、Model、租户和 Release 切片，避免新旧版本混在总平均值里。

评测集要覆盖同一问题的不同表达、越权范围、过期版本、工具超时、客户端断线和重复提交。报告保留失败样本的事件序列与状态差异，不能只输出一个分数。

### 交互式平台还要保留人工介入点

风险较高的写操作、跨租户访问和长时间任务需要人工审批或暂停。审批事件应绑定 Run、动作签名、策略版本和有效期，过期后重新评估。人工点击“通过”也不能跳过后置测试和业务验收。

## 平台发布的最小测试矩阵

能力契约测试检查 Schema、错误分类、停止原因和回执字段。策略测试覆盖允许、拒绝、撤回、租户切换和版本并发。灰度测试确认比例变化只影响新 Run，旧 Run 保持原快照。

故障注入包括适配器超时、事件重复、策略缓存过期、回滚期间客户端重连和外部系统部分成功。每个测试都检查副作用次数、事件序号、Artifact 保留和资源清理。

平台要通过这些测试，才有资格承诺“可治理”。治理不是多一层配置页面，而是每个候选动作都能追溯到版本、范围、证据和终态。

## 从平台治理回到产品交付

新工具经过注册、兼容验证、隔离回放、灰度和门禁后，才能进入 active Release。一次 Run 仍然沿上一篇定义的命令、事件和终态运行，平台只提供更稳定的策略和回滚边界。

当能力越来越多，下一项难题是如何让运行时在截止时间、预算和取消信号下继续推进，并把阶段状态交给后台 Worker。接下来应阅读 [Agent Runtime 的领域模型与状态归属](/docs/ai-agent/agent-runtime-domain-model)。
