# Skill 怎样按需加载任务知识

同一个 Agent 可以审代码、处理 PDF 或发布服务。工具没有变化，任务步骤、判断标准和需要查阅的资料却差很多。把所有工作方法常驻在系统提示中，输入会越来越长，互不相关的规则还会彼此干扰。

**Agent Skill** 把一类任务的说明、脚本、参考资料和模板放进独立目录。运行时先暴露名称与描述，匹配任务后读取 `SKILL.md`，更大的参考文件继续按需加载。这种 **Progressive Disclosure（渐进式披露）** 把上下文成本和任务知识的规模拆开。

## Skill 保存任务知识

Skill 可以说明如何审查技术事实、什么时候运行测试、证据不足时怎样停止。它不会增加模型本身的能力，也不会因为文档里写了“只读”就获得系统权限。

| 对象 | 回答的问题 |
| --- | --- |
| Prompt | 本轮怎样向模型表达任务 |
| Tool | Agent 能执行什么动作 |
| MCP | 外部能力怎样发现和连接 |
| Skill | 一类任务应该按什么方法完成 |
| Runtime | 谁授权、执行、保存状态和验收 |

Skill 可以引用 Tool 和 MCP，但最终动作仍通过运行时。脚本放进 Skill 目录也不会自动获得执行许可，调用时照常经过沙箱、参数和审批检查。
## 三层披露控制上下文

第一层是目录元数据，通常只有名称和描述，用于触发判断。第二层是完整 `SKILL.md`，包含工作流、边界和资源路由。第三层是脚本、模板和参考资料，只在当前步骤需要时读取。

```text
source-grounded-review/
├── SKILL.md
├── scripts/
│   └── check-citations.py
├── references/
│   ├── evidence-rules.md
│   └── output-contract.md
└── assets/
    └── report-template.md
```

如果第二层又内嵌全部参考资料，目录拆分就失去意义。`SKILL.md` 应告诉 Agent 哪种现象对应哪个文件，不能只写“阅读 references 目录”。
## 描述负责触发，正文负责执行

描述需要同时写清适用任务和排除项。过宽的“帮助处理文档”会在任何 Markdown 任务中触发，过窄的关键词列表又会漏掉同义表达。更稳的描述包含任务目标、输入形态和边界，例如：“审查带引用的技术文章，核对断言与来源；不用于普通文案润色。”

正文从结果契约开始：完成后交付什么，什么条件算通过，需要哪些证据。随后写执行顺序、失败处理和资源路由。版本、凭证和内部地址不应硬编码进公开 Skill。

## 脚本适合确定性步骤

格式检查、Schema 验证、哈希计算和固定转换适合脚本。模型负责判断哪些步骤需要执行，脚本提供可重复结果。脚本参数必须有边界，默认只读，并把结构化错误返回给运行时。

不要把任意 shell 片段放进文档后让模型直接拼接。Skill 只能引用受版本控制的脚本，运行时限制工作目录、环境变量、网络和资源。需要写入或发布的脚本继续走审批。
## 资料按问题路由

一个 SEO Skill 可以把抓取、索引、页面、追踪和广告拆成不同参考文件。任务只涉及 Canonical 时，读取页面与抓取规则即可，不需要把完整 SEM 课程放进上下文。

路由说明应具体：

```text
发现未收录问题：读取 crawl-index.md
检查页面标题与 Canonical：读取 on-page.md
涉及 GA4 请求：读取 analytics-evidence.md
```

引用链不宜太深。`SKILL.md` 指向一个索引，索引再指向十几个目录，会让 Agent 花大量调用寻找规则，也难以判断是否读全。
## 版本与冲突要有确定规则

Skill 由多个来源安装时，可能出现同名和不同版本。运行时应使用稳定 ID 和明确优先级，记录本轮加载的版本。项目规则、用户明确要求和 Skill 建议发生冲突时，优先级由 Host 定义，不能让模型按措辞强弱自行选择。

更新 Skill 时同时更新测试语料。新增触发词可能造成误触发，删除步骤可能改变安全边界，脚本升级还要检查参数兼容。正在运行的 Turn 固定旧版本，下一次执行才使用新版本，最容易回放。
## 怎样评测触发和执行

Skill 评测分为两部分。触发评测使用正例、近邻反例和含糊表达，检查该触发时是否触发，不该触发时是否保持安静。执行评测固定输入和工具替身，检查文件读取顺序、脚本参数、失败终止和输出合同。

不要只用 Skill 标题里的关键词做正例。真实用户可能说“这篇文章的引用对不上”，而没有说“证据审查”。近邻反例也很重要，例如“帮我润色一篇带链接的文章”未必需要验证所有来源。

上线后记录触发理由、加载文件和结果状态，避免保存敏感正文。误触发率、漏触发率、额外 Token 和任务通过率要一起看，单纯减少常驻 Token 不能证明任务质量提高。
## Multi-Agent 中谁加载 Skill

父 Agent 可以只读取目录元数据，在分配子任务时把稳定 Skill ID 写进任务契约。子 Agent 再加载完整说明和必要资源，这样父上下文不会承载所有专业规则。

子 Agent 不能凭 Skill 请求扩大工具目录。父任务给出的资料范围、工具和 Deadline 仍然有效；Skill 若需要额外权限，应返回缺口，由父运行时决定是否重新授权。
## 哪些内容不适合做 Skill

频繁变化的业务状态应放在数据库或 API，安全策略应进入确定性策略层，简单的一句格式要求直接写在当前 Prompt，公共领域事实更适合检索。Skill 适合可复用、步骤较稳定、需要配套资源的任务方法。

判断标准可以很务实：规则短到十几行且每次都需要，就常驻；只在某类任务出现且包含多步方法，就做 Skill；内容需要实时授权查询，就交给工具。这样分层后，上下文里只留下当前任务真正会用到的知识。
