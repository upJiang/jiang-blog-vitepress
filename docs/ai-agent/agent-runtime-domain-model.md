# Agent Runtime 的领域模型与状态归属

区分 Conversation、Turn、Message、Event、Task、Release 和 Policy 的生命周期与所有者。**Runtime**、**Turn**、**Domain Model** 分别指向同一条执行链上的不同对象：用户请求、幂等键、身份范围、知识 Release、Policy、截止时间和执行资源进入系统，各实体 ID、所有者、生命周期、关联键、版本快照、终态和审计时间保存处理中间状态，最终得到有序事件、最终答案、失败原因、取消确认、可恢复检查点和审计轨迹。

Agent Runtime 的领域模型与状态归属位于 API 请求之外负责长期状态、异步执行、控制信号和结果交付的运行时层，主要机制是 Conversation 管长期会话容器，Turn 管一次目标与终态，Message 管有序交流，Event 管状态变化，Task 管异步执行，Release 与 Policy 固定事实和行为版本。把 HTTP request 当 Turn、Message 同时当事件、Task 结果覆盖 Turn、版本只存当前指针和实体没有明确所有者会让链路在不同位置停止，错误记录必须保留发生阶段、当时的状态和终止原因。

::: info 贯穿示例

Agent Runtime 的领域模型与状态归属场景：一个研究型回答需要运行数分钟，期间用户断开连接、重新打开页面，并在第二次连接中请求取消。Agent Runtime 的领域模型与状态归属需要的身份、权限、版本和业务事实由应用提供，模型与外部内容只产生候选。

:::

这次推演用幂等键、状态版本、Lease、Event 序号、Checkpoint 和终止原因把请求和终态关联起来。与聊天会话、作业系统、事件溯源、状态机和工作流实例比较时，重点看输入来源、状态所有者、下一步的决策者和失败终点。

Agent Runtime 的领域模型与状态归属的执行顺序是“创建 Turn → 领取执行权 → 推进状态 → 写入事件或检查点 → 形成终态”。用户请求从入口进入，各实体 ID 记录进度，有序事件通过当前主题的校验条件后才会交付。

把 HTTP request 当 Turn 与 Message 同时当事件会产生不同证据。前者先检查各实体 ID 和输入来源，后者沿调用记录定位依赖或状态冲突；不区分发生位置，重试会掩盖原始原因。

Agent Runtime 的领域模型与状态归属与聊天会话的共同点不代表它们可以互换。当前主题拥有所有者，相邻组件只通过契约读取或提交候选，不能直接修改这个状态。

Agent Runtime 的领域模型与状态归属的架构图要标出组件职责、各实体 ID 的唯一所有者、幂等键经过的接口，以及把 HTTP request 当 Turn 怎样传播。架构取舍需要说明新增状态和恢复成本，只列组件名称无法用于故障定位。

## 长任务为什么需要独立运行时

区分 Conversation、Turn、Message、Event、Task、Release 和 Policy 的生命周期与所有者。在“Agent Runtime 的领域模型与状态归属场景：一个研究型回答需要运行数分钟，期间用户断开连接、重新打开页面，并在第二次连接中请求取消”这类任务里，Agent Runtime 的领域模型与状态归属负责把用户请求带入处理链，并明确有序事件可以交付的条件。

Agent Runtime 的领域模型与状态归属位于 API 请求之外负责长期状态、异步执行、控制信号和结果交付的运行时层。它处理 Conversation 管长期会话容器，Turn 管一次目标与终态，Message 管有序交流，Event 管状态变化，Task 管异步执行，Release 与 Policy 固定事实和行为版本，身份认证、授权结果和最终业务状态仍由应用中的确定性组件负责。

用户请求是这条链路的起点；来源缺失时，程序只能拒绝请求或采用明确记录的默认值，模型补出的字段不能继续驱动领取执行权。

把 HTTP request 当 Turn 会破坏各实体 ID 与有序事件之间的对应关系，排查时先保留原始输入摘要和发生阶段，再判断是否允许重试。

Message 同时当事件影响所有者或下游解释，不能和把 HTTP request 当 Turn 共用“重新调用一次模型”的处理方式。

Agent Runtime 的领域模型与状态归属完成时至少留下各实体 ID、所有者、有序事件和检查结论；只有最终文字，无法证明结果来自本次请求。

各实体 ID 在单进程 Demo 中可以留在内存，跨进程、带权限或有副作用的任务则要持久化输入、状态转移和停止原因，不能依赖 Prompt 保存状态。

Agent Runtime 的领域模型与状态归属还要把业务条件写成状态条件：身份范围何时就绪，有序事件何时允许交付，把 HTTP request 当 Turn 发生后是否还能继续。

Agent Runtime 的领域模型与状态归属对外区分完成、部分完成和无法确认，三个状态若都包装成有序事件，上层界面无法采用不同处理方式。

## Agent Runtime 的领域模型与状态归属在执行链中的位置

Agent Runtime 的领域模型与状态归属接收用户请求、幂等键、身份范围、知识 Release、Policy、截止时间和执行资源，向下游交付有序事件、最终答案、失败原因、取消确认、可恢复检查点和审计轨迹，输入与输出之间用明确契约连接，调用方不能把一句含糊目标直接交给底层适配器。

Runtime 拥有 Turn 和状态机，Worker 只在有效 Lease 内推进一次状态修订。因此各实体 ID 与所有者要有唯一写入方，其他组件只能通过版本化命令申请修改。

聊天会话与 Agent Runtime 的领域模型与状态归属解决的问题相邻，但控制权不同，比较时要看谁选择推进状态、谁保存各实体 ID、谁确认有序事件。

作业系统可以参与同一请求，却不能替代 Agent Runtime 的领域模型与状态归属；组合后仍要单独检查幂等键的可信来源和把 HTTP request 当 Turn 的终止规则。

生命周期若只保存在 SDK 对象里，重试或进程退出后就失去解释依据；需要恢复或审计的字段进入持久层，体积较大的有序事件只保存稳定引用。

Agent Runtime 的领域模型与状态归属使用的身份、范围和版本来自可信运行时，用户请求可以表达意图，但不能提升权限或改写活动 Release。

Message 同时当事件发生时，错误回到所有者的所有者处理，上游缺输入、当前组件违反不变量和下游不可用分别形成不同终态。

Agent Runtime 的领域模型与状态归属的确定性边界位于各实体 ID 写入之前。模型可以建议值，应用核对来源和当前版本；涉及权限、金额、发布或不可逆动作时，再进入策略或人工批准。

Agent Runtime 的领域模型与状态归属内部可以使用更细的临时对象，跨边界只暴露稳定协议。替换聊天会话时，调用方不需要理解内部缓存和 SDK 响应。

## 领域状态与唯一所有者

Agent Runtime 的领域模型与状态归属的输入合同至少列出用户请求、幂等键和身份范围，每项都注明来源、是否必需、允许的缺省值，以及缺失后是在入口拒绝还是进入降级路径。

状态合同中的各实体 ID 表示当前进度，所有者保存本次执行依赖的快照，生命周期关联前后动作，三者不能合并成一段自由文本。

并发分支按稳定身份合并生命周期，完成顺序只反映耗时，不能决定结果属于哪个请求，更不能让迟到的旧状态覆盖新修订。

输出合同同时描述有序事件和最终答案，并为拒绝、取消、部分完成和未知状态提供固定形状，调用方据此分支，无需解析错误文案猜测结果。

所有者参与乐观并发检查；处理开始后若版本变化，旧候选只保留作审计，不能继续写入各实体 ID。

用户请求里若包含模型填写的同名字段，应用会丢弃它，再从认证、配置或活动版本中补入可信值，因为结构校验通过不等于授权或业务校验通过。

幂等键、状态版本、Lease、Event 序号、Checkpoint 和终止原因组成 Agent Runtime 的领域模型与状态归属的最小追踪材料，日志只保存稳定 ID、版本和错误类，完整 Prompt、文档正文与凭证不进入指标标签。

撤回或删除幂等键时，相关缓存、候选和未完成任务按版本失效；稳定 ID 可以保留审计关系，已撤回内容不能继续进入有序事件。

契约还需要描述新鲜度。所有者对应的数据发生变化后，旧缓存、旧候选和未完成任务怎样失效，应由版本或时间规则直接判断，不能依赖模型注意到矛盾。

删除和撤回也属于数据生命周期。Agent Runtime 的领域模型与状态归属引用的原始对象被移除时，稳定 ID 可以保留审计关系，正文与派生结果则按策略失效，避免继续向用户展示过期内容。

有序事件通过结构校验后仍是候选。Agent Runtime 的领域模型与状态归属使用的身份、权限、知识版本与业务事实由应用从可信服务读取，核对完成后才能执行或交付。

## API、Worker 与存储怎样协作

Agent Runtime 的领域模型与状态归属按“Conversation 管长期会话容器，Turn 管一次目标与终态，Message 管有序交流，Event 管状态变化，Task 管异步执行，Release 与 Policy 固定事实和行为版本”推进，这段机制必须落成各实体 ID 和所有者的实际变化，不能只列框架节点名称。

创建 Turn 接收用户请求并建立各实体 ID，入口校验未通过就地结束，后续模型、检索器或工具调用次数保持为零。

领取执行权固定身份、范围、配置版本和绝对 Deadline，后续子步骤只继承剩余时间，不能各自重新获得完整超时。

推进状态读取所有者并执行主题逻辑，参数由应用组装，外部返回先保存为最终答案，尚未获得修改领域状态的资格。

写入事件或检查点检查结构、范围、版本和主题不变量；有序事件缺少来源、落在旧版本或越过权限时，各实体 ID 停在 rejected 或 failed。

形成终态先保存有序事件与终止原因，再产生事件或通知，交付失败可以重放，核心状态写入失败则不能对外宣称完成。

推进状态出现部分结果时，由任务合同决定保留、补偿还是整体丢弃；有序事件若可重建就重新生成，外部副作用则查询回执或执行补偿。

实现可以使用函数、Graph、Middleware 或 Workflow，各实体 ID 的所有权和把 HTTP request 当 Turn 的停止规则不会随框架改变。

部分成功需要在步骤边界处理。推进状态已经产生一部分有序事件时，程序按任务合同决定保留、补偿或整体丢弃，并记录未完成项，不能默认为全部成功。

推进状态和写入事件或检查点都要写明逆向动作或不可逆原因，有序事件若可重建就删除后重算，已发送的外部命令只能查询回执或补偿。

## 沿断线和取消推演一个 Turn

沿“Agent Runtime 的领域模型与状态归属场景：一个研究型回答需要运行数分钟，期间用户断开连接、重新打开页面，并在第二次连接中请求取消”推演 Agent Runtime 的领域模型与状态归属：入口创建 request_id，读取可信身份，把用户请求和当前版本写入初始状态。

创建 Turn 生成各实体 ID 与输入摘要；若幂等键缺失，请求返回 rejected，并指出缺少哪项材料，不继续消耗模型或外部服务配额。

领取执行权冻结 scope、release、policy 和 deadline_at，用户或模型在正文中提供的同名值只作为普通内容，不能覆盖这份运行时快照。

推进状态按“Conversation 管长期会话容器，Turn 管一次目标与终态，Message 管有序交流，Event 管状态变化，Task 管异步执行，Release 与 Policy 固定事实和行为版本”推进，每次依赖调用保存 call_id、参数摘要、开始时间与状态版本，以便判断超时前是否已经产生结果。

候选结果对应有序事件、最终答案、失败原因、取消确认、可恢复检查点和审计轨迹，写入事件或检查点逐项检查权限、版本与领域约束，问题列表为空才允许形成下一状态。

形成终态写入终态；客户端断开只影响交付通道，重新连接时读取已经保存的各实体 ID 或事件游标，不重跑核心逻辑。

故障注入选择 Task 结果覆盖 Turn，程序保留原候选和错误位置，只重做失败边界，不能从入口复制整个任务并产生第二份状态。

推演结束后用 request_id 关联各实体 ID、有序事件与终止原因，测试据此排除并发请求串线，并确认失败路径没有遗留未关闭资源。

Agent Runtime 的领域模型与状态归属在输入拒绝时不调用依赖，正常路径按 5 个阶段推进，有限修复只重做失败边界。调用次数是控制流断言，不是性能宣传。

Agent Runtime 的领域模型与状态归属的最终记录用 request_id 关联各实体 ID、有序事件和失败问题，测试据此证明结果来自本次执行，没有混入并发请求。

## 终态、事件和恢复证据

Agent Runtime 的领域模型与状态归属正常完成时，各实体 ID、所有者和有序事件指向同一次执行，重复读取返回同一终态，未完成分支已经取消或有明确所有者。

幂等键、状态版本、Lease、Event 序号、Checkpoint 和终止原因用于还原 Agent Runtime 的领域模型与状态归属的处理过程，可以按阶段和版本聚合；敏感正文留在受控存储中，不复制到日志与指标。

最终答案可能是合法的空结果，但必须带范围、版本和原因；任务明确要求找到材料时，同一个空结果进入拒答而非成功。

依赖返回成功状态只证明传输完成。Agent Runtime 的领域模型与状态归属还要检查有序事件是否满足业务范围、质量阈值和当前版本，明确拒绝也可能是正确终态。

推进状态并发完成时，每个分支保留自己的身份和局部预算，写入事件或检查点按任务合同接纳可用结果，慢分支不能抹掉已经确认的记录。

各实体 ID 的状态迁移必须单调：完成不能退回运行中，取消不能被迟到结果覆盖，失败重试也不能绕过入口已经固定的权限。

Agent Runtime 的领域模型与状态归属的成功证据最终要同时回答输入是什么、执行了哪些步骤、交付了什么以及为什么停止；任一项缺失都应留在未确认状态。

Agent Runtime 的领域模型与状态归属把业务验收与服务健康分开。依赖返回 200 只说明传输成功，有序事件仍要满足当前范围和质量要求；明确拒答也可能是正确终态。

Agent Runtime 的领域模型与状态归属的观测指标按阶段和版本聚合。错误率、空结果率、拒绝率、恢复次数与资源消耗回答不同问题，不能压成一个成功率。

## 重复投递、竞态与失联处理

Agent Runtime 的领域模型与状态归属按输入、状态、依赖、结果和交付五个位置分类错误，发生位置决定恢复动作，不能用同一个重试循环处理全部失败。

遇到把 HTTP request 当 Turn 时，系统要返回稳定的错误类型、发生阶段和可重试标记。Agent Runtime 的领域模型与状态归属保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

遇到 Message 同时当事件时，系统要返回稳定的错误类型、发生阶段和可重试标记。Agent Runtime 的领域模型与状态归属保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

Agent Runtime 的领域模型与状态归属发现 Task 结果覆盖 Turn 后重新读取权威状态，旧候选可以保留作审计，却不能覆盖新版本；前后状态无法兼容时，当前尝试以 conflict 结束。

Agent Runtime 的领域模型与状态归属发现版本只存当前指针后重新读取权威状态，旧候选可以保留作审计，却不能覆盖新版本；前后状态无法兼容时，当前尝试以 conflict 结束。

遇到实体没有明确所有者时，系统要返回稳定的错误类型、发生阶段和可重试标记。Agent Runtime 的领域模型与状态归属保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

Agent Runtime 的领域模型与状态归属结束错误处理时保存终态、可重试性和资源清理结果，后台扫描器依靠各实体 ID 和这些字段区分仍在运行、等待恢复和已经失败的任务。

Agent Runtime 的领域模型与状态归属在执行前写入绝对 Deadline、最大动作数、重复签名、无进展阈值、预算和人工取消信号，任一条件触发后推进状态都不再创建新工作。

Agent Runtime 的领域模型与状态归属把重试时间和次数计入总预算。依赖连续失败会减少后续额度，达到上限后保留原始错误，不再用模型重新措辞掩盖失败。

Agent Runtime 的领域模型与状态归属的清理动作可以重复执行。临时对象、文件句柄、子进程、连接或 Lease 仍被活动任务引用时，清理器必须拒绝删除。

## 崩溃注入和并发测试

模拟重复提交、进程崩溃、断线重连和过期租约，断言只有一个逻辑 Turn、事件序号连续且副作用幂等；测试显式给出用户请求、初始各实体 ID、预期有序事件和终止原因，不能只断言返回值非空。

Agent Runtime 的领域模型与状态归属的单元测试用 Fake Adapter 固定有序事件与错误，断言参数、调用顺序、状态修订和清理动作，这些结果只证明本地控制逻辑。

契约测试围绕用户请求、各实体 ID 和最终答案构造合法与非法样本，Schema 解析成功后继续检查权限、版本与领域不变量。

故障测试注入把 HTTP request 当 Turn 和 Message 同时当事件，记录推进状态是否被调用、各实体 ID 是否改变、资源是否释放，以及同一身份重试会不会重复执行。

在推进状态前后终止进程可以检查恢复边界：调用前退出允许重新领取，外部动作后退出先查回执，形成终态完成后只重放交付。

Agent Runtime 的领域模型与状态归属的集成测试连接真实协议与隔离存储，检查序列化、约束、并发和超时；需要在线服务时另行记录服务版本、时间、配置与凭证条件。

Agent Runtime 的领域模型与状态归属的回归报告要保留失败类型分布。明确拒绝变成超时、权限错误变成普通空结果，都属于行为回归，即使总通过数没有变化。

Agent Runtime 的领域模型与状态归属的性质测试随机改变各实体 ID 顺序、重复提交、完成顺序或状态版本，断言权限不扩大、终态不倒退、同一身份不产生两次副作用。

离线评测关注固定输入下的质量变化，运行时测试关注控制和恢复。Agent Runtime 的领域模型与状态归属只有两类证据都存在，才能同时回答“结果是否合格”和“系统是否安全完成”。

## 容量、Lease 与版本演进

Agent Runtime 的领域模型与状态归属长期运行后，输入 Schema、各实体 ID 结构和依赖配置可能独立升级，每次执行固定一组版本，旧记录才能被正确读取或迁移。

Agent Runtime 的领域模型与状态归属的容量主要受队列积压、Worker 并发、租约时长、事件吞吐和恢复扫描影响，并发可能缩短单次等待，也会占用连接、配额、内存和下游吞吐，必须沿创建 Turn、领取执行权、推进状态、写入事件或检查点、形成终态逐层核算。

Agent Runtime 的领域模型与状态归属的候选版本在固定样本上比较正确性、错误类型、延迟和资源消耗，把 HTTP request 当 Turn 等安全红线回归时直接停止发布，不能用平均质量抵消。

把 HTTP request 当 Turn 的降级路径在发布前写好，可以减少非关键增强、返回已经确认的有序事件，或明确暂时无法确认，缺失事实不能交给模型补写。

Agent Runtime 的领域模型与状态归属的运行手册从 request_id 定位幂等键、状态版本、Lease、Event 序号、Checkpoint 和终止原因，再决定重试、补偿、取消或回滚，无需先展开完整的用户请求。

Agent Runtime 的领域模型与状态归属的数据按证据用途分级保留，聚合字段可以留得更久，用户请求和大体积有序事件设置短期限、访问控制与删除通道。

Agent Runtime 的领域模型与状态归属先在单进程实现各实体 ID、超时、错误和测试，只有恢复与容量证据提出要求时，再增加队列、Lease、分布式缓存或工作流引擎。

Agent Runtime 的领域模型与状态归属的监控阈值要对应可执行动作。队列积压、Worker 并发、租约时长、事件吞吐和恢复扫描中的某项接近上限时，系统可以限流、排队、缩小候选或切换保守路径；只发送告警不会保护正在运行的任务。

回滚要覆盖代码之外的状态。Agent Runtime 的领域模型与状态归属若改变 Schema、缓存键或持久化记录，旧版本是否还能读取新写入数据必须提前验证；无法双向兼容时采用候选版本隔离。

## 何时需要队列或工作流引擎

采用 Agent Runtime 的领域模型与状态归属前先画出用户请求到有序事件的最小控制图；固定函数已经能完成任务时，新增模型决策和跨进程各实体 ID 只会扩大测试与运维范围。

Agent Runtime 的领域模型与状态归属与聊天会话的差别落在控制权：谁选择下一步，谁保存各实体 ID，谁确认有序事件可信。

作业系统可以与 Agent Runtime 的领域模型与状态归属组合，但外部知识仍需授权，工具调用仍需校验，模型产生的有序事件仍停留在候选状态。

Agent Runtime 的领域模型与状态归属适合价值足够、把 HTTP request 当 Turn 可观察且预算可接受的任务，高风险、不可逆的决定需要确定性规则或人工批准。

格式正确但事实错误的有序事件是必要反例；若它直接进入成功，说明写入事件或检查点缺少业务验证，应保留候选并给出证据问题。

执行期间修改所有者可以检验并发设计，旧动作若仍能覆盖各实体 ID，说明版本或 Lease 有缺口，增加 Prompt 规则无法修复这类竞态。

Agent Runtime 的领域模型与状态归属增加了各实体 ID、依赖调用、恢复责任和故障面，设计记录既要说明获得的能力，也要列出新增的退出、降级与回滚路径。

Agent Runtime 的领域模型与状态归属从一个调用、一个各实体 ID、一组明确错误和几条确定性测试开始，真实 Trace 证明需要后再加入并发、缓存、队列或更复杂策略。

聊天会话只在能处理把 HTTP request 当 Turn 时引入，不为目录完整强行组合；接口保持可替换，后续需求出现再扩展。
