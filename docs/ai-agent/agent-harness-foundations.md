# Agent Harness 的职责与接口

**Agent Harness** 是承载一次交互式 Agent 执行的应用层。它把模型适配、工具目录、上下文装配、状态保存、权限检查、沙箱、事件和评测接在同一条可回放链路上。Harness 不替模型回答业务问题，也不替业务服务授予权限，它负责把候选动作变成可检查、可拒绝、可恢复的执行请求。

这篇文章只解决一个工程问题：当模型、浏览器、终端和知识服务都可能更换时，怎样仍然知道一次 Run 读到了什么、提出了什么、谁批准了动作，以及最终为什么停止。**Run**、**Model Session**、**Capability Registry** 和 **Workspace** 是不同对象，不能把它们拼成一段 Prompt 当作状态。

::: info 贯穿示例

编码助手需要读取仓库、修改一个文件并运行测试，但不能访问工作区之外的路径，也不能在测试失败时宣称完成。身份、权限、版本和业务事实由应用提供，模型与外部内容只产生候选。

:::

## Harness 先解决哪类组合问题

适配器泄漏供应商语义会破坏 run_id 与受控动作之间的对应关系，排查时先保留原始输入摘要和发生阶段，再判断是否允许重试。

工具权限散落影响 model session 或下游解释，不能和适配器泄漏供应商语义共用“重新调用一次模型”的处理方式。

## 五类接口怎样把候选动作接到执行器

Agent Harness 的 Harness 持有工作区、工具和权限，模型只能根据观察提出动作候选。因此 run_id 与 model session 要有唯一写入方，其他组件只能通过版本化命令申请修改。

Agent Framework 与 Harness解决的问题相邻，但控制权不同，比较时要看谁选择检查权限、谁保存 run_id、谁确认受控动作。

Runtime 可以参与同一请求，却不能替代 Harness；组合后仍要单独检查环境观察的可信来源和适配器泄漏供应商语义的终止规则。

Harness使用的身份、范围和版本来自可信运行时，用户目标可以表达意图，但不能提升权限或改写活动 Release。

工具权限散落发生时，错误回到 model session 的所有者处理，上游缺输入、当前组件违反不变量和下游不可用分别形成不同终态。

Harness 的确定性边界位于 run_id 写入之前。模型在 Agent Harness 中只提交候选值，程序仍要从认证、版本和策略快照补入可信字段。

Harness内部可以使用更细的临时对象，跨边界只暴露稳定协议。替换 Agent Framework 时，调用方不需要理解内部缓存和 SDK 响应。

## Run、会话与工作区版本怎样分工

Harness 的输入合同至少列出用户目标、环境观察和能力目录，每项都注明来源、是否必需、允许的缺省值，以及缺失后是在入口拒绝还是进入降级路径。

Harness 要把 `run_id`、模型会话、能力目录和工作区版本分开管理。Run 决定一次执行的生命周期，会话保存上下文连续性，能力目录决定可以提出哪些动作；权限或环境变化时，Harness 才能单独撤销其中一层。

并发分支按稳定身份合并 capability registry，完成顺序只反映耗时，不能决定结果属于哪个请求，更不能让迟到的旧状态覆盖新修订。

Agent Harness 的对外结果要分别表达可交付内容、缺口、取消和未知状态，调用方不必解析错误文案。

model session 参与乐观并发检查；处理开始后若版本变化，旧候选只保留作审计，不能继续写入 run_id。

观察版本、动作参数、审批、文件差异、进程结果、截图和测试输出组成 Harness 的最小追踪材料，日志只保存稳定 ID、版本和错误类，完整 Prompt、文档正文与凭证不进入指标标签。

契约还需要描述新鲜度。model session 对应的数据发生变化后，旧缓存、旧候选和未完成任务怎样失效，应由版本或时间规则直接判断，不能依赖模型注意到矛盾。

删除和撤回也属于数据生命周期。Harness引用的原始对象被移除时，稳定 ID 可以保留审计关系，正文与派生结果则按策略失效，避免继续向用户展示过期内容。

::: warning Harness 的可信边界

受控动作通过结构校验后仍是候选。Harness使用的身份、权限、知识版本与业务事实由应用从可信服务读取，核对完成后才能执行或交付。

:::

## 一次 Run 的事件顺序与终态

Harness 的最小实现应先创建一个 Run，再依次装配模型、工具、上下文、策略和沙箱，并为每次动作留下 Trace 与 Eval 结果。替换模型适配器后，Run 的权限和验证记录仍应保持相同，才能说明接口真的隔离了供应商差异。

观察环境接收用户目标并建立 run_id，入口校验未通过就地结束，后续模型、检索器或工具调用次数保持为零。

检查权限读取 model session 并执行主题逻辑，参数由应用组装，外部返回先保存为可审查差异，尚未获得修改领域状态的资格。

执行并重新观察检查结构、范围、版本和主题不变量；受控动作缺少来源、落在旧版本或越过权限时，run_id 停在 rejected 或 failed。

实现可以使用函数、Graph、Middleware 或 Workflow，run_id 的所有权和适配器泄漏供应商语义的停止规则不会随框架改变。

部分成功需要在步骤边界处理。

## 用一次仓库修改检查状态交接

沿“Harness场景：编码助手需要读取仓库、修改一个文件并运行测试，但不能访问工作区之外的路径，也不能在测试失败时宣称完成”推演 Harness：入口创建 request_id，读取可信身份，把用户目标和当前版本写入初始状态。

观察环境生成 run_id 与输入摘要；若环境观察缺失，请求返回 rejected，并指出缺少哪项材料，不继续消耗模型或外部服务配额。

检查权限按“Harness 提供统一 Model、Tool、Context、State、Policy、Sandbox、Trace 和 Eval 接口，具体供应商与执行环境通过适配器替换”推进，每次依赖调用保存 call_id、参数摘要、开始时间与状态版本，以便判断超时前是否已经产生结果。

运行确定性验证写入终态；客户端断开只影响交付通道，重新连接时读取已经保存的 run_id 或事件游标，不重跑核心逻辑。

故障注入选择状态只在 Prompt，程序保留原候选和错误位置，只重做失败边界，不能从入口复制整个任务并产生第二份状态。

推演结束后用 request_id 关联 run_id、受控动作与终止原因，测试据此排除并发请求串线，并确认失败路径没有遗留未关闭资源。

Harness在输入拒绝时不调用依赖，正常路径按 5 个阶段推进，有限修复只重做失败边界。调用次数是控制流断言，不是性能宣传。

Harness 的最终记录用 request_id 关联 run_id、受控动作和失败问题，测试据此证明结果来自本次执行，没有混入并发请求。

## 交付差异怎样获得确定性验证

Harness正常完成时，run_id、model session 和受控动作指向同一次执行，重复读取返回同一终态，未完成分支已经取消或有明确所有者。

观察版本、动作参数、审批、文件差异、进程结果、截图和测试输出用于还原 Harness 的处理过程，可以按阶段和版本聚合；敏感正文留在受控存储中，不复制到日志与指标。

依赖返回成功状态只证明传输完成。Harness还要检查受控动作是否满足业务范围、质量阈值和当前版本，明确拒绝也可能是正确终态。

run_id 的状态迁移必须单调：完成不能退回运行中，取消不能被迟到结果覆盖，失败重试也不能绕过入口已经固定的权限。

Harness 的成功证据最终要同时回答输入是什么、执行了哪些步骤、交付了什么以及为什么停止；任一项缺失都应留在未确认状态。

Harness把业务验收与服务健康分开。依赖对 Agent Harness 返回 200 只说明传输完成，内容仍要满足当前范围和质量条件。

Harness 的观测指标按阶段和版本聚合。评估 Agent Harness 时，把错误、空结果、拒绝、恢复和资源消耗分开统计，避免一个成功率掩盖不同故障。

## 过期观察和越界动作怎样被拒绝

Harness 的错误定位从观察开始：没有能力目录是初始化失败，动作越过工作区是策略拒绝，命令返回结果不完整是执行失败，差异没有经过测试则不能交付。每个阶段留下自己的回执，比让模型重新描述一次过程更可靠。

遇到适配器泄漏供应商语义时，先记录发生阶段、错误类别和责任对象。Harness保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

工具权限散落触及 Harness 的安全边界，重试不会使它自动合法；执行路径保存拒绝规则和输入来源，清除未授权候选，并以稳定错误结束当前动作。

遇到状态只在 Prompt 时，先记录发生阶段、错误类别和责任对象。Harness保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

沙箱不可替换触及 Harness 的安全边界，重试不会使它自动合法；执行路径保存拒绝规则和输入来源，清除未授权候选，并以稳定错误结束当前动作。

遇到测试只能走真实模型时，先记录发生阶段、错误类别和责任对象。Harness保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

遇到平台锁定时，先记录发生阶段、错误类别和责任对象。Harness保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

Harness将终态、可重试性和资源清理结果写入记录；后台扫描器根据 run_id 判断任务是在运行、等待恢复还是已失败。

Harness执行前固定 Deadline、动作上限、重复签名、无进展阈值、预算和取消信号；任一条件触发，检查权限停止创建新工作。

Harness把重试时间和次数计入总预算。Agent Harness 每次重试先扣减剩余额度，达到上限就保留原始错误。

Harness 的清理动作设计成幂等操作；仍被活动任务或 Lease 引用的资源拒绝删除。

## 用事件回放测试 Harness 契约

使用隔离工作区和假环境重放观察动作循环，断言越界动作被拒绝、写操作需要审批、验证失败不会标记完成；测试显式给出用户目标、初始 run_id、预期受控动作和终止原因，不能只断言返回值非空。

Harness 的单元测试用 Fake Adapter 固定受控动作与错误，断言参数、调用顺序、状态修订和清理动作，这些结果只证明本地控制逻辑。

契约测试围绕用户目标、run_id 和可审查差异构造合法与非法样本，Schema 解析成功后继续检查权限、版本与领域不变量。

故障测试注入适配器泄漏供应商语义和工具权限散落，记录检查权限是否被调用、run_id 是否改变、资源是否释放，以及同一身份重试会不会重复执行。

Harness 的集成测试连接真实协议与隔离存储，检查序列化、约束、并发和超时；需要在线服务时另行记录服务版本、时间、配置与凭证条件。

Harness 的回归报告要保留失败类型分布。在 Agent Harness 的回归中，拒绝、超时、权限错误和空结果必须保持各自类型，状态变化本身就是行为契约。

Harness 的性质测试随机改变 run_id 顺序、重复提交、完成顺序或状态版本，断言权限不扩大、终态不倒退、同一身份不产生两次副作用。

Agent Harness 的离线评测关注质量变化，运行时测试关注控制和恢复，两类证据都齐全才可交付。Harness只有两类证据都存在，才能同时回答“结果是否合格”和“系统是否安全完成”。

## 版本、容量和运行治理

Harness 要把 `ModelAdapter`、`ToolRegistry`、`Policy`、`StateStore` 和 `EventSink` 的协议版本写进 Run。替换适配器时，旧事件仍按原类型回放，不能让供应商字段直接改变状态迁移。

Harness 的容量主要受观察体积、工具调用、后台进程、浏览器会话、文件差异和循环步数影响，并发可能缩短单次等待，也会占用连接、配额、内存和下游吞吐，必须沿观察环境、提出动作、检查权限、执行并重新观察、运行确定性验证逐层核算。

Harness 的候选版本在固定样本上比较正确性、错误类型、延迟和资源消耗，适配器泄漏供应商语义等安全红线回归时直接停止发布，不能用平均质量抵消。

适配器泄漏供应商语义的降级路径在发布前写好，可以减少非关键增强、返回已经确认的受控动作，或明确暂时无法确认，缺失事实不能交给模型补写。

出现未知工具或迟到事件时，用 `request_id` 找 Run、事件序号、审批记录、工具回执和最后一个 Checkpoint，再决定拒绝、恢复还是人工接管。排查依赖事件，不需要重新解释用户目标。

Harness 的数据按证据用途分级保留，聚合字段可以留得更久，用户目标和大体积受控动作设置短期限、访问控制与删除通道。

Harness先在单进程实现 run_id、超时、错误和测试，只有恢复与容量证据提出要求时，再增加队列、Lease、分布式缓存或工作流引擎。

Harness 的监控阈值要对应可执行动作。Agent Harness 的分支、依赖、上下文和预算接近上限时，应限流或缩小候选；告警本身不会停止正在运行的任务。

回滚要覆盖代码之外的状态。Harness若改变 Schema、缓存键或持久化记录，旧版本是否还能读取新写入数据必须提前验证；无法双向兼容时采用候选版本隔离。

## Harness、Runtime 与 MCP 的边界

采用 Harness前先画出用户目标到受控动作的最小控制图；固定函数已经能完成任务时，新增模型决策和跨进程 run_id 只会扩大测试与运维范围。

框架提供模型循环和组件接口，Harness 负责把候选动作接到策略、状态和事件记录。模型可以提出下一步，Policy 决定能否执行，StateStore 保存事实，EventSink 让结果可回放。

Runtime 可以与 Harness组合，但外部知识仍需授权，工具调用仍需校验，模型产生的受控动作仍停留在候选状态。

Harness适合价值足够、适配器泄漏供应商语义可观察且预算可接受的任务，高风险、不可逆的决定需要确定性规则或人工批准。

执行期间修改 model session 可以检验并发设计，旧动作若仍能覆盖 run_id，说明版本或 Lease 有缺口，增加 Prompt 规则无法修复这类竞态。

Harness增加了 run_id、依赖调用、恢复责任和故障面，设计记录既要说明获得的能力，也要列出新增的退出、降级与回滚路径。

Harness 的价值在于把供应商差异收敛到适配器边界。上层只处理统一的 Message、Tool Call、Observation、Checkpoint 和 Trace；适配器负责把不同 SDK 的流式事件、错误和 usage 转换成内部类型。转换层必须保留原始请求 ID 和终止原因，否则出现供应商字段变化时只能重新猜测历史行为。

## 先定义 Harness 的最小协议

一个可测试的 Harness 至少需要五类接口。`ModelAdapter` 接收已经装配好的消息并返回候选事件，`ToolRegistry` 根据稳定名称查找工具，`Policy` 判断当前动作是否允许，`StateStore` 保存 Turn 和 Checkpoint，`EventSink` 记录可重放事件。接口之间传递内部类型，不把供应商 SDK 的对象直接暴露给业务代码。这样 Fake Adapter 可以在没有网络和密钥的情况下验证循环，在线适配器只负责协议转换。

一次执行从 `TurnStarted` 事件开始。Harness 读取版本快照和预算，向模型请求下一事件；收到文本就进入验证，收到 Tool Call 就通过注册表和策略校验，工具结果包装为 Observation 后再次调用模型。每一步都带 `attempt_id` 和 `parent_event_id`，恢复时从最后一个 Checkpoint 继续。模型返回未知事件、参数解析失败或流中断时，统一归一化为可重试或不可重试错误，不能把异常字符串交给上层猜测。

Harness 不拥有业务权限，也不决定某个工具能否访问租户数据。它只执行已经发布的策略和工具契约。把审批、ACL 或数据库写入藏在 Harness 内，会让不同产品共享一套不透明的副作用。高风险工具应要求外部审批事件，审批完成前只保存候选，不执行动作。

回归测试固定模型事件序列，覆盖正常回答、一次工具调用、连续两次调用、未知工具、超时、取消、重复事件和 Checkpoint 恢复。断言事件顺序、状态单调、工具调用次数和预算扣减。真实模型的选择倾向、延迟和费用另行测量，不能由 Harness 的单元测试代替。

迁移供应商时先回放同一组事件，再比较错误归一化、流式结束原因和 usage。若新适配器丢失原始请求 ID 或改变终态名称，先补兼容层，不要让业务代码同时认识两套协议。

适配器还要声明能力矩阵，例如是否支持流式、工具并行、取消和结构化输出。调用方先读取矩阵，不在运行中试探一个可能产生副作用的能力。

## Harness 契约的回放自测

用“一次读取文件、调用工具并验证结果的执行”回放时，Harness 先固定观察版本、工作区和执行预算。ModelAdapter、ToolRegistry、Policy、StateStore 和 EventSink由事件和 Checkpoint 保存，模型只能提出动作候选，策略层决定候选能否进入执行器。

正常路径是观察、候选、授权、动作、再观察和确定性验证。每次动作都带 `attempt_id`，输出包含退出码、差异或截图摘要。过期观察、未知工具或取消后的迟到事件要保留原始回执，不能让模型用一句“已完成”覆盖。

测试故意让观察过期、工具未知、命令超时和渠道断开。在“一次读取文件、调用工具并验证结果的执行”中，前两种在执行前拒绝，后两种要根据是否产生副作用决定重试或进入未知状态。恢复从最后一个 Checkpoint 开始，不重放已经确认的写动作。

“一次读取文件、调用工具并验证结果的执行”的离线 Fake Adapter 只验证接口和状态迁移，真实浏览器、终端或供应商还要做权限、资源和网络测试。候选动作没有通过策略就不执行。

“一次读取文件、调用工具并验证结果的执行”的取舍要写清：更大的观察窗口能减少重新读取，却会增加 Token 和敏感内容暴露；更长的自动循环能覆盖更多步骤，却提高失控和回滚成本。

“一次读取文件、调用工具并验证结果的执行”的回放报告保存策略版本、动作数量、失败阶段和清理结果，平台升级后再用同一组事件比较，才能判断变化来自实现还是环境。
