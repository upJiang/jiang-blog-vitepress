# Handoff 怎样移交任务、上下文与责任

研究型 Agent 已经把“核对当前发布策略”交给协议检索分支，检索分支却发现需要先确认活动版本。它不能只发一句“麻烦查一下最新版本”，因为接收方不知道“最新”属于哪个租户、哪个时间点，也不知道可以读取哪些资料、何时算完成。**Handoff** 解决的正是这种责任转移：一个执行单元把定义完整的任务交给另一个执行单元，接收方确认合同后承担执行责任，再按约定返回结果或失败原因。

Handoff 不等于普通函数调用。函数调用通常由调用者同步等待结果，调用关系和局部变量已经确定；Handoff 可能跨 Agent、进程和较长时间，发送方与接收方各自拥有状态，还可能共享工作区。它也不等于把聊天历史复制给另一个模型。聊天摘要可以成为一条 `context_ref`，却不能代替任务目标、权限、版本、Deadline 和返回条件。

::: info 贯穿示例

主 Agent 正在判断一条访问策略是否仍然有效。它把“确认活动 Release，并返回可定位证据”交给只读审查 Agent。移交时工作区修订号为 4；审查 Agent 接受前，另一个分支把修订号推进到 5。系统必须拒绝旧移交，让发送方根据新快照重建任务，而不能让接收方继续使用过期上下文。

:::

下面沿 `offered -> accepted -> returned` 的状态变化解释一次完整移交。重点不是 Agent 之间说了什么，而是谁在什么时候拥有任务、每一步读取哪个工作区版本，以及取消、迟到和越权怎样结束。

## Handoff 解决的是责任转移

在 Handoff 流程中，入口先固定可信范围；缺少来源时直接结束当前路径，不能让模型补字段继续推进。

只传聊天摘要会破坏 handoff_id 与带来源的子结果之间的对应关系，排查时先保留原始输入摘要和发生阶段，再判断是否允许重试。

文件所有权冲突影响发送方或下游解释，不能和只传聊天摘要共用“重新调用一次模型”的处理方式。

## Handoff 与函数调用、消息和 SubAgent 的边界

在 Handoff 中，运行时持有全局预算和依赖状态，局部执行单元只能修改合同允许的那部分。因此 handoff_id 与发送方要有唯一写入方，其他组件只能通过版本化命令申请修改。

函数调用与 Handoff 移交任务、上下文与责任解决的问题相邻，但控制权不同，比较时要看谁选择并行取证、谁保存 handoff_id、谁确认带来源的子结果。

消息队列可以参与同一请求，却不能替代 Handoff 移交任务、上下文与责任；组合后仍要单独检查子任务契约的可信来源和只传聊天摘要的终止规则。

Handoff 移交任务、上下文与责任使用的身份、范围和版本来自可信运行时，父目标可以表达意图，但不能提升权限或改写活动 Release。

文件所有权冲突发生时，错误回到发送方的所有者处理，上游缺输入、当前组件违反不变量和下游不可用分别形成不同终态。

Handoff 移交任务、上下文与责任的确定性边界位于 handoff_id 写入之前。模型在 Handoff 中只提交候选值，程序仍要从认证、版本和策略快照补入可信字段。

Handoff 移交任务、上下文与责任内部可以使用更细的临时对象，跨边界只暴露稳定协议。替换函数调用时，调用方不需要理解内部缓存和 SDK 响应。

## 移交合同要固定哪些输入

Handoff 移交任务、上下文与责任的输入合同至少列出父目标、子任务契约和依赖图，每项都注明来源、是否必需、允许的缺省值，以及缺失后是在入口拒绝还是进入降级路径。

Handoff 要分开保存 `handoff_id`、发送方快照、接收方承诺和工作区修订号。移交身份用于幂等，快照说明接收方看到什么，承诺说明它可以返回什么；工作区版本变化时，运行时才能阻止旧移交覆盖新修改。

并发分支按稳定身份合并接收方，完成顺序只反映耗时，不能决定结果属于哪个请求，更不能让迟到的旧状态覆盖新修订。

Handoff 对外结果要分别表达可交付内容、缺口、取消和未知状态，调用方不必解析错误文案。

发送方参与乐观并发检查；处理开始后若版本变化，旧候选只保留作审计，不能继续写入 handoff_id。

若 Handoff 收到模型代填的身份、范围或版本，应用会丢弃这些值并从可信上下文重新装配。

子任务身份、来源、工作区版本、覆盖缺口、冲突和合并裁决组成 Handoff 移交任务、上下文与责任的最小追踪材料，日志只保存稳定 ID、版本和错误类，完整 Prompt、文档正文与凭证不进入指标标签。

撤回 Handoff 的来源或任务时，相关候选按版本失效，稳定 ID 只保留审计关系。

契约还需要描述新鲜度。发送方对应的数据发生变化后，旧缓存、旧候选和未完成任务怎样失效，应由版本或时间规则直接判断，不能依赖模型注意到矛盾。

删除和撤回也属于数据生命周期。Handoff 移交任务、上下文与责任引用的原始对象被移除时，稳定 ID 可以保留审计关系，正文与派生结果则按策略失效，避免继续向用户展示过期内容。

::: warning Handoff 移交任务、上下文与责任的可信边界

带来源的子结果通过结构校验后仍是候选。Handoff 移交任务、上下文与责任使用的身份、权限、知识版本与业务事实由应用从可信服务读取，核对完成后才能执行或交付。

:::

## 从 offered 到 returned 的状态变化

Handoff 的执行轨迹要包含 offered、accepted 和 returned 三个状态。发送方冻结目标、事实、工具和工作区版本，接收方显式接受后才获得写入责任；若版本冲突，移交停在冲突状态而不是直接覆盖工作区。

拆分问题接收父目标并建立 handoff_id，入口校验未通过就地结束，后续模型、检索器或工具调用次数保持为零。

分派 Handoff 的子任务时，身份、范围、配置版本和绝对 Deadline 一次冻结，后续只继承剩余时间。

并行取证读取发送方并执行主题逻辑，参数由应用组装，外部返回先保存为缺口清单，尚未获得修改领域状态的资格。

处理冲突检查结构、范围、版本和主题不变量；带来源的子结果缺少来源、落在旧版本或越过权限时，handoff_id 停在 rejected 或 failed。

汇合 Handoff 结果时先保存来源和终止原因，再发送事件；核心状态未写入就不能宣称完成。

并行 Handoff 分支只完成一部分时，程序按任务合同选择保留、补偿或整体丢弃，并列出未完成项。

实现可以使用函数、Graph、Middleware 或 Workflow，handoff_id 的所有权和只传聊天摘要的停止规则不会随框架改变。

部分成功需要在步骤边界处理。当 Handoff 已经产生部分候选，先记录哪些可重建、哪些有外部副作用，再决定重试或补偿。

Handoff 的并行和冲突处理都要记录逆向动作；可重建结果可以重算，已发送命令只能查回执或补偿。

## 用版本冲突推演一次移交

沿“Handoff 移交任务、上下文与责任场景：研究任务需要同时核对协议规范、实现约束和测试证据，三个分支完成时间不同且可能给出冲突结论”推演 Handoff 移交任务、上下文与责任：入口创建 request_id，读取可信身份，把父目标和当前版本写入初始状态。

拆分问题生成 handoff_id 与输入摘要；若子任务契约缺失，请求返回 rejected，并指出缺少哪项材料，不继续消耗模型或外部服务配额。

启动 Handoff 分支前冻结 Scope、Release、Policy 和 Deadline，正文中的同名字段不能覆盖运行时快照。

并行取证按“发送方创建不可变移交包，包含目标、已知事实、未决问题、允许工具、预算、工作区版本和返回条件；接收方显式接受后才获得责任”推进，每次依赖调用保存 call_id、参数摘要、开始时间与状态版本，以便判断超时前是否已经产生结果。

Handoff 的候选必须带来源、范围和版本，校验通过后才进入下一状态。

汇合结果写入终态；客户端断开只影响交付通道，重新连接时读取已经保存的 handoff_id 或事件游标，不重跑核心逻辑。

故障注入选择接受前发送方继续修改，程序保留原候选和错误位置，只重做失败边界，不能从入口复制整个任务并产生第二份状态。

推演结束后用 request_id 关联 handoff_id、带来源的子结果与终止原因，测试据此排除并发请求串线，并确认失败路径没有遗留未关闭资源。

Handoff 移交任务、上下文与责任在输入拒绝时不调用依赖，正常路径按 5 个阶段推进，有限修复只重做失败边界。调用次数是控制流断言，不是性能宣传。

Handoff 移交任务、上下文与责任的最终记录用 request_id 关联 handoff_id、带来源的子结果和失败问题，测试据此证明结果来自本次执行，没有混入并发请求。

## 返回结果怎样证明来自当前任务

Handoff 移交任务、上下文与责任正常完成时，handoff_id、发送方和带来源的子结果指向同一次执行，重复读取返回同一终态，未完成分支已经取消或有明确所有者。

子任务身份、来源、工作区版本、覆盖缺口、冲突和合并裁决用于还原 Handoff 移交任务、上下文与责任的处理过程，可以按阶段和版本聚合；敏感正文留在受控存储中，不复制到日志与指标。

Handoff 可以返回空结果，但必须同时说明范围、版本和原因；要求命中材料时，空结果应进入拒答。

依赖返回成功状态只证明传输完成。Handoff 移交任务、上下文与责任还要检查带来源的子结果是否满足业务范围、质量阈值和当前版本，明确拒绝也可能是正确终态。

Handoff 的分支按稳定身份合并，完成顺序只代表耗时，迟到结果不能覆盖新修订。

handoff_id 的状态迁移必须单调：完成不能退回运行中，取消不能被迟到结果覆盖，失败重试也不能绕过入口已经固定的权限。

Handoff 移交任务、上下文与责任的成功证据最终要同时回答输入是什么、执行了哪些步骤、交付了什么以及为什么停止；任一项缺失都应留在未确认状态。

Handoff 移交任务、上下文与责任把业务验收与服务健康分开。依赖对 Handoff 返回 200 只说明传输完成，内容仍要满足当前范围和质量条件。

Handoff 移交任务、上下文与责任的观测指标按阶段和版本聚合。评估 Handoff 时，把错误、空结果、拒绝、恢复和资源消耗分开统计，避免一个成功率掩盖不同故障。

## 取消、迟到结果与权限拒绝

Handoff 的失败要看责任是否已经转移：发送方未冻结快照时由发送方重试，接收方拒绝时保持 offered，接收后超时由父任务回收，已产生副作用却没有回执则查询外部系统。不能把迟到的返回直接当成成功。

遇到只传聊天摘要时，先记录发生阶段、错误类别和责任对象。Handoff 移交任务、上下文与责任保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

Handoff 移交任务、上下文与责任发现文件所有权冲突后重新读取权威状态，旧候选可以保留作审计，却不能覆盖新版本；前后状态无法兼容时，当前尝试以 conflict 结束。

遇到接受前发送方继续修改时，先记录发生阶段、错误类别和责任对象。Handoff 移交任务、上下文与责任保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

遇到父任务取消未传播时，先记录发生阶段、错误类别和责任对象。Handoff 移交任务、上下文与责任保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

遇到接收方无法验证来源时，先记录发生阶段、错误类别和责任对象。Handoff 移交任务、上下文与责任保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

Handoff 移交任务、上下文与责任将终态、可重试性和资源清理结果写入记录；后台扫描器根据 handoff_id 判断任务是在运行、等待恢复还是已失败。

Handoff 移交任务、上下文与责任执行前固定 Deadline、动作上限、重复签名、无进展阈值、预算和取消信号；任一条件触发，并行取证停止创建新工作。

Handoff 移交任务、上下文与责任把重试时间和次数计入总预算。Handoff 每次重试先扣减剩余额度，达到上限就保留原始错误。

Handoff 移交任务、上下文与责任的清理动作设计成幂等操作；仍被活动任务或 Lease 引用的资源拒绝删除。

## 用共享示例验证控制逻辑

用可重复的依赖图模拟完成、超时与取消，核对每份结果的任务 ID、来源、预算和合并裁决；测试显式给出父目标、初始 handoff_id、预期带来源的子结果和终止原因，不能只断言返回值非空。

共享示例把移交拆成两个确定性函数。`HandoffState` 初始为 `offered`，`accept_handoff` 只接受合同指定的 `receiver`，并比较接收时的工作区修订号；通过后才迁移到 `accepted`。接收方提交稳定的结果引用，`return_handoff` 才能迁移到 `returned`。这三个状态不是模型生成的标签，而是运行时可以拒绝的状态机。

Handoff 移交任务、上下文与责任的回归报告要保留失败类型分布。在 Handoff 的回归中，拒绝、超时、权限错误和空结果必须保持各自类型，状态变化本身就是行为契约。

Handoff 移交任务、上下文与责任的性质测试随机改变 handoff_id 顺序、重复提交、完成顺序或状态版本，断言权限不扩大、终态不倒退、同一身份不产生两次副作用。

Handoff 的离线评测关注质量变化，运行时测试关注控制和恢复，两类证据都齐全才可交付。Handoff 移交任务、上下文与责任只有两类证据都存在，才能同时回答“结果是否合格”和“系统是否安全完成”。

## 并发、预算与恢复的工程取舍

Handoff 合同把任务目标、上下文引用、工作区版本、返回状态和写入范围固定在 `handoff_id` 下。合同变更时，旧交接仍按原权限完成，新接收者不能读取历史没有授权的资料。

Handoff 移交任务、上下文与责任的容量主要受分支数量、来源抓取、共享工作区冲突、综合调用和截止时间影响，并发可能缩短单次等待，也会占用连接、配额、内存和下游吞吐，必须沿拆分问题、分派窄任务、并行取证、处理冲突、汇合结果逐层核算。

Handoff 移交任务、上下文与责任的候选版本在固定样本上比较正确性、错误类型、延迟和资源消耗，只传聊天摘要等安全红线回归时直接停止发布，不能用平均质量抵消。

只传聊天摘要的降级路径在发布前写好，可以减少非关键增强、返回已经确认的带来源的子结果，或明确暂时无法确认，缺失事实不能交给模型补写。

交接失败时，用 `request_id` 找发起者快照、接收者确认、上下文来源、工作区版本和返回状态，再决定重发、撤销授权还是人工合并。没有确认的交接不能当作已接管。

Handoff 移交任务、上下文与责任的数据按证据用途分级保留，聚合字段可以留得更久，父目标和大体积带来源的子结果设置短期限、访问控制与删除通道。

Handoff 移交任务、上下文与责任先在单进程实现 handoff_id、超时、错误和测试，只有恢复与容量证据提出要求时，再增加队列、Lease、分布式缓存或工作流引擎。

Handoff 移交任务、上下文与责任的监控阈值要对应可执行动作。Handoff 的分支、依赖、上下文和预算接近上限时，应限流或缩小候选；告警本身不会停止正在运行的任务。

回滚要覆盖代码之外的状态。Handoff 移交任务、上下文与责任若改变 Schema、缓存键或持久化记录，旧版本是否还能读取新写入数据必须提前验证；无法双向兼容时采用候选版本隔离。

## 什么时候不需要 Handoff

采用 Handoff 移交任务、上下文与责任前先画出父目标到带来源的子结果的最小控制图；固定函数已经能完成任务时，新增模型决策和跨进程 handoff_id 只会扩大测试与运维范围。

函数调用通常只返回一次结果，Handoff 还要转移上下文和责任。发送方保留原快照，接收方负责新动作，父运行时确认交接完成并裁决迟到结果。

消息队列可以与 Handoff 移交任务、上下文与责任组合，但外部知识仍需授权，工具调用仍需校验，模型产生的带来源的子结果仍停留在候选状态。

Handoff 移交任务、上下文与责任适合价值足够、只传聊天摘要可观察且预算可接受的任务，高风险、不可逆的决定需要确定性规则或人工批准。

执行期间修改发送方可以检验并发设计，旧动作若仍能覆盖 handoff_id，说明版本或 Lease 有缺口，增加 Prompt 规则无法修复这类竞态。

Handoff 移交任务、上下文与责任增加了 handoff_id、依赖调用、恢复责任和故障面，设计记录既要说明获得的能力，也要列出新增的退出、降级与回滚路径。

用“一个子 Agent 接收任务并把结果交还父 Agent”做自测时，入口先记录输入摘要、身份和执行版本。交接合同、上下文引用、工作区版本和返回状态由唯一组件写入，其他组件只能提交带修订号的候选。在“一个子 Agent 接收任务并把结果交还父 Agent”里，读者可以从任务 ID 找到它经过的节点，不必靠最终文案猜过程。

针对“一个子 Agent 接收任务并把结果交还父 Agent”，正常路径从准入开始，先检查范围和资源，再创建一次调用。调用结果带稳定 ID、来源和终止原因，权限拒绝、版本冲突或子 Agent 取消分别记录。针对“交接合同、上下文引用、工作区版本和返回状态”，输出进入下一节点前还要确认版本和权限，空结果也要说明范围。

在“一个子 Agent 接收任务并把结果交还父 Agent”的故障测试中，依赖调用前和结果已经产生但状态尚未提交时各切断一次。前者应没有外部调用，后者要留下可重放的未知状态。恢复使用同一幂等键，先查询外部回执，再决定补偿。

“一个子 Agent 接收任务并把结果交还父 Agent”的取舍需要写在结果里：扩大缓存、并行或自动修复可能缩短等待，也会增加状态、成本和失败组合；保持较小能力面则更容易做权限隔离和人工接管。

回放“一个子 Agent 接收任务并把结果交还父 Agent”时改变输入顺序、重复提交、缩短 Deadline 或撤回权限，确认状态单调、范围不扩大、资源按时释放。指标用于定位变化，不替代事实核验。

在“一个子 Agent 接收任务并把结果交还父 Agent”中，入口收到的资料可能不完整，程序先保存缺口和当前版本，不能让模型用常识填入 交接合同、上下文引用、工作区版本和返回状态。“一个子 Agent 接收任务并把结果交还父 Agent”的输入后来补齐时，新的执行沿同一个任务 ID 继续；已经结束的失败记录不被覆盖。

“一个子 Agent 接收任务并把结果交还父 Agent”的正常输出先经过范围、版本和权限检查，再进入交付或下一个节点。责任未确认时父 Agent 保留任务为未完成。“一个子 Agent 接收任务并把结果交还父 Agent”的输出只满足结构而没有可验证来源时，状态保持为候选，前端应显示缺口而不是成功标记。
