# Tool Calling 的提议、校验与执行契约

[上一篇](/docs/ai-agent/agent-fit-deterministic-workflow)刚把受限 Agent 的边界收紧：模型可以在固定检查留下的未知分支中提出下一项调查，执行责任仍由运行时、策略和完成验证器承担。

现在的问题更具体。模型提出“查询远程访问制度”后，这次查询要经过哪些检查，才有资格进入外部系统？

拿到一段 JSON 只是交接的开始。一次 **Tool Calling（工具调用）** 会逐步收敛：目录决定模型能看见什么，Schema 判断候选结构，可信上下文重建主体和权限上限，业务策略决定是否授权。

适配器执行获准的命令，再返回可回放的结果。前面的任何一步都可能拒绝候选，也都要留下下一轮能够理解的状态。

这里先跟踪一次工具调用，完整 Agent Loop 和并行批次留在相邻文章中。主案例保持为只读查询，写操作只用于解释超时后的未知副作用。

## 先看一次候选为什么不能直接执行

远程访问调查已经确认设备、账号和审批状态正常，但连接仍失败。Agent 想查制度文档，模型返回一个工具名和查询参数。此时系统只知道“模型建议这样查”，还不知道工具是否存在、参数是否合法、当前用户是否能看这份制度。

### 提议和命令不是同一件事

模型输出的候选属于不可信输入。它可能引用不存在的工具，遗漏必填字段，把数字写成字符串，或携带一个超出当前用户范围的目标。即使文本看起来合理，也不能直接调用外部服务。

运行时至少要把候选经过以下检查：

1. 工具名是否属于本轮公开目录。
2. 原始参数是否能解析为 JSON。
3. 参数是否满足当前工具的 Schema。
4. 主体、权限上限、目标资源和版本是否来自可信上下文。
5. 业务策略是否允许这次调用。

前两步解决“这是什么”，后面三步解决“当前请求能不能发生”。把它们合成一个模糊的 `validate()`，出了问题就无法知道是模型格式错了、权限不够，还是资源状态不允许。

### 沿同一个查询看状态变化

初始状态是“需要调查，但工具尚未执行”。模型提议制度查询后，状态变成“候选待解析”。只有解析、授权和执行都通过，系统才会得到“制度检索已完成”或“没有匹配资料”。如果权限拒绝，调用在执行前结束；如果网络超时，系统还不能判断外部业务是否发生。

运行时因此要先限制可见能力，再验证结构和授权，最后解释执行结果。跳过任何一层，下一轮 Agent 都只能猜。

## 工具目录先决定模型能看什么

工具目录是模型本轮可见的能力集合。每项定义应该包含动作、输入、结果和限制，例如“只读搜索制度片段，不读取个人申请状态”。描述的作用是减少错误选择，不是替代权限系统。

### 描述必须同时写出能力和边界

只写“搜索制度”会留下几个关键问题：是否只读，查询范围是什么，结果是否包含个人数据，空结果如何表示，服务不可用时会返回什么。描述越含糊，模型越容易把相邻工具当成同一能力。

本轮调查只需要制度检索，因此工具定义要写清搜索对象、返回结果和不可触碰的范围：

```text
工具：search_policy
动作：读取制度文档片段
输入：查询词、允许的主题过滤器
结果：匹配片段或明确空结果
限制：只读，不查询个人申请，不改变策略
```

这段是教学用的工具描述，不是某个供应商的完整 Schema。它证明的是“模型看见的能力需要有范围”，不能证明真实服务已经具备认证、限流和撤销能力。

### 目录过滤不是授权

研究问题可以只公开搜索和读取，写操作单独经过策略。目录过滤降低了模型误选的机会，但不能阻止伪造请求直接调用内部接口，也不能证明当前主体有权读取每个结果。

目录发生变化时，模型的选择分布也会变化。生产系统应记录本轮可见工具及其版本，出现错误时才能复盘当时模型究竟看到了什么。这份记录只用于还原候选空间，业务授权层仍负责最终放行。

## Schema 只约束结构，不负责授权

目录匹配后，运行时要把原始参数解析成类型化候选。这里至少分三层：JSON 语法解析，Schema 的显式结构约束，业务授权与范围交集。三层不能互相代替。

### 未知字段必须由 Schema 明确拒绝

JSON 本身不会自动拒绝未知字段。解析器只有读到 Schema 中明确的额外属性约束，才有依据把未知字段判为错误。

以 OpenAI strict Structured Outputs 为例，对象 Schema 仍需显式设置 `additionalProperties: false`，strict 不能代替这项声明。测试必须以实际 Schema 为准，不能凭“用了 JSON”推断安全边界。

同样，Schema 可以检查 `limit` 是整数、范围不超过上限，却不能判断某个制度主题是否属于当前用户可见范围。后者需要可信主体、权限策略和资源状态。

### 用可信上下文重建请求

模型可以提出目标资源和过滤条件，但以下字段不应由模型决定：

- `principal`：当前认证主体。
- `authority` 或 `scope`：主体的权限上限。
- `policy_snapshot`：运行时正在使用的策略快照。
- `resource_state`：目标资源当前是否存在、可见和可操作。

运行时应把候选目标与权限范围求交，再检查资源存在、状态允许和版本匹配。这样既不会把模型提供的范围当成授权来源，也不会把所有模型目标无条件丢弃。

下面的伪代码只展示责任顺序。`parse_schema`、`build_context` 和 `authorize` 都是抽象接口，不能证明任何真实供应商或下游服务行为。

```python
candidate = parse_schema(tool_name, raw_arguments, tool_catalog)
context = build_context(
    principal=authenticated_principal,
    authority=current_scope,
    policy_snapshot=runtime_policy_snapshot,
)
command = bind_target(candidate, context)
authorized = authorize(command, context)
if not authorized:
    return Rejected(reason="policy_denied")
return execute(command)
```

代码把 Schema 解析放在授权之前，把主体从认证上下文取出。它没有处理超时、回执和幂等，因此只能证明“候选不能绕过这两层”，不能被当作完整执行器。

## 授权通过才进入执行

业务授权不是 Schema 的更复杂版本。它要回答的是：当前主体能否访问这个目标，目标状态是否允许，策略是否要求审批，以及这次动作是否会产生副作用。

### 五类身份不能共用一个名字

模型协议、运行时和外部系统观察的是不同对象。把这些对象都叫 `call_id`，单次调用看不出问题，进入并行、重试和恢复后就会发生错配。

| 身份 | 何时出现 | 用途 | 不能替代 |
| --- | --- | --- | --- |
| `provider_call_id` | 模型供应商协议提供调用关联时 | 关联模型候选与 tool output | 运行时分支身份 |
| `invocation_id` | 运行时接受并调度候选时 | 关联授权、执行尝试和结果 | 副作用动作身份 |
| `action_id` | 运行时发出外部副作用前 | 在本地关联原始动作、迟到结果和人工核对 | 下游可查询身份 |
| `idempotency_key` | 下游明确支持幂等时 | 在首次请求前由 `action_id` 稳定映射并发送 | 内部动作记录 |
| `receipt_id` | 外部系统提供可查询回执时 | 核对实际处理效果 | 授权通过的证据 |

`provider_call_id` 是运行时保存的归一化字段，值来自具体供应商的协议关联。

以 OpenAI Responses API 为例，原始字段名是 `call_id`，应用要把同一个值放进 `function_call_output`。它不是所有供应商都会原样返回的统一字段。

每个已调度候选都应有 `invocation_id`。只读查询通常不需要 `action_id`。

写操作即使没有下游幂等能力，也要在发出前创建内部 `action_id`，否则超时后无法把人工核对和迟到结果关联到原动作。下一篇会在 `batch_id` 下用 `invocation_id` 归属并行结果。

### 只读查询也要有范围检查

“只读”只说明工具不会修改状态，不说明结果可以被任何主体读取。制度文档可能按组织、项目或数据等级分层。授权层要把候选目标与当前权限求交，拒绝越界目标，并把拒绝原因转换成不会泄露内部规则的结构化状态。

写操作还要检查状态迁移、审批、幂等和版本冲突。模型返回 `approved`、`completed` 或 `paid` 只是候选文本，不能直接改变领域状态。业务状态必须由可信服务根据授权命令推进。

授权拒绝发生在执行前，所以它不是工具执行失败，也不是空结果。下一轮只能知道“这条路径不允许”，不能让模型换一个用户或扩大范围继续尝试。

## 一次逻辑调用何时结束

授权通过后，运行时还不能立刻把“已经调用”交给模型。适配器可能得到响应，也可能超时或断连。先把一次逻辑调用的边界定住，结果字段和恢复规则才不会互相覆盖。

### 调用内的尝试和调用后的核对是两段过程

同一个 `invocation_id` 可以产生多次 **attempt（尝试）**。每次 attempt 都记录发送时间、传输观测、下游响应或异常，记录本身不覆盖。

只读制度查询遇到短暂超时，且调用的总 Deadline 和重试上限还没有用尽时，可以在这个调用内再试一次。

调用内的尝试结束后，归约器关闭唯一一份 `ExecutionOutcome`。它是这次逻辑调用在关闭时拥有的全部证据，也是返回给模型的 tool output。

关闭后的迟到回执不能覆盖这份输出，否则同一个 `invocation_id` 会在模型看不见的地方改变含义。

写操作还需要一个寿命更长的对象。`ActionRecord` 从副作用发送前开始保存，接收后续的回执和核对事件。

调用关闭后，运行时可以在动作核对的独立 Deadline、次数上限和退避策略内追加 `reconciliation_attempt`。它不是原调用的新 attempt，也不消耗已经结束的调用预算。

| 对象 | 生命周期 | 接收什么 | 不能做什么 |
| --- | --- | --- | --- |
| `ExecutionOutcome` | 一个 `invocation_id`，关闭一次 | 调用内 attempt 与关闭前的查询证据 | 被迟到回执改写或重新打开 |
| `ActionRecord` | 一个外部写动作，可长于调用 | 回执、权威查询与核对事件 | 用新动作身份替代原来的外部效果 |

只读的 `search_policy` 通常没有 `ActionRecord`。它的调用关闭后，结果已经足够指导下一轮改写查询或停止。下面的写入超时只是为了说明，外部副作用为什么需要另一条可追加的证据链。

### 执行前拒绝和执行后结论各自说什么

目录、JSON、Schema、授权或版本检查失败时，适配器尚未开始执行。

运行时应返回执行前决定，例如 `stage=authorization`、`decision=rejected` 和可公开的原因码。这种结果与 `invocation_id` 关联，却不是 `ExecutionOutcome`。

一旦命令交给适配器，结论需要分开观察传输、业务和外部效果。

传输状态描述是否收到响应，例如 `response`、`timeout` 或 `transport_error`。业务结果描述响应表达的含义，例如 `success`、`empty` 或 `business_error`。

外部效果只针对副作用，表示是否已由权威证据确认。

制度查询的 `business=empty` 表示工具已执行，没有找到匹配资料。权限拒绝发生在执行前。

写操作的 `transport=timeout` 只能说明客户端没有观察到响应，效果仍可能是 `unknown`。这些差异决定 Agent 是改写查询、停止路径，还是启动动作核对。

### 返回模型的是关闭时的最小观察

下面的结构是教学近似，描述已经关闭的只读调用。它不代表某个供应商 SDK 的固定字段。

```json
{
  "provider_call_id": "供应商协议关联",
  "invocation_id": "运行时调用关联",
  "transport": "response",
  "business": "success",
  "effect": "not_applicable",
  "source": "policy-service",
  "preview": "可供下一轮使用的最小摘要"
}
```

原始响应和 attempt 观测留在受控存储，`preview` 只包含当前任务所需的摘要。凭证、SQL、内部堆栈和无关个人数据不应进入模型上下文。

若核对后来确认了写入效果，运行时另生成带来源的更正观察供新一轮使用，不回写旧的 tool output。

这个只读案例按 `provider_call_id` 关联模型交接，按 `invocation_id` 找回运行时分支。副作用路径在首次发送前还需要 `action_id`，下游提供可查询回执时才记录 `receipt_id`。

## 超时后怎样避免重复副作用

写操作超时比只读查询危险。客户端没有收到响应，服务端却可能已经处理请求。此时用新的调用身份再提交，可能造成重复发送、重复扣款或重复发布。

### 发送前先建立恢复依据

外部效果的恢复条件必须在首次请求前存在。运行时先持久化 `action_id`、规范化请求摘要和 `ActionRecord(prepared)`。

适配器在任何可能对外发送的 I/O 前，把记录改为 `dispatch_started`。这个标记不证明下游已经收到请求，只规定了保守边界：从这一刻起，效果默认从 `unknown` 开始核对。

下游支持幂等时，运行时还要在首次发送前持久化 `action_id` 与 `idempotency_key` 的稳定映射，并随同一份规范化请求发送。

下游合同应明确键的作用域、保留期、同键同载荷的重放语义与同键异载荷的冲突规则。超时后新建一个键，无法识别此前动作。

权威查询也需要下游认可的依据，例如已有 `receipt_id`、业务引用，或请求前已经传给下游且允许查询的客户端引用。只存在本地日志里的 `action_id`，不能证明下游发生了什么。

### 关闭前可以重试，关闭后只能核对

若逻辑调用尚未关闭，且重试策略和总 Deadline 允许，运行时可以用原 `invocation_id`、原 `action_id`、同一个 `idempotency_key` 和同一规范化请求进行下一次 attempt。

所有调用内尝试结束后，`ExecutionOutcome` 才以当时最后的证据关闭。

关闭时仍无法观察业务结果，就返回 `business=not_observed` 和 `effect=unknown`，同时把 `ActionRecord.reconciliation` 置为 `pending`。

以后发生的权威查询或同键发送只追加 `reconciliation_attempt`。它们可以把动作投影更新为 `confirmed_applied` 或 `confirmed_not_applied`。

原 `invocation_id` 不会多出一次 attempt，已经交给模型的结果也保持不变。

恢复按下游已经提供的能力分流：

1. 有权威效果查询时，用已有回执、业务引用或外部查询引用核对。
2. 有有效幂等合同且键仍在保留期内时，复用原键和原请求受控重试。
3. 两种能力都没有时，将 `ActionRecord` 置为 `manual_hold`，效果继续保持 `unknown`，交给人工核对。

普通“未找到”只有在查询合同覆盖完整保留期，并明确把未命中定义为未执行时，才足以得到 `confirmed_not_applied`。否则它只是新的未知观测。

### 错误回传也要限制下一步

参数范围错误可以让模型修正一次。权限拒绝不应触发“换用户再试”。副作用未知不应触发“新建调用再提交”。结构化分类应同时给出允许的下一步，避免模型把模糊错误文本当成继续执行的许可。

## Tool Calling 和相邻机制的边界

普通 API 由应用代码主动发起调用，Tool Calling 允许模型先提出候选，但二者都需要可信上下文、业务授权和结果处理。差异在于候选来源，不在于 API 可以绕过权限。

MCP 是跨组件的协议与能力交接层，涉及 Host、Client、Server、版本与能力发现、工具、资源、提示和传输。本文只讨论模型候选到运行时执行器的契约。MCP 即使提供工具发现，Host 与 Server 仍要在各自责任层校验 Schema、业务授权和执行结果。

Skill 在本文中只作为一种运行时的知识、步骤或工具配置入口。纯文本 Skill 不一定有工具 Schema；当它触发脚本或工具执行时，执行分支仍需遵守该运行时适用的授权和结果合同。Skill 的文本、白名单或脚本入口不能凭自身内容取得权限。

工作流拥有预定义的外层控制图，Agent Loop 在运行时根据观察选择动作。Tool Calling 位于动作候选和工具执行器之间，负责把候选收敛成可信调用，不负责决定整条业务流程的终态。

## 契约测试检查什么

测试要逐层断言不变量，模型最后收到一段文本只能证明交接完成了一部分：

- 未知工具、JSON 语法错误和 Schema 约束失败不会触发外部调用。
- 额外字段是否拒绝与实际 Schema 配置一致，不能假设 JSON 默认安全。
- 模型不能覆盖 `principal` 和权限上限，目标资源必须经过范围交集与状态检查。
- 存在模型协议关联时 `provider_call_id` 能配对候选与 tool output；每个调度分支的 `invocation_id` 唯一；写操作始终先创建 `action_id`；存在幂等合同时，映射和 `idempotency_key` 在首次请求前已持久化并随请求发送；下游实际提供 `receipt_id` 或支持外部查询引用时才能核对效果。
- 授权拒绝、空结果、传输超时和外部效果未知不会被压成同一种状态。
- 未知写结果不会生成新的动作身份盲目重试；无查询和无幂等能力时进入明确核对路径。
- 凭证、内部堆栈和不必要的个人数据不会进入模型可见结果。

仓库中的测试替身只能证明本地候选和结果映射。真实工具还要验证认证、限流、响应大小、撤销、幂等和回执查询。单元测试返回成功，不等于生产写工具已经安全。

## 结尾：把候选变成可恢复的调用

回到远程访问调查：模型先提出制度查询，目录限制它能看见的能力，Schema 检查参数结构，运行时重建主体和权限上限，授权器决定是否放行，适配器再把传输、业务和效果状态回传。任何一层拒绝，下一轮都应收到明确原因，而不是一段看似成功的文本。

这份契约还要分清身份所有者。`provider_call_id` 保存供应商协议关联，`invocation_id` 负责运行时调用，`action_id` 负责内部副作用记录。

副作用恢复需要下游认可的身份。`idempotency_key` 必须在首次请求前按合同建立并发送，`receipt_id` 或业务引用负责外部查询。

传输超时不能证明副作用没有发生，普通回执未命中也不能确认动作未执行。结构合法只说明参数通过了对应检查，业务授权仍需单独判断。

下一篇把这条单调用契约放进并行批次：多个候选同时执行时，怎样保持每个结果的身份、顺序、取消传播和共享预算不被网络完成顺序打乱。
