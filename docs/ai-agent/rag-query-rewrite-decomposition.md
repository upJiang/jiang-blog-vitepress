# 查询改写与问题分解怎样保留原意

用户问题适合交流，不一定适合搜索。查询改写把同一目标变成检索表达，问题分解把多个目标拆成有依赖的子问题。两者都必须保留实体、时间、否定和权限范围。

## 改写解决表达差异

“连不上公司电脑怎么办”可以改写为“远程访问连接失败 排查”，但不能擅自加入某个操作系统或把“公司电脑”改成私人设备。原问题与改写查询同时保存，便于回看语义漂移。

别名表和领域词典适合确定性扩展，模型负责处理多样表述。明确 ID、版本号和引用语句优先原样保留。

## 分解解决多目标和依赖

“比较新旧规则并说明如何申请”可以拆成旧版条件、新版条件、差异和当前申请步骤。差异依赖前两项，申请步骤只使用当前 Release。

子问题有唯一 ID、父目标、依赖和预期证据，不生成无限层级。

## 结构化计划经过范围校验

运行时确认每个查询仍在用户选择的知识库、Release、语言和时间范围内，分支数不超限。模型不能通过改写加入更宽 Scope。

包含“不要”“除外”“仅限”的条件单独存字段，避免向量化后语义被稀释。

## 多路查询要控制重复

生成的查询先做规范化和相似去重，再并行检索。结果按来源 ID 合并，记录每条 Evidence 由哪个查询找到。连续查询返回同一候选时，不再扩展同一方向。

分解的价值是覆盖不同维度，不是把一句话改写十次。

## 用语义保持测试防止漂移

评测样例覆盖实体、省略、否定、时间和多轮指代。检查改写前后硬约束相同，并验证召回是否增加。

模型生成的漂亮查询若扩大范围或改变目标，应判为失败。检索提升必须建立在原意不变的前提上。
