# 从 DAG 到 Agent Loop 的运行时选择

比较静态依赖图和运行时行动循环，说明生产系统为何常把两者组合。**DAG**、**Agent Loop**、**Runtime** 分别指向同一条执行链上的不同对象：用户请求、幂等键、身份范围、知识 Release、Policy、截止时间和执行资源进入系统，静态节点、依赖、循环状态、观察、节点终态、预算和跨边界检查点保存处理中间状态，最终得到有序事件、最终答案、失败原因、取消确认、可恢复检查点和审计轨迹。

从 DAG 到 Agent Loop 的运行时选择位于 API 请求之外负责长期状态、异步执行、控制信号和结果交付的运行时层，主要机制是稳定依赖用 DAG 表达并行与汇合，不确定的下一动作留给有限 Agent Loop；生产运行时通常让 DAG 节点包住一个受限循环，而不是二选一。把运行时动态分支硬编码成巨图、让 Loop 绕过 DAG 资源限制、检查点粒度不一致和循环失败无法映射到节点状态会让链路在不同位置停止，错误记录必须保留发生阶段、当时的状态和终止原因。

这次推演用幂等键、状态版本、Lease、Event 序号、Checkpoint 和终止原因把请求和终态关联起来。与工作流引擎、状态机、ReAct、DAG 和动态任务图比较时，重点看输入来源、状态所有者、下一步的决策者和失败终点。

从 DAG 到 Agent Loop 的运行时选择的执行顺序是“创建 Turn → 领取执行权 → 推进状态 → 写入事件或检查点 → 形成终态”。用户请求从入口进入，静态节点记录进度，有序事件通过当前主题的校验条件后才会交付。

把运行时动态分支硬编码成巨图与让 Loop 绕过 DAG 资源限制会产生不同证据。前者先检查静态节点和输入来源，后者沿调用记录定位依赖或状态冲突；不区分发生位置，重试会掩盖原始原因。

从 DAG 到 Agent Loop 的运行时选择与工作流引擎的共同点不代表它们可以互换。当前主题拥有依赖，相邻组件只通过契约读取或提交候选，不能直接修改这个状态。

从 DAG 到 Agent Loop 的运行时选择的架构图要标出组件职责、静态节点的唯一所有者、幂等键经过的接口，以及把运行时动态分支硬编码成巨图怎样传播。架构取舍需要说明新增状态和恢复成本，只列组件名称无法用于故障定位。

## 长任务为什么需要独立运行时

比较静态依赖图和运行时行动循环，说明生产系统为何常把两者组合。在“从 DAG 到 Agent Loop 的运行时选择场景：一个研究型回答需要运行数分钟，期间用户断开连接、重新打开页面，并在第二次连接中请求取消”这类任务里，从 DAG 到 Agent Loop 的运行时选择负责把用户请求带入处理链，并明确有序事件可以交付的条件。

从 DAG 到 Agent Loop 的运行时选择位于 API 请求之外负责长期状态、异步执行、控制信号和结果交付的运行时层。它处理稳定依赖用 DAG 表达并行与汇合，不确定的下一动作留给有限 Agent Loop；生产运行时通常让 DAG 节点包住一个受限循环，而不是二选一，身份认证、授权结果和最终业务状态仍由应用中的确定性组件负责。

用户请求是这条链路的起点；来源缺失时，程序只能拒绝请求或采用明确记录的默认值，模型补出的字段不能继续驱动领取执行权。

把运行时动态分支硬编码成巨图会破坏静态节点与有序事件之间的对应关系，排查时先保留原始输入摘要和发生阶段，再判断是否允许重试。

让 Loop 绕过 DAG 资源限制影响依赖或下游解释，不能和把运行时动态分支硬编码成巨图共用“重新调用一次模型”的处理方式。

从 DAG 到 Agent Loop 的运行时选择完成时至少留下静态节点、依赖、有序事件和检查结论；只有最终文字，无法证明结果来自本次请求。

静态节点在单进程 Demo 中可以留在内存，跨进程、带权限或有副作用的任务则要持久化输入、状态转移和停止原因，不能依赖 Prompt 保存状态。

从 DAG 到 Agent Loop 的运行时选择还要把业务条件写成状态条件：身份范围何时就绪，有序事件何时允许交付，把运行时动态分支硬编码成巨图发生后是否还能继续。

从 DAG 到 Agent Loop 的运行时选择对外区分完成、部分完成和无法确认，三个状态若都包装成有序事件，上层界面无法采用不同处理方式。

## 从 DAG 到 Agent Loop 的运行时选择在执行链中的位置

从 DAG 到 Agent Loop 的运行时选择接收用户请求、幂等键、身份范围、知识 Release、Policy、截止时间和执行资源，向下游交付有序事件、最终答案、失败原因、取消确认、可恢复检查点和审计轨迹，输入与输出之间用明确契约连接，调用方不能把一句含糊目标直接交给底层适配器。

Runtime 拥有 Turn 和状态机，Worker 只在有效 Lease 内推进一次状态修订。因此静态节点与依赖要有唯一写入方，其他组件只能通过版本化命令申请修改。

工作流引擎与从 DAG 到 Agent Loop 的运行时选择解决的问题相邻，但控制权不同，比较时要看谁选择推进状态、谁保存静态节点、谁确认有序事件。

状态机可以参与同一请求，却不能替代从 DAG 到 Agent Loop 的运行时选择；组合后仍要单独检查幂等键的可信来源和把运行时动态分支硬编码成巨图的终止规则。

循环状态若只保存在 SDK 对象里，重试或进程退出后就失去解释依据；需要恢复或审计的字段进入持久层，体积较大的有序事件只保存稳定引用。

从 DAG 到 Agent Loop 的运行时选择使用的身份、范围和版本来自可信运行时，用户请求可以表达意图，但不能提升权限或改写活动 Release。

让 Loop 绕过 DAG 资源限制发生时，错误回到依赖的所有者处理，上游缺输入、当前组件违反不变量和下游不可用分别形成不同终态。

从 DAG 到 Agent Loop 的运行时选择的确定性边界位于静态节点写入之前。模型可以建议值，应用核对来源和当前版本；涉及权限、金额、发布或不可逆动作时，再进入策略或人工批准。

从 DAG 到 Agent Loop 的运行时选择内部可以使用更细的临时对象，跨边界只暴露稳定协议。替换工作流引擎时，调用方不需要理解内部缓存和 SDK 响应。

## 领域状态与唯一所有者

从 DAG 到 Agent Loop 的运行时选择的输入合同至少列出用户请求、幂等键和身份范围，每项都注明来源、是否必需、允许的缺省值，以及缺失后是在入口拒绝还是进入降级路径。

状态合同中的静态节点表示当前进度，依赖保存本次执行依赖的快照，循环状态关联前后动作，三者不能合并成一段自由文本。

并发分支按稳定身份合并循环状态，完成顺序只反映耗时，不能决定结果属于哪个请求，更不能让迟到的旧状态覆盖新修订。

输出合同同时描述有序事件和最终答案，并为拒绝、取消、部分完成和未知状态提供固定形状，调用方据此分支，无需解析错误文案猜测结果。

依赖参与乐观并发检查；处理开始后若版本变化，旧候选只保留作审计，不能继续写入静态节点。

用户请求里若包含模型填写的同名字段，应用会丢弃它，再从认证、配置或活动版本中补入可信值，因为结构校验通过不等于授权或业务校验通过。

幂等键、状态版本、Lease、Event 序号、Checkpoint 和终止原因组成从 DAG 到 Agent Loop 的运行时选择的最小追踪材料，日志只保存稳定 ID、版本和错误类，完整 Prompt、文档正文与凭证不进入指标标签。

撤回或删除幂等键时，相关缓存、候选和未完成任务按版本失效；稳定 ID 可以保留审计关系，已撤回内容不能继续进入有序事件。

契约还需要描述新鲜度。依赖对应的数据发生变化后，旧缓存、旧候选和未完成任务怎样失效，应由版本或时间规则直接判断，不能依赖模型注意到矛盾。

删除和撤回也属于数据生命周期。从 DAG 到 Agent Loop 的运行时选择引用的原始对象被移除时，稳定 ID 可以保留审计关系，正文与派生结果则按策略失效，避免继续向用户展示过期内容。

有序事件通过结构校验后仍是候选。从 DAG 到 Agent Loop 的运行时选择使用的身份、权限、知识版本与业务事实由应用从可信服务读取，核对完成后才能执行或交付。

## API、Worker 与存储怎样协作

从 DAG 到 Agent Loop 的运行时选择按“稳定依赖用 DAG 表达并行与汇合，不确定的下一动作留给有限 Agent Loop；生产运行时通常让 DAG 节点包住一个受限循环，而不是二选一”推进，这段机制必须落成静态节点和依赖的实际变化，不能只列框架节点名称。

创建 Turn 接收用户请求并建立静态节点，入口校验未通过就地结束，后续模型、检索器或工具调用次数保持为零。

领取执行权固定身份、范围、配置版本和绝对 Deadline，后续子步骤只继承剩余时间，不能各自重新获得完整超时。

推进状态读取依赖并执行主题逻辑，参数由应用组装，外部返回先保存为最终答案，尚未获得修改领域状态的资格。

写入事件或检查点检查结构、范围、版本和主题不变量；有序事件缺少来源、落在旧版本或越过权限时，静态节点停在 rejected 或 failed。

形成终态先保存有序事件与终止原因，再产生事件或通知，交付失败可以重放，核心状态写入失败则不能对外宣称完成。

推进状态出现部分结果时，由任务合同决定保留、补偿还是整体丢弃；有序事件若可重建就重新生成，外部副作用则查询回执或执行补偿。

实现可以使用函数、Graph、Middleware 或 Workflow，静态节点的所有权和把运行时动态分支硬编码成巨图的停止规则不会随框架改变。

部分成功需要在步骤边界处理。推进状态已经产生一部分有序事件时，程序按任务合同决定保留、补偿或整体丢弃，并记录未完成项，不能默认为全部成功。

推进状态和写入事件或检查点都要写明逆向动作或不可逆原因，有序事件若可重建就删除后重算，已发送的外部命令只能查询回执或补偿。

## 终态、事件和恢复证据

从 DAG 到 Agent Loop 的运行时选择正常完成时，静态节点、依赖和有序事件指向同一次执行，重复读取返回同一终态，未完成分支已经取消或有明确所有者。

幂等键、状态版本、Lease、Event 序号、Checkpoint 和终止原因用于还原从 DAG 到 Agent Loop 的运行时选择的处理过程，可以按阶段和版本聚合；敏感正文留在受控存储中，不复制到日志与指标。

最终答案可能是合法的空结果，但必须带范围、版本和原因；任务明确要求找到材料时，同一个空结果进入拒答而非成功。

依赖返回成功状态只证明传输完成。从 DAG 到 Agent Loop 的运行时选择还要检查有序事件是否满足业务范围、质量阈值和当前版本，明确拒绝也可能是正确终态。

推进状态并发完成时，每个分支保留自己的身份和局部预算，写入事件或检查点按任务合同接纳可用结果，慢分支不能抹掉已经确认的记录。

静态节点的状态迁移必须单调：完成不能退回运行中，取消不能被迟到结果覆盖，失败重试也不能绕过入口已经固定的权限。

从 DAG 到 Agent Loop 的运行时选择的成功证据最终要同时回答输入是什么、执行了哪些步骤、交付了什么以及为什么停止；任一项缺失都应留在未确认状态。

从 DAG 到 Agent Loop 的运行时选择把业务验收与服务健康分开。依赖返回 200 只说明传输成功，有序事件仍要满足当前范围和质量要求；明确拒答也可能是正确终态。

从 DAG 到 Agent Loop 的运行时选择的观测指标按阶段和版本聚合。错误率、空结果率、拒绝率、恢复次数与资源消耗回答不同问题，不能压成一个成功率。

## 何时需要队列或工作流引擎

采用从 DAG 到 Agent Loop 的运行时选择前先画出用户请求到有序事件的最小控制图；固定函数已经能完成任务时，新增模型决策和跨进程静态节点只会扩大测试与运维范围。
