# Computer Use 的视觉上下文管理

区分浏览器图像和用户图像，处理采集大小、图像老化、幂等缓存、引用和对话契约。**Computer Use**、**Visual Context**、**Cache** 分别指向同一条执行链上的不同对象：用户目标、环境观察、能力目录、工作区范围、审批策略和运行预算进入系统，image_id、source type、viewport、captured_at、page revision、cache key、conversation reference 和 stale flag 保存处理中间状态，最终得到受控动作、可审查差异、截图或可访问性观察、测试证据、暂停请求和最终交付。

Computer Use 的视觉上下文管理位于为交互式 Agent 统一上下文、工具、权限、执行、观察和评测的承载层，主要机制是浏览器截图与用户上传图像分开管理，每张图保存来源、尺寸、采集时间、页面状态和引用；重复观察可缓存，但动作后必须使旧图失效。混淆用户图与页面图、压缩后文字不可读、缓存旧页面、图像进入错误会话和只看局部截图遗漏弹窗会让链路在不同位置停止，错误记录必须保留发生阶段、当时的状态和终止原因。

Computer Use 的视觉上下文管理场景：编码助手需要读取仓库、修改一个文件并运行测试，但不能访问工作区之外的路径，也不能在测试失败时宣称完成。Computer Use 的视觉上下文管理需要的身份、权限、版本和业务事实由应用提供，模型与外部内容只产生候选。

:::

这次推演用观察版本、动作参数、审批、文件差异、进程结果、截图和测试输出把请求和终态关联起来。与多模态上下文、截图缓存、DOM 快照、Conversation 和 Computer Use 比较时，重点看输入来源、状态所有者、下一步的决策者和失败终点。

Computer Use 的视觉上下文管理的执行顺序是“观察环境 → 提出动作 → 检查权限 → 执行并重新观察 → 运行确定性验证”。用户目标从入口进入，image_id 记录进度，受控动作通过当前主题的校验条件后才会交付。

混淆用户图与页面图与压缩后文字不可读会产生不同证据。前者先检查 image_id 和输入来源，后者沿调用记录定位依赖或状态冲突；不区分发生位置，重试会掩盖原始原因。

Computer Use 的视觉上下文管理与多模态上下文的共同点不代表它们可以互换。当前主题拥有 source type，相邻组件只通过契约读取或提交候选，不能直接修改这个状态。

Computer Use 的视觉上下文管理的架构图要标出组件职责、image_id 的唯一所有者、环境观察经过的接口，以及混淆用户图与页面图怎样传播。架构取舍需要说明新增状态和恢复成本，只列组件名称无法用于故障定位。

## 交互式 Agent 需要什么承载环境

区分浏览器图像和用户图像，处理采集大小、图像老化、幂等缓存、引用和对话契约。在“Computer Use 的视觉上下文管理场景：编码助手需要读取仓库、修改一个文件并运行测试，但不能访问工作区之外的路径，也不能在测试失败时宣称完成”这类任务里，Computer Use 的视觉上下文管理负责把用户目标带入处理链，并明确受控动作可以交付的条件。

Computer Use 的视觉上下文管理位于为交互式 Agent 统一上下文、工具、权限、执行、观察和评测的承载层。它处理浏览器截图与用户上传图像分开管理，每张图保存来源、尺寸、采集时间、页面状态和引用；重复观察可缓存，但动作后必须使旧图失效，身份认证、授权结果和最终业务状态仍由应用中的确定性组件负责。

用户目标是这条链路的起点；来源缺失时，程序只能拒绝请求或采用明确记录的默认值，模型补出的字段不能继续驱动提出动作。

混淆用户图与页面图会破坏 image_id 与受控动作之间的对应关系，排查时先保留原始输入摘要和发生阶段，再判断是否允许重试。

压缩后文字不可读影响 source type 或下游解释，不能和混淆用户图与页面图共用“重新调用一次模型”的处理方式。

Computer Use 的视觉上下文管理完成时至少留下 image_id、source type、受控动作和检查结论；只有最终文字，无法证明结果来自本次请求。

image_id 在单进程 Demo 中可以留在内存，跨进程、带权限或有副作用的任务则要持久化输入、状态转移和停止原因，不能依赖 Prompt 保存状态。

Computer Use 的视觉上下文管理还要把业务条件写成状态条件：能力目录何时就绪，受控动作何时允许交付，混淆用户图与页面图发生后是否还能继续。

Computer Use 的视觉上下文管理对外区分完成、部分完成和无法确认，三个状态若都包装成受控动作，上层界面无法采用不同处理方式。

## Computer Use 的视觉上下文管理的接口与权限边界

Computer Use 的视觉上下文管理接收用户目标、环境观察、能力目录、工作区范围、审批策略和运行预算，向下游交付受控动作、可审查差异、截图或可访问性观察、测试证据、暂停请求和最终交付，输入与输出之间用明确契约连接，调用方不能把一句含糊目标直接交给底层适配器。

Harness 拥有工作区、工具、权限和循环，模型只读取观察并提出动作候选。因此 image_id 与 source type 要有唯一写入方，其他组件只能通过版本化命令申请修改。

多模态上下文与 Computer Use 的视觉上下文管理解决的问题相邻，但控制权不同，比较时要看谁选择检查权限、谁保存 image_id、谁确认受控动作。

截图缓存可以参与同一请求，却不能替代 Computer Use 的视觉上下文管理；组合后仍要单独检查环境观察的可信来源和混淆用户图与页面图的终止规则。

viewport 若只保存在 SDK 对象里，重试或进程退出后就失去解释依据；需要恢复或审计的字段进入持久层，体积较大的受控动作只保存稳定引用。

Computer Use 的视觉上下文管理使用的身份、范围和版本来自可信运行时，用户目标可以表达意图，但不能提升权限或改写活动 Release。

压缩后文字不可读发生时，错误回到 source type 的所有者处理，上游缺输入、当前组件违反不变量和下游不可用分别形成不同终态。

Computer Use 的视觉上下文管理的确定性边界位于 image_id 写入之前。模型可以建议值，应用核对来源和当前版本；涉及权限、金额、发布或不可逆动作时，再进入策略或人工批准。

Computer Use 的视觉上下文管理内部可以使用更细的临时对象，跨边界只暴露稳定协议。替换多模态上下文时，调用方不需要理解内部缓存和 SDK 响应。

## 观察、动作和工作区状态

Computer Use 的视觉上下文管理的输入合同至少列出用户目标、环境观察和能力目录，每项都注明来源、是否必需、允许的缺省值，以及缺失后是在入口拒绝还是进入降级路径。

状态合同中的 image_id 表示当前进度，source type 保存本次执行依赖的快照，viewport 关联前后动作，三者不能合并成一段自由文本。

并发分支按稳定身份合并 viewport，完成顺序只反映耗时，不能决定结果属于哪个请求，更不能让迟到的旧状态覆盖新修订。

输出合同同时描述受控动作和可审查差异，并为拒绝、取消、部分完成和未知状态提供固定形状，调用方据此分支，无需解析错误文案猜测结果。

source type 参与乐观并发检查；处理开始后若版本变化，旧候选只保留作审计，不能继续写入 image_id。

用户目标里若包含模型填写的同名字段，应用会丢弃它，再从认证、配置或活动版本中补入可信值，因为结构校验通过不等于授权或业务校验通过。

观察版本、动作参数、审批、文件差异、进程结果、截图和测试输出组成 Computer Use 的视觉上下文管理的最小追踪材料，日志只保存稳定 ID、版本和错误类，完整 Prompt、文档正文与凭证不进入指标标签。

撤回或删除环境观察时，相关缓存、候选和未完成任务按版本失效；稳定 ID 可以保留审计关系，已撤回内容不能继续进入受控动作。

契约还需要描述新鲜度。source type 对应的数据发生变化后，旧缓存、旧候选和未完成任务怎样失效，应由版本或时间规则直接判断，不能依赖模型注意到矛盾。

删除和撤回也属于数据生命周期。Computer Use 的视觉上下文管理引用的原始对象被移除时，稳定 ID 可以保留审计关系，正文与派生结果则按策略失效，避免继续向用户展示过期内容。

## 受控循环怎样运行

Computer Use 的视觉上下文管理按“浏览器截图与用户上传图像分开管理，每张图保存来源、尺寸、采集时间、页面状态和引用；重复观察可缓存，但动作后必须使旧图失效”推进，这段机制必须落成 image_id 和 source type 的实际变化，不能只列框架节点名称。

观察环境接收用户目标并建立 image_id，入口校验未通过就地结束，后续模型、检索器或工具调用次数保持为零。

提出动作固定身份、范围、配置版本和绝对 Deadline，后续子步骤只继承剩余时间，不能各自重新获得完整超时。

检查权限读取 source type 并执行主题逻辑，参数由应用组装，外部返回先保存为可审查差异，尚未获得修改领域状态的资格。

执行并重新观察检查结构、范围、版本和主题不变量；受控动作缺少来源、落在旧版本或越过权限时，image_id 停在 rejected 或 failed。

运行确定性验证先保存受控动作与终止原因，再产生事件或通知，交付失败可以重放，核心状态写入失败则不能对外宣称完成。

检查权限出现部分结果时，由任务合同决定保留、补偿还是整体丢弃；受控动作若可重建就重新生成，外部副作用则查询回执或执行补偿。

实现可以使用函数、Graph、Middleware 或 Workflow，image_id 的所有权和混淆用户图与页面图的停止规则不会随框架改变。

部分成功需要在步骤边界处理。检查权限已经产生一部分受控动作时，程序按任务合同决定保留、补偿或整体丢弃，并记录未完成项，不能默认为全部成功。

检查权限和执行并重新观察都要写明逆向动作或不可逆原因，受控动作若可重建就删除后重算，已发送的外部命令只能查询回执或补偿。

## 差异与验证怎样形成闭环

Computer Use 的视觉上下文管理正常完成时，image_id、source type 和受控动作指向同一次执行，重复读取返回同一终态，未完成分支已经取消或有明确所有者。

观察版本、动作参数、审批、文件差异、进程结果、截图和测试输出用于还原 Computer Use 的视觉上下文管理的处理过程，可以按阶段和版本聚合；敏感正文留在受控存储中，不复制到日志与指标。

可审查差异可能是合法的空结果，但必须带范围、版本和原因；任务明确要求找到材料时，同一个空结果进入拒答而非成功。

依赖返回成功状态只证明传输完成。Computer Use 的视觉上下文管理还要检查受控动作是否满足业务范围、质量阈值和当前版本，明确拒绝也可能是正确终态。

检查权限并发完成时，每个分支保留自己的身份和局部预算，执行并重新观察按任务合同接纳可用结果，慢分支不能抹掉已经确认的记录。

image_id 的状态迁移必须单调：完成不能退回运行中，取消不能被迟到结果覆盖，失败重试也不能绕过入口已经固定的权限。

Computer Use 的视觉上下文管理的成功证据最终要同时回答输入是什么、执行了哪些步骤、交付了什么以及为什么停止；任一项缺失都应留在未确认状态。

Computer Use 的视觉上下文管理把业务验收与服务健康分开。依赖返回 200 只说明传输成功，受控动作仍要满足当前范围和质量要求；明确拒答也可能是正确终态。

Computer Use 的视觉上下文管理的观测指标按阶段和版本聚合。错误率、空结果率、拒绝率、恢复次数与资源消耗回答不同问题，不能压成一个成功率。

Computer Use 的视觉上下文管理按输入、状态、依赖、结果和交付五个位置分类错误，发生位置决定恢复动作，不能用同一个重试循环处理全部失败。

遇到压缩后文字不可读时，系统要返回稳定的错误类型、发生阶段和可重试标记。Computer Use 的视觉上下文管理保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

Computer Use 的视觉上下文管理发现缓存旧页面后重新读取权威状态，旧候选可以保留作审计，却不能覆盖新版本；前后状态无法兼容时，当前尝试以 conflict 结束。

遇到只看局部截图遗漏弹窗时，系统要返回稳定的错误类型、发生阶段和可重试标记。Computer Use 的视觉上下文管理保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

Computer Use 的视觉上下文管理结束错误处理时保存终态、可重试性和资源清理结果，后台扫描器依靠 image_id 和这些字段区分仍在运行、等待恢复和已经失败的任务。

Computer Use 的视觉上下文管理在执行前写入绝对 Deadline、最大动作数、重复签名、无进展阈值、预算和人工取消信号，任一条件触发后检查权限都不再创建新工作。

Computer Use 的视觉上下文管理把重试时间和次数计入总预算。依赖连续失败会减少后续额度，达到上限后保留原始错误，不再用模型重新措辞掩盖失败。

Computer Use 的视觉上下文管理的清理动作可以重复执行。临时对象、文件句柄、子进程、连接或 Lease 仍被活动任务引用时，清理器必须拒绝删除。

## 隔离环境中的回放测试

使用隔离工作区和假环境重放观察动作循环，断言越界动作被拒绝、写操作需要审批、验证失败不会标记完成；测试显式给出用户目标、初始 image_id、预期受控动作和终止原因，不能只断言返回值非空。

Computer Use 的视觉上下文管理的单元测试用 Fake Adapter 固定受控动作与错误，断言参数、调用顺序、状态修订和清理动作，这些结果只证明本地控制逻辑。

契约测试围绕用户目标、image_id 和可审查差异构造合法与非法样本，Schema 解析成功后继续检查权限、版本与领域不变量。

故障测试注入混淆用户图与页面图和压缩后文字不可读，记录检查权限是否被调用、image_id 是否改变、资源是否释放，以及同一身份重试会不会重复执行。

在检查权限前后终止进程可以检查恢复边界：调用前退出允许重新领取，外部动作后退出先查回执，运行确定性验证完成后只重放交付。

Computer Use 的视觉上下文管理的集成测试连接真实协议与隔离存储，检查序列化、约束、并发和超时；需要在线服务时另行记录服务版本、时间、配置与凭证条件。

Computer Use 的视觉上下文管理的回归报告要保留失败类型分布。明确拒绝变成超时、权限错误变成普通空结果，都属于行为回归，即使总通过数没有变化。

Computer Use 的视觉上下文管理的性质测试随机改变 image_id 顺序、重复提交、完成顺序或状态版本，断言权限不扩大、终态不倒退、同一身份不产生两次副作用。

离线评测关注固定输入下的质量变化，运行时测试关注控制和恢复。Computer Use 的视觉上下文管理只有两类证据都存在，才能同时回答“结果是否合格”和“系统是否安全完成”。

## 后台进程、容量和治理

Computer Use 的视觉上下文管理长期运行后，输入 Schema、image_id 结构和依赖配置可能独立升级，每次执行固定一组版本，旧记录才能被正确读取或迁移。

Computer Use 的视觉上下文管理的容量主要受观察体积、工具调用、后台进程、浏览器会话、文件差异和循环步数影响，并发可能缩短单次等待，也会占用连接、配额、内存和下游吞吐，必须沿观察环境、提出动作、检查权限、执行并重新观察、运行确定性验证逐层核算。

Computer Use 的视觉上下文管理的候选版本在固定样本上比较正确性、错误类型、延迟和资源消耗，混淆用户图与页面图等安全红线回归时直接停止发布，不能用平均质量抵消。

混淆用户图与页面图的降级路径在发布前写好，可以减少非关键增强、返回已经确认的受控动作，或明确暂时无法确认，缺失事实不能交给模型补写。

Computer Use 的视觉上下文管理的运行手册从 request_id 定位观察版本、动作参数、审批、文件差异、进程结果、截图和测试输出，再决定重试、补偿、取消或回滚，无需先展开完整的用户目标。

Computer Use 的视觉上下文管理的数据按证据用途分级保留，聚合字段可以留得更久，用户目标和大体积受控动作设置短期限、访问控制与删除通道。

Computer Use 的视觉上下文管理先在单进程实现 image_id、超时、错误和测试，只有恢复与容量证据提出要求时，再增加队列、Lease、分布式缓存或工作流引擎。

Computer Use 的视觉上下文管理的监控阈值要对应可执行动作。观察体积、工具调用、后台进程、浏览器会话、文件差异和循环步数中的某项接近上限时，系统可以限流、排队、缩小候选或切换保守路径；只发送告警不会保护正在运行的任务。

回滚要覆盖代码之外的状态。Computer Use 的视觉上下文管理若改变 Schema、缓存键或持久化记录，旧版本是否还能读取新写入数据必须提前验证；无法双向兼容时采用候选版本隔离。

## Harness 与 Runtime、MCP 的区别

采用 Computer Use 的视觉上下文管理前先画出用户目标到受控动作的最小控制图；固定函数已经能完成任务时，新增模型决策和跨进程 image_id 只会扩大测试与运维范围。

Computer Use 的视觉上下文管理与多模态上下文的差别落在控制权：谁选择下一步，谁保存 image_id，谁确认受控动作可信。

截图缓存可以与 Computer Use 的视觉上下文管理组合，但外部知识仍需授权，工具调用仍需校验，模型产生的受控动作仍停留在候选状态。

Computer Use 的视觉上下文管理适合价值足够、混淆用户图与页面图可观察且预算可接受的任务，高风险、不可逆的决定需要确定性规则或人工批准。

格式正确但事实错误的受控动作是必要反例；若它直接进入成功，说明执行并重新观察缺少业务验证，应保留候选并给出证据问题。

执行期间修改 source type 可以检验并发设计，旧动作若仍能覆盖 image_id，说明版本或 Lease 有缺口，增加 Prompt 规则无法修复这类竞态。

Computer Use 的视觉上下文管理增加了 image_id、依赖调用、恢复责任和故障面，设计记录既要说明获得的能力，也要列出新增的退出、降级与回滚路径。

Computer Use 的视觉上下文管理从一个调用、一个 image_id、一组明确错误和几条确定性测试开始，真实 Trace 证明需要后再加入并发、缓存、队列或更复杂策略。

多模态上下文只在能处理混淆用户图与页面图时引入，不为目录完整强行组合；接口保持可替换，后续需求出现再扩展。
