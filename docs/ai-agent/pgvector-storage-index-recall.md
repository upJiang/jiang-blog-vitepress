# pgvector 存储、索引与向量检索

向量已经生成，接下来要把它放进数据库，查询时找到相近的 Chunk。看起来只是给 embedding 建一个索引，实际同时涉及距离函数、活动版本、租户范围、权限、过滤选择性、Top K、邻接补全和召回评测。任何一层不匹配，都会得到“SQL 成功但答案不对”的结果。

当前参考迁移把向量列定义为固定维度的 pgvector，并创建带余弦距离操作符的 HNSW 索引，条件是 Chunk active 且 embedding 非空。表中还保存全文搜索、精确字段、结构字段、Source Version 和 Release。pgvector 的距离运算、HNSW 与 IVFFlat 参数应以其[官方实现与说明](https://github.com/pgvector/pgvector)为准，并用目标数据集建立精确基线。**IVFFlat 在本文作为比较路线，不是当前迁移已经创建的索引**。

::: info 先区分三个数字

距离是数据库为一对向量计算的排序信号；Top K 是返回多少候选；Recall 是评测集中相关结果被找回的比例。距离更小、K 更大，都不自动意味着 Recall 更高，更不代表最终答案正确。

:::

本文用三个 Chunk 推演：A 是“生产外部连接须由系统负责人批准”，B 是同一制度的故障处理，C 是办公用品采购。查询“外部连接由谁审批”应优先得到 A；查询 RA-204 时，精确字段比距离更可靠；无权用户即使与 A 的向量最近，也不能看到 A。

```mermaid
flowchart LR
  A[Query] --> B[Embedding]
  B --> C[精确或近似 KNN]
  C --> D[Release 与 ACL 过滤]
  D --> E[Top K 候选]
  E --> F[邻接补全或重排]
  F --> G[召回评测与降级]
```

## 向量列与活动版本怎样配套

Embedding 列只有在维度固定时才适合同一距离操作。入库适配器把模型返回的数组转为 pgvector 字面量，Repository 在事务内检查所有 Chunk 都是 ready 且长度为 1024。数据库迁移还保存 embedding model、dimension、index version 和 embedding hash，排查时可以知道向量来自哪套配置。

tp_rag_chunks 同时有 document_version_id、source_version_id、release_id 和 active。普通查询以文档 active_version_id 约束 Chunk；指定知识 Release 的查询则按 Release 关系选快照，不要求它一定是文档当前活动版本。版本条件必须和向量距离一起进入 SQL，不能先取全库近邻再在应用层过滤。

当前迁移建立了数据集、文档、版本、对象和全文字段索引，向量索引只接收 active 且有向量的行。空向量不会参与 HNSW，legacy JSON 向量也不能假定与新列兼容。重新索引完成前，候选版本保持不可见。

表格的 exact_terms 和 structured_fields 也在同一张 Chunk 表。数据库可以为业务编号、表格列和全文建立独立索引。把所有问题都改写成向量查询，会丢掉确定性通道本来就能提供的保证。

## 先用精确 KNN 建立召回基线

近似索引之前，先用同样的向量、距离和过滤条件做精确排序。精确查询遍历满足活动版本、Release、租户和 ACL 的候选，按 cosine distance 排序，取足够大的 K。它慢，但可以回答“相关 Chunk 在这个可见集合里究竟排第几”。

基线查询的过滤必须与线上查询一致。若基线在全库计算，线上先限制某个知识范围，二者比较出的 Recall 没有意义；若基线允许管理员读所有来源，普通用户的召回也会被高估。评测记录用户范围、Release、查询通道和禁止来源。

假设可见集合只有 A、B、C，精确距离排序为 A、B、C，Top 2 应包含 A。之后启用 HNSW，结果为 B、C，说明近似索引或参数在这条查询上漏了 A；不是重排器还没发挥作用，因为目标在进入重排前已经消失。

基线也需要精确的查询向量。查询与文档使用不同模型或不同表示模板，即使数据库返回距离，比较仍无效。向量维度、模型、归一化和距离操作符随评测快照保存。

精确基线不证明语义答案正确。它只证明在已经生成的向量与已过滤集合中，哪些 Chunk 距离更近。若 A 的 OCR 内容本身错误，精确检索仍会忠实地找回错误；内容和证据门禁另负责这一层。

## HNSW 怎样换取查询速度

HNSW 用分层图结构组织向量，查询从高层入口逐步寻找邻近点，再在底层扩展候选。它通常不需要在每次查询时扫描全部向量，适合需要较低延迟的在线检索。查询参数控制探索范围，构建参数影响图的连接与构建成本。

探索范围太小，可能很快返回但漏掉相关 Chunk；增加探索范围通常会访问更多节点，延迟和资源上升。参数不是越大越好，要在固定语料、过滤和查询集上对比 Recall 与 p95，而不是只跑一次热门问题。

当前迁移的索引条件包含 active = TRUE AND embedding IS NOT NULL。这让不可见候选和空向量不进入图，但也意味着激活切换后索引包含的行集合会变化。新版本构建应在候选空间完成质量校验，再切活动；直接在活动表上边写边建会让查询看到不一致集合。

HNSW 的近似性质不会替代 Release 过滤。先用图找全库近邻再过滤，可能 Top K 都被无权来源占掉，过滤后为空；SQL 需要让可见集合成为检索条件。实际执行计划和版本的 pgvector 行为要在目标数据库测试，文章只描述当前迁移与通用取舍。

## IVFFlat 是另一种取舍，不是当前现状

IVFFlat 先把向量分到若干列表，查询只探测其中一部分列表。列表数量、训练样本和探测数量决定召回与成本。它可能适合数据规模、写入方式和运维习惯不同的系统，但需要训练或重建，候选分布变化后参数也可能失效。

不能把“支持 pgvector”直接写成“HNSW 和 IVFFlat 都已配置”。当前迁移只创建 HNSW cosine partial index；若未来评估 IVFFlat，应建立独立候选索引，记录训练数据、lists、probes、过滤策略和评测版本，再决定是否替换。

比较两种索引要固定同一查询集、同一可见集合、同一距离和 Top K。报告包含精确基线 Recall、近似 Recall、查询延迟、构建时间、写入影响和过滤后候选数量。一个索引更快但 Recall 下降，是否可接受取决于问题类型与失败代价。

## 过滤选择性会改变近似索引表现

过滤条件可能是数据集、Release、租户、Source、节点范围、ACL、文档版本和表格字段。全局有一百万向量，当前用户只有一千条可见 Chunk，近似索引若先在百万行找近邻再过滤，留下的候选可能不足；探测更多节点增加成本，仍可能遗漏。

Scope 通道必须显式提供范围 ID。当前检索参数把 scope_ids 去重并记录 has_scope，SQL 同时匹配 root node 或 document ID。没有范围时不能因为查询包含“这个范围内”就猜一个节点，也不能自动扩大到整个数据集。

ACL 过滤还要考虑撤回状态、Subject、Group 和管理员身份。缓存命中后的 Chunk ID 会再次通过可见性 SQL 检查，不能只信缓存写入时的权限。向量相似与授权是两条独立关系，数据库应在候选阶段裁掉无权记录。

过滤选择性变化时，原来的 ANN 参数可能不再合适。热门公开数据和窄租户数据分别评测；对极窄范围可先用精确或稀疏通道，对大范围再使用 HNSW。选择路径由范围与查询类型决定，不让一个固定 Top K 覆盖所有场景。

## SQL 的过滤顺序要用执行计划验证

向量操作符出现在 ORDER BY，并不表示数据库一定先应用所有业务过滤。Join、子查询、Release 关系、ACL 和 Scope 可能改变计划。线上检查应使用隔离或只读数据运行 EXPLAIN，确认查询没有因为参数分布变化退化成大范围扫描，也不能为了追求向量索引而删掉必要过滤。

查询条件可以分成身份条件、版本条件、可见性条件和排序条件。数据集、Release 和 active 决定候选集合；ACL、Scope 和撤回决定用户能看什么；距离只在这个集合里排序。应用层拿到全库前 K 再过滤，逻辑顺序已经反了，窄范围和权限都会丢召回。

参数化 SQL 还要防止数组为空和类型漂移。没有 Scope 时用显式 has_scope，不能把空数组误解释成“匹配任何节点”；Release ID 为空时走活动文档版本，指定 Release 时走发布链接。测试应检查两种模式都包含相同的 dataset、index_status 和 ACL 条件。

向量查询返回候选后，邻接补全通常再做几次 Join。执行计划可能在主查询快、补全慢时形成 p95 长尾。补全只取必要数量、同一版本并限制候选文档数，不能因为主查询使用 ANN 就把所有父子内容无界展开。性能指标要拆主检索、融合、补全、重排和证据装配。

## 维护索引不能把候选暴露给读路径

HNSW 索引所在表的 active 行集合随版本切换变化。新增候选 Chunk 先保持 inactive，候选索引或批量写入完成后通过版本事务切换；删除旧版本也按保留窗口进行。直接在活动表中插入一部分新 Chunk，查询会看到不完整文档，不能以“索引最终会收敛”为理由接受。

重新索引需要记录开始版本、目标模型、维度、距离、参数和成功计数。中途失败时，旧索引继续服务，候选对象标记 failed 或 superseded。候选使用独立索引空间时，完成后切别名或活动版本；当前实现依赖 active 字段和版本条件，不能宣称有独立物理索引别名。

HNSW 构建会消耗 CPU 和内存，写入批次与查询并发相互影响。维护窗口不是质量证据，仍要跑查询集和权限回归。索引创建命令成功只证明数据库接受了 DDL，不证明近似 Recall、邻接和答案引用没有退化。

数据删除也要考虑图索引结构、全文向量、缓存和 Release。撤回 Source 后先让它从可见集合消失，再按清理策略回收向量和索引空间；如果删除失败，查询过滤仍需拒绝来源。只删除正文而留下可命中的向量，会形成没有可引用来源的候选。

统计信息和执行计划会随版本数据分布变化。新增一批高度相似的 Chunk，向量索引与融合去重压力增加；某租户内容大幅增长，Scope 选择性变化。维护记录保存前后样本和查询类型，不能把一次建索引后的表现当作长期保证。

## 距离与归一化的反例必须进测试

余弦相似度关注向量方向，内积还受长度影响，欧氏距离直接比较坐标差异。模型输出是否已经归一化决定这些排序是否近似等价。数据库用 cosine 操作符，而入库或查询只对一侧归一化，结果会发生不可解释变化。

构造三个二维向量可以看出差异：查询为 [1, 0]，候选 P 为 [1, 0]，候选 Q 为 [10, 0.1]。余弦更关注方向，Q 可能仍很接近；内积会被 Q 的长度放大。这个例子不代表任何真实模型，只用来测试代码与 SQL 选择的数学一致性。

维度相同不代表坐标语义相同。模型 M1 和 M2 都返回 1024 维，M1 的文档向量与 M2 的查询向量仍不能混算。配置迁移必须绑定模型、模板、维度、规范化和距离，缓存键也要包含这些身份。

距离阈值不应直接当置信度。每个模型和语料的距离分布都不同，阈值要在标注查询集上校准。越过阈值的候选仍要检查权限、版本和 Claim 支撑；没有任何候选超过阈值时，输出证据不足而不是调用生成模型猜测。

## 一个近似召回失败怎样定位

查询“外部连接由谁审批”在精确 KNN 中把 A 排第一，HNSW 却返回 B、C。先确认 A active、embedding ready、版本和 ACL 正确，再用同一查询向量检查精确基线。若 A 的向量缺失，属于入库问题；若 A 在精确结果却不在 HNSW，才进入索引参数和执行计划排查。

假设 HNSW 探索范围较小，A 位于未探索的局部图。增加探索参数后 A 回到候选，Recall 恢复但 p95 上升。此时不能只把参数调到最大，还要评估 Top K、过滤选择性和是否对这类查询切换精确或稀疏通道。参数取舍必须记录在版本配置中。

另一种情况是 A 与 B 都属于当前用户，但 A 的 Source Version 已撤回。精确查询与 HNSW 都返回 A 的 ID，ACL 和 Release 过滤将它排除，最终只剩 B。这里的空结果或排序变化是安全行为，不应为“召回低”而放宽权限。

如果 A 在 dense 候选中，融合后却被 B 替换，检查候选身份去重、通道权重和每文档上限；如果重排后消失，检查重排输入是否包含表头、章节和结构字段；如果 Claim 验证拒绝，说明文本无法支撑“审批人”，不是向量检索失败。每层都保留候选 ID，排查不会跳回模型猜测。

最终回归至少包含同义问法、编号问法、相近编号、无权限用户和无答案问题。修复后要求 A 在语义问题中出现，RA-204 精确匹配保持稳定，相近编号不替代目标，无权限候选为空，无答案保持拒答。只有一条查询变好，不足以说明索引改动安全。

## 运行指标要和评测指标对齐

线上记录 dense 调用成功率、向量查询耗时、候选数量、过滤数量、邻接耗时、Rerank 状态和 Evidence 数量。离线记录 Recall、MRR、nDCG、相关 Source 覆盖和禁止来源命中。两者通过索引、模型、Release 和查询哈希关联，不用一个总成功率掩盖问题。

空结果率上升可能来自新 Release 内容减少、ACL 收紧、Embedding 服务失败、HNSW 探索不足或稀疏词项变化。Trace 里的通道状态和过滤计数能把它们分开。没有这些字段，运维只能调大 Top K，甚至把无权内容重新放回候选。

延迟下降也可能伴随 Recall 下降。按查询类型和用户范围分组看 p50、p95 与 Recall，公开大范围和窄权限范围分别观察。单次本地运行不代表线上效果，公开报告中不要写未经执行的延迟或召回数字。

召回评测失败应阻止候选索引激活，安全越权测试更不能用平均 Recall 抵消。索引的质量门禁、发布门禁和运行告警互相配合，每一层对自己能观察的事实负责。

最终报告还要保留一条从查询到 Evidence 的完整轨迹：查询向量版本、过滤条件、近似候选、精确候选、融合排名、邻接补全和引用校验。只有这条轨迹能说明某个结果为什么出现，以及下一次回归应在哪个环节复现。

## 查询向量到候选 Chunk 的数据流

用户 U 输入“外部连接由谁审批”。查询服务先解析身份、知识范围、Release、最大候选数和 Deadline。如果启用 dense 通道，就用当前 Embedding 模型生成查询向量；生成失败时记录警告，检索器可以保留 sparse、exact 和 table 通道，不能悄悄把空向量当成合法向量。

数据库 dense 查询在可见 Chunk 中计算距离，返回 Chunk ID、文档版本、Source 标题、章节、表头、结构字段、分数和通道名。A 排第一，B 也可能因为“连接”一词进入候选。每条记录带版本身份，便于后续邻接补全和引用。

融合器把 dense、sparse、exact 和 table 的结果按候选身份去重。RA-204 查询若 exact 通道命中行级 Chunk，dense 的相邻制度只能作为补充，不能以通用语义覆盖精确身份。重排器读取标题、章节、正文、表头和结构字段，不直接读取未经授权的原始表。

最终证据预算只保留能支撑 Claim 的 Chunk。若 dense 返回 A，但 A 的当前用户权限被过滤，结果为空或转由其他通道寻找，不把 B 的“故障处理”拼成批准人。答案生成不是补齐检索失败的步骤。

~~~text
query
  -> identity / scope / release pinned
  -> query embedding ready or dense degraded
  -> filtered vector candidates
  -> exact and sparse candidates fused
  -> rerank with fields and source context
  -> evidence budget and citation validation
~~~

## 邻接补全只能在同一版本内发生

一个 Chunk 命中后，检索器可以读取 previous、next 或父章节，补足被切块分开的条件。当前 SQL 通过 Chunk 身份与版本字段连接相邻记录，结果仍带 Source Version 和 Release。补全不是重新做一次全库向量检索。

补全必须限定同一 Source Version、Document Version 和可见范围。V3 的前一块不能连到 V2，主文末尾不能连到附件开头，父节点也不能跨租户。质量门禁已经检查孤立与跨版本关系，查询层遇到缺邻居可以降级只用当前 Chunk，但不应把越界邻居当作正常结果。

邻接会增加上下文长度和重复。候选预算先保留命中 Chunk，再按必要条件补一两个邻居；一篇长章节的所有父子节点不能因为向量命中一个标题就全部展开。邻接内容在取回时重新鉴权，缓存只存身份与版本绑定的结果。

## Recall 怎样与近似参数一起验证

评测集为每条查询标注相关 Chunk 或允许的 Source 集合，并记录用户范围、Release、问题类型和禁止来源。Recall@K 计算前 K 候选中是否包含至少一个相关项；MRR 关注首个相关项位置；nDCG 对多级相关性和排序位置赋权。三者分别回答覆盖、首命中和整体排序。

精确 KNN 是基线。固定模型、切块和可见集合，先得到基线结果，再改 HNSW 探索参数。报告按语义问题、编号问题、表格问题、窄范围问题和无结果问题拆分，不能只看全局平均。

如果 HNSW Recall 下降，先确认索引使用了正确距离操作符和过滤条件；再调探索参数；最后才考虑改变 Chunk 或模型。若精确基线本身漏掉目标，问题在入库、表示或标注，不应靠 ANN 参数掩盖。

评测结果绑定索引版本、语料版本、模型、维度、距离和查询集。候选模型或模板变化后，旧 Recall 不能直接复用。没有真实模型或隔离数据库运行证据，只能说明测试计划，不能写具体通过数。

## 超时和空结果怎样安全降级

dense 查询超时不等于知识为空。检索器记录 dense 依赖错误，继续执行允许的 sparse、exact、table 通道；权限与 Release 条件保持不变。所有通道都没有可见证据时，返回范围内无证据的安全终态。

近似索引返回空结果时，可以按策略增加探索或切换精确查询，但必须受 Deadline 和候选预算控制。重复调用直到有结果会把超时放大。窄范围下精确查询可能比调大 ANN 更可控，选择应由范围规模和失败记录决定。

查询向量维度错误、索引运算符不匹配和数据库不可用属于配置或依赖故障，不应作为普通空结果缓存。普通空结果可以短时缓存，键包含 Release 和权限；故障缓存要短且可区分，否则修复后仍然返回“没有资料”。

Rerank 超时可以按任务合同保留初始融合排序，但必须在结果元数据中标注未重排；若初始候选不足或涉及高风险 Claim，则安全拒答。降级只减少不确定性，不增加模型自己补答案的权限。

## pgvector 之外的通道怎样互补

全文搜索使用 search_vector GIN 索引，适合中文词项、错误消息和短语；exact_terms 与结构字段适合编号、状态和表格列；Graph 可以沿确定关系扩展实体。向量擅长词面不同的语义候选。每条通道返回候选身份与分数来源，融合器负责去重。

当前实现对稀疏查询先做严格词项清理，再只做有限放宽，不用无界 ILIKE 扫全表。这样“发布后如何用于检索”不会因为问句噪声直接变成空，也不会把所有文档放进结果。dense 失败时，sparse 仍要执行同样的 Release、ACL 和 scope 过滤。

图谱和 Wiki 结果是上下文增强，不应绕过 RAG 证据。图谱关系有来源和构建版本才能进入重排上下文；Wiki 别名只能帮助路由，别名命中后仍返回可见原文。任何通道都不能把“名称相似”直接当作事实。

## 生产迁移怎样避免改变线上查询

新模型或索引参数先构建候选索引 I8，活动索引 I7 继续服务。离线评测用同一查询集比较精确基线、I7 和 I8；影子查询记录 I8 候选差异但不把结果交给用户。通过 Recall、权限和延迟检查后，在版本事务中切换活动指针。

迁移期间查询向量和文档向量必须同空间。I8 使用 M2 时，查询服务要按请求版本选择 M2，旧 Turn 继续用 M1/I7。缓存键加入模型和索引版本，不能让 M2 查询命中 M1 的候选。

切换后观察空结果、通道耗时、候选数、权限过滤数和答案引用失败。若 I8 Recall 退化，回滚到 I7，保留 I8 失败样本。回滚是切回不可变索引，不是把 I8 的参数改回旧值后猜测图结构已经恢复。

索引构建会消耗数据库 CPU、内存和磁盘，不能在业务高峰无计划运行。当前迁移通过预检创建 HNSW partial index，实际构建时间和并发影响需要在隔离或维护窗口测量。文章不伪造构建耗时或线上 p95。

## 自测从数据库契约到查询回归

Schema 测试确认向量列维度、余弦操作符、HNSW 条件和全文、精确、结构字段索引存在。当前测试可断言 SQL 含 active、index_status ready、Release 链接和 ACL 撤回条件；这证明查询没有忘记关键过滤，不等于 ANN 召回已经达标。

检索单元测试验证查询词、业务编号优先级、严格稀疏查询和有限放宽。密集 Embedding 失败时，Fake 模型抛超时，候选仍来自非 dense 通道；返回结果的标题、表头、前后邻接和结构字段不能丢失。

集成测试在隔离数据库插入同义 Chunk、相近编号、不同 Release 和无权限 Source。精确 KNN 结果作为基线，HNSW 结果与它比较；指定 Release 可以读取已固定但不是文档当前活动的版本；权限撤回后缓存 Chunk ID 会再次被过滤。

回归样本至少包含“外部连接由谁审批”“RA-204 的状态”“这个范围内的负责人”和一个没有答案的问题。分别断言目标 Source、精确编号、显式范围和安全空结果。再次执行时记录模型、维度、距离、索引、Release 和查询集版本。

pgvector 的职责是把向量比较变成可过滤、可评测的数据库查询。索引类型解决访问路径，Release 与 ACL 决定可见集合，混合通道补足精确和结构问题，Recall 回归决定近似代价是否值得。少掉其中任一层，距离再漂亮也不能独立构成答案证据。

## 一次索引参数变更怎样安全验证

改变距离函数、HNSW 的连接数或查询 `ef` 前，先固定同一批带标注查询和精确扫描结果，把精确扫描当作召回基线。实验组只替换索引或参数，保持 Release、Scope、过滤条件和 Top K 不变；比较 Recall@K、延迟分位数、过滤后的空结果率和不同文档类型的差异。若整体召回上升，却让表格编号查询下降，不能用平均值掩盖这个回归，应按查询桶分别决定是否启用。

索引重建期间让旧活动版本继续服务。候选索引完成构建后执行抽样校验，确认向量维度、模型版本、Chunk 身份和 ACL 字段一致，再在事务中切换活动指针。构建失败、资源不足或校验不通过时删除候选索引并保留旧版本，恢复过程不需要重新生成文档向量。这样数据库索引的实验不会扩大为一次不可逆的知识发布。

## 向量索引要用精确基线校准
HNSW 和 IVFFlat 用更低查询成本换取近似结果，过滤条件、探测参数、距离函数和 Top K 会共同改变召回。先用同一 Scope 的精确扫描建立基线，再比较近似索引的 Recall 与延迟。

没有索引命中、过滤后候选不足或向量服务不可用时，系统要选择全文、结构化通道或明确空结果。近似距离不能绕过 ACL、Release 和 Evidence 预算。
