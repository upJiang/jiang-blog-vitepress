# 并行工具执行怎样保持身份、顺序与预算

一个知识请求需要读取设备合规、审批条件和有效期，三次网络等待可以同时发生。并行解决的是等待时间，不能改变授权、状态和完成条件。把调用直接丢进 `gather`，常见结果是响应错配、取消不完整、共享预算被超用，或者一条失败后其他写操作仍继续。

## 先证明调用可以并行

调用级并发安全要同时看数据依赖和副作用。只读标签不是充分条件，读取可能使用不一致快照或占用同一锁；写入不同资源理论上可并发，也可能需要按业务顺序提交。

对一批候选逐项回答：

| 问题 | 证据 |
| --- | --- |
| 参数是否依赖兄弟结果 | 输入字段与依赖图 |
| 是否读取同一快照 | Release、事务和时间戳 |
| 是否会改变外部状态 | 工具副作用声明与领域规则 |
| 取消能否传到下游 | 客户端接口与清理测试 |
| 预算是否共享 | 批次计数器与原子扣减 |

有依赖的调用进入下一层。没有依赖但共享外部状态时，先确认一致性和限流，再决定是否并行。
## 批次需要自己的身份

模型给出三项候选后，运行时创建 `batch_id`，每个调用分配稳定 `call_id`。结果按 ID 归属，完成先后只影响事件时间，不改变语义顺序。

```text
batch-7
  call-1: device_compliance
  call-2: approval_policy
  call-3: expiration_rule
```

客户端可以按原规划顺序交付结果，或者按完成顺序逐项展示，前提是每项带工具名和调用 ID。依赖图和回答生成器不能用数组位置推断身份。
## 共享预算需要原子扣减

并行分支同时读取 `remaining=3`，每条都判断“还有额度”，最终可能执行三次以上。预算应在准入时原子预留，失败取消后再按规则释放，工具重试也要消耗额度。

```python
reservation = budget.reserve(batch_id, requested=len(calls))
if not reservation.granted:
    return stop("budget_exceeded")
```

批次预算和单调用预算分开。一个大结果可能用完 Token 预算，其他已经启动的读取仍会返回，融合器需要在超限时丢弃预览或停止生成，不把“并行已经发出”当作继续消耗的理由。
## 取消传播要覆盖三个层次

用户取消首先改变运行时状态，调度器停止创建新调用，调用适配器向支持取消的下游发送取消，无法取消的请求则等待回执并丢弃迟到结果。已经发生的写操作还要进入补偿或人工确认，不能假设网络断开等于撤销。

取消与完成并发时，状态版本决定谁获胜。已进入终态的批次拒绝新的成功写入，事件记录保留迟到响应供审计。
## 部分成功怎样交给上层

三条只读查询中一条超时，有几种产品选择：等待有限重试，使用两条结果生成带缺口的回答，或者整体拒答。选择由覆盖要求决定，不能让模型自行把“缺了有效期”当成无关信息。

结果状态可以这样汇总：

```text
success + success + timeout
  → evidence_incomplete
success + denied + success
  → scope_limited
unknown on a write call
  → manual_reconciliation
```

每种汇总结果都要绑定缺失调用和终止原因，用户才能判断是否补充权限或稍后重试。

不要用裸 `asyncio.gather` 处理需要部分失败的批次。默认异常传播可能让一个子任务失败后，其他任务继续运行但其句柄已经丢失。每个子任务的结果应转成值，最后由融合器决定批次状态。
## 顺序和融合是两件事

执行可以并行，答案中的证据顺序仍需稳定。融合器按问题分支或检索排名排序，去重使用稳定来源 ID，不能按网络完成时间排序。相同来源被两个分支返回时，保留一次并记录多个命中路径。

模型接收并行结果时，最好附带 `branch_id`、来源和状态。把三个结果拼成无标签大段文本，模型可能把设备状态误配到审批条件上。
## 失败、清理与重试

只读调用超时可以在总 Deadline 内退避。对未知写结果，先走回执查询；对参数错误，不应重试原请求；对权限拒绝，扩大并发没有意义。批次结束前必须等待可取消任务的清理完成，释放连接、文件句柄和预算预留。

重试策略按调用分类：

- 同一查询的短暂网络错误，使用有限重试和相同 `call_id` 的尝试序号。
- 服务端限流，依据响应时间和批次剩余预算退避。
- 业务拒绝，保留原错误并结束该分支。
- 下游结果未知，查询回执，禁止直接新建第二次副作用。
## 什么时候退回串行

分支依赖紧密、需要同一事务快照、下游连接有严格限额或故障恢复难以解释时，串行更稳。并行只把等待重叠起来，无法消除数据依赖和业务顺序。

固定的三步查询还可以用工作流节点表达，获得更清晰的重试和可视化。Agent 只在分支数量或工具选择确实由观察决定时参与规划，执行器仍可用并行批次。
## 测试需要比较并行与串行语义

单元测试固定每个调用的返回延迟，故意让 `call-3` 先完成，断言最终结果仍按调用身份归属。再注入一条失败、一条取消和一个未知写回执，检查预算不超用，终态不回退，迟到结果不产生副作用。

集成测试使用隔离服务验证连接池、下游限流和取消支持。并行后的总耗时改善只是观察结果，不能替代权限、证据覆盖和恢复不变量。

设计评审最后只需问一句：如果任意一条调用在任意时刻完成、失败或消失，系统能否凭 `batch_id`、`call_id`、状态版本和回执恢复出同一结论？回答不清楚时，先收紧并发范围。
