# 并行工具执行怎样保持身份、顺序与预算

[上一篇](/docs/ai-agent/tool-calling-contracts)已经把单次 Tool Calling 拆成目录、Schema、授权、执行回执和未知效果。现在把三个只读候选放到同一轮：设备合规、审批制度和有效期规则。

它们可能都需要等待网络。如果没有数据依赖，同时发出可以缩短等待；但“同时发出”不等于“可以安全并行”。结果可能先后无序，用户可能中途取消，多个分支还会争抢同一份调用或 Token 预算。

本文只解决一个批次的并发不变量：先判断能否并行，再建立身份和预算，最后融合部分结果。并发库的 API 只是执行手段，不能替代这些语义约束。

## 先证明候选可以并行

并行准入不是看到工具标记为只读就直接放行。每项候选都要回答依赖、快照、副作用、限流和取消五个问题。

### 依赖图先于线程池

如果审批结果决定设备查询的参数，设备查询就依赖审批，必须分两层执行。如果三项查询都只使用请求开始时的用户范围和同一份快照，它们才可能进入同一批次。

一个简单的准入清单如下：

1. 参数是否依赖兄弟调用的结果。
2. 是否需要读取同一事务或版本快照。
3. 是否会修改共享外部状态。
4. 下游是否支持并发、限流和取消。
5. 失败后是否能独立重试或明确交给上层。

前三项决定业务安全，后两项决定运行时是否能收口。存在数据依赖或并发能力不足时可以缩小批次或改为串行；如果正确性依赖同一快照而下游没有这种能力，就要拒绝执行或显式降低一致性要求，串行本身补不出快照。

### 只读也可能互相影响

三次读取都不写数据库，不代表它们观察到的是同一时刻。一个读取可能持有锁，另一个读取可能依赖正在变化的版本。快照、时间戳和一致性等级要进入工具合同，不能由调度器默认推断。

反过来，不同资源也不必然可以并行。两个写操作即使目标不同，也可能共享配额、审批或领域顺序。并行是对依赖证据的结论，不是对工具名称的结论。

## 批次身份要独立于完成时间

准入通过后，运行时创建一个 `batch_id`，再为每个候选分配稳定且唯一的 `invocation_id`。`batch_id` 表示这次并行集合，`invocation_id` 表示集合中由运行时调度的一次调用。供应商协议若提供调用关联，运行时将原始值归一化保存为 `provider_call_id`；它仍只负责模型交接，不能代替运行时分支身份。

### 结果按身份归属

设备查询最后提交却最先完成时，结果仍然属于设备的 `invocation_id`。如果代码把完成数组的第一个元素当成第一个候选，设备状态就可能被当成审批状态。

下面的关系只描述身份，不描述真实请求记录：

```text
batch_id
  ├─ invocation_id: device_compliance
  ├─ invocation_id: approval_policy
  └─ invocation_id: expiration_rule
```

示例中的名称是教学字段。真实系统还要把工具版本、状态版本和权限快照写入可回放事件，不能只保存工具名和一段返回文本。

### 完成顺序不等于语义顺序

网络完成顺序只反映哪个服务先返回。最终回答需要按问题分支、来源优先级或依赖顺序组织。调度器可以按完成顺序接收结果，融合器必须按业务键排序。

这两个顺序分开后，系统既能尽早记录已完成的调用，也不会让网络抖动改变用户看到的事实关系。持久化事件可以保留完成时间，面向模型的观察则要带上稳定的分支身份。

## 不同预算需要不同控制方式

并行分支会争抢调用次数、连接槽、响应字节、模型上下文和外部计费额度，还受同一个 Deadline 约束。这些资源不能塞进一个 `remaining` 整数。可预留的容量、只能持续计量的流量，以及不会随取消恢复的时间，控制方法不同。

### 容量在启动前原子预留

调用次数和连接槽能在启动前确定，应由调度器原子预留。预留成功才允许提交任务，提交失败按明确规则释放；重试也要重新占用调用额度，不能因为属于同一个 `invocation_id` 就免费。

```python
reservation = capacity.reserve(
    batch_id,
    calls=len(calls),
    connections=min(len(calls), connection_limit),
)
if not reservation.granted:
    return stop(reason="budget_exceeded")

try:
    results = run_batch(calls, reservation)
finally:
    capacity.release_unused(reservation)
```

这段代码只证明已知容量的原子预留和释放顺序。`capacity` 与 `run_batch` 是抽象接口，不能证明跨进程协调或其他预算已经正确。真实实现还要让预留和批次状态使用同一事务或版本边界。

### 流量在执行中持续计量

工具响应长度在请求发出前通常未知，需要为每个分支设置响应字节上限，并在流式读取时停止超额内容。模型上下文 Token 发生在结果进入下一次模型调用之前，装配器应先估算或计数，再按证据优先级裁剪，不能把完整工具响应都塞进上下文后才检查。

Deadline 由单调时钟计算剩余时间，时间过去不会因为任务取消而退还。外部计费额度若能预估，可以先做上限预留；不能准确预估时，要在执行后结算，并把已发生费用与未使用预留分开。于是“预算没有超用”需要按资源逐项证明，不能由一次 `reserve(len(calls))` 代替。

## 取消传播要覆盖三个层次

用户点击取消，首先改变运行时的批次状态。调度器停止创建新调用，适配器向支持取消的下游发送信号，融合器拒绝用迟到结果推进已取消终态。

### 可取消和不可取消要分开

网络客户端支持取消时，运行时应等待取消确认或明确记录失败。下游不支持取消时，客户端只能等待回执，再丢弃它对已取消回答的影响。丢弃迟到响应不等于外部动作被撤销。

只读请求通常可以丢弃迟到结果。写请求在发出前就必须创建并保留内部 `action_id`；若下游支持幂等，还要在首次请求前建立并持久化 `idempotency_key` 映射，把键随第一次请求发送。取消后仍要用原动作身份关联本地事件、外部回执和迟到结果，不能把连接断开当成回滚。

### 取消与完成竞争时谁获胜

如果一个调用和用户取消同时到达，状态版本决定哪一个事件可以推进批次。已经进入完成、失败或取消终态的批次拒绝迟到成功写入，但事件仍要保留，便于检查外部效果和解释用户看到的结果。

取消信号不是一个孤立布尔值。它必须同时影响调度、适配器和融合器，任何一层继续推进都会造成资源泄漏或状态倒退。

## 部分成功怎样交给上层

三项查询中一项超时，系统不能只返回“有两项成功”。上层需要知道缺失哪一项，缺口是否影响回答，以及应该等待、重试、补充权限还是拒答。

### 先判断覆盖要求

如果设备和审批已经足以解释失败，有效期缺失可能只需要提示“证据不完整”。如果有效期是重新提交的必要条件，融合器就必须停止生成完整建议，转入有限重试或等待。

结果可以收口成几种明确结论：

```text
success + success + timeout
  -> evidence_incomplete
success + denied + success
  -> scope_limited
unknown on a write call
  -> effect_unknown
```

这些状态是教学示例，不是固定供应商枚举。`effect_unknown` 只是恢复入口：有权威查询就核对，首次请求已携带有效幂等键才可复用原键重试，两者都没有时才进入 `manual_reconciliation`。每种结论都要绑定缺失的 `invocation_id`、终止原因和可执行的下一步，不能让模型根据一个空数组自行猜测。

### 融合要稳定排序和去重

同一来源可能被多个分支返回。融合器按稳定来源标识去重，按问题分支或检索排名排序，不能按网络完成时间排序。传给模型的每条观察都应带分支身份、来源和状态，避免把设备证据误配给审批条件。

融合器的职责是解释缺口，不是掩盖失败。只要关键证据缺失，它就应保留 `evidence_incomplete`，把是否继续交给上层策略，而不是用自然语言把结果润色成完整答案。

## 并行代码的控制点

仓库示例可以用线程池或任务组执行一批本地工具，但它只证明调用身份和返回顺序的控制流。真实并行实现还要验证连接池、下游限流、快照、取消支持和未知写回执。

```python
futures = {
    executor.submit(execute_call, call): call.invocation_id
    for call in calls
}
completed = {}
for future in as_completed(futures):
    result = future.result()
    completed[result.invocation_id] = result

# 网络完成顺序不稳定，输出按原业务顺序重排。
ordered = [completed[call.invocation_id] for call in calls]
```

前文已经说明为什么需要 `invocation_id`。这里的代码只展示“按身份收集，按业务顺序返回”，不包含授权、预算原子性、取消传播和未知副作用处理，不能直接作为生产执行器。

不要用裸 `gather` 处理需要部分失败的批次。一个任务抛出异常后，其他任务可能仍在运行；如果句柄丢失，调度器就无法等待清理、记录迟到响应或释放预算。每个任务都应转换成结构化结果，最终由融合器决定批次状态。

## 失败、清理与重试

只读调用的短暂网络错误，可以在总 Deadline 内有限退避。参数错误不应重复原请求，权限拒绝不应通过增加并发解决，业务拒绝要保留原状态。

未知写结果按下游合同处理：有权威查询就用外部系统认可的回执或业务引用核对；首次请求已携带有效 `idempotency_key` 时，才复用原键受控重试；两者都没有时进入人工核对。内部 `action_id` 只负责本地关联，除非请求前已映射成下游认可的查询引用。新建第二个动作身份会把“是否已执行”变成重复副作用风险。批次结束前还要等待可取消任务清理完成，释放未使用的容量预留。

### 何时串行，何时拒绝

存在数据依赖、授权顺序或严格并发限额时，串行能消除执行重叠：

- 分支参数依赖兄弟结果。
- 外部服务有严格并发限额或取消不可达。

另一些缺口不能由串行修复：

- 正确性要求同一快照，但下游不支持共享快照。此时应改用支持快照的读取边界，或明确降低一致性要求并保留每项结果的版本；两者都不允许就拒绝执行。
- 写操作的回执、幂等或补偿路径无法证明。串行仍可能在超时后留下未知副作用，应停在人工审批或拒绝写入。
- 关键证据缺失时无法定义批次终态。调度顺序不会补出完成条件，应先重写覆盖规则。

并行只重叠等待时间，不能消除数据依赖、授权顺序和恢复责任。固定的三步查询若一直稳定，也可以继续由工作流节点按顺序表达；Agent 只负责决定何时需要扩大调查范围。

## 测试需要比较并行与串行语义

测试先固定每个调用的返回延迟，故意让最后提交的调用先完成，断言结果仍按 `invocation_id` 归属并按业务顺序输出。再注入一条失败、一条取消和一条未知写回执，检查预算没有超用，终态不会回退。

并发测试还要检查：

- 重复 `invocation_id` 在提交前被拒绝。
- 调用和连接容量的原子预留不会超上限，失败分支释放未使用容量。
- 响应字节在读取时受限，模型上下文在装配前计量，Deadline 不因取消回退，外部费用按预留与结算分别记账。
- 用户取消后不创建新任务，迟到结果不能覆盖取消终态。
- 部分结果保留缺失调用和终止原因，不伪装成完整证据。
- 同一个来源在融合后只出现一次，结果排序不受网络完成顺序影响。

集成测试再验证连接池、下游限流、真实取消支持和写回执。并行后的总耗时改善只是观察结果，不能替代权限、证据覆盖和恢复不变量。

## 结尾：让并行只改变等待，不改变语义

回到远程访问调查，设备、审批和有效期查询只有在依赖、快照和限流条件成立时才进入同一批次。`batch_id` 记录集合，`invocation_id` 归属运行时结果，分层预算分别限制容量、流量、时间和费用，取消传播阻止新任务和错误回写，融合器按业务顺序处理部分证据。

因此，并行的价值只是重叠等待时间，不能改变授权、状态和完成条件。任何分支先完成、失败、取消或迟到，系统都应凭身份、预算和回执恢复出同一结论。
