# 并行工具执行：如何保证身份、预算与结果收敛

[上一篇](/docs/ai-agent/tool-calling-contracts)把单次工具调用拆成目录、Schema、授权、执行回执和未知效果。

现在把问题扩大一点：远程访问调查同时需要设备合规、审批制度和有效期规则三份证据，是否应该把三个工具一次发出？

并行可以重叠网络等待，但它也会引入三个新风险。结果可能乱序，分支可能争抢不同资源，用户还可能在其中一路返回前取消请求。本文只研究一个运行时批次，目标是证明“可以并行”之后，仍能把结果归属、预算消耗和不完整结论说清楚。

## 先证明候选可以并行

并行准入发生在线程池或任务组之前。调度器要先检查每个候选使用哪些输入、观察哪个快照、是否产生副作用，以及下游能否承受并发。工具名称上写着“只读”，只能说明它不应修改业务状态，不能自动证明这些条件都满足。

### 依赖关系决定批次边界

假设审批查询返回的组织范围，才是设备查询的参数。设备查询依赖审批结果，此时两者不能放进同一批次；先完成审批，再创建下一批次，结果才有明确含义。

本案例的三项查询都只读取请求开始时已经确定的主体、权限范围和资料版本。它们之间没有参数依赖，因此可以提出同批候选。准入记录的不是“用了并发库”，而是这份依赖证据。

### 共同快照和下游能力也要成立

三次读取都不写数据库，也不代表它们看到同一时刻。制度服务可能已经切换版本，设备服务仍返回旧缓存。工具合同必须说明快照或版本要求；如果业务要求同一快照而下游不支持，串行也补不出一致性，只能换读取边界或拒绝本批次。

还要检查连接池、服务限流和取消能力。两个只读请求共享一个严格为一的连接配额时，业务上虽然互不依赖，运行时仍必须拆批。准入结果应明确是“同批、分批”还是“拒绝”，这样下一步调度才有输入。

准入通过后，三路调查从“证据不足”变成“允许同批执行”。接下来需要保证每个返回值仍然找得回自己的问题。

## 用分层身份保存归属

一个批次使用 `batch_id` 表示三路集合；集合中的每个逻辑调用使用独立的 `invocation_id`。如果供应商协议返回了调用关联，再原样保存为 `provider_call_id`。供应商关联只能帮助追踪模型交接，不能代替运行时分支身份。

### 完成时间不能改变调用身份

可以把归属关系画成：

```text
batch_id
  ├─ invocation_id: device_compliance
  ├─ invocation_id: approval_policy
  └─ invocation_id: expiration_rule
```

这里的名称是教学用业务键，不是供应商生成的真实编号。设备查询最后提交却最先完成时，结果仍归属于 `device_compliance`。如果融合器按完成数组的位置填充，网络抖动就会把设备证据错配给审批分支。

运行时事件可以按发生时间记录，面向模型的观察却要带上调用身份和业务键。这样既保留了“哪一路先返回”的诊断事实，也不会让完成顺序改变用户看到的语义顺序。

身份固定之后，三路调用会同时消耗资源。不同资源的消耗时点不同，不能只设置一个模糊的剩余额度。

## 预算不是一个 `remaining` 数字

调用次数、连接槽、响应字节、模型上下文 Token、Deadline 和外部费用属于不同预算。它们有不同的预留、计量和释放规则，混成一个整数会掩盖“哪一项先耗尽”。

### 能预留的容量先原子占用

调用数和连接槽在提交前可知，应该由调度器一次预留。预留失败就不创建任务；提交过程中发生异常，只释放没有使用的部分。重试是新的实际请求，不能因为沿用同一个 `invocation_id` 就免除调用额度。

```python
reservation = capacity.reserve(
    batch_id=batch_id,
    calls=len(calls),
    connections=min(len(calls), connection_limit),
)
if not reservation.granted:
    return BatchStopped(reason="capacity_exceeded")

try:
    results = run_batch(calls, reservation)
finally:
    capacity.release_unused(reservation)
```

这段代码只展示“先预留、再提交、最后释放未用容量”的控制顺序。`capacity` 和 `run_batch` 是抽象接口，不能证明跨进程预算原子性、授权或下游限流；这些能力要由真实实现和集成测试补证据。

### 流量、Token、时间和费用分别计量

响应字节和结果条数要在读取过程中持续计量，达到上限就停止接收或截断为明确的超限结果。工具输出进入下一次模型调用前，装配器还要估算 Token，并按证据优先级裁剪；不能把完整响应塞进上下文后才发现窗口已满。

Deadline 使用单调时钟计算剩余时间。取消或某一路提前结束都不会把已经过去的时间返还。费用如果能预估，可以先预留上限；不能准确预估时，就把预留和实际结算分开记录。只有逐项检查，才能回答批次是否超出预算。

在三路调查中，这意味着“容量允许同批”并不等于“最终证据一定能进入上下文”。预算门通过后，调度器才可以开始工作；接下来还要定义用户取消时哪些工作必须停下。

## 取消先停止新工作

用户取消首先改变批次控制状态。调度器停止创建尚未提交的分支，适配器根据下游能力发出取消信号，融合器拒绝用迟到结果推进已经取消的回答。三个层次都要执行，单独设置一个布尔值不够。

### 可取消和不可取消分开处理

网络客户端支持取消时，运行时应记录取消请求和下游确认；如果下游不支持取消，客户端只能等待回执，再丢弃它对当前回答的影响。丢弃迟到响应，只表示不再采用它，不表示外部动作已经撤销。

本案例是只读调查，迟到的设备结果可以作为诊断事件保存而不进入已取消回答。若换成写操作，副作用发出前必须已有动作身份和下游可识别的幂等键。取消发生在发送之后，只能进入动作核对流程，不能把未知效果写成“未执行”。

### 取消与完成同时到达时保持单向终态

批次一旦进入完成、失败或取消终态，就拒绝迟到事件再次推进它。迟到事件仍要保留，便于确认外部效果、释放预算和解释为什么用户没有看到那条结果。

因此，取消并不是“清空 futures”。它还要停止新调度、等待可等待任务清理，并让融合器知道哪些分支永远不会补齐。状态边界明确后，部分结果才能被诚实地交给上层。

## 部分结果怎样形成可用结论

三项查询中一路超时，返回“两项成功”还不够。上层必须知道缺少哪一路、缺口是否影响当前问题，以及下一步是等待、重试、补权限还是拒答。

### 先判断证据覆盖，再决定批次状态

如果设备和审批已经足以解释失败，有效期缺失可以收口为“证据不完整”；如果有效期是重新提交的必要条件，融合器就不能生成完整建议，而应停在等待或补查。

可以用结构化结果表达这种差异：

```text
success + success + timeout
  -> evidence_incomplete
success + denied + success
  -> scope_limited
cancelled before dispatch
  -> cancelled_without_execution
```

这些状态是教学示例，不是固定供应商枚举。每个状态都要绑定缺失的 `invocation_id`、终止原因和可执行下一步。空数组不能让模型自行猜测“没有证据”还是“请求没有发出”。

### 归约按业务键排序并去重

融合器先按调用身份接收结果，再按问题分支或稳定来源键排序。相同来源被多个分支返回时，按来源标识去重；网络完成时间只能写入诊断字段，不能决定最终顺序。

传给模型的每条观察都应包含分支身份、来源和状态。这样模型能区分“审批查询被拒绝”和“审批查询尚未返回”，也能知道是否还有必要补查。融合器的职责是解释缺口，不是把失败润色成完整答案。

## 用最小代码固定归约不变量

前面已经说明为什么不能按完成位置认领结果。下面的本地示例只展示按身份收集、按业务顺序返回；它不包含授权、预算、真实取消或外部写入。

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

def collect_in_order(calls, execute_call):
    with ThreadPoolExecutor(max_workers=len(calls)) as executor:
        futures = {
            executor.submit(execute_call, call): call["invocation_id"]
            for call in calls
        }
        completed = {}
        for future in as_completed(futures):
            result = future.result()
            completed[result["invocation_id"]] = result

    return [
        completed.get(call["invocation_id"], {
            "invocation_id": call["invocation_id"],
            "status": "missing",
        })
        for call in calls
    ]
```

`as_completed` 只负责尽快观察完成任务，字典键负责保存归属，最后一次遍历才恢复业务顺序。生产代码还需要把异常转成结构化失败、检查重复身份、遵守 Deadline，并等待取消后的清理；这个片段不能证明线程池之外的任何分布式保证。

## 测试要证明哪些不变量

先固定三路返回延迟，让最后提交的分支最先完成，断言结果仍按 `invocation_id` 归属并按业务键输出。再注入一条超时、一条拒绝和一次用户取消，确认缺失原因没有被压成空值，批次终态不会回退。

预算测试分别覆盖调用/连接容量、响应字节、上下文 Token 和 Deadline。需要验证预留失败不创建任务，未用容量会释放，时间不会因取消返还，超出响应上限会形成可解释结果。费用预留和实际结算也应分开断言。

集成测试再检查真实连接池、下游限流和取消支持。写操作的超时测试沿上一篇的 `action_id`、幂等键和回执核对，不把“客户端断开”当成 exactly-once 证明。并行耗时变短只是观察结果，不能替代权限、覆盖和恢复不变量。

## 结尾：并行只改变等待，不改变语义

回到远程访问调查，设备、审批和有效期查询只有在依赖、快照和下游能力成立时才进入同一批次。`batch_id` 记录集合，`invocation_id` 归属分支，预算按资源维度计量；取消停止新工作，融合器保留迟到事实和缺失原因。

因此，并行的价值是重叠等待时间，不是让系统更快地猜测。任何分支先完成、失败、取消或超时，都必须依据稳定身份和覆盖规则形成同一类可解释结论。
