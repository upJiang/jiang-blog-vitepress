# Message、Token 与上下文：模型一次调用看到了什么

沿一条请求解释消息角色、分词、输入窗口、输出预算和停止原因。**Message**、**Token**、**Context** 分别指向同一条执行链上的不同对象：开发者规则、用户问题、消息历史和本次可见资料进入系统，消息角色、内容片段、Token 估算、输入上限、输出上限和停止原因保存处理中间状态，最终得到文本、结构化对象、工具调用候选、完成状态或可分类错误。

Message、Token 与上下文位于模型调用与应用控制边界。它的主要机制是应用按角色和顺序构造消息，Tokenizer 再把内容编码为 Token；上下文窗口同时容纳输入与预留输出。角色优先级混淆、工具结果未配对、按字符误算 Token、输入占满窗口和截断后丢失当前问题会让链路在不同位置停止，错误记录必须保留发生阶段、当时的状态和终止原因。

::: info 贯穿示例

Message、Token 与上下文场景：用户询问为什么自己的远程访问申请被拒绝，系统需要在不猜测账号状态的前提下给出解释。身份、权限、版本和业务事实由应用提供，模型与外部内容只产生需要检查的候选。

:::

这次推演用请求快照、响应类型、停止原因、用量字段和业务校验记录把请求和终态关联起来。与聊天记录、Tokenizer、模型上下文窗口和外部记忆比较时，重点看输入来源、状态所有者、下一步的决策者和失败终点。

一次 Message、Token 与上下文执行可以画成“装配输入 → 发送请求 → 解析响应 → 校验候选 → 写入结果”。开发者规则在入口出现，消息角色记录进度，文本只有通过当前主题的校验条件后才会成为可交付结果。

角色优先级混淆与工具结果未配对会产生不同证据。前者先检查消息角色和输入来源，后者沿调用记录定位依赖或状态冲突；不区分发生位置，重试会掩盖原始原因。

Message、Token 与上下文与聊天记录的共同点不代表它们可以互换。当前主题拥有内容片段，相邻组件只通过契约读取或提交候选，不能直接修改这个状态。

理解 Message、Token 与上下文不能停在定义。还要解释应用按角色和顺序构造消息，Tokenizer 再把内容编码为 Token；上下文窗口同时容纳输入与预留输出，再用角色优先级混淆这个反例检查定义是否真的约束了输入、状态和终态。

## 问题从一次模型调用开始

先把三个词分开。**Message** 是应用组织输入的结构单位，它带有角色、内容和顺序；**Token** 是模型实际处理的编码单位，中文字符、英文单词、数字和标点不会按固定比例换算；**Context** 是一次调用真正装配进去的全部材料，包括规则、消息历史、检索证据和工具结果。三者处在同一条输入链上，却不是同一层的概念。

假设用户问“我的账号为什么不能远程访问”。应用首先创建 user message，再把开发者规则放在更高优先级的位置。如果需要补充账号状态，程序先调用受控工具，并把工具结果与原来的 call_id 配对。只有这些内容被重新装配进请求，它们才成为本次上下文。模型不会因为数据库里已经存在账号记录就自动看到它，也不会因为上一轮回答过相似问题就自动保留记忆。

这条输入链解决两个常见误解。第一，聊天界面里看得到的历史，不一定全部发送给模型；应用可能裁剪、摘要或只取最近几轮。第二，字符数不是 Token 数。预算必须使用目标模型对应的 Tokenizer 或供应商返回的 usage 核对，按“一个汉字等于一个 Token”估算只能作为粗略预警，不能作为硬限制。



## Message、Token 与上下文是什么，处在哪一层

Message 属于应用协议。角色告诉模型一段内容在本次调用中扮演什么作用，顺序则决定对话怎样展开。常见输入至少包含开发者规则和用户消息；发生 Tool Calling 时，还会出现模型提出的调用与程序返回的工具结果。工具结果必须绑定原调用，单独塞入一段“查询成功”的文字会丢失来源，也可能让模型误把另一次调用的结果用于当前问题。

Token 属于模型编码过程。应用提交文本或多模态内容后，服务会把它们编码为模型可处理的序列。上下文窗口通常同时容纳输入和输出，因此不能把窗口上限全部给历史消息。若计划让模型最多输出一段较长回答，输入装配阶段就要预留输出预算，否则请求可能在入口被拒绝，或者输出在未完成时因长度限制停止。

Context 属于一次请求。长期记忆、知识库、数据库和聊天记录都在模型之外，只有经过选择并放入请求的片段才进入上下文。这个区别决定了数据治理方式：删除长期记忆要修改外部存储和后续装配，撤回一份知识文档要让对应 Release 与缓存失效，不能只在 Prompt 里要求模型“忘记”。



## 输入消息、状态与输出契约

一次调用可以用下面这份最小记录表示：

| 阶段 | 需要保存的字段 | 用途 |
| --- | --- | --- |
| 装配前 | `request_id`、模型、规则版本、历史范围 | 解释为什么选择这些材料 |
| 装配后 | 消息角色、内容引用、Token 估算、预留输出 | 在发送前发现超限 |
| 返回后 | 响应状态、停止原因、文本或结构项、usage | 区分完成、截断和空响应 |
| 业务校验 | 证据版本、权限结果、字段校验问题 | 防止把候选当事实 |

预算可以写成一个明确不等式：`固定规则 + 当前问题 + 历史 + 检索证据 + 工具结果 + 预留输出 <= 上下文窗口`。真正需要裁剪时，先保护开发者规则、当前问题、未完成工具调用和本轮证据，再处理较旧历史。不能从数组开头机械删除，因为最早的消息里可能保存了当前任务的约束。

输出也不是只有文本。一次调用可能返回结构化对象、工具调用候选、拒绝信息或不完整状态。应用要按响应项类型读取，而不是假设数组第一个元素永远是文本。usage 用于成本和容量核对，不用于证明内容正确；`status=completed` 也只表示模型服务完成了请求，不表示业务事实已经验证。



::: warning Message、Token 与上下文的可信边界

文本通过结构校验后仍是候选。身份、权限、知识版本与业务事实由应用从可信服务读取，核对完成后才能执行或交付。

:::

## 内部处理顺序

完整顺序是：应用收集材料并标注来源，按角色装配 Message，使用目标模型的规则估算 Token，预留输出后执行超限策略，再发送请求。服务返回响应项和停止状态，应用解析后继续做业务校验。任何一步失败，都应保留发生位置。

以窗口超限为例，正确处理不是直接重试同一个请求。程序先输出各类材料的预算明细，确认是历史、检索证据还是工具结果占用过多；随后按既定优先级缩减。摘要只能替换已经完成且可回查的历史，未完成动作、否定约束和当前证据不能被摘要成模糊结论。裁剪后重新估算，并在记录中保存被移除的引用和原因。

停止原因同样需要进入控制流。正常完成可以继续业务验证；长度截断意味着回答可能缺少结尾或结构字段，不能直接交付；内容过滤、服务错误和取消各有不同处理。把所有非空文本都视为成功，会让半个 JSON、缺少引用的答案或中途停止的工具参数进入下游。

最后再核对一次界面和真实请求是否一致。界面可能展示完整会话，实际请求却只发送摘要；调试面板可能显示字符数，供应商计费却按 Token；应用可能收到 completed，业务验证却把答案拒绝。把装配清单、模型返回和业务终态分开保存，才能定位偏差发生在哪一层。测试还应固定一份长对话，分别触发正常装配、主动裁剪和无法满足预算三条路径，并断言当前问题与开发者规则始终保留。这样才能证明窗口策略没有悄悄改变任务，结果也能重复验证。

Message、Token 与上下文的处理机制是：应用按角色和顺序构造消息，Tokenizer 再把内容编码为 Token；上下文窗口同时容纳输入与预留输出。这条描述要落成可检查的状态变化，不能只停在框架节点名称上。

装配输入接收开发者规则并建立消息角色。入口校验未通过时就地结束，后续模型、检索器或工具调用次数保持为零。

发送请求固定身份、范围、配置版本和绝对 Deadline。子步骤只继承剩余时间，不能各自重新获得完整超时。

解析响应读取内容片段并执行主题逻辑。调用参数由应用组装，外部返回先保存为候选，尚未获得修改领域状态的资格。

校验候选检查候选的结构、范围、版本和主题不变量。文本缺少来源、落在旧版本或越过权限时，当前状态停在 rejected 或 failed。

写入结果先保存文本与终止原因，再产生事件或通知。交付失败可以重放，核心状态写入失败则不能对外宣称完成。

解析响应出现部分结果时，由任务合同决定保留、补偿还是整体丢弃。可重建制品可以重新生成，外部副作用需要查询回执或执行补偿。

实现可以使用函数、Graph、Middleware 或 Workflow，消息角色的所有权和角色优先级混淆的停止规则不会随框架改变。

部分成功需要在步骤边界处理。解析响应已经产生一部分文本时，程序按任务合同决定保留、补偿或整体丢弃，并记录未完成项，不能默认为全部成功。

每个步骤都应有逆向动作或明确的不可逆说明。可重建制品可以删除后重算，已发送的外部命令只能查询回执或补偿；两类失败不能共用同一重试函数。

## 沿同一个问题推演一次

用“Message、Token 与上下文场景：用户询问为什么自己的远程访问申请被拒绝，系统需要在不猜测账号状态的前提下给出解释”推演一次 Message、Token 与上下文。入口创建 request_id，读取可信身份，把开发者规则和当前版本写入初始状态。

装配输入阶段生成消息角色与输入摘要。若用户问题缺失，请求返回 rejected，并指出缺少哪项材料，不继续消耗模型或外部服务配额。

发送请求阶段冻结 scope、release、policy 和 deadline_at。用户或模型在正文中提供的同名值只作为普通内容，不覆盖运行时快照。

解析响应按“应用按角色和顺序构造消息，Tokenizer 再把内容编码为 Token；上下文窗口同时容纳输入与预留输出”推进。每次依赖调用保存 call_id、参数摘要、开始时间与状态版本，后续才能判断超时前是否已经产生结果。

候选结果对应文本、结构化对象、工具调用候选、完成状态或可分类错误。校验候选逐项检查权限、版本与领域约束，问题列表为空才允许形成下一状态。

写入结果写入终态。客户端断开只影响交付通道，不触发核心逻辑重跑；重新连接时读取已经保存的状态或事件游标。

故障注入选择按字符误算 Token。程序保留原候选和错误位置，只重做失败边界，不能从入口复制整个任务并产生第二份状态。

推演结束后用 request_id 关联消息角色、文本与终止原因。测试据此排除并发请求串线，也能确认失败路径没有遗留未关闭资源。

Message、Token 与上下文在输入拒绝时不调用依赖，正常路径按 5 个阶段推进，有限修复只重做失败边界。调用次数是控制流断言，不是性能宣传。

Message、Token 与上下文的最终记录用 request_id 关联消息角色、文本和失败问题，测试据此证明结果来自本次执行，没有混入并发请求。

## 正常返回要检查什么

Message、Token 与上下文正常完成时，消息角色、内容片段和文本指向同一次执行。重复读取返回同一终态，未完成分支已经取消或有明确所有者。

请求快照、响应类型、停止原因、用量字段和业务校验记录用于还原处理过程。它们可以按阶段和版本聚合，敏感正文留在受控存储中，不复制到日志与指标。

结构化对象可能是合法的空结果。空结果要带范围、版本和原因；如果任务要求必须找到材料，则同一个空结果应进入拒答而非成功。

依赖返回成功状态只证明传输完成。Message、Token 与上下文还要检查文本是否满足业务范围、质量阈值和当前版本，明确拒绝也可能是正确终态。

并发完成时，每个分支保留自己的身份和局部预算。汇合节点按任务合同接纳可用结果，慢分支不能抹掉已经确认的记录。

消息角色的状态迁移必须单调：完成不能退回运行中，取消不能被迟到结果覆盖，失败重试也不能绕过入口已经固定的权限。

Message、Token 与上下文的成功证据最终要同时回答输入是什么、执行了哪些步骤、交付了什么以及为什么停止；任一项缺失都应留在未确认状态。

Message、Token 与上下文把业务验收与服务健康分开。依赖返回 200 只说明传输成功，文本仍要满足当前范围和质量要求；明确拒答也可能是正确终态。

Message、Token 与上下文的观测指标按阶段和版本聚合。错误率、空结果率、拒绝率、恢复次数与资源消耗回答不同问题，不能压成一个成功率。

## 错误从哪里产生

Message、Token 与上下文按输入、状态、依赖、结果和交付五个位置分类错误。分类决定恢复动作，不能用同一个重试循环处理全部失败。

遇到角色优先级混淆时，系统要返回稳定的错误类型、发生阶段和可重试标记。Message、Token 与上下文保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

遇到工具结果未配对时，系统要返回稳定的错误类型、发生阶段和可重试标记。Message、Token 与上下文保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

遇到按字符误算 Token 时，系统要返回稳定的错误类型、发生阶段和可重试标记。Message、Token 与上下文保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

遇到输入占满窗口时，系统要返回稳定的错误类型、发生阶段和可重试标记。Message、Token 与上下文保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

遇到截断后丢失当前问题时，系统要返回稳定的错误类型、发生阶段和可重试标记。Message、Token 与上下文保存当时的输入摘要与状态版本，再由拥有该依赖的组件决定重试、降级或终止。

Message、Token 与上下文结束错误处理时保存终态、可重试性和资源清理结果。后台扫描器依靠这些字段区分仍在运行、等待恢复和已经失败的任务。

Message、Token 与上下文在执行前写入绝对 Deadline、最大动作数、重复签名、无进展阈值、预算和人工取消信号。任一条件触发后都不再创建新工作。

Message、Token 与上下文把重试时间和次数计入总预算。依赖连续失败会减少后续额度，达到上限后保留原始错误，不再用模型重新措辞掩盖失败。

Message、Token 与上下文的清理动作可以重复执行。临时对象、文件句柄、子进程、连接或 Lease 仍被活动任务引用时，清理器必须拒绝删除。

## 怎样测试而不伪造在线结果

固定输入快照、断言响应类型、覆盖空结果与超时，并核对业务字段是否由可信系统补齐。测试需要显式给出开发者规则、初始消息角色、预期文本和终止原因，不能只断言返回值非空。

Message、Token 与上下文的单元测试用 Fake Adapter 固定文本与错误，断言参数、调用顺序、状态修订和清理动作。它只证明本地控制逻辑。

契约测试围绕开发者规则、消息角色和结构化对象构造合法与非法样本。Schema 解析成功后继续检查权限、版本与领域不变量。

故障测试注入角色优先级混淆和工具结果未配对，记录依赖是否被调用、状态是否改变、资源是否释放，以及同一身份重试会不会重复执行。

在解析响应前后终止执行进程，可以检查恢复边界。调用前退出允许重新领取；外部动作后退出先查回执；终态写入后只重放交付。

集成测试连接真实协议与隔离存储，检查序列化、约束、并发和超时。需要在线服务时单独记录服务版本、时间、配置与是否具备凭证。

Message、Token 与上下文的回归报告要保留失败类型分布。明确拒绝变成超时、权限错误变成普通空结果，都属于行为回归，即使总通过数没有变化。

性质测试可以补足固定样本。随机改变消息顺序、重复提交、完成顺序或状态版本，断言权限不扩大、终态不倒退、同一身份不产生两次副作用。

离线评测关注固定输入下的质量变化，运行时测试关注控制和恢复。Message、Token 与上下文只有两类证据都存在，才能同时回答“结果是否合格”和“系统是否安全完成”。

## 生产接入的版本与容量

Message、Token 与上下文长期运行后，输入 Schema、消息角色结构和依赖配置可能独立升级。每次执行固定一组版本，旧记录才能被正确读取或迁移。

Message、Token 与上下文的容量主要受上下文长度、并发请求、供应商限流和输出预算影响。并发可能缩短单次等待，也会同时占用连接、配额、内存和下游吞吐，容量要沿调用链逐层核算。

候选版本在固定样本上比较正确性、错误类型、延迟和资源消耗。角色优先级混淆等安全红线回归时直接停止发布，不能用平均质量抵消。

角色优先级混淆的降级路径在发布前写好：减少非关键增强、返回已经确认的结果，或明确暂时无法确认。缺失事实不能交给模型补写。

Message、Token 与上下文的运行手册从 request_id 定位请求快照、响应类型、停止原因、用量字段和业务校验记录，再决定重试、补偿、取消或回滚，无需先展开完整敏感内容。

数据保留按证据用途分级。聚合字段可以保留更久，原始输入和大结果设置短期限、访问控制与删除通道。

Message、Token 与上下文先在单进程实现状态、超时、错误和测试；只有恢复与容量证据提出要求时，再增加队列、Lease、分布式缓存或工作流引擎。

Message、Token 与上下文的监控阈值要对应可执行动作。上下文长度、并发请求、供应商限流和输出预算中的某项接近上限时，系统可以限流、排队、缩小候选或切换保守路径；只发送告警不会保护正在运行的任务。

回滚要覆盖代码之外的状态。Message、Token 与上下文若改变 Schema、缓存键或持久化记录，旧版本是否还能读取新写入数据必须提前验证；无法双向兼容时采用候选版本隔离。

## 适用范围与相邻概念

采用 Message、Token 与上下文前先画最小控制图。固定函数已经能完成任务时，新增模型决策和跨进程状态只会扩大测试与运维范围。

Message、Token 与上下文与聊天记录的差别落在控制权：谁选择下一步，谁保存消息角色，谁确认文本可信。

Tokenizer 可以与 Message、Token 与上下文组合。组合之后，外部知识仍需授权，工具调用仍需校验，模型输出仍停留在候选状态。

Message、Token 与上下文适合价值足够、失败可观察、动作可约束且预算可接受的任务。高风险且不可逆的决定需要确定性规则或人工批准。

格式正确但事实错误的文本是必要反例。系统若直接进入成功，说明业务验证缺失；保留候选并给出证据问题，才符合边界。

执行期间修改内容片段可以检验并发设计。旧动作仍能覆盖新状态，说明版本或 Lease 有缺口，增加 Prompt 规则无法修复竞态。

Message、Token 与上下文增加了状态、调用、恢复责任和故障面。设计记录应明确获得的能力，也列出新增的退出、降级与回滚路径。

演进可以从最小闭环开始：一个调用、一个状态对象、一组明确错误和几条确定性测试。真实 Trace 证明瓶颈后，再加入并发、缓存、队列或更复杂策略。

相邻文章提供的能力只按依赖引入。聊天记录解决不了当前失败时，不应为了目录完整强行组合；设计保持可替换，后续需求出现再扩展。
