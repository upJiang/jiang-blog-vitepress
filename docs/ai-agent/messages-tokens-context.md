# Message、Token 与上下文：模型一次调用看到了什么

先看一个具体请求。员工问：“我的远程访问为什么被拒？”系统里已经有员工的申请状态，也有当前生效的访问制度。模型仍然无法直接读取这两份数据。只有应用把它们整理进本次请求，模型才有机会基于事实作答。

这次请求会经过一条严格的装配链：先把材料编码成 **Message（消息）**，再按 **Token（词元）** 计算容量，最后生成本次调用实际可见的 **Context（上下文）**。三者分别描述协议、成本和可见状态。混用它们，排障时就会把“数据没装进来”“窗口超限”和“模型拒答”误判成同一个问题。

## 先沿请求找到 Message 的边界

应用提交给模型的通常是一组有序消息。每条消息包含角色和内容，内容还可能是文本、图片、工具调用或工具结果。角色影响解释优先级，消息顺序影响指代关系，但它们只构成输入协议，不能替代认证和授权。

把案例中的材料先写成最小消息序列：

```text
system：只能回答当前员工可见范围内的问题；无证据时说明缺口。
user：我的远程访问为什么被拒？
tool：申请状态=rejected；原因码=device_not_compliant；state_version=42
tool：制度版本=v7；设备合规是审批前置条件；source=policy-remote-access
```

这里的 `tool` 消息不是模型自己发现的事实。应用先检查员工身份和文档范围，再把工具回执序列化。若 `state_version=42` 已过期，装配器应重新读取状态，不能让模型替应用猜测最新值。

### 角色影响解释，不能承担权限

系统规则、用户输入、助手历史输出和工具回执各有职责。网页、检索片段和用户粘贴的文本都可能包含指令，它们即使被放进消息，也仍是外部内容。真正的权限判断必须发生在工具调用前，由认证上下文、租户范围和策略版本共同完成。

因此，把权限规则写进 system 只能约束模型的候选输出。一个缺少 ACL 检查的数据库工具仍可能返回越界数据。这个边界会在后文的 Context 装配和工具执行阶段再次出现。

### 工具调用必须按 ID 成对回填

模型可能在一个回合提出多个工具调用。应用需要为每次调用保存稳定的 `call_id`，并把同一个 ID 写入结果。并行执行按完成时间返回，不能按数组位置配对，否则甲工具的结果可能被当成乙工具的观察。

回执还要携带状态。权限拒绝、超时、成功但为空和服务暂时不可用，会导向不同的控制流。给模型的摘要可以很短，运行时保存的原始回执、开始时间、状态版本和错误类别不能丢失。

Message 解决了材料以什么身份出现，接下来还要解决容量问题。消息序列一旦确定，模型并不会按字符数收费，它会先把序列编码成 Token。

## Token 把“能放多少”变成可计算的约束

应用提交前会经过 tokenizer。Token 不是字符的固定替身，中文、代码、数字和工具 Schema 的切分方式都不同。用“最多两万字”估算窗口，只能做粗略提示，不能作为调用准入条件。

一个请求至少要满足下面的容量关系：

```text
输入 Token + 最大输出 Token + 协议与安全余量 <= 模型上下文窗口
```

案例里的申请状态和制度证据都属于输入。回答还需要输出预算，工具定义和多模态内容也可能占用窗口。输入接近上限时，模型可能成功收到请求，却在回答半句后因为达到输出上限而停止。

### 预算按职责分区

装配器应该先扣除输出预留，再为材料分区。各区的裁剪责任不同：

| 区域 | 典型材料 | 超限时的处理 |
| --- | --- | --- |
| 规则 | 行为约束、格式和拒答条件 | 版本化，缺失就拒绝调用 |
| 当前任务 | 用户问题与已确认范围 | 保留，含糊时先澄清 |
| 当前状态 | Turn、焦点、未完成动作 | 结构化保存，禁止只留摘要 |
| 历史消息 | 已闭合的对话回合 | 按相关性压缩或外置 |
| 证据与回执 | 检索片段、工具状态 | 保留来源、版本和状态码 |
| 输出预留 | 最大输出和安全余量 | 始终保留，不能被输入挤掉 |

估算器用于调用前的准入和裁剪，供应商返回的 `usage` 用于调用后的记账。两者出现偏差很正常，因为聊天模板、工具定义和图片也可能计入 Token。记录估算值、真实值、模型版本和装配版本，才能知道偏差来自哪里。

### 超限应在调用前结束

如果硬约束、当前问题或权限范围都无法放入窗口，应用应返回“需要缩小问题或减少材料”的稳定状态。继续删除规则，再发送一个“尽量回答”的请求，会把容量故障变成内容故障，后面很难定位。

Token 预算确定了能放入多少材料，但还没有决定放入哪些材料。这个选择要形成一个带版本和来源的 Context 快照。

## Context 是本次调用的可见快照

数据库、文件和历史会话都在上下文之外。**Context** 是应用选中材料、完成授权和序列化之后形成的快照，它回答一个可审计的问题：模型在这一次调用中究竟看到了哪些版本的哪些事实。

快照至少要记录材料 ID、来源、版本、信任级别、估算 Token、是否选中以及未选中的原因。案例中的状态和制度证据可以这样表示：

```json
{
  "context_version": "ctx-18",
  "scope": "employee:1842",
  "selected": [
    {"id": "turn:92", "kind": "task", "tokens": 18},
    {"id": "access:1842:v42", "kind": "tool_result", "tokens": 24},
    {"id": "policy:remote-access:v7", "kind": "evidence", "tokens": 61}
  ],
  "omitted": [
    {"id": "message:11", "reason": "stale_focus"}
  ]
}
```

这份计划保存稳定 ID 和脱敏摘要，完整正文留在受控存储中。排查回答错误时，可以先比较两次计划的差异，再决定问题发生在检索、授权、裁剪还是模型生成。

### 记忆、历史和证据各有所有者

记忆是跨请求保存的数据，历史是对话事件，检索证据是某个知识版本中的材料。它们都要经过当前范围检查才能进入快照。把模型过去的回答摘要写进长期记忆，会让未经验证的猜测获得事实地位；把整张记忆表常驻窗口，又会让过期偏好持续影响新问题。

结构化状态应保存身份、对象 ID、版本、审批状态、未完成工具调用和引用关系。自由文本摘要可以压缩已经闭合的叙述，不能独自维护这些不变量。

### 顺序表达变化，信任要单独标记

稳定规则和工具 Schema 通常放在低变化区域，当前任务、检索片段和工具回执放在后面，便于前缀缓存和增量装配。顺序不能代替信任标记，检索片段即使排在规则之后，也可能带有提示注入。

运行时应给每份材料标记来源和信任级别，并在工具执行前再次验证权限。模型看到 `policy:remote-access:v7`，只代表它得到一份证据，不代表它可以修改制度或替员工发起审批。

## 响应的停止原因决定业务终态

HTTP 200 只能说明协议层拿到了响应。应用还要读取停止原因、usage、工具调用状态和服务端任务状态，才能决定结果是否可交付。常见终态包括 `completed`、`incomplete`、`refused`、`tool_pending`、`cancelled` 和 `failed`。

例如模型生成“设备不合规，并且”后达到输出上限。文本非空，语义却未完成。运行时应保留部分文本供诊断，对外返回 `incomplete`，是否重试由剩余 Deadline、幂等键和预算共同决定。

流式场景还要区分交付通道和核心任务。客户端收到一半增量后断开，服务端可能已经完成生成。重连应按事件游标恢复，或读取已持久化的终态，不能因为页面没收到结束事件就重新执行工具。

## 把一次请求完整回放出来

把前面的概念串起来，案例的状态变化应当是可回放的：

```mermaid
flowchart LR
    A[认证与问题] --> B[消息序列]
    B --> C[预算与裁剪]
    C --> D[Context 快照]
    D --> E[模型或工具]
    E --> F[终态判定]
```

入口记录员工身份、问题和权限范围。消息编译器加入规则与当前任务。预算器计算 Token，保留输出空间并记录裁剪原因。Context 固化状态和制度版本后，模型可以组织答案，工具可以继续提供观察。最后，运行时根据停止原因、证据状态和业务校验写入终态。

任何一环都可能留下未解决的缺口：身份未通过就没有快照，预算不足就不能调用模型，证据版本冲突就不能交付答案，工具超时则需要等待或安全结束。下一次重试只能从拥有该状态的边界继续，不能复制整个请求制造第二份副作用。

## 用测试验证“模型到底看到了什么”

角色测试固定一段带恶意指令的外部文本，确认它不会改变应用规则；工具测试同时提交两个 `call_id`，确认并行回执不会错配；权限测试确认越界材料在 Context 生成前就被排除。

预算测试覆盖中文、代码、长数字、工具 Schema 和大回执，比较估算 Token 与真实 `usage`，并断言输出预留始终存在。装配回归测试保存上下文计划，版本或权限改变时必须出现可解释的差异。

终态测试分别模拟完整回答、长度截断、工具等待、拒绝、取消和流式断线。每种情况都应有稳定状态、可重试性和资源清理结果，不能把所有分支压成一条“模型调用失败”。

回到开头的问题：模型能否解释远程访问被拒，取决于这次调用的 Message、Token 和 Context 是否把当前员工状态与有效制度一起装入，并给回答留下足够输出空间。下一篇将把这份快照送进真实的 Responses API，继续追踪响应对象、工具调用和错误边界。
