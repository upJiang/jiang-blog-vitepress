# Message、Token 与上下文：模型一次调用看到了什么

聊天页面里有十轮记录，模型就看到了十轮吗？数据库里已经保存了账号状态，模型能直接用吗？一段文字还没到模型允许的最大字符数，为什么请求仍会超限？这三个问题分别落在 **Message**、**Token** 和 **Context** 上。

Message 是应用提交给模型的协议项，记录角色、内容和顺序。Token 是模型编码和计量输入输出的单位。Context 是某一次调用真正送进模型的全部材料。聊天记录、知识库、长期记忆和业务数据库都在模型外部，应用把其中一部分选进请求后，它们才成为本轮上下文。

::: info 三个概念在同一条链上

- **Message** 决定内容以什么身份、什么顺序进入请求。
- **Token** 决定这些内容占用多少模型容量。
- **Context** 是预算和规则筛选后，模型在本轮实际可见的内容集合。

:::

本文沿“我的账号为什么不能远程访问”这个问题拆解整条输入链。应用掌握一份远程访问制度，但还没有查询当前账号。最终回答必须区分通用制度与个人状态，不能让模型根据前者猜出后者。

## 一次模型调用需要解决哪些输入问题

模型调用的入口看起来很简单：给出输入，等待输出。应用真正要处理的对象比输入框多。它要确定哪条规则优先、哪些历史与当前问题有关、检索证据来自哪个版本、工具调用有没有对应结果，还要给输出预留容量。任意一项处理错误，请求都可能在服务端成功，却在业务上产生错误回答。

以远程访问问题为例，系统现在有四类材料：应用规则要求“只依据可见证据回答”；用户问自己的账号为什么被拒绝；历史对话提到用户上周更换过设备；制度文档写着远程访问需要设备合规和审批。这里没有当前设备检查结果，也没有审批状态。

界面可以展示全部材料，模型输入却不能直接把它们拼成一段文字。应用规则与用户问题的权威级别不同，历史里的“更换设备”只是用户说法，制度文档也只能证明通用条件。如果来源和角色被抹平，模型只能看到一段看似连贯的叙述，很容易把“更换设备”推成“设备不合规”。

输入装配至少要回答下面几件事：

| 问题 | 应用需要保存的记录 |
| --- | --- |
| 这段内容是谁提供的 | 角色、来源类型、来源 ID |
| 它属于哪次任务 | 请求 ID、会话 ID、当前轮次 |
| 模型能否把它当事实 | 信任级别、权限结果、版本 |
| 它占多少容量 | Token 估算、内容类型、预留输出 |
| 超限时能否删除 | 固定项、优先级、省略原因 |
| 返回结果是否完整 | 响应状态、停止原因、输出项类型 |

这些记录不是给模型看的解释文字，而是应用控制请求的依据。模型负责根据输入产生候选，输入的身份、范围和预算仍由程序确定。

## Message 保存角色、内容与顺序

Message 可以理解为带元数据的内容容器。文本只是其中一部分，角色和顺序决定模型应当怎样解释这段文本。以 OpenAI 当前的文本生成接口为例，应用可以通过 `instructions` 提供本次请求的高层指令，也可以在输入数组中使用 developer、user 和 assistant 等角色。官方文档明确说明，developer 消息优先于 user 消息；`instructions` 只作用于当前响应请求，使用 `previous_response_id` 管理后续轮次时，上一轮的 `instructions` 不会自动出现在新一轮上下文中。

这意味着应用不能把“上一轮发过规则”当成持久保证。若后续请求仍依赖那条规则，就要根据所用 API 的状态管理方式重新提供，或者确认服务端保存的会话状态确实包含它。接口帮应用保存响应链，不等于替应用维护业务规则。

### 角色表达内容的来源

developer 位置适合放应用规则，比如回答格式、可使用的资料范围和禁止执行的动作。user 位置保存终端用户当前表达。assistant 消息表示先前模型输出，它能帮助维持对话，却不能因为角色名是 assistant 就升级为可信事实。模型上一轮说“审批可能没有通过”，下一轮仍只能把它视为历史回答。

检索证据和工具结果也需要明确来源。不同 API 对内容项和工具结果有各自的结构，应用内部可以先统一成自己的消息模型，再由供应商适配器转换。内部模型至少保留 `role`、`content_type`、`source_id`、`trust_level` 和 `created_at`。适配器只负责协议映射，不能在转换时删掉来源。

多模态输入进一步说明了 Message 不等于字符串。一条消息可以包含文本、图片或文件引用，每类内容的容量计算和安全检查不同。图片中的文字可能需要视觉模型读取，文件也可能先经过上传与解析。把所有内容都强制转换成一段文本，会丢失媒体类型、来源位置和解析警告。

### 顺序表达对话与动作关系

消息顺序首先表示对话先后。当前问题应当位于相关历史之后，工具结果必须出现在模型提出调用之后。若应用为了节省空间重新排序，代词指向和问答关系可能一起改变。

工具调用还有更严格的配对要求。模型提出工具调用时会产生调用标识，程序执行后要用对应标识提交结果。只有结果而没有原调用，模型无法确定这是哪个动作的观察；只有调用没有结果，下一轮又可能重复执行。裁剪历史时应把调用与结果视为不可拆分的一组，不能按单条消息独立删除。

顺序正确也不代表内容可信。不可信网页里出现“忽略前面的规则”时，它仍是外部资料，不能因为插入位置靠前就变成 developer 指令。角色由应用在边界处赋予，外部文本没有改变自己角色的权力。

## Token 决定输入与输出怎样共享窗口

模型并不按字符直接读取文本。Tokenizer 会把文本编码为 Token 序列，常见汉字、英文片段、数字、空格、标点和特殊符号的切分方式并不相同。同一句话换一个模型或 Tokenizer，结果也可能变化。字符数可以用来做界面提示，不能作为请求上限的唯一依据。

Token 在这里承担两个职责。一方面，模型以 Token 序列处理输入并生成输出；另一方面，服务和应用用 Token 估算容量与成本。两者相关，却不能混成一个数字。发送前的估算用于决定请求能不能进入模型，响应中的 usage 用于核对实际消耗。usage 正常只说明计量字段可读，无法证明证据充分或答案正确。

### 输入预算要先扣除输出与安全余量

上下文窗口需要同时容纳输入和预期输出。应用可以把预算关系写成：

```text
输入预算 = 模型上下文窗口 - 输出预留 - 安全余量

固定规则 + 当前问题 + 历史 + 记忆 + 检索证据 + 工具结果 <= 输入预算
```

输出预留取决于任务。只返回一个分类标签和生成长报告需要的空间不同。安全余量用来吸收消息包装、估算误差和供应商协议开销，不能把窗口上限全部分给正文。示例里的比例只是应用策略，具体数值要随模型、任务和真实 usage 校准。

预算还需要按材料类型分配。规则、当前问题和未完成动作通常属于固定项；近期历史、滚动摘要、长期记忆和检索证据按任务选择。知识问答可能给证据更高比例，多轮闲聊则会保留更多近期历史。固定比例不是通用答案，关键是每种材料有独立额度，超限时能说明删了什么。

### 估算器必须暴露自己的精度

生产环境优先使用与目标模型匹配的 Tokenizer。离线环境可能没有编码文件，这时可以使用确定性的保守估算器，但结果必须带 `approximate=true`，不能伪装成供应商计数。离线估算的价值是稳定触发裁剪和拒绝分支，不是复刻在线模型的每个 Token。

响应返回后，把估算值与实际 usage 按模型版本持续比较。差异突然扩大时，检查模型是否切换、Tokenizer 缓存是否失效、消息包装是否增加了字段。不能根据某一次偏差发明“一个汉字固定等于几个 Token”的新规则。

输出 Token 也要单独观察。输入很长而回答很短，成本和首个结果等待时间仍可能偏高；输入不大但输出到达上限，答案可能在句中停止。把输入与输出相加成一个平均数，会同时掩盖这两类问题。

## Context 是本轮真正可见的内容

上下文不是聊天记录的别名。聊天记录是应用保存的原始会话，Context 是装配器为某一次调用选出的内容。原始会话应当保持不变，摘要和裁剪只生成新的请求视图。若装配器直接修改历史，后续轮次无法判断一段内容是用户原话、旧摘要还是被截断后的残片。

数据库、知识库和长期记忆也不自动属于上下文。程序需要先按身份和范围读取，再选择与问题相关的片段，最后放入请求。数据存在只说明它可以被读取；权限通过只说明当前用户允许读取；只有出现在最终装配清单里，才能说模型本轮看到了它。

### 上下文材料有不同的事实等级

应用规则规定模型怎样工作，不提供业务事实。当前用户消息是待解决的问题，也可能包含未经验证的说法。会话摘要帮助维持话题，它压缩过内容，不能比原始证据更可信。长期记忆适合保存偏好、历史问题和未完成任务，不能据此断言当前账号状态。检索证据与工具结果要绑定权限、来源和版本，才能支撑回答。

远程访问例子里，制度文档可以支撑“通常需要设备合规和审批”，账号查询结果才能支撑“这次失败发生在哪个检查”。即使历史摘要写着“用户设备曾不合规”，它也不能替代当前查询，因为状态可能已经变化。装配器应把记忆标成非事实上下文，让回答生成和证据验证使用不同字段。

### 摘要与裁剪解决的是容量问题

短对话可以保留完整历史。历史超过触发阈值后，常见做法是保留近期消息，把更早且已经完成的对话合并为滚动摘要。摘要应保留问题、结论、实体、数字、条件、用户纠正和未完成事项，并区分用户说法与模型回答。

摘要模型可能超时或返回错误结构。应用需要确定性回退，比如按 Token 从最近消息向前保留，直到进入预算。回退路径宁可少带一段旧历史，也不能在失败时跳过预算检查。摘要和确定性裁剪都应记录压缩方式、被摘要数量、被省略数量与最终 Token 数。

自动截断需要格外谨慎。服务端若从输入前部移除内容，请求可能继续成功，但最早的开发者规则或任务背景也可能消失。任务含有不可删除项时，应用自己完成装配和超限拒绝更容易验证。允许自动截断时，要把这个选择写进请求记录，并接受它会改变可见上下文。

示例按优先级从高到低选择材料，能验证“低优先级内容在预算不足时不进入请求”。生产装配器还要补三项约束：固定项即使超限也不能静默丢弃；工具调用与结果按组选择；同一优先级不能靠输入顺序制造不稳定结果。预算不足以容纳固定项时，应返回明确错误，并保持模型调用次数为零。

一份可审计的装配过程可以分成五步：

1. 读取模型配置，确定上下文窗口、输出预留、Tokenizer 和内容类型能力。
2. 收集规则、当前问题、相关历史、记忆与证据，给每项标注来源、权限和版本。
3. 先放固定项，再按各类额度选择可裁剪项。调用与结果作为一个单元处理。
4. 生成 context manifest，重新计算总量并验证角色顺序、固定项和输入上限。
5. 适配为供应商请求；模型返回后保存响应状态、输出项和 usage，再进入业务校验。

context manifest 不必保存敏感正文，可以记录内容哈希、来源 ID、角色、内容类型、估算 Token、是否固定和省略原因。排查模型为何“不知道”某件事时，先看这份清单，比直接阅读回答更有效。

::: warning 请求成功不代表上下文正确

服务返回 completed，只能证明模型调用结束。角色放错、证据版本过期、用户无权查看或固定规则被截断，都可能生成语法完整但业务错误的回答。

:::

## 用远程访问问题推演完整状态变化

应用收到问题后生成请求 ID，并读取当前模型配置。假设这次输入预算为 6000 Token，输出预留为 1200 Token，另有安全余量。数字只用于展示控制过程，不代表某个模型的固定限制。

装配器收到以下材料：

| 材料 | 角色或类型 | 是否固定 | 能证明什么 |
| --- | --- | --- | --- |
| 只依据可见证据回答 | developer 规则 | 是 | 约束回答方式 |
| 我的账号为什么不能远程访问 | user 消息 | 是 | 当前问题 |
| 上周更换过设备 | 历史用户消息 | 否 | 用户曾这样描述 |
| 远程访问需要合规检查与审批 | 检索证据 | 是 | 通用制度 |
| 较早的其他话题 | 历史消息 | 否 | 与当前问题无关 |

旧话题先被省略，并写入 `omission_reason=irrelevant`。其余内容进入预算后，装配器生成如下逻辑顺序：

```text
developer: 只依据本次提供的证据回答；没有账号状态就明确说明无法确认。
user: 我的账号为什么不能远程访问？
conversation history: 用户上周说自己更换过设备。
retrieved evidence: 远程访问需要设备合规检查和审批。
```

模型回答“通用条件包括设备合规和审批，现有资料没有当前账号与设备的检查结果”，业务校验可以接受这段候选。它回答了现有证据能覆盖的部分，也说明了缺失信息。

若模型回答“你的新设备不合规，所以申请被拒绝”，调用本身可能仍是 completed，业务层却要将候选标成 unsupported。历史只证明用户换过设备，制度只给出通用条件，两者都没有提供当前检查结果。程序可以发起一次经过授权的状态查询，或让用户补充信息，不能通过再次生成把猜测写得更像事实。

再注入一个容量故障：开发者规则、当前问题和制度证据已经超过输入预算。装配器不能删除其中任意一项来换取请求成功，而是返回 `context_budget_exceeded`。记录里应当包含各固定项的估算、模型配置版本和模型调用次数 0。这个终态与供应商限流、网络超时和输出截断不同。

工具查询加入后，状态还会多一组配对项：assistant 产生带调用标识的账号查询，程序执行权限检查并返回工具结果。下一次模型调用必须同时包含调用与结果。查询若被拒绝，结果应明确表示 permission_denied，不能省略失败后让模型继续猜。

## 正常响应与失败路径怎样分开

模型返回后，适配器先解析响应项。当前 Responses API 的 `output` 可能包含多种项目，官方文档提醒应用不要假设文本总在 `output[0].content[0].text`。SDK 提供的 `output_text` 便于聚合文本，但工具调用、推理项和其他输出仍要从类型化列表读取。下一篇会沿一次真实请求详细拆解这些字段。

正常路径需要满足四层条件：协议请求成功，响应状态允许继续，输出项满足任务契约，业务事实通过验证。文本非空只覆盖其中很小一部分。结构化任务遇到长度停止时，局部 JSON 不应保存为正式对象；工具调用任务拿到调用候选时，也还没有完成业务动作。

常见失败可以按发生位置处理：

**装配失败**，固定项已超过预算、角色序列非法或工具配对被破坏。应用在本地结束，不调用模型。

**传输与服务失败**，包括认证、限流、网络超时和供应商错误。是否重试取决于错误类型、剩余 Deadline 和请求幂等性，不能解析错误文案猜类别。

**生成未完成**，输出因长度、取消或内容策略停止。适配器保留部分输出和停止原因，业务层按任务合同决定展示草稿、补充调用或整体失败。

**证据校验失败**，模型补出了上下文不存在的账号状态，或引用了不允许当前用户查看的材料。系统保留原候选与缺失证据，拒绝交付具体结论。

**压缩失败**，摘要服务不可用或返回空结果。装配器使用确定性裁剪重新计算；若仍超限，就以预算错误停止，不把未受控的完整历史发送出去。

错误分类决定重试是否有意义。角色放错、固定项超限和证据不足不会因原样重试而消失；临时网络错误可能重试；工具副作用是否能重试，还取决于调用有没有幂等键和可查询回执。

## 测试要证明模型看见了什么

本地单元测试不需要真实模型。固定 Message、预算、Tokenizer 替身和 Fake Response，就能验证应用自己的控制逻辑。至少要覆盖短历史完整保留、长历史保留近期消息并生成摘要、摘要失败后确定性裁剪、固定项超限时零调用、工具调用结果不拆分、停止原因不被改写为 completed。

测试断言不能只看最终文本。它还要检查最终角色序列、来源 ID、输入预算、压缩方式、被摘要消息数和省略原因。对于长期记忆，测试应确认它被标为非事实上下文；回答需要具体业务事实时，只允许当前可见证据承担支撑关系。

一条最小回放轨迹可以写成：

```text
输入：固定规则 1 条，当前问题 1 条，旧历史 4 条，制度证据 1 条
预算：允许固定项、制度证据和 1 组相关问答
装配：3 条无关历史被省略，调用与结果仍保持成组
输出：请求进入模型，manifest 记录 4 个输入单元

故障：固定规则、当前问题和制度证据已经超出预算
终态：context_budget_exceeded，模型调用次数为 0
```

在线验证只核对真实服务才能给出的事实，包括目标模型的输入限制、响应项、停止状态、usage 和 Tokenizer 差异。没有实际发送请求时，不写具体 usage、延迟或通过数量。Fake Adapter 产生的 usage 只能用于字段映射测试。

生产回放要固定模型快照、Prompt 版本、装配策略和一组脱敏长对话。升级任一项时，比较最终 manifest、压缩路径、停止原因和业务校验结果。模型行为可能变化，应用控制不应因此丢失固定规则或放宽权限。

指标同样按层分开：装配层记录输入估算、裁剪次数和预算拒绝；模型层记录输入输出 usage、响应状态和停止原因；业务层记录证据不足、权限拒绝和字段校验失败。这样才能判断问题来自容量、服务还是事实边界。

消息正文可能含有隐私。普通 Trace 只保存长度、角色、来源类型、稳定 ID 和哈希，完整内容进入受控存储并设置保留期限。用户删除会话后，摘要、缓存和后续装配都不能继续取回已撤回内容。

## 生产环境怎样固定版本与会话顺序

本地预算测试通过后，生产接入还缺一份模型配置快照。模型 ID、Tokenizer、上下文窗口、输出预留、各类材料额度和裁剪策略共同决定最终输入，只记录模型名不够。一次请求开始装配时就固定这组配置，运行途中即使管理员发布了新配置，当前请求也继续使用旧快照。下一次请求再读取新版本，日志才能解释同一问题为什么产生不同的上下文。

配置升级要用固定对话回放，而不是只看请求是否返回 200。回放比较原始历史条数、摘要切点、近期消息、证据数量、估算与实际 usage 差异，以及最终停止原因。Tokenizer 变化可能让原来刚好进入预算的证据被裁掉；输出预留增加也会压缩输入空间。这些都是可预期的配置影响，应当在发布前暴露。

同一会话的并发请求会制造另一类顺序问题。用户连续提交 A、B 两个问题时，B 装配上下文的时刻可能早于 A 完成。若系统默认“界面上排在前面的消息一定已经进入上下文”，B 就可能引用一个尚不存在的回答。每个 Turn 应绑定父消息或会话序号，装配器只读取该快照之前已经提交的消息。A 完成后是否让 B 重新装配，要由产品语义决定，不能悄悄把新内容塞进已经发出的请求。

摘要写入同样需要并发保护。两个请求同时压缩相同历史，如果后完成的旧摘要覆盖了包含更多消息的新摘要，后续对话就会倒退。摘要记录至少带已覆盖消息数或版本条件，保存时检查当前版本。冲突时重新读取，不能无条件覆盖。原始会话仍保持不可变，摘要失败不会破坏历史本身。

缓存键需要包含影响上下文的身份与版本。只按“用户问题文本”缓存装配结果，会让不同用户、不同权限或不同知识 Release 共享输入。更稳妥的键包含租户或用户范围、会话快照、模型配置版本、规则版本与证据版本；命中后仍要检查当前权限。缓存只是减少重复计算，不能替代授权。

Deadline 也会影响可见内容。记忆检索或知识检索超过剩余时间时，应用可能选择降级为较少材料，也可能停止请求。降级策略必须写入 manifest，比如 `memory_timeout` 或 `evidence_timeout`，回答端才能避免声称自己检查了所有资料。对必须由指定证据支撑的任务，证据超时应直接结束，不允许让模型凭历史知识补齐。

运行指标要能重建这些决定。一次请求至少关联会话快照、配置版本、估算方式、输入输出用量、压缩路径、省略原因和终止状态。指标不保存敏感正文，问题排查需要正文时再通过受控引用读取。只记录最终答案和总 Token，无法区分配置变化、并发顺序与检索超时。

## Message、Token、Context 与相邻概念的边界

Message 是一次调用的协议单位，聊天记录是应用保存的会话事实。前者可以由后者装配，但两者不相等。删除某次请求里的 Message 不会自动删除原始会话，删除原始会话也要同步处理摘要与缓存。

Token 是编码和计量单位，字符、单词和字节都不能稳定替代它。Tokenizer 负责切分，context window 规定一次调用可容纳的总范围，应用的 input budget 则是在窗口内扣除输出和安全余量后的控制值。

Context 是本轮输入集合，Memory 是调用外保存的可检索信息。记忆要经过身份过滤、相关性选择和预算装配才会进入 Context。RAG 负责从外部知识取得证据，也只有最终选中的证据片段会出现在请求中。

Prompt Cache 复用稳定前缀的计算结果或计费能力，具体行为由供应商实现决定。它不会扩大上下文窗口，不会把已裁剪内容重新放回请求，也不会替应用判断缓存内容是否仍符合当前权限和版本。

排查“模型为什么没看到某条信息”时，沿一条固定链路查：外部存储是否存在，当前身份是否可见，检索或历史选择是否选中，manifest 是否装入，请求是否裁剪，模型返回时为何停止。每个问题都有不同的状态所有者，不能统一归因于模型忘记了。

掌握这三个概念后，下一次阅读 API 响应就有了位置感：请求字段决定消息怎样进入，usage 描述 Token 消耗，响应状态说明生成在哪里结束，而业务验证负责判断候选能否成为最终结果。
