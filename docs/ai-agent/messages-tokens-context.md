# Message、Token 与上下文：模型一次调用看到了什么

用户问：“为什么我的远程访问申请被拒绝？”数据库里可能有申请状态，制度文档里也可能写着设备要求。模型不会因为这些材料存在于应用里，就自动读取它们。

应用每次调用模型时，都要提交一份输入。本文把同一个问题放进三次调用，逐步增加材料，观察模型究竟多看到了什么。这样可以把四个容易混淆的词放回同一个对象上理解：**Context（上下文）** 描述本次调用可见的材料，**Message（消息）** 描述这些材料的协议结构，**Token（词元）** 描述可见内容如何被编码和计量，**Context Window（上下文窗口）** 描述容量边界。

本文只讨论一次文本调用的输入边界。工具调用、记忆选择和 Agent 循环会建立在这个边界之上，放到后续文章展开。

## 先固定同一个问题

观察对象只有一个：远程访问申请为什么被拒绝。我们不改变问题，只改变提交给模型的材料。每次调用都从空白请求开始，上一调用的输入不会自动流入下一调用。

三次请求的差异如下：

| 调用 | 提交的材料 | 模型能够判断什么 | 仍然缺少什么 |
| --- | --- | --- | --- |
| A | 用户问题 | 只能理解提问本身 | 申请状态、制度依据 |
| B | 应用指令、用户问题 | 知道回答规则和问题 | 仍没有这次申请的事实 |
| C | 应用指令、用户问题、当前证据 | 可以对照状态与制度解释原因 | 证据过期或权限错误仍会误导 |

表格先给出结果，后文再解释这些材料怎样组织、怎样计量，以及容量不足时会发生什么。这里最重要的观察是：模型看到的范围由本次请求决定，和应用里“已经存在什么”是两件事。

## Context 是一次调用的可见材料

**Context（上下文）** 指应用完成选择和序列化后，准备提交给模型的全部输入材料。它可能包含指令、用户问题、历史消息、检索片段或工具结果，具体取决于本次请求装配了什么。

Context 是一次调用的快照。请求结束后，应用可以把其中一部分保存为历史或记忆，但下一次调用仍要重新选择。数据库、文件库和完整历史都属于应用侧资源，只有被读取并放进请求，才会进入当前 Context。

回到三次调用，A 的 Context 只有用户问题，B 的 Context 增加了应用指令，C 的 Context 又增加了当前证据。三次调用的差别先由 Context 表达，Message 负责说明这些材料在协议中怎样排列。

## Message 把材料组织成协议结构

**Message（消息）** 是对话输入中的一个有序项。它通常带有角色和内容，角色帮助模型区分指令、用户表达、工具结果等来源，顺序保留对话的前后关系。

Message 解决的是“材料以什么结构出现”。它不负责把材料从数据库取出来，也不替应用判断用户是否有权读取某条证据。权限检查应该在消息装配之前完成。

下面用抽象格式表示三次调用。字段名用于说明关系，不代表某一家服务商的固定请求格式。

```json
{
  "callA": [
    { "role": "user", "content": "为什么我的远程访问申请被拒绝？" }
  ],
  "callB": [
    { "role": "system", "content": "只根据已提供材料回答，缺少材料时说明缺口。" },
    { "role": "user", "content": "为什么我的远程访问申请被拒绝？" }
  ],
  "callC": [
    {
      "role": "system",
      "content": "只根据已提供材料回答，缺少材料时说明缺口。\n当前材料：申请状态为已拒绝，原因是设备不符合要求；当前制度要求远程访问设备通过合规检查。"
    },
    { "role": "user", "content": "为什么我的远程访问申请被拒绝？" }
  ]
}
```

这段结构让差异可见。A 只有提问，B 增加回答规则，C 把两条证据加入应用指令。真实接口可能使用不同角色、内容项或输入字段，证据应按目标 API 的协议序列化，不能把这里的抽象结构直接复制成请求。应用还要在装配前检查证据的权限、时效和来源。

Message 与 Context 的关系是组成关系：一组 Message 组织了 Context 中的内容。Context 这个词关注“本轮可见的全部材料”，Message 关注“每份材料怎样排列和标记”。两者描述同一次输入的不同层面。

## Token 把可见内容变成计量单位

**Token（词元）** 是目标模型的 tokenizer 根据词表编码输入和输出时使用的单位。一个 Token 可能对应一个汉字、一个词的一部分、标点或代码片段，具体切分由模型和 tokenizer 决定。

Token 关注的是计算和容量，不是 Message 的角色语义。相同的用户问题放在不同 Message 中，协议结构会变化；经过目标模型编码后，内容仍会被计入输入 Token。换一个模型，切分结果也可能变化。

可以把计量过程抽象成下面的函数。它只表达输入输出关系，不给出某个模型的固定数量。

```text
messages + 模型的序列化规则
        -> tokenizer
        -> 输入 Token 序列
输入 Token + 预留输出 Token
        -> 容量检查
```

代码块中的“序列化规则”很关键。服务商可能为角色、分隔符、工具定义和多模态内容加入额外开销，所以字符数不能直接当作 Token 数。需要裁剪或计费时，应使用目标模型的 tokenizer；只能估算时，必须把结果标成近似值。

响应中的 `usage` 才是服务商对实际调用的统计入口。调用前的估算用于准入和裁剪，响应后的 usage 用于校准，两者不应混写成同一个事实。

## Context Window 规定能装多少

**Context Window（上下文窗口）** 是一次调用可使用的容量上限。它约束输入、预留输出以及某些模型会计入的额外 Token。窗口描述“最多能装多少”，Context 描述“这次实际装了什么”。

容量检查可以先用一个不依赖供应商字段的关系表示：

```text
输入 Token + 预留输出 Token + 其他计入项 <= Context Window
```

如果 C 的证据已经占满窗口，应用需要减少历史、压缩材料或拒绝调用。裁剪时要保留回答规则和当前任务所需的证据，不能为了塞入更多文本而删除权限边界。窗口检查通过，只能说明材料装得下，不能说明材料新鲜、相关或有权限。

这也解释了四个词为什么同时出现在标题里。Context 是观察对象，Message 是组织它的协议，Token 是计量它的单位，Context Window 是约束这次计量结果的容量边界。它们相互关联，却不是四个连续的处理阶段。

## 重新回放三次调用

现在用四个问题检查刚才的差异。

### 调用 A：只有用户问题

模型能识别用户想知道“被拒绝的原因”，却没有申请状态和制度依据。它可以请求补充材料，不能从应用数据库中自行找出事实。此时 Context 很小，缺口很大。

### 调用 B：增加应用指令

应用指令规定回答应基于已提供材料，缺少材料要说明缺口。Message 数量增加，Context 的可见范围也增加了规则，但申请事实仍未出现。指令改变了回答约束，不能替代证据。

### 调用 C：增加当前证据

申请状态和当前制度都进入了 Message，因而也进入了这次 Context。模型可以把“设备不符合要求”和“制度要求设备合规”放在一起解释。若两条材料来自不同时间，或用户无权读取其中一条，程序必须在装配前拦截。

三次调用只改变输入材料，问题保持不变。这个对照说明，模型回答变得具体，原因在于 Context 增加了可用证据；Message 让证据的来源和顺序可辨认；Token 与窗口决定这些材料能否完整放入请求。

## 如何验证模型实际看到了什么

验证时应保存提交前的输入快照，并与响应 usage 对照，无需猜测模型“记住了什么”。应用可以记录材料类型、来源、版本、是否入选和裁剪原因，正文内容按数据分级保存。

下面是应用侧的示意结构。它用于回放装配结果，不是某个模型供应商要求的字段。

```json
{
  "messages": [
    {
      "position": 0,
      "role": "system",
      "source": "应用指令和当前证据",
      "sourceVersion": "记录装配时的真实版本",
      "contentDigest": "根据实际提交内容计算",
      "protectedContentRef": "指向受控存储中的实际内容"
    },
    {
      "position": 1,
      "role": "user",
      "source": "当前用户输入",
      "contentDigest": "根据实际提交内容计算",
      "protectedContentRef": "指向受控存储中的实际内容"
    }
  ],
  "selectedMaterials": [
    {
      "insertedAtMessagePosition": 0,
      "source": "申请状态",
      "sourceVersion": "记录查询时的真实版本",
      "contentDigest": "根据实际入选片段计算"
    },
    {
      "insertedAtMessagePosition": 0,
      "source": "当前制度",
      "sourceVersion": "记录检索时的真实版本",
      "contentDigest": "根据实际入选片段计算"
    }
  ],
  "estimatedInputTokens": "由目标 tokenizer 计算",
  "reservedOutputTokens": "由应用预算决定",
  "omitted": [
    { "kind": "old_history", "reason": "超出当前关注范围" }
  ]
}
```

`position` 固定提交顺序，`sourceVersion` 标记材料版本，摘要用于比较内容是否变化，受控引用用于在有权限的环境中取回实际文本。正文不适合长期写入普通日志时，可以只保存摘要和受控引用，但必须保证引用的内容不会被静默覆盖。

这份快照能确认提交了哪些 Message、证据放进了哪个位置、哪些材料被排除。响应返回后，再把真实 usage 写回同一次调用的记录，用于定位 Token 估算偏差。usage 只证明服务商如何计量本次调用，不能证明某段证据的具体内容；内容回放仍以输入快照为准。

测试可以沿三层安排。Message 测试检查角色和顺序，Token 测试使用目标 tokenizer 覆盖中文、代码和长数字，Context 测试检查权限、版本、裁剪原因和最终入选材料。Fake tokenizer 或 Fake 模型只能验证应用分支，不能证明真实服务的序列化开销和 usage 口径。

## 四个边界要记住

- Message 是协议结构，角色不会授予权限。
- Token 是编码单位，同样的字符数不保证同样的 Token 数。
- Context 是本次可见快照，历史和记忆必须重新装配才能进入其中。
- Context Window 是容量上限，容量足够不代表证据正确或仍然有效。

把这四个边界写进输入装配和测试后，模型输出才有可追溯的输入依据。下一篇会把这份输入快照映射到一次 Responses API 请求，继续看字段、响应状态和 usage 怎样落到代码里。
