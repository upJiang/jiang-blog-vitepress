# Message、Token 与 Context：模型实际看到了什么

模型不会直接看到网页、数据库或一整段“会话记忆”。应用先把需要的信息整理成消息，再由 SDK 编码并发送。排查回答为什么遗漏事实时，应该先看请求中到底放了什么。

## Message 用角色和顺序组织输入

一条消息至少有角色和内容。开发者消息放规则，用户消息放当前问题，工具结果要与对应调用配对。不同 API 的字段名称会有差异，但顺序仍然重要：模型处理的是应用最终提交的有序输入，不是后台所有可用数据。

```text
developer: 只使用已授权证据，缺少资料时明确说明。
user: 远程访问为什么被拒绝？
tool: account_status = disabled
tool: policy_excerpt = 账号停用后需先恢复身份状态
```

如果最后两条工具结果没有进入请求，模型无法凭空知道账号被停用。把事实存在数据库里和把事实交给模型，是两件事。

## Token 是模型处理文本的单位

SDK 会按目标模型的 tokenizer 把文本转换成 Token。一个 Token 不固定等于一个汉字或一个英文单词，代码、标点和不同语言的切分也不同。预算应使用目标模型对应的计数器；按字符数估算只适合提前做保守筛选。

一次调用的总预算通常包括输入和输出。输入里有系统规则、历史消息、检索证据、工具结果和当前问题，输出还要预留回答空间。把上下文窗口全部塞满，会让模型没有足够位置生成结果，或者触发 API 的超限错误。

## Context 是本次调用的完整可见输入

上下文不只等于聊天记录。知识 Agent 常见的装配顺序是：稳定策略、当前问题、可信身份摘要、最近历史、长期记忆候选、检索证据和工具观察。每部分都需要来源和预算。

::: warning 上下文不是权限边界

隐藏一段资料不放进 Prompt，可以减少泄漏机会，但真正的权限过滤必须发生在查询和数据访问层。已经越权检索出来的内容，不该指望模型主动忽略。

:::

## 输出不只有正文

模型响应通常包含输出项、完成状态和 usage。正文是给用户看的内容，状态用于判断请求是否完成，usage 用来记录输入和输出 Token。工具调用也是一种输出项，不能当作最终文本显示，更不能直接执行其中的参数。

流式返回会把同一个响应拆成有类型的事件。客户端可以边接收文本增量边渲染，但只有完成事件到达后，才能确认整次响应结束。中途断线留下的是部分输出，不应标记为完整答案。

## 超限时先保留承重信息

裁剪顺序取决于任务。安全策略和当前问题通常不能删，直接支撑答案的证据优先于久远闲聊。历史可以保留最近窗口，较早内容压成带来源的摘要；工具返回先提取需要的字段，避免把完整日志塞回模型。

真正的 tokenizer 计数应在调用前执行。完成后再记录服务端 usage，对比预估和实际值。如果两者长期偏差很大，检查模型是否换了 tokenizer、消息格式是否增加了隐藏开销，以及工具结果是否被重复提交。
