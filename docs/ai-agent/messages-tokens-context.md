# Message、Token 与上下文：模型一次调用看到了什么

聊天记录里有十轮对话，模型未必能看到十轮。数据库已经存了用户资料，模型也不会自动知道。一份材料能否影响本轮输出，只取决于应用有没有把它装进这次请求。

这条输入链里有三个容易混在一起的概念：**Message（消息）** 是带角色和内容的协议项，**Token（词元）** 是模型编码与计量文本的单位，**Context（上下文）** 是本次调用实际提交给模型的全部材料。数据库、文件和历史会话都在上下文之外，直到应用选中并序列化它们。

## Message 先解决内容以什么身份出现

模型 API 通常接收一组有顺序的消息。不同接口对角色名称和内容块结构的定义略有差异，稳定的语义大致可以分成三类：应用规则、用户输入、模型之前的输出。工具调用与工具结果还会形成成对的协议项。

角色会影响模型怎样解释内容，但角色本身不构成安全边界。把一段网页文字放进高优先级消息，等于应用主动提高了不可信内容的影响力；把“只能访问当前租户”写进规则，也阻止不了一个缺少授权检查的数据库工具。

顺序同样有含义。下面两组消息包含相同句子，得到的任务却不同：

```text
用户：远程访问需要什么条件？
助手：需要设备合规并通过审批。
用户：那我的申请为什么失败？
```

最后一句里的“我的申请”依赖前文主题，但前文没有个人申请状态。模型可以解释一般条件，不能据此推断具体失败原因。应用若想回答个人问题，必须先从已授权的数据源取得状态，再把结果作为新观察加入消息。

### 工具结果要能和调用对应

一个模型回合可能提出多个工具调用。应用保存工具名还不够，每次调用都需要稳定的 `call_id`，结果按 ID 回填。并行请求按完成时间返回时，列表顺序很容易变化，依赖数组位置会把甲工具的结果错配给乙工具。

工具结果还要保留状态。空结果、权限拒绝、超时和成功返回空数组，在文本里都可能只剩“没有内容”，后续控制流却完全不同。给模型的观察可以简化，程序保存的原始回执不能丢。

## Token 决定窗口怎样分配

模型先把输入编码为 Token，再逐个生成输出 Token。Token 与字符、汉字或单词没有固定的一一关系，代码、数字、空格和不同语言的切分都会变化。因此，“最多 2 万字”不能替代真实 tokenizer 或供应商返回的 usage。

一次调用的窗口可以写成下面的容量关系：

```text
输入 Token + 最大输出 Token + 模型保留空间 <= 上下文窗口
```

输入预算不能直接取窗口上限。应用要先留出输出额度和安全余量，再把剩余空间分给规则、当前问题、历史、记忆、检索证据和工具结果。若输入塞满窗口，模型即使成功接收请求，也可能没有足够空间完成回答。

| 预算项 | 为什么要单独计算 |
| --- | --- |
| 固定规则 | 每次调用都占空间，版本变化还会影响缓存 |
| 当前任务 | 通常优先级最高，裁剪后可能改变目标 |
| 历史消息 | 数量持续增长，旧内容未必仍与当前焦点相关 |
| 外部证据 | 需要保留来源、范围和能直接支撑结论的片段 |
| 工具结果 | 容量波动大，完整对象常常不适合直接送入模型 |
| 输出预留 | 决定回答能否完整结束 |

估算器适合在调用前做准入和裁剪，真实 usage 用于调用后记账。两者会有偏差，因为聊天模板、图片、工具 Schema 和供应商协议也可能计入 Token。工程上应记录估算值、真实值和模型版本，偏差持续扩大时更新估算策略。

## Context 是一次调用的可见快照

上下文工程的工作可以概括为装配一个快照：此刻的目标是什么，哪些规则有效，哪些事实属于当前用户可见范围，最近发生了什么，模型可以调用哪些能力。

材料进入快照前要区分来源和职责：

- 应用规则约束行为，版本由程序固定。
- 用户消息表达意图，其中可能包含错误或恶意指令。
- 会话状态记录焦点、已确认实体和未完成动作。
- 检索片段提供证据，仍属于不可信外部内容。
- 工具回执描述外部动作结果，可信程度由工具和数据源决定。

这些材料不能简单按“越新越重要”排序。最近一条网页结果可能包含提示注入，较早的用户范围却必须保留；很长的工具输出可以转成短预览，调用 ID、状态和来源不能被摘要丢掉。

### 上下文和记忆分工不同

记忆是模型调用之外的持久数据，上下文是本轮输入。记忆只有经过检索、授权和装配后才进入上下文。把整张用户记忆表长期拼进每次请求，会增加成本，也会让过期偏好持续干扰当前任务。

摘要也只是新的输入材料。它能减少容量，无法天然保证事实完整。身份、范围、对象 ID、金额、审批状态、未完成工具调用和来源引用应由结构化状态保存，不交给自由文本摘要维护。

## 输出为什么停止也属于协议

HTTP 200 只说明请求成功到达服务并获得响应。输出还可能因为长度上限、内容策略、工具调用或取消而停止。应用应读取响应状态、停止原因和 usage，再决定能否把文本当成完整答案。

假设模型输出到“需要设备合规，并且”就结束，字符串非空，却明显不完整。程序若只检查 `text.length > 0`，会把截断内容交付给用户。更稳的处理是保留部分文本用于诊断，对外返回可识别的 `incomplete`，是否重试由剩余 Deadline、预算和请求幂等性决定。

流式传输还多一层边界。客户端收到若干文本增量后断开，不代表模型任务已经取消；服务端也可能已经生成完整结果。核心终态应由服务端状态决定，重连只恢复事件或读取结果，不能因为 UI 没收到结尾就重新执行整个任务。

## 用四组测试守住输入边界

**角色测试**检查不可信网页不会变成应用规则，工具结果必须和原调用 ID 对应。

**预算测试**覆盖中文、代码、长数字、工具 Schema 和大结果，断言输出预留不会被输入挤占，估算误差会被记录。

**装配测试**固定同一份状态，比较选中片段、顺序、来源和裁剪原因。涉及权限的材料在进入模型前已经过滤，不能指望模型自行忽略越界内容。

**终态测试**分别模拟完成、长度截断、拒绝、超时和流式中断。每种情况都应产生不同的应用状态，而非统一成“模型调用失败”。
