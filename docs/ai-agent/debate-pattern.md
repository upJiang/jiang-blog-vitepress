# Debate 模式怎样处理有证据的分歧

让不同角色提出和质询证据，再由独立规则裁决，避免多数票替代事实验证。**Debate**、**Evidence**、**Multi Agent** 分别指向同一条执行链上的不同对象：目标、当前状态、可用动作、证据缺口、预算和停止条件进入系统，议题、立场、Claim、Evidence、质询、回应、裁决规则和未决问题保存处理中间状态，最终得到下一动作、受限计划、修复建议、候选评分或停止决定。

Debate 模式处理有证据的分歧位于单个受限行动循环中的决策策略层，主要机制是不同角色围绕同一证据包提出主张和质询，裁决器按证据充分性与约束判断；角色数量和轮次固定，不能靠多数票确认事实。角色共享同一错误前提、辩论变成长文本竞争、少数正确证据被多数压过和没有停止条件会让链路在不同位置停止，错误记录必须保留发生阶段、当时的状态和终止原因。

::: info 贯穿示例

Debate 模式处理有证据的分歧场景：一个知识问题可能只需单次检索，也可能需要分解成多个子问题，系统必须在开始时选择足够但不过度的执行模式。Debate 模式处理有证据的分歧需要的身份、权限、版本和业务事实由应用提供，模型与外部内容只产生候选。

:::

这次推演用候选路径、动作记录、观察、评分、剩余预算和停止原因把请求和终态关联起来。与 Reflection、多模型集成、人工评审和研究综合比较时，重点看输入来源、状态所有者、下一步的决策者和失败终点。

Debate 模式处理有证据的分歧的执行顺序是“读取目标 → 生成候选步骤 → 执行受限动作 → 观察变化 → 裁决继续或停止”。目标从入口进入，议题记录进度，下一动作通过当前主题的校验条件后才会交付。

角色共享同一错误前提与辩论变成长文本竞争会产生不同证据。前者先检查议题和输入来源，后者沿调用记录定位依赖或状态冲突；不区分发生位置，重试会掩盖原始原因。

Debate 模式处理有证据的分歧与 Reflection 的共同点不代表它们可以互换。当前主题拥有立场，相邻组件只通过契约读取或提交候选，不能直接修改这个状态。

实现 Debate 模式处理有证据的分歧时，代码顺序应与状态顺序一致：入口拒绝不会调用依赖，正常分支保存 Claim，错误分支返回稳定类型，测试分别断言调用次数、参数、输出和清理结果。

## 任务为何需要运行时决策

让不同角色提出和质询证据，再由独立规则裁决，避免多数票替代事实验证。在“Debate 模式处理有证据的分歧场景：一个知识问题可能只需单次检索，也可能需要分解成多个子问题，系统必须在开始时选择足够但不过度的执行模式”这类任务里，Debate 模式处理有证据的分歧负责把目标带入处理链，并明确下一动作可以交付的条件。

Debate 模式处理有证据的分歧位于单个受限行动循环中的决策策略层。它处理不同角色围绕同一证据包提出主张和质询，裁决器按证据充分性与约束判断；角色数量和轮次固定，不能靠多数票确认事实，身份认证、授权结果和最终业务状态仍由应用中的确定性组件负责。

目标是这条链路的起点；来源缺失时，程序只能拒绝请求或采用明确记录的默认值，模型补出的字段不能继续驱动生成候选步骤。

角色共享同一错误前提会破坏议题与下一动作之间的对应关系，排查时先保留原始输入摘要和发生阶段，再判断是否允许重试。

辩论变成长文本竞争影响立场或下游解释，不能和角色共享同一错误前提共用“重新调用一次模型”的处理方式。

Debate 模式处理有证据的分歧完成时至少留下议题、立场、下一动作和检查结论；只有最终文字，无法证明结果来自本次请求。

议题在单进程 Demo 中可以留在内存，跨进程、带权限或有副作用的任务则要持久化输入、状态转移和停止原因，不能依赖 Prompt 保存状态。

Debate 模式处理有证据的分歧还要把业务条件写成状态条件：可用动作何时就绪，下一动作何时允许交付，角色共享同一错误前提发生后是否还能继续。

Debate 模式处理有证据的分歧对外区分完成、部分完成和无法确认，三个状态若都包装成下一动作，上层界面无法采用不同处理方式。

## Debate 模式处理有证据的分歧控制哪一部分

Debate 模式处理有证据的分歧接收目标、当前状态、可用动作、证据缺口、预算和停止条件，向下游交付下一动作、受限计划、修复建议、候选评分或停止决定，输入与输出之间用明确契约连接，调用方不能把一句含糊目标直接交给底层适配器。

策略提出候选，执行器管理动作，运行时保存状态并裁决终止。因此议题与立场要有唯一写入方，其他组件只能通过版本化命令申请修改。

Reflection 与 Debate 模式处理有证据的分歧解决的问题相邻，但控制权不同，比较时要看谁选择执行受限动作、谁保存议题、谁确认下一动作。

多模型集成可以参与同一请求，却不能替代 Debate 模式处理有证据的分歧；组合后仍要单独检查当前状态的可信来源和角色共享同一错误前提的终止规则。

Claim 若只保存在 SDK 对象里，重试或进程退出后就失去解释依据；需要恢复或审计的字段进入持久层，体积较大的下一动作只保存稳定引用。

Debate 模式处理有证据的分歧使用的身份、范围和版本来自可信运行时，目标可以表达意图，但不能提升权限或改写活动 Release。

辩论变成长文本竞争发生时，错误回到立场的所有者处理，上游缺输入、当前组件违反不变量和下游不可用分别形成不同终态。

Debate 模式处理有证据的分歧的确定性边界位于议题写入之前。模型可以建议值，应用核对来源和当前版本；涉及权限、金额、发布或不可逆动作时，再进入策略或人工批准。

Debate 模式处理有证据的分歧内部可以使用更细的临时对象，跨边界只暴露稳定协议。替换 Reflection 时，调用方不需要理解内部缓存和 SDK 响应。

## 目标、候选动作与搜索状态

Debate 模式处理有证据的分歧的输入合同至少列出目标、当前状态和可用动作，每项都注明来源、是否必需、允许的缺省值，以及缺失后是在入口拒绝还是进入降级路径。

状态合同中的议题表示当前进度，立场保存本次执行依赖的快照，Claim 关联前后动作，三者不能合并成一段自由文本。

并发分支按稳定身份合并 Claim，完成顺序只反映耗时，不能决定结果属于哪个请求，更不能让迟到的旧状态覆盖新修订。

输出合同同时描述下一动作和受限计划，并为拒绝、取消、部分完成和未知状态提供固定形状，调用方据此分支，无需解析错误文案猜测结果。

立场参与乐观并发检查；处理开始后若版本变化，旧候选只保留作审计，不能继续写入议题。

目标里若包含模型填写的同名字段，应用会丢弃它，再从认证、配置或活动版本中补入可信值，因为结构校验通过不等于授权或业务校验通过。

候选路径、动作记录、观察、评分、剩余预算和停止原因组成 Debate 模式处理有证据的分歧的最小追踪材料，日志只保存稳定 ID、版本和错误类，完整 Prompt、文档正文与凭证不进入指标标签。

撤回或删除当前状态时，相关缓存、候选和未完成任务按版本失效；稳定 ID 可以保留审计关系，已撤回内容不能继续进入下一动作。

契约还需要描述新鲜度。立场对应的数据发生变化后，旧缓存、旧候选和未完成任务怎样失效，应由版本或时间规则直接判断，不能依赖模型注意到矛盾。

删除和撤回也属于数据生命周期。Debate 模式处理有证据的分歧引用的原始对象被移除时，稳定 ID 可以保留审计关系，正文与派生结果则按策略失效，避免继续向用户展示过期内容。

## 一次决策怎样变成可执行步骤

Debate 模式处理有证据的分歧按“不同角色围绕同一证据包提出主张和质询，裁决器按证据充分性与约束判断；角色数量和轮次固定，不能靠多数票确认事实”推进，这段机制必须落成议题和立场的实际变化，不能只列框架节点名称。

读取目标接收目标并建立议题，入口校验未通过就地结束，后续模型、检索器或工具调用次数保持为零。

生成候选步骤固定身份、范围、配置版本和绝对 Deadline，后续子步骤只继承剩余时间，不能各自重新获得完整超时。

执行受限动作读取立场并执行主题逻辑，参数由应用组装，外部返回先保存为受限计划，尚未获得修改领域状态的资格。

观察变化检查结构、范围、版本和主题不变量；下一动作缺少来源、落在旧版本或越过权限时，议题停在 rejected 或 failed。

裁决继续或停止先保存下一动作与终止原因，再产生事件或通知，交付失败可以重放，核心状态写入失败则不能对外宣称完成。

执行受限动作出现部分结果时，由任务合同决定保留、补偿还是整体丢弃；下一动作若可重建就重新生成，外部副作用则查询回执或执行补偿。

实现可以使用函数、Graph、Middleware 或 Workflow，议题的所有权和角色共享同一错误前提的停止规则不会随框架改变。

部分成功需要在步骤边界处理。执行受限动作已经产生一部分下一动作时，程序按任务合同决定保留、补偿或整体丢弃，并记录未完成项，不能默认为全部成功。

执行受限动作和观察变化都要写明逆向动作或不可逆原因，下一动作若可重建就删除后重算，已发送的外部命令只能查询回执或补偿。

## 沿一个知识问题推演

沿“Debate 模式处理有证据的分歧场景：一个知识问题可能只需单次检索，也可能需要分解成多个子问题，系统必须在开始时选择足够但不过度的执行模式”推演 Debate 模式处理有证据的分歧：入口创建 request_id，读取可信身份，把目标和当前版本写入初始状态。

读取目标生成议题与输入摘要；若当前状态缺失，请求返回 rejected，并指出缺少哪项材料，不继续消耗模型或外部服务配额。

生成候选步骤冻结 scope、release、policy 和 deadline_at，用户或模型在正文中提供的同名值只作为普通内容，不能覆盖这份运行时快照。

执行受限动作按“不同角色围绕同一证据包提出主张和质询，裁决器按证据充分性与约束判断；角色数量和轮次固定，不能靠多数票确认事实”推进，每次依赖调用保存 call_id、参数摘要、开始时间与状态版本，以便判断超时前是否已经产生结果。

候选结果对应下一动作、受限计划、修复建议、候选评分或停止决定，观察变化逐项检查权限、版本与领域约束，问题列表为空才允许形成下一状态。

裁决继续或停止写入终态；客户端断开只影响交付通道，重新连接时读取已经保存的议题或事件游标，不重跑核心逻辑。

故障注入选择少数正确证据被多数压过，程序保留原候选和错误位置，只重做失败边界，不能从入口复制整个任务并产生第二份状态。

推演结束后用 request_id 关联议题、下一动作与终止原因，测试据此排除并发请求串线，并确认失败路径没有遗留未关闭资源。

Debate 模式处理有证据的分歧在输入拒绝时不调用依赖，正常路径按 5 个阶段推进，有限修复只重做失败边界。调用次数是控制流断言，不是性能宣传。

Debate 模式处理有证据的分歧的最终记录用 request_id 关联议题、下一动作和失败问题，测试据此证明结果来自本次执行，没有混入并发请求。

## 收敛时应出现哪些信号

Debate 模式处理有证据的分歧正常完成时，议题、立场和下一动作指向同一次执行，重复读取返回同一终态，未完成分支已经取消或有明确所有者。

候选路径、动作记录、观察、评分、剩余预算和停止原因用于还原 Debate 模式处理有证据的分歧的处理过程，可以按阶段和版本聚合；敏感正文留在受控存储中，不复制到日志与指标。

受限计划可能是合法的空结果，但必须带范围、版本和原因；任务明确要求找到材料时，同一个空结果进入拒答而非成功。

依赖返回成功状态只证明传输完成。Debate 模式处理有证据的分歧还要检查下一动作是否满足业务范围、质量阈值和当前版本，明确拒绝也可能是正确终态。

执行受限动作并发完成时，每个分支保留自己的身份和局部预算，观察变化按任务合同接纳可用结果，慢分支不能抹掉已经确认的记录。

议题的状态迁移必须单调：完成不能退回运行中，取消不能被迟到结果覆盖，失败重试也不能绕过入口已经固定的权限。

Debate 模式处理有证据的分歧的成功证据最终要同时回答输入是什么、执行了哪些步骤、交付了什么以及为什么停止；任一项缺失都应留在未确认状态。

Debate 模式处理有证据的分歧把业务验收与服务健康分开。依赖返回 200 只说明传输成功，下一动作仍要满足当前范围和质量要求；明确拒答也可能是正确终态。

Debate 模式处理有证据的分歧的观测指标按阶段和版本聚合。错误率、空结果率、拒绝率、恢复次数与资源消耗回答不同问题，不能压成一个成功率。

## 用确定性模型测试控制逻辑

## 何时改用工作流或多 Agent

采用 Debate 模式处理有证据的分歧前先画出目标到下一动作的最小控制图；固定函数已经能完成任务时，新增模型决策和跨进程议题只会扩大测试与运维范围。
