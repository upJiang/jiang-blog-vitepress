# Computer Use Agent 的观察、动作与验证循环

**Computer Use** 让模型通过截图或可访问性树观察环境，再提出点击、输入、滚动等动作。它不是把鼠标直接交给模型：运行时还要保存观察版本，检查动作目标、风险和权限，执行后重新观察并确认页面确实改变。动作类型和接口约束可对照 [OpenAI Computer Use 指南](https://developers.openai.com/api/docs/guides/tools-computer-use)。

本文沿一个受限页面任务解释五个对象：`observation_id` 记录看到的页面，`element identity` 描述动作目标，`approval` 表示是否允许执行，`execution result` 是浏览器回执，`stop reason` 说明为什么停止。旧截图、坐标漂移、遮挡元素、重复提交、验证码和敏感操作未确认，都必须在对应阶段停下。

::: info 贯穿示例

贯穿示例是一个受限页面任务：读取申请状态，点击“查看详情”，但不能提交表单。身份、权限、页面版本和审批状态由应用提供，模型只产生动作候选。

:::

截图本身不是成功证据。只有动作回执、页面新状态和确定性检查都对应同一个 `observation_id`，运行时才可以把这一步标为已完成。

## 页面操作为什么需要独立的观察层

旧截图执行会破坏 observation_id 与受控动作之间的对应关系，排查时先保留原始输入摘要和发生阶段，再判断是否允许重试。

坐标漂移影响 viewport 或下游解释，不能和旧截图执行共用“重新调用一次模型”的处理方式。

## 观察、动作与确认如何组成接口

Computer Use 的 Harness 持有工作区、工具和权限，模型只能根据观察提出动作候选。因此 observation_id 与 viewport 要有唯一写入方，其他组件只能通过版本化命令申请修改。

浏览器自动化与 Computer Use解决的问题相邻，但控制权不同，比较时要看谁选择检查权限、谁保存 observation_id、谁确认受控动作。

RPA 可以参与同一请求，却不能替代 Computer Use；组合后仍要单独检查环境观察的可信来源和旧截图执行的终止规则。

Computer Use使用的身份、范围和版本来自可信运行时，用户目标可以表达意图，但不能提升权限或改写活动 Release。

坐标漂移发生时，错误回到 viewport 的所有者处理，上游缺输入、当前组件违反不变量和下游不可用分别形成不同终态。

Computer Use 的确定性边界位于 observation_id 写入之前。模型在 Computer Use 中只提交候选值，程序仍要从认证、版本和策略快照补入可信字段。

Computer Use内部可以使用更细的临时对象，跨边界只暴露稳定协议。替换浏览器自动化时，调用方不需要理解内部缓存和 SDK 响应。

## 截图、DOM 与页面版本怎样对应

Computer Use 的输入合同至少列出用户目标、环境观察和能力目录，每项都注明来源、是否必需、允许的缺省值，以及缺失后是在入口拒绝还是进入降级路径。

Computer Use 要分开保存 `observation_id`、viewport、element identity 和动作回执。观察 ID 标识看到的环境版本，viewport 限定空间，元素身份连接观察与动作，回执证明执行后的结果；任一项缺失，都不能把截图当作成功。

并发分支按稳定身份合并 element identity，完成顺序只反映耗时，不能决定结果属于哪个请求，更不能让迟到的旧状态覆盖新修订。

Computer Use 的对外结果要分别表达可交付内容、缺口、取消和未知状态，调用方不必解析错误文案。

viewport 参与乐观并发检查；处理开始后若版本变化，旧候选只保留作审计，不能继续写入 observation_id。

观察版本、动作参数、审批、文件差异、进程结果、截图和测试输出组成 Computer Use 的最小追踪材料，日志只保存稳定 ID、版本和错误类，完整 Prompt、文档正文与凭证不进入指标标签。

契约还需要描述新鲜度。viewport 对应的数据发生变化后，旧缓存、旧候选和未完成任务怎样失效，应由版本或时间规则直接判断，不能依赖模型注意到矛盾。

删除和撤回也属于数据生命周期。Computer Use引用的原始对象被移除时，稳定 ID 可以保留审计关系，正文与派生结果则按策略失效，避免继续向用户展示过期内容。

::: warning Computer Use 的可信边界

受控动作通过结构校验后仍是候选。Computer Use使用的身份、权限、知识版本与业务事实由应用从可信服务读取，核对完成后才能执行或交付。

:::

## 一次页面动作的控制流

Computer Use 的一次循环要留下成对观察：动作前的截图或可访问性树带版本，动作参数经过风险检查，执行回执产生后再采集新观察。若新观察没有显示预期变化，运行时停在待确认，而不是根据模型的文字宣布成功。

观察环境接收用户目标并建立 observation_id，入口校验未通过就地结束，后续模型、检索器或工具调用次数保持为零。

检查权限读取 viewport 并执行主题逻辑，参数由应用组装，外部返回先保存为可审查差异，尚未获得修改领域状态的资格。

执行并重新观察检查结构、范围、版本和主题不变量；受控动作缺少来源、落在旧版本或越过权限时，observation_id 停在 rejected 或 failed。

实现可以使用函数、Graph、Middleware 或 Workflow，observation_id 的所有权和旧截图执行的停止规则不会随框架改变。

部分成功需要在步骤边界处理。

## 沿一次受限点击推演动作回执

沿“Computer Use场景：编码助手需要读取仓库、修改一个文件并运行测试，但不能访问工作区之外的路径，也不能在测试失败时宣称完成”推演 Computer Use：入口创建 request_id，读取可信身份，把用户目标和当前版本写入初始状态。

观察环境生成 observation_id 与输入摘要；若环境观察缺失，请求返回 rejected，并指出缺少哪项材料，不继续消耗模型或外部服务配额。

检查权限按“循环先获取截图或可访问性树并标记观察版本，模型提出动作，运行时验证目标与风险，执行后重新观察；高风险点击和提交需要确认”推进，每次依赖调用保存 call_id、参数摘要、开始时间与状态版本，以便判断超时前是否已经产生结果。

运行确定性验证写入终态；客户端断开只影响交付通道，重新连接时读取已经保存的 observation_id 或事件游标，不重跑核心逻辑。

故障注入选择遮挡元素，程序保留原候选和错误位置，只重做失败边界，不能从入口复制整个任务并产生第二份状态。

推演结束后用 request_id 关联 observation_id、受控动作与终止原因，测试据此排除并发请求串线，并确认失败路径没有遗留未关闭资源。

Computer Use在输入拒绝时不调用依赖，正常路径按 5 个阶段推进，有限修复只重做失败边界。调用次数是控制流断言，不是性能宣传。

Computer Use 的最终记录用 request_id 关联 observation_id、受控动作和失败问题，测试据此证明结果来自本次执行，没有混入并发请求。

## 动作完成后怎样确认页面真的改变

Computer Use正常完成时，observation_id、viewport 和受控动作指向同一次执行，重复读取返回同一终态，未完成分支已经取消或有明确所有者。

观察版本、动作参数、审批、文件差异、进程结果、截图和测试输出用于还原 Computer Use 的处理过程，可以按阶段和版本聚合；敏感正文留在受控存储中，不复制到日志与指标。

依赖返回成功状态只证明传输完成。Computer Use还要检查受控动作是否满足业务范围、质量阈值和当前版本，明确拒绝也可能是正确终态。

observation_id 的状态迁移必须单调：完成不能退回运行中，取消不能被迟到结果覆盖，失败重试也不能绕过入口已经固定的权限。

Computer Use 的成功证据最终要同时回答输入是什么、执行了哪些步骤、交付了什么以及为什么停止；任一项缺失都应留在未确认状态。

Computer Use把业务验收与服务健康分开。依赖对 Computer Use 返回 200 只说明传输完成，内容仍要满足当前范围和质量条件。

Computer Use 的观测指标按阶段和版本聚合。评估 Computer Use 时，把错误、空结果、拒绝、恢复和资源消耗分开统计，避免一个成功率掩盖不同故障。

## 坐标过期、弹窗和登录失效

Computer Use 的错误要按观察到执行的顺序定位：观察过期时重新采集，元素身份变化时停止旧动作，执行器超时先查询回执，验证失败则保留差异并暂停交付。重复点击不是通用修复，可能把一次可逆失败变成不可逆副作用。

Computer Use发现旧截图执行后重新读取权威状态，旧候选可以保留作审计，却不能覆盖新版本；前后状态无法兼容时，当前尝试以 conflict 结束。

Computer Use发现坐标漂移后重新读取权威状态，旧候选可以保留作审计，却不能覆盖新版本；前后状态无法兼容时，当前尝试以 conflict 结束。

遇到遮挡元素时，先记录发生阶段、错误类别和责任对象。Computer Use保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

Computer Use处理重复提交时需要稳定身份和结果回执，再次收到同一请求先读取旧结果；外部结果未知就停在 unknown，不能猜测失败后重新执行。

Computer Use发现页面跳转后沿用旧身份后重新读取权威状态，旧候选可以保留作审计，却不能覆盖新版本；前后状态无法兼容时，当前尝试以 conflict 结束。

遇到验证码时，先记录发生阶段、错误类别和责任对象。Computer Use保留输入摘要和状态版本，由对应组件决定重试、降级或终止。

Computer Use将终态、可重试性和资源清理结果写入记录；后台扫描器根据 observation_id 判断任务是在运行、等待恢复还是已失败。

Computer Use执行前固定 Deadline、动作上限、重复签名、无进展阈值、预算和取消信号；任一条件触发，检查权限停止创建新工作。

Computer Use把重试时间和次数计入总预算。Computer Use 每次重试先扣减剩余额度，达到上限就保留原始错误。

Computer Use 的清理动作设计成幂等操作；仍被活动任务或 Lease 引用的资源拒绝删除。

## 在假页面中回放动作序列

使用隔离工作区和假环境重放观察动作循环，断言越界动作被拒绝、写操作需要审批、验证失败不会标记完成；测试显式给出用户目标、初始 observation_id、预期受控动作和终止原因，不能只断言返回值非空。

Computer Use 的单元测试用 Fake Adapter 固定受控动作与错误，断言参数、调用顺序、状态修订和清理动作，这些结果只证明本地控制逻辑。

契约测试围绕用户目标、observation_id 和可审查差异构造合法与非法样本，Schema 解析成功后继续检查权限、版本与领域不变量。

故障测试注入旧截图执行和坐标漂移，记录检查权限是否被调用、observation_id 是否改变、资源是否释放，以及同一身份重试会不会重复执行。

Computer Use 的集成测试连接真实协议与隔离存储，检查序列化、约束、并发和超时；需要在线服务时另行记录服务版本、时间、配置与凭证条件。

Computer Use 的回归报告要保留失败类型分布。在 Computer Use 的回归中，拒绝、超时、权限错误和空结果必须保持各自类型，状态变化本身就是行为契约。

Computer Use 的性质测试随机改变 observation_id 顺序、重复提交、完成顺序或状态版本，断言权限不扩大、终态不倒退、同一身份不产生两次副作用。

Computer Use 的离线评测关注质量变化，运行时测试关注控制和恢复，两类证据都齐全才可交付。Computer Use只有两类证据都存在，才能同时回答“结果是否合格”和“系统是否安全完成”。

## 浏览器会话、资源上限与治理

Computer Use 的观察图像、可访问性树、动作 Schema 和浏览器版本必须绑定在同一执行记录中。页面结构升级后，旧动作只能对旧观察版本回放，不能拿新截图替旧证据。

Computer Use 的容量主要受观察体积、工具调用、后台进程、浏览器会话、文件差异和循环步数影响，并发可能缩短单次等待，也会占用连接、配额、内存和下游吞吐，必须沿观察环境、提出动作、检查权限、执行并重新观察、运行确定性验证逐层核算。

Computer Use 的候选版本在固定样本上比较正确性、错误类型、延迟和资源消耗，旧截图执行等安全红线回归时直接停止发布，不能用平均质量抵消。

旧截图执行的降级路径在发布前写好，可以减少非关键增强、返回已经确认的受控动作，或明确暂时无法确认，缺失事实不能交给模型补写。

动作失败时先用 `request_id`定位观察版本、坐标或语义定位参数、审批事件、动作回执和下一帧截图，再判断是定位错误、权限拒绝还是页面没有完成。确认原动作没有副作用后才允许重试。

Computer Use 的数据按证据用途分级保留，聚合字段可以留得更久，用户目标和大体积受控动作设置短期限、访问控制与删除通道。

Computer Use先在单进程实现 observation_id、超时、错误和测试，只有恢复与容量证据提出要求时，再增加队列、Lease、分布式缓存或工作流引擎。

Computer Use 的监控阈值要对应可执行动作。Computer Use 的分支、依赖、上下文和预算接近上限时，应限流或缩小候选；告警本身不会停止正在运行的任务。

回滚要覆盖代码之外的状态。Computer Use若改变 Schema、缓存键或持久化记录，旧版本是否还能读取新写入数据必须提前验证；无法双向兼容时采用候选版本隔离。

## Computer Use 与普通工具调用的边界

采用 Computer Use前先画出用户目标到受控动作的最小控制图；固定函数已经能完成任务时，新增模型决策和跨进程 observation_id 只会扩大测试与运维范围。

浏览器自动化可以固定选择器和步骤，Computer Use 让模型依据观察提出下一步，因此必须额外保存 `observation_id`、动作风险和审批结果。模型的点击描述不能代替页面回执。

RPA 可以与 Computer Use组合，但外部知识仍需授权，工具调用仍需校验，模型产生的受控动作仍停留在候选状态。

Computer Use适合价值足够、旧截图执行可观察且预算可接受的任务，高风险、不可逆的决定需要确定性规则或人工批准。

执行期间修改 viewport 可以检验并发设计，旧动作若仍能覆盖 observation_id，说明版本或 Lease 有缺口，增加 Prompt 规则无法修复这类竞态。

Computer Use 会增加观察 ID、浏览器状态和动作恢复责任。设计记录要写清停止、审批与回滚路径。

先用一个观察 ID、几类明确错误和确定性测试验证循环，再考虑多窗口或并发。

若普通浏览器自动化已有稳定选择器和固定步骤，就继续使用它；页面状态需要模型判断时再引入 Computer Use。

## 一次受限的页面操作如何结束

Computer Use Agent 的输入包括目标、当前页面截图、可操作区域、会话权限和动作预算。模型只能提出点击、输入、滚动或停止等候选，Runtime 检查坐标是否在允许区域，确认页面域名和当前用户范围，再交给浏览器适配器执行。适配器返回新的截图、可访问性树摘要和动作结果，Runtime 把它们写成下一轮 Observation。

例如目标是打开“远程访问申请”页面。第一次观察只显示导航栏，模型提出点击“服务目录”；程序验证该元素仍存在且不在禁止区域。页面加载后出现外链确认按钮，策略要求人工批准，循环在 `awaiting_approval` 停止，不会因为模型继续提出点击而绕过审批。用户拒绝后，系统记录拒绝原因并关闭浏览器会话。

视觉动作必须有回读。点击成功不代表业务状态改变，表单提交后要从页面状态、网络响应或后端查询确认结果。元素位置变化、遮挡、弹窗和网络超时都属于不同错误，重试前先重新截图并确认动作没有副作用。重复提交表单需要幂等键或状态查询，不能只靠“上一次点击看起来失败”。

测试使用静态截图和假的浏览器适配器，固定元素坐标变化、域名跳转、审批拒绝和超时，断言越界坐标不会执行、敏感页面会暂停、终态事件唯一。真实浏览器验证还要记录浏览器版本、登录状态和测试账号，截图写入临时目录并在验证结束后删除。

## Computer Use 的动作验证自测

用“编码助手读取文件、修改内容并运行测试”回放时，Harness 先固定观察版本、工作区和执行预算。观察版本、动作风险、工作区范围和验证结果由事件和 Checkpoint 保存，模型只能提出动作候选，策略层决定候选能否进入执行器。
