# LLM、工作流、RAG 与 Agent 如何分工

假设员工问：“远程访问为什么被拒绝，我该怎样申请？”系统可能需要理解问题、查询当前账号、读取最新规则，再决定是否给出申请步骤。这个任务同时碰到了语言理解、事实查询和业务控制，把它统称为“AI”会掩盖真正的设计问题。

::: info 四个概念先放在一张图上

- **LLM** 根据当前上下文生成候选文本或结构。
- **工作流** 由程序预先定义步骤和条件分支。
- **RAG** 先检索外部知识，再把证据交给模型生成。
- **Agent** 保存运行状态，让模型提出下一步动作，再由程序决定是否执行。

:::

## 同一个问题会经过四条不同路径

单独使用 LLM 时，应用只把问题发给模型。模型可以解释“远程访问”这个概念，却看不到当前账号状态，也不知道组织刚更新的申请规则。

固定工作流会按代码规定的顺序执行：校验身份、查询账号、读取规则、渲染答复。每一步都可预测，用户怎样措辞不会改变控制图。

RAG 在生成前加入检索。它能从已授权文档中找出最新规则，但检索本身不决定“下一步要查账号还是查规则”。这项决定可以由固定代码做，也可以交给受限 Agent。

Agent 会在运行时保存观察结果。模型可以先提议查询账号，程序校验工具名、参数和权限后执行；结果回到状态中，模型再提议检索规则或结束。**模型提出候选动作，程序拥有执行权。**

| 方案 | 输入 | 状态在哪里 | 谁决定下一步 | 失败怎样停止 |
| --- | --- | --- | --- | --- |
| LLM | 消息和上下文 | 本次请求 | 模型继续生成 | 输出上限或 API 失败 |
| 工作流 | 业务请求 | 程序状态 | 代码和状态机 | 已定义的失败终态 |
| RAG | 查询和知识范围 | 检索链与索引 | 程序或 Agent | 无结果、超时或证据不足 |
| Agent | 目标、状态、可用动作 | Agent Runtime | 模型提议，程序裁决 | 步数、Deadline、拒答或取消 |

## LLM 负责生成候选

LLM 位于模型层。应用把消息编码为 Token，模型根据参数和本次上下文计算后续 Token 的候选分布，直到生成结束。它擅长处理同一意图的不同说法，也适合摘要、分类、抽取和文本生成。

下面四条边界都在回答同一个问题：模型能生成什么，哪些事实仍要由应用确认。

### 模型参数不是事实数据库

参数保存训练得到的统计规律，不能按账号 ID 精确读取当前状态。文档更新以后，模型参数也不会自动变化。需要当前事实时，应用要查询业务系统或检索已发布知识。

### 上下文只属于当前调用

系统规则、历史消息、证据和工具结果只有被装进上下文，才会影响这次生成。调用结束后，应用若没有持久化并在下次重新装配，它们不会自动成为长期记忆。

### 生成不是确定性查询

模型在多个语言候选中继续生成，数据库则按条件、索引和事务返回记录。降低采样随机性可以让措辞更稳定，却不能把概率生成变成事实查询。

### 结构正确不代表内容真实

JSON Schema 可以要求 `status` 必须是字符串，却无法证明模型给出的账号状态存在。用户身份、可见范围、知识版本和截止时间应由服务端补入，不能接受模型回填。

## 工作流把确定步骤写进程序

工作流适合步骤已知、分支有限、业务规则必须稳定的任务。比如报销审核无论如何表述，都要经过身份校验、字段检查、额度判断和审批。LLM 可以负责从附件提取字段，但审批顺序和金额规则留在代码中。

工作流并不等于同步脚本。它可以排队、并行、暂停和重试。判断依据是控制图是否在开发时已经确定，而不是执行用了多少服务。

## RAG 为回答补充外部证据

RAG 横跨检索和生成。查询先进入关键词、向量或结构化检索，候选经过权限与版本过滤，再把少量证据交给模型。模型负责组织答案，引用和事实验证仍由程序处理。

RAG 可以嵌在工作流里，也可以成为 Agent 的一个工具。它解决的是“知识从哪里来”，不负责通用任务规划，也不天然拥有长期记忆。

## Agent 在受限循环中选择动作

Agent 位于更上层的控制运行时，至少需要目标、当前状态、动作集合、观察结果和终止条件。只有一次模型调用、没有状态变化的问答，更准确地说是 LLM 应用。

Agent 的自主性也有范围。只读知识查询可以允许模型选择检索分支；删除数据、发送付款或修改权限则应进入审批，甚至完全排除在模型可选动作之外。

## 选择能完成任务的最小方案

资料已经在输入中，只需改写或抽取时，用一次 LLM 调用。步骤固定而且需要审计时，先写工作流。回答依赖外部文档时加入 RAG。只有中间结果确实会改变后续动作，而且分支无法用少量规则提前列完时，再引入 Agent 循环。

复杂方案会增加状态、成本和失败面。选择 Agent 之前，可以先写出可用动作、每个动作的权限、最大步数和所有终态；这些内容写不清，运行时也无法可靠控制它。
