# Block 文档模型怎样保留结构与来源

解析器把 DOCX、PDF 或 HTML 变成一段规范文本以后，结构仍然很脆弱。标题只是一行 `##`，表格只是几行带管道符的文本，页码也可能只剩 `Page 4`。切块器若直接按字符数截取，不知道某段属于哪个章节，也无法保证代码围栏、表头和正文不会被拆散。

Block 是解析结果与 Chunk 之间的文档中间表示。它把标题、段落、列表、代码和表格识别成不同类型，同时保存章节路径、出现顺序和来源身份。Chunk 决定“检索一次召回多大内容”，Block 负责回答“原文中这一块是什么，位于哪里，与周围内容有什么结构关系”。

这层模型的价值会在引用时显出来。答案说“远程访问需要审批”时，系统不应只返回一个向量相似的字符串，还要能定位到文档版本、Source、章节和页码。Block 提供结构坐标，Chunk 把一组相邻结构组织成检索单元，Evidence 再把选中的 Chunk 与最终 Claim 绑定。

## Source、ParsedDocument、Block 与 Chunk 分别保存什么

一份文档进入知识库后会经过四层表示。Source 描述来源身份和层级，例如根制度、附件或外部页面；ParsedDocument 是某个解析器版本恢复出的规范文本与警告；Block 是规范文本内部的结构单元；Chunk 是面向召回和上下文预算的派生单元。

Source 的身份应跨同一逻辑来源的版本保持稳定。它保存类型、父 Source、顺序、标题、来源地址、解析版本和可见范围。ParsedDocument 可以随解析器升级重新生成，Block 会跟着变化。Chunk 还会受切块参数、Embedding 文本和索引版本影响，生命周期最短。

这四层不能用一个 `content` 字段替代。若只有 Chunk，解析器升级后无法比较结构变化；若只有 Block，检索时还得临时决定组合和预算；若只保留原件，线上查询每次都重新解析，成本与延迟无法接受。每层都保留指向上一层的稳定引用，才支持重建、回滚和引用。

```text
原始对象
  -> Source Version
      -> ParsedDocument
          -> Block
              -> Chunk
                  -> Evidence
```

当前配套实现采用了一个较紧凑的版本：Source Version 和 Chunk 会持久化，`SemanticBlock` 只在切块过程中存在内存里，并没有独立 Block 表。页码由解析器生成的标题行传递，Chunk 最终保存 Source Version、章节路径和邻接关系。这个实现能验证结构切块主线，却不能声称已经持久化页面坐标或 Block 历史。需要精确版面引用时，应扩展模型并补迁移与回归。

这个取舍省掉了 Block 持久层和一次写入代价，但解析结构无法单独审计，切块异常也较难与解析结果分开回放。是否增加独立存储，应由精确引用、跨版本差异和重建成本决定。

## Block 类型要对应后续处理差异

最小类型集合可以从 `heading`、`paragraph`、`list`、`code` 和 `table` 开始。它们不是为了让数据看起来整齐，而是因为切块和检索策略确实不同。标题更新章节路径，通常不单独成为答案正文；段落可以按语义句子拆分；连续列表应尽量保住项目关系；代码需要保持围栏；表格要同时支持整表语义和按行精确查询。

更完整的系统还可能有 `image_caption`、`quote`、`callout`、`page_break`、`footnote` 和 `formula`。新增类型之前先确认下游会如何使用。解析器识别出一个图像，却没有说明文字、OCR 或版面坐标，仅创建 `image` Block 并不会增加可检索知识，只会让类型数量膨胀。

Block 的基础字段可以这样设计：

```python
from dataclasses import dataclass, field
from typing import Any, Literal


BlockKind = Literal["heading", "paragraph", "list", "code", "table"]


@dataclass(frozen=True)
class Block:
    block_id: str
    source_version_id: str
    kind: BlockKind
    ordinal: int
    content: str
    section_path: tuple[str, ...] = ()
    heading_level: int = 0
    page_number: int | None = None
    locator: dict[str, Any] = field(default_factory=dict)
    structured: dict[str, Any] = field(default_factory=dict)
```

`ordinal` 表示当前 Source Version 内的阅读顺序，`section_path` 表示所属标题链，`page_number` 和 `locator` 提供可选的格式坐标，`structured` 保存表头、表格行或其他类型字段。身份、权限和 Release 不从正文推断，它们经 Source Version 继承。

这个模型中的页面字段属于完整设计建议。若解析结果只有 `## Page 4`，构建器可以把它识别为特殊标题并传入章节路径，但没有真实坐标就不能生成 PDF 高亮框。公开接口应区分“可定位到页”和“可定位到页面区域”，不能把前者包装成精确引用。

## 标题状态机怎样生成章节路径

规范文本按行扫描时，标题会修改一个章节栈。遇到一级标题，清空旧路径并放入新标题；遇到二级标题，保留一级标题，替换第二级以及更深内容；遇到四级标题却没有三级标题，可以保留稀疏层级，也可以记录层级跳跃警告。选择哪一种要固定，否则同一文档重建时路径会漂移。

假设输入如下：

```md
# 远程访问制度

## 申请条件

正式员工需要已登记设备。

### 审批范围

生产权限需要负责人批准。

## 失败处理

审批拒绝后不得自动重试。
```

两个正文 Block 的路径分别是 `远程访问制度 / 申请条件`、`远程访问制度 / 申请条件 / 审批范围`，最后一个正文属于 `远程访问制度 / 失败处理`。标题本身会计入结构覆盖统计，但紧凑实现不会直接把它写成叶子 Chunk。后续可以生成 section parent，把章节标题与多个叶子内容关联起来。

扫描器还要处理代码围栏。进入围栏后，里面以 `#` 开头的行是代码，不是标题；看到空行也不应结束代码 Block。只有匹配到关闭围栏，才恢复普通解析。若文档结束时围栏未关闭，可以保留代码并写警告，或者让质量门禁失败，不能把剩余所有代码误当正文标题。

列表与段落也需要状态。连续列表项组成一个 list Block，普通正文积累到空行形成 paragraph Block。标题、表格或代码开始前先刷新缓冲区，避免上一段内容被带进新类型。这样的确定性状态机比让模型逐段分类更容易回归，也不会因模型版本变化改变基础结构。

## 表格必须保留结构和原始呈现

Markdown 表格的第一行是表头，第二行是分隔线，后面是数据行。Block 构建器确认这个形状后，解析转义管道符，补齐每行列数，得到 `table_headers` 与 `table_rows`。同时保留规范表格文本，界面和引用可以展示原样结构。

表格不能只变成一段“字段值字段值”的文本。用户按编号、人员或日期查询时，需要把每行映射成 `{表头: 单元格}`，精确词检索也要保留完整单元格。另一方面，整表标题、列间关系和汇总语义无法由单行表达，所以小表可以生成一份整表 Chunk，再为每行生成结构化 Chunk。

Block 层负责识别表头和行，Chunk 层决定是否生成整表、怎样拆超大表。职责分开后，表格策略变化不需要重新解析 DOCX 或 PDF。若表格识别失败退化成段落，Coverage Manifest 的表格计数会下降，关键编号可能只剩连续文本。回归应把这种变化视为结构损失，而不是“仍然有文字所以成功”。

合并单元格会让矩形化变得困难。简单解析器通常复制、留空或丢失跨行含义。选择必须进入结构字段与警告。对于审批矩阵这类关键表，更可靠的做法是保存原表坐标、合并范围和显示值，由专门表格切块器处理，而不是在 Block 构建时凭相邻行猜关系。

## 代码、列表和页面标记不能按普通段落处理

代码 Block 要保存语言围栏和换行。内容超过 Chunk 最大值时，可以在代码行或语义片段之间拆分，每一段重新补齐开闭围栏。直接截断会产生无法渲染的 Markdown，还可能把函数签名与关键分支分开。代码检索常需要符号名，结构字段可以额外保存语言、函数或文件来源，但这些信息要来自解析器或语法树，不由通用正则随意猜测。

列表表达一组同层条件。把每个项目拆成独立 Block，可能丢掉前面的总领句；把十几项塞进一个 Block，又会让检索只需要其中一项时浪费预算。最小实现先将连续项目保留为一块，后续语义切块根据长度拆分，并让各子块继承同一章节路径。

页码标记既不是普通章节标题，也不是答案正文。PDF 解析器输出 `Page N` 后，Block 层可以更新 `page_number`，但不应让“Page 4”参与 Embedding，避免每页都产生相似噪声。页码与章节路径是两个维度：章节可以跨页，一页也可以包含多个章节。只把页码塞进 section path，会让标题树混入版面信息。

紧凑实现把页码作为二级标题保存，这有利于先跑通来源定位，却存在限制：真实二级章节和页码处在同一个栈层，可能互相覆盖。要支持精确引用，应在解析阶段输出独立 page marker 或 Block locator，再由构建器同时维护章节栈与当前页。

图片说明应独立于 OCR 原文。可见题注可以作为 paragraph 或 image caption，OCR 文字带上图片或页面定位，模型生成的图片摘要还要保存生成版本与低信任标记。三者混成一个 `content`，后续无法知道引用的是作者原话还是视觉模型解释。

## 显示文本、回答文本与 Embedding 文本用途不同

`display_content` 面向读者，应尽量接近原文，保留标题、表格和代码格式。`answer_content` 面向模型上下文，可以补上章节标题或表头，使单个 Chunk 离开原位置后仍可理解。`embedding_text` 面向向量模型，可以加入必要的来源标题和章节路径，但应去掉重复导航、页码噪声和纯展示符号。

三个字段都必须指向同一个 Block 或 Chunk 身份。它们允许表达不同，不能承载互相冲突的事实。例如显示文本是“需要负责人批准”，Embedding 文本可以是“远程访问审批范围：生产权限需要负责人批准”，却不能自行加入“仅部门负责人”这种原文没有的限制。

这一拆分也避免在界面展示为检索优化添加的前缀。若把标题和别名直接写回正文，用户复制引用时会看到系统补充词，还可能误以为它们来自原文。检索表示的构造方式应版本化，便于 Embedding 模型切换后重建。

当前 Chunk 记录同时保存内容、回答内容、Embedding 文本和显示文本，还保留表格字段与精确词。这些字段由 Block 和 Chunk 构建过程确定，不由模型临时生成。模型可以在回答阶段选择引用，但不能修改历史 Source 的展示文字。

## 稳定 ID 要区分逻辑来源与具体版本

ID 设计经常在两种需求间拉扯。一方面，希望文档小改后相同段落保持身份，便于引用和缓存；另一方面，任何内容变化都必须产生新版本，避免旧证据与新正文混在一起。解决办法不是找一个万能 ID，而是分层。

Source ID 表示逻辑来源，例如一份制度或一个附件。Source Version ID 由文档版本和 Source ID 生成，明确指向某次发布。Block ID 再包含 Source Version 与结构身份，Chunk ID 包含版本、类型、章节路径和内容摘要。跨版本比较可以通过 Source ID 和结构匹配完成，在线引用始终使用版本化 ID。

只使用数组位置会漂移。文档开头新增一个段落，后面所有 `block-12` 都变成 `block-13`。只使用内容哈希也会冲突，同一句“适用范围如下”可能出现多次，两个 Block 得到同一身份。较稳的组合包括 Source Version、类型、章节路径、同路径内序号和内容摘要。若要跨版本保持逻辑身份，还需单独的匹配过程，不能让旧 ID 静默指向新文字。

稳定 ID 的输入要规范化。换行、标题路径和表格结构采用固定序列化，哈希算法与构建版本写入元数据。序列化字段顺序变化也会造成全部 ID 重建，所以实现前要把编码规则固定并加黄金样本测试。

权限不编码进内容哈希，却必须跟随 Source Version。两个范围内恰好有相同正文，内容摘要可以相同，版本身份和权限指纹仍然不同。检索缓存命中相同 Chunk 文本后也要重新鉴权，不能以哈希相同为由复用另一租户的结果。

## 一页制度怎样变成可追踪 Block

输入是上一节解析后的制度文档片段。它来自 Source `policy-main` 的候选版本，解析器已经给出页码标记、标题、两段正文、一份审批表和一个代码围栏。构建器读取时同时维护当前页、章节栈、Block 序号和代码状态。

先遇到 `Page 3`，当前页设为 3；随后读取二级标题“申请条件”，章节栈更新。第一段生成 paragraph Block，内容是设备要求，路径为“申请条件”，页码为 3。审批表生成 table Block，保存两个表头和三行字段。后面的配置片段从开围栏到闭围栏组成 code Block，即使内部出现 `# production` 也不会修改章节。

输出状态包含四类 Block、连续 ordinal、共同 Source Version、章节路径和页码。紧凑实现随后跳过 heading Block，对段落、列表与代码按长度产生叶子 Chunk，对表格产生整表和行 Chunk，再添加章节父 Chunk。叶子之间写入 previous 与 next 引用，供召回后的邻接补全使用。

正常输出可以回答“生产权限由谁审批”，表格行 Chunk 提供字段值，display content 仍能展示原表，引用回 Source Version 的第三页。若构建器故意漏掉表格分隔线，表格会退化为 paragraph，Coverage 中 `tables` 与 `table_cells` 降为零。质量测试据此失败，候选版本不会激活。

另一个故障样本在代码结尾移除围栏。构建器若把剩余页面都吞进 code Block，后续标题数和段落数会明显下降。测试不仅要检查 Block 数，还要检查类型序列、章节路径和最后一个 Block 的范围。错误证据指向未闭合围栏与解析版本，而不是笼统返回“切块失败”。

这条推演的输入、状态、调用和输出都是确定的，不需要模型参与。模型不会比状态机更可靠地识别 Markdown 基础结构。若原格式需要视觉版面理解，应该在解析层引入受评测的视觉适配器，并把结果标成派生内容，而不是让 Block 构建器临时猜测。

## 来源定位器要服从原格式的坐标

`source_version_id` 只能定位到一份来源版本，不能定位到原文中的具体位置。用户点击引用后想看到第三页的审批表，系统还需要页码、表格身份或文本区间。不同格式没有统一的天然坐标，Block 的 `locator` 应采用带类型的结构，而不是一个含义不明的字符串。

PDF 最常见的定位器是页码，若解析库保留版面信息，还可以加矩形框与页面尺寸。页码在原文件内稳定，矩形框却会受重新排版和 OCR 结果影响，所以引用必须固定到原始对象版本。只有页码时，界面可以打开对应页面；有经过验证的矩形框时才做高亮。不能根据 OCR 文本长度反推坐标后宣称精确定位。

HTML 可以保存最终 URL、DOM 路径、元素属性和规范文本偏移。DOM 路径会因导航或广告改版变化，文本偏移会因前文插入内容变化。更稳的引用同时带 Source Version、元素路径和一小段原文摘要，打开历史快照时按版本定位；无法保存快照的网页只能标注为可变来源，并在重新抓取后生成新版本。

DOCX 的定位器可以描述正文元素序号、标题路径、表格序号与行列；XLSX 使用工作表名和单元格范围；PPTX 使用幻灯片编号与形状身份。当前通用解析器没有为这些对象持久化完整坐标，只保留规范文本、结构计数和 Source Version，因此现阶段可以提供章节级引用，不能承诺单元格或形状级高亮。补充 locator 时要从解析器一路传到 Block、Chunk、Evidence 和引用界面，单改最终 URL 没有用。

定位器还要考虑原文修改。活动版本切换后，旧答案引用仍应打开旧 Source Version，或者明确提示该版本已经撤回；不能拿旧页码跳到新文件同一页。新旧 Block 的相似度可以帮助迁移收藏和缓存，但不能改变历史 Claim 的证据身份。

引用展示时优先返回 `display_content` 的短片段，并对照 locator 从原件再次读取。两者不一致说明对象、解析结果或索引发生漂移，系统应停止高亮并记录完整性错误。模型生成的 `answer_content` 和增强过的 `embedding_text` 不适合作为原文引用，因为其中可能含系统补充的标题或别名。

## Block Schema 升级要能重建旧结果

Block Schema 会演进。早期版本可能只有 `kind` 和 `content`，后续增加章节路径、页码、表格字段或 locator。若直接在原记录上补默认值，读者无法分清“当时解析到了空值”还是“旧版本根本没有这个字段”。每批 Block 应记录 schema 版本和构建器版本，缺失字段按版本解释。

序列化必须确定。章节路径保持数组顺序，结构字段使用固定键顺序，换行统一，页码和 ordinal 使用明确整数类型。稳定 ID 计算前采用同一套规范化字节，语言运行时或 JSON 库升级不能悄悄改变结果。黄金样本应保存输入、规范序列化和期望哈希，任何调整都需要显式升级构建版本。

新增可选字段通常能让旧读取器忽略，新类型或字段语义变化却可能不兼容。例如把 `table` 拆成 `table_header` 与 `table_row`，旧 Chunker 不认识新类型时不能按 paragraph 兜底，否则表格质量门禁被绕过。候选任务应检查读取器支持的 schema 范围，不兼容就拒绝构建，并保留旧活动索引。

迁移有两种方式。可从旧 Block 计算出新字段且语义确定时，可以做版本化数据迁移；需要新的页码、坐标或表格结构时，应从原始对象重新解析。缺少原件就无法可靠补出 locator，系统只能保留旧能力并标记不可重建，不能让模型猜一个位置写回历史记录。

回滚也要看数据格式。新版本只写候选区，旧服务继续读取旧活动 Block 或 Chunk；候选通过后再切换。若新 Schema 已经覆盖了旧记录，代码回滚可能无法读取，因此“部署可以回滚”不代表内容索引可以回滚。保存原件、解析版本和旧活动索引，才有真正的恢复路径。

重建完成后的差异报告按 Source 展示：Block 数量、类型序列、章节路径、页码覆盖、表格结构和警告怎样变化。只报告“重建成功 100%”没有审查价值。某一章节从 table 变成 paragraph，即使所有任务都返回成功，也应阻止自动激活。

## Coverage Manifest 检查结构有没有丢失

Block 构建过程中可以统计标题、段落、列表项、表格、表格行、非空单元格、代码块、链接和可见字符。生成 Chunk 后再统计 Source 数、Chunk 数、保留内容单元、重复 Chunk、孤立邻接和超限 Chunk。这些数据合成 Coverage Manifest，为候选版本提供可比较的结构快照。

保留率的分母和分子要定义清楚。若按字符计算，Markdown 符号和格式前缀可能影响结果；按结构单元计算，又要规定表格一行算一个还是每个单元格算一个。指标适合发现大规模丢失，不替代关键事实断言。保留率很高，仍可能恰好漏掉一行权限条件。

结构计数应按 Source 分开后再汇总。一份附件完全为空，而主文档很长，汇总字符保留率可能仍然通过。至少检查每个必需 Source 有内容、每份表格有表头和行、章节路径没有异常断裂，再看全局比例。

Coverage 数据要和解析器、Block 构建器及 Chunker 版本一起保存。版本升级后比较差异时，标题增加可能来自识别改进，也可能来自代码注释被误判。自动门禁发现显著变化后应输出具体 Source 和结构类型，供人工核对，而不是只报一个总分。

## Block 测试要覆盖顺序、身份和退化

单元测试从短小的规范文本开始，断言标题栈变化、列表边界、代码围栏、表格矩形化和空行刷新。一个样本专门在代码里放 Markdown 标题，在表格单元格里放转义管道符，证明状态机没有误分。另一个样本使用重复正文，确认两个位置不会得到同一个版本化身份。

来源测试构造根 Source 与附件，顺序字段故意和输入数组不同。构建结果应按明确顺序组织，同时保持每个 Block 的 Source Version。父 Source 不存在、Source ID 重复或没有根 Source 时，Manifest 在 Block 构建前就拒绝，避免生成无法追踪的派生数据。

表格测试同时检查原始呈现与结构字段。表头为空时生成的占位列名要稳定，短行补空列，超长行遵循固定规则；关键业务编号进入 exact terms，但普通中文描述不会被错误当成编号。小表整表 Chunk 和逐行 Chunk 指向同一个 table ID。

性质测试可以随机插入空行、调整换行风格或重复执行构建，断言相同规范输入得到相同 Block 序列和 ID。插入一个真实段落后，受影响章节可以变化，其他 Source 的身份不应全部重建。若实现仅有内存 Block，就测试最终 Chunk 的章节路径、类型与 Source 引用，不能声称验证了不存在的 Block 持久层。

端到端回归从 ParsedDocument 进入候选版本，故意让表格退化，检查 Coverage 门禁拒绝激活；恢复解析后重建，确认活动版本切换。测试输出要记录输入版本、构建版本、类型序列和失败原因，没有这些证据时不能写“Block 模型已完整保留原文”。

## Block 的边界是结构事实，不是检索策略

Block 不决定向量 Top K、Rerank 或 Evidence 预算，也不直接把一段文字塞进模型。它提供稳定结构，Chunker 根据目标长度、最大长度、表格策略和父子关系生成检索单元。Embedding 层再为这些单元构造向量表示。

Block 也不能修复解析器没有拿到的内容。OCR 漏了一行编号，Block 最多保存缺失警告；把相邻文字拼起来猜编号会破坏来源。标题样式错误导致章节路径为空时，可以降级为无章节 paragraph，但必须记录结构退化，不能虚构标题。

显示文本与检索文本可以不同，来源事实必须一致。任何为了召回添加的标题、别名和上下文都放在派生字段，引用仍返回原始显示内容和 Source Version。这样读者能分清作者写了什么，系统为了检索补了什么。

下一步由[语义切块](/docs/ai-agent/rag-semantic-chunking)决定 Block 怎样组合成 Chunk。它会处理目标长度、最大长度、父 Chunk、前后邻接和稳定 Chunk ID，同时用 Coverage Manifest 检查内容是否在拆分中丢失。
