# 上下文压缩怎样选择保留与丢弃

窗口快满时让模型“概括一下历史”，很容易把计划写成完成、删掉否定词，或把旧回答里的猜测提升成事实。摘要还能失败和超限，它本身也是一次有成本的模型调用。

上下文压缩要设计允许发生的信息损失。原始消息继续作为事实记录，压缩结果只是派生视图；可恢复来源、当前目标和未完成动作不能只存在于自由文本摘要中。

## 裁剪与压缩的损失不同

裁剪直接省略低价值内容，适合寒暄、重复确认和可重新读取的大对象。压缩用较短表示替代一段历史，适合已经闭合的旧阶段。两者都要记录覆盖范围和恢复引用。

旧内容没有独特信息时，裁剪更可靠。压缩适合仍有因果关系需要保留，却没有空间携带原文的情况。不要为了显得“有记忆”给每段历史都生成摘要。
## 在请求超限前触发

压缩通常设三道门：达到软阈值时后台准备，正式请求前同步确认，供应商返回超限时进行有限应急。软阈值要留出摘要输入、输出和当前任务的空间。

```text
soft_limit < hard_input_budget < model_window
```

等到硬上限才启动，摘要器很可能装不下同一份历史。后台摘要完成后还要比较状态版本，若期间会话已经追加消息，旧摘要不能覆盖新范围。
## 先划定可压缩区间

压缩单位应是已闭合的消息组或任务阶段。区间包含起止消息 ID、状态版本和内容哈希。工具调用尚未得到结果、用户正在纠正事实或审批仍在等待时，不应跨越这些边界。

压缩后保留：

- 当前目标、明确约束和用户范围。
- 活动实体、对象 ID 与版本。
- 未完成动作、调用 ID 和副作用状态。
- 最后一次有效纠正。
- 证据与原始消息的稳定引用。

Token 很贵也不能成为删除这些字段的理由。它们应保存在结构化状态中，摘要只负责解释历史进展。
## 摘要合同要可验证

相比一段自由文本，结构化摘要更容易检查：

```json
{
  "goal": "定位远程访问失败",
  "confirmed_facts": [
    {"text": "审批仍在等待", "source_ids": ["tool-8"]}
  ],
  "discarded_hypotheses": ["周一自动生效"],
  "open_actions": [],
  "range": {"from": "msg-1", "to": "msg-20"}
}
```

模型生成后，程序检查非空、覆盖范围、来源 ID 存在、未完成动作没有丢失，以及摘要没有引用范围外材料。程序无法验证的语义继续标记为候选，不能直接写进权威状态。

## 保存摘要时不要覆盖原记录

摘要记录包含 `summary_id`、覆盖消息范围、输入哈希、模型与 Prompt 版本、创建状态版本和来源引用。接纳成功后，装配器可以用摘要替代该区间，原消息仍按会话保留策略存在。

新消息追加后无需重写所有历史。下一次只压缩尚未覆盖的闭合区间，或者在明确版本上合并摘要。摘要的摘要会累积误差，层级过深时应回到原始记录重新生成。
## 摘要失败怎样退化

超时或校验失败时，保留上一版上下文计划，优先裁剪明确低价值项和外溢大对象。仍无法装入硬锚点，就返回 `context_too_large`，请求用户缩小范围。

不要在失败后改用更宽松 Prompt 并接纳未校验摘要，也不要删除原消息“腾空间”。压缩失败是输入准备失败，不是历史记录清理指令。
## 缓存与压缩会相互影响

摘要文本每次变化，位于它后面的 Prompt 前缀也会失效。稳定规则和工具定义放在摘要之前，摘要按固定序列化输出，减少无意义的字节变化。缓存收益和摘要质量要分开测量，不能为了命中率保留过期摘要。
## 哪些场景应避免摘要

精确代码、合同条款、金额、配置、错误堆栈和待执行命令需要原文或结构化表示。短对话直接用窗口选择即可；知识事实走版本化检索；用户偏好进入可撤回记忆。摘要适合保留过程含义，不承担权威数据。
## 验证压缩后的行为

建立成对用例：同一任务分别使用原始历史和压缩视图，比较目标、实体、未完成动作、引用和最终终态。故意加入否定、纠正、同名对象、过期权限和提示注入，检查摘要是否传播错误。

指标可以记录压缩前后 Token、摘要耗时、失败率、再次读取原文次数和回归通过率。只看到 Token 下降还不够，若模型频繁重读或错误率上升，压缩只是把成本挪到了后面。
