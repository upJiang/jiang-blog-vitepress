# 上下文压缩怎样选择保留与丢弃

上下文压缩不是“窗口满了，让模型概括一下”。摘要本身也是一次模型调用，也需要输入空间、时间和可用模型。如果等供应商已经拒绝原请求才开始压缩，摘要器很可能因为同一批超大历史再次超限。即使摘要成功，它也可能删掉否定词、把计划写成完成、把旧 Assistant 的猜测写成事实。

压缩真正要设计的是损失：哪些信息允许用较短表达替代，哪些必须保留原样，丢失后能否回到原始来源。原始会话是记录，压缩结果只是本轮模型输入的派生视图。两者的保留策略不能混为一谈。

本篇使用一段持续排查远程访问失败的对话。旧历史包含目标、错误尝试和一条已经被纠正的生效时间；近期消息包含“不是周一，仍需等待审批”的纠正，以及正在运行的工具调用。压缩既要腾出窗口，也要保证模型不会把旧结论恢复成当前事实。

::: info 压缩成功需要同时满足四件事

- 可压缩范围有明确的起止消息。
- 当前目标、约束、未完成动作和近期观察仍然存在。
- 摘要通过非空、覆盖范围和承重事实检查。
- 原消息保留可回查，摘要失败不会删除或覆盖它们。

:::

## 压缩和裁剪解决的不是同一个问题

裁剪根据预算选择材料，通常完全由程序完成。旧消息未入选，不产生新的内容。压缩则把一段材料转换成更短的派生文本，通常要调用模型，因此可能产生概括错误。两者都减少输入，却有不同的失败模式。

近期滑动窗口适合保留局部连续性，摘要适合承接更早的目标、决定和未完成事项。单个超大 Tool Result 不适合混进会话摘要，它应外溢到对象存储，窗口只留结构化预览与引用。把 100,000 字的 JSON 交给摘要器，既消耗预算，也容易掩盖结果字段。

压缩也不同于长期记忆。摘要描述某段会话发生过什么，记忆是经过写入、范围与遗忘规则管理的跨会话状态。不能把摘要中的每句话自动保存为用户记忆，更不能把旧模型回答变成知识库事实。

压缩对象是模型看到的工作上下文，不是审计记录。用户要求导出的完整转录、原始日志或合规证据必须原样保存。为了让模型继续运行而删掉交付物，等于破坏任务本身。

## 为什么需要主动、发送前和响应式三道闸门

第一道是**主动压缩**。输入估算达到配置阈值后，在正常流程中选择旧前缀、调用摘要器、验证并保存摘要。主动触发要留足当前请求和预期输出空间，阈值从实际余量倒推，而不是照抄一个整数百分比。

第二道是**发送前检查**。最终消息、工具 Schema 和输出预留都确定后，使用目标模型 Tokenizer 重新计数。估算偏小、并行 Tool Result 突然增大或工具目录变化，都可能让主动检查漏掉超限。此时仍未发送请求，可以进一步压缩或确定性裁剪。

第三道是**响应式处理**。只有供应商能最终判断序列是否满足其当前协议。若 API 明确返回上下文长度错误，运行时可以执行一次受限的紧急压缩后重试。标志属于整个 Turn，重试后再次超限就停止，不能进入“压缩、重试、再压缩”的付费循环。

三道闸门的证据要分开。主动触发说明预算逐渐上升；发送前触发通常表示最终序列化成本超过初估；响应式触发说明本地计数与供应商判断仍有差异。把它们都记成 `compression_failed`，排障时无法决定应该调阈值、修 Tokenizer 还是检查工具结果。

阈值应写成配置与推导说明。例如窗口为 16,000，输出与安全共预留 3,000，期望压缩后输入不超过 8,000；主动阈值可以落在仍能容纳摘要请求的位置，发送前阈值更靠近硬限制。这里的数字只是演算，真实值由模型、任务输出、摘要器窗口和峰值材料分布共同决定。

## 摘要前要先划定压缩范围

压缩不是对整段会话反复总结。应用先保留系统规则和当前问题，再把历史划成三个区域：已经存在的旧摘要、这次新增的可压缩前缀、需要原样保留的近期尾部。摘要器只处理旧摘要与新增前缀，近期尾部不进入本次摘要。

压缩范围使用消息 ID 或单调序号记录。例如旧摘要覆盖到 `m-20`，这次可压缩消息是 `m-21` 到 `m-34`，近期窗口从 `m-35` 开始。新摘要保存 `covered_until=m-34`。下一次只处理 `m-35` 之后真正离开近期窗口的消息，不会重复压缩已经覆盖的区域。

近期尾部要有硬下限，但下限按消息组而不是单条消息。Tool Call 与 Tool Result、用户纠正与确认、审批申请与决定不能切成半组。预算压力再大，也不能留下供应商无法接受的孤立 Tool Result。若尾部下限和必保项已经超限，请求停止，不能继续削掉协议边界。

开场是否原样保留取决于状态模型。用户最初目标只存在自然语言时，保留开场有价值；目标已经转成版本化 Task Contract 后，可以渲染短合同而不必永久携带首轮全文。无论选择哪种方式，目标变更要可追踪，不能让旧开场压过用户后来明确修改的需求。

压缩前还要剥离运行时注入的临时消息。例如“检测到重复动作”“即将达到预算”属于控制提示，不是用户与 Agent 的事实对话。把它们交给摘要器，会让未来模型反复读到已经过期的警告，甚至把保护机制当成任务内容。

## 哪些内容不能只交给自由文本摘要

当前目标、硬约束、用户纠正、未完成动作、外部回执和安全状态属于承重信息。它们应该先写入结构化字段，再允许摘要用自然语言解释。验证器可以检查字段仍然存在，却不能可靠证明两段自由文本语义完全等价。

一个未完成动作至少包含 `call_id`、工具、参数指纹、状态和 Deadline。摘要写“系统正在查询”不够，恢复时需要知道查询是否已经发出、是否允许重试。外部副作用未知时，必须保留 `unknown`，不能被摘要改成“查询失败”。

数字、时间、否定与条件容易在压缩中变形。“审批通过后的次日生效”不能概括成“很快生效”，“不是周一”不能变回“周一”，“仅预览环境”不能丢掉“仅”。这些值可以提取成 protected facts，摘要接受前逐项核对。提取本身若由模型完成，仍需要来源与校验，关键业务状态优先来自确定性数据。

用户说法与 Assistant 回答也要分开。旧 Assistant 曾回答“负责人是平台组”，随后用户纠正为安全组。摘要应写“Assistant 曾给出平台组，用户已纠正为安全组”，不能只留下前者，也不能把用户未经证据支持的说法写成企业事实。当前事实最终由 Evidence 核对。

错误尝试不应全部删除。保留失败动作、错误类别和为什么不再尝试，能避免模型重复同一路径；完整栈和冗长输出可以外部化。压缩的目标是去掉重复细节，不是把失败历史洗成一条看似顺畅的成功叙事。

## 摘要合同应该包含哪些字段

只要求摘要器返回一个 `summary` 字符串，很难验证任务状态。更实用的输出会把自然语言概述与结构化字段分开：`goal` 保存当前目标，`constraints` 保存仍然生效的限制，`entities` 记录实体与指代，`decisions` 记录决定及其来源消息，`open_items` 记录未完成动作，`corrections` 记录被替换的旧说法，`source_range` 标明覆盖范围。

结构化不等于事实自动可信。摘要器可以生成形状正确的 `open_items`，却把已取消动作写成进行中。应用先用 Schema 拒绝缺字段和错误类型，再用运行时状态核对 `call_id`、状态和参数指纹。用户纠正与决定通过原消息 ID 回查，Evidence Claim 通过 Source ID 回查。无法验证的内容可以留在自然语言概述中标为“历史说法”，不能进入可信状态锚点。

每个决定需要区分提出者和确认者。Assistant 建议“周一发布”不代表用户已经同意，用户问“能否周一发布”也不是发布指令。`decisions` 可以包含 `status=proposed|accepted|rejected`、`actor` 和 `message_id`。摘要器没有足够证据判断时使用 proposed，而不是选择更顺畅的 accepted。

纠正使用替代关系，不只保存新文本。`corrections` 指向旧 Claim 或消息，说明新值和纠正来源。装配时只把当前值放进状态锚点，摘要概述可以保留“曾经误认为周一，后来更正”。这样模型既不会继续沿用旧值，也知道为什么不应重复旧结论。

未完成事项至少包含所有者、状态、下一检查点和恢复引用。`running` 工具保存 `call_id`，等待审批保存审批记录，等待用户输入保存缺少字段。摘要器若只写“继续处理权限”，恢复后无法判断该调用工具、等待回执还是向用户追问。

摘要还应显式列出省略类别。寒暄、重复确认和已外溢日志可以只记录数量与引用；关键材料因预算无法表示时，摘要状态不是 success，而是 `incomplete`。上下文编译器看到 incomplete 后决定取回原消息或请求澄清，不能把它当成完整历史。

接纳顺序应固定：解析结构，验证覆盖范围，核对 protected facts，校验未完成动作，检查角色归属，最后才保存候选。任一步失败都保留旧 revision 与原消息。自然语言流畅度排在这些不变量之后，因为一份不够漂亮但状态正确的摘要可以继续使用，一份漂亮却改写任务的摘要会让后续每轮都走错。

合同版本随着字段和语义更新。旧摘要缺少 `corrections` 时，读取器不能假设没有纠正；它可以回查原消息或触发重建。新旧版本并存期间，编译清单记录实际读取的合同版本，回归测试分别覆盖升级和回滚，避免一次 Schema 发布让所有长会话失去摘要。

摘要展示也应保留这种区别。面向模型的短文本可以把结构化字段渲染成紧凑段落，面向用户的会话界面仍显示原始消息，运维界面则展示覆盖范围、修订和验证问题。不要让同一段摘要同时承担模型输入、用户转录和审计证据，三个消费者对完整性与权限的要求并不相同。

## 摘要器的输入也需要预算

把待压缩的全部历史直接交给较小摘要模型，会在最需要恢复时再次超限。摘要请求有自己的窗口、输出预留和输入上限。历史超过上限时先按完整消息或 UTF-8 安全边界分批，不能按任意字节切开多字节字符、JSON 或 Tool Call 协议。

分批摘要会增加误差传播。第一批得到 S1，第二批以 S1 加新消息得到 S2；如果 S1 已漏掉约束，后面不会自动恢复。批次之间保留 protected facts，每次生成后重新验证。超过一定批次数时，与其继续递归压缩，不如重新从原消息和结构化状态构建摘要。

摘要器返回必须经过结构校验和空值检查。`{"summary":" "}` 在 JSON 层完全合法，却等于删除中段历史。空结果、超时、内容被安全策略拒绝或超限，都不能更新摘要覆盖位置。上一版摘要与原消息保持不变，当前轮切换到确定性裁剪。

摘要模型与回答模型可以不同，但要记录模型和 Prompt 版本。更小模型降低成本，也可能更容易遗漏细节；更大模型提高摘要质量，却占用更多时间和配额。选择依据是回归集上的承重信息保留与故障表现，不是把“摘要任务简单”当成事实。

摘要调用还受到 Turn 的绝对 Deadline 约束。临近截止时，不应为了保存输入再发一个可能超时的模型请求。保留旧摘要，缩小近期窗口或明确停止，比在 Deadline 后得到一份无法使用的新摘要更清楚。

## 摘要怎样保存而不覆盖原始记录

摘要记录至少包含 Conversation、用户、知识空间、摘要文本、覆盖到的消息 ID、修订号、模型配置、Prompt 版本、输入哈希和创建时间。它是会话派生状态，不和原消息写在同一文本字段里。

保存时做乐观并发检查。两个 Turn 同时基于 revision 4 生成摘要，先提交的得到 revision 5；后提交者发现基线已经变化，不能覆盖。它可以重新读取新增消息并生成 revision 6，或者放弃当前候选。按完成时间最后写入会丢掉另一个分支已覆盖的消息。

摘要提交与 `summarized_message_count` 或 `covered_until` 在同一事务更新。只保存新文本而覆盖位置仍旧，会让下一轮重复总结；只推进位置而文本提交失败，则会永久跳过消息。摘要事件在事务提交后发布，实时通知失败只影响界面，不改变持久状态。

原消息仍按会话保留策略存在。摘要发现问题时，从覆盖范围重新生成；用户删除会话或达到保留期时，再按数据政策清理。审计只读取有权限的原消息，摘要不能成为绕过删除与访问控制的副本。

## 从触发到恢复的一次完整轨迹

Conversation C7 已有摘要 S3，覆盖 `m-1` 到 `m-20`；近期历史为 `m-21` 到 `m-46`。编译器计算原始输入接近主动阈值，计划保留最后八个消息组，因此 `m-21` 到 `m-34` 成为新增摘要范围，`m-35` 到 `m-46` 保持原文。

摘要请求输入 S3、新增原消息、protected facts 与输出 Schema。模型返回 S4 候选，验证器确认目标仍为只读排查、用户已否定周一、审批任务尚未完成。Repository 以 revision 3 为条件保存 S4 和 `covered_until=m-34`，成功后 revision 变为 4。

上下文编译器渲染规则、当前问题、S4、近期原文和当前 Evidence，再使用目标 Tokenizer 复算。输入低于发送前上限，模型调用成功。装配清单记录压缩前后 Token、摘要 revision、覆盖范围和保留消息。

故障轨迹让摘要器返回“远程访问已在周一生效”。它同时丢掉“只读”和未完成审批，验证失败。Repository 不保存候选，覆盖位置仍是 `m-20`。本轮改用旧摘要 S3 加较短的近期窗口，压缩状态标记为 `deterministic_trim`。如果仍无法满足必保预算，请求在调用模型前停止。

另一个故障发生在供应商请求：本地复算通过，Provider 仍返回 Context Length 错误。运行时确认本 Turn 尚未执行 reactive retry，进一步外溢大 Tool Result、保留更短原文尾部后重试一次。第二次仍超限则失败，标志不复位，不继续收费循环。

## 摘要失败时怎样确定性退化

确定性退化不生成新事实。系统保留上一版已验证摘要，从最近消息向前按组选择，在预算不足时省略更旧内容，并记录没有进入摘要也没有进入窗口的消息数量。这会损失连续性，但损失位置可知。

若没有旧摘要，退化结果只有近期原文和结构化锚点。用户追问依赖被省略内容时，模型应请求澄清或通过读取历史工具取回，不能假装拥有摘要。应用可以在界面显示“早期对话未载入”，但不要把内部故障细节塞进模型输入。

摘要服务短暂超时可以在下一轮再试，当前轮不必无限等待。错误计入本 Turn Deadline，重试使用尚未覆盖的同一消息范围。模型返回空摘要属于内容错误，换同一输入立即重试价值有限，应保留样本并检查 Prompt 或模型。

压缩执行到一半收到取消时，不保存候选。原消息和旧摘要仍完整，已支付的摘要调用无法撤销，但不会污染下轮状态。恢复时根据持久 revision 重新计划，不信任进程内临时文本。

## 压缩为什么会破坏 Prompt Cache

Prompt Cache 通常复用相同前缀，压缩却会重写历史中段。摘要从 S3 变成 S4 后，该位置之后的字节都可能变化，缓存命中自然失效。这是压缩换取窗口空间的成本，不能同时假设历史被重写且缓存完全不受影响。

稳定布局可以减少无谓失效。规则、固定工具定义和版本化前缀放在前面，摘要与动态历史放在后面；截断边界从模型窗口和固定策略推导，不根据每一轮当前历史长度来回移动。同一条超大消息若每轮在不同位置被截断，会不断生成新前缀。

压缩触发不应过于频繁。每新增一条消息就重写摘要，会增加模型费用、延迟和缓存失效；等到硬上限才压，又缺少恢复空间。通过真实会话的 Token 分布和压缩回归确定阈值，并分别观察压缩次数、缓存命中、回答质量和 Provider 超限。

缓存收益不能凌驾于事实新鲜度。Policy、权限、工具目录或知识 Release 变化时，即使使整个前缀失效，也必须重编译。为了保留缓存而发送旧规则，比多一次计算更危险。

## 哪些场景不应该使用摘要压缩

短会话不会接近阈值，压缩只增加有损转换。保持原文更便宜，也更准确。是否启用应由预算状态决定，不为架构对称每轮调用摘要器。

单个大 Tool Result 应先外溢。摘要整个对话无法解决一个新结果瞬间越过窗口，而且会把结果里的稳定 ID 与字段关系改成自然语言。保留预览、统计与读取引用更合适。

用户要求编辑或导出完整文本时，目标内容不能被摘要替代。可以压缩围绕它的讨论，交付物本身保存在工作区或对象存储，生成步骤按范围读取。把待编辑文件放进滚动摘要会失去格式和细节。

严格审计任务可以让模型使用压缩视图，但审计证据必须原样保存并可引用。摘要无法证明用户原句、执行时间或工具回执。涉及法律、财务或权限决定时，结构化状态和原证据优先，摘要只做导航。

任务存在大量相互独立的探索分支时，分层压缩或 SubAgent 隔离可能更好。把所有分支揉进一段摘要会混淆哪些结论属于哪条证据。下一篇会讨论怎样按信息年龄与工作层级逐步降级。

## 怎样验证摘要没有把错误滚到下一轮

单元测试覆盖短历史不压缩、压缩范围、近期尾部下限、Tool Call 配对、空摘要、protected facts 缺失和并发 revision 冲突。成功断言摘要与覆盖终点同提交，失败断言旧状态完全不变。

摘要质量回归准备包含目标变更、否定、数字、时间、用户纠正、未完成动作、错误尝试和来源引用的固定会话。每份标注必须保留项与允许丢弃项。检查不能只看摘要长度，要逐项判断承重状态和角色归属。

故障测试分别触发主动、发送前和响应式路径。主动路径验证正常压缩；发送前路径加入突然增大的工具 Schema；响应式路径让 Fake Provider 第一次返回超限、第二次仍返回超限，断言只重试一次。每条路径保存独立错误标签。

恢复测试在摘要生成前、候选生成后、事务提交前和提交后通知前终止进程。前三种都沿用旧 revision，后一种读取新 revision 并只补发事件。不能因重投任务再次覆盖同一批消息。

隐私测试确认摘要不复制凭证、隐藏 Evidence 或其他用户记忆。原消息删除或用户执行遗忘后，对应摘要需要失效或重建，不能继续成为绕过数据生命周期的副本。

共享示例使用以下命令运行：

```bash
PYTHONPATH=examples/ai-agent python3 -m unittest discover \
  -s examples/ai-agent/tests -p 'test_*.py'
```

测试通过只证明示例的范围划分、非空检查和承重事实门禁。真实摘要模型还要在隔离数据上运行质量评测，记录模型与 Prompt 版本。上线时先影子生成摘要，不替换活动结果；差异通过后再切换，旧摘要保留为可回滚版本。

压缩的底线是先保存来源，再接受有损视图。主动、发送前和响应式闸门处理不同故障；开场或任务合同、已验证摘要和近期消息承担不同职责；失败时回到旧摘要与确定性裁剪。只有这些退出路径明确以后，“摘要一下”才是一项可恢复的工程能力。
