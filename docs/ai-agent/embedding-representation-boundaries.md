# Embedding 表示什么，不能证明什么

搜索“远程访问申请需要谁审批”时，关键词检索会寻找“远程访问”“审批”等词。可文档里也许写的是“生产环境的外部连接须由系统负责人确认”，字面不同，意思却很接近。Embedding 的用途就在这里：它把查询与知识片段映射为一组数，让检索器能够寻找语义邻近的候选。

这组数没有保存句子的逐字翻译，也没有把知识压缩成一张可以精确读取的事实表。向量距离只能回答一个受限问题：**在当前模型、当前输入文本和当前距离规则下，这两个对象有多接近**。模型接口的输入和返回约束可以对照 [OpenAI Embeddings 指南](https://developers.openai.com/api/docs/guides/embeddings)，用户是否有权读取文档、文档是不是最新版本、编号是否完全相等、候选里的结论是否真实，都要由向量之外的系统确认。

::: info Embedding 在 RAG 中的位置

文档入库时，Embedding 模型把每个 Chunk 的检索文本转换成固定维度向量。查询到来时，同一个模型把查询也转换成向量。数据库比较查询向量和候选向量的距离，返回邻近 Chunk，后续还要经过范围过滤、融合、重排和证据选择。

:::

本文用两个查询贯穿这条链路。第一个是自然语言问题“外部连接要经过谁批准”，适合语义召回；第二个是“RA-204 的状态是什么”，其中 `RA-204` 是必须精确匹配的业务编号。两者都可以生成向量，但检索策略不能因此相同。

## 文本怎样变成一个向量

Embedding 模型接收文本，输出长度固定的浮点数数组。假设演示模型只有四个维度，“外部连接审批”可能得到 `[0.72, -0.11, 0.33, 0.08]`，“远程访问批准”可能得到 `[0.69, -0.08, 0.36, 0.05]`。两个数组很接近，检索器便把对应 Chunk 视为候选。

真实模型通常有更多维度。单个维度很少能被稳定解释为“权限”或“时间”，各维共同形成一个位置。模型在训练时让相关文本更靠近，让不相关文本分开；使用者得到的是这种表示能力，不是人工定义的字段含义。试图查看第 17 维并断言它代表审批人，通常没有可靠依据。

向量化的输入也会改变位置。只嵌入一句“负责人确认”，信息太少；加入文档标题和章节路径后，模型能看到它属于“远程访问制度 > 生产环境”。相反，把作者、内部备注和不可见权限字段一股脑拼进去，会让向量混入检索时不该使用的信号。下一篇会专门处理 `embedding_text` 的组成，这里先记住：**向量表示的是交给模型的那段文本，不是 Chunk 在系统里的全部事实**。

下面的代码用人为构造的短向量演示余弦相似度。它不调用真实 Embedding 服务，只验证距离计算和排序控制流。

```python
from math import sqrt


def cosine_similarity(left: list[float], right: list[float]) -> float:
    if len(left) != len(right):
        raise ValueError("vector dimensions do not match")
    dot = sum(a * b for a, b in zip(left, right, strict=True))
    left_norm = sqrt(sum(value * value for value in left))
    right_norm = sqrt(sum(value * value for value in right))
    if left_norm == 0 or right_norm == 0:
        raise ValueError("zero vector has no cosine direction")
    return dot / (left_norm * right_norm)


query = [0.70, -0.10, 0.35, 0.06]
candidates = {
    "remote-access": [0.72, -0.11, 0.33, 0.08],
    "meal-reimbursement": [-0.15, 0.60, 0.04, 0.22],
}

ranking = sorted(
    candidates,
    key=lambda item: cosine_similarity(query, candidates[item]),
    reverse=True,
)
assert ranking[0] == "remote-access"
```

输出只证明在这组手工向量和余弦规则下，`remote-access` 排在前面。它没有证明真实模型也会生成这些数，更没有证明这份候选文档能对当前用户开放。测试若把 Fake Vector 的排序结果写成“真实召回已验证”，证据就跨过了它能支持的范围。

## 距离函数决定怎样理解“接近”

常见的比较方式有余弦距离、内积和欧氏距离。余弦关心方向，向量长度对结果影响较小；内积同时受到方向和长度影响；欧氏距离直接测量两点之间的几何距离。三者不是任意替换的排序按钮，模型训练方式、向量是否归一化和数据库操作符必须配套。

如果模型输出已经归一化为单位向量，余弦相似度和内积排序可能呈现稳定关系；没有这一前提，换操作符就可能改变结果。工程配置至少保存模型标识、维度、距离度量和规范化方式。查询向量与文档向量来自不同模型，即使数组长度相同，也位于不同表示空间，彼此距离没有可用含义。

“相似度 0.82 算不算相关”也没有通用答案。不同模型、语言、文本长度和领域会改变分布。一套制度文档的阈值不能直接搬到代码仓库；同一模型升级后，旧阈值也要重测。更可靠的做法是保存带相关性标注的查询集，用 Recall、MRR 和 nDCG 比较排序，再根据错误代价决定候选数量与阈值。

Top K 同样只是候选预算。取前五条并不代表第五条之后都无关，取前五十条也不会自动提高最终答案质量。候选过少会漏掉证据，过多则挤占重排与上下文预算。过滤条件很窄时，近似索引还可能在过滤前没有访问到足够多的合格向量，具体索引行为会在 pgvector 文章展开。

## 一次语义查询的完整状态变化

活动知识版本中有三个 Chunk：A 讲外部连接审批，B 讲办公用品采购，C 讲远程桌面故障。用户 U 提问“外部连接要经过谁批准”。请求进入检索器时，系统先固定租户、用户身份、知识 Release、允许的 Source 范围和绝对截止时间，这些状态不能由模型补写。

查询文本经过与入库一致的 Embedding 模型，得到 1024 维查询向量。向量服务返回后，适配器验证响应数量和维度；少一个结果或出现 768 维数组都立即失败，不能补零后继续。模型标识随 Trace 保存，便于判断查询是否和索引使用同一表示空间。

数据库检索在活动 Release 内比较距离，同时应用可见范围。假设 A 的距离最小，C 次之，B 最远，检索器返回 A 与 C。候选仍保留 Chunk ID、Source Version、Release、标题、距离和访问范围，不能只返回一段脱离来源的文本。

重排器结合查询和候选正文判断 A 与“谁批准”直接相关，C 只是在谈连接故障。证据选择器保留 A，随后答案生成器从 A 中抽取审批角色，引用仍指向 A 的来源位置。最终验证再次确认 Citation 属于固定 Release，当前用户仍可见，然后才交付回答。

这次执行的正常状态可以概括为：

```text
查询 received
  -> 身份与 Release pinned
  -> query embedding ready
  -> filtered candidates [A, C]
  -> reranked evidence [A]
  -> claim linked to source A
  -> answer delivered
```

失败路径要保留发生位置。Embedding 服务超时，状态停在 `query_embedding_failed`，不伪装成“没有相关文档”；维度不匹配，返回配置错误并阻止数据库查询；范围过滤后为空，记录“当前范围无可见证据”；候选存在但无法支持审批角色，答案验证进入证据不足的拒答。四种结果对用户可能都没有正文答案，运维含义却不同。

验证至少包含三层。单元测试用固定向量检查距离和排序；集成测试用隔离数据库确认 Release 与 ACL 过滤没有被向量条件绕开；离线检索评测用真实 Embedding 和标注查询比较召回。只有第三层能说明模型对目标语料的语义表示是否合适，Fake Vector 只证明程序分支。

## 语义邻近不等于事实正确

向量检索找到的是表达相近的文本。候选文档可以过期、写错、互相矛盾，也可能只是提到同一个主题。查询“当前远程访问审批人是谁”，旧制度与新制度语义高度相似，旧版本甚至可能因为措辞更完整而排得更高。向量不知道“当前”对应哪个 Release，版本过滤必须先固定可查询集合。

候选与问题相近，也不代表它支持答案中的每个 Claim。文档写“审批流程由平台组维护”，不能推出“平台组负责人批准每一次申请”。生成模型可能把相邻句子补成听起来合理的结论，Claim 验证必须检查原文是否直接支撑角色、动作和条件。

相似度分数不是置信概率。0.91 不等于结论有 91% 的可能为真，它只是距离经过某种转换后的排序信号。模型、索引与候选集合一变，数值含义也会变。界面若把相似度显示成“可信度 91%”，会误导使用者把检索邻近当成事实判断。

反例很容易构造。把“外部连接无需负责人批准”和“外部连接须负责人批准”放在一起，两句共享大量词，向量往往非常接近，结论却相反。否定、数字和细粒度条件在某些表示中不一定主导距离，后续的精确检索、重排和证据验证不能省略。

## 精确编号不能只靠向量寻找

查询 `RA-204` 时，字符本身就是身份。`RA-204` 与 `RA-240` 可能拥有很接近的上下文，Embedding 也可能把两个编号视为低信息片段。只走向量通道，结果有机会返回同类制度或相邻编号，却漏掉完全匹配项。

入库阶段应从 `embedding_text` 或结构字段提取业务编号，保存为 `exact_terms`；表格行还可以保存列名与字段值。查询理解识别编号后，优先运行精确通道，要求规范化后完全相等。精确结果与语义、全文和结构化结果随后再融合，而不是让向量距离裁定身份。

这并不意味着含编号的查询完全不用向量。用户问“RA-204 为什么被拒绝”，精确通道先锁定对象，语义通道再寻找与拒绝原因、审批条件有关的片段。两条通道各自保留候选来源，融合时对完全匹配给予明确加权，重排器不能把别的编号换上来。

故障推演可以这样设计：活动版本包含 `RA-204` 和 `RA-240` 两行，正文语句高度相似。测试输入 `RA-204 的状态`，断言精确通道命中 `RA-204`，最终 Evidence 不得出现 `RA-240`；关闭精确通道后，记录向量通道是否发生混淆。这个反例验证的是检索职责划分，不需要编造真实模型一定会错。

## 权限不能编码成语义特征

把“仅管理员可见”拼进 Embedding 文本，并不能执行权限控制。查询“管理员制度”可能反而更容易召回它；向量只观察文本相似度，不知道当前身份是否属于管理员，也不会处理撤权和临时授权。

权限应以确定性字段贯穿候选选择。请求固定用户、租户、角色或 Subject，数据库在返回 Chunk 前核对 ACL 和 Release。父 Chunk、邻接补全、缓存读取与重排后取回全文时都要重复保持这个范围，不能只在第一条 SQL 里过滤一次。

缓存尤其容易破坏边界。用户 A 的查询向量和用户 B 相同，不代表候选可以共享。缓存键至少绑定知识范围、Release、检索配置和权限指纹；命中后还要按当前授权重新检查。撤权事件使旧权限版本失效，不能期待向量变化把敏感内容自然排到后面。

权限过滤后的空结果是一个合法终态。系统可以说明当前范围没有可用证据，但不能自动扩大到整个知识库，也不能让模型凭常识补出答案。管理员用同样查询能够命中，只证明两个用户的可见集合不同，不是 Embedding 不稳定。

## 时间与版本不在向量空间里自动更新

文档从 V1 更新到 V2 后，模型参数不会知道哪一版生效。索引需要为 V2 重新生成 Chunk 与向量，构建候选版本，通过质量检查后再切换活动指针。V1 可以留作回滚或历史查询，但普通请求只检索固定的活动 Release。

同一段文字在 V1 和 V2 没有变化时，可以按内容哈希评估是否复用向量；复用仍要生成属于 V2 的来源关系和权限快照。仅凭向量相同就复用整条 Chunk 记录，会把旧 Source Version、邻接或 ACL 带进新版本。

查询开始后也不应中途换版本。一次回答先检索 V1，生成前活动指针切到 V2，如果后续引用验证读取 V2，Claim 与 Citation 就可能对应不上。Turn 在开始时固定知识 Release，整次执行沿用它；新请求再使用 V2。

时效性问题还需要查询理解。用户问“目前的审批人”，系统要选择当前 Release；问“去年三月的规则”，则要有可查询的历史版本与时间范围。Embedding 可以找语义相近片段，版本选择仍由程序根据明确字段执行。

## Embedding 与其他检索方式怎样分工

全文检索擅长保留词项，适合专有名词、错误消息和固定短语；精确检索处理业务编号、ID 和严格字段；结构化查询处理日期、状态、金额和表格列；知识图谱沿已确认关系扩展实体；Embedding 负责词面不同但语义接近的召回。

生产 RAG 通常并行使用多条通道。每条通道返回带身份的候选，融合算法根据排名而不是虚构统一分数进行合并，重排器再比较查询与候选。某条通道超时可以按任务合同降级，权限过滤和版本固定不能跟着降级。

选择是否使用 Embedding，可以看查询是否容许语义近似。查“远程工作需要哪些审批”适合；查订单号、版本号或一条精确错误码，先走确定性通道；数据规模很小、词汇稳定时，全文检索也可能已经足够。Embedding 增加了模型调用、向量存储、索引维护和评测成本，不是所有搜索框的默认答案。

## Embedding 不是分类器、生成器或长期记忆

Embedding、分类和生成都可能使用神经网络，输出契约却不同。Embedding 返回连续向量，应用再用距离做检索或聚类；分类器返回预先定义标签的分数；生成模型按上下文产生 Token。把三者混在一起，最常见的后果是对向量提出它无法回答的问题。

要判断文档属于“制度”“故障记录”还是“操作手册”，类别稳定且需要可解释错误时，可以训练或配置分类器。Embedding 也能通过近邻样本辅助分类，但标签规则、阈值和拒绝区间仍由分类任务维护。最近的制度样本不等于待分类文本一定是制度，近邻距离不是类别证明。

Embedding 也不会生成摘要。应用可以检索相近片段，再让生成模型写摘要；摘要里的每条事实仍要回到原文。把向量反向解码为原句通常不是常规检索链路提供的能力，向量数据库保存向量时仍要保存 Chunk 身份和可显示正文，否则命中后没有证据可以交付。

“把文档做成向量，模型就记住了”也是职责混淆。向量存储是应用管理的外部索引。模型调用结束后不会自动保留这次检索结果，新文档也不会自行进入索引。上传、解析、切块、向量化、激活和撤回都要有明确任务；查询时再按身份和版本取回内容，组装进本次上下文。

长期记忆使用 Embedding 时，向量只是查找入口。记忆内容由谁写入、何时过期、能否被用户修改、是否允许跨会话使用，需要独立的数据模型与治理规则。相似的旧对话被召回，不代表它仍然正确，也不代表它属于当前用户。记忆文章会继续处理生命周期，这里只划清一点：Embedding 没有替应用保存授权和时间语义。

知识图谱和向量也不是替代关系。向量适合发现可能相关的文本，图谱适合沿已经确认的节点与边扩展关系。查询“系统 A 依赖哪些服务”时，图谱可以返回有来源的依赖边；查询“哪些文档可能在描述类似的接入风险”时，向量更自然。语义抽取得到的候选边仍需证据和版本，不能因为节点名称向量相近就直接建立关系。

## 模型选择要围绕目标语料评测

模型名称、排行榜分数和最大输入长度只能缩小候选范围，不能替代本地评测。中文制度、代码与中英混合接口文档对分词和语义表示的要求不同；短问题与长 Chunk 的长度分布也会影响结果。真正需要回答的是：在目标语料与查询分布上，相关 Chunk 能否进入后续预算。

建立评测集时，问题不能都照抄文档标题。需要包含同义改写、缩写、中文与英文术语混用、否定条件、多个相近对象、短查询和带上下文的长查询。编号题与权限题保留在集合中，但评估的是混合检索有没有正确分工，不强迫 Embedding 单独完成它不擅长的任务。

候选模型必须和索引配置一起测试。文档向量使用模型 M1，查询向量换成 M2，即使二者都输出 1024 维，也不能视为兼容；维度只是数组形状，不是空间版本。模型、供应方、维度、输入模板和规范化方式共同组成 Embedding 版本，其中任一项变化都要评估重建。

长文本支持也不表示应该把整份文档嵌入成一个向量。一个向量混合多个章节后，查询可能只能捕捉文档的大主题，具体审批条件被稀释。切块长度要与问题粒度、证据引用和上下文预算一起评测。把 Chunk 切得极短又会失去条件与结论的联系，出现大量语义相似但无法独立回答的碎片。

多语言模型需要看跨语言查询。中文问题检索英文接口说明时，测试集应明确哪些英文 Source 相关；若召回不稳定，可以增加翻译查询通道或选择跨语言表示更合适的模型，但翻译内容仍是派生查询，原始问题、译文和来源要分别保留。不能把一次翻译成功写成模型对所有语言都等价。

模型迁移采用影子索引更容易比较。活动索引继续用 M1，候选索引用 M2 对同一语料向量化，离线查询同时跑两套结果。差异记录到具体问题与 Source，确认权限、版本和结构化通道一致后再讨论语义召回。直接覆盖原向量会失去基线，迁移失败时也没有可切回的空间。

成本评估至少包括入库调用量、查询调用量、向量存储、索引构建时间和重新索引窗口。缓存可以减少相同文本的重复计算，但缓存键必须包含模型与输入哈希。为了省一次调用复用不同模型的旧向量，得到的是无法解释的混合空间。

## 召回异常怎样定位到具体环节

用户输入“外部连接谁批准”，结果只出现办公网络故障。排查先保存查询文本、查询向量版本、固定 Release、权限范围、各通道候选和最终排序。直接调高 Top K 只能改变症状，不能说明问题出在表示、索引、过滤还是重排。

第一步核对目标文档是否进入活动版本。若 Source 没有入库、候选版本尚未激活或权限范围排除了它，Embedding 模型没有机会召回。这个阶段查看 Release、Chunk 状态和 ACL，不需要重新计算查询向量。

目标 Chunk 存在后，比较它的 `embedding_text` 与可显示正文。章节标题是否缺失，审批条件是否被切到另一个 Chunk，表格行是否退化成无表头文本，这些输入问题会直接改变向量。Embedding 服务成功返回数组，只能证明调用完成，不能证明输入代表了想检索的知识。

再用精确距离查询建立基线。目标在精确 KNN 中排名靠前、近似索引却找不到，问题更可能在索引参数、过滤顺序或探测预算；精确查询也排得很后，才重点检查模型、输入模板和切块。没有精确基线时，模型与索引问题会混成同一个“向量召回差”。

候选阶段已经命中目标，最终 Evidence 却没有它，需要查看融合去重和重排。多个 Chunk 共用错误身份可能被误合并，RRF 权重可能让通用全文结果占前，Rerank 超时也可能触发保守降级。每一步保留候选 ID 与分数来源，才能知道目标在哪一层消失。

空结果还要区分合法和异常。固定范围确实没有相关资料，返回证据不足；向量服务超时，记录依赖失败；过滤配置错误把全部候选排除，属于检索故障；目标只存在于未发布候选，普通请求继续使用旧版本。四种状态都不应该由生成模型补一句相同的“未找到相关内容”后结束。

修复后用原问题、同义改写、相近编号和无权限用户做回归。原问题进入期望 Source，同义问题保持召回，精确编号不被相邻编号替换，无权限用户仍为空。只验证最初那句话，容易把针对字符串的修补当成通用改进。

::: warning 四条不能跨越的边界

1. 相似不能证明事实为真，答案仍需可见证据支持。
2. 距离不能执行权限，ACL 必须在应用和数据层过滤。
3. 语义不能替代精确身份，编号与结构字段要走确定性检索。
4. 向量不会自动感知新版本，索引和查询必须绑定 Release。

:::

## 怎样验证一套 Embedding 检索

验证从一份带标注的查询集开始。每条问题记录允许的知识范围、期望 Source、相关性等级、禁止出现的来源和问题类型。语义改写题检查模型能否跨越词面差异，精确编号题检查向量通道不会覆盖确定性结果，权限题确认不可见 Chunk 从候选阶段就被排除，版本题确认结果来自固定 Release。

离线评测先建立精确距离基线，再比较近似索引。记录 Recall@K、首个相关结果位置、排序质量和过滤后候选数，同时保存模型、维度、距离函数、索引参数与语料版本。只报平均分会掩盖编号、否定句和少数租户的严重失败，因此还要按查询类型查看失败样本。

在线 Trace 不保存敏感原文时，也应包含查询身份、Embedding 模型、向量维度、Release、通道耗时、候选 ID、过滤数量、最终 Evidence 和终止原因。出现空答案时，可以判断是向量服务失败、近似召回不足、权限过滤为空，还是重排后没有证据。

回归过程使用同一输入比较旧模型和候选模型。若总体 Recall 上升，但否定句与精确编号明显退化，不能只看总分发布。候选模型先构建独立索引，通过检索、权限与答案回归后再激活；失败时继续使用旧索引，保留差异记录。

一次可复现的失败样本应写清：输入“RA-204 的状态”，固定 Release 为 R7，当前用户只允许 Source S1；精确通道命中 S1 的表格行，向量通道同时返回 S2 的相邻编号，但 S2 因 ACL 被过滤；融合后 Evidence 只含 S1。删除精确通道时测试失败，放开 ACL 时安全测试失败，更换模型导致维度不匹配时入库或查询立即终止。

Embedding 的价值是把语义邻近变成可计算的候选关系。守住它的职责边界，系统才会把相似结果当作检索起点，而不是未经核验的答案。

## 向量距离只是候选排序信号
Embedding 把文本映射到向量空间，距离近表示模型认为语义相近。它不能确认编号精确、权限可见、版本最新或结论真实。检索必须先应用 Scope 与 Release，再用距离生成候选。

评测同时放入同义问、近义误导、同号不同对象和权限外同文档。只有距离变化而事实和边界不变，才说明表示改进值得发布。
