# 哪些任务不该使用 Agent

Agent 能根据观察调整下一步，代价是路径不再完全确定。系统要多管理模型调用、工具候选、状态、预算、无进展、取消和恢复。任务本来只有固定规则时，这些成本不会带来新的业务能力。

选型可以从一个问题开始：程序是否已经知道每一步该做什么？答案是肯定的，就先写函数或工作流。只有任务路径需要根据开放式语义和新观察变化，而且每个动作都能验证、限制和停止时，Agent 才可能合适。

::: info 四种常见方案

- **确定性函数**，输入、规则和输出都能在代码中表达。
- **固定工作流**，步骤较多，分支与依赖仍能提前枚举。
- **模型辅助工作流**，模型负责抽取、分类或写作，程序控制路径。
- **Agent**，模型根据当前状态提出下一动作，运行时受限执行。

:::

这四种方案可以组合，不存在“Agent 比工作流高级”这种排序。身份认证应该是确定性函数，审批流程适合工作流，非结构化文本分类可以由模型辅助，开放式研究才可能需要 Agent。

## 先画出任务的控制图

不要从框架和模型开始选。先把输入、步骤、分支、外部依赖、输出和失败终态画出来。若每个箭头都能由字段和规则决定，控制图已经足够，模型没有必要接管路由。

比如“用户提交远程访问申请”：校验字段、检查设备合规、读取审批状态、写入申请、发送通知。这些步骤有明确顺序，失败也能枚举。即使通知文案由模型生成，整个任务仍是固定工作流。

换成“分析远程访问失败的可能原因，并根据已有资料决定还要查什么”，路径才有开放性。系统可能先查制度，也可能根据错误码直接查设备状态；第一份观察会改变下一步。只读 Agent 可以在这里减少预写分支，但最终权限和事实仍由程序确认。

### 输入是否能够结构化

输入是订单金额、用户角色、审批状态或配置字段时，规则通常可以直接编码。让模型判断“金额是否超过上限”会把精确比较变成概率输出。即使模型几乎总答对，也没有理由接受剩余错误。

输入是长文本、模糊问题或多来源资料时，模型在理解语义上有价值。价值不等于需要 Agent。若只做一次分类或抽取，模型辅助工作流已经够用；只有分类结果会触发不同工具，并且后续观察继续改变路径，才考虑循环。

### 分支是否真的无法提前枚举

分支数量多，不代表分支未知。几十种审批状态可以用表驱动规则，复杂税率可以用规则引擎，长 DAG 可以用工作流编排。它们难写，却仍然确定。

Agent 适合分支由自然语言证据决定、候选路径数量无法在开发时穷举的任务。即便如此，动作集合仍要有限。模型可以从已注册工具中选下一步，不能动态创造新的执行能力。

### 完成条件能否由程序判断

有明确完成字段的任务应让程序判定。文件是否存在、测试是否通过、审批是否生效、余额是否扣减，都能读取领域状态。模型输出“任务已完成”不能替代这些检查。

研究、写作和综合分析的完成标准更难，但仍需可检查条件，比如覆盖指定问题、每个 Claim 有 Evidence、冲突已列出、预算尚未超限。完全依赖模型自评，会出现过早结束和循环不收敛。

## 确定性函数适合什么任务

函数适合规则清楚、输入可验证、执行时间短的任务。它不一定只有几行，也可以封装复杂算法和数据库事务。判断标准是相同输入和版本应得到可预测结果。

### 计算与校验

金额、配额、日期、哈希、权限集合和状态转换由代码计算。模型可以解释结果，不参与最终数值。边界条件、精度与舍入都写进测试，错误会在固定输入下复现。

Schema 校验也属于确定性函数。模型生成搜索参数后，程序检查允许字段、类型和范围；身份、Scope 与 Release 从认证和配置读取。把这些步骤交给另一次模型调用，只会让错误更难定位。

### 权限与策略

用户能否读取对象、工具能否执行写操作、证据是否可见，都必须由策略和数据决定。Prompt 中的“只访问自己的数据”是对模型的行为提示，不是授权系统。

策略可能很复杂，可以使用策略引擎或领域服务。只要它需要可审计、可复现和默认拒绝，就不该让模型做最终裁决。模型可以从自然语言请求中提取候选动作，授权函数决定是否允许。

### 状态迁移与事务

pending 能否变成 approved、cancelled 是否允许回到 running、重复请求是否复用原结果，这些属于领域状态机。数据库约束、乐观锁和事务保证并发一致性，模型不拥有状态写入权。

涉及多个表或外部副作用时，确定性代码还要处理幂等和补偿。Agent 可以提出动作，不能替代事务语义。未知执行结果需要查询回执，不允许模型猜“应该失败了”后重试。

### 稳定转换

固定模板渲染、格式转换、协议适配和字段映射通常用函数完成。模型适合语义转换，不适合把已知字段映射成另一个已知结构。确定性转换更快、便宜，也容易做完整测试。

如果函数已经解决任务，给它包一层聊天界面不会把它变成 Agent。界面形式不参与架构选型。

## 固定工作流适合什么任务

工作流处理多个确定步骤、等待、重试和条件分支。步骤可以调用模型，但控制图仍由程序定义。模型是节点，不是编排器。

### 业务流程与审批

文档上传后执行准入、对象存储、解析、切块、向量化、候选索引和原子激活，这条链路有明确依赖。文件类型不同会选择不同解析器，失败会进入清理或重试，分支仍能预先设计。固定工作流比 Agent 更适合保证每个阶段只执行一次。

审批流程还包含长时间等待。持久化工作流能够保存计时器和事件，进程重启后继续。模型可以生成审批摘要，不能决定跳过审批或把超时改成批准。

### 数据管道

定时同步、ETL、索引构建、报表生成和备份都有明确输入输出。数据异常进入隔离队列，重试遵循幂等规则。让 Agent 自由选择是否执行某个清理步骤，会破坏可追踪性。

模型可以作为数据管道中的一个处理器，比如从文档抽取实体。它的输出进入 Schema 与质量门禁，失败记录保存原文引用。整个管道仍由 DAG 或工作流调度。

### 可以枚举的故障恢复

网络超时重试、业务拒绝不重试、未知副作用查回执、永久错误进入人工队列，这些恢复规则适合程序。Agent 可以阅读错误并生成诊断建议，不能覆盖幂等与重试策略。

工作流的优势在于路径可回放。给定事件历史，可以解释为何走到当前节点。对于审计要求高的任务，这比模型每轮重新选择更重要。

## 模型辅助工作流常常已经够用

很多团队需要的是模型能力，不是 Agent。把模型放进一个窄节点，可以获得文本理解和生成能力，同时保留确定性控制。

### 一次抽取后进入规则

用户用自然语言描述问题，模型抽取 `intent`、`entity` 和候选参数。程序验证结构，再根据 intent 进入固定处理器。若类别有限且后续路径清楚，这就是 Router 节点，不需要循环。

抽取失败可以要求用户补充，或做一次有限修复。模型不会因为不确定就自行调用更多工具。成本、延迟和失败分支都更容易估算。

### 先检索再生成

标准 2-Step RAG 先按固定策略检索，再把证据交给模型回答。查询改写、混合检索、重排和 Evidence 预算都可以由固定管道完成。若大多数问题一次检索就足够，Agentic RAG 只会增加模型调用。

只有查询需要根据首轮证据动态分解、追加来源或改变工具时，Agent 循环才可能带来收益。升级前用评测集确认哪些失败来自固定检索路径，而不是切块、权限或索引质量。

### 生成草稿后确定性验证

模型写 SQL、配置或操作建议，程序只做静态检查和展示，不自动执行。用户确认后，由普通命令处理器执行。这种设计把高风险动作留在人和程序边界，仍能利用模型生成能力。

无需为了“自动闭环”马上加入自我修复循环。验证问题可读时，先让用户看到具体错误；只有错误类型稳定、修复可限制、收益可测量时，再允许一次自动修复。

## 哪些信号说明 Agent 可能合适

Agent 的核心收益是根据观察改变路径。以下条件需要同时满足大部分，才值得承担新增复杂度。

任务含有开放式信息缺口，下一步不能只由固定字段决定；系统有一组边界清晰的工具；每个动作都有可观察结果；动作可以授权、限额和停止；完成条件能够由证据或领域状态验证；失败代价在可接受范围内。

### 研究与排障

研究问题可能需要拆分主题、搜索不同来源、发现冲突后追加查询。排障会根据日志和探针结果改变下一步。它们的路径难以完全预写，观察又能缩小问题空间。

这类任务仍要限制工具和范围。研究 Agent 不能把“搜索更多”作为无限默认，排障 Agent 不能在没有审批时重启生产服务。停止条件包括覆盖、证据质量、预算与 Deadline。

### 跨工具的开放任务

用户目标需要在文档、代码、工单和测试之间切换，具体顺序依赖现场状态。Agent 可以先读仓库，再根据错误决定查文档或运行测试。Harness 提供文件和命令边界，运行时保存差异与验证结果。

若每次都按同一顺序读三个文件、改一个字段、跑一个命令，固定脚本更合适。工具多不代表路径开放。

### 用户愿意接受受限探索

部分任务允许 Agent 返回“尚未确认”或请求人工选择，错误不会立即造成不可逆损失。这样的场景适合从只读 Agent 开始。用户必须知道系统可能暂停、拒答或需要审批，产品不能把所有终态包装成成功回答。

## 明确不该交给 Agent 的任务

高频、低延迟、规则稳定的请求不适合多轮模型循环。一个权限检查需要毫秒级返回，Agent 增加网络调用和不可预测延迟，没有收益。

精确计算、法定公式和资金结算不交给模型。模型可以解释账单，结果由经过测试的代码计算。任何“模型判断通过后直接扣款”的设计都缺少确定性边界。

不可逆或高风险动作不能由模型单独决定。删除数据、发布生产、授予权限和签署审批需要策略与人工确认。Agent 可以准备候选命令和影响摘要，执行器只接受已批准快照。

缺少可验证结果的任务也不适合全自动 Agent。目标写成“让用户更满意”，系统既不知道何时停止，也无法区分真实改善和模型自评。先建立验收和反馈，再谈自治。

数据权限尚未建立的系统不能先接 Agent。检索器如果无法保证当前用户只看到允许资料，模型再多安全提示也会泄露内容。先修数据边界。

依赖没有幂等或回执时，不要让 Agent 自动重试写动作。网络断开后不知道命令是否执行，循环再次调用可能造成重复。先补幂等键和状态查询。

任务样本太少、没有基线时，不应直接用复杂模式。无法测量固定方案的失败，就无法证明 Agent 带来改善。先记录真实任务并建立最小评测集。

## 用远程访问任务比较四种方案

用户问“远程访问需要什么条件”。确定性函数可以直接读取配置字段并返回模板；若制度保存在文档中，固定 RAG 检索一次后生成回答。Agent 没有必要。

用户问“我的申请为什么失败”。固定工作流依次查询设备合规与审批状态，只要接口明确，就能给出可验证原因。模型负责解释字段，程序固定查询与权限。

用户问“最近多次失败，帮我找共同原因，并说明还缺什么信息”。路径可能随时间、设备和审批记录变化。只读 Agent 可以先查失败记录，再根据观察选择制度、设备或审批工具。最大步骤与证据要求限制探索。

用户接着说“直接帮我恢复访问”。写操作不应自动继承只读 Agent 的权限。系统生成候选修复动作，策略检查对象与风险，需要时等待审批，再由幂等执行器调用。也可以保持 Agent 只读，在界面提供确定性按钮完成操作。

四种请求共享同一领域，却适合不同控制方式。按“这是 AI 功能”统一使用 Agent，会让简单问题变慢，也让高风险动作失去边界。

## 选型时怎样比较成本与失败代价

不要只比较模型 Token。Agent 增加多轮延迟、工具连接、状态存储、Trace、恢复扫描、评测和人工审批。固定工作流开发分支较多，却能用普通测试覆盖；Agent 少写部分路由代码，后续需要更多行为评测。

### 一次选型评审的具体顺序

先把一个真实请求写成事件表，不要写“用户想要智能处理”。事件表列出输入字段、当前状态、外部依赖、可逆动作、完成证据和所有失败终态。然后逐个问：这一步能否用函数表达，是否需要等待或重试，分支条件是否能从字段确定，模型的判断会不会改变外部动作。

若所有步骤都有确定条件，组合成工作流；若只有一两个文本节点需要语义理解，把模型限制在这些节点；若某一步需要从开放观察中选择工具，再检查工具是否只读、是否有回执和是否能停止。最后才估算 Agent 的收益。先画流程再谈模型，能把“需要 AI”与“需要自治”分开。

把每一个模型候选都标在控制图上。若候选只影响展示文案，它属于低风险输出；若候选决定检索通道，运行时仍可限制到白名单；若候选决定写操作，必须增加授权和审批节点。候选越靠近外部副作用，确定性校验越要前置，不能让模型先执行再验证。

评审还要记录不确定性的来源。输入歧义、知识缺口、工具结果冲突和业务规则变化是不同问题。输入歧义可用澄清问题解决，知识缺口可用 RAG，规则变化需要版本化策略，工具冲突需要确定性裁决。用 Agent 循环覆盖所有不确定性，通常会让真正的缺口变得更难定位。

### 看到失败时先找责任层

固定工作流回答错误，先查数据、版本、查询条件和模板，不要马上改成 Agent。模型辅助节点输出格式错误，先修 Schema、解析和重试上限，不要增加更多模型轮次。Agent 重复调用，先查动作签名、观察是否变化和预算，不要只调大最大步骤。

如果证据已经正确但回答遗漏，问题在 Claim 提取或答案验证；如果工具结果为空，问题在范围、索引或数据准入；如果权限越界，问题在授权边界。只有确认路径需要根据新观察变化，才把路由交给 Agent。否则换模式不能修复根因。

失败分类也帮助判断是否降级。模型暂时不可用时，固定工作流可能仍能返回结构化状态；检索超时时，界面可以展示已确认的部分并标出缺口；授权服务不可用时，应安全拒绝所有需要权限的动作。降级路径在设计时写清，不能等 Agent 自己决定“先继续”。

评审输出保留这张事件表、选择理由和回退方案，后续改动才能知道哪些边界是刻意保留的，哪些只是当时尚未实现。上线后按同一表格记录新失败，避免每次事故都重新发明一套判断。

选型不是一次性的架构标签，数据、规则、工具目录或失败代价变化后要重新评审，并保留上一版的回归结果。评审还要记录参与者、证据版本、未解决假设和回退负责人。

当真实流量出现新问题时，先把样本加入同一评测集，再判断是补规则、修数据还是扩大路径选择，不要直接增加模型轮次。

这一步保留质量、延迟和安全基线，才能知道改变真正带来了什么。

基线还要包含拒答和人工接管等比例。

### 延迟与吞吐

一次分类模型调用可能满足实时界面，多轮 Agent 会把模型与工具耗时累加。并行工具可以缩短墙钟时间，也会占用更多连接和配额。用户请求有严格 SLO 时，先评估最坏路径，不看平均两轮就结束的演示。

后台任务可以接受更长时间，仍要有 Deadline 和进度。延迟不敏感不等于可以无限运行。

### 失败代价

只读搜索选错路径，代价可能是多一次调用；发送错误邮件会影响他人；错误付款或删除数据难以恢复。失败代价越高，模型能直接执行的权限越小，确定性策略与审批越重要。

把失败按可逆、可补偿、不可逆分类。可逆不代表可以随意尝试，恢复本身也有成本；补偿通常无法完全抹掉外部影响。

### 审计与解释

监管或内部审计要求复现每一步时，固定工作流更容易。Agent 也可以记录候选、审批、工具回执和状态版本，但建设成本更高。若团队没有能力维护这套 Trace，就不要让 Agent 接管关键流程。

解释模型为何产生某个 Token 很难，解释运行时为何允许某个动作必须做到。审计重点放在输入范围、动作候选、授权决定、外部结果和终止条件。

### 测试与评测

函数用单元测试覆盖边界，工作流用状态与故障注入测试，模型节点需要固定样本评测，Agent 还要覆盖动作选择、循环停止和跨轮状态。每提升一层，验证面都会扩大。

团队能维护的最高验证能力，决定系统可接受的自主范围。只有演示 Prompt、没有回归集时，先停在模型辅助工作流。

## 从固定方案渐进升级

先实现最小确定性基线。它可能回答不了所有问题，但能提供延迟、正确率、空结果和人工处理率。没有基线，Agent 的“看起来更聪明”无法量化。

第二步把模型放进窄节点，处理分类、改写或生成。保持输入输出 Schema 和固定控制图，记录模型失败。若主要问题来自语义理解，这一步可能已经解决。

第三步只开放只读 Agent 路径，动作数量少、范围固定、每次调用有证据。用同一评测集比较任务完成、工具次数、拒答、延迟和费用，安全红线单独统计。

第四步才考虑可逆写操作与审批。每个动作有幂等键、回执、补偿和人工确认。不可逆能力单独上线，不能随工具目录自动暴露。

升级必须保留回退路径。Agent 超时或模型服务不可用时，可以回到固定检索、展示部分结果或转人工；不能让失败直接进入无限重试。回退结果明确标记能力降低，不伪装成完整调查。

## 用测试证明选型没有越界

为四种方案使用同一组业务样本。确定性基线记录能覆盖哪些任务；模型辅助方案检查结构与内容；Agent 方案额外检查动作、观察和终止。只有业务质量确实改善，新增复杂度才有依据。

故障注入至少覆盖模型超时、工具空结果、工具拒绝、未知执行状态、相同动作重复、Deadline、取消和状态写入失败。固定工作流和 Agent 应按各自语义留下不同证据，不能统一返回“系统繁忙”。

安全回归让模型提出越权 Scope、跳过审批和调用未注册工具。运行时必须在外部执行前拒绝，工具调用次数为零。模型是否服从 Prompt 不是通过条件。

反例同样重要。准备几个明显适合函数的任务，如果 Agent 版本更慢、更贵或出现不稳定结果，选型门禁应阻止发布。评测不能只挑开放式任务证明 Agent 有用。

版本升级时固定模型、Prompt、工具目录、策略和数据 Release。任一项变化后重放样本，比较的不只是最终回答，还包括动作数量、错误分类和拒答边界。平均质量上升不能抵消权限或不可逆动作回归。

最终的选型记录应该很具体：哪些步骤固定，哪一处路径交给模型，允许哪些工具，谁确认完成，失败怎样停止，怎样回到较简单方案。写不清这些内容时，任务还没有准备好使用 Agent。
