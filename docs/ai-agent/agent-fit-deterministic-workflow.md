# 哪些任务不该使用 Agent

[上一篇](/docs/ai-agent/python-agent-loop-from-scratch)已经把 Agent Loop 写成一个可验证的运行时合同：模型提出候选，运行时校验并执行，工具返回观察，完成验证器决定是否结束。合同成立后还剩一个更现实的问题：这段循环是否真的应该存在？

继续沿用远程访问故障这个材料。用户只想知道连接为什么失败，并在条件满足时重新提交。若客户端已经返回稳定错误码，增加模型循环不会带来新的事实；若固定检查无法解释原因，动态调查才可能有价值。

本文不把 Agent 当成“更高级的工作流”。我们先看控制拓扑，再看证据如何变化，最后用风险和评测决定是否升级。案例中的写操作会停在确定性策略和人工审批之后，这是一条教学边界，不是所有生产系统的唯一实现。

## 先区分任务复杂和路径开放

“任务很复杂”只能说明需要更多代码或更多步骤，不能说明下一步无法预先表达。真正需要回答的是三个问题：外层节点和合法边是谁定义的，运行时动作是否会依据新观察改变，以及终止和副作用由谁把关。

### 三条控制轴

**外层拓扑** 描述阶段、节点、合法转移、循环上限和执行器。订单审批即使有并行检查、等待和补偿，只要这些关系由代码或策略定义，就仍然是固定拓扑。

**运行时动作空间** 描述模型是在阶段内填充内容，还是可以看到新证据后选择尚未逐一写入业务转移表的工具和顺序。模型输出一个分类标签，和模型根据日志决定下一项调查，属于不同的控制范围。

**终止与副作用权** 描述谁能宣布完成、谁能停止循环、谁能执行写操作。应用代码、策略引擎、人工检查点和外部系统都可能参与。模型通常只能提出候选，不能凭一段文本取得终态。

下面的关系可以帮助我们避免二分法：

```text
局部规则直接计算输出        -> 固定程序
外层阶段和合法边预先定义    -> 固定路径工作流
模型只在封闭阶段生成候选    -> 模型辅助工作流
模型依据新观察持续选动作    -> 受限 Agent Loop
```

这条分层不是能力等级，而是控制责任的分配。确定了观察轴，才有可能解释为什么同一个系统可以同时包含四种方式。

## 固定程序先处理能直接计算的部分

**固定程序（Function）** 是一次调用内由代码按照明确输入和局部规则计算输出的变换。它可以查表、校验、计算或调用一个固定接口，但不负责跨节点等待、重试、补偿和恢复。

远程访问接口返回 `DEVICE_NON_COMPLIANT` 时，程序只需把错误码映射为“设备条件未满足”，再返回处理入口。输入是可信错误码，输出是固定说明，下一步不依赖新的语义探索。模型即使能把说明写得更自然，也没有增加诊断事实。

固定程序的边界可以这样验证：给定同一组可信输入，单元测试和边界样本能否复算合法输出；错误码未知时，程序是否明确返回未知或升级，而不是静默猜测。规则遗漏、映射过期和输入契约错误，都应由程序及其调用方负责。

函数能解决的问题，放进 Agent 只会增加模型调用和新的失败面。真正的缺口不是输出格式，而是一次调用结束后还要不要沿着多个节点继续走。这个缺口属于工作流层。

## 固定路径工作流覆盖可枚举分支

**固定路径工作流（Workflow）** 预先定义外层阶段、合法边、等待、重试和终态，运行时只在这套控制骨架内推进。它可以包含数据库查询、人工审批、外部工具和模型节点，但节点之间的关系仍由代码或策略拥有。

### 步骤多，不等于路径开放

文件入库可能经过上传校验、病毒扫描、解析、切块、向量化、质量检查和版本激活。文件类型会带来分支，服务故障会带来重试，发布前还可能等待人工确认。只要每个结果都有合法去向，工作流就能表达这条链路。

同样，远程访问检查可以先读设备状态，再读账号状态，最后读审批状态。设备不合规进入修复指导，账号锁定进入解锁流程，审批未完成进入等待。未知值必须进入明确的失败或升级分支，不能让流程误以为任务已完成。

### 工作流的验证对象

工作流的核心不是“有多少步骤”，而是状态转移是否可回放。对每个节点结果运行转移表测试，应该能够回答：这个状态允许去哪一个节点，重试是否有上限，等待如何恢复，最终失败由谁负责。

工作流能承载很长的业务周期，也能把模型放进某个节点。只要外层拓扑和终态仍然固定，使用 LLM 并不会改变它的类别。接下来要把这类中间情况单独说清楚，否则读者会把“模型提出候选”误当成 Agent。

## 模型辅助工作流仍然是工作流

**模型辅助工作流（Model-assisted Workflow）** 让 LLM 在预定义阶段中完成分类、抽取、查询、评估或候选子任务生成。模型输出受节点合同或 Schema 约束，代码仍拥有阶段、允许边、执行器、终止和副作用策略。

例如，工单模型把用户描述分成 `device`、`account` 或 `approval`。代码只接受这三个标签，并把它们映射到固定节点。模型处理了非结构化语言，控制拓扑没有交给模型。

模型甚至可以动态拆分子任务。中央模型将资料整理目标分成多个检索任务，工作流按既定的 worker 创建、执行、汇总和结束规则运行。模型改变的是子任务内容，代码仍限制执行器、阶段依赖和停止条件。这类 orchestrator-workers 结构不能仅因“模型生成了任务”就被称为 Agent。

验证模型辅助工作流时，要检查候选是否只能在封闭图内被消费，非法标签是否被拒绝，模型是否能绕过阶段顺序或写操作门禁。候选内容越开放，越需要把执行合同写得越窄。若下一动作开始依赖每轮新观察，而不是固定阶段的合同，才进入下一层判断。

## 受限 Agent 只处理固定图留下的未知

**受限 Agent Loop（受限 Agent 循环）** 在每轮把目标、已确认观察和约束交给模型，由模型提出当前动作，运行时负责校验、执行、记录和停止。它不是取消确定性控制，而是在固定拓扑无法覆盖的分支上增加运行时动作选择。

它至少需要五项输入：目标、已经确认的事实、允许工具、剩余预算和审批边界。输出可以是工具候选、暂停候选、完成候选或失败候选。模型提出“查认证日志”之后，运行时仍要检查工具权限、数据范围和调用预算；工具返回的观察进入下一轮，完成验证器确认是否真的找到原因。

受限 Agent 和模型辅助工作流的边界，不在工具名称是否预先登记，也不在模型是否输出 JSON，而在动作顺序是否由新观察驱动。若代码为每一种日志结果写好了下一节点，属于工作流；若模型读到证书错误后才决定查哪一份策略文档，且这种顺序无法由业务转移表逐一枚举，动态路径才成立。

这也解释了 Agent 的新增责任：模型负责候选质量，工具和环境负责事实，运行时负责权限、预算和停止，策略或人工负责高风险放行，完成验证器负责终态。任何一层缺失，开放路径都不应直接上线。

## 远程访问故障的分层升级回放

下面三段回放共享同一个用户目标，但掌握的初始证据不同。因此它们展示的是“未知逐层减少后，控制方式如何升级”，不是固定输入下比较三种实现性能的实验。

### 回放 A：稳定错误码由固定程序结束

客户端返回可信错误码 `DEVICE_NON_COMPLIANT`。固定程序查映射表，给出设备条件未满足和处理入口。

此时没有新的语义材料需要探索。Agent 循环既不能提供额外事实，也不能改变业务判断，任务应在函数层结束。若错误码不在映射表内，函数应返回未知并把问题交给上层，而不是让模型凭经验补一个原因。

### 回放 B：已知状态组合由工作流结束

错误码不足以定位原因，固定工作流读取设备、账号和审批状态。结果组合决定进入修复、解锁、等待或明确失败。

模型可以把三项状态整理成用户能读懂的说明，但不能新增数据源、改变转移或把 `approved` 写回业务状态。工作流若发现某个状态未知，应保存证据并升级，而不是静默走“成功”分支。

### 回放 C：固定检查无结论后进入只读 Agent

设备、账号和审批都正常，连接仍失败。固定工作流把已确认事实、允许的只读工具、最大轮数和完成证据交给 Agent。

Agent 先查认证日志。若观察出现证书错误，它可以选择查对应策略文档；若策略文档没有匹配项，再决定读取历史事件。每一步的选择都依赖刚得到的语义观察，运行时仍拒绝越权工具、写操作和无证据完成。

最终产物是带证据的原因假设和重新提交建议，不是业务终态。真正提交仍要读取可信状态，并按本案例的策略和人工审批执行。若只读调查在预算内没有形成证据，系统应停止并交付“未定位”及已有轨迹。

分层回放带来的判断很具体：先让确定性控制消化已知问题，再评估剩余未知是否值得动态探索。它不能替代同一任务集、同一输入和同一成功标准下的性能与风险评测。

## 风险决定 Agent 的活动范围

路径开放只是准入的第一道门。动态调查还要有可验证目标、受限工具、明确预算和停止条件，最坏失败必须可检测、可恢复，且收益能够在统一评测中被观察。

### 把副作用留在可信门禁之后

身份、权限、策略、金额和合法状态迁移不能由模型文本直接决定。Agent 可以收集证据、生成候选或草拟变更，运行时和策略负责把不允许的动作变成不可达分支。

本案例选择人工审批作为重新提交前的检查点。其他系统也可以组合策略引擎、自动化授权、幂等事务、沙箱和回滚机制。关键不是必须有哪一种组件，而是要证明副作用边界、检测时间和恢复成本与风险相称。

### 评测要看最坏路径

不要用一个主观分数给任务贴“Agent 适配度”标签。固定工作流和受限 Agent 应在同一任务集上比较：完成率、人工转接、模型和工具调用量、尾延迟、越权拒绝、无证据完成以及恢复耗时。

平均成功率掩盖不了高风险尾部。即使大多数调查都能找到原因，只要少数轨迹可能绕过权限或在未知状态下宣告完成，系统仍需缩小自主范围。评测结果没有显示动态动作带来可测收益时，保留工作流通常是更可解释的选择。

## 用一次评审决定是否升级

可以按下面顺序评审一个待自动化任务。每一步都应留下可回放的证据，而不是只写结论。

1. 单次调用能否由可信输入和局部规则直接得到结果。能，就使用固定程序。
2. 若需要多节点编排，外层阶段、合法边、执行器、终止和副作用策略能否由代码预先定义。能，就使用固定路径工作流。
3. 模型是否只在这些预定义阶段中处理非结构化输入、生成查询或候选子任务。是，就保持模型辅助工作流。
4. 固定检查后，当前动作和工具顺序是否必须依赖刚获得的语义观察，且无法由转移表逐一表达。否，就不需要 Agent。
5. 动态调查是否有目标、允许动作、预算、停止条件和完成证据。缺一项，先重写任务合同。
6. 最坏副作用是否可接受、可检测并可恢复，并已有相称的策略、自动化授权、幂等、回滚、沙箱或人工审批。不能证明，就把 Agent 限制在只读调查或候选生成。
7. 受限 Agent 是否在相同输入和成功标准下带来可测收益。没有，就退回更简单的方案。

这份顺序把“是否需要动态路径”和“是否值得承担动态路径”分开。前者是控制拓扑问题，后者是风险和证据问题，不能用任务复杂度替代。

## 结尾：把未知交给合适的控制层

回到开头的远程访问请求：稳定错误码由固定程序解释，设备、账号和审批组合由固定工作流推进，只有固定检查仍无结论时，受限 Agent 才在只读工具中选择下一项调查。它不因为任务听起来复杂而获得写权限，也不因为找到一段解释就取得业务终态。

因此，“哪些任务不该使用 Agent”的答案不是一个行业清单，而是一条控制边界：能由代码计算的不要交给模型，能由固定拓扑覆盖的不要开放运行时路径，只有无法预写且可验证的语义探索才值得升级。下一篇继续处理升级后的交接问题：模型提出工具候选后，怎样经过 Schema、权限、审批和执行回执，才能真正进入外部系统。
