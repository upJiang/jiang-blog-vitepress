# 哪些任务不该使用 Agent

Agent 允许模型根据观察改变路径，同时引入了更多运行责任：候选动作要校验，状态要保存，预算要计算，循环要停止，副作用要恢复。任务本来只有固定规则时，这些成本没有带来新的能力。

选型先画控制图。程序若已经知道下一步是什么，就用函数或工作流表达；路径确实依赖开放式语义和新观察，并且每个动作都能验证、限制与终止时，才需要 Agent。

## 四种方案处理不同的不确定性

| 方案 | 路径由谁决定 | 模型承担什么 | 适合场景 |
| --- | --- | --- | --- |
| 确定性函数 | 代码 | 不需要模型 | 计算、校验、授权、格式转换 |
| 固定工作流 | 代码与显式条件 | 可处理局部非结构化输入 | 审批、数据管道、状态机 |
| 模型辅助工作流 | 代码 | 抽取、分类、生成或评分 | 邮件分类、检索后回答、草稿生成 |
| Agent | 模型提出，运行时批准 | 根据观察选择下一动作 | 开放式研究、跨来源排障 |

这些方案可以组合。一次知识问答里，认证用确定性函数，文档检索走固定管道，模型整理答案；只有证据缺口需要动态补查时，局部进入研究循环。
## 控制图先回答三个问题

### 输入能否变成稳定字段

税率计算、库存扣减和权限判断都有明确输入。即使用户用自然语言描述需求，也可以让模型只负责抽取候选字段，随后由代码校验与计算。让 Agent 自主试探规则，会扩大测试面并降低可解释性。

输入长期开放、来源不固定时，模型可能有价值。排查“为什么服务偶尔变慢”需要根据日志、指标和配置逐步缩小范围，下一步取决于上一条观察，很难提前列完所有分支。

### 分支真的无法提前枚举吗

步骤多不等于路径开放。订单创建包含库存预占、支付、出库和失败补偿，流程很长，但状态与分支可以枚举，工作流引擎更合适。

“生成周报”也常被误判成 Agent。数据源、查询和版式都固定时，定时任务加模型摘要就够了。只有数据源需要动态发现、缺口需要补查并且允许范围明确时，才出现行动选择。

### 完成能否由程序确认

可验证产物会显著降低 Agent 风险。代码任务可以运行测试，文件转换可以校验格式，检索回答可以检查引用覆盖。若目标只有“让结果更好”，Agent 很容易自行结束，评审也难以复现。

完成条件模糊时，可以先改造任务：限定产物、证据、范围和预算。改造后若路径也固定，Agent 的需求往往随之消失。
## 确定性逻辑不要交给模型

### 身份、权限与策略

模型不能决定当前用户是谁、可以访问哪个租户、某个动作是否通过审批。它可以解释策略或提出候选，最终判断必须读取可信上下文并运行确定性规则。

### 金额、配额与事务状态

余额计算、费率、版本号和合法状态迁移都应由程序完成。模型生成的 `approved`、`paid` 或 `completed` 只是字符串，不能改变领域状态。

### 可逆性很差的操作

删除数据、转账、发布生产版本和发送具有法律效力的内容，不适合让模型自行决定。Agent 可以收集材料和生成操作草案，执行前仍需强校验与人工确认。

### 稳定的格式转换

CSV 到 JSON、日期归一化、图片尺寸调整等任务已有成熟库。模型增加费用和不确定性，还可能改坏边界数据。自然语言字段抽取可以使用模型，转换本身继续交给解析器。
## 固定工作流通常覆盖大部分业务自动化

工作流适合步骤已知、持续时间较长或需要补偿的任务。它可以并行执行、等待人工、重试和跨进程恢复，这些能力不专属于 Agent。

以文件入库为例，上传校验、病毒扫描、解析、切块、向量化、质量检查和版本激活都有明确依赖。解析器会因文件类型走不同分支，仍然可以由代码选择。让模型决定是否跳过质量检查，只会破坏发布边界。

模型可以嵌在某个节点中，例如识别扫描页结构或生成摘要。节点的输入、输出、重试和失败终态由工作流控制，这就是模型辅助工作流。
## Agent 适合路径会随证据变化的任务

开放式研究需要根据已找到的材料决定还缺什么，排障需要根据新日志调整假设，代码维护需要先读仓库再决定修改位置。这些任务共享几个条件：

- 下一动作依赖上一轮语义观察。
- 工具范围可以收紧，动作结果能够记录。
- 目标有可检查的完成或停止条件。
- 用户接受在预算内探索，失败可以明确交付。

缺少第二和第三项时，系统得到的是无边界自动化。比如“自动优化所有云资源”既包含高风险写操作，也没有清晰完成状态，不能因为模型会调用 API 就交给 Agent。
## 用一个问题比较四种实现

用户问“我的远程访问为什么失败？”

**确定性函数**适合已知错误码。接口返回 `DEVICE_NON_COMPLIANT`，程序查映射表并展示固定说明。

**固定工作流**依次查询设备与审批状态，根据明确规则组合结果。数据源稳定、分支有限时，它的行为最好测试。

**模型辅助工作流**先运行同样的查询，再让模型把技术状态写成自然语言。模型不选择数据源，也不决定失败原因。

**只读 Agent**在制度、设备、审批和历史事件之间动态选择查询，适合问题表达模糊或来源较多的情况。运行时仍限制当前用户范围、最大次数和证据要求。

如果产品只需要展示两项状态，第三种方案已经足够。动态路径能否减少用户来回补充信息，是这里真正需要验证的价值。
## 失败代价会改变选型

同样的路径不确定性，在不同风险下会得到不同方案。

| 失败后果 | 推荐控制方式 |
| --- | --- |
| 草稿不理想，可以丢弃 | 允许模型或 Agent 探索 |
| 查询遗漏，会得到不完整答案 | Agent 加证据覆盖与拒答 |
| 写错配置，可以快速回滚 | 固定变更集、审批和旁路验证 |
| 扣款或删除错误 | 确定性命令与强人工确认 |

平均准确率无法描述高风险尾部。一个任务即使 99% 成功，剩余 1% 会删除生产数据，仍然不能自主执行。评审要看单次最坏后果、可检测时间和恢复成本。
## 延迟、成本和吞吐也要计算

固定工作流的模型调用次数通常可预测。Agent 会因任务而变化，最坏路径需要单独估算：

```text
最坏调用量 = 最大轮数 × 每轮模型调用 + 工具重试 + 验证与修复
```

多个并行分支会共享 Token、连接和外部 API 配额。平均耗时看起来可接受时，P95 和 P99 可能已经被长尾工具拖高。选型实验应比较同一组任务在固定工作流与受限 Agent 下的完成率、总调用数、尾延迟和人工介入率。
## 渐进升级比一次性自治更容易判断

可以沿下面的顺序增加不确定性：

1. 用确定性程序完成可枚举部分。
2. 在单个节点加入模型，输出只作为候选。
3. 允许模型在一组只读工具中选择路径。
4. 加入有限循环、证据验证和明确终态。
5. 用户价值已经得到数据支持后，再评审可逆写操作。

每一步保留上一阶段的回归集。新增工具会改变模型的选择分布，即使旧工具代码未变，也要重测拒答、权限与终止行为。
## 选型评审要留下可证伪结论

“任务很复杂，所以需要 Agent”无法验证。更具体的假设可以写成：“在 100 条排障任务中，固定流程因未知来源需要人工转接 30 次；允许模型在四个只读工具中选择后，希望降低转接，同时越权率保持为零，P95 延迟不超过约定阈值。”

实验失败时也能知道退回哪里。若动态路由没有提高任务完成率，就保留模型辅助工作流；若效果提升但尾延迟过高，收紧最大轮数或只对部分问题启用；若权限测试失败，停止扩大工具范围。

Agent 选型的保守线很简单：固定路径能够完成任务，就保留固定路径。把不确定性限制在确实需要语义判断的那一小段，系统会更便宜，也更容易解释和恢复。
