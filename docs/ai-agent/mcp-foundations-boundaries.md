# MCP 的系统位置与能力边界

一个 Agent 要连接文件、知识库和外部业务服务时，逐个编写专用客户端会造成能力描述、错误格式和会话管理的重复。**MCP（Model Context Protocol，模型上下文协议）** 把发现能力、协商会话和调用外部 Server 的消息格式统一起来，让同一个 Host 可以接入不同实现。

协议统一了交互方式，仍然不会替应用做权限判断，也不会替 Agent 规划循环。模型能看到哪些工具、当前用户能调用哪些工具、结果是否可进入回答，属于 Host 和运行时的控制层。

## 四个角色的边界

| 角色 | 持有的责任 |
| --- | --- |
| Host | 用户会话、应用策略、多个 Client 和最终交付 |
| Client | 与某个 Server 建立会话，协商版本、能力和传输状态 |
| Server | 暴露工具、资源或提示，并在服务端校验与执行 |
| MCP | 规定消息、初始化、能力发现、调用和关闭流程 |

一个 Host 可以为每个 Server 创建独立 Client。Client 的连接状态和能力目录不能跨 Server 混用，工具调用回执要同时带上 Client 或 Server 身份。
## Tools、Resources 与 Prompts 解决不同问题

**Tools** 是可以被调用的动作，例如搜索或写入。它们有输入 Schema 和结果。

**Resources** 是可读取的内容或上下文入口，读取协议资源不等于允许访问业务数据库，Server 仍需执行授权。

**Prompts** 是可复用的提示模板或交互入口，提供任务表达方式，不能把它当作系统规则或权限配置。

把资源文本直接当作可信指令会带来提示注入。Host 要标记来源，模型上下文装配器把外部内容当作数据，策略层继续掌握工具调用权。
## 协商是会话的第一步

MCP Client 建立传输后，先发送初始化信息，包含协议版本与客户端能力。Server 返回选择的版本和服务端能力，双方再进入可处理普通请求的运行阶段。版本不兼容应在初始化阶段失败，不能等到第一次工具调用才报一个模糊错误。

能力目录是会话快照的一部分。Server 后续可能声明能力变化，Client 需要刷新或让当前 Turn 使用旧版本直到结束，避免半路改变 Schema 造成同一调用不可重放。
## MCP 和 Tool Calling 的分工

Tool Calling 解决模型如何提出一个结构化候选，MCP 解决 Host 与远程能力提供者如何发现和交换这个候选。一个 MCP Tool 最终仍要经过本地运行时的 Schema、权限、预算和审批。

```text
模型 → Tool Calling 候选 → Host 策略 → MCP Client → MCP Server
       ← 结构化结果    ← 观察与回执 ← JSON-RPC 响应
```

本地函数可以没有 MCP，远程服务也可以用普通 HTTP。引入协议的理由应是互操作、生命周期和能力发现，而不是把“协议”当作安全证明。
## API、Skill 与 MCP 不在同一层

HTTP API 是服务接口，应用代码通常直接决定调用。MCP 规定一套适合 Agent 工具和资源的协商协议。Skill 保存任务知识、判断步骤和参考文件，告诉 Agent 在什么条件下使用能力。工作流或 Agent Runtime 仍负责控制顺序、恢复和终态。

一个合成例子是：Skill 说明如何审查一份文档，Host 根据当前任务过滤工具目录，MCP Client 连接审查 Server，模型通过 Tool Calling 提出检查动作，运行时验证范围后执行。
## 多 Server 的注册表不能等于全量暴露

Host 可以维护 Server 注册信息，包括名称、传输、能力、版本和健康状态。模型拿到的工具目录应是当前任务的投影，不是所有 Server 的原始清单。工具名最好带来源命名空间，避免两个服务都叫 `search` 时发生选择歧义。

注册表缓存要绑定租户、权限和能力版本。Server 下线或目录变化时，缓存失效后重新协商；旧的模型候选按版本拒绝，不能把相同名字当作兼容。
## 失败怎样定位到协议层

| 现象 | 优先检查 |
| --- | --- |
| 连接建立失败 | 传输、进程、TLS 或地址 |
| 初始化被拒绝 | 协议版本与能力协商 |
| 工具不存在 | 目录刷新、命名空间与权限过滤 |
| 参数错误 | Schema 版本与 Server 校验 |
| Server 返回错误 | 服务实现、下游依赖和超时 |
| Agent 错误回答 | Host 装配、证据验证与模型控制流 |

最后一种不应归咎于 MCP。协议调用成功只说明消息往返完成，业务结果是否支持答案仍要由应用核验。
## 传输选择改变资源边界

本地 `stdio` 通常由 Client 启动子进程，进程生命周期、环境变量和标准错误流由 Host 管理。远程 Streamable HTTP 需要认证、连接池、代理、重连、并发和服务发现。两种传输都要限制响应体大小与总超时。

远程 Server 不能默认信任 Host 传来的用户 ID。身份应通过受控认证上下文传递，Server 对资源和工具再次授权。Host 的“已登录”状态不自动转换为 Server 的业务权限。
## 安全边界仍在应用

域名白名单、请求大小限制、SSRF 防护、工具级权限和输出清理都需要确定性代码。工具描述中写“只读”无法阻止一个有写副作用的实现，MCP 规范名称也不会自动降低风险。

外部内容可能携带 lookalike tool 指令，Host 应展示真实 Server 和工具来源，策略按稳定 ID 判断，不能按展示名称模糊匹配。高风险动作继续经过审批与幂等回执。
## 何时值得引入 MCP

需要让多个 Host 复用同一组能力、希望替换 Server 实现、需要标准化发现与会话生命周期时，MCP 有明显价值。只有一个应用、一个内部模块且接口稳定时，直接调用服务可能更简单。

引入前先列出协议外仍要维护的部分：身份、租户范围、策略版本、预算、审计、重试、取消和业务验证。若团队只需要一个函数调用，协议层的额外维护会成为负担。

测试应覆盖初始化、能力发现、工具调用、非法参数、响应过大、超时、取消、重连和关闭。再用应用级测试证明 MCP 返回的内容没有越过权限和证据边界。
