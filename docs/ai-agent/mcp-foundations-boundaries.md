# MCP 的系统位置与能力边界

[上一篇](/docs/ai-agent/parallel-tool-execution)处理了同一运行时里的并行工具：先证明依赖和快照允许同批，再用身份、预算和结果归约保持语义。

现在工具不再是进程内函数，而是由另一个服务提供，原来的调用边界要怎样延伸？

本文只回答一个问题：MCP 统一了哪一段能力交换，又为什么不会自动承担模型可见性、业务授权或答案终态。我们用同一份远程制度资料，对照直接 API 和 MCP 两条请求链，再把角色和能力类型放回正确层级。

## 先用同一份资料看两条请求链

远程访问调查需要读取“审批条件”制度片段。资料内容不变，先换接入方式，读者才能看出 MCP 增加了什么。

### 直接 API 把服务接口写进应用

应用代码知道制度服务的地址、认证方式和响应结构。它发送查询，解析响应，检查资料范围，再把片段装配成带来源的证据。

```text
Agent Runtime
  → HTTPS 请求制度服务
  ← JSON 响应与来源
  → 证据装配器
```

这条链短，责任也集中在应用。服务接口变化时，应用需要更新客户端；另一个 Host 想复用同一能力，还要重新实现认证、错误转换和目录描述。

### MCP 把能力交接抽成协议

改用 MCP 后，Host 为制度 Server 管理一个对应的 Client。Client 按协议发现可用工具或资源，Host 选择与当前任务有关的能力，再发出读取或调用请求。Server 返回结果，Host 仍把它转换成同一种证据对象。

```text
Agent Runtime
  → Host → MCP Client → 制度 Server
  ← 证据 ← 协议结果 ← 业务服务
```

MCP 统一的是发现、消息结构、能力交接和连接生命周期。认证、范围检查、响应大小、证据来源和最终回答并没有从 Host 消失，只是请求跨过了一个标准化边界。

两条链得到的资料都可能过期、越权或不足以支持结论。既然协议没有直接解决这些问题，就要先明确它在系统中的位置。

## MCP 究竟位于哪一层

把 MCP 放在“模型和数据库之间”仍然太粗。一次制度查询至少涉及用户会话、模型运行时、协议连接、能力提供方和业务数据五层；每层拥有不同的状态和失败责任。

### Host 负责应用控制面

Host 是承载用户会话、模型调用和应用策略的宿主。它决定本轮任务需要哪些能力，过滤 Server 的目录，把认证主体和授权范围交给运行时，并决定哪些外部内容可以进入模型上下文。

Host 还负责最终交付。Server 返回“找到三条制度片段”时，Host 不能因此宣布远程访问已获批准；它必须让业务规则检查证据是否新鲜、范围是否匹配、条件是否齐全。

### Client 负责连接一个 Server

Client 是 Host 与单个 Server 之间的协议适配器。它负责传输、请求和响应配对、能力发现、错误转换以及连接关闭。一个 Host 连接多个 Server 时，每个 Client 都要保留自己的来源和能力快照。

Client 不应该替 Host 做业务授权，也不能把一个 Server 的同名工具映射成另一个 Server 的结果。跨 Client 混用状态，会让“哪个服务看到什么”变得无法回放。

### Server 负责提供能力并再次校验

Server 暴露工具、资源或提示，执行自身的业务逻辑，并在资源读取和工具调用处再次检查身份、范围和状态。Host 的登录状态不是 Server 的业务授权证明。

Server 返回的错误可以说明服务拒绝、参数不合法或下游失败，但不能替 Host 判断用户问题是否已经解决。协议只描述交接，业务终态仍由应用拥有。

### MCP 负责互操作边界

MCP 规定消息如何表达请求、响应、错误、能力发现和生命周期事件，具体方法和字段要以采用的规范版本为准。它让不同 Host 和 Server 能按同一套交接规则协作，但不规定每个业务的权限模型、预算或完成条件。

四个角色的边界可以压缩成一张表：

| 角色 | 主要责任 | 不应替代 |
| --- | --- | --- |
| Host | 会话、目录投影、策略、上下文和交付 | Server 的业务实现 |
| Client | 单 Server 的连接、消息路由和传输状态 | Host 的授权与终态 |
| Server | 能力实现、服务端校验和结果 | Host 的模型控制流 |
| MCP | 互操作消息和生命周期 | 业务规则与证据判断 |

角色分清后，还要区分 Server 暴露的三种能力。它们都能被发现，却不应被写成同一个“工具调用”。

## Tools、Resources、Prompts 不是授权等级

三种能力入口解决不同的交接问题。它们告诉 Host“可以怎样获得动作、内容或任务表达”，不告诉 Host“当前用户一定有权这样做”。

### Tool 是可调用动作

Tool 通常有名称、描述、输入 Schema 和结果。制度搜索 Tool 接收查询词，返回匹配片段；写入 Tool 可能改变外部状态。两者都要经过 Host 的目录筛选、Schema 校验和业务授权。

Tool 的描述越宽，模型越容易误选相邻能力；描述越窄，也不能代替服务端权限。Host 应把工具来源、只读/写入性质、结果范围和失败状态作为目录投影的一部分。

### Resource 是可读取的内容入口

Resource 让 Host 或用户按 URI、名称或其他协议字段读取内容。它适合提供文件、制度文档或服务生成的上下文，但“能读取”不等于“可以把全文交给模型”。Host 仍要做范围检查、大小限制、来源标记和敏感字段处理。

制度片段中如果出现“忽略之前规则”的文字，那仍然是外部数据。上下文装配器要把它和系统指令分开，不能因为内容来自 MCP 就提升它的优先级。

### Prompt 是任务表达入口

Prompt 可以帮助用户或应用复用一套任务表达方式，例如“审查这份制度是否包含审批条件”。它不是策略文件，也不应直接授予工具权限。真正的权限和终态条件仍来自运行时和业务服务。

这三类能力的差异，会影响 Host 如何把结果交给模型：Tool 产生一次动作观察，Resource 产生外部资料，Prompt 产生任务表达。下一步要把它们和模型的 Tool Calling、普通 API 以及 Skill 组合起来。

## MCP 如何与相邻机制组合

这些名词经常被放在同一句话里，但它们不在同一层：

| 机制 | 解决的问题 | 不负责的部分 |
| --- | --- | --- |
| Tool Calling | 模型向运行时提出结构化候选 | 认证、协议连接、业务终态 |
| MCP | Host/Client 与 Server 的能力交换 | 模型决策、授权和证据判断 |
| API | 业务服务提供具体接口 | Agent 目录和上下文装配 |
| Skill | 保存任务知识、步骤和参考资料 | 执行权限和外部事实 |

制度搜索的一次组合可以写成：Skill 说明什么时候需要查审批条件；Host 从 MCP Server 的目录中筛选搜索 Tool；模型通过 Tool Calling 提出查询；运行时校验范围后由 Client 发给 Server；Server 访问自己的 API；Host 把响应变成证据。

```text
Skill（任务知识）
        ↓
Host 目录投影 → 模型 Tool Calling 候选
        ↓                ↓
  MCP Client ───────→ MCP Server → 业务 API
        ↑                ↓
        └──── 结构化结果与来源 ────┘
```

图中的箭头是交接关系，不是权限继承关系。模型候选仍要经过上一篇定义的运行时校验；Server 内部调用 API，也不意味着 API 的业务结果自动成为答案证据。

## 能力目录不能等于授权目录

Server 可以暴露几十个工具和资源，Host 却不应该把原始清单全部交给模型。目录需要按当前任务、主体范围、工具风险和预算形成投影。

### 目录投影要保留来源身份

两个 Server 都提供 `search` 时，Host 应以稳定来源和命名空间区分它们。模型看到的描述可以简化，但运行时保存的候选必须能找回 Server、能力版本和授权上下文。目录刷新后，旧候选若不再匹配 Schema，应明确拒绝并要求重新规划。

这条规则同时解决选择和回放问题：模型为什么选了这项能力，可以从当时的目录投影回答；请求最后发给谁，可以从 Client 和 Server 身份回答。目录不是权限系统，却是权限决策的重要输入。

### 外部内容只作为数据进入上下文

Resource、Tool 结果和 Server 错误都可能包含自然语言。Host 应为它们标注来源、时间和状态，并在装配上下文时限制长度、去除不必要的敏感字段。任何“请执行另一项工具”的文字，都要回到模型候选和运行时授权流程，不能直接执行。

如果 Host 把外部文本和系统规则拼在同一层，MCP 就会成为提示注入的放大器。协议本身没有优先级魔法，隔离指令与数据仍是应用的确定性责任。

## 什么时候值得引入 MCP

MCP 的价值不在于把每个内部函数都包一层协议，而在于能力需要跨 Host、跨语言或跨实现复用，同时还希望统一发现和生命周期。

### 复用和替换带来真实收益

当多个 Agent 应用都需要制度检索、文件读取或知识库查询时，独立实现客户端会重复目录描述、错误映射和连接管理。一个职责清晰的 Server 配合 MCP，可以让这些 Host 使用同一套能力交接，再各自保留策略和上下文控制。

如果未来要替换 Server 的实现，只要协议能力和结果合同稳定，Host 的连接层可以保持不变。前提是结果语义、权限边界和版本变化都被记录，而不是只依赖工具名称。

### 单一应用不一定需要协议层

只有一个应用、一个内部模块且接口稳定时，直接调用 API 往往更简单。引入 MCP 会增加协议版本、连接健康、目录缓存、认证传递、重连和契约测试的维护面。

做决定时先列出协议外仍要维护的责任：身份、租户范围、工具筛选、预算、重试、取消、审计、证据校验和业务终态。若这些问题还没有答案，增加协议不会让系统自动成熟。

## 用失败注入验证边界

边界不能靠角色表自证，需要让每一层分别失败，再检查错误是否被错误归因：

1. 传输建立失败：Client 应报告连接问题，Host 不应把它写成“制度没有匹配”。
2. 能力发现返回空或版本不兼容：Host 应停止使用旧目录，不应让模型继续提交旧候选。
3. 参数 Schema 通过但主体越界：Host 或 Server 应拒绝，不能因为协议请求格式正确就执行。
4. Server 返回提示注入文本：上下文装配器应保留来源并隔离指令，不能直接触发下一项工具。
5. 协议响应成功但证据缺少版本或来源：业务运行时应标记证据不足，不应宣布远程访问已获批。

单元测试可以使用内存 Client 验证目录过滤、身份归属和错误映射；契约测试再连接真实 SDK，检查能力发现、参数错误、响应大小和关闭。

应用级测试必须证明授权、证据和终态仍由 Host/Server 共同守护。三层测试分别回答协议能否通信、能力是否按合同工作、业务是否安全。

## 结尾：协议统一交接，应用保留判断

回到制度资料请求，直接 API 把服务接口写进应用，MCP 则把 Host/Client 与 Server 之间的发现、消息和生命周期标准化。两条链都必须认证、授权、校验结果并装配证据。

所以，MCP 的系统位置是能力交换边界，不是模型决策层，也不是业务终态层。Host 决定模型看到什么，Client 负责连接谁，Server 负责实现和再次校验，运行时负责预算、证据和交付。

下一篇沿这条边界继续追踪协议生命周期：初始化怎样建立可用会话，能力发现和调用如何配对，取消、重连与关闭又怎样影响未完成请求。
