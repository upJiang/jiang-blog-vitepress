# 文件上传、准入与对象存储

用户在页面上看到“上传成功”，通常只说明服务器收到了文件。对知识库来说，这时还不能解析，更不能检索。文件名可能带路径穿越片段，扩展名可能伪装，Office 文档可能是压缩炸弹，远程地址可能指向内网，正文甚至可能夹着要求模型泄露提示词的指令。对象存储返回成功，也没有证明数据库里已经存在一份可恢复、可授权、可发布的文档记录。

一条可靠的入库链路会把这些问题拆开处理：上传入口负责接收和限流，准入层判断原始字节能否进入隔离存储，对象存储保存不可变原件，Manifest 描述原件属于哪个知识范围以及包含哪些来源，入库任务再解析、切块、向量化并构建候选版本。候选版本通过质量检查以后，在线检索才切换到新版本。

::: info 上传成功的准确含义

上传成功表示原始对象已通过入口检查并被安全保存。它不表示解析成功、索引完成或新知识版本已经生效。客户端应看到明确阶段，而不是一个覆盖整条链路的 `success`。

:::

本文用一份名为 `remote-access-policy.docx` 的制度文档贯穿整条链路。文件包含普通段落和表格，大小约 2 MB，用户希望替换知识库中的旧版本。正常路径要留下原始对象、准入结论、Manifest、入库版本和激活记录；失败路径则必须指出停在哪一步，并保证旧版本仍可查询。

## 上传接口只接收原始对象和可信范围

上传请求至少有两类输入。第一类是用户提交的原始信息，包括文件字节、原始文件名和浏览器声明的媒体类型。第二类由应用补入，包括当前用户身份、目标知识范围、权限上下文、请求标识和资源上限。两类输入不能混用。文件正文里出现 `scope=admin`，只是一串不可信文本，不能覆盖认证系统给出的范围。

接口可以使用 `multipart/form-data`，也可以接收一个已经完成分片上传的对象引用。无论传输方式怎样变化，服务端都要固定几个不变量：请求属于哪个知识范围；本次上传的稳定标识是什么；最大允许字节数是多少；客户端断开后由谁清理未完成数据；同一幂等键再次提交时返回旧结果还是创建新任务。

对于几十 MB 以内的文档，先读入受限缓冲区再检查实现简单，但内存占用会随并发增长。更大的对象适合边接收边写隔离区，同时累计实际字节数。两种方式都不能只相信 `Content-Length`。请求头可以缺失或伪造，流式读取必须在越过上限时立刻停止。本文推演把单文件上限设为 50 MB，这只是配置示例，不是 RAG 的固定标准；实际值要按解析器、Worker 内存和并发预算确定。

上传状态也不该只存在于 HTTP 连接。可以保存一条最小记录，包含 `upload_id`、知识范围、创建者、当前阶段、对象键、准入错误类和更新时间。客户端超时后用 `upload_id` 查询，系统才能回答对象究竟没有写入、已经写入还是等待入库。若连接断开就丢掉所有状态，重试很容易产生第二份原件。

幂等键与内容哈希解决的问题不同。幂等键表示“这是同一个提交意图”，适合网络重试；内容哈希表示“这些字节相同”，适合内容身份和版本比较。同一文件可以由两个用户提交到不同知识范围，哈希相同也不能自动共享权限。反过来，同一幂等键携带了不同字节，服务端应拒绝冲突，而不是悄悄把后一次覆盖前一次。

## 文件准入从文件名检查到内容签名

准入层的输入是原始字节、原始文件名和声明媒体类型，输出应是结构化结果，例如规范化文件名、检测到的类型、是否为图片以及安全告警。任何强制策略失败都在写入正式对象前结束。入口拒绝后，解析器、Embedding 服务和索引仓库的调用次数都应为零。

文件名检查先处理路径问题。绝对路径、`..`、空路径段、反斜杠变体和 NUL 字节都不应该进入对象键。服务端只保留一个经过规范化的叶子文件名，长度也要受限。原名用于界面展示和审计，真正的对象键由服务端生成，不能直接采用用户传入的路径。

扩展名只能决定候选解析器，不能证明文件内容。一个名为 `manual.pdf` 的文件若以 Windows 可执行文件的 `MZ` 签名开头，应在解析前拒绝。ELF 和常见 Mach-O 签名也需要同样处理。对于 PDF、图片和 Office 文档，还要比较扩展名、客户端声明的 MIME 与实际检测结果。三者冲突时应返回类型不一致，而不是挑一个看起来最合理的继续执行。

普通 ZIP 文件不应借 Office 上传入口进入系统。DOCX、XLSX 和 PPTX 本身是 ZIP 容器，所以准入层需要确认容器内有对应的 Office 目录和内容类型描述，并逐项检查成员路径。成员名出现绝对路径或 `..` 会造成解压路径穿越；条目数、总展开大小和单项压缩比不受限，则会把一个很小的压缩包变成内存或磁盘耗尽攻击。带宏或可执行附件的成员也应按产品策略拒绝。

图片还有另一种资源风险。压缩后的图片可能很小，解码后却包含极多像素。准入层应让图片库实际解析并校验格式，同时设置像素上限；只检查文件大小不够。文件为空、格式无法识别或图片校验失败都应返回稳定错误类型，调用方不能靠匹配自然语言错误判断是否重试。

下面这段代码只展示控制顺序。`detect_type`、`inspect_archive` 和 `inspect_image` 需要使用成熟库实现，不能用几行字符串判断代替。

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class AdmissionResult:
    filename: str
    media_type: str
    warnings: tuple[str, ...]


def admit_file(data: bytes, filename: str, declared_type: str) -> AdmissionResult:
    if not data:
        raise AdmissionError("empty_file")
    if len(data) > MAX_FILE_BYTES:
        raise AdmissionError("file_too_large")

    safe_name = normalize_leaf_filename(filename)
    reject_executable_extension(safe_name)
    reject_executable_magic(data)

    detected_type = detect_type(data, safe_name)
    require_consistent_type(safe_name, declared_type, detected_type)
    inspect_archive_if_needed(data, safe_name)
    inspect_image_if_needed(data, detected_type)

    warnings = scan_untrusted_text(data, safe_name, detected_type)
    return AdmissionResult(safe_name, detected_type, warnings)
```

这段函数只返回准入结果，不写数据库也不激活索引。空文件、超限和伪装类型会抛出可枚举错误；正文里的提示注入、疑似秘密或个人信息则进入 `warnings`。把扫描命中一律当成上传失败并不合适，因为合法制度文档可能正在讲“忽略之前指令”这类攻击文本。更稳妥的做法是保留文件，将它标为不可信内容，在后续上下文装配时隔离并限制影响范围。

安全扫描也不能把原始秘密复制到日志。记录 `prompt_injection:pattern_1`、`pii:email` 这样的类别即可。这样既能让审核人员定位风险，又不会因为安全日志再制造一次泄露。

## 远程导入需要单独防住 SSRF

从 URL 导入文档看起来只是把上传动作换成一次 GET，请求边界却更危险。用户控制的地址可能访问 `localhost`、云主机元数据服务或公司内网；公开域名还可能在 DNS 解析后切换到私网地址。普通 URL 格式校验拦不住这些情况。

远程导入只接受 HTTP 和 HTTPS，不允许 URL 携带账号密码，也不开放任意端口。主机名解析出的每个地址都必须是公网 IP。发起连接后还要读取实际 Peer IP，确认它仍在刚才的解析集合中，从而限制 DNS Rebinding。若 HTTP 客户端拿不到连接对端信息，安全策略应失败关闭，不能因为“很可能是同一个地址”继续读取。

每次重定向都要重新执行完整校验。第一个 URL 指向公网，并不代表它返回的 `Location` 也安全。重定向次数应有上限，缺失 Location 或超限形成独立错误。HTTP 客户端还应关闭环境代理继承，否则部署机器上的代理配置可能改变实际访问路径。

响应体同样做两层大小检查。`Content-Length` 已经超过上限时可以在读取前拒绝；服务端没有提供长度，或者声明值比真实值小，流式累计仍会在越界时停止。下载完成后，字节还要经过与本地上传相同的文件准入，不能因为来源是 HTTPS 就跳过 Magic Number、Office 容器和图片检查。

以本例文件为例，若远程地址先返回 302，再把请求导向 `127.0.0.1`，请求应在第二跳连接前停止。若域名解析到一个公网地址，真正连接却落在另一个 IP，也应拒绝。此时没有对象键，没有 Manifest，更不会创建入库任务。这些“零次下游调用”是安全测试中很重要的断言。

## 对象键隔离身份，原始文件名只做元数据

通过准入后，原始字节进入对象存储。对象键适合采用“知识范围前缀 + 服务端随机标识 + 已确认后缀”，例如 `scope-id/uuid.docx`。随机标识避免同名覆盖，范围前缀让读取和删除可以再次验证归属。原始文件名保存在对象元数据或 Manifest 中，用来展示，不能参与授权。

读取和删除都要走同一个键规范化函数。它应移除允许的固定展示前缀，拒绝绝对路径、空段和 `..`，再确认规范化后的键确实位于预期知识范围之下。调用方即使拿到了另一个范围的完整对象键，也会得到权限错误。对象不存在与无权访问最好使用不同的内部错误，但公开接口是否隐藏存在性，要由威胁模型决定。

对象读取不能假设写入时的限制永远有效。管理员可能导入历史对象，存储桶也可能被其他系统写入，所以读取流仍要设置上限，并在结束后关闭响应体。对象存储返回 404 时转成稳定的“原件缺失”错误，入库任务据此停止；把空字节交给解析器只会把存储问题伪装成解析问题。

本例上传后会得到一个新对象键，原名和检测类型作为元数据保存。此时可以把上传状态改为 `stored`。**它仍不是知识版本。** 对象存储只负责原件的持久字节和基础元数据，不应该保存哪一版 Chunk 已激活，也不负责判断当前用户能否检索某个派生结果。

写对象成功、更新上传记录失败是一个真实的部分成功边界。此时客户端可能收到 500，但对象已经存在。重试若重新生成键，会留下多个孤立对象。解决办法是在写入前保存稳定 `upload_id`，对象键由这次提交确定；重试先查记录和对象回执，再决定补写元数据还是重新上传。对象存储本身没有跨数据库事务，应用必须显式处理这段不一致窗口。

## Manifest 描述来源，不替代原始对象

Manifest 是入库任务的结构化输入，它回答“这次要把哪些来源组织成一份文档”。对象存储回答的是“字节放在哪里”。两者不能合并成一条随意扩展的元数据记录。

一个 Manifest 至少要有文档身份、知识对象、根节点、目标 Release、创建者、可见范围和 Source 列表。每个 Source 有稳定 ID、类型、父 Source、顺序、标题、正文或对象引用、解析版本与警告。Source ID 必须唯一；非根 Source 引用的父 ID 必须存在；整份 Manifest 至少有一个根 Source。多来源文档如果没有这些约束，附件会在重试后挂到错误父节点，引用也无法稳定指回原件。

可见主体需要去除空白并去重，但它不能由文件正文提供。创建者、权限范围和 Release 都来自应用的可信状态。Manifest 即使通过 Pydantic 或 JSON Schema 校验，也只证明字段形状正确，后续仍要核对 Release 是否是当前可发布版本、创建者是否有权限以及对象键是否属于目标范围。

内容哈希在这条链路上有两个合理位置。若上传服务边接收边计算原始字节哈希，它可以识别完全相同的原件，并辅助校验分片传输。另一种实现让上传层只保存对象，在解析完成后按规范化 Source 内容计算哈希，用于文档版本和派生索引身份。两者不能混写成一个字段：原始 DOCX 的字节哈希和解析后正文哈希含义不同，解析器升级后，前者不变，后者可能变化。

本文所依据的配套实现采用后一个边界：对象上传方法生成范围内随机键并保存原名，没有在上传函数中按哈希去重；内容哈希在 Source 版本与文档版本入库时计算。因此“同一文件重复上传会自动复用原始对象”不能写成现有事实。若产品确实需要原件级去重，应增加明确的哈希索引、权限隔离和引用计数，并补并发测试。

## 入库任务先建候选版本，再原子激活

Manifest 校验完成后，入库服务生成稳定文档身份、文档版本和索引版本。它先查询相同版本是否已经处理。若命中已存在结果，就作为幂等重放返回，不再调用 Embedding，也不重新激活一个旧版本。这个规则很重要，因为队列至少一次投递或客户端重试都可能让同一任务再次到达。

新版本沿固定顺序处理：从 Source 生成 Chunk，为 Chunk 计算 Embedding，写入候选文档版本、Source 版本和 Chunk，然后核对候选区。核对内容至少包括 Source 数、Chunk 数、向量数和覆盖统计是否一致，正文保留率是否达到要求，是否存在重复 Chunk、断裂的邻接关系或超限 Chunk。只要一项失败，候选版本保持不可见，旧活动版本继续服务。

激活过程要在一个数据库事务内完成。旧 Chunk 退出活动状态，新版本 Chunk 变为活动，文档版本切换发布状态，文档指针更新到新版本。事务提交后，在线检索才能看到新的制度文档。若 Embedding 超时，服务记录失败并回滚，不执行激活；若入库任务在激活前崩溃，恢复任务可以根据版本状态判断是继续构建还是清理候选。

这里还有一个容易混淆的“上传完成”。对象键写入成功属于上传层完成；候选版本的解析、切块和向量齐全属于入库构建完成；活动指针切换才属于发布完成。API 与页面可以分别展示 `stored`、`indexing`、`active` 和 `failed`。只给一个百分比会让用户看到 100% 时仍查不到内容，也让排障人员不知道该查存储还是索引。

本例的正常状态轨迹可以写成：

```text
received
  -> admitted
  -> stored
  -> manifest_ready
  -> indexing_staging
  -> staging_validated
  -> active
```

若文档在准入时被识别成伪装的可执行文件，终态是 `rejected`，对象和入库版本都不存在。若对象已保存但 Embedding 超时，上传状态仍可保持 `stored`，入库版本是 `failed`，旧 Release 不变。两种失败不能共用“上传失败”一条文案，它们的恢复动作完全不同。

## 重复提交和部分成功要按边界恢复

现在完整推演一次重试。用户提交 `remote-access-policy.docx`，请求标识为 `req-42`，应用创建 `upload_id=up-42`。文件通过 50 MB 上限、文件名、内容签名和 Office 容器检查，扫描发现正文中有一段提示注入示例，于是保存一个安全告警，但不拒绝文件。对象写入后，上传记录保存对象键，Manifest 引用该对象并固定当前知识范围。

入库 Worker 领取版本 `ver-42`，解析与切块完成，Embedding 调用超时。版本记录保存错误类别和失败阶段，没有改变活动版本。客户端看到的是“原件已保存，索引构建失败”，而不是重新上传按钮。Worker 使用同一版本重试时先查询已有状态，复用原件与解析结果是否安全取决于各阶段的版本契约；至少不能创建第二个对象，也不能绕过候选区直接激活。

另一种故障发生在对象写入之后、上传记录提交之前。应用重启后只剩对象存储里的字节，没有可查询的 `upload_id` 引用。完整生产系统需要孤立对象回收流程，但回收器不能看到“数据库没有记录”就立即删除，因为事务可能仍在提交，队列任务也可能持有对象。更安全的判定要同时满足：对象超过暂存宽限期；没有活动 Manifest 或上传记录引用；没有运行中 Lease；对象前缀确实属于暂存区。删除动作本身要幂等，并记录删除键和判定依据。

反向的不一致是数据库已经保存对象键，实际对象却不存在。入库任务读取时得到稳定的 `source_missing`，停止解析并保留版本失败记录。它不应创建空文档，也不能把旧版本内容冒充新上传结果。是否允许用户重新绑定原件，需要新的受权命令，不能由 Worker 猜测。

部分成功的恢复原则可以归纳为一句：**从拥有状态的边界继续。** 上传入口拥有传输状态，对象存储拥有原件回执，Manifest 拥有来源关系，入库版本拥有派生数据，发布事务拥有活动指针。重试先查这个边界留下的状态，再决定续做、补偿或停止。把整条链从头再跑，通常会制造更多重复对象和过期候选。

## 删除原件时还要撤回派生数据

删除对象不等于知识已经消失。解析正文、Chunk、Embedding、全文索引、缓存和答案引用都可能继续保留内容。删除命令需要先判断语义：是撤销一次尚未发布的上传，删除一个文档版本，还是让整个知识对象退出服务。三种操作影响的引用不同，不能共用一个“删文件”按钮。

未发布的暂存对象没有 Manifest 和活动版本引用，超过宽限期后可以直接清理。删除历史版本时，先把版本标为撤回，阻止新查询命中，再异步清理可重建的 Chunk 与向量；活动版本被删除，则要先切到经过验证的上一版本，或者让该文档进入不可用状态。切换和清理的先后顺序反了，在线请求会在短时间内读到已经声明撤回的内容。

原件被多个版本引用时，引用计数或关联查询必须在对象删除前完成。只按内容哈希判断“还有一份一样的文件”不够，因为另一份可能属于不同权限范围，不能成为当前范围的替代来源。保留期、审计冻结和用户删除请求也会改变物理删除时间，状态中要区分“停止服务”和“字节已擦除”。

删除后的回归验证至少发起一次旧引用查询，确认检索结果、缓存和引用接口都不再返回撤回版本；随后检查对象、派生 Chunk 与向量是否按策略清理。若系统只能证明对象存储的 `delete` 调用成功，却没有验证在线索引和缓存，最多只能说原件被删了，不能说知识已经撤回。

撤回事件还应携带对象身份与版本，而不是复制正文。缓存消费者收到事件后按版本失效，迟到的旧入库任务再次提交时也会因版本过期被拒绝，避免已经删除的内容被后台重建回来。

## 测试要证明拒绝、隔离和激活顺序

单元测试先覆盖准入函数。空字节、超过限制、危险扩展名、可执行 Magic Number、PDF 伪装、图片伪装、Office 路径穿越、异常压缩比和无效图片分别进入明确错误。合法 DOCX 即使包含提示注入文字，也应被接收并带上告警，这个反例可以防止开发者把“风险文本”和“可执行攻击”混为一谈。

远程导入测试使用受控 HTTP Transport，不访问真实内网。用例让首跳公网 URL 重定向到回环地址，断言第二跳被拒绝；让 DNS 返回一个公网 IP、连接 Peer 却是另一个地址，断言失败关闭；让 `Content-Length` 先报超限以及流式正文后续越界，确认两种路径都不会写对象。客户端在测试结束后关闭，避免连接泄漏被忽略。

对象存储的集成测试应连接隔离桶，验证上传后可读取原字节、检测类型与原始文件名，删除后再次读取得到缺失错误。再补路径测试：跨知识范围键、带 `..` 的键和非规范键都不能读取或删除。读取超限对象时也要停止，证明历史数据无法绕开新限制。

入库服务测试关注调用顺序和活动状态。正常样本应调用一次 Embedding，候选校验完成后激活；同一版本重放不再调用 Embedding，也不重新激活；Embedding 抛出超时后记录失败，活动指针不变。数据库集成测试再核对候选数量、向量就绪数量、覆盖率和事务切换，单元测试里的内存仓库不能证明这些约束。

清理流程需要时钟和并发测试。构造一个超过宽限期且无引用的暂存对象，它应被删除；构造仍被 Manifest、上传记录或 Lease 引用的对象，即使很旧也不能删除；重复运行清理器，第二次不应报错或影响其他对象。若代码库只有上传、读取和删除适配器，却没有引用扫描与宽限期逻辑，就只能说“具备删除原语”，不能宣称“已实现孤立对象自动清理”。

最后用 `request_id`、`upload_id`、对象键、文档版本和激活版本串起一次端到端断言。输入是 2 MB 的 DOCX，状态按预期推进，调用顺序是准入、对象写入、Manifest、候选构建、候选校验、激活；输出是可查询的新版本。故障样本把 Embedding 替换为超时，证据包括失败阶段、调用次数和未变化的活动版本。只有这组证据齐全，才说明上传链路既接住了文件，也没有把半成品交给检索。

下一步由[多格式文档解析与 OCR](/docs/ai-agent/rag-document-parsing-ocr)接管 Manifest 中的原件。解析器只读取已经通过准入并属于当前知识范围的对象，输出带结构和警告的 Block；上传层不需要知道 PDF 页码或表格怎样切块，解析层也不能反过来修改上传身份和对象归属。
