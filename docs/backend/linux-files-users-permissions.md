# Linux 文件、用户、组与权限：服务为什么读不到文件

Linux 用用户和组表示进程身份，用所有者、权限位以及可选 ACL 约束文件访问。检查发生在进程访问路径时，不只看目标文件，还会逐级验证父目录能否遍历。这套机制处在应用进程与文件系统之间，决定服务能否读取配置、写日志或进入数据目录。

`journalctl` 显示 `permission denied`，但文件本身是 `644`。这并不矛盾：进程还要有权遍历每一级父目录，且服务可能以不同用户运行。Linux 权限排查要看“谁、访问什么路径、经过哪些目录”。

## 权限检查是逐级的

文件 mode 的 owner、group、other 三组位只在进程走到该 inode 时生效。父目录缺少 `x`，即使文件可读也无法打开；ACL、umask 和挂载选项还可能改变结果。先用 `id` 确认实际用户，再用 `namei -l` 展开路径。

要以服务的真实 UID/GID 观察路径。终端账户能读只说明当前 shell 有权限，不能替代 systemd 或容器进程的结果。

```bash
id
namei -l /srv/backend/config/app.env
getfacl /srv/backend/config/app.env
```

把命令输出保存下来。`namei` 用于确认每一级目录的遍历位，`getfacl` 用于发现 mode bits 之外的 ACL。

## 最小权限和 Secret 文件

服务只需要读取配置时，目录可以由部署用户拥有，文件由服务组读取；不要把目录整体改成 777。容器中还要确认挂载后的 UID/GID 与镜像内用户一致。Secret 轮换时写入新文件、原子替换软链接，再让进程重新加载。

| 现象 | 高概率原因 | 处理顺序 |
| --- | --- | --- |
| 文件不存在 | 路径或挂载错误 | 确认工作目录、挂载点、文件名 |
| Permission denied | 用户、父目录、ACL | id -> namei -> getfacl |
| 容器能读宿主不能读 | UID/GID 或 SELinux 标签 | 检查容器用户和挂载上下文 |
| 改权限后仍失败 | 进程缓存旧配置或只读挂载 | 确认重新加载和挂载模式 |

## 文件操作也有并发状态

直接 `echo > app.env` 会先截断旧文件，进程可能读到半份内容。写临时文件、`fsync` 后 `rename` 能让读取者看到旧文件或新文件。权限正确只是前提，原子替换才解决并发读取。

## 把 permission denied 缩到一个检查点

| 现象 | 先确认 | 处理顺序 |
| --- | --- | --- |
| 只给文件加读权限仍失败 | 先确认父目录的执行位和进程用户。 | 逐级展开路径，再检查 ACL 和挂载 |
| 能否用 root 启动修复权限 | root 会掩盖真实权限缺口，发布后换回普通用户仍会失败。 | 用目标服务用户复现并修复所有者/组 |
| Secret 更新后应用没变化 | 进程可能只在启动时读取环境或文件。 | 确认 reload 能力；不能 reload 时采用滚动替换 |

依次记录进程用户、每级目录的搜索权限、目标 inode 的 mode/ACL、挂载只读状态和安全模块拒绝日志。哪一步第一次不满足，修复就停在哪一步。直接 chmod 777 会同时改变多个假设，既扩大权限，也让人不知道原来的阻断究竟来自目录、ACL 还是挂载。

## 文件权限的继承与扩展

**目录的 x 权限为什么表示“进入”而不是“执行文件”？**

对目录来说，x 代表沿目录项查找 inode 的能力。没有 x，即使知道文件名和文件本身是 644，也不能访问它。读取目录列表还需要 r，因此只给目录 x 可以允许访问已知文件名而不允许列目录。

**什么时候应该使用 ACL？**

当传统 owner/group 无法表达少量例外访问时使用 ACL，例如审计进程需要读取某个日志目录。ACL 要纳入部署和备份，否则换机器后权限会悄悄丢失。

## 服务管理器会改变进程看到的文件世界

systemd 的 User、Group、WorkingDirectory、ReadOnlyPaths 和环境文件共同决定服务实际能力。终端里用当前账户能读，不代表 systemd 服务用户能读；容器的只读根文件系统也可能让临时文件写入失败。排查时应读取服务定义和进程 status，不要只在 shell 中复现。

日志目录还涉及创建权。进程只需要追加现有文件时可以只给文件写权限；日志轮转会创建新文件，因此轮转器与服务进程必须约定目录属组、创建 mode 和重新打开信号。否则轮转后才出现 permission denied，看起来像随机故障。

**为什么 umask 会让部署结果在不同机器上不一样？**

创建文件的最终权限由程序请求的 mode 再减去 umask。交互 shell、systemd 和 CI 的 umask 可能不同。部署脚本应显式安装文件的 owner、group 和 mode，而不是依赖创建者默认值。
