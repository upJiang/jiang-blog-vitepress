# MySQL 备份、恢复与数据操作纪律

MySQL 备份保存某个时间点或时间段内可用于重建数据库的数据与日志，恢复则在目标环境重放这些材料并验证业务状态。它们处在生产数据与灾难恢复流程之间，用来满足可接受的数据丢失量和恢复时间。只有生成文件而没有做过恢复演练，不能证明备份可用。

备份任务每天显示“成功”，真正删除一张表后却发现备份无法恢复：文件损坏、binlog 缺段、加密密钥不在，恢复脚本也从未跑过。备份的完成条件不是生成文件，而是在隔离环境恢复到目标时间并通过业务校验。

## RPO、RTO 与恢复目标

RPO 表示允许丢失多少时间的数据；RTO 表示允许服务多久恢复。每天一次全量备份只能提供接近 24 小时的基础 RPO，若还要恢复到删除前一分钟，就需要持续保留 binlog。

RPO/RTO 是业务决定，不是 DBA 单方面参数。订单与审计的容忍度可能不同；恢复方案必须包含应用版本、Schema、对象存储和消息状态，不能只还原 MySQL 就宣告系统恢复。

| 目标 | 需要的材料 | 主要风险 |
| --- | --- | --- |
| 恢复到昨夜备份 | 全量或物理备份 | 丢失备份后的写入 |
| 恢复到误删前一分钟 | 基线备份 + 连续 binlog | 时间点、GTID 或日志缺口 |
| 快速恢复大库 | 物理备份或就绪副本 | 版本兼容与一致性 |
| 只找回少量逻辑数据 | 隔离恢复后导出目标行 | 直接覆盖生产造成二次损失 |

## 逻辑备份和物理备份解决不同问题

逻辑备份保存建表与 INSERT 等逻辑内容，可读、可选择对象，跨环境迁移方便，但大库恢复慢。物理备份复制 InnoDB 数据文件和日志，恢复快，却更依赖版本、存储布局与工具。

复制不是备份。误删除和错误更新会复制到从库，攻击者也可能删除所有在线副本。备份需要独立权限、保留周期、不可变或离线副本，并定期验证校验和。

下面只展示逻辑备份与隔离恢复的骨架。命令中的主机、账号、证书和目标库必须替换为隔离环境配置，不能把恢复直接指向生产库。

```bash
mysqldump --single-transaction --routines --events \
  --set-gtid-purged=OFF app > app.sql
sha256sum app.sql > app.sql.sha256

sha256sum -c app.sql.sha256
mysql -h restore-db -u restore_user -p app_restore < app.sql
```

`--single-transaction` 为 InnoDB 提供一致快照，但长时间导出会保留旧版本并增加 undo 压力。含非事务表或 DDL 变更时还要采用额外策略。

## 恢复演练按时间线执行

先创建隔离实例，验证备份与密钥，恢复基线，再应用目标范围的 binlog。到达目标时间后停止写入，运行 Schema、行数、关键约束和业务查询校验。最后记录耗时、人工步骤和失败点。

误删恢复通常不要直接把整个旧库覆盖生产。可把备份恢复到隔离库，导出缺失记录，经过依赖和冲突检查后再执行受审计的数据修复。这样避免把误删之后的合法新数据一起抹掉。

```mermaid
flowchart LR
  B[校验基线备份] --> R[恢复到隔离 MySQL]
  R --> L[应用 binlog 到目标时间]
  L --> V[Schema 与业务校验]
  V -->|通过| P[制定切换或数据修复]
  V -->|失败| S[停止并保存证据]
```

恢复过程中最重要的停止条件是目标时间与校验不确定。宁可停在隔离环境查清，也不要把不确定数据切回生产。

## 备份也要纳入权限和告警

备份账号使用最小权限，文件与加密密钥分开管理。监控不仅看任务退出码，还看最近成功时间、文件大小突变、校验和、binlog 连续性和恢复演练日期。

Schema 迁移发布前保留可验证回滚点。大规模不可逆数据变换应使用扩展/迁移/收缩流程，不要把“有备份”当作可以随意执行破坏性 DDL 的理由。

## 恢复方案必须回答的问题

**为什么备份文件大小正常也可能不可用？**

文件可能截断但仍很大，内容可能缺表、缺存储过程，密钥可能丢失，恢复工具也可能与版本不兼容。只有校验和与实际恢复能证明可读，业务查询才能证明内容满足恢复目标。

**Point-in-time recovery 怎样选择停止点？**

根据明确的 binlog position、GTID 或经过校准的事件时间选择。服务器时间、时区和事务边界都要核对；应在隔离库重放并检查目标操作前后的事件。

**从库能否直接承担备份？**

可以降低主库读取压力，但要确认复制没有延迟或错误，备份快照与 binlog 坐标一致。还要避免备份 IO 把从库拖到无法承担故障切换。

**恢复演练会不会浪费资源？**

它消耗资源，但能提前暴露密钥、版本、脚本和时间预算问题。可按数据等级安排频率，并在隔离资源上自动化；从未恢复过的备份只能算未经验证的希望。
