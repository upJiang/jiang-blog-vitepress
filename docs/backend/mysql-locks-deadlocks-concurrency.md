# MySQL 锁、死锁与并发顺序

两个事务更新同一批记录：事务 A 先锁项目 1 再锁项目 2，事务 B 先锁项目 2 再锁项目 1。双方各自持有对方需要的锁，MySQL 检测到等待环后回滚其中一个事务。这是死锁处理机制正常工作，不代表数据库随机坏了。

## 锁保护当前版本的记录与范围

普通一致性读依赖 MVCC 快照，通常不加记录锁；`SELECT ... FOR UPDATE` 是当前读，会锁住扫描到的索引记录，供后续更新。UPDATE 与 DELETE 也按访问路径获取排他锁。

在 InnoDB 默认 REPEATABLE READ 下，范围当前读可能使用 next-key lock，也就是记录锁与间隙锁的组合，阻止其他事务在范围中插入幻影。**锁住多少不只取决于 WHERE 文本，还取决于优化器实际扫描的索引范围。**

```mermaid
flowchart LR
  I1[索引记录 10] --- G1[间隙 10..20]
  G1 --- I2[索引记录 20]
  I2 --- G2[间隙 20..30]
  Q[FOR UPDATE 范围 10..20] --> I1
  Q --> G1
  Q --> I2
```

精确命中唯一索引通常只需记录锁；非唯一范围可能覆盖记录和间隙。缺少合适索引会扩大扫描与锁范围。

## 双会话复现等待与死锁

在隔离数据库打开两个连接，各自关闭自动提交。下面按相反顺序更新两行，第二轮更新会形成等待环。记录每条语句发生时间和事务 ID。

不要在生产表上复现。两个会话交错执行后，其中一个应收到 deadlock 错误并回滚；另一个继续后仍需显式 COMMIT。

```sql
-- Session A
START TRANSACTION;
UPDATE projects SET name = 'A1' WHERE id = 1;
-- 等 Session B 锁住 id=2
UPDATE projects SET name = 'A2' WHERE id = 2;

-- Session B
START TRANSACTION;
UPDATE projects SET name = 'B2' WHERE id = 2;
UPDATE projects SET name = 'B1' WHERE id = 1;
```

应用收到死锁错误时，当前事务已失败，不能继续复用其中间结果。仅对完整、幂等且有重试上限的事务重新执行，并采用抖动退避。

## 死锁报告用于还原资源顺序

`SHOW ENGINE INNODB STATUS` 可查看最近一次死锁，performance_schema 可观察当前锁等待。关注两个事务各自持有什么索引锁、等待什么 SQL，以及扫描使用哪个索引。

修复通常是统一访问顺序、缩短事务、补充索引或减少一次锁住的范围。把死锁重试次数调到无限只会放大负载；直接把隔离级别降低也可能改变业务可见性，必须先证明需要。

| 现象 | 证据 | 处理方向 |
| --- | --- | --- |
| 同两张表经常死锁 | 事务访问顺序相反 | 统一按资源 ID/表顺序加锁 |
| 锁等待范围很大 | 执行计划扫描大量索引项 | 补索引或改为精确条件 |
| 事务持锁数分钟 | 事务内有网络调用或人工等待 | 把外部调用移出事务 |
| 重试后副作用重复 | 事务外已发消息/调用支付 | Outbox 与幂等保护 |

## 锁等待超时与死锁不是同一种失败

死锁是等待图存在环，数据库可立即选择牺牲者；锁等待超时是一直等不到资源但未必成环。两者都要求当前操作失败，但诊断证据和修复方式不同。

连接断开、语句超时与事务回滚范围还受驱动和配置影响。Service 捕获错误后应明确 rollback，记录事务阶段和业务键，再决定是否重试完整事务。

## 并发下还要能推演这些问题

**为什么给 WHERE 字段加索引能减少锁冲突？**

UPDATE/FOR UPDATE 沿索引寻找记录。合适索引缩小扫描范围，通常也缩小被锁的索引记录和间隙。但具体锁仍需用执行计划和锁监控确认。

**死锁能否彻底消灭？**

复杂系统很难保证绝不发生，数据库也把死锁检测与回滚作为正常机制。目标是降低频率、保证事务可安全重试，并对持续上升告警。

**乐观锁是否完全不用数据库锁？**

条件 UPDATE 执行时仍会获取数据库写锁，只是不先长时间持有显式悲观锁。它通过版本条件检测并发冲突，适合冲突较少、可让用户重试或合并的场景。

**把所有更新按主键排序就一定不会死锁吗？**

它能消除一类顺序相反的死锁，但事务还可能涉及不同索引、外键、唯一约束和多张表。要从真实死锁报告还原完整等待图。
