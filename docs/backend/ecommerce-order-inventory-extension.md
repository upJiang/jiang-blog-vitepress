# 电商扩展：商品、库存、订单与支付回调

两个请求同时购买最后一件商品。两边都先读到 stock=1，再各自减一，就会超卖。订单扩展必须在数据库事务和锁层保护库存不变量，并让支付回调可幂等重放。

## 商品、库存和订单的事实边界

商品、库存和订单的事实边界不能只靠术语记忆。先确定输入来自谁、状态由谁拥有、一次操作改变了哪些记录，再看输出如何被下一层使用。**状态所有者一旦含糊，重试和故障恢复就会出现重复或丢失。**

```mermaid
flowchart LR
  A[输入与上下文] --> B[商品、库存和订单的事实边界]
  B --> C[状态检查]
  C -->|满足约束| D[提交结果]
  C -->|不满足| E[稳定错误]
  D --> F[日志 / 指标 / 审计]
```

图中失败分支不会假装成空成功。项目的调用方应根据稳定错误码决定停止、重试或重新读取状态。

## 下单事务锁住库存行

下单事务锁住库存行要放回请求时间线：开始时读到什么，中间获得什么锁、连接或租约，成功时提交什么，失败时又能否回到原状态。这样才能判断超时后是安全重试、查询原结果，还是进入人工对账。

下面的片段抓住 项目 中最容易出错的一条执行路径。先观察输入条件和状态标识，再看副作用在什么位置发生。

```text
UPDATE inventory
SET available = available - :quantity, version = version + 1
WHERE tenant_id = :tenant AND product_id = :product
  AND available >= :quantity;
-- affected_rows 必须为 1，否则库存不足
```

片段之后要核对实际输出或影响行数。只看到函数没有抛错还不够；还要确认状态版本、提交结果和下游可见性与预期一致。

## 支付回调和 Outbox 状态

支付回调和 Outbox 状态最终要落实到可观察证据。项目的配置、日志或执行结果需要携带稳定标识，例如 requestId、资源版本、任务 ID 或制品摘要，避免只凭“看起来正常”判断系统。

| 阶段 | 应保存的事实 | 失败后的动作 |
| --- | --- | --- |
| 接收输入 | 身份、范围、版本、requestId | 拒绝无效或越界输入 |
| 执行中 | 锁、连接、租约或任务 attempt | 超时后取消或等待恢复 |
| 提交结果 | 影响行数、状态版本、事件 ID | 冲突则重新读取，不覆盖新状态 |
| 交付输出 | 状态码、结构化日志和指标 | 根据稳定错误码处理 |

这张表的重点是可恢复性：每次状态变化都要能回答“现在由谁负责，下一步允许什么”。

## 支付回调和 Outbox 状态出现异常时怎样定位

| 现象 | 先确认 | 处理顺序 |
| --- | --- | --- |
| 调用超时或无响应 | 确认请求是否到达当前组件，以及是否已产生副作用。 | 先查 requestId 和状态记录，再决定取消或重试 |
| 返回成功但状态不对 | 比较提交影响行数、版本号和后续读取。 | 绕过缓存读取真相，再检查序列化和失效 |
| 重试后出现重复 | 检查幂等键、唯一约束或消息 ID 是否覆盖副作用。 | 停止自动重试，查询原结果并修复去重边界 |

先固定版本、输入、时间窗口和资源状态，再沿 项目 的状态记录找到等待发生在哪一步。只有确认瓶颈后，才改变超时、池大小或副本数，并记录改变后的新证据。

## 下单事务锁住库存行之后还要追问

### 商品、库存和订单的事实边界为什么不能只放在调用方处理？

调用方可以改善交互，但无法控制并发请求、绕过客户端的调用和进程故障。约束必须由拥有业务状态的一层执行，并由数据库约束、消息确认或运行时所有权提供最终裁决。

### 下单事务锁住库存行遇到超时后，什么时候可以重试？

超时只说明调用方没有及时拿到结果，不能证明服务端没有提交。读请求通常可以重试；写请求需要幂等键、版本条件或可查询的任务 ID，否则重试可能产生第二次副作用。

### 怎样用失败路径证明 项目 真的被理解了？

用一条正常路径和至少两条失败路径做对照，记录输入、状态变化、原始输出和恢复动作。测试应覆盖并发、重复、取消或依赖不可用，而不只是单次 200。

### 支付回调和 Outbox 状态与前一层的责任怎样交接？

交接内容写入契约：输入带身份、范围和版本，输出带结果、状态码和可追踪 ID。支付回调和 Outbox 状态只处理自己拥有的状态。

### 项目怎样保证三个实现不会逐渐分叉？

OpenAPI、标准化后的 information_schema 和同一套 Bruno 场景是三条外部基线。功能先改契约和共享迁移，再分别实现；CI 依次访问三个 API，同一安全失败和状态转换必须得到相同结果。

### 综合项目出现跨层故障时从哪里切入？

从浏览器拿到 requestId，沿代理、API Trace、数据库事务、Outbox、消息 ID 和任务事件查询。先找最后一个已确认状态，再判断缺失的是提交、发布、消费还是客户端展示，避免同时修改多层。
