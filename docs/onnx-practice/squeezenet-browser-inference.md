# ONNX 浏览器图片识别：从整图分类到目标检测

浏览器图片识别是把已经训练好的视觉模型放进网页运行环境，由 JavaScript 完成图片解码和预处理，再由 ONNX Runtime Web 调度 WebGPU 或 WASM 执行计算图，最后把输出 Tensor 转成用户能读懂的类别、概率或检测框。图片不必先上传到业务服务器，适合隐私敏感、本地预览和弱网场景；代价是模型下载、浏览器兼容性、内存和前端后处理都要由页面承担。

“识别图片”不是单一任务。整图分类回答整张图最像哪个预设类别，目标检测回答图中哪些位置出现了哪些物体，关注区域分析只能观察哪些像素影响了当前分类。三类输出不能互相替代。

同一张猫图放进两个模型后会得到两种答案。SqueezeNet 在 1000 个 ImageNet 类别中判断“整张图最像什么”，地毯的纹样甚至可能让“蚊帐”排到前面。YOLOX-Nano 回答的是“哪里有什么”。在 Chrome 的本地 WASM 验证中，它用一个检测框覆盖猫的主体，“猫”的置信度约为 78.9%；它还把大片家具区域当成“床”，置信度约为 25.1%。后者是一次可见的误检。浏览器的图片缩放实现不同，具体分数可能有小幅变化。

先在下面切换“整图分类”和“目标检测”。两个模式使用同一张图片和同一个执行后端，但它们的输入、输出和用途不同。

## 整图分类、关注区域与目标检测

“整图分类”把一张图压成一组类别分数。页面里的五项结果是同一个问题的五个备选答案，不是图片中有五个物体。如果第一名是“蚊帐”，准确的读法是：在这个模型的 1000 个备选类别里，当前整张图对“蚊帐”这个类别的响应最高。它不等于图中真有一顶蚊帐。

“关注区域”检查哪些像素区域影响了当前分类。实验把中心裁剪图分成 `5 x 5` 格，每次遮住一格后重新推理。如果遮住某格后第一候选的概率降得很多，这一格就会更深。它能告诉我们模型依赖哪里，但不能把深色格子直接命名为“耳朵特征”或“毛发特征”。

“目标检测”才会返回物体的类别和位置。这个实验使用 COCO 的 80 个常见类别，可以检测人、猫、狗、汽车、手机、电脑、椅子和多种食物。圆形、颜色、文字和 Logo 不属于这 80 个目标类别。换成只有彩色圆形的图片时，页面没有检测结果是正常现象：它表示没有候选结果达到阈值，不表示图片没有内容。

| 页面结果 | 模型回答的问题 | 不能说明什么 |
| --- | --- | --- |
| 五个整图候选 | 整张图最像哪些预设类别 | 图片中有五个物体 |
| 遮挡热力图 | 哪些区域影响当前第一候选 | 模型已经命名了局部特征 |
| 类别、置信度和检测框 | 什么物体大概在哪里 | 结果一定正确，或能检测任意物体 |
## ONNX 文件的计算图与权重

训练通常发生在 PyTorch、TensorFlow 等框架中。训练完成后，导出器会把计算步骤和已学到的参数写进 `.onnx` 文件。ONNX 使用 Protobuf 序列化这些数据，其中最值得关注的是四类信息：

- 输入和输出的名称、类型与形状。
- `Conv`、`Relu`、`MaxPool`、`Concat` 等计算节点。
- 节点之间的 Tensor 连接，它们构成一张有向计算图。
- 卷积核、偏置等已训练参数，ONNX 把它们称为 `initializer`。

这些权重才是模型从训练数据里学到的部分。ONNX 本身不会训练，也不会“理解”图片；它提供了一种可跨框架交付计算图与权重的格式。

实验中的 SqueezeNet 输入是 `float32[1, 3, 224, 224]`，输出是 1000 个类别概率。YOLOX-Nano 输入是 `float32[1, 3, 416, 416]`，输出是 `float32[1, 3549, 85]`。这些形状是模型契约，不是页面可以随意改的参数。
## ONNX Runtime 的推理执行链路

浏览器真正执行计算的是 `onnxruntime-web`。从用户点击“运行”到页面出现结果，中间经过了以下过程。

```text
图片文件
  -> 浏览器解码为 RGB 像素
  -> 按模型契约裁剪或缩放
  -> Float32Array + NCHW
  -> Worker 创建 Tensor
  -> InferenceSession.run()
  -> WebGPU 或 WASM 执行计算图
  -> 输出 Tensor
  -> 页面后处理为中文标签、概率和检测框
```

`InferenceSession.create()` 会获取 ONNX 文件，解析序列化数据，验证算子和 Tensor 连接，然后根据 `graphOptimizationLevel: 'all'` 做图优化。例如，运行时可以合并能够连续执行的节点，并提前折叠与输入无关的常量计算。

接着，Runtime 把节点分配给 Execution Provider。本实验优先尝试 WebGPU，用 GPU 计算管线执行卷积等算子；如果浏览器、驱动或模型算子不满足条件，自动模式会用 WASM 在 CPU 上执行。WASM 固定为单线程，因此不需要 `SharedArrayBuffer` 和跨源隔离响应头。

页面把预处理结果作为可转移的 `ArrayBuffer` 发给 Worker。Worker 用它创建 `Tensor`，然后把 Tensor 绑定到模型的输入名称：

```ts
const tensor = new ort.Tensor('float32', new Float32Array(data), [1, 3, 224, 224])
const output = await session.run({ [session.inputNames[0]]: tensor })
```

`session.run()` 会按数据依赖顺序计算节点。后一个节点要等前一个节点产生 Tensor，没有依赖的分支则有机会并行。每种 Execution Provider 会为算子选择自己的内核实现。最终返回的仍然是 Tensor，而不是“猫”这样的文字。
## SqueezeNet 的特征提取过程

像素进入第一层卷积时，每个卷积核只看局部小块。这些核在训练后通常会对亮暗变化、颜色对比、边缘方向或重复纹理产生不同响应。`Relu` 保留正响应，`MaxPool` 缩小空间尺寸，后续层再把低层响应组合成更大范围的形状与类别证据。

这份 SqueezeNet 图中包含 26 个 `Conv`、26 个 `Relu`、3 个 `MaxPool` 和 8 个 `Concat` 节点。接近输出的 `conv10_2` Tensor 形状为 `[1, 1000, 13, 13]`，表示 1000 个类别在 `13 x 13` 空间位置上的数值响应。`GlobalAveragePool` 把每个类别的空间响应压成一个值，`Softmax` 再得到 1000 个概率。

这也解释了为什么“分析图片特征”容易被过度解读。中间 Tensor 的通道是高维数值，通常没有人类可读的名称。它们可能同时响应形状、纹理和背景组合。如果产品必须明确输出“有猫耳”或“长毛”，就需要带这些属性标注的多标签模型，不能靠观察一张热力图替代。
## 分类模型与检测模型的预处理差异

SqueezeNet 先取原图中间的正方形，缩放到 `224 x 224`。每个 RGB 像素先除以 255，再用 ImageNet 的均值 `[0.485, 0.456, 0.406]` 和标准差 `[0.229, 0.224, 0.225]` 归一化。

```ts
input[position] = (red / 255 - 0.485) / 0.229
input[planeSize + position] = (green / 255 - 0.456) / 0.224
input[2 * planeSize + position] = (blue / 255 - 0.406) / 0.225
```

YOLOX-Nano 需要保留整张图的纵横比，否则检测框无法准确映射回原图。它把图片等比缩放到 `416 x 416` 画布的左上角，右侧或下方空白处填入 RGB `114`。这个固定发布版的输入使用 `0-255` 的 Float32 RGB 像素，不除以 255，也不做 ImageNet 均值和标准差归一化。

这些处理是模型训练契约的一部分。Runtime 只会检查 Tensor 形状和数据类型，无法发现“数值范围不对”或“通道顺序写反了”。一次无报错的 `session.run()` 不代表结果有意义。
## YOLOX-Nano 如何从 301665 个数里得到检测框

YOLOX-Nano 返回 `[1, 3549, 85]`。`3549` 来自三组空间网格：

```text
52 x 52 + 26 x 26 + 13 x 13 = 3549
```

每个网格点有 85 个数：4 个边界框参数、1 个物体分数和 80 个 COCO 类别分数。Worker 使用 stride `8`、`16`、`32` 还原网格坐标，然后把框除以预处理阶段的缩放比例，映射回原图像素坐标。

一个类别的最终置信度是：

```text
置信度 = 存在物体的分数 x 该物体属于某类的分数
```

页面默认只保留置信度不低于 25% 的候选。多个网格点可能同时包围一只猫，因此后处理还要做按类别的非极大值抑制（NMS）。两个框的重叠率高于 `0.45` 时，留下置信度更高的一个。

置信度滑杆修改的是后处理阈值。Worker 会缓存上一次 `[1, 3549, 85]` 输出，调整滑杆时只重新筛选和执行 NMS，不会重复运行 369 个 ONNX 节点。所以滑杆可以让人直接看到一个实际取舍：阈值高会减少误检，也可能隐藏真实但分数较低的物体。
## Worker 中的模型执行与后处理

主线程负责图片解码、Canvas 预处理和界面状态。模型解析、卷积推理、遮挡分析和 NMS 放在 Worker。这与[把大数组计算移出主线程](/docs/frontend/web-worker-off-main-thread)的原则一致。

统一 Worker 会按模型缓存 Session。第一次运行整图分类时只下载 SqueezeNet，第一次运行目标检测时才下载 YOLOX-Nano。切换图片可以复用已创建的 Session；切换 WebGPU 和 WASM 时则会终止旧 Worker，避免不同执行后端共用状态。

加载时间包含模型请求、解析、图优化和 Session 创建。推理时间只记录 `session.run()`。预处理和后处理分开记录，否则一个“总耗时”无法告诉我们瓶颈在网络、Canvas、模型还是 NMS。
## 这些输出能用来做什么

整图分类适合做粗粒度打标、候选分组和人工审核前的预筛。它只选择整张图的主要类别，很难处理一张图里同时有多个对象的任务。

目标检测提供了可直接消费的坐标。业务程序可以根据“猫”的框自动裁图，根据“人”的框做本地隐私遮挡，统计图片里同类物体数量，或在检测到特定物体后触发后续流程。这些操作仍然需要业务阈值、验证集和人工兜底，不能把演示图上的一次命中当成精度报告。

浏览器本地推理的优势是图片不需要上传，断网后也有机会继续使用已缓存的模型。它适合小模型和交互式单张图片。大模型、大批量图片、需要统一硬件性能或必须保护模型权重的任务，仍然更适合服务端推理。
## 模型和样例从哪里来

SqueezeNet 1.0 Opset 12 来自固定的 `onnxmodelzoo/squeezenet1.0-12` 仓库提交 `0e6cddd4291d78516c22543bc5a347d5916154a0`。文件大小为 4,952,956 bytes，SHA-256 为 `dec81a8684617770b3cf13fadc1d92565d1d453d23935fc6388b792d99c992bd`，许可证为 Apache-2.0。

YOLOX-Nano 来自 Megvii YOLOX `0.1.1rc0` Release，对应源码提交 `e1052df71842031413f6030723c3607b839c80ce`。文件大小为 3,659,407 bytes，SHA-256 为 `c789161ed43c8269fcd4e67c67eeeb4e80c622da2eb296a20bc6007bd18a0b7d`，许可证为 Apache-2.0。

ImageNet 中文标签使用 `DWHNicholas/ImageNet_chinese_cls` 提交 `4c9d449bfd473628c3bba0dba39536bc4c97be77` 的 1000 行映射，许可证为 Apache-2.0。COCO 中文标签与 YOLOX 的 80 类输出顺序一致。页面会同时检查标签行数，避免标签错位后把数值解释成错误类别。

内置图片是 Wikimedia Commons 的 `Domestic cat 2011 G02.jpg`，作者 George Chernilevsky，原页标记为 Public Domain。两个模型、标签和样例图都由站点静态自托管，运行实验时不依赖外部模型 CDN。

**为什么猫图的整图分类可能不是猫？**

SqueezeNet 看到的是中心裁剪后的整张图，其中同时有猫、地毯纹样和家具。它必须在固定的 1000 个类别中排序，没有目标检测的位置约束。小模型可能对大面积纹理的响应超过猫的响应。用关注区域可以查看这个候选更依赖哪里，但单张图不能证明模型整体精度。

**猫的 78.9% 置信度是“有 78.9% 概率这是猫”吗？**

不完全是。这个值是模型内部的物体分数与类别分数之积，适合排序和设定阈值，但不一定经过概率校准。要把它当成业务风险概率，必须先在目标数据集上验证和校准。

**为什么还会检测出“床”？**

样例图里的沙发和地毯占据大面积，轮廓和纹理与模型学到的床类样本有部分重叠。调高置信度阈值可以隐藏这个低分结果，但通用解法不是永远把阈值调高，而是用业务图片评估误检和漏检，再确定阈值。

**为什么 WebGPU 会回退到 WASM？**

当前浏览器可能没有 `navigator.gpu`，页面环境、硬件驱动或模型算子也可能不满足 WebGPU 要求。自动模式会显示回退状态并继续用单线程 WASM 推理。显式选择 WebGPU 时不会隐藏失败，便于区分能力缺失和模型加载错误。

**图片真的没有上传吗？**

组件用本地 `File`、`ImageBitmap` 和 Canvas 生成 Tensor，Worker 通过 `postMessage` 接收像素数组。当前代码没有图片上传请求，网络面板只应出现站点文件、模型、标签和 WASM 资源。这个结论只覆盖当前页面代码；浏览器扩展、本地代理和自定义 Service Worker 仍需要单独纳入隐私审查。
## 推理复核：模型输出要经过后处理验证

浏览器端推理的边界由预处理、Execution Provider、Tensor 形状和后处理共同决定。模型返回数值并不代表类别、框选或显著区域已经符合业务定义，阈值、NMS、坐标缩放和标签映射都要单独测试。

验收覆盖 WebGPU 不可用、Worker 取消、模型下载失败、图片尺寸异常和内存回收。示例中的浏览器性能与置信度只属于当前模型和输入，换设备、模型或量化版本后重新测量，不把单次分数写成稳定承诺。
