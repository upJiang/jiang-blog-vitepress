# 站点抽样、重复页面与收录异常排查

收录异常排查是一种沿发现、抓取、渲染、Canonical 与索引状态逐层缩小原因的诊断过程。它位于监控变化和页面修复之间，用于分清页面没有被发现、抓取受阻、内容被判重复，还是已经索引但未获得展示。

自然点击突然下降，团队有人建议改标题，有人怀疑算法更新，还有人准备继续发文章。此时最重要的动作不是选一个听起来合理的原因，而是先确定故障发生在哪一层。

排查路径从数据口径进入服务器、抓取、索引、排名和点击，再用分层抽样、模板聚类与聚合日志扩展单页证据。每一步都需要正常页面作对照，一次只验证少量假设。

[单页审计报告](/docs/seo/browser-page-seo-audit)提供站点抽样的候选入口。将其中“同模板待确认、疑似重复、可能孤立、参数膨胀”带入页面库存；不要重新检查一次首页就写成全站结论。

## 站点审计的抽样边界

一个创业网站可能有几十到数百万 URL，直接“全量抓取”会消耗服务器、触发限流，还可能遍历无穷参数。**Stratified Sampling（分层抽样）**是先按目录、页面类型和业务重要性分层，再从每层选代表 URL。

第一轮可从最多 20 个样本开始，确认方法与模板问题；需要扩大证据时再到 50 或 100。样本优先包括当前页、首页、Sitemap URL、不同目录/模板、近期变更、正常与边界数据。数字不是通用标准，大站还需要专业爬虫、数据仓库和受控速率。

抽样的输入是同源 URL、Sitemap、页面内链与页面类型，处理时遵守 robots.txt、限制正文体积、并发和域名，输出是样本内库存与候选问题。它不执行登录抓取，不携带 Cookie/Authorization，不把 20 页说成“全站已检查”。
## 页面库存、模板簇与分层样本

**Template Cluster（模板簇）**把路径模式、页面类型和结构相近的 URL 归组。每个模板至少记录样本数、状态分布、可索引数、Sitemap 数、重复 Title/正文候选与抽样 URL。

模板聚类解决“一次错误影响多少页面”的定位问题。例如 8 张产品页都输出同一 Title，应先检查模板变量和空值，不逐页手改。路径相似只是候选，最终要用页面任务与实际渲染确认。

页面库存可汇总：

- 2xx、3xx、4xx、5xx 与请求失败；
- index/noindex、Canonical 自指/外指与目标状态；
- Sitemap 中 URL 与样本实际状态；
- 搜索页、标签页、筛选页和分页页数量；
- 正文为空、Title/Description/正文重复候选；
- hreflang、JSON-LD 和内链入口候选。

所有计数都要带“样本 N 页”前缀。抽样中 3/20 页为空，不等于全站 15% 空页；可以作为扩大同模板检查的依据。
## 将模糊现象拆成可验证状态

“SEO 下降”可能代表完全不同的问题：页面打不开、爬虫没有访问、已抓取但未索引、仍有索引但查询排名变化，或者展示正常却点击减少。

```mermaid
flowchart LR
  A[确认数据口径] --> B[页面可访问]
  B --> C[发现与抓取]
  C --> D[渲染与索引]
  D --> E[查询排名]
  E --> F[展示与点击]
  F --> G[业务转化]
```

前一层不成立时，先修前一层。服务器持续 5xx 时改正文没有意义；页面仍有稳定展示但转化下降，也不应直接归因于收录。
## 确认异常范围和时间线

记录异常开始日期，并按目录、模板、设备、地区、查询和页面拆分。随后对照同一时期的发布、迁移、服务器故障、追踪改动和业务季节变化。

至少选一个正常 URL 和一个异常 URL。若只有总流量曲线，没有具体页面、查询和时间范围，任何归因都只能写成假设。
## 从匿名 GET 建立公开页面证据

在浏览器能打开还不够。记录最终状态码、跳转、响应头和原始 HTML，确认公开 URL 刷新后也能得到正确文件。

```bash
curl -sS -L -o /tmp/seo-page.html \
  -w 'status=%{http_code}\nurl=%{url_effective}\nredirects=%{num_redirects}\n' \
  'https://example.com/docs/topic'
```

输入是受影响 URL，输出是最终状态、地址和跳转次数。正文另存到临时目录，便于检查标题、canonical、robots 指令和主要内容。不要只依赖 HEAD，请求链中的代理可能对 HEAD 与 GET 有不同处理。

正常文章返回稳定 200，不存在地址返回真实 404 或 410。有明确替代内容时才永久跳转；把所有删除页都跳到首页会掩盖真实不存在状态。
## 检查发现、抓取与渲染链路

通过站内链接和站点地图确认搜索引擎有机会发现 URL。再查看服务器日志，判断疑似爬虫是否访问、访问了什么、得到何种状态和耗时。

User-Agent 名称可以伪造，不能单独作为身份凭证。日志格式也各不相同，先查看服务器 `log_format` 和一行样本，再写统计命令，避免照抄固定列号。

抓取成功后还要看原始 HTML 是否包含标题、正文和重要链接。如果只有完整浏览器运行脚本后才出现内容，就继续排查脚本、接口和资源失败。

### 日志聚合应回答哪些问题

服务器日志先解析为 URL、状态、时间、响应耗时和疑似爬虫类别，再做聚合，不需要长期保存完整 Referer、IP 和原始 User-Agent。CSV 也要处理 BOM、引号和中英文表头；无法识别字段时应让操作者确认映射。

| 日志候选 | 判断依据 | 正确下一步 |
| --- | --- | --- |
| 错误状态 | 4xx/5xx 按 URL 和模板聚合 | 区分坏链接、正确删除页与服务故障 |
| 慢 URL | 平均与 p95 达到复核阈值 | 看缓存、数据库、依赖，再关联 LCP/FCP |
| 参数浪费 | 追踪、排序、筛选 URL 重复请求 | 核对页面任务、内链、Canonical/noindex |
| Sitemap 无样本 | 清单 URL 未出现疑似爬虫请求 | 延长日志窗口并补平台证据 |

日志中 Sitemap 地址没有疑似请求，只说明“在当前时间范围、当前日志和 UA 识别规则里没看到”。它不能证明搜索引擎从未抓取。爬虫身份默认标未验证，确认方式按目标平台官方机制执行。
## 检查索引目标与页面信号

`robots.txt` 管理抓取许可，`noindex` 表示页面不应进入索引，`canonical` 指出重复页面中的首选版本。三者不能互相替代。

站点地图只应包含希望被索引的规范 URL，排除重定向、错误页、`noindex` 和无价值参数页。提交站点地图帮助发现 URL，但不保证收录。

对于“已抓取未索引”，继续检查重复页面、空壳模板、正文是否解决独立问题，以及站内是否有清晰入口。每天重复提交不能修复这些问题。

### 全站常见冲突怎样判断

| 候选问题 | 为什么不能自动下结论 | 二次验证 |
| --- | --- | --- |
| Sitemap URL 同时 noindex | 信号明确冲突，但需先确认页面目标 | 查索引矩阵并修清单或页面指令 |
| Canonical 外指 | 可能是正常重复合并 | 请求目标，核对 200、index 与页面任务 |
| 分页都指向第一页 | 对独立列表可能有害，对重复视图可能合理 | 比较后续页独立条目和发现路径 |
| 站内搜索可索引 | 常制造无限薄页，少数策划专题可能有价值 | 核对模板、查询组合和内容资格 |
| 空正文 | 可能是 CSR 失败、接口异常，也可能工具解析不到 | 比较原始/渲染、状态和业务数据 |
| hreflang 不互返 | 样本可能没包含目标页 | 请求完整语言矩阵和 Canonical |

工具应把这些问题标为已确认、风险候选或不可测，不能仅凭路径名称批量 noindex。
## 重复、近重复和模板重叠不是同一件事

**Duplicate Content（重复内容）**表示多 URL 的主要任务与内容实质相同；**Near Duplicate（近似重复）**是文本或结构高度相似的候选；**Template Overlap（模板重叠）**则可能只是导航、固定开头和变量缺失造成的模式。

自动检查可以对 Title、Description、正文指纹与开头相似度分组，但处理必须回到用户任务：

- 任务相同且没有独立价值：合并内容，旧 URL 301 到最相关主页面；
- URL 仍需给用户使用但内容是重复版本：Canonical 指向可索引主版本；
- 页面无需搜索展示：允许抓取并 noindex，再从 Sitemap/内链治理；
- 任务确实不同：补充独特数据、实体、案例与链接，不为“去重”随意换词。

近似文本不是自动删除依据。地区、语言、产品变体、法律条款和权限页面可能看起来接近，却有不同任务。相反，只把城市名替换掉的程序化页面，文字略有不同也可能没有独立价值。
## Orphan Candidate 为什么只能叫候选

**Orphan Page（孤立页）**通常指没有任何站内可跟随链接入口的页面。站点抽样若发现某 URL 在 Sitemap 中、但本次样本没有入链，只能标 **Orphan Candidate（疑似孤立页）**；样本没覆盖全部页面。

二次确认需要更完整的站内爬取、渲染链接、数据库页面关系或服务器日志。重要页面应从相关栏目、专题或正文获得有语境的入口；无搜索价值页面则从 Sitemap 清理，而不是为了消除告警随便在页脚加链接。
## 索引稳定后的排名与点击诊断

排名需要绑定查询、页面、日期、设备和地区。全站平均排名会混合大量不同意图，难以指导改动。

如果排名下降，比较结果页的主流页面类型、内容变化和用户意图；如果排名稳定但 CTR 下降，再检查标题表达、品牌信任和结果页是否出现新的模块。不要同时改 URL、标题、正文和内链，否则数据恢复后也无法知道哪项有效。
## 故障分级与处理顺序

| 等级 | 示例 | 首要动作 |
| --- | --- | --- |
| P0 | 全站 5xx、生产误禁抓取、核心模板空白 | 停止扩大影响并恢复可用版本 |
| P1 | 核心目录 canonical 错误、大量软 404 | 修复规则并逐日观察 |
| P2 | 内链弱、内容重复、部分意图偏差 | 纳入迭代并做对照 |
| P3 | 单日小幅波动、证据不足 | 保存基线继续观察 |

严重程度取决于影响范围、业务损失和是否继续扩大，不取决于问题听起来有多“技术”。
## 可复查记录与无效记录的区别

正常记录会写：8 月 1 日起帮助目录点击下降；异常集中在无后缀 URL；GET 返回 404，而对应 `.html` 返回 200；同模板正常页不存在；修复服务器映射后先验证 200/404，再观察抓取和索引。

失败记录只写“疑似降权，建议增加原创内容”。它没有范围、时间、对照、证据和可证伪的假设。
## 最小 Runbook

1. 保存时间线、样本 URL、响应和当前配置；
2. 选正常与异常页面逐层比较；
3. 提出不超过三个主要假设；
4. 为每个假设指定能够证伪的证据；
5. 实施最小、可回滚的修复；
6. 分别验证用户访问、抓取、索引和业务结果。
## 从现象到回归的诊断树

收到“页面搜不到”时先确认具体 URL、目标查询、地区设备和发生时间。接着沿发现、抓取、渲染、索引、排序、展现逐层保存证据，前一层没有通过就先停止，不要直接修改标题或买外链。

| 层级 | 可观察证据 | 常见动作 |
| --- | --- | --- |
| 发现 | 内链、站点地图、历史入口 | 修孤立页和错误地图，不靠反复提交 URL |
| 抓取 | GET 响应、服务器日志、robots | 修状态、限流、超时和阻断规则 |
| 渲染 | 原始/渲染 HTML、资源错误 | 输出关键正文，修脚本与资源访问 |
| 索引 | 规范地址、重复、内容价值、平台报告 | 合并重复、纠正 noindex/canonical |
| 排序 | 查询意图、页面类型、竞争与链接 | 改页面承诺和内容，不保证位置 |
| 点击 | 展现、位置、标题和设备 | 在口径稳定后做展示实验 |

对于批量异常，用页面类型和模板抽样，不只检查首页。若某天开始大量详情页 404，优先查看路由或发布变更；若页面仍 200 但正文变成统一空壳，搜索系统可能把它视为 Soft 404 或低价值重复。

诊断记录必须区分事实、假设和缺口，并为每个动作写验证与回滚。修复后观察重新抓取和索引需要时间，不能一天内不断叠加变更。不存在真实替代内容的删除页保留 404/410，不要把所有地址跳到首页制造误导。
## 站点 P0-P3 排障报告

报告至少包含：

```text
业务目标与异常时间线｜样本选择方法与限制｜模板库存｜
正常/异常对照｜页面、Sitemap、robots 与日志证据｜
已确认问题 / 风险候选 / 无法检测｜影响 URL 与估算方式｜
根因聚类｜P0-P3｜负责人｜修改动作｜验证｜观察周期｜回滚
```

开发/运维负责状态、模板、日志和回滚；SEO 负责人负责抽样、索引关系和查询；内容负责人判断独立价值；数据负责人确认搜索数据口径；创业者决定 P0/P1 止损与资源。站点扫描不得未经控制地扩大抓取或携带用户凭据。

验收时随机抽三个候选问题，必须能说出样本范围、为何还不是全站事实、需要什么二次证据。页面内部修复与站外信任属于不同问题，不能混成一个笼统的“权重”概念。
