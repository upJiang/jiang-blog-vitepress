# 页面 SEO、TDK 与结构化数据

页面 SEO 的目标是让用户和搜索系统都能快速判断“这页解决什么问题、谁负责、证据在哪里、下一步是什么”。`title`、description、H1 和正文不是互相独立的填空题；它们共同表达页面职责。结构化数据也不是排名捷径，而是对可见内容的机器可读补充，不能标记页面没有展示的事实。

## 页面头部的责任

一个可维护的页面模板应由路由数据驱动生成元信息，同时允许编辑人员预览最终结果。不要从正文前 160 个字符机械截取 description，也不要让多个页面共享一个无差别标题。

```html
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>SSE 断线重放：事件序列与 Last-Event-ID | AI 全栈</title>
  <meta name="description" content="解释 SSE 事件序列、断线重放、背压和权限边界，并给出可验证的实现路径。">
  <link rel="canonical" href="https://example.com/docs/backend/node-realtime">
  <meta property="og:title" content="SSE 断线重放：事件序列与 Last-Event-ID">
  <meta property="og:type" content="article">
</head>
```

canonical 必须指向同内容的规范 URL，不要把所有页面都指到首页；Open Graph 服务于分享预览，不能代替 `<title>`；description 是搜索摘要候选，不保证原样展示。域名、语言和页面路径应由配置生成，避免预览环境地址进入生产页面。

## 标题层级和正文结构

一个页面通常只有一个表达主任务的 H1，H2/H3 表达可预测的子问题。标题不是为了堆词，而是让读者在目录和搜索结果中判断是否值得继续。高质量页面应先给结论和适用范围，再解释机制、边界、示例和验证；关键术语首次出现时给出定义，代码和图表必须有上下文。

```text
H1 主题与任务
  H2 适用范围与不适用范围
  H2 核心机制
    H3 数据或状态模型
    H3 失败路径
  H2 验证与观测
  H2 参考资料
```

不要用 CSS 字号代替语义层级，也不要让一个 H2 只包含一个没有解释的列表。页面内容需要能在关闭脚本、缩放文字和移动端窄屏时仍然可读。

## 索引控制的边界

公开页面通常使用可抓取链接和规范 URL；预览、内部搜索、登录后结果和没有独立价值的参数组合按需 `noindex`。不要用 robots 阻止爬虫后再期待它看到 noindex；不要为了让页面“看起来干净”把正文完全放进图片或脚本。

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
X-Robots-Tag: noindex
```

响应头的 `X-Robots-Tag` 适合非 HTML 资源或统一策略，实际页面仍要检查模板是否意外继承。索引资格、canonical 和 sitemap 必须形成同一套决策，不能一个说“主页面”，另一个却把参数页列入 sitemap。

## 结构化数据的正确姿势

优先使用 Schema.org 中与页面真实内容匹配的类型，例如 Article、BreadcrumbList、Product 或 SoftwareApplication。JSON-LD 只是表达格式，富结果是否展示由搜索引擎决定。字段必须来自页面可见事实，作者、日期、价格、评分和库存不能编造或过期。

```json
{
  "@context": "https://schema.org",
  "@type": "TechArticle",
  "headline": "SSE 断线重放：事件序列与 Last-Event-ID",
  "description": "解释事件序列和断线重放的工程边界。",
  "dateModified": "2026-08-04",
  "author": {
    "@type": "Person",
    "name": "AI 全栈"
  },
  "mainEntityOfPage": "https://example.com/docs/backend/node-realtime"
}
```

示例使用模拟站点和日期。生产模板应从文章元数据生成，并对 URL、日期格式、类型和必填字段做单元测试。禁止使用 `aggregateRating`、FAQ 或产品优惠来包装没有真实证据的页面。

## 作者、来源与责任链

技术文章需要让读者知道作者或维护主体、更新时间、适用版本和参考来源。引用规范、源码和实验结果时说明版本与访问日期；如果正文包含推断或模拟数据，要明确标注。AI 参与起草不改变发布者的事实核验责任，不能把模型署名当作专业责任主体。

## 页面验收矩阵

| 项目 | 验收问题 | 失败动作 |
| --- | --- | --- |
| 主任务 | 首屏能否说清用户要解决的问题 | 改标题、导语和结构 |
| TDK | title、description、H1 是否一致且唯一 | 修复模板或元数据 |
| 链接 | canonical、内链、sitemap 是否指向同一规范 URL | 统一 URL 规则 |
| 内容 | 结论、边界、代码、验证和来源是否完整 | 补证据或降低结论强度 |
| 结构化数据 | 标记内容是否在页面可见且能通过验证 | 删除不适用字段 |
| 可访问性 | 标题、链接、图片替代文本和键盘顺序是否合理 | 按 WCAG 语义修复 |

```bash
curl -sS https://example.com/docs/backend/node-realtime \
  | npx --yes structured-data-testing-tool --stdin
```

工具命令只是示例；自动化验证不能替代人工查看页面可见内容。发布前还要用移动端浏览器检查长标题、目录、代码块和跳转，避免元信息正确但页面实际不可用。

## 实施记录：从问题到动作

元信息和结构化数据应由同一份内容模型生成，避免编辑器、渲染器和 JSON-LD 各自维护事实。发布时校验主 URL、语言、日期、作者和可见正文；删除页面或字段后同时清理结构化标记、内链和缓存。

执行记录需要保留四类信息：基线快照、改动版本、观察条件和业务对账。基线至少包含 URL、模板、查询/搜索词、状态码、索引资格、事件口径和时间范围；改动要能定位到内容、路由、缓存、创意或出价的具体版本；观察条件要记录设备、地域、语言、模型或平台版本；业务对账要以服务端的资格、成交、退款和回款为准。这样在结果变差时可以回到上一个可用版本，而不是凭记忆争论。

## 故障演练与回滚

| 演练场景 | 预期信号 | 保护动作 | 恢复证据 |
| --- | --- | --- | --- |
| robots 或 WAF 误拦截 | 抓取 4xx 上升、核心 URL 失败 | 恢复规则并限制变更面 | GET、日志、覆盖报告 |
| 模板发布错误 | title/canonical/正文异常 | 回滚模板或内容版本 | 原始 HTML 对比 |
| 追踪重复或丢失 | 客户端与服务端数量不一致 | 停止自动化学习，修复去重 | 事件 ID 对账 |
| 业务质量下降 | 有效率、退款或毛利越过护栏 | 收紧查询/预算或下线页 | CRM/订单状态 |

演练使用模拟场景和最小流量，不改变真实生产预算或数据。回滚后再次检查公开页面、缓存、站点地图、广告参数、事件队列和业务状态；只有所有关键证据恢复，才允许继续实验。

## 结果判定与后续动作

把结论分为事实、假设和缺口。事实必须能由页面、日志、平台、实验或业务记录直接复核；假设写出可证伪的预测；缺口说明缺少哪项数据以及它会影响哪项判断。观察周期内不要连续叠加多个主变量，也不要把平台评分、平均排名或单次引用当作有效业务的替代。

```text
基线 -> 小范围变更 -> 技术验收 -> 搜索/广告观察 -> 业务对账 -> 继续、调整、合并或停止
```

## 操作清单与决策记录

模板和内容模型一起版本化，删除、改名和作者变更都要重新校验可见事实与结构化数据。

发布或投放前按顺序记录：

1. **范围**：目标用户、语言、地域、页面类型和明确不覆盖的需求。
2. **证据**：查询样本、页面版本、规范/源码/实验来源、数据时间和负责人。
3. **技术**：状态码、抓取规则、canonical、sitemap、内链、缓存、脚本失败和移动端表现。
4. **业务**：主转化、资格条件、去重键、成交/退款状态和归因窗口。
5. **保护**：预算或发布范围、护栏指标、观察周期、回滚版本和停止条件。

## 指标与停止条件

| 信号 | 可继续的证据 | 应暂停或回滚 |
| --- | --- | --- |
| 技术 | 公开 URL 状态稳定，规范页和索引目标一致 | 5xx、误拦截、canonical 冲突或空壳正文 |
| 搜索 | 相关查询、页面和点击方向一致 | 查询意图偏移、重复页面或无效展现激增 |
| 用户 | 到站后完成主要任务，错误反馈可解释 | 跳转、表单、脚本失败导致任务中断 |
| 业务 | 有效率、毛利和退款符合护栏 | 低质量线索、退款上升或归因无法对账 |

停止不是失败，而是保护样本和现金流的工程动作。停止后保留原始事件、页面快照和决策日志；需要恢复时先回到最后一个可验证版本，再单独改变一个变量。

```text
事实（页面/日志/业务记录） -> 假设（可证伪预测） -> 动作（单一变量） -> 观察（固定口径） -> 决策（继续/调整/停止）
```
