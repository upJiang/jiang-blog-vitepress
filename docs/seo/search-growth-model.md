# 搜索增长模型与 SEO 项目评估

SEO 不是“发文章以后等流量”，也不是把一个关键词重复塞进标题。它是一条从市场需求到有效业务的漏斗：用户提出问题，搜索引擎发现页面、抓取并建立索引，页面在某个查询下获得展示，用户点击进入站点，最终完成有价值的动作。任何一层断裂，下一层的报表都会被误读。例如页面已经被索引但没有匹配搜索意图，继续增加页面数量不会解决转化问题；广告有点击但没有有效线索，增加预算只会放大测量误差。

## 先定义业务结果和证据范围

开始一个 SEO 项目前，先把以下问题写成可检查的记录：服务对象是谁，覆盖哪个语言和地域，用户在什么场景搜索，站点希望用户完成什么动作，这个动作如何与订单、有效线索或留存关联。`page_view`、按钮点击和表单提交是行为事件，不天然等于收入；需要在 CRM 或订单系统中核对状态、退款和成交时间。

```text
目标：在 90 天内验证「问题型查询 -> 试用申请」是否存在可重复需求
核心转化：经过资格校验的申请，而不是任意表单提交
证据：搜索控制台查询/页面数据 + 服务端事件 + 业务系统状态
约束：不承诺排名，不把平台转化数直接当作收入
```

把“流量增长”改写成假设更可靠：如果为某一类明确意图建立能完整解决问题的页面，并且页面可抓取、可索引，那么该类查询的有效展示和到站率可能提高；如果到站后的资格通过率没有提高，问题在产品匹配或承诺兑现，而不是继续调关键词密度。每个假设都应该有时间范围、样本量、停止条件和负责人。

## 五层漏斗不要跨层诊断

```mermaid
flowchart LR
  D[搜索需求] --> P[页面与意图匹配]
  P --> C[发现/抓取/渲染]
  C --> I[索引与排序]
  I --> X[展示与点击]
  X --> L[到站行为]
  L --> B[有效业务结果]
```

建议把每层的事实、假设和缺口分开记录：

| 层级 | 可观察证据 | 常见误判 | 下一步验证 |
| --- | --- | --- | --- |
| 需求 | 查询词、趋势、访谈、站内搜索 | 搜索量大就等于愿意购买 | 看意图和业务相关性 |
| 页面 | 标题、正文、结构、内部链接 | 同一页面能覆盖所有意图 | 建立页面职责表 |
| 抓取 | HTTP 状态、robots、日志 | 能在浏览器打开就能被索引 | 用爬虫视角请求并看资源 |
| 索引 | URL 检查、规范页、覆盖报告 | 已抓取等于已收录 | 区分发现、抓取和索引 |
| 点击 | 展示、CTR、查询和页面 | CTR 低一定是标题差 | 对照排名、意图和 SERP 形态 |
| 业务 | 服务端事件、订单状态、毛利 | 平台转化就是成交 | 去重并回传最终状态 |

## 评估一个 SEO 项目是否值得做

可以使用六维评分，但分数只能帮助排序，不能替代证据：需求强度、业务匹配、竞争门槛、内容可交付性、技术可控性和回报周期。每项用 0 到 3 的整数记录证据来源；没有证据就记为“未知”，不要为了通过评审填高分。

```ts
type ProjectScore = {
  demand: 0 | 1 | 2 | 3
  businessFit: 0 | 1 | 2 | 3
  competition: 0 | 1 | 2 | 3
  delivery: 0 | 1 | 2 | 3
  technicalControl: 0 | 1 | 2 | 3
  payback: 0 | 1 | 2 | 3
}

function scoreProject(score: ProjectScore) {
  const values = Object.values(score)
  const unknown = values.filter((value) => value === 0).length
  return {
    total: values.reduce((sum, value) => sum + value, 0),
    unknown,
    needsExperiment: unknown > 1 || score.businessFit < 2
  }
}
```

“竞争”不能只看搜索结果数量。要抽样观察排名页面解决了什么问题、是否有一手数据、更新频率如何、页面速度和品牌信任是否形成门槛。结果页里大量是百科、论坛或厂商文档时，商业页面的转化路径可能并不适合直接竞争；应先选择更具体的任务型查询，做小规模反证实验。

## 经济模型必须保守

用模拟值表达计算方式，而不是伪造真实指标：

```text
有效业务价值 = 访问数 × 业务相关率 × 转化率 × 有效率 × 单次毛利
SEO 可承受成本 = 有效业务价值 - 内容与维护成本 - 归因误差预留
```

模型要包含成交延迟、重复线索、退款、品牌自然流量和跨渠道影响。SEO 的边际成本可能随内容规模下降，但维护和更新成本会累积；一篇排名页如果规则变化后仍然带来错误咨询，流量增长反而会降低有效率。为每个内容集设置“继续、改写、合并、下线”条件，比承诺一个固定流量目标更诚实。

## 一个可执行的验证周期

第一周完成需求访谈、查询聚类、竞争样本和基线数据；第二周建立页面映射和技术验收清单；第三至四周发布一组能互相引用的核心页面，记录版本、来源和更新时间；随后至少观察一个完整的抓取与转化周期。期间只改变一个主要变量，例如先修复索引，再测试标题，避免同时改 URL、内容和转化事件后无法归因。

验证不是“排名上升”这一项：技术层检查状态码、规范页、站点地图和渲染；搜索层观察被抓取 URL、索引覆盖、查询和 CTR；产品层观察首屏到关键动作的路径；业务层核对有效线索、订单、毛利和退款。任何一层数据缺失，都要在报告中标记为缺口。

## 常见失败方式

- 用固定字数、关键词密度或 AI 生成数量代替问题解决程度。
- 把搜索量、展现和点击混为一谈，跳过业务匹配与有效率。
- 没有发布前快照就批量改 URL，之后只能凭感觉判断下降原因。
- 同一意图创建多个近似页面，让内部页面互相竞争。
- 在没有追踪和停止条件时直接买广告，最后无法知道是需求、页面还是归因出错。

## 验证清单

1. 是否写明目标用户、市场、业务事件和归因限制？
2. 每个优先查询是否有页面职责、证据来源和更新责任人？
3. 是否把发现、抓取、渲染、索引、排名、点击和转化分开测量？
4. 是否建立了最小实验、观察周期、停止条件和回滚方案？

## 实施记录：从问题到动作

项目评估要把现金流、内容维护、销售承接和归因延迟一起纳入，而不是只计算预计访问。先选择一组能被证伪的查询和业务动作，设置最小样本、观察周期与停止条件；如果实验无法排除产品匹配或数据缺失，应先修正输入。

执行记录需要保留四类信息：基线快照、改动版本、观察条件和业务对账。基线至少包含 URL、模板、查询/搜索词、状态码、索引资格、事件口径和时间范围；改动要能定位到内容、路由、缓存、创意或出价的具体版本；观察条件要记录设备、地域、语言、模型或平台版本；业务对账要以服务端的资格、成交、退款和回款为准。这样在结果变差时可以回到上一个可用版本，而不是凭记忆争论。

## 故障演练与回滚

| 演练场景 | 预期信号 | 保护动作 | 恢复证据 |
| --- | --- | --- | --- |
| robots 或 WAF 误拦截 | 抓取 4xx 上升、核心 URL 失败 | 恢复规则并限制变更面 | GET、日志、覆盖报告 |
| 模板发布错误 | title/canonical/正文异常 | 回滚模板或内容版本 | 原始 HTML 对比 |
| 追踪重复或丢失 | 客户端与服务端数量不一致 | 停止自动化学习，修复去重 | 事件 ID 对账 |
| 业务质量下降 | 有效率、退款或毛利越过护栏 | 收紧查询/预算或下线页 | CRM/订单状态 |

演练使用模拟场景和最小流量，不改变真实生产预算或数据。回滚后再次检查公开页面、缓存、站点地图、广告参数、事件队列和业务状态；只有所有关键证据恢复，才允许继续实验。

## 结果判定与后续动作

把结论分为事实、假设和缺口。事实必须能由页面、日志、平台、实验或业务记录直接复核；假设写出可证伪的预测；缺口说明缺少哪项数据以及它会影响哪项判断。观察周期内不要连续叠加多个主变量，也不要把平台评分、平均排名或单次引用当作有效业务的替代。

```text
基线 -> 小范围变更 -> 技术验收 -> 搜索/广告观察 -> 业务对账 -> 继续、调整、合并或停止
```

## 操作清单与决策记录

从一组查询和一个业务事件开始，先做小样本反证，再决定是否扩大页面和预算。

发布或投放前按顺序记录：

1. **范围**：目标用户、语言、地域、页面类型和明确不覆盖的需求。
2. **证据**：查询样本、页面版本、规范/源码/实验来源、数据时间和负责人。
3. **技术**：状态码、抓取规则、canonical、sitemap、内链、缓存、脚本失败和移动端表现。
4. **业务**：主转化、资格条件、去重键、成交/退款状态和归因窗口。
5. **保护**：预算或发布范围、护栏指标、观察周期、回滚版本和停止条件。

## 指标与停止条件

| 信号 | 可继续的证据 | 应暂停或回滚 |
| --- | --- | --- |
| 技术 | 公开 URL 状态稳定，规范页和索引目标一致 | 5xx、误拦截、canonical 冲突或空壳正文 |
| 搜索 | 相关查询、页面和点击方向一致 | 查询意图偏移、重复页面或无效展现激增 |
| 用户 | 到站后完成主要任务，错误反馈可解释 | 跳转、表单、脚本失败导致任务中断 |
| 业务 | 有效率、毛利和退款符合护栏 | 低质量线索、退款上升或归因无法对账 |

停止不是失败，而是保护样本和现金流的工程动作。停止后保留原始事件、页面快照和决策日志；需要恢复时先回到最后一个可验证版本，再单独改变一个变量。

```text
事实（页面/日志/业务记录） -> 假设（可证伪预测） -> 动作（单一变量） -> 观察（固定口径） -> 决策（继续/调整/停止）
```
