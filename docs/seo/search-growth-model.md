# SEO、SEM、GEO 与搜索增长全景

**搜索增长**是让用户从提出需求开始，经由搜索结果或生成式回答找到网站，并最终完成有效业务动作的过程。SEO 负责改善自然搜索中的发现、理解和展示条件；本文语境下的 SEM 指付费搜索广告；GEO 关注内容能否被生成式搜索理解、核验和引用。三者都位于用户需求与站内转化之间，但介入方式不同。

假设你刚上线一个提供技术审计服务的网站。页面能打开，标题也写了“专业技术审计”，但一个月后几乎没有有效咨询。此时继续写文章、投搜索广告，还是优化页面让 AI 搜索引用，取决于链路究竟卡在哪一层。

下面建立一套可执行的诊断模型。遇到流量不足或转化不佳时，先检查对应证据，不把所有问题都归因于“权重低”，也不承诺无法验证的排名时间。

## 搜索增长的三类入口

同一个人想找“网站性能审计服务”，可能走三条路径：

1. 在搜索引擎输入问题，点击自然结果。
2. 点击带有“赞助”标记的搜索广告。
3. 向生成式搜索或 AI 助手提问，从回答中的引用进入网站。

对应的三类工作分别是：

| 渠道 | 全称 | 主要工作对象 | 是否直接购买展示机会 |
| --- | --- | --- | --- |
| SEO | Search Engine Optimization，搜索引擎优化 | 网站、页面、内容、技术可访问性和站外信号 | 否 |
| SEM | Search Engine Marketing，搜索引擎营销；本系列特指搜索广告 | 关键词、匹配、出价、创意、落地页和转化追踪 | 是 |
| GEO | Generative Engine Optimization，生成式引擎优化 | 可验证内容、实体关系、来源表达和机器可理解性 | 否，但结果不可承诺 |

三者不是三套互不相干的技巧。搜索广告里表现好的真实搜索词，可以帮助发现 SEO 页面需求；SEO 中解释清楚、可引用的内容，也更适合作为 GEO 的事实来源；无论哪条渠道，落地页和真实转化都要共用同一业务口径。

## SEO 的作用范围

SEO 的目标不是让爬虫“喜欢”网页，而是让搜索引擎能够发现、抓取、理解一张真正满足搜索需求的页面，并有足够理由在相关查询中展示它。

一张页面进入自然搜索结果，至少会经历：

```mermaid
flowchart LR
  A[市场需求] --> B[对应页面]
  B --> C[发现与抓取]
  C --> D[渲染与索引]
  D --> E[查询排序]
  E --> F[展示与点击]
  F --> G[站内转化]
```

每一层都可能失败。页面没有被索引，继续修改按钮颜色没有意义；页面有展现却没有点击，要检查标题和搜索意图；有点击没有有效咨询，则要回到页面任务、信任信息和业务承接能力。

### 一个容易混淆的例子

你发布了一篇“如何进行网站性能审计”的教程，但真正想获得的是企业客户的审计咨询。教程可能满足学习意图，服务页才承接购买意图。如果所有关键词都塞进同一页面，页面既不像完整教程，也不像能让客户做决策的服务页。

SEO 的第一步通常不是增加关键词密度，而是弄清用户问题应该由哪种页面回答：教程、产品页、服务页、案例页、工具页还是专题页。

## SEM 的即时流量与验证作用

搜索广告允许广告主针对查询参与竞价。用户搜索时，平台综合出价、广告质量、预期影响和竞争环境决定是否展示以及展示位置。广告主通常为点击或约定的结果付费。

它“快”的地方是可以较快获得展示、点击和搜索词数据，不代表可以跳过需求与页面。一个错误的关键词会更快消耗预算，一个不匹配的落地页会更快证明用户不愿转化。

一次 SEM 链路可以拆成：

```text
用户查询 -> 关键词匹配 -> 广告竞价 -> 创意展示 -> 点击
         -> 落地页 -> 平台转化 -> 有效线索/订单 -> 收入与毛利
```

“平台转化”与“有效业务”要分开。按钮点击、表单提交或拨号可能被平台记录为转化，但它们不自动等于有效客户。若自动出价只看到容易触发的中间事件，系统可能越来越擅长买到低价值流量。

### 先算清一笔最小账

假设模拟周期内发生：

| 数据 | 数值 |
| --- | ---: |
| 展示 | 1,000 |
| 点击 | 50 |
| 广告成本 | 500 元 |
| 平台表单 | 10 |
| 经人工确认的有效咨询 | 4 |
| 最终成交 | 1 |

那么点击率是 `50 / 1000 = 5%`，平均点击成本是 `500 / 50 = 10 元`。**CPA（Cost per Acquisition/Action，每次获客或行动成本）** 按“成本 / 对应结果数”计算：按平台表单计算是 50 元，按有效咨询计算则是 125 元。

两个 CPA 都能正确计算，却回答不同问题。优化广告账户时，如果只报告 50 元，就隐藏了线索质量。是否赚钱还需要订单收入、退款、交付成本和毛利，不能看到一笔成交就直接宣称广告有效。

## GEO 的作用与证据边界

生成式搜索会把多个来源的信息组织成回答，有时附带引用。GEO 关注的是：当系统需要回答一个主题时，你的内容是否容易被识别、核实、抽取和正确引用。

它通常需要：

- 页面明确回答一个具体问题，而不是堆积空泛观点。
- 结论有来源、作者责任、更新时间和适用条件。
- 名称、实体、属性和上下文表达一致。
- 页面允许相应系统访问，并能稳定渲染核心内容。
- 原创数据或方法能够被第三方核对。

这些工作与高质量 SEO 内容高度重合，但 GEO 不是“在文章里多写几个问答”或“批量生成内容”。外部系统如何选择和引用来源不由站长控制，任何“保证被 AI 推荐”的承诺都缺乏可验证依据。

## 搜索增长漏斗的分层诊断

把搜索增长理解成一条从“有人产生需求”到“公司获得收入”的流水线。拆成下面十二层后，从左到右检查，哪一层没有证据或没有结果，就先解决哪一层：

```text
市场需求 -> 关键词与页面 -> 发现 -> 抓取 -> 渲染 -> 索引
-> 查询排名 -> 搜索展示 -> 点击 -> 到站行为 -> 有效业务 -> 收入
```

这条漏斗最重要的用法，是避免跳过前面的条件去猜后面的问题。例如，页面还没有被搜索引擎收录，当然不会有展示和点击；网站已经获得点击却没有有效咨询，才应该继续检查页面承接与销售转化。

### 没有自然点击：先查展示、收录和抓取

按“展示 → 收录 → 抓取”的顺序倒查：

1. 有展示但没有点击，检查标题、摘要和排名是否匹配用户的搜索意图。
2. 没有展示，先在搜索平台检查 URL 是否已经被收录。
3. 没有收录，再查搜索引擎是否抓取过页面，以及内部链接、Sitemap、robots 和 HTTP 响应是否阻止了抓取。

不能因为“点击为零”就直接断定标题不吸引人。没有展示时，用户根本没有看到标题；没有收录时，页面甚至还没有进入参与搜索展示的候选集合。

### 广告转化很多：先确认是不是真客户

“平台转化”可能只是按钮点击、表单提交或拨号，并不自动等于有效客户。先逐条核对转化定义、重复上报、无效线索和销售结果，再确认广告点击能否通过点击 ID 或 UTM 参数关联到 CRM 中的客户与订单。然后拆分品牌词、非品牌词、真实搜索词和落地页，找出是哪一类流量带来了无效转化。此时直接提高预算，只会把错误信号放大。

### AI 没引用网站：先检查内容是否值得引用

先确认页面是否允许访问、核心答案能否被单独读懂、结论有没有原始证据，以及内容是否提供了现有来源没有的信息。修好这些基础条件，只能增加内容被理解和引用的可能性，不能保证某个 AI 一定引用网站。没有平台级引用数据时，把“没有被引用”记录为待验证问题，不能用一次人工提问代表整体表现。

## 用一张诊断表找到当前问题

下面用“技术审计服务”做一张最小诊断表。每一行代表漏斗的一层；第二列说明要回答什么，第三列说明去哪里找证据，第四列才写当前结论。这里的数据全部是教学用模拟值，不代表真实项目：

| 层级 | 要回答的问题 | 证据来源 | 当前判断 |
| --- | --- | --- | --- |
| 需求 | 用户会怎样描述问题 | 客户访谈、搜索词、销售记录 | 待收集真实问法 |
| 页面 | 哪张页面负责回答 | URL 清单、页面模板 | 教程与服务页需分开 |
| 抓取 | 搜索引擎能否获得页面 | GET 响应、robots、日志 | 需要实际检查 |
| 索引 | 页面是否进入索引 | 搜索平台 URL 检查 | 当前无数据 |
| 展示 | 哪些查询产生曝光 | 搜索表现报表 | 当前无数据 |
| 点击 | 标题是否匹配意图 | CTR、查询与页面 | 需有展示后判断 |
| 转化 | 用户是否完成咨询 | 站内事件 | 只能作为中间信号 |
| 业务 | 咨询是否有效 | CRM 或人工确认 | 核心结果 |
| 收入 | 是否产生可持续价值 | 订单、退款、毛利 | 最终业务约束 |

表里允许写“无数据”。数据缺口本身就是结论，它能阻止团队在证据不足时编造原因。

## 网站搜索基础的五项检查

这五步有明确的先后关系：先确认客户在问什么，再决定用哪张页面回答；页面能被搜索引擎访问后，才有资格讨论流量；获得流量后，还要连接到客户和收入；最后通过单变量实验持续改进。前一步的产物，就是后一步的输入。

| 步骤 | 要解决的问题 | 本步产物 |
| --- | --- | --- |
| 1. 收集真实问题 | 客户到底会搜索什么 | 客户问题清单 |
| 2. 指定承接页面 | 哪张页面负责回答 | 问题与页面映射表 |
| 3. 检查搜索可访问性 | 搜索引擎能否取得并理解页面 | 技术检查记录 |
| 4. 连接业务结果 | 搜索流量有没有带来有效客户 | 搜索到收入的数据链 |
| 5. 记录单变量实验 | 哪项修改真正产生了效果 | 可复查的优化记录 |

### 第一步：收集客户真实会搜索的问题

::: tip 本步目标
把团队听到的客户原话，整理成一份有来源、有场景、可以继续验证的问题清单。
:::

先看一个具体例子。客户说“网站打开特别慢，怎么知道卡在哪里”，这句话同时包含问题、使用场景和期望结果。若团队直接把它改成“Core Web Vitals 优化”，虽然更专业，却丢掉了客户真正会使用的表达。

#### 从哪里收集

优先从已经发生的业务接触中找问题：

1. 销售咨询：客户购买前反复追问什么，因为什么迟迟没有决定。
2. 客服和工单：客户在使用中遇到什么故障，用什么语言描述。
3. 站内搜索：访问者进入网站后仍然在找什么。
4. 广告搜索词：用户实际输入了什么，而不是账户里设置了什么关键词。
5. 客户访谈和社群讨论：客户如何比较方案、评价风险和描述结果。

没有这些数据时，先访谈少量真实目标客户，并明确记录“尚无搜索平台数据”。不要用团队头脑风暴冒充客户证据。

#### 怎样整理

每条问题至少记录以下字段：

| 字段 | 记录什么 | 示例（教学用） |
| --- | --- | --- |
| 客户原话 | 不改写的完整表达 | 网站打开慢怎么查 |
| 发生场景 | 购买前、比较中、使用中或故障中 | 故障排查 |
| 来源 | 销售、客服、站内搜索、广告搜索词或访谈 | 客服工单 |
| 出现时间 | 证据来自哪个周期 | 最近一个完整业务周期 |
| 业务价值 | 了解问题、比较方案、准备购买或售后支持 | 可能需要审计服务 |
| 数据缺口 | 当前还缺什么证据 | 尚无搜索展示数据 |

表达不同但任务相同的问题可以先归为一组，同时保留原话。例如“网站加载慢怎么查”和“首页为什么一直转圈”可能都属于性能排查；“网站性能审计多少钱”已经进入购买比较，应单独保留。

#### 做到什么算完成

- 每条重点问题都有真实来源，而不是只来自关键词工具。
- 原始说法、发生场景和业务价值都已记录。
- 团队知道哪些是事实，哪些只是待验证猜测。
- 能选出一批最值得先回答的问题，进入第二步。

### 第二步：让每类问题由一张合适页面回答

::: tip 本步目标
让每一类重要问题都有明确的承接页面，并规定页面回答什么、引导用户做什么。
:::

仍以网站性能为例。“网站打开慢怎么查”适合由教程或诊断工具回答；“网站性能审计多少钱”更适合由服务页回答。把两种需求强塞进同一页面，通常会让教程不够完整，服务信息也不够直接。

#### 先判断用户要完成什么任务

可以先用四类任务做初步判断：

| 用户任务 | 用户想得到什么 | 常见页面类型 | 合适的下一步 |
| --- | --- | --- | --- |
| 了解 | 弄懂概念或原因 | 指南、解释页 | 阅读相关方法 |
| 操作 | 按步骤解决问题 | 教程、工具页 | 使用工具或检查清单 |
| 比较 | 判断不同方案是否适合 | 对比页、案例页 | 查看价格、能力和案例 |
| 购买 | 找到可交付的产品或服务 | 产品页、服务页 | 试用、询价或提交需求 |

#### 建立问题与页面映射

为每组问题记录目标页面、页面状态和下一步动作。下面是教学示例：

| 客户问题 | 用户任务 | 承接页面 | 页面状态 | 下一步动作 |
| --- | --- | --- | --- | --- |
| 网站打开慢怎么查 | 操作 | `/guide/site-speed-audit` | 需要新建 | 查看诊断步骤 |
| LCP 过高怎么处理 | 操作 | `/guide/lcp-optimization` | 已有页面待补充 | 查看开发优化方案 |
| 网站性能审计多少钱 | 购买 | `/services/site-audit` | 已有页面 | 提交审计需求 |

具体执行时按下面的顺序判断：

1. 先找网站是否已有合适页面，不要看到一个问题就新建 URL。
2. 已有页面能完整回答，就更新原页面；页面任务重复，就考虑合并。
3. 确实没有承接页面，再决定新建教程、产品页、服务页、案例页或工具页。
4. 为页面规定一个主要任务和一个主要下一步动作。
5. 将目标页面加入相关导航、专题页或正文内链，让用户和搜索引擎都能发现。

#### 做到什么算完成

- 每个高优先级问题都有唯一的主要承接页面。
- 页面类型与用户任务匹配，学习需求和购买需求没有被强行混在一起。
- 已明确页面是保留、更新、新建还是合并。
- 每张页面都有自然的下一步，而不是所有页面都只放“联系我们”。

### 第三步：确认搜索引擎能访问并读懂页面

::: tip 本步目标
证明目标页面能够被公开访问、允许抓取，并向搜索引擎提供稳定且一致的主要内容。
:::

先选代表页面，不必一开始就抓完整个网站。小型网站至少检查首页、核心产品或服务页、代表性内容页和最近发布页；页面模板很多时，每种模板都选正常、空数据和边界状态样本。

#### 按五层顺序检查

| 检查层 | 要回答的问题 | 主要证据 |
| --- | --- | --- |
| 可访问 | 匿名用户能否正常取得页面 | 最终 URL、HTTP 状态码、跳转链、响应头 |
| 可发现 | 搜索引擎从哪里知道这个 URL | 内部链接、Sitemap、外部链接 |
| 可抓取 | 搜索爬虫是否被允许请求页面 | `robots.txt`、访问控制、WAF/CDN 响应、服务器日志 |
| 可索引 | 页面是否允许进入索引且规范信号一致 | Meta Robots、`X-Robots-Tag`、Canonical、搜索平台 URL 检查 |
| 可理解 | 核心主题和正文是否稳定可读 | Title、H1、原始 HTML、渲染后 DOM、结构化数据 |

具体检查顺序如下：

1. 在退出登录或无 Cookie 的环境中请求页面，记录完整跳转链和最终状态码。应公开的正式页面通常应稳定返回 `200`。
2. 从首页、栏目页或相关文章实际点击目标链接，并检查 Sitemap，确认搜索引擎有稳定入口发现 URL。
3. 查看 `robots.txt`、访问控制和 WAF/CDN 返回内容，确认爬虫请求没有被禁止、重定向到登录页或替换成挑战页。
4. 查看 Meta Robots、`X-Robots-Tag` 和 Canonical，确认索引指令符合页面目标。登录后台允许 `noindex`，公开服务页意外出现 `noindex` 才是问题。
5. 对比原始 HTML 和 JavaScript 渲染后的 DOM。若 Title、H1 或核心正文只在接口成功后出现，要继续检查脚本失败时搜索系统能拿到什么。
6. 最后查看搜索平台的 URL 检查、索引状态和搜索表现数据。页面工具只能证明页面侧信号，不代表搜索引擎已经收录。

#### 记录结论时不要只写“通过”

一条可复查记录至少包含：检查 URL、检查时间、匿名或登录状态、观察到的值、预期值、证据截图或响应摘要、影响范围和复查方法。这样开发修复后，另一位同事能够用同样条件复验。

浏览器扩展或审计工具可以收集证据，但工具分数不是搜索引擎评分。每条问题都要展示检测依据、影响范围和复查方法。

#### 做到什么算完成

- 应公开的页面能匿名访问，并记录了最终状态与跳转链。
- 抓取、索引、Canonical 和 Sitemap 信号与页面任务一致。
- 原始 HTML 与渲染页面的核心主题没有冲突或缺失。
- 搜索平台状态与页面侧证据分开记录，没有把“可索引”写成“已收录”。

### 第四步：把搜索数据连接到客户和收入

::: tip 本步目标
把“搜索带来一次访问”连接到“这次访问是否产生有效客户、订单和收入”。
:::

网站有 100 次点击，不代表获得了 100 个客户。数据需要跨过四个系统层级：

| 数据层 | 至少记录什么 | 回答什么问题 |
| --- | --- | --- |
| 搜索平台 | 查询、页面、展示、点击、日期、品牌分类 | 用户从哪里看到并点击网站 |
| 广告平台 | 成本、搜索词、匹配方式、系列、创意、落地页 | 预算买到了什么流量 |
| 网站分析 | 落地页、会话、关键事件、来源参数 | 用户到站后做了什么 |
| CRM / 订单 | 线索 ID、有效状态、订单、退款、毛利 | 流量是否产生真实业务价值 |

#### 先统一“转化”定义

把转化分成两类：

- 观察转化：浏览价格、点击咨询按钮、开始填表，用来理解行为。
- 主要转化：有效咨询、完成试用激活、支付或其他接近业务结果的动作，用来评估渠道。

若把按钮点击设为主要转化，广告系统可能越来越擅长购买“愿意点按钮”的人，却没有学到谁会成为客户。

#### 建立可追踪的数据链

1. 访问发生时记录搜索页面、落地页、UTM 渠道参数或平台点击 ID。
2. 用户提交表单或注册时，生成内部 `lead_id`，并把允许保存的来源信息与该 ID 关联。
3. 销售在 CRM 中更新有效、无效、成交、退款等状态，不覆盖原始来源。
4. 用 `lead_id` 或 `order_id` 连接访问、客户和订单；邮箱、电话等个人信息不要放进 URL 或分析参数。
5. 数据条件允许时，把有效线索或成交结果回传广告平台，让自动出价学习更接近业务价值的信号。
6. 报表同时展示成本、平台转化、有效客户、订单和毛利，避免只展示最好看的一个数字。

前文示例中，500 元广告成本带来 10 个表单、4 个有效咨询和 1 笔成交。因此表单 CPA 是 50 元，有效咨询 CPA 是 125 元。两个数字都可以保留，但报表必须写清分母，不能把表单成本当成真实获客成本。

关联不上时，应降低结论置信度，而不是把全部收入按最后一次点击强行分配。

#### 做到什么算完成

- 平台转化、有效客户和订单使用不同字段，不再混为一个“转化数”。
- 抽查一批近期线索时，能够从业务结果追溯到来源和落地页。
- 无法关联的订单被标记为未知来源，而不是强行归给最后一次点击。
- 报表能同时回答“有多少流量”“有多少有效客户”和“是否赚钱”。

### 第五步：每次只改一个重点并记录结果

::: tip 本步目标
让每次优化都能回答三个问题：为什么改、改了什么、结果是否支持原来的判断。
:::

假设一张服务页没有咨询。如果团队同时改 Title、重写正文、调整价格、提高广告预算并更换转化目标，即使咨询增加，也无法知道是哪项修改起作用。下一次遇到相同问题，团队仍然只能靠猜。

#### 每次优化先写一条实验记录

| 字段 | 应记录什么 | 示例（教学用） |
| --- | --- | --- |
| 问题与证据 | 当前观察到什么 | 有展示，非品牌 CTR 持续偏低 |
| 假设 | 为什么可能发生 | Title 没有说明页面解决的问题 |
| 本次变量 | 这次只改什么 | 重写 Title |
| 保持不变 | 哪些内容暂时不动 | 正文、价格、广告预算 |
| 基线 | 修改前的数据口径 | 同查询、页面、设备和周期的展示与点击 |
| 观察条件 | 什么时候再判断 | 页面重新抓取且获得足够可比较展示后 |
| 成功标准 | 什么结果支持假设 | 目标查询更匹配，CTR 改善且有效咨询未下降 |
| 停止或回滚条件 | 什么情况立即处理 | 排名、有效咨询或页面功能明显异常 |

#### SEO 和 SEM 的等待条件不同

- SEO 修改后，先确认搜索引擎重新抓取并识别了新版本，再比较查询、展示、点击和业务结果。固定等待七天或十四天没有普适意义，抓取频率和流量规模不同。
- SEM 修改预算、出价策略或主要转化后，要考虑平台学习状态和业务转化延迟。频繁改动会让前后数据失去可比性。
- 页面故障、追踪中断或成本突然失控属于保护性问题，应立即暂停或回滚，不需要等待实验周期结束。

#### 每次复盘只得出证据允许的结论

结果改善时，记录“现有数据支持该假设”，不要写成“已经证明这是唯一原因”。结果没有改善，也不等于 SEO 或 SEM 整体无效，只能说明本次变量在当前条件下没有得到支持。样本不足时继续观察，并明确记录数据缺口。

#### 做到什么算完成

- 每次修改都有日期、负责人、基线、主要变量和影响范围。
- 判断窗口同时考虑重新抓取、平台学习期和业务转化延迟。
- 团队知道何时继续观察、何时停止、何时立即回滚。
- 下一位执行者能够复现本次判断，而不是只看到“已优化”三个字。

## SEO、SEM 和 GEO 怎样协同

可以用一个循环把三者连接起来：

1. SEM 小范围验证真实查询和落地页匹配，但不把短期点击当作需求真相。
2. 将反复出现且有业务价值的问题沉淀为 SEO 页面。
3. 页面使用可验证事实、清晰结构和原始证据，提高搜索和生成式系统理解的可能性。
4. SEO 页面获得的查询和站内行为继续修正广告关键词与创意。
5. 三个渠道最终都回到有效业务和收入，而不是各自汇报漂亮的中间指标。

品牌流量要单独看。用户已经知道品牌后再点击广告，平台可能获得一次转化，但不代表广告创造了全部需求。必要时通过地域、时间或受控停投实验估计增量价值。

## 小团队怎样分工

创业早期可以一人兼任多个角色，但不能把职责混成一句“让运营去做 SEO”。同一条增长漏斗至少有五类责任：

| 角色 | 对这张漏斗负责什么 | 不应单独决定什么 |
| --- | --- | --- |
| 创业者 | 产品定位、毛利、核心转化、资源上限和停止条件 | 不能只按流量给团队下目标 |
| SEO / 内容 | 需求研究、页面职责、内容证据、内链和搜索表现 | 不能绕过开发承诺技术结果 |
| 开发 / 运维 | 状态码、渲染、性能、发布、日志和回滚 | 不能只因工具提示批量开放索引 |
| SEM 投手 | 搜索词、匹配、创意、出价、预算和学习期 | 不能把平台转化定义成最终业务成功 |
| 数据负责人 | 事件口径、归因键、有效线索、退款和毛利 | 不能在关联缺失时强行给渠道分收入 |

人员可以重叠，证据责任不能消失。比如创业者亲自投广告，也要把“平台表单”和“有效咨询”分开；开发者同时写内容，也要让业务负责人确认页面是否应该索引。

## 搜索增长诊断表

将下面字段放进表格或项目文档，每个层级占一行：

```text
漏斗层级｜目标结果｜当前数值｜证据来源｜数据日期｜
已确认事实｜待验证假设｜数据缺口｜负责人｜下一步动作
```

先填“需求、页面、抓取、索引、展示、点击、有效业务、收入”八行。无法填写的地方保留为空并写明补证方式。这张表中的产品、需求、毛利和数据缺口，是后续判断项目是否值得投入 SEO 的依据。

## 带到工作中的搜索增长检查表

- 我们解决的是需求、抓取、索引、排名、点击还是转化问题？
- 每个重要查询是否有职责明确的页面？
- 页面是否通过真实 GET 返回正确状态和核心内容？
- 搜索数据是否区分品牌与非品牌？
- 平台转化是否与有效业务结果核对？
- SEO、SEM、GEO 是否使用同一页面任务和业务口径？
- 当前结论是事实、可验证假设还是数据缺口？
- 本次修改改变了几个主要变量，如何判断成功或回滚？

## 证据复核：SEO、SEM、GEO 与搜索增长全景
SEO 结论要放回“需求、抓取、渲染、索引、排名、点击、转化”这条漏斗定位。页面源代码、渲染 DOM、响应头、搜索平台、分析数据和业务结果各自只能证明一段事实，不能用单页审计分数推断收录、排名或收入。

执行前固定页面类型、目标查询、地区语言、Canonical、观察窗口和成功指标。修复后使用同一 URL 集、同一设备条件与同一数据口径复验，并保留发布日期、抓取状态、展示点击、转化延迟和回滚方案。无法取得的数据明确标为检测边界。

SEM 与自然搜索共享意图和落地页证据，预算、匹配方式和归因仍有独立语义。广告短期结果可以帮助发现搜索词和页面问题，不能直接替代 SEO 长周期判断；自动建议先进入候选列表，再由人工核对业务边界。
