# 技术 SEO 与网站性能怎样一起检查

一篇文章在桌面开发机打开很快，移动网络却先显示空白，几秒后正文和主图一起跳出来。页面最终“能看见”，不代表用户和搜索引擎能稳定、及时地得到主要内容。

技术 SEO 关注页面能否访问、渲染、索引和保持唯一身份；性能关注内容出现速度、交互响应和布局稳定。两者共享服务器、HTML、脚本和媒体这条交付链。

## 先从一次页面加载看全流程

```mermaid
flowchart LR
  A[请求 URL] --> B[服务器响应]
  B --> C[解析 HTML]
  C --> D[发现 CSS/脚本/图片]
  D --> E[渲染主要内容]
  E --> F[用户交互]
```

如果 URL 返回 404，应先修服务器映射；如果 HTML 没有正文，应检查渲染策略；如果正文已有但主图很晚发现，再调整资源优先级。按层处理比一次安装多个“优化插件”更容易验证。

## 第一步：保存四份基线证据

对一个代表页面记录真实 GET 响应、原始 HTML、完整浏览器结果和移动网络性能数据。再选一个正常页面作对照。

原始 HTML 应包含主标题、核心正文和重要链接。现代搜索系统可以处理 JavaScript，但复杂脚本、接口失败和资源阻塞会增加延迟与不确定性。公开内容不应依赖登录状态或浏览器存储才出现。

## 第二步：理解三个核心网页指标

| 指标 | 观察什么 | 常见问题 |
| --- | --- | --- |
| LCP | 主要内容何时出现 | 主图晚发现、服务器慢、CSS 阻塞 |
| INP | 交互后的响应延迟 | 长任务、脚本过多、主线程繁忙 |
| CLS | 页面是否意外移动 | 图片无尺寸、字体或组件晚插入 |

实验室数据适合定位，真实用户数据反映实际设备与网络。一次 Lighthouse 分数不是长期业务表现，也不能替代抓取和索引检查。

## 第三步：逐类处理资源

先减少不必要的第三方脚本和首屏 JavaScript，再考虑拆包。服务端缓存和 CDN 可以缩短资源传输，但要明确缓存键、更新和失效策略，避免用户长期看到旧内容。

图片按实际显示尺寸提供候选资源，声明宽高。首屏主图与屏外图片使用不同加载优先级。字体控制字重和子集，避免下载大量不会使用的文件。

优化动作要对应瓶颈。压缩图片不会修复 API 500，代码分割也不会修复错误 canonical。

## 第四步：验证脚本失败后的页面

禁用 JavaScript 或阻断一个非关键脚本，检查标题、正文、导航和链接是否仍然可用。交互功能可以降级，但核心信息不应变成空白。

再检查移动端按钮、表格和代码块是否溢出，键盘焦点是否可见，错误页是否返回真实状态。性能和可访问性问题往往共同影响实际使用。

## 正常结果和失败结果

正常结果会记录：GET 200；原始 HTML 有正文；移动数据中 LCP 元素是主图；主图由脚本晚插入。修改为 HTML 直接声明并设置合适优先级后，再比较同一环境的数据。

失败结果只写“Lighthouse 82 分，需要压缩全部资源”。它没有页面、设备、瓶颈元素和前后对照，也无法判断修改是否有效。

## 一次只改一个主要假设

建立变更记录：观察事实、假设、修改、保护指标、验证环境和回滚。缓存、渲染和媒体同时大改后，即使分数提高，也难以知道哪个动作有效，索引异常时也更难回退。

下一篇会把这些证据放入完整故障树，处理页面不收录和排名下降。
