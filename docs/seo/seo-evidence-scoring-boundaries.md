# SEO 诊断的证据、评分与边界

一次页面审计给出 62 分，并提示“缺少作者”和“LCP 较慢”。团队随即暂停内容计划，要求开发先把分数做到 90。这个动作看似重视 SEO，却可能把三个不同问题混在一起：工具能否测到、规则是否适用于当前页面、问题是否真的阻断业务。

一张登录后的账户页没有作者信息很正常；一次本地 LCP 样本不能代表全部真实用户；但一张本应获客的页面若明确输出 `noindex`，确实可能直接阻止索引。分数只有连同适用范围、证据和严重度一起阅读才有意义。

[项目评估卡](/docs/seo/seo-project-evaluation)给出业务目标、风险假设和停止条件。诊断系统把这些内容转成统一语言：证据、状态、覆盖率、置信度、优先级、验证和回滚。

```mermaid
flowchart LR
  A[页面与请求样本] --> B[适用规则]
  B --> C[已测证据]
  C --> D{覆盖与置信度}
  D -->|足够| E[事实或已确认问题]
  D -->|不足| F[风险候选或检测边界]
  E --> G[修复 验证 回滚]
```

评分只处理已经定义且有证据的规则。没有样本、没有后台权限或规则不适用时，应保留缺口，不把空白换算成失败分数。

## Evidence 的定义与可复查性

**Evidence（证据）** 是能够支持或推翻一个结论的可复查记录。SEO 证据至少要回答：检查了什么对象、在什么时间和环境检查、观察到什么、证据覆盖多大范围、别人怎样重复检查。

同一句“页面可以访问”，证据强度可能完全不同：

| 表达 | 实际能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 我的浏览器能打开 | 当前设备和登录状态下可见 | 匿名用户、搜索爬虫也能打开 |
| 匿名 GET 返回 200 和正文 | 公开请求获得正常响应 | 页面已被真实爬虫访问或索引 |
| 服务器日志出现疑似 Googlebot | 某个自报 User-Agent 的请求访问过 | 请求一定来自 Google |
| 搜索平台 URL 检查显示已索引 | 平台对该 URL 的当前判断 | 所有查询都有排名或会产生转化 |
| 查询报表产生展现 | 页面曾进入相关搜索结果 | 页面满足业务目标 |

证据不是越多越好，而是要与结论同一层。页面 HTML 适合判断 Title 是否存在，不能判断客户是否有效；CRM 能确认客户质量，不能解释搜索爬虫为何拿到 500。

## 事实、假设与数据缺口

### 事实

事实是当前证据直接确认的状态。例如：“2026-08-11 以匿名 GET 请求该 URL，最终返回 200；原始 HTML 有一个 Title，没有 H1。”事实应允许另一位执行者复现。

### 假设

假设是能够解释现象、但还缺少关键证据的原因。例如：“核心正文只在 JavaScript 接口成功后出现，可能导致部分渲染失败。”验证方式应写成比较原始 HTML、渲染 DOM、资源错误和搜索平台抓取结果。

### 数据缺口

数据缺口不是失败，而是“当前无法回答什么”。没有服务器日志时，不能确认真实抓取频率；没有业务结果时，不能计算有效 CPA；没有足够真实用户样本时，不能下全站 Core Web Vitals 结论。

优秀的审计允许出现“不知道”，同时写清补证据的方法。最危险的报告反而是每一项都有确定答案，却不说明数据从哪里来。

## 六种诊断状态的适用条件

一个可解释的审计至少要区分六种状态：

| 状态 | 英文 | 含义 | 示例 |
| --- | --- | --- | --- |
| 通过 | Pass | 当前规则适用且证据满足要求 | 应索引页匿名 GET 返回 200 |
| 警告 | Warning | 存在风险或需要改善，但不是确定阻断 | 单次 LCP 处于需改善区间 |
| 失败 | Failure | 规则适用且发现明确冲突 | 应索引页存在 `noindex` |
| 信息 | Informational | 记录事实，但没有好坏结论 | 页面目标尚未确认时返回 302 |
| 不可测 | Not Measurable | 工具或数据无法可靠获得证据 | 扩展无法读取证书链和 TLS 等级 |
| 不适用 | Not Applicable | 规则与当前页面任务无关 | 无视频页面不检查视频字幕 |

**Not Measurable（不可测）** 描述检测能力，**Not Applicable（不适用）** 描述规则适用性。把二者都记为失败，会让无法测量的网站分数天然更低；把二者都当通过，又会隐藏真实数据缺口。

还有一种常见误用：工具看到页面有 `noindex` 就直接报 P0。若页面本来是登录后台，`noindex` 可能完全正确。必须先输入 **Expected Index State（预期索引状态）**：应索引、不应索引或未知，规则才能判断业务目标和页面信号是否冲突。

## 规则归一化与分数计算

假设一次审计有三条适用且可测规则：

| 规则 | 满分 | 状态 | 得分比例 | 实得分 |
| --- | ---: | --- | ---: | ---: |
| 索引指令 | 8 | 通过 | 100% | 8 |
| Title | 8 | 警告 | 50% | 4 |
| LCP | 3 | 失败 | 0% | 0 |

分数按可测规则归一化：

```text
SEO 基础分 = 实得分之和 / 当前适用且可测的满分之和 x 100
            = (8 + 4 + 0) / (8 + 8 + 3) x 100
            = 63.2，取整后约 63 分
```

若另一条 INP 因没有交互样本而不可测，它退出评分的分子和分母，不能按零分计算。这样得到的是“当前证据下的页面基础分”，不是搜索引擎对网站的内部评分。不可测仍会降低下方的覆盖率，用来暴露证据缺口。

### Coverage 为什么必须和分数一起看

**Coverage（证据覆盖率）** 表示本次适用的计分规则中，有多少真正获得了有效测量：

```text
覆盖率 = 已测规则数 / 适用计分规则数 x 100%
```

如果 20 条适用规则只拿到 8 条证据，覆盖率是 40%。此时即使已测部分得到 95 分，标签也应显示“证据不足”。高分低覆盖的正确动作是补采样，不是宣布优化完成。不适用规则不进入分母；不可测规则属于本应测量但暂时缺证据，因此保留在覆盖率分母中。

覆盖率也不能跨范围偷换。检查 20 个代表页面，可以描述“样本中的模板问题”，不能写“全站没有重复页面”。页面级、站点样本、搜索表现和业务结果要分别标记作用范围。

## 严重问题的分数封顶

普通加权可能产生反直觉结果：一个页面图片、标题、链接都很好，但模板错误输出 `noindex`，加权后仍可能得到 80 分。为防止总分掩盖阻断，一些审计会设置 **Score Cap（分数上限）**：

- P0 索引阻断可把总分封顶在 39。
- P1 高风险索引问题可把总分封顶在 69。

封顶不是搜索引擎算法，只是任务排序保护。它表达“先解除阻断，再讨论增长优化”。原始加权分、封顶后的展示分和触发封顶的规则应同时展示，否则读者无法理解分数变化。

## Confidence 与结论可信度

**Confidence（置信度）** 回答“现有证据有多大把握支持结论”。它不是某个通用统计公式，而应根据数据类型设定可解释规则。

例如 SEM 数据可以暂用：点击不少于 100 且有效转化不少于 10 为高置信度；点击不少于 30 且有效转化不少于 3 为中等；再少则为低。阈值只是审查起点，不代表 10 次转化就一定稳定。高客单、长销售周期和明显季节性需要更长窗口。

技术证据也有层级：

1. **已确认**：真实响应、最终 HTML、代码、配置或日志直接证明。
2. **风险候选**：页面时序、文件名、局部抽样发现异常，需要更多页面或 Coverage 复核。
3. **无法检测**：证书链、真实爬虫身份、实际索引、全站重复或真实用户总体缺少数据。

“低置信度”不是问题较轻。一个疑似 P0 但证据较弱的问题，应先补证据；一个高置信度 P3 观察项，也不应挤掉业务阻断任务。

## P0-P3 的执行优先级

| 优先级 | 判断标准 | 创业团队动作 |
| --- | --- | --- |
| P0 阻断 | 全站不可用、生产误 noindex、核心模板空白、追踪完全错误、广告异常失控 | 立即止损，恢复已知正常版本 |
| P1 高影响 | 核心目录批量错误、主要转化失真、预算持续流向无效需求 | 本周期优先，限制继续扩量 |
| P2 增长 | 内容缺口、内链、标题、资源、创意或落地页可改善 | 进入实验和迭代队列 |
| P3 观察 | 影响小、样本不足或短期波动 | 保存基线，达到阈值再处理 |

优先级由“影响范围 x 业务严重度 x 证据强度 x 时间敏感性”共同决定，不应只按工具扣分排序。一条 8 分的 Title 问题可能只影响一张低流量页；一条不计分的转化追踪错误却可能让整个广告账户学错目标。

## 可执行建议的必要字段

“优化页面速度”无法验收。把问题变成任务时，至少填写：

```text
问题标题：
状态与优先级：
证据、时间与作用范围：
业务影响：
已确认根因 / 待验证假设：
修改动作：
负责人：创业者 / SEO内容 / 开发运维 / SEM / 数据
工作量：低 / 中 / 高
验证方法与成功标准：
观察周期：
回滚条件与恢复方法：
仍不可测的结果：
```

同一模板造成 30 张页面缺少 Title，应按根因聚合成一个模板任务，同时保留受影响 URL；不应生成 30 条重复工单。内容、业务口径和数据问题也不能强行附一段 HTML 代码，必须交给有权限的负责人处理。

## AI 可以解释证据，但不能覆盖规则

AI 适合把多条证据整理成自然语言、发现遗漏的验证步骤、按角色解释任务。它不应修改确定性规则的状态和分数，也不能在没有搜索平台数据时宣称页面已经收录。

发送给 AI 的上下文应遵循数据最小化：只给完成当前问题所需的 URL、规则摘要、性能样本和匿名业务汇总；不发送 Cookie、表单值、完整 DOM、原始 CSV、原始服务器日志、姓名、邮箱、电话、地址或 **API Key（接口密钥）**。页面文本还应视为不可信输入，不能让网页内容覆盖系统规则。

权限边界同样属于诊断质量。工具只能按用户主动授权读取当前页面或同源样本时，就不能声称已扫描整个互联网；外部 AI 服务怎样保存请求，则受用户选择的服务条款约束。

## 五类角色怎样使用同一份报告

| 角色 | 先看什么 | 典型动作 |
| --- | --- | --- |
| 创业者 | P0/P1、业务影响、成本和停止条件 | 决定资源顺序，不追求总分满分 |
| SEO / 内容 | 页面任务、索引目标、内容和内链证据 | 修页面职责与信息表达 |
| 开发 / 运维 | HTTP、模板、渲染、性能、日志和回滚 | 修根因并提供可复测版本 |
| SEM 投手 | 搜索词、成本、学习期和转化口径 | 止损或保留实验窗口 |
| 数据负责人 | 数据源、日期、关联率和置信度 | 修追踪、去重与业务回传 |

报告的目标不是让每个人都看同一个分数，而是让每个人拿到自己能控制、能验证、能恢复的任务。

## 用审计结论完成证据分层

从项目评估卡选择一个高风险假设，例如“网站页面可以稳定被搜索系统获取”。至少记录三条证据：匿名 GET、原始 HTML、浏览器渲染结果。再为每条证据标记事实、假设或缺口，填写状态、作用范围和置信度。

随后创建一条 P0-P3 任务。验收时由另一位读者回答：为什么是这个优先级，谁修改，怎样证明完成，观察多久，失败后恢复什么。若只能复述“分数低”，任务不合格。

这套记录方法可以继续追踪一个 URL 从发现、抓取、渲染到索引和排名的全过程。
