# Lighthouse 100 分，为什么真实用户仍然说页面慢

开发者在高速电脑上跑了一次 Lighthouse，性能得分 100；客服记录却显示，部分移动用户打开价格页后要等很久，点击套餐按钮也会卡住。两边数据并不矛盾：一次受控实验与一段时间内的真实访问，测量对象不同。

性能指标不是一张“网站速度总分”。它们分别描述首字节、第一块内容、主要内容、交互响应和布局稳定；还必须说明样本来自实验室还是真实用户、哪个页面、何种设备、哪个周期和哪个分位数。

上一篇的[原始响应与渲染对照表](/docs/seo/http-javascript-rendering-seo)提供 URL、资源和失败链路。本篇先学会读懂数据，输出性能诊断表；下一篇才由开发针对根因修改服务器、媒体和代码。

## Core Web Vitals 是什么

**Core Web Vitals（核心网页指标，CWV）**是 Google 用来描述真实用户页面体验的一组核心指标。截至 2026 年 8 月，核心集合是：

- LCP：主要内容加载体验；
- INP：交互响应体验；
- CLS：视觉稳定体验。

它们解决“用户是否较快看到主要内容、操作后是否及时反馈、页面是否意外移动”三个问题。输入是浏览器性能事件，处理是按指标规则计算并对一段时间样本取分位数，输出是毫秒或无单位分数。

CWV 是页面体验信号之一，不是搜索排名保证。相关内容、可抓取、搜索意图、品牌与其他系统信号仍然存在。即使排名不变，较差体验也可能增加放弃、误点和转化损失，因此创业者应同时观察用户任务和业务结果。

## 先分清 Field Data 与 Lab Data

### Field Data：真实用户字段数据

**Field Data（字段数据，也称真实用户数据）**来自真实访问者在各自设备、网络、地区和页面状态下的测量。它适合回答“用户总体经历怎样”，但受流量、用户构成、缓存、登录状态和发布周期影响。

公开数据常来自 **CrUX（Chrome User Experience Report，Chrome 用户体验报告）**。它汇总符合条件的 Chrome 真实用户样本，低流量页面可能没有 URL 级数据，只显示 **Origin（源，即协议、主机和端口的组合）**级数据，或者完全无数据。缺失不能判为性能通过或失败。

团队自己的 **RUM（Real User Monitoring，真实用户监控）**可以通过浏览器指标库或监控 SDK 收集更细的页面、版本、设备与业务维度。RUM 必须控制隐私、采样、同意和数据质量，不能采集不必要的个人信息。

### Lab Data：实验室数据

**Lab Data（实验室数据）**是在受控设备、网络和页面状态下重复加载得到的样本。Lighthouse、浏览器 DevTools 和 WebPageTest 常用于这类诊断。它适合重现资源瀑布、主线程长任务和具体元素，但一次实验不能代表真实用户分布。

同一 URL 的字段数据差、实验室数据好，可能是测试设备过强、真实用户地区远、缓存状态不同、第三方脚本只对部分用户加载或真实交互未被覆盖。字段数据好、实验室偶尔差，也可能是单次网络波动。两类数据应互相定位，不互相替代。

## p75 为什么是核心判断口径

**p75（75th Percentile，第 75 百分位）**表示样本按指标从好到坏排序后，75% 的体验不超过该值，25% 更差。若 100 次访问的 LCP p75 是 2.4 秒，可理解为约 75 次不慢于 2.4 秒，剩余约 25 次更慢。

采用 p75 是为了关注大多数用户，同时不让少量极端异常完全控制结论。它不是平均值：十个非常快的样本可能拉低平均数，却不一定改善较慢用户群。

真实用户 CWV 通常在移动端和桌面端分别评估。一个 URL 或 Origin 要达到“良好”，核心指标应在相应字段样本的 p75 落入良好区间。数据窗口与平台更新有延迟，因此发布后不能期待第二天的公开字段数据立刻改变。

## LCP：主要内容什么时候出现

**LCP（Largest Contentful Paint，最大内容绘制）**测量从导航开始，到视口内最大的合格文本块、图片或视频封面完成绘制所经历的时间，单位是毫秒或秒。它试图描述用户何时看到页面主要内容。

常用判断区间：

| p75 LCP | 判断 |
| ---: | --- |
| `<= 2.5s` | 良好 |
| `> 2.5s` 且 `<= 4.0s` | 需要改进 |
| `> 4.0s` | 较差 |

LCP 的输入来自导航时序与绘制候选，浏览器会随着更大元素出现更新候选。输出既有时间，也应保留 LCP 元素与资源 URL。只记录“3.8 秒”而不知道元素，开发很难定位。

常见上游包括 TTFB 慢、主图发现晚、图片体积大、关键 CSS 阻塞、字体延迟、客户端渲染等待和第三方脚本。把所有图片压缩并不一定修复文本 LCP；服务端很快也不代表主图会及时绘制。

单次页面工具测得 2.3 秒，只说明该次会话处于良好区间，不能证明所有真实用户达标。验证应先在同环境复测资源链，再观察 RUM/CrUX p75 与页面转化。

## INP：用户操作后多久看到反馈

**INP（Interaction to Next Paint，交互到下一次绘制）**评估页面生命周期中的点击、触摸和键盘交互延迟，单位毫秒。一次交互延迟包含三个主要阶段：

```text
输入延迟 -> 事件处理耗时 -> 浏览器呈现下一帧的延迟
```

INP 会从页面的一组交互中选择一个代表较差响应体验的值，而不是简单平均每次点击。常用判断区间：

| p75 INP | 判断 |
| ---: | --- |
| `<= 200ms` | 良好 |
| `> 200ms` 且 `<= 500ms` | 需要改进 |
| `> 500ms` | 较差 |

INP 的输入必须包含真实或主动触发的交互。只打开页面不点击，无法获得有意义的 INP；页面扫描工具若没有足够交互样本，应标不可测，而不是零分或通过。

Lighthouse 的一次导航审计通常不能直接测量真实 INP。**TBT（Total Blocking Time，总阻塞时间）**可以作为实验室主线程阻塞线索，但它不是 INP 的同义词，也不能直接换算。DevTools 可录制具体交互，RUM 则用于观察真实任务。

常见根因是长 JavaScript 任务、大量同步计算、框架重复渲染、第三方脚本、事件处理器做过多工作或主线程在交互时仍忙于水合。验证时要记录交互名称，例如“打开价格弹窗”或“提交预约”，不能只看全站 INP 平均值。

## CLS：页面是否在用户没有预期时移动

**CLS（Cumulative Layout Shift，累积布局偏移）**衡量页面生命周期中非预期布局移动的严重程度，没有时间单位。单次布局偏移分数大致由受影响面积比例与移动距离比例相乘，页面 CLS 使用会话窗口规则聚合一组偏移。

常用判断区间：

| p75 CLS | 判断 |
| ---: | --- |
| `<= 0.10` | 良好 |
| `> 0.10` 且 `<= 0.25` | 需要改进 |
| `> 0.25` | 较差 |

CLS 不是“页面移动了多少像素”。一张占据大面积的组件小幅移动，可能比小图大幅移动影响更大。用户主动点击后预期出现的界面变化，在特定时间窗口内也可能不计为非预期偏移。

常见根因包括图片和广告没有尺寸、异步内容插到现有正文上方、字体替换改变文本尺寸、Cookie 横幅和组件占位不稳定。实验室加载可能看不到滚动后或交互后偏移，因此字段数据与 RUM 仍然重要。

验证要保存发生偏移的元素、时间和触发条件。为所有容器写固定高度可能掩盖响应式问题；正确做法是给已知比例预留空间，并让未知内容以不覆盖已有任务的方式出现。

## FCP：第一块内容何时出现

**FCP（First Contentful Paint，首次内容绘制）**测量从导航到浏览器首次绘制文本、图片、SVG 或非白色 Canvas 的时间，单位毫秒。常用诊断区间是：良好 `<= 1.8s`，需要改进 `1.8–3.0s`，较差 `> 3.0s`。

FCP 解决“用户何时不再看到空白”，但第一块内容可能只是 Logo 或加载提示，不能替代 LCP。FCP 很慢时检查 TTFB、阻塞样式、字体、客户端启动和首屏脚本；FCP 快而 LCP 慢，说明页面很早显示了少量内容，主要内容仍被延后。

FCP 不是当前 Core Web Vitals 三项之一，但适合作为加载诊断指标。页面工具测得单次 FCP 时，同样要标记为本次会话数据。

## TTFB：第一字节之前发生了什么

**TTFB（Time to First Byte，首字节时间）**测量导航请求开始到收到响应第一个字节的时间，单位毫秒。常用诊断区间是：良好 `<= 0.8s`，需要改进 `0.8–1.8s`，较差 `> 1.8s`。

TTFB 可能包含重定向、连接建立、网络往返、CDN、服务器排队、数据库和模板生成等等待。它回答“HTML 开始到达前花了多久”，不等于纯后端处理时间；需要结合服务器日志、CDN 计时和浏览器时序进一步拆解。

TTFB 好不代表 LCP 好，HTML 很快到达后仍可能被脚本和主图拖慢；TTFB 差则会给后续 FCP/LCP 留下更少预算。它也不是 CWV 三项之一，而是重要诊断输入。

## Viewport 是移动体验前提，不是性能分数

**Viewport（视口）**是浏览器用于布局页面的可见区域。响应式页面通常需要：

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
```

浏览器读取这项配置后，使用设备宽度作为布局视口，页面输出才会按响应式断点计算。配置缺失时，移动浏览器可能按桌面宽度布局再缩放，文字、点击和横向滚动都会受影响；配置冲突时应检查模板是否输出了重复标签。不要通过 `user-scalable=no` 禁用用户缩放。

这个标签只是基础条件，不能证明页面在 320px、低端设备或辅助技术下可用。验收还要检查文字、表格、导航、弹窗、点击区域和真实交互。

## Lighthouse、PSI、CrUX 和 RUM 怎样搭配

| 工具 / 数据 | 全称 | 主要输入 | 最适合回答 | 主要限制 |
| --- | --- | --- | --- | --- |
| Lighthouse | 开源自动化审计工具 | 一次受控页面加载 | 哪些资源和主线程问题可复现 | 单次环境，不代表真实用户；不能直接给出真实 INP |
| PSI | PageSpeed Insights | URL，结合字段与实验室数据 | 公开 CrUX 状态与 Lighthouse 诊断 | 低流量 URL 可能无字段数据；两部分不能混看 |
| CrUX | Chrome User Experience Report | 合格 Chrome 用户样本 | 公开页面/来源的真实体验分布 | 聚合、有延迟，维度有限 |
| RUM | Real User Monitoring | 自己网站的真实浏览器事件 | 哪类用户、版本、页面和任务受影响 | 需要正确采样、隐私和数据治理 |

PageSpeed Insights 页面上方可能显示过去一段窗口的字段数据，下方显示当次实验室审计。一个是用户分布，一个是诊断复现；把上方 LCP 与下方得分直接做前后因果比较是常见误用。

还要记录页面级还是 Origin 级数据。页面级 URL 没有足够样本时，工具可能展示来源汇总；它可以发现全站风险，却不能证明当前页面自身的表现。

## 一次会话数据怎样正确进入报告

浏览器扩展或自建脚本可在当前访问采集 LCP、CLS、FCP 和 TTFB。INP 因需要足够交互，应作为数据缺口。单次指标的合理用途是：

1. 在同设备、网络和缓存条件下复现问题；
2. 找到 LCP 元素、布局偏移或资源链；
3. 修改后做快速回归；
4. 等待真实用户 p75 验证总体影响。

单次结果不能进入“真实用户 CWV 已通过”的结论。采集失败也不应当作性能失败，可能是页面加载方式、浏览器生命周期或脚本时机没有形成样本。

## 本篇产物：性能指标诊断表

为首页、列表页、详情页和关键转化页分别建立：

```text
页面/模板｜指标｜数值与单位｜良好/需改善/较差｜
Field/Lab/单次会话｜URL级/Origin级｜设备｜地区｜日期窗口｜p75/其他统计｜
关联元素或交互｜可能上游｜证据缺口｜业务保护指标｜负责人
```

至少同时保存一个字段数据来源和一次可复现实验；没有字段数据就明确写缺口。创业者关注关键页面与转化，SEO 负责人确认页面样本和搜索影响边界，开发负责人读取元素与资源证据，数据负责人维护 RUM 口径。

验收时，另一位执行者应能回答“慢在哪里、数据代表谁、为什么暂时只能算候选、下一步由谁定位”。下一篇将把这些指标候选转成服务器、资源、主线程和布局任务。
