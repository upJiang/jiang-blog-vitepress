# 关键词意图与页面映射

关键词表不是一列词和一列搜索量。一个词在不同上下文里可能代表学习、比较、排障、购买或导航需求；同一任务也会被不同的人用完全不同的词描述。页面规划的核心不是“每个词写一篇”，而是判断哪些查询共享同一个答案、哪个页面应该承担转化、哪些词必须由产品页或文档页分别承接。

## 从查询还原任务

先收集可解释的原始样本：搜索控制台中的查询和页面、站内搜索、客服问题、销售记录、产品日志、竞品结果页以及用户访谈。搜索量和趋势可以帮助排序，却不能说明查询是否匹配业务。每条样本至少记录语言、地域、时间、查询上下文、结果形态和用户下一步动作。

```ts
type QuerySample = {
  query: string
  locale: string
  source: 'search' | 'site' | 'support' | 'sales' | 'research'
  observedTask: string
  resultShape: 'guide' | 'tool' | 'list' | 'product' | 'local' | 'video'
  businessFit: 'high' | 'medium' | 'low' | 'unknown'
}
```

不要用单个词推断意图。比如“监控”可能是在找概念解释、工具选型或生产故障排查；“价格”可能是比较方案、查看历史账单或寻找免费替代。把修饰词、结果页标题和用户后续行为一起看，才能判断页面是否应该覆盖该查询。

## 六种常见意图

| 意图 | 用户要完成的任务 | 合适的页面职责 | 业务信号 |
| --- | --- | --- | --- |
| 了解 | 建立概念和边界 | 教程、术语、规范说明 | 继续阅读、收藏 |
| 排障 | 解决明确错误 | 故障手册、可复现步骤 | 复制命令、解决反馈 |
| 比较 | 判断方案取舍 | 对比页、决策指南 | 查看规格、试用 |
| 交易 | 选择并购买 | 产品、定价、服务页 | 申请、下单 |
| 导航 | 找到已知主体 | 品牌或资源入口 | 直接到达 |
| 本地/即时 | 在时空约束下行动 | 地域服务、库存或实时页 | 电话、预约、到店 |

一个页面可以覆盖多个相邻意图，但必须有一个主任务。概念文章里放一段产品广告，不会自动变成交易页；产品页加入长篇理论，也可能让用户找不到价格和行动入口。页面映射表应该写主意图、辅助问题、不能覆盖的意图和成功事件。

## 用语义聚类而不是机械分词

聚类的单位是“任务和答案”，不是词形。可以先做人工小样本，再用向量相似度辅助发现同义表达，最后由领域人员确认。聚类结果至少包括：核心问题、约束条件、用户阶段、所需证据、页面类型和唯一 URL。词根相同但答案不同的查询必须拆开；词根不同但答案相同的查询可以合并。

```text
同一页面候选：
  “如何让 SSE 支持断线续传”
  “Last-Event-ID 重放怎么设计”
共同任务：设计可重放的 SSE 事件流

必须拆分：
  “SSE 是什么”       -> 概念文章
  “SSE 断线重放”      -> 工程实现文章
  “SSE 服务报价”      -> 产品/服务页面
```

聚类后要做 SERP 交叉验证：随机抽取每组查询，观察排名靠前页面的主题、格式、更新时间和用户期待。如果不同查询返回的页面几乎完全不同，说明它们不是一个页面的职责；如果结果页面高度重合且问题相同，合并通常比生产两篇近似文章更健康。

## 页面映射表的最小字段

| 字段 | 说明 |
| --- | --- |
| queryCluster | 语义簇 ID 和一句话任务 |
| primaryQuery | 代表性查询，不承诺固定排名 |
| intent | 主意图和辅助意图 |
| pageType | 指南、参考、产品、比较或工具 |
| ownerUrl | 唯一主页面 |
| supportingUrls | 上下游支撑页面 |
| evidence | 一手数据、规范、实验或产品事实 |
| conversion | 页面成功事件与业务事件 |
| status | planned、published、refresh、merge、retire |

```json
{
  "cluster": "sse-replay",
  "intent": "problem-solving",
  "ownerUrl": "/docs/backend/node-realtime",
  "supportingUrls": ["/docs/agent-practice/15-sse-event-replay"],
  "successEvent": "copy-replay-checklist",
  "reviewAfter": "2026-11-04"
}
```

## 识别关键词内耗

内耗不是“两个页面都出现了同一个词”这么简单，而是两个页面在相同查询下竞争、承诺相似答案，却没有清晰的首选页面。诊断时按查询查看 URL、点击、平均排名、页面意图和更新时间，不能只看页面数量。常见原因有复制模板、标签页参数、语言版本互相声明错误、旧页没有迁移或内部链接同时指向多个近似 URL。

处理顺序通常是：保留证据更完整、业务职责更明确的主页面；把可合并的内容迁移并设置单一规范 URL；有明确替代内容才使用永久重定向；没有替代内容时返回真实 404 或 410；更新 sitemap、内链和 canonical；在观察周期内记录旧 URL 的抓取与业务影响。不要为了“保留权重”把所有旧页都重定向到首页。

## 页面生命周期

页面不是发布后永久存在。规划表需要定期把页面分为保留、刷新、合并、下线和实验。刷新应先保留当前版本快照，记录改动原因和验证指标；合并需要检查外部链接、引用和业务入口；下线需要处理内部链接、站点地图、缓存和搜索结果中的残留。任何批量操作先在一小组 URL 上验证。

## 验证路径

发布前验收页面是否有主任务、唯一 URL、真实证据和清晰下一步；发布后分别检查索引和业务，不用“页面上线”作为成功指标。一个最小查询审计可以输出同一查询近 90 天的点击 URL：

```sql
select query, page, sum(clicks) as clicks, avg(position) as avg_position
from search_query_daily
where day >= current_date - interval '90 days'
group by query, page
having sum(clicks) > 0
order by query, clicks desc;
```

查询表属于示例模型，实际字段必须按数据源替换。重点是发现同一查询是否被多个页面瓜分、页面改变后是否发生意图偏移，以及点击增加是否带来有效业务。

## 实施记录：从问题到动作

页面映射还要记录版本和负责人。查询意图会随季节、产品和结果页变化，旧页面不能因为仍有几个点击就永久保留。每次合并保留旧 URL、内链和转化快照，确认新页面能覆盖原任务后再清理。

执行记录需要保留四类信息：基线快照、改动版本、观察条件和业务对账。基线至少包含 URL、模板、查询/搜索词、状态码、索引资格、事件口径和时间范围；改动要能定位到内容、路由、缓存、创意或出价的具体版本；观察条件要记录设备、地域、语言、模型或平台版本；业务对账要以服务端的资格、成交、退款和回款为准。这样在结果变差时可以回到上一个可用版本，而不是凭记忆争论。

## 故障演练与回滚

| 演练场景 | 预期信号 | 保护动作 | 恢复证据 |
| --- | --- | --- | --- |
| robots 或 WAF 误拦截 | 抓取 4xx 上升、核心 URL 失败 | 恢复规则并限制变更面 | GET、日志、覆盖报告 |
| 模板发布错误 | title/canonical/正文异常 | 回滚模板或内容版本 | 原始 HTML 对比 |
| 追踪重复或丢失 | 客户端与服务端数量不一致 | 停止自动化学习，修复去重 | 事件 ID 对账 |
| 业务质量下降 | 有效率、退款或毛利越过护栏 | 收紧查询/预算或下线页 | CRM/订单状态 |

演练使用模拟场景和最小流量，不改变真实生产预算或数据。回滚后再次检查公开页面、缓存、站点地图、广告参数、事件队列和业务状态；只有所有关键证据恢复，才允许继续实验。

## 结果判定与后续动作

把结论分为事实、假设和缺口。事实必须能由页面、日志、平台、实验或业务记录直接复核；假设写出可证伪的预测；缺口说明缺少哪项数据以及它会影响哪项判断。观察周期内不要连续叠加多个主变量，也不要把平台评分、平均排名或单次引用当作有效业务的替代。

```text
基线 -> 小范围变更 -> 技术验收 -> 搜索/广告观察 -> 业务对账 -> 继续、调整、合并或停止
```

## 操作清单与决策记录

每次合并或拆分都要保留查询、页面、内链和业务快照，避免把流量变化误判成内容质量。

发布或投放前按顺序记录：

1. **范围**：目标用户、语言、地域、页面类型和明确不覆盖的需求。
2. **证据**：查询样本、页面版本、规范/源码/实验来源、数据时间和负责人。
3. **技术**：状态码、抓取规则、canonical、sitemap、内链、缓存、脚本失败和移动端表现。
4. **业务**：主转化、资格条件、去重键、成交/退款状态和归因窗口。
5. **保护**：预算或发布范围、护栏指标、观察周期、回滚版本和停止条件。

## 指标与停止条件

| 信号 | 可继续的证据 | 应暂停或回滚 |
| --- | --- | --- |
| 技术 | 公开 URL 状态稳定，规范页和索引目标一致 | 5xx、误拦截、canonical 冲突或空壳正文 |
| 搜索 | 相关查询、页面和点击方向一致 | 查询意图偏移、重复页面或无效展现激增 |
| 用户 | 到站后完成主要任务，错误反馈可解释 | 跳转、表单、脚本失败导致任务中断 |
| 业务 | 有效率、毛利和退款符合护栏 | 低质量线索、退款上升或归因无法对账 |

停止不是失败，而是保护样本和现金流的工程动作。停止后保留原始事件、页面快照和决策日志；需要恢复时先回到最后一个可验证版本，再单独改变一个变量。

```text
事实（页面/日志/业务记录） -> 假设（可证伪预测） -> 动作（单一变量） -> 观察（固定口径） -> 决策（继续/调整/停止）
```
