# “把图片压一下”为什么没有修复 4 秒 LCP

性能报告显示价格页 LCP 为 4 秒。团队把全部 JPEG 转成 WebP，文件小了很多，LCP 却几乎不变。查看瀑布后才发现：服务器首字节要 1.4 秒，主图 URL 又要等客户端 JavaScript 执行后才出现。图片传输只是整条关键路径的最后一段。

上一篇的[性能指标诊断表](/docs/seo/technical-seo-rendering-performance)已经说明哪个模板、什么数据来源、哪个元素或交互存在风险。本篇只处理开发侧可控项：服务器、缓存、HTML、媒体发现、CSS/JS、主线程、布局和发布验证。关键词、robots、Sitemap、页面是否应该索引，不属于性能代码改动。

## 先画 Critical Rendering Path

**Critical Rendering Path（关键渲染路径）**是浏览器从收到 HTML 到绘制首屏所必须完成的请求、解析、样式、布局和绘制工作。输入是服务器响应与页面资源依赖，处理发生在网络和浏览器主线程，输出是用户看到的首屏。

```text
导航 -> TTFB -> HTML 到达 -> 发现 CSS/JS/主图 -> 请求资源
     -> 构建 DOM/CSSOM -> 执行必要脚本 -> 布局与绘制 -> LCP
```

优化不是把每一项都做到最小，而是找到当前瓶颈。主图已经很小但发现晚，应先让 HTML 直接声明；HTML 很快但渲染被大段同步脚本阻塞，应处理执行；数据库慢，则前端 preload 不能修复源站。

## 第一步：把 TTFB 拆到服务器链路

浏览器 TTFB 包含网络与服务器等待。先按层保存证据：

| 层 | 观察证据 | 常见动作 |
| --- | --- | --- |
| 跳转与连接 | 跳转链、DNS/TLS、地区差异 | 缩短跳转，合理使用 CDN 与连接复用 |
| CDN/WAF | 命中率、边缘时间、回源时间 | 调整缓存键、TTL、回源与规则 |
| 应用 | 路由、模板、外部接口耗时 | 并行安全请求、超时、降级、页面缓存 |
| 数据库 | 慢查询、锁、连接池 | 索引、查询边界、缓存与容量治理 |
| 依赖 | 第三方 API、对象存储 | 超时、熔断、异步化、就近交付 |

服务器日志的 p95 响应时间能指出慢 URL，却不等于用户 TTFB 或 LCP。**p95（第 95 百分位）**表示约 95% 请求不超过该耗时，适合暴露尾部延迟。把浏览器、CDN、应用和数据库时序用请求 ID 或时间窗口关联，才能找到责任层。

缓存前先明确页面是否公开、是否个性化、更新频率和失效机制。不能为了 TTFB 把账户页放进公共缓存，也不能让价格和库存长期陈旧。

## 第二步：让 LCP 资源尽早可发现

先在性能记录中确认 LCP 元素。若是图片：

1. 在初始 HTML 中直接输出真实 `src`/`srcset`，不要等待组件挂载；
2. 不给首屏候选使用普通 `loading="lazy"`；
3. 声明宽高和接近显示尺寸的资源；
4. 仅在确认关键后使用 `fetchpriority="high"` 或 preload；
5. 检查 CSS 背景图是否因样式表晚到才被发现；
6. 检查服务器、CDN、格式与缓存，而不是只看源文件大小。

下面示例假设主图确定是首屏 LCP 候选，且 URL 与最终响应一致。输入是 1280x720 的优化资源，目标是让浏览器在解析 head/body 时尽早发现并分配高优先级：

```html
<link rel="preload" as="image" href="/assets/hero.hash.webp" fetchpriority="high">

<img
  src="/assets/hero.hash.webp"
  width="1280"
  height="720"
  fetchpriority="high"
  alt="团队预约看板的周视图">
```

preload 会额外占用连接与带宽，URL、`as`、跨域属性或响应式候选不一致时还可能重复下载。修改后必须检查网络瀑布是否只有一次请求，并确认其他关键 CSS/字体没有被错误降级。

若 LCP 是文本，重点检查 TTFB、阻塞 CSS、字体和客户端渲染。不要为了追求早绘制而短暂展示不可读无样式内容，再造成 CLS。

## 第三步：控制 CSS、字体和首屏样式

CSS 通常参与首次渲染。开发可以：

- 删除有覆盖证据且经过页面回归的无用样式；
- 把首屏必要样式控制在小范围，避免每页重复内联巨大 CSS；
- 按路由或组件加载非关键样式，同时防止交互时闪烁；
- 为字体选择需要的字重和字符子集，避免一个页面下载全部家族；
- 对关键自托管字体正确 preload，并保留系统字体回退；
- 调整字体指标或使用适当 `font-display`，同时观察文字可见时间和布局偏移。

HTTP/2/3 支持多路复用，不能只为减少请求数机械合并全部 CSS。拆分依据是首屏依赖、缓存复用、变更频率和执行成本。

## 第四步：让 JavaScript 不阻塞解析

同步经典脚本会阻塞 HTML 解析。`defer` 适合依赖 DOM、需要按顺序执行的脚本；`async` 适合独立脚本；`type="module"` 默认延后。修改属性前要画出依赖，避免导航、埋点或支付初始化顺序被破坏。

下面示例的输入是三个已经确认职责的文件，目标是让导航在 DOM 解析后执行，让独立分析脚本下载完即可执行，让应用按模块加载：

```html
<script src="/assets/navigation.hash.js" defer></script>
<script src="/assets/analytics.hash.js" async></script>
<script type="module" src="/assets/app.hash.js"></script>
```

浏览器按各自语义调度：defer 保持文档顺序，async 不保证与其他脚本顺序，module 有自己的依赖图。验收要覆盖首次访问、缓存命中、慢网和脚本失败，查看控制台与关键业务流程。

路由级编辑器、报表、客服和 AI 对话可以动态导入，但重要正文、H1、导航与核心 CTA 不应等用户动作后才创建。第三方脚本必须有业务所有者、加载条件、错误隔离和退出机制。

## 第五步：优化 INP 的三个阶段

INP = 输入延迟 + 事件处理 + 下一帧呈现等待。定位时录制一个具体任务，不要只说“JavaScript 太多”。

### 输入延迟

用户操作发生时，主线程正在执行其他长任务。将大任务拆成可让出主线程的小批次，把非紧急工作延后；减少启动阶段水合、解析和第三方执行。

### 事件处理

处理器内同步计算、JSON 解析、复杂验证或大量状态更新会增加耗时。可以减少工作量、缓存计算结果、在适用时使用 Web Worker，并避免一个操作触发多次重复渲染。

### 呈现延迟

修改大量 DOM、强制同步布局和复杂样式会拖慢下一帧。批量读写、减少布局范围、虚拟化真正的大列表，并给即时反馈与最终结果不同优先级。

Worker 也不是免费解决方案：数据序列化、线程通信和错误恢复都有成本。只有性能记录显示 CPU 工作适合移出主线程，并且业务状态边界清楚时才使用。

验证至少包含低端设备上的关键点击、输入和提交任务。实验室用 DevTools 观察长任务与呈现，RUM 记录交互名称和 p75 INP；TBT 改善只能作为线索，不能替代 INP。

## 第六步：从布局偏移元素修 CLS

对每次布局偏移记录受影响元素和触发者，再选择动作：

- 图片、视频、iframe 使用真实宽高或 `aspect-ratio`；
- 广告和异步组件预留合理空间，空内容时回收策略要可预测；
- 通知条和 Cookie 横幅尽量不把已有正文向下推，或在首屏结构中预留；
- 字体用回退和指标调整减少替换后的尺寸变化；
- 动画优先使用 transform/opacity，避免反复触发布局；
- 不在现有内容上方无提示插入推荐、登录或促销模块。

固定一个过大高度会产生空白和响应式问题。预留的是合理比例或业务上限，不是用魔法数字隐藏指标。

## 第七步：压缩与缓存按资源分类

下面 Nginx 片段只是输出目标示例。它假设 `/assets/` 文件名包含内容哈希，公开 HTML 可以保存但每次复用前验证；登录与 API 还需在真实配置中单独处理。修改前先备份并执行配置语法检查：

```nginx
gzip on;
gzip_vary on;
gzip_min_length 1024;
gzip_types text/css application/javascript application/json application/xml image/svg+xml;

location /assets/ {
  add_header Cache-Control "public, max-age=31536000, immutable";
}

location / {
  add_header Cache-Control "no-cache";
  try_files $uri $uri/ =404;
}
```

服务器只对适合的文本响应压缩；带哈希资源可长期缓存；公开路径找不到时保留 404，而不是一律回退到 SPA 入口。若资源文件名不会随内容变化，不能照搬 immutable；若应用公开路由必须 SSR，也要按框架重写 `try_files`。

发布后用真实 GET 检查 Content-Encoding、Cache-Control、Vary、ETag/Last-Modified、304、正常页和随机不存在页。若配置导致旧 HTML、用户串号、资源损坏或错误状态，立即恢复旧配置。

## 第八步：建立 Performance Budget

**Performance Budget（性能预算）**是每种页面模板在资源和体验上允许的上限。它把“上线后再优化”变成设计与发布约束。

预算可以包含：

| 预算项 | 示例口径 | 超出时的处理 |
| --- | --- | --- |
| 首屏 JS / CSS / 图片 | 压缩传输字节与执行成本 | 拆需求、延迟或由业务接受风险 |
| 第三方资源 | 数量、传输、主线程耗时 | 要求所有者和退出开关 |
| Lab LCP/CLS/任务延迟 | 固定设备网络的回归门槛 | 阻止明显回退 |
| RUM p75 CWV | 页面模板、设备、版本 | 观察发布影响并回滚异常 |
| 错误与转化 | JS 错误、表单成功、支付 | 作为不可牺牲的保护指标 |

预算按页面类型设定，不能用全站平均掩盖关键结算页。新功能确实有业务收益时可以接受性能成本，但必须记录谁批准、补偿动作和复查日期。

## 发布、观察和回滚

一次改动记录一个主要假设，例如“主图晚发现是 LCP 主要瓶颈”。上线前保存资源版本、配置、实验室基线、RUM 版本标记和业务保护指标。先在代表页面或小流量范围验证，再扩大。

即时验证包括：HTML、状态码、瀑布、关键交互、布局和控制台；字段验证需要等待足够样本和成熟窗口。若同时换 CDN、重写页面、删除脚本并改图片，就无法把结果归因到一项，回滚也困难。

回滚条件不只看性能。正文缺失、404 变 200、缓存旧内容、登录串号、转化下降、错误率增加，都应优先恢复上一已知正常版本，再分析。

## 开发任务单与预算

每条任务填写：

```text
页面/模板｜目标指标与数据源｜问题元素/交互｜已确认瓶颈｜
修改假设｜代码/配置范围｜负责人｜工作量｜实验室验收｜
RUM 验收｜业务保护指标｜观察周期｜回滚条件与版本
```

开发/运维负责实现与技术证据，设计负责媒体与稳定布局，数据负责人维护 RUM 和业务保护指标，SEO 负责人确认关键公开页面没有因优化丢失内容，创业者决定性能预算与功能收益的取舍。

验收至少覆盖正常页、跳转页、不存在页、移动端、脚本失败、缓存命中与核心转化。下一篇会把这些技术证据与页面内容、链接和索引目标汇总为一次完整单页审计。
