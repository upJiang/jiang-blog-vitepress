# Redis 在 AI 系统中的缓存、Session、限流与任务角色

模型响应缓存突然大量失效，数据库流量上升；同一时间，作为任务 Broker 的 Redis 也开始淘汰消息。问题不只是“Redis 内存不够”，而是可丢失缓存与不可随意丢失的协调状态共享了同一容量和淘汰策略。

Redis 提供低延迟数据结构、过期、原子命令和持久化选项。它可以承担多种角色，但每个角色的真相源、丢失后果、TTL、容量和恢复方式不同。把所有状态放进一个实例，会让最宽松的缓存策略伤害最严格的任务语义。

## 五类常见状态

| 场景 | 常用结构 | 真相源 | 失效或恢复 |
| --- | --- | --- | --- |
| 模型/检索缓存 | String、Hash | 模型调用或数据库 | TTL 后重算，防止集中回源 |
| Session | String、Hash | 认证系统或会话记录 | 过期后重新认证，撤销需主动失效 |
| 限流 | String、Sorted Set | Redis 自身的时间窗口状态 | TTL 回收，原子更新，失败时明确降级 |
| 任务通知/Broker | List、Stream 或框架协议 | 持久任务表与消息协议 | ACK、重投、死信和幂等消费 |
| Lease/调度 | String、Sorted Set | 业务状态与租约记录 | 所有者、过期、续期和 fencing |

选择结构前先写出操作：按键读取、原子递增、按时间范围删除、消费组确认，还是竞争一个租约。数据结构应匹配访问模式，而不是只因为团队熟悉 String。

## 缓存解决读取成本，不改变真相

Cache-aside 中，应用先读缓存，未命中再读数据库或调用模型，最后写缓存。数据库和已确认模型结果仍是真相源。写操作通常先提交数据库，再删除或更新缓存；事务回滚时不能发布新缓存。

缓存键必须包含会改变结果的维度，例如租户 Scope、知识版本、模型 Revision、Prompt 版本和规范化输入。遗漏权限或版本会产生错误命中，比单纯未命中更危险。缓存值还要记录生成时间和来源，便于判断是否能继续使用。

热门 Key 同时过期会形成击穿，许多 Key 集中到期会形成雪崩。可以使用随机抖动、请求合并、预热和有上限的旧值降级，但任何降级都要说明数据新鲜度和权限边界。

## Session 与限流是安全状态

Session Key 通常包含随机会话 ID、用户 ID、权限版本和过期时间。退出、凭证泄露或权限变更时，不能只等待自然 TTL。Cookie 安全属性和服务端会话是两层边界，Redis 不替代 HTTPS 与 CSRF 防护。

限流需要原子读改写。固定窗口实现简单但边界会突发；滑动日志准确但更占内存；令牌桶允许受控突发。策略的输入应是服务端确认的主体、租户和模型能力，不能完全相信客户端传来的用户标识。

Redis 不可用时是放行还是拒绝属于产品与安全决策。高成本模型入口通常倾向保护系统，低风险只读缓存可退回真相源，但必须限制回源并发，避免把 Redis 故障放大成数据库故障。

## Broker 与缓存应隔离风险

缓存可以接受淘汰，未确认任务通常不能。若二者共享实例，`maxmemory-policy`、持久化、备份和延迟抖动都互相影响。至少要分开逻辑容量与告警，关键任务更适合使用独立 Broker 或专用 Redis 实例。

“消息进入 Redis”不等于任务完成。系统还需要持久任务 ID、消费所有者、ACK 时机、重试次数、死信和幂等键。Worker 崩溃后，恢复逻辑必须知道任务是未开始、执行中还是副作用已发生但 ACK 未写入。

## TTL、淘汰与持久化不是同一个概念

TTL 是业务设置的过期时间；惰性和主动过期负责清理已到期键；淘汰是在达到内存边界时按策略删除仍可能有效的键。一个 Key 没有 TTL，也可能被某些淘汰策略移除。

RDB 提供时间点快照，AOF 记录写命令并可重写。它们改变恢复点与写入成本，但不把 Redis 变成关系数据库，也不替代业务备份。主从复制提高可用性，却可能在故障切换中丢失尚未复制的写入，锁和任务协议要考虑这种现实。

## 运行检查要回答业务问题

内存使用、碎片率、命中率、淘汰数、过期数、阻塞客户端、慢命令、连接数、复制延迟和持久化状态都值得观察，但不能脱离角色解释。缓存命中率下降可能是新版本主动换 Key；`evicted_keys` 对缓存是容量信号，对 Lease 和 Broker 则可能是正确性事故。

最终的 Redis 设计表应为每类 Key 写明前缀、结构、创建者、读取者、TTL、估算大小、真相源、失效事件、敏感等级和故障降级。只有这些字段齐全，Redis 才是受控基础设施，而不是无法解释的共享内存区。
