# AI 系统的 CI/CD 是什么？代码、模型和配置怎样成为可信制品

把代码推到 Git 仓库，只说明源码有了一个版本。AI 服务还要绑定基础镜像、Python 或 Node 依赖、模型 revision、Tokenizer、配置模板和构建工具。若测试环境和生产环境各自重新构建，源码 commit 相同也可能得到不同镜像。回滚时找不到原来的字节，问题就从一次发布变成了供应链追溯事故。

CI/CD 是一组把修改变成可验证、可提升制品的自动化流程。CI 负责在隔离环境中取得固定输入、安装依赖、运行检查并生成结果；CD 负责把已经验证的制品提升到候选环境和正式环境。它不是一条永远成功的脚本，任何阶段都应有输入、输出、停止条件和可追溯身份。

本文以一个包含 API 镜像和模型制品的 AI 服务为例。示例命令使用占位摘要和临时 Registry，不代表已经连接某个真实仓库；代码与配置说明流程，实际签名密钥、Registry 权限和模型下载凭证需要在受控环境配置。

## CI/CD 是什么，为什么要把构建和发布拆开

CI 的输入是一个明确的源码 revision、锁定的依赖文件、构建参数和测试数据。流水线在干净 Worker 中执行构建，输出镜像、模型适配器或其他制品，同时输出测试报告、依赖清单和构建日志。相同输入应该得到可解释的结果，若基础镜像或下载内容漂移，Manifest 要把差异记录下来。

CD 的输入是已经产生并通过准入的制品摘要。它可以把同一个镜像 digest 从测试环境提升到候选，再提升到生产，环境差异通过外部配置、Secret 和资源声明注入。CD 不应该在每个环境重新运行“拉代码、安装依赖、构建镜像”，否则验证过的字节与上线字节就不是同一份。

CI 和 CD 的区别也限制了权限。构建 Worker 需要读取源码和依赖缓存，通常不需要生产数据库写权限；发布控制器需要修改部署对象，但不应读取构建阶段的长期云凭证。权限按阶段隔离，某个测试脚本被攻破时，攻击者不能直接切换生产流量。

一次失败要保留阶段身份。依赖下载失败、单元测试失败、SBOM 生成失败、签名验证失败和候选探针失败不是同一类错误。流水线界面可以显示统一的 failed，但事件记录要有 stage、attempt、source revision、制品摘要和最早错误，恢复时才能知道从哪里重跑。

CI/CD 与“服务器上执行一段部署脚本”的区别，在于前者会保存每一阶段的输入、结果和判定。部署脚本可以完成复制文件、重启进程这些动作，却未必知道文件从哪个源码产生、测试针对哪份字节、失败后应回到哪个候选。小项目可以用一台 Runner 和几段脚本实现 CI/CD，关键不在产品规模，而在流程是否把制品身份、证据和权限边界固定下来。

::: info 记住这个边界

构建产生制品，测试产生证据，签名建立来源和完整性关系，发布只提升已经批准的制品。任何环境都不应把一个可变 tag 当成“当前版本”的唯一身份。

:::

## 一次提交要经过哪些固定输入

提交 revision 是第一份输入，但还不够。锁文件固定直接依赖，基础镜像 digest 固定操作系统和编译工具，构建脚本固定命令，模型 Manifest 固定权重与 Tokenizer。缺少其中任何一项，构建系统可能从网络获取另一份内容。

AI 服务通常有两条制品线。应用镜像包含代码和运行库，模型制品包含权重、配置、Tokenizer 或 Adapter。两者可以分开构建和缓存，最后在 release manifest 中绑定。这样更新 Python 代码不必重新上传数百 GB 权重，更新模型也不会偷偷换掉 API 代码。

下面的 Manifest 是一个严格 JSON 示例。字段值是占位符，真实流水线应在生成后重新读取 digest 和摘要，而不是让提交者手写。

```json
{
  "source_commit": "COMMIT_SHA",
  "image": "registry.example/ai-api@sha256:IMAGE_DIGEST",
  "model_revision": "MODEL_COMMIT",
  "tokenizer_revision": "TOKENIZER_COMMIT",
  "sbom": "sha256:SBOM_DIGEST",
  "provenance": "sha256:PROVENANCE_DIGEST",
  "builder": "ci-worker-pool",
  "candidate_id": "release-20260818-01"
}
```

读这个文件时，先看它把哪些输入绑定在一起，再看它是否能指向实际字节。`source_commit` 解释代码来源，image 和 model_revision 指向不同制品，SBOM 和 provenance 是构建证据，candidate_id 是一次发布尝试。JSON 本身不是签名，发布控制器还要校验它的来源和摘要。

## 测试通过说明了什么，又没有说明什么

单元测试验证函数和模块在给定输入下的行为，协议测试验证 HTTP、SSE、错误码和字段结构，集成测试验证数据库、队列或对象存储边界。AI 服务还需要做模型制品静态检查、Tokenizer 回归、最小推理和取消释放测试。每种测试的结论范围不同，不能用一个绿色图标覆盖全部风险。

质量门禁要把“未执行”与“失败”区分开。没有 GPU 的 CI 可以检查 Config、权重 shard、量化字段和启动参数，但不能宣称模型在目标 GPU 上吞吐达标；没有外部 API 凭证的流水线可以使用 Fake Adapter 验证错误映射，却不能证明真实供应商的限流语义。

测试产物也要有身份。报告记录源码、镜像、模型 revision、测试数据版本、运行器版本和时间窗口，日志中带 request ID 或 test case ID。重新运行同一用例时，比较结果差异，而不是只看最新的一次输出。

一项测试失败时，发布系统应停止提升，并保留可重放输入。重试只适合可能暂时失败的网络和资源问题，代码断言失败不能靠无限重试变绿。对生成式输出，固定 Tokenizer、采样参数和评测样本，使用明确的结构、质量或引用断言，不把任意文本相似当作通过。

## SBOM、签名和 Provenance 分别证明什么

SBOM 是软件物料清单，记录镜像或制品包含哪些包、版本和依赖关系。它帮助回答“漏洞可能位于哪里”，不直接证明漏洞可达、运行时已加载或业务安全。镜像更新后 SBOM 必须随摘要更新，不能复用上一版本的清单。

签名是受信身份对制品摘要或声明签署的密码学证明。验证签名可以确认字节没有被替换，并把制品绑定到某个密钥或工作负载身份。签名通过不代表代码无漏洞，也不代表签名者有权把制品发布到生产，信任根和策略仍由组织维护。

Provenance 描述制品怎样产生，包括源码 revision、构建器、参数、依赖来源和步骤。它帮助审查“这份镜像是不是由允许的流水线用指定源码构建”，与 SBOM 的内容清单和签名的完整性证明不同。三者可以绑定在同一 release manifest，也不能互相代替。

| 证据 | 回答的问题 | 不能单独证明 |
| --- | --- | --- |
| Digest | 具体部署的是哪些字节？| 来源和业务正确性 |
| SBOM | 包含哪些软件物料？| 所有风险都可利用或已修复 |
| Signature | 字节是否被受信身份签署且未被替换？| 签署者有业务发布权限 |
| Provenance | 源码和构建过程怎样产生它？| 运行时容量和回答质量 |
| Test Report | 固定输入下哪些行为通过？| 未覆盖的环境和故障 |

表格前的定义用于区分证据，表格后的发布策略还要把它们组合起来。一个候选至少应能按 digest 找到 SBOM、签名、Provenance 和测试报告，缺任何一项就停在候选状态，而不是把 tag 推到生产。

## Secret 怎样进入流水线而不进入制品

Secret 是运行或构建时需要保护的凭证，如 Registry Token、模型下载凭证和云对象存储密钥。它应该由 CI 平台的受控 Secret Store 在任务开始时短暂注入，任务结束后撤销或过期。源码、Dockerfile、镜像层、构建日志和 SBOM 都不应包含 Secret 值。

构建阶段确实需要下载私有模型时，使用短期、最小权限凭证，并把下载结果写到受控缓存或 staging 对象。不要把 `ARG MODEL_TOKEN` 写进 Dockerfile，也不要让 shell 在失败时把完整环境变量打印出来。即使后续层删除文件，早期镜像层仍可能保留泄露内容。

发布阶段的 Secret 与镜像分离。Kubernetes Secret、外部 Secret Manager 或运行器身份可以在容器启动时提供凭证，release manifest 只记录 Secret 引用和版本，不记录值。候选环境先验证服务能读取必要配置，日志只显示字段存在、权限结果和非敏感摘要。

轮换和撤销也属于 CI/CD。发现泄露后先撤销凭证、停止使用相关制品，再调查日志和镜像层；仅修改当前配置并不能清掉已经公开的密钥。流水线要有 Secret 扫描和阻断规则，但扫描通过也不能替代最小权限与运行时隔离。

## 代码、模型和配置怎样形成同一发布候选

应用镜像可以从源码构建，模型制品可以由训练或量化流水线提供，配置包含路由、资源、探针和策略。三者的生命周期不同，却需要在一次发布中绑定。release manifest 记录应用 digest、模型 revision、配置 digest、Schema 版本和目标环境，发布控制器按这份清单创建候选。

配置不要通过手工编辑生产文件获得“最终值”。模板可以有环境变量和 Secret 引用，但渲染后的配置要在候选阶段保存摘要，并在启动日志中打印非敏感版本。未知字段、旧 Schema 或模型能力不匹配应在渲染或启动时失败，不能静默忽略。

模型更新还要考虑 Tokenizer、Adapter 和量化 Kernel。应用镜像没有变化，模型 revision 变化也可能改变输入 Token 数、显存峰值和输出停止条件。准入测试固定代表性 Prompt，检查 Tokenizer、启动、最小生成、流式结束和取消；未在真实 GPU 验证的性能结论保留为待验证。

同一候选在环境间提升时，改变的应是连接、资源和 Secret，而不是制品 digest。开发环境通过只说明该环境的测试完成，生产还要检查权限、容量、备份、观测和回滚条件。候选 ID 连接所有证据，避免“镜像是同一个但配置没人知道”的灰色状态。

## 依赖锁定怎样让一次构建可复现

依赖锁定不是把版本号写得更长，而是让解析结果和来源可以复查。Python 需要锁定直接与间接依赖、平台标记和哈希，Node 需要锁文件与包管理器版本，基础镜像要使用 digest。模型下载也要固定 revision 和每个文件摘要，不能让安装脚本在构建时自行追踪主分支。

构建 Worker 先创建干净目录，读取锁文件和构建参数，再从允许的 Registry 或缓存取得字节。缓存可以加快速度，但命中后仍要校验摘要，缓存 miss 不能悄悄切换到另一个版本。构建日志记录解析器、操作系统、架构和时间，遇到不同平台时要说明为什么产物摘要不同。

一个可复现构建不要求每次时间戳完全相同。文件排序、编译器和压缩参数要稳定，生成的元数据时间可以放在 Provenance，不写入最终运行代码。若构建仍然产生不同 digest，先比较基础镜像、下载清单和生成步骤，再决定是否允许把差异作为有意的构建输入。

## 流水线怎样把每个阶段变成可重放工作单

流水线配置描述顺序，工作单描述某一次执行。工作单至少保存 candidate ID、stage、attempt、输入摘要、Runner 身份、开始与结束时间、输出位置和状态修订。构建阶段失败后，新 attempt 读取同一源码、锁文件和基础镜像摘要；如果操作者修改了模型 revision 或构建参数，就应创建新候选，不能把不同输入伪装成同一次重试。

阶段之间通过制品和证据交接，不通过 Runner 的临时目录交接。构建阶段把镜像推入 Registry，模型准备阶段把 Manifest 写入对象存储，测试阶段按 digest 拉取，签名阶段对同一 digest 和声明签署。Runner 被回收后，下一阶段仍能从受控存储取得完全相同的输入。临时目录可以做缓存，但不能成为唯一来源。

可重放也不等于允许无限重试。网络下载超时可以在固定输入下重试，确定性的编译失败、测试断言失败、摘要不一致和策略拒绝要先修复原因。每种失败都设置最大次数和退出状态，避免一条坏流水线长期占用 GPU Runner、Registry 带宽或签名服务。重试成功时保留前几次 attempt，审查者才能看到失败是否只是暂时抖动。

对 AI 制品还要保存评测输入的版本。模型 revision 相同，Prompt 模板、Tokenizer、评测样本或采样参数变化都会改变结果。工作单把这些摘要与报告绑定，下一次复读可以区分“模型变化”和“评测方法变化”。没有这层身份，质量分数上升也无法说明候选本身更好。

一个适用边界是外部不可复现服务。流水线调用商业模型、在线数据集或会变化的漏洞数据库时，无法保证未来得到相同响应，只能记录供应商版本、请求摘要、时间和返回证据，并把强确定性断言放到本地 Fake 或固定快照。可重放要求解释输入，不等于假设整个互联网永远不变。

## Registry、签名策略和发布控制器怎样闭合信任链

Registry 保存镜像或模型制品，签名系统把受信身份绑定到摘要，发布控制器执行组织策略。三者分工不同。Registry 中存在一个 tag，只说明对象可被查找；签名验证通过，说明摘要由某个身份签署；发布控制器还要判断该身份是否允许发布到目标环境，以及测试、许可证、漏洞和模型审批是否齐全。

发布控制器读取 release manifest 后，应重新向 Registry 解析 digest，并校验关联的 SBOM、Provenance 和签名。它不能相信提交者在 YAML 中写下的摘要，也不能只验证 tag 当前指向。可变 tag 可以用于人类浏览，Deployment 和审计记录应保存不可变 digest。tag 后来被移动时，正在运行的版本身份仍然清楚。

模型制品可能不适合直接打进容器镜像。几十 GB 或数百 GB 权重可以放在受控对象存储或模型 Registry，由 Manifest 记录每个 shard 的路径、大小和校验和。候选启动时先下载到 staging，逐项校验后再原子切换到可读目录。下载完成不等于模型可用，Tokenizer、Config、量化格式和目标 Kernel 还要一起验证。

撤销也是信任链的一部分。发现私钥泄露、恶意依赖或模型许可证问题后，策略可以吊销签名身份或拒绝某个 digest。已经运行的候选需要被控制器发现并停止继续扩流，不能只阻止下一次部署。审计记录保留吊销原因、受影响候选、当前 upstream 和回滚目标，避免值班人员在事故中重新启用同一制品。

这套闭环不保证业务逻辑正确。签名制品仍可能包含经过正常评审却有缺陷的代码，SBOM 也可能漏掉运行时动态下载。它能把“谁构建了什么、根据哪些证据放行、当前运行哪份字节”变成可查询事实，再由测试、候选验证和运行观测补上行为层结论。

## 一个紧急修复怎样避免绕过原有证据

紧急修复常发生在生产故障期间，时间压力会诱使操作者登录服务器改文件。更可靠的路径是从当前生产 digest 建立修复分支，只改必要代码，生成新的 source revision 和 candidate ID。依赖、模型和配置若没有变化，Manifest 明确复用原摘要；任何字节发生变化，都重新构建、测试、生成 SBOM 和签名。

流水线可以缩短测试集合，但不能隐藏缩短这一事实。修复候选至少运行受影响单元测试、协议回归、启动探针、最小业务请求和回滚检查，报告标记哪些完整测试尚未执行。审批者看到的是受控风险，而不是一个与常规绿色流水线外观相同、实际缺少步骤的结果。

假设生产模型接口因错误映射返回 500，修复只调整 Gateway 的状态码转换。输入仍是原模型 revision 和配置，输出是新的 API 镜像 digest。候选在独立端口启动，用固定请求分别验证成功响应、供应商限流和超时，确认日志保留原始错误且客户端得到预期状态。若候选失败，upstream 没有改变，旧版本继续服务。

发布后还要补跑被缩短的检查，并设置明确截止时间。若完整测试发现新的阻断问题，控制器按已保留的旧 digest 回滚。紧急流程的边界是“减少等待但保留身份和证据”，不是把不可追溯的手工修改合理化。故障解除后应删除临时凭证和测试数据，修复制品则继续由 Registry 与审计策略管理。

## 制品 Registry 怎样保存候选与回滚版本

Registry 保存镜像 manifest、配置附件、SBOM 和签名声明。tag 适合人类检索，digest 适合部署合同；候选标签可以指向最新验证版本，但正式 Deployment 应保存 digest。清理策略要保留当前版本、已验证回滚版本和仍被审计或恢复任务引用的制品。

模型制品通常体积大，上传可以使用分片和断点续传。上传完成后先校验每个 shard 和 Manifest，再把 revision 状态从 staging 改为 verified。删除旧权重前查引用关系，不能只按对象年龄清理，否则唯一恢复点可能被后台生命周期误删。

Registry 权限按动作分开。构建身份可以推送新 digest，发布身份可以读取和提升 verified 制品，清理任务只能删除明确不再引用的 staging 对象。任何一次提升都写 candidate_id、操作者或工作负载身份、审批和时间，回滚时直接引用旧 digest，不重新构建。

运行实例也要报告自己的制品身份。启动日志、健康接口和部署状态中至少暴露非敏感的 candidate ID、镜像 digest、模型 revision 与配置摘要。值班人员看到异常请求时，可以从实例反查流水线证据，而不必根据容器启动时间猜测当前版本。

## AI 评测和基础设施测试怎样放进同一准入

AI 服务的准入既要检查协议，也要检查模型与知识的行为。固定 Prompt 和 Tokenizer 可以检查输出结构、工具调用 Schema、引用 ID、停止条件和安全拒答；基础设施测试检查启动、就绪、取消、超时、限流和资源释放。两者结果在同一 candidate_id 下关联，但各自的失败原因仍然分开。

没有目标 GPU 时，静态阶段可以检查模型 Config、权重形状、量化字段、Tokenizer revision 和 vLLM 参数。目标 GPU 阶段再测显存峰值、TTFT、TPOT、并发和长上下文。把静态通过写成“性能达标”会让发布记录失去边界，也会让容量计划引用不存在的实测数据。

评测数据要有版本和权限。生产用户 Prompt 不应直接复制到公共 CI，脱敏样本仍可能包含租户信息。失败样本保存最小输入和结构化差异，模型回答原文按策略留在受控存储。重跑时固定采样、版本和环境，才能知道改动带来的变化。

## 发布审批怎样避免绿灯被误读

审批不是在流水线末尾点击“通过”就结束。规则可以自动检查签名、SBOM、测试报告、漏洞策略、模型许可证、Secret 扫描和候选状态，人工确认则处理业务范围、数据迁移、成本和回滚窗口。每一项审批都绑定摘要和版本，候选换了字节后应自动失效。

发布策略还应写拒绝原因。制品摘要不一致、模型 revision 未批准、迁移不兼容、候选没有 Ready、容量余量不足和恢复演练过期，都是不同的拒绝状态。把它们都显示成“门禁失败”会让下一次重试无法选择正确的修复动作。

审批准入后只允许提升同一制品。环境变量、Secret 和副本数可以按环境改变，但应用和模型 digest 不应改变。若生产需要重新构建，必须生成新的 candidate_id，重新跑测试、生成 SBOM 和签名，不能把紧急构建挂在旧审批记录上。

## 从提交到生产候选的一次完整推演

输入是 `COMMIT_SHA`、锁文件、基础镜像 digest、模型 revision 和目标环境配置。流水线先创建唯一 candidate_id，读取这些输入并生成构建上下文；接着在隔离 Worker 中拉取依赖和模型 Manifest，构建 API 镜像，运行单元、协议和静态制品检查，最后生成 SBOM、Provenance 和测试报告。

状态从 `created` 变成 `building`，构建成功后进入 `tested`，所有摘要和签名验证通过才进入 `verified`。发布控制器把 verified candidate 渲染成候选 Deployment，启动实例，等待存活、就绪和最小推理检查，再把它标记为 `candidate_ready`。正式流量切换属于下一篇的发布决策，这里只把候选交付给控制器。

调用顺序很重要：先锁输入，再构建，之后测试和生成证据，最后签名与发布准入。先签名再测试没有意义，测试过程中重新构建也会让签名对应错误的字节。每个阶段写入 event，事件带 candidate_id、attempt_id、制品摘要和状态修订。

假设模型下载在 `model_revision` 对应的第三个 shard 上返回 checksum mismatch。构建进程可能仍然成功，但候选不能进入 `tested`，因为模型输入不完整。失败证据包括对象 Key、声明摘要、实际摘要、下载尝试、Worker 身份和时间；重试同一固定 revision，仍失败就进入 `artifact_rejected`，不能换成 `latest` 继续。

验证结果至少检查四件事：Manifest 中的摘要能从 Registry 或对象存储重新读取；签名和 Provenance 的主体符合发布策略；测试报告引用的 digest 与候选一致；候选实例的日志和探针使用同一配置版本。只有这些断言都通过，`candidate_ready` 才有可靠含义。

## 这条流水线的边界和可运行范围

CI/CD 能把输入、构建、测试、证据和制品关系固定下来，不能替产品定义质量，也不能替运行平台解决容量和故障恢复。模型输出质量要由离线评测、在线观测和业务抽样共同判断；GPU 性能要在目标硬件和请求分布上压测；数据库迁移和流量切换需要独立的兼容与回滚流程。

本文中的 JSON、图和命令是流程级示例，没有执行真实 Registry 签名、私有模型下载或 GPU 候选部署。若落地，应把占位摘要替换成流水线实际生成值，运行 `cosign verify` 或等价工具核对签名，读取 SBOM 与 Provenance，最后用隔离环境恢复一次候选。

一个值得保留的停止条件是：无法回答“生产正在运行的具体字节由哪个源码、哪个模型 revision、哪个配置和哪个构建身份产生”，就不要继续扩大流量。能查询、能验证、能重放的制品链，才是 CI/CD 在 AI 系统里的实际交付物。
