# 模型制品、精度、量化与推理优化

同一个模型换成 INT4 后终于能加载，答案质量却在长上下文场景明显波动；FP16 版本能跑，换到 BF16 又因硬件支持不同而失败。精度和量化不是“越低越好”，而是制品、硬件、内核和质量约束共同决定的选择。

## 模型制品包含的不只是权重

| 制品 | 影响 |
| --- | --- |
| 权重分片与索引 | 参数存储、加载顺序和校验 |
| Tokenizer 与 Chat Template | 输入 Token、特殊符号和停止条件 |
| 量化配置与 Kernel | 反量化位置、支持的 GPU 和速度 |
| 模型 Revision 与许可证 | 复现、合规和回滚 |
| 校准数据/Scale | INT8/INT4 的误差分布和质量 |

只替换 safetensors 文件而不替换量化配置，可能得到“能打开但语义错误”的服务。每个可部署版本都应有 manifest，把权重、配置、Tokenizer、运行参数和评测证据绑定起来。

## 精度怎样影响容量账本

粗略估算权重显存可以写成：参数量 × 每参数字节数，再加上激活、工作区、运行时开销和 KV Cache。FP32 每参数 4 字节，FP16/BF16 通常是 2 字节，INT8/INT4 的存储更低，但实际还要加 scale、元数据和计算转换。这个公式只能做上界估算，不能替代引擎实测。

| 格式 | 容量优势 | 需要核对 |
| --- | --- | --- |
| FP32 | 基准精度和兼容性 | 显存成本、吞吐 |
| FP16/BF16 | 常见推理/训练折中 | Tensor Core 与算子支持 |
| INT8 | 更低权重占用 | 校准、Kernel 和质量 |
| INT4 | 显著压缩 | 长上下文、异常输入和反量化开销 |

## 量化验证要看失败样本

不要只用平均准确率比较。固定一组长短输入、结构化输出、代码、数字和多语言样本，比较拒答、格式、引用、停止和延迟。若质量下降集中在某种输入，模型注册表要记录能力边界，而不是写成“INT4 可替代 FP16”。

## 优化的顺序

先确认制品身份和基线，再测 Batch、KV、Prefix Cache、Kernel 和并行；最后才决定精度或量化。优化结果必须带模型 Revision、引擎版本、硬件、请求分布和时间窗口。下一阶段从 GPU 架构开始，解释为什么这些数字最终都落在计算和显存上。

## 质量门槛应当与业务契约相连

摘要模型可以接受少量措辞变化，结构化抽取、代码生成、工具调用和安全分类则更依赖格式与边界。量化评测不能只问“答案像不像”，还要检查 JSON 是否可解析、数字是否稳定、停止符是否正确、拒答是否保留，以及长上下文是否发生明显退化。

当某个 Revision 只适合低成本聊天，就在能力声明中写清楚，Gateway 不应把它路由给要求严格结构输出的 Agent。这样把量化选择从硬件技巧变成可治理的产品决策。

## 制品校验要在加载前失败

Serving 在加载权重前可以验证 manifest、文件长度、摘要、Tokenizer 与配置版本。校验失败应标记制品不可部署，而不是让实例反复 CrashLoop。对大型分片文件，流式哈希可以避免把全部内容读入内存。

量化格式的兼容性也属于制品元数据。即使参数量相同，不同布局和 Kernel 要求也会改变能否加载。模型注册表将这类约束变成显式能力，部署调度就不必靠启动失败来试错。
