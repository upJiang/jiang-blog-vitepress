# Linux 服务运行：从“启动失败”还原真实原因

模型容器反复重启，日志最后一行只有 `Killed`。这可能是内核 OOM Killer 结束了进程，也可能是容器内存上限触发，不能仅凭一个单词认定“GPU 显存不够”。Linux 排障的第一条规则是：先确认失败发生在哪一种资源和哪个进程，再讨论修复。

本篇建立一条固定证据链。输入是服务名、端口、时间范围和可复现操作；处理过程依次查看进程、日志、端口、权限、文件描述符、CPU、内存和磁盘；输出是一张能支持或否定假设的记录。

## 进程是运行状态的所有者

程序文件静静放在磁盘上，进程才拥有 PID、地址空间、线程、打开文件和信号处理。线程共享进程地址空间，因此一个线程泄漏内存会影响整个服务；子进程则有独立 PID 和资源统计，父进程退出后还可能留下孤儿或未回收的僵尸状态。

服务管理器或容器 Runtime 通常是父级控制者。它决定启动参数、环境变量、工作目录、重启策略和资源上限。排查时要同时看业务进程与控制者，不能只执行一次 `ps`。

## 固定顺序收集证据

下面的命令用于只读检查。把 `model-api`、PID 和端口替换为目标服务的真实值，并让时间范围覆盖故障发生前后。执行目标不是收集越多输出越好，而是回答“进程是否存在、为什么退出、端口由谁占用、资源是否接近边界”。

```bash
# 先看服务状态和最近日志，再定位 PID、端口与资源。
systemctl status model-api --no-pager
journalctl -u model-api --since "15 minutes ago" --no-pager
pgrep -af model-api
ss -lntp | grep ':8000'
ps -o pid,ppid,stat,etime,%cpu,%mem,rss,vsz,cmd -p 12345
cat /proc/12345/limits
ls -l /proc/12345/fd | wc -l
free -h
df -h
df -ih
journalctl -k --since "15 minutes ago" | grep -i -E 'oom|killed process'
```

`systemctl` 给出控制者看到的终态和退出码；`journalctl` 按统一时间线连接启动参数、应用异常和内核事件；`ss` 证明监听套接字是否建立以及属于哪个进程。`ps` 中的 `RSS` 是实际驻留内存，`VSZ` 是虚拟地址空间，两者不能互换。`/proc/<pid>/limits` 与 `fd` 数量可以支持“文件描述符耗尽”的判断。`df -h` 看容量，`df -ih` 看 inode；任一耗尽都可能让日志、临时文件或数据库写入失败。

## CPU、内存和磁盘要分别解释

CPU 高不一定是故障。持续计算可能是正常推理或分词，真正需要判断的是运行队列、单核饱和、上下文切换和请求延迟是否一起变化。一个进程显示 100% CPU，在多核机器上通常只代表一个逻辑核被占满。

内存问题至少分三层：进程 RSS、容器 cgroup 上限、宿主机总内存。应用捕获到 `MemoryError`、容器显示 OOMKilled、内核日志记录 killed process，三者对应不同证据。GPU 显存 OOM 通常出现在框架或驱动日志中，不会由 `free` 直接反映。

磁盘也不只看剩余 GB。日志滚动失败、inode 用尽、只读挂载、权限错误和写入延迟都会造成服务异常。删除文件后空间没有释放，可能是进程仍持有已删除文件描述符，应先用 `lsof +L1` 确认所有者，而不是继续随机删除目录。

## 端口和权限怎样形成故障

端口冲突表示已有套接字绑定相同地址与端口。先找出 PID，再确认它是旧实例、健康实例还是来源不明的进程。不要直接结束它，因为这可能把另一个正式服务当成残留进程。

权限问题要检查执行用户、文件所有者、目录每一级的搜索权限、挂载模式和安全策略。进程能读取配置文件，不代表能写日志目录；能绑定高端口，也不代表能绑定特权端口。把服务改成 root 只会扩大攻击面并隐藏错误的所有权设计。

## 信号决定服务怎样结束

正常停止通常先发送 `SIGTERM`，应用停止接收新请求，等待在途任务，刷新必要状态，然后退出。`SIGKILL` 无法被捕获，也不给应用清理机会。只有确认进程无法响应、并理解可能丢失的状态后，才把强制结束作为最后措施。

优雅退出还要有时间上限。模型请求可能持续很久，服务不应无限等待；到达 Deadline 后，应取消可取消的下游调用，把未完成任务保留为可恢复状态，再退出。控制者的停止宽限期必须大于应用自身排空预算。

## 用排障表收敛结论

| 问题 | 证据 | 支持的结论 | 下一步 |
| --- | --- | --- | --- |
| 进程是否启动 | 状态、PID、退出码 | 启动失败或运行后退出 | 查第一条异常和控制者配置 |
| 端口是否监听 | 地址、端口、PID | 未绑定、冲突或绑定错误地址 | 对照启动参数与实例身份 |
| 是否内存终止 | RSS、cgroup、内核日志 | 进程、容器或宿主机压力 | 还原峰值输入与资源上限 |
| 是否无法写入 | 容量、inode、权限、挂载 | 空间或所有权问题 | 明确文件生命周期和写入用户 |
| 是否能优雅停止 | 信号日志、在途请求、退出时间 | 排空成功或超时 | 调整取消传播与宽限期 |

一次合格排障应该能被别人复查：故障时间、目标实例、命令、关键字段、被否定的假设和最后结论都写清楚。只有证据落到具体资源和所有者，修复才不会从“重启看看”开始。
