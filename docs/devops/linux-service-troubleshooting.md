# Linux 服务是怎样运行的？从进程、端口到正常退出

把一个 Python 文件放到服务器上，它还不是服务。操作系统需要找到解释器和依赖，创建进程，允许进程读取配置与模型文件，再让它绑定一个网络地址。只有进程开始监听端口并能够处理请求，其他程序才能通过网络使用它。服务停止时，操作系统还要把信号交给进程，让它停止接收新请求、完成正在处理的工作并释放资源。

Linux 服务排障经常从一句“启动不了”开始。这句话可能表示命令根本没有执行、进程立即退出、进程仍在但端口没有监听、端口只绑定到本机、服务正在加载模型，或者请求已经到达却在应用内部失败。把这些状态分开，才能选择有意义的命令。

::: info Linux 服务的含义

**Linux 服务是长期运行并向其他进程提供能力的一个或多个进程。** 它通常读取配置，打开文件或设备，绑定本地端口，处理请求，并响应停止信号。systemd、Supervisor 或容器运行时可以管理它的启动与重启，但真正执行代码、占用内存和监听端口的仍是进程。

:::

## 程序文件怎样变成正在运行的进程

程序是磁盘上的代码和数据，进程是操作系统为一次执行创建的运行实例。相同的 Python 文件可以同时启动两个进程，它们有不同的进程号、内存、打开文件和网络连接。修改磁盘上的代码也不会自动改变已经运行的进程，通常需要重新启动，让新进程加载新文件。

Shell 执行 `python app.py` 时，最终会通过 `execve` 系统调用把当前进程映像替换成 Python 解释器。内核检查可执行文件、用户权限和参数，建立虚拟地址空间，装入动态链接器与共享库，再从程序入口开始运行。Python 随后解析脚本、导入模块、读取环境变量，应用框架才有机会创建网络 socket。

进程号（PID）只是当前启动实例的数字标识。进程退出后，PID 可以被系统重新使用，因此一份很久以前记录的 PID 不能单独证明当前进程身份。排障时同时核对启动命令、执行用户、启动时间、工作目录和可执行文件，避免把另一个服务当成目标实例。

可以把它想成一次有明确所有者的交接。Shell 或 systemd 负责发起执行，内核负责创建地址空间和文件描述符，解释器负责加载代码，应用负责读取配置并创建监听器。任何一段没有完成，后面的“服务已启动”都只是猜测。比如进程存在但 `ss` 没有监听端口，问题仍在初始化或 bind 阶段，不能直接把它归类为网络故障。

进程也有自己的资源账本。打开的模型文件、日志文件、socket、线程栈和子进程都由该实例持有；实例退出后，内核会回收其中大部分资源，挂载卷和外部数据库则不会自动消失。排障要分清哪些资源随进程生命周期结束，哪些需要应用或编排器显式清理。

下面的生命周期图把模型 API 从命令到退出的主要状态放在一条线上。任何一步失败，后面的状态都不会自动成立。

```mermaid
flowchart LR
  C[Shell 或服务管理器执行命令] --> E[内核执行 execve]
  E --> I[解释器和应用初始化]
  I --> F[读取配置、模型与日志目录]
  F --> B[bind 地址和端口]
  B --> L[listen 建立监听队列]
  L --> R[accept 并处理请求]
  R --> T[收到 SIGTERM]
  T --> X[停止接入、完成在途请求并退出]
```

图中 `bind` 和 `listen` 是两件事。`bind` 让 socket 占用一个本地地址与端口，`listen` 才把它变成被动接受连接的监听 socket。框架通常封装了这些系统调用，日志只显示“server started”，仍可以用操作系统命令核对真实状态。
## 进程状态告诉了什么，又没有告诉什么

`ps` 从内核暴露的进程信息中读取 PID、父进程、状态、CPU、内存和命令。找到进程说明它尚未退出，不说明初始化已经完成，也不说明它能正确回答请求。模型加载阶段可能持续占用 CPU 和磁盘，进程一直存在，端口尚未开放。

下面的命令适用于常见 Linux 环境，只读取状态。输入是服务关键字或已确认的 PID，输出需要结合目标环境解释。

```bash
pgrep -af 'python.*model_api'
ps -o pid,ppid,user,stat,lstart,etime,%cpu,%mem,cmd -p 2481
readlink -f /proc/2481/exe
readlink -f /proc/2481/cwd
tr '\0' ' ' < /proc/2481/cmdline
```

`pgrep -af` 会同时显示 PID 和完整命令，结果为空可能表示进程已退出，也可能是匹配表达式不对。`STAT` 中的 `R` 表示正在或等待 CPU，`S` 表示可中断睡眠，`D` 常见于不可中断的 I/O 等待，`Z` 是已经退出但父进程尚未回收的僵尸进程。状态只是一瞬间的快照，需要结合持续时间、日志和资源变化判断。

`PPID` 指向父进程。服务由 systemd 启动时，父子关系和 cgroup 能帮助确认管理边界；由 Shell 后台启动时，终端关闭可能影响进程。容器内的主进程通常是 PID 1，它承担信号转发与子进程回收责任。仅使用 `nohup` 并不能提供健康检查、重启策略和一致日志管理。

若进程立即消失，先查看退出码和首次错误。服务管理器不断自动重启会让日志快速滚动，也可能掩盖相同的确定性错误。保存最早一次启动输出，再决定是否重试，比连续执行 restart 更容易找到缺失文件、非法参数或导入失败。
## 环境变量和工作目录为什么会改变同一条启动命令

进程除了命令行参数，还会继承环境变量、当前工作目录、用户和资源限制。开发者在登录 Shell 中运行成功，systemd 启动失败，常见原因不是代码发生变化，而是这几项输入不同。Shell 配置文件里的 `PATH`、代理和虚拟环境通常不会自动进入系统服务。

工作目录决定相对路径从哪里解析。代码写 `open("config.yaml")` 时，内核不会去源码目录寻找，它把路径拼到进程当前工作目录。命令在项目目录执行可以读到文件，服务管理器默认从其他目录启动就会返回 `ENOENT`。使用明确绝对路径或在服务定义中设置 `WorkingDirectory`，比依赖操作者先 `cd` 更可复现。

环境变量也是进程启动时的快照。登录终端里执行 `export MODEL_PATH=/srv/models/chat`，只会影响当前 Shell 及其后代，不会修改已经运行的服务。敏感变量不能直接输出到排障日志，读取 `/proc/<pid>/environ` 也需要权限并可能暴露凭证。核对时只确认变量是否存在、来源文件和非敏感配置，Secret 值使用受控方式验证。

```bash
systemctl show model-api \
  -p User -p Group -p WorkingDirectory -p EnvironmentFiles \
  -p ExecStart -p LimitNOFILE -p MemoryMax
sudo -u model-api -- /usr/bin/env -i \
  PATH=/usr/local/bin:/usr/bin \
  MODEL_PATH=/srv/models/chat \
  /opt/model-api/venv/bin/python -m app --check-config
```

第一条读取 systemd 最终采用的配置，避免只看某个 unit 文件片段而忽略 drop-in。第二条用干净环境模拟服务用户执行配置检查，命令和路径要按实际应用替换。它不会证明网络与模型推理已经可用，只用于缩小“登录环境能运行、服务环境不能运行”的差异。

应用依赖当前时区、locale、临时目录或代理时，也要把这些输入写进部署合同。未声明的环境依赖会让同一制品在两台机器上产生不同结果。更改环境变量后必须让进程重新执行，reload 是否生效取决于应用是否实现了重新读取，不能从配置文件已修改推断运行状态已经变化。
## 端口是什么，进程怎样开始监听

IP 地址标识网络接口，端口是传输协议中的 16 位编号，用来把到达一台主机的连接交给不同 socket。服务监听 `127.0.0.1:8000` 时，只接受本机回环接口的 IPv4 连接；监听 `0.0.0.0:8000` 表示接受所有本地 IPv4 接口收到的连接。端口相同而地址不同，有时可以同时绑定，具体还受 socket 选项和地址族影响。

应用创建 socket 后调用 `bind`。内核检查该地址是否属于本机、端口是否已被占用、进程是否有权限。绑定成功后调用 `listen` 建立等待连接的队列，客户端的 TCP 连接才能被内核接受。应用再调用 `accept` 取得一个已连接 socket，用它读取 HTTP 字节。

端口冲突不是“网络坏了”，而是另一个 socket 已占用不允许共享的地址和端口。占用者可能是旧进程，也可能是正常运行的另一个服务。直接结束 PID 有可能中断正式流量，必须先确认进程身份、监听地址、启动来源和连接情况。

```bash
ss -ltnp 'sport = :8000'
sudo lsof -nP -iTCP:8000 -sTCP:LISTEN
systemctl status model-api --no-pager
```

一段解释性的 `ss` 输出可能如下：

```text
State  Recv-Q Send-Q Local Address:Port Peer Address:Port Process
LISTEN 0      2048   127.0.0.1:8000    0.0.0.0:*     users:(("python",pid=2481,fd=7))
```

这行说明 PID 2481 的 Python 进程用文件描述符 7 监听本机回环地址的 8000 端口。其他机器访问服务器公网 IP 的 8000 端口不会命中这个 socket。若期望由 Nginx 在同机反向代理到该服务，绑定回环地址可能正合适；若期望容器或另一台主机直连，就需要核对网络边界，而不是机械改成 `0.0.0.0`。

`Recv-Q` 与 `Send-Q` 在监听和已连接 socket 上含义不同。观察到非零队列不能只凭一行快照断言应用处理不过来，要结合持续采样、连接状态和应用延迟。端口已经 LISTEN 也只证明内核建立了监听 socket，健康接口和真实推理仍可能失败。
## 权限为什么会在读取文件、写日志和绑定端口时分别失败

Linux 权限围绕用户、组和对象的访问位工作。进程继承启动用户的有效身份，读取文件时需要文件读权限，也需要沿路径每一级目录的搜索权限。`/srv/model/config.yaml` 本身可读，如果 `/srv/model` 目录没有执行位，进程仍无法到达这个文件。

写日志需要目标文件或目录的写权限。进程能读取配置，不代表能创建 `/var/log/model-api/service.log`。挂载目录还可能带有只读模式，容器内看到的 UID 与宿主机文件所有者也可能不一致。把进程改成 root 会扩大它能访问和破坏的范围，并把错误的所有权设计隐藏起来。

低于 1024 的端口在常见 Linux 配置中属于特权端口，普通进程通常不能直接绑定。更常见的部署方式是让 Nginx 或负载均衡器监听 80/443，应用监听高端口。也可以通过 capability 精确授权，但需要理解能力继承、容器配置和攻击面，不能把 `setcap` 当成通用修复命令。

```bash
id
namei -l /srv/model/config.yaml
stat -c '%A %U:%G %n' /srv/model/config.yaml /var/log/model-api
findmnt -T /var/log/model-api -o TARGET,SOURCE,FSTYPE,OPTIONS
```

`id` 显示当前用户和组，服务管理器里的 `User=` 可能与登录 Shell 不同。`namei -l` 展开路径各级权限，比只看最终文件更容易发现目录不可进入。`findmnt` 能确认目标目录来自哪个挂载以及是否只读。修复时按服务真正需要的最小权限调整所有者、组或挂载，不给无关目录开放全局写权限。

权限拒绝应在日志或系统调用中留下 `EACCES`、`Permission denied` 等证据。若应用只捕获异常并返回“初始化失败”，可以在隔离环境使用 `strace -f -e trace=file,network` 观察失败的系统调用。`strace` 会增加开销并可能看到敏感路径，生产环境使用前要控制范围和输出。
## 文件描述符为什么会让正常进程突然不能接收请求

Linux 用文件描述符表示进程打开的文件、socket、管道和部分设备。它是进程表中的小整数，不只用于磁盘文件。每接受一个网络连接、打开一个日志或建立一个上游连接，都可能消耗描述符。

进程有软限制和硬限制。软限制是当前可用上限，进程可以在硬限制范围内调整；服务管理器也可能设置独立限制。达到上限后，`open`、`socket` 或 `accept` 返回 `EMFILE`，应用可能表现为无法打开日志、无法连接数据库或拒绝新请求。

```bash
cat /proc/2481/limits | sed -n '/open files/p'
ls /proc/2481/fd | wc -l
sudo lsof -p 2481 | awk '{print $5}' | sort | uniq -c
```

第二条命令给出当前描述符数量，不能单独证明泄漏。需要在相似负载下连续观察：请求结束后连接是否回收，文件数量是否持续单调增长，连接池上限是否符合配置。提高限制可以缓解容量不足，若应用忘记关闭文件或连接，数值只会晚一些再次耗尽。

连接的另一端也有上限。API 描述符充足，PostgreSQL 达到连接数上限时仍会失败；反向代理、客户端和内核连接跟踪表也可能成为边界。排查要确认错误由哪个进程返回，不能看到“too many open files”就只修改当前 Shell 的 `ulimit`。
## 线程和子进程为什么会改变资源与退出行为

一个服务进程可以包含多个线程。线程共享进程地址空间和大部分文件描述符，各自有调用栈与调度状态。Python Web 服务还可能启动多个 Worker 进程，每个进程分别加载应用，拥有独立堆、连接池和监听行为。观察到一个服务名称，背后不一定只有一个执行单元。

多进程可以利用多个 CPU 核并隔离部分故障，代价是内存和外部连接按进程增加。四个 Worker 各自创建二十条数据库连接，数据库看到的上限接近八十，而不是二十。每个 Worker 都加载一份模型到 GPU 还可能立即耗尽显存。部署参数必须和进程模型一起理解。

线程卡住时，进程仍然存在，健康接口也可能由其他线程返回成功。`ps -L -p <pid>` 可以查看线程，`top -H -p <pid>` 观察各线程 CPU。进一步的栈分析要使用语言运行时工具或调试器，并注意暂停、性能和敏感数据风险。单凭线程数量无法判断泄漏，线程池会长期保留空闲线程。

子进程退出后，父进程需要调用 `wait` 回收退出状态。没有回收会留下僵尸进程，它不再执行代码，也几乎不占内存，却保留进程表项。容器中的 PID 1 若不处理 `SIGCHLD`，频繁启动外部命令可能积累僵尸。使用能够转发信号和回收子进程的入口，或者让应用本身正确承担 PID 1 责任。

停止服务时，信号通常先到主进程。主进程要通知 Worker 停止接收新任务，再等待它们退出。直接向某一个 Worker 发送 SIGKILL 可能触发管理器自动补充新 Worker，表面上 PID 消失，服务仍在运行。确认服务管理边界后，通过相应管理器执行停止，才能让期望状态和实际进程一起变化。
## 日志怎样成为时间线，而不只是错误文字

日志是进程主动写出的事件，不是内核对真实状态的完整记录。应用没有走到初始化日志，可能在解释器加载或导入阶段退出；日志写入失败时，进程也可能继续运行却没有文件。排障要把日志和进程、socket、系统调用证据放在同一时间线上。

结构化日志至少需要时间、级别、组件、实例和请求 ID。启动日志还应记录不敏感的版本、配置来源和监听地址。不能记录完整 API Key、Authorization、Prompt、响应正文或数据库密码。为了查问题把敏感内容长期写入日志，会把可观测性系统变成新的数据泄露面。

systemd 管理的服务通常把标准输出和标准错误送进 Journal。下面的命令按 unit 和启动时间读取，不会修改服务：

```bash
systemctl status model-api --no-pager -l
journalctl -u model-api --since '-15 min' --no-pager -o short-iso
journalctl -u model-api -b -p warning..alert --no-pager
```

`status` 只展示有限的最近日志，完整时间窗口用 `journalctl`。`-b` 限制当前系统启动，适合区分重启前后的事件。没有日志不能直接得出“请求没到应用”，还要核对日志级别、采样、输出目标、磁盘和进程权限。

日志轮转也会影响取证。应用持续持有旧日志描述符时，轮转程序把文件重命名后，新事件仍写入旧 inode。删除文件名不一定释放空间，也可能让操作者误以为应用停止记录。应用支持 reopen 时可在轮转后发送约定信号；更简单的做法是写标准输出，由运行环境统一收集和轮转。

请求日志应在入口和结束各留下必要状态。入口记录 request_id、方法、路径模板和调用身份的脱敏标识；结束记录状态、耗时、输出大小和错误码。流式请求不能等连接关闭才记录所有信息，否则异常断开时没有中间进度。阶段事件要能够用同一个请求 ID 关联，同时避免每个 Token 写一条高成本日志。
## systemd 管理了什么，应用仍要负责什么

systemd 的 unit 描述启动命令、依赖、用户、环境、资源限制和重启策略。它维护“服务应该运行”的期望状态，进程异常退出后可以按策略重启。它不理解模型是否回答正确，也不会自动处理业务事务、消息幂等和流式取消。

`After=network.target` 只规定启动顺序，不保证数据库、DNS 或外部 API 已经可用。应用连接依赖时仍需设置超时和有限重试。重试必须区分临时不可用与确定性配置错误，密码错误和 schema 缺失不会因为无限重启自动恢复。

下面是一段解释性 unit，用来说明字段关系，路径和用户必须按实际环境替换：

```ini
[Unit]
Description=Model API
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=model-api
Group=model-api
WorkingDirectory=/opt/model-api
EnvironmentFile=/etc/model-api/runtime.env
ExecStart=/opt/model-api/venv/bin/python -m app --host 127.0.0.1 --port 8000
Restart=on-failure
RestartSec=5s
LimitNOFILE=65536
TimeoutStopSec=90s
KillSignal=SIGTERM

[Install]
WantedBy=multi-user.target
```

`Restart=on-failure` 让非正常退出触发重启，正常停止不会反复拉起。它仍可能掩盖快速失败，所以要配合启动频率限制和告警。`TimeoutStopSec` 是 systemd 等待退出的时间，超过后会继续终止流程；应用的请求 Deadline 应小于可用宽限，并提前停止接收新流量。

unit 修改后运行 `systemctl daemon-reload` 只是让管理器重新读取定义，不会自动重启进程。重启会中断服务，生产环境需要副本、摘流和回滚安排。`systemctl show` 可以看到合并 drop-in 后的最终值，避免编辑的文件不是当前 unit 实际加载来源。

systemd 还使用 cgroup 组织进程并施加 CPU、内存和任务数量限制。服务主进程创建的子进程通常留在同一 cgroup，停止 unit 时可以一起管理。容器和 Kubernetes 也建立 cgroup，下一层资源限制可能比 systemd 更小。看到宿主机资源充足时，仍要确认进程所在 cgroup 的限制和事件。
## 内存、显存和磁盘不足分别留下什么证据

进程使用虚拟内存，操作系统把地址映射到物理内存、文件或交换空间。`RSS` 近似表示当前驻留物理内存的页面，`VSZ` 包含更大的虚拟地址范围。Python 分配器、共享库、文件缓存和多进程复制都会影响数字，不能把 VSZ 直接当成实际占用。

系统内存紧张时，内核可能回收缓存、进行交换，严重时由 OOM Killer 选择进程终止。此时应用日志可能突然停止，退出码常表现为收到 `SIGKILL`，真正原因在内核日志。容器和 systemd cgroup 还可能有更小的内存限制，即使宿主机仍有空闲内存，进程也会在自己的 cgroup 内触发 OOM。

```bash
free -h
ps -o pid,rss,vsz,%mem,cmd -p 2481
cat /proc/2481/status | sed -n '/VmRSS\|VmSize\|Threads/p'
journalctl -k --since '-15 min' | grep -i -E 'out of memory|killed process'
```

GPU 显存由设备和驱动管理，不包含在进程 RSS 中。模型加载失败显示 CUDA out of memory 时，增加系统交换空间通常不能解决问题。要用 `nvidia-smi` 或推理引擎指标核对权重、KV Cache 和其他进程的设备占用。系统内存、GPU 显存是两个资源池，错误信息和恢复动作不同。

磁盘满会让日志、临时文件、数据库和模型下载失败。`df -h` 看文件系统块空间，`df -i` 看 inode；删除一个仍被进程打开的大文件，目录里看不到它，空间要等描述符关闭后才释放。`lsof +L1` 可以寻找已经删除但仍打开的文件。清理前先确认文件归属和保留策略，不能在来源不明的目录执行批量删除。
## SIGTERM 和 SIGKILL 为什么产生不同结果

信号是内核通知进程发生事件的一种机制。`SIGTERM` 表示请求进程终止，应用可以注册处理器，停止接收新请求，等待正在处理的任务，刷新必要状态并退出。它可以被捕获、处理或忽略。服务管理器和容器停止通常先发送 SIGTERM，再等待一个宽限期。

`SIGKILL` 由内核立即终止进程，应用无法捕获，也没有机会执行清理代码。它适合进程已经无法响应且必须终止的最后手段，不适合作为日常重启方式。数据库写入、队列任务、流式回答和临时文件可能停在中间状态，后续需要依靠事务、幂等或恢复流程处理。

优雅退出还取决于时间预算。模型请求可能持续几十秒，停止宽限只有十秒时，应用无法等待所有请求。入口应先停止发送新流量，应用标记不再就绪，再等待在途请求到 Deadline。后台任务如果能持久化检查点，可以在其他 Worker 恢复；无法恢复的任务要返回明确终态。

```bash
kill -TERM 2481
for second in 1 2 3 4 5; do
  ps -p 2481 -o pid=,stat=,etime= || break
  sleep 1
done
ss -ltnp 'sport = :8000'
```

这组命令向已确认身份的进程发送 SIGTERM，并观察它是否退出和释放端口。生产环境还要通过服务入口确认实例已经摘流，避免在仍接收请求时终止。进程退出后端口不再监听只是一个结果，还应检查任务终态、连接池、临时文件和下一次启动的恢复日志。
## 沿生命周期完成一次排查

假设 `curl http://127.0.0.1:8000/health` 返回 connection refused。先确认命令使用的地址和端口，再用 `ss` 检查是否监听。没有监听时查看目标进程是否存在；进程不存在，读取服务状态、退出码和最早日志；进程存在，核对它是否仍在加载、是否绑定了不同地址，或者在 `bind` 前因权限和文件错误停住。

如果 TCP 可以连接，但健康接口返回 503，网络层已经完成，证据转到应用初始化。检查模型加载状态、数据库连接和 readiness 条件。健康接口返回 200，而真实推理超时，再看请求日志、队列、CPU、GPU 和上游依赖。每一步都使用上一层的结果决定下一步，不把所有命令无差别执行一遍。

| 观察结果 | 当前能确认的事实 | 还不能确认的事实 |
| --- | --- | --- |
| `ps` 能找到 PID | 进程尚未退出 | 初始化完成、端口监听、业务健康 |
| `ss` 显示 LISTEN | 内核建立了监听 socket | HTTP 路径正确、模型可推理 |
| `nc` 连接成功 | TCP 连接可建立 | TLS、HTTP、鉴权和业务结果 |
| 健康接口 200 | 探针定义的条件成立 | 所有模型、所有依赖和回答质量正常 |
| SIGTERM 后 PID 消失 | 该进程已经退出 | 在途任务和外部副作用都已一致结束 |

服务恢复后要重复原始输入，而不是只看重启命令返回成功。记录新的 PID、版本、监听地址、健康结果和一次最小业务请求；若故障涉及资源泄漏，还要在一段可比负载下观察资源是否稳定。Linux 提供的进程、文件和 socket 证据回答了服务在一台机器里的状态，下一篇继续解释请求离开客户端后怎样经过 DNS、TCP、TLS 和 HTTP 到达这个进程。

可以把完整回放写成一条不修改系统的证据链。输入是服务名、预期端口和健康路径；先读 unit 最终配置与当前状态，再确认 PID 身份、执行用户和工作目录，随后检查监听 socket，最后发起本机 HTTP 请求。任何一步失败就停在该层读取日志，不要继续用后续成功掩盖前面的差异。

```bash
systemctl show model-api -p ActiveState -p SubState -p MainPID -p ExecMainStatus
main_pid=$(systemctl show model-api -p MainPID --value)
ps -o pid,ppid,user,stat,lstart,etime,cmd -p "$main_pid"
ss -ltnp 'sport = :8000'
curl -fsS --connect-timeout 2 --max-time 5 http://127.0.0.1:8000/health
```

这里的变量只保存读取到的 PID，没有执行结束进程或修改服务的动作。`MainPID=0` 表示当前没有可报告的主进程，应回到状态和日志。`curl` 失败时保留错误输出和时间，connection refused、连接超时、HTTP 503 与 JSON 解析错误代表不同阶段，不能合成一个“健康检查失败”。

修复完成后使用同一组输入复测，并加上一条最小业务请求。若修复的是权限，确认服务用户能够访问所需文件，同时仍不能读取无关 Secret；若修复的是描述符，观察连接结束后数量回落；若修复的是退出流程，确认 SIGTERM 期间不再接收新请求，在途请求按合同完成或取消。复测结果需要回答原始故障是否消失，也要确认修复没有扩大权限或留下新资源泄漏。
