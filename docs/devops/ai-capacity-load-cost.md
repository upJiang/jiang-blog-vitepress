# 容量规划是什么？怎样从请求、队列和延迟估算 GPU 与成本

“一张 GPU 能撑多少并发”没有脱离模型和请求的固定答案。200 个短 Prompt 与 20 个长 Prompt 可能产生相同请求数，却有完全不同的 Prefill、KV Cache 和输出工作量。模型精度、Batch、上下文、GPU 型号、延迟目标和取消率都会改变有效容量。只把官方峰值 FLOPS 除以参数量，得不到用户能感知的 TTFT 和 TPOT。

容量规划要把真实请求分布变成可测工作负载，先估算，再在目标硬件压测，最后加入故障、发布和增长余量。结果不是一个永久数字，而是一组前提下的容量区间、过载行为和成本。本文使用解释性数字演算，不代表任何具体 GPU 或模型实测。

::: info 容量规划的准确含义

容量规划是根据需求到达率、请求形状、服务时间、SLO、资源效率、故障和增长，估算需要多少实例、GPU、CPU、内存、存储和网络，并设计扩缩容与过载保护的过程。

AI 容量规划还要按输入 Token、输出 Token、Prefill、Decode、KV Cache 和 Batch 拆解。估算用于形成候选，压测和生产观测才提供实际容量证据。

:::

## 请求数为什么不是足够的工作负载单位

一个请求包含输入 Token、最大或实际输出 Token、模型、采样、流式、工具、RAG 上下文和 Deadline。输入长主要增加 Prefill，输出长主要增加 Decode 与 KV Cache 生命周期。两个请求都计数 1，计算和显存成本可以相差几十倍。

工作负载至少按模型、输入 Token 桶、输出 Token 桶、到达时间、流式、优先级和租户分类。桶不必极细，但要保留 p50、p95、p99 和最大合法值。平均值只用于粗算，不能代表容量边界。

到达过程也重要。稳定每秒 10 请求与一分钟内集中 600 请求有相同平均 RPS，后者会形成队列。开环负载按外部到达率发送，能观察过载；闭环客户端等待上一次完成再发，容易把服务变慢自动变成发送变少。

取消与重试属于负载。客户端超时后若后端继续生成，GPU 做了用户不可见工作；重试又增加一条请求。容量报告要统计 accepted、completed、canceled、rejected 和 wasted tokens，而不是只看成功响应。

RAG 和 Agent 还会产生下游放大。一次用户请求可能有三次模型调用、两次检索和四个工具。容量按根请求数估算会低估。运行 Trace 中的步骤分布和 Token 使用要进入工作负载模型。

容量规划描述的是在给定需求和约束下，系统可以持续承受多少工作，并在过载时怎样拒绝、排队或降级。它不是把“每秒请求数”乘一个经验倍数，也不是只看 GPU 利用率。请求形状、到达过程、服务时间、尾延迟、资源占用、故障余量和成本都属于同一个估算问题。

例如两个 API 都收到 10 RPS，一个请求平均 200 输入 Token、50 输出 Token，另一个有 8,000 输入 Token、1,000 输出 Token，它们的 Prefill、Decode、KV Cache 和网络传输完全不同。估算应先按模型和 Token 桶拆开，再用目标硬件测服务时间，最后把队列、取消、发布和一台 GPU 故障纳入余量。平均请求数只能是入口，不是结论。

容量规划与压测的区别也要写清。规划先用假设推导候选副本和成本，压测在固定版本、固定硬件和固定分布上验证实际 TTFT、TPOT、吞吐与错误；生产观测再检查工作负载是否变了。三者没有任何一个可以替代另外两个。

```text
输入：到达率、输入/输出 Token 分布、SLO、模型与硬件
状态：队列、running sequences、KV blocks、GPU 与连接池
输出：安全吞吐、p95/p99 延迟、拒绝条件、GPU 副本与单位成本
失败证据：队列持续增长、OOM、超时、取消浪费或容量余量耗尽
验证：同版本开环压测与生产窗口对账
```

这段计算过程把容量表中的字段和可观察状态对应起来。若压测只产生闭环请求，服务变慢会让发送端自动变慢，看起来好像系统没有过载；若只报告平均延迟，则尾部排队和长上下文请求会被隐藏。

## 吞吐、并发和延迟是什么关系

吞吐是单位时间完成的请求或 Token，并发是某时刻系统中的请求数，延迟是单个请求从进入到完成的时间。它们相关但不等价。增加并发可以让 GPU Batch 更大、吞吐上升，也会增加排队和单请求等待。

Little 定律在稳定系统中给出 `L = λW`：系统平均在途数量 L 等于平均到达率 λ 乘平均逗留时间 W。若每秒到达 5 个请求，平均在系统中 4 秒，平均在途约 20。它包括等待和执行，不是“需要 20 个线程”。

当到达率接近或超过可服务率，队列不再稳定，Little 定律的有限平均前提被破坏。等待持续增长，用户取消和重试进一步增加负载。容量计划不能把压测中短暂达到的极限吞吐当成长期安全到达率。

分位数不能从平均值直接推导。平均 2 秒可能同时存在 p99 20 秒。SLO 通常约束 p95/p99 TTFT、TPOT 或完成时间，副本数要在目标分位数下满足，而不是让总吞吐最大。

并发上限还受 KV Cache。运行 100 条短序列可能可行，100 条长序列会耗尽 Cache。Engine 的最大序列、最大 Batched Token 和 Block Pool 共同决定准入，Gateway 的并发只能是第一层保护。

## Prefill 和 Decode 怎样分别估算压力

Prefill 一次处理 Prompt Token，矩阵较大，通常更偏计算。其工作量与输入 Token、Batch、隐藏维和模型层数有关。相同模型和硬件下，可以用每秒 Prompt Token 与 TTFT 分布作为实测指标，不直接拿理论 FLOPS 换算。

Decode 每一步为每条活跃序列生成一个 Token，单步矩阵较窄，Batch 增大可提高权重复用。输出 Token/s、TPOT 和 running 序列描述 Decode 容量。长输出让序列在系统中停留更久，也让 KV Cache 增长。

Chunked Prefill 和 Continuous Batching 会让两类工作交错。长 Prefill 若一次占满 Batch，短请求 TTFT 受影响；切块后调度更公平，但参数和 Kernel 开销改变。容量压测使用真实引擎配置，不能把 Prefill 与 Decode 当完全独立服务器。

一个粗略工作量可以写成每秒输入 Token 与每秒输出 Token 两条曲线。假设峰值每秒 4 个请求，p95 输入 2000、平均输入 600，平均输出 150。平均工作量约 2400 input tokens/s 和 600 output tokens/s；p95 场景不能简单把两个 p95 同时相乘，需要真实联合分布。

上下文还影响 KV Cache。每 Token Cache 字节乘活跃 Token 得到容量估算，运行峰值与并发共同限制。即使计算吞吐够，Cache 不够也会拒绝或抢占。因此容量有计算、显存和 SLO 三个上限，取最小值。

## 服务时间和排队怎样进入副本估算

单实例在给定负载下有服务能力 μ。若稳定到达率 λ 接近 μ，排队延迟会非线性上升。生产通常不把目标利用率设在理论极限，留出突发、长请求和故障余量。具体安全利用率由压测曲线与 SLO 决定，不套固定 70%。

可以先用粗算得到下限：峰值有效 Token 工作量除以单实例在 SLO 内的 Goodput，再向上取整。Goodput 只统计完成且满足 TTFT/TPOT 的请求或 Token。然后用混合请求压测验证队列和分位数。

例如工作负载需要 900 output tokens/s，某候选实例在目标 p95 下能提供 260 output tokens/s，理论至少 `ceil(900/260)=4` 个实例。若要容忍一实例故障且不让剩余超过目标，可能需要 5 个；发布 Surge 和区域故障还要另算。

队列必须有上限和 Deadline。副本不足时允许短暂等待，超过阈值返回过载比无限排队更可控。队列长度转成等待时间要使用当前服务率和请求 Token 估计，不是固定“100 个请求”。

多模型共享实例池时，服务率取决于混合和路由。一个高成本模型不能用另一个小模型的 Token/s 抵消。按模型或能力池分别测量，再决定是否共享和公平队列。

## Little 定律怎样做一次解释性计算

假设工作日高峰平均到达率为 3 request/s，平均端到端时间 6 秒。稳定条件下，平均在途 `L = 3 × 6 = 18`。其中 10 个可能在 waiting，8 个 running。这个数字帮助检查监控是否量级合理，不直接决定副本。

若目标把平均时间降到 4 秒，而到达率不变，平均在途应接近 12。增加副本后 waiting 下降，若实际仍有 18，可能请求形状变长或下游工具耗时。Little 定律提供对账，不说明具体优化动作。

对 Agent 任务，平均时间 30 秒、到达率 0.5 task/s，平均在途约 15。每个任务又平均调用模型 3 次，因此模型调用到达约 1.5/s，但调用时长与 Token 不同。Runtime Worker 与模型实例要分别建容量模型。

平均公式会隐藏突发和长尾。若 10 秒内集中 100 个请求，短时间在途远高于 18。队列、Autoscaler 冷启动和过载要用时间序列模拟或开环压测。p95 不能代入 Little 定律假装得到 p95 并发。

计算前确认系统接近稳定：观察窗口内到达、完成、拒绝和队列没有持续漂移。若队列一直增长，W 仍在变化，有限平均结果没有容量意义。此时先找到安全服务率和过载边界。

## 压测怎样得到可用的 Goodput

压测固定模型 Revision、镜像、GPU、驱动、引擎、参数和数据集。请求集包含真实的输入/输出 Token 联合分布、流式比例、采样和缓存命中，敏感内容用合成或脱敏样本。客户端有足够 CPU、网络，并与服务时钟对齐。

先 Warmup，再分阶段增加开环到达率。每阶段等待状态稳定，记录 p50/p95/p99 TTFT、TPOT、总延迟、完成、拒绝、取消、waiting、running、Batch、Cache、显存和功耗。发现错误或队列持续增长时停止增加。

Goodput 的定义示例是“在 TTFT 与 TPOT SLO 内完成的 output Token/s”。总 Token/s 包含超时、取消和慢请求，不能直接作为有效容量。不同模型的 Goodput 不能无条件相加。

测试持续时间要覆盖 Cache、热状态和周期性行为。几分钟测试可能只看到模型热、没有节点抖动；长测试能发现内存爬升、碎片和取消回收。容量候选至少重复运行，报告方差与异常。

改变 Batch、最大序列、量化或并行参数时，每次只改一组变量并重跑正确性。更高吞吐若质量、SLO 或错误变差，不是可用提升。没有目标 GPU 的环境只验证压测脚本、请求分布和统计公式。

## 余量怎样覆盖故障、发布和增长

故障余量确保一台实例或一个 Node 离线时，剩余容量仍满足核心 SLO 或有明确降级。N+1 是常见起点，不同区域和共享故障域可能需要更多。两副本跨两个 Node，只坏一个就损失 50%，风险与十副本损失一个不同。

发布余量用于新旧版本并存、模型下载和 Warmup。GPU 独占池没有 Surge 设备，RollingUpdate 可能先减少可用副本。候选发布要把额外 GPU 和对象存储流量进入计划，不把验证资源当免费。

增长余量来自业务预测和不确定性。短期活动、租户迁移和模型上下文升级会改变 Token 分布。使用情景而非单点：基线、峰值、故障、发布和增长后峰值，分别计算需求。

过多余量会增加成本，过少会让 Autoscaler 永远追赶。冷启动时间越长，提前预热的比例越高。可以用预热池、定时扩容、较小备用模型或有界排队降低代价，各自有服务合同。

余量要按最紧资源。GPU 计算有 30% 空闲，但显存 Cache 只剩 5%，仍不能接长请求；GPU 足够而 CPU Tokenize 满，增加 GPU 无效。容量表同时列 GPU、显存、CPU、主存、网络和对象存储。

## 自动扩缩容怎样避免只追 GPU 利用率

扩容信号可以使用 waiting Token、排队时间、SLO 消耗、running 序列、预计工作量和 Ready 容量。GPU utilization 作为辅助，不能单独触发。每个模型池或优先级队列分别观察，避免平均后看不见局部压力。

控制器计算 desired replicas 时，需要当前 Ready、Warming、Pending 和计划删除的副本。Warming 已占 GPU 但没有容量，Pending 可能等待 Node 扩容。只看 Deployment replicas 会高估可服务资源。

扩容有冷却和最大步长，防止一个尖峰一次创建大量昂贵 Node。缩容更保守，先移流量、Drain、等待 Cache 和任务清空。最近扩出的实例至少运行一定时间，避免模型刚加载就被缩掉。

Autoscaler 自身失败时，Gateway 仍有过载保护。无限队列不是扩容替代，Node 创建失败也不能让请求永远 waiting。拒绝率进入容量告警，值班人员能看到供给没有跟上。

验证用时间变化负载：稳定、突发、持续增长、一个实例故障和流量回落。观察触发时间、Ready 时间、SLO、拒绝、成本和缩容。只证明 Pod 数变化，不代表扩缩容对用户有效。

## 成本怎样从 GPU 小时变成单位请求

基础成本包括 GPU、CPU、主存、磁盘、网络、监控和平台。GPU 小时按实际实例运行时间计，候选、Warmup、空闲和回滚实例都要算。云 API 则按 Token、请求或工具价格结算，价格版本随请求固定。

单位请求成本可以用窗口总成本除以成功请求，但请求长度差异大。单位 output Token 或总 Token 更适合模型比较，Agent 任务还要加工具与多轮调用。Goodput 成本只分摊到 SLO 内成功结果，能暴露浪费。

示例：5 张 GPU 每小时各 3 个成本单位，窗口运行 1 小时，总 GPU 成本 15。完成 9000 个 SLO 内请求，GPU 部分约每千请求 1.67；若输出 180 万 Token，约每百万输出 Token 8.33。这个计算未含其他资源，也不是实际价格。

取消后继续生成、失败重试、冷启动和空闲都提高单位成本。监控按 model revision、region 和 workload class 分摊，不能把内部测试流量计入付费用户产出。账务事件与 Metric 对账，避免抓取丢失导致低估。

成本优化要同时看 SLO 和质量。量化降低权重或提高吞吐，但需要质量回归；共享提高利用率但可能增加抖动；缩小余量降低空闲却增加故障风险。任何“节省百分比”都要来自相同负载和窗口实测。

## 工作负载数据怎样从生产请求中采集

Gateway 在不记录原文的前提下，可以统计模型、输入 Token、最大和实际输出 Token、流式、状态、租户等级、到达时间和 Deadline。Serving 补充 waiting、running、Batch、Cache、TTFT 与 TPOT。Agent 和 RAG 还记录步骤数、工具数和检索上下文 Token。

采集窗口要覆盖工作日、周末、活动和月末等周期。只取一天平均会漏掉业务峰值。时间序列按分钟或更细粒度保留到达突发，再用小时和日汇总做长期趋势。数据缺失和采样率明确标记。

请求 Token 使用实际 Tokenizer 统计，模型升级后重新分桶。客户端声明的 `max_tokens` 用于预留，实际 output 用于结算；两者差值影响 Cache 和预算。取消请求记录已生成 Token 和后端是否真正停止。

隐私处理把用户与 Prompt 换成受控 tenant 和 Hash，不把内容导出到容量仓库。高基数 request ID 保留在 Trace 或抽样记录，Metric 只做聚合。原始业务数据访问有权限和保留期限。

生产数据存在幸存者偏差。已经被限流或超时的请求没有进入 Serving，若只看完成 usage 会低估真实需求。Gateway 拒绝、排队放弃和客户端重试要一起统计，区分“用户需求”和“系统实际处理”。

## 队列什么时候从吸收突发变成持续过载

有界队列吸收短暂到达峰值，让实例不用为每个尖峰立即扩容。只要峰值结束后服务率高于到达率，队列会回落。若长期 λ 大于有效 μ，队列长度和等待持续上升，再大队列也只是推迟失败。

可以观察队列斜率。到达和完成差持续为正，waiting Token 每分钟增加，说明系统不稳定。此时 p95 还可能暂时正常，因为早到请求先完成；等队列积累后延迟突然恶化。扩容或限流要在预算耗尽前触发。

Deadline 让过期请求退出队列，避免 GPU 处理用户已经放弃的工作。队列项保存接受时间、剩余 Token 估计、优先级和租户。调度器每次选择时丢弃过期项并写明确 canceled/expired 事件，账务释放预留。

优先队列可以保护在线请求，但低优先级也要防饥饿。离线任务设置最大等待、可检查点和独立容量窗口。高优先级流量持续占满时，低优先级按合同拒绝或延后，不能悄悄丢失。

队列压测使用开环发送，验证在安全到达率下回落，在超过能力时稳定拒绝，不发生进程 OOM。关闭客户端重试后先测系统本身，再开启受控重试观察放大。无限指数重试会把短故障变成长期过载。

## CPU、主存、网络和存储怎样进入容量表

CPU 负责 TLS、JSON、Tokenize、Scheduler、采样和流式编码。GPU 有余量而 CPU 达到 Throttling，TTFT 和事件 flush 仍会变慢。每实例记录 CPU 时间、Run Queue、Throttling 和 Tokenize 延迟，副本规格不能只写 GPU。

主存用于模型下载、权重加载暂存、Tokenizer、进程和缓存。滚动发布新旧实例并存时，Node 主存峰值可能先触发 OOM Kill。模型最终进入显存，也不代表加载过程不需要大主存。每个阶段的 RSS 与 Page Cache 要测量。

网络包含客户端 SSE、对象存储下载、跨卡/跨机通信和监控出口。大量流式小事件更受连接和系统调用影响，模型冷启动则可能占满对象存储带宽。多卡训练或推理还需要 RDMA/NCCL 指标，不能用公网带宽代替。

磁盘和对象存储决定镜像、模型与缓存。节点扩容同时拉取几十个模型会形成启动风暴，下载慢让 Ready 容量长时间低于 replicas。预热、分批和节点缓存要进入冷启动模型，缓存清理保留回滚版本。

容量表为每种资源写需求、测量、限制和告警。GPU 是最贵资源，但不是唯一瓶颈。增加 GPU 后 CPU、网络或存储不扩，会降低每卡有效 Goodput，单位成本反而上升。

## 多区域和故障域怎样计算可用容量

两个区域各承担 50% 流量，不表示任一区域只需一半容量。如果目标允许一个区域完全故障后另一边接管，接管区域需要额外余量或明确降级。跨区域模型、数据和 Secret 也要准备，不能只增加 GPU 数。

区域故障切流会在短时间产生突发，DNS、负载均衡和 Gateway 状态传播需要时间。预热实例、模型缓存和价格配置应提前存在。否则理论容量足够，冷启动期间仍大量超时。

故障域还包括 Node、机架、电源、网络和对象存储。十个副本都在同一 Node 不提供十副本可用性，跨 Zone 的 Pod 需要考虑模型卷和延迟。容量报告列出副本分布与共同依赖。

降级策略可以把长上下文限制降低、切备用小模型、关闭非关键工具或拒绝低优先级任务。每项改变用户合同，需预先测试和沟通。故障时临时拍板会导致质量、账务和权限不一致。

演练在候选或受控窗口模拟一个实例、一个 Node 和一个区域不可用，观察路由、队列、SLO、拒绝和恢复。未做区域级测试时，只能声明实例级余量，不能把 N+1 写成跨区域容灾。

## 容量计划怎样滚动更新而不是一次性文档

容量基线绑定模型 Revision、GPU、引擎、精度、并行、上下文和请求分布。任一项变化，选择相关压测重新运行。发布系统把候选 Goodput 和资源峰值写入版本记录，不用手工复制旧表。

每周或每月回顾预测与实际：到达率、Token、取消、拒绝、Ready 容量、Goodput、成本和 SLO。预测偏差按业务增长、请求形状或系统效率分类。单纯把偏差归为“流量波动”不会改善下一轮。

短期计划决定预热和 Autoscaler 参数，中期计划决定 Node Pool、GPU 采购和区域，长期情景评估模型变大、上下文增长与产品变化。不同时间尺度使用不同误差和审批，不能用长期预测直接控制今日副本。

容量变更要有回滚。Batch、并发、上下文和量化调整先在候选测试，逐步切流，监控 SLO、质量和成本。若结果变差，恢复旧参数和实例池。只扩大限额而不加容量，会把拒绝变成 OOM。

计划输出包含假设、数据时间窗、计算、测试、未验证项、过载行为、扩缩容和成本。数字到期或版本变化后标记 stale，避免半年后仍被当作当前承诺。

## 一次容量估算怎样从输入走到验证

输入是峰值 4 request/s、平均输入 600 Token、平均输出 150 Token，候选实例 Goodput 260 output tokens/s，并要求容忍一实例故障。平均输出压力约 600 output tokens/s，理论需要 `ceil(600/260)=3` 个实例，加入一实例故障得到至少 4 个。

这只是第一轮。按输入/输出联合分布生成开环压测，在 3、4、5 个实例下分别运行。若 4 个实例的 p95 TTFT 超目标或 KV Cache 接近上限，规划不能停在算术结果；增加实例、限制长请求或调整 Batch 后重测。

状态变化包括请求进入 Gateway、waiting 增长、实例 Batch 调度、SLO 内完成、取消和拒绝。压测输出保存每阶段 TTFT、TPOT、Goodput、Queue、Cache、错误和成本。一次故障演练删除一个 Ready 实例，剩余三实例应保持核心 SLO 或触发预定过载。

若队列持续增长，说明到达率超过稳定能力，这一阶段数据不能当长期容量。若 GPU utilization 只有 70% 但 TPOT 已超目标，说明当前 SLO 受其他资源或调度限制，不能继续加并发追求 100%。失败证据进入报告。

验证完成后形成容量区间、最大安全到达、过载响应、扩容时间和单位成本。当前文章没有在目标硬件执行这些数字，所有 Goodput、价格与副本只用于演示方法。真实上线前必须用目标模型、GPU、引擎、配置和请求分布重做。

最后用生产旁路或小比例流量校准。压测客户端的网络、合成 Prompt 和缓存命中可能与真实用户不同，候选 Goodput 只能作为上界或区间。观察实际到达、排队与 SLO，逐步调整副本和准入，不一次把压测极限全开放。

校准期间每次只改一个主要参数，保留旧配置和实例。若增加 Batch 后总吞吐上升但 p95 TTFT 变差，容量目标应按 SLO 选择较低点；若限制长请求后拒绝率上升，产品侧需要明确新的合同，而不是把拒绝从报表中删掉。

容量评审还要检查请求之间是否独立。会话粘性、Prefix Cache、相同文档和工具调用可能让真实流量有相关性，随机打乱后压测会失去热前缀和突发模式。测试集应同时保留冷缓存、热缓存和混合场景，分别报告，不把最有利的热缓存数字当成全部请求能力。

模型升级后即使参数量相同，Tokenizer、架构和 Kernel 也会改变输入 Token、KV Cache 和服务率。旧容量表只能作为对照，先在候选上测新版本，再决定是否沿用副本与限额。未完成校准前保留旧路由和过载边界。

## 机制复核：容量规划是什么？怎样从请求、队列和延迟估算 GPU 与成本
基础设施文章最终要回答资源从哪里来、由谁调度、失败如何回收。把模型、GPU、网络、队列、制品和数据的生命周期画成一条链，分别记录容量单位、版本身份、健康信号和所有权。单一利用率或一次成功启动不能证明系统可用。

落地验证分成离线配置检查、隔离环境运行和候选发布回归。至少覆盖资源不足、进程重启、重复任务、网络抖动和旧版本并存，并保留命令输出、指标时间窗和回滚点。生产环境只运行已构建产物，构建和压力实验放在独立环境。

性能数字需要说明硬件、输入规模、并发模型和测量口径。观察到长尾或成本异常时，先定位排队、计算、传输、存储和重试分别占用的时间，再决定扩容、限流、批处理或降级。
