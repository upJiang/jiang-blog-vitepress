# TTFT、TPOT、吞吐、队列、容量与成本

压测报告写着“支持 100 并发”，却没有输入长度、输出长度、到达率、模型、GPU、TTFT 和错误率。这个数字无法迁移到任何业务。容量工程要先固定请求分布和 SLO，再用队列、服务时间和成本解释系统能接多少什么样的请求。

## 先把负载写清楚

| 维度 | 至少记录 |
| --- | --- |
| 请求形状 | 输入/输出 Token 分布、工具/RAG 次数、流式比例 |
| 到达方式 | 开放负载到达率，或闭合负载并发数 |
| 系统版本 | 模型 Revision、Serving、GPU、参数和入口 |
| 目标 | TTFT/TPOT 分位数、错误率、队列年龄、成本 |

100 个同时连接不等于每秒 100 个请求。开放负载按时间到达，闭合负载由固定客户端数循环发请求，两者在排队饱和后的行为不同。压测报告必须说明负载模型。

## Little’s Law 用来检查自洽

稳定系统近似满足 L = λW：平均并发 L 等于到达率 λ 乘以平均响应时间 W。它不能直接给出 GPU 容量，却能发现报告中的口径矛盾。例如到达率、队列长度和观测到的延迟无法同时成立时，先检查采样和时间窗口，而不是马上扩容。

```text
示例推演（不是实测）：
到达率 λ = 2 req/s
平均在系统请求数 L = 10
则平均响应时间 W ≈ 5 s
若报告同时声称 W=1 s，需要重新核对统计口径。
```

示例只演示公式和单位，不代表任何模型性能。真实容量还要看 P95/P99、长尾输入、失败和资源上限。

## TTFT、TPOT 和吞吐要分开

TTFT 受排队、Tokenize、Prefill 和首事件影响；TPOT 反映 Decode 间隔；输出 Token/s 可以按单请求或实例总量统计。总吞吐上升可能伴随 TTFT 变差，不能用一个平均延迟替代所有 SLO。

## 成本从一次 attempt 算起

| 成本项 | 计量单位 | 常见漏算 |
| --- | --- | --- |
| 托管模型 | 输入/输出 Token、请求或时间 | 重试和失败请求 |
| 自托管 GPU | 实例小时、空闲和峰值副本 | 模型加载、备用容量 |
| 数据设施 | 向量、对象、网络、日志 | 过期版本和观测存储 |
| 工程预算 | 压测、评测、运维人力 | 回滚与灾备演练 |

## 容量结论必须带边界

::: warning
**不填虚构数字**

没有目标硬件和真实请求样本时，只能给出测量模板、公式和扩容信号。容量结论应附模型、版本、硬件、时间窗口和过载行为。下一篇从一个不可信输入穿过网关、Agent 和 RAG，建立平台安全边界。
:::

## 压测要故意包含失败形状

只用短 Prompt 和固定输出会得到一个漂亮但脆弱的数字。请求集应包含典型、长上下文、流式慢消费者、取消、缓存命中/未命中和 RAG/工具路径，并分别记录结果。过载阶段要观察拒绝是否及时、队列是否有上限、取消是否释放资源，而不是只追求最高吞吐。

压测结束后把原始配置、生成器版本、随机种子、指标定义和数据脱敏策略留档。下一次模型、引擎或 GPU 变更后，才能做可比的回归，而不是重跑一次完全不同的实验。

## 成本优化不能绕过可靠性目标

把 max output 降到很小、让请求更早超时或强制命中缓存，都可能让账面成本下降，却把失败转移给用户。成本方案应同时报告成功率、截断率、重试率和业务质量，确认节省不是由拒绝更多请求换来的。

自托管与托管的比较也要包含备用容量和运维复杂度。GPU 空闲看似浪费，可能是在换取低 TTFT 和故障余量；托管按 Token 计费看似简单，也要考虑峰值价格、速率限制和数据边界。
